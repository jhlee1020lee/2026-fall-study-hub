### Instruction Set Architecture(ISA; 명령어 집합 구조)와 Microarchitecture(마이크로아키텍처)

<span id="isa와-microarchitecture"></span>

[[concepts/instruction-set-architecture|Instruction Set Architecture]]는 program이 관찰하고 제어할 수 있는 기계 동작의 약속이다. Instruction Set(명령어 집합)은 그중 제공되는 명령의 목록이다. ISA를 설명하려면 명령의 목록 외에 데이터 표현, register(레지스터), Program Counter(PC; 프로그램 카운터), encoding(이진 부호화), 보호·특권 동작 등을 함께 봐야 한다. 자료는 software convention도 넓은 인터페이스 논의에 포함하지만, 소프트웨어의 관례와 하드웨어가 강제하는 규칙을 무조건 같은 것으로 취급하지는 말자. [M01 p.5-6] [M01 p.9] [M01 p.28]

[[concepts/microarchitecture|Microarchitecture]]는 이 약속을 실현하는 내부 조직이다. “덧셈 결과를 어느 register에 남긴다”는 ISA 의미와 “그 연산에 몇 cycle이 걸리는가”라는 구현 질문은 서로 다르다. p.5의 x86-64, Alder Lake, Zen 4, cache 용량은 이 차이를 보여 주는 자료 속 사례이며 최신 제품 비교표가 아니다. [M01 p.5]

<span id="핵심-그림-직접-읽기"></span>

먼저 p.4의 system organization 그림을 읽으면 CPU 내부의 ALU, Register File(RF; 레지스터 파일), cache가 memory bus를 통해 DRAM 및 I/O bridge 쪽과 연결된다. I/O bus 아래에는 disk, video, keyboard/mouse, network 장치가 놓인다. 이 그림은 프로그램이 사용하는 CPU·memory가 더 큰 입출력 시스템 안에 있다는 배경이다. Bus에 적힌 GB/sec·100MB/sec는 자료의 설명용 표기이며 모든 시스템의 실측 속도가 아니다. [M01 p.4]

### Stored-program과 Programmer Visible State(프로그래머 가시 상태)

<span id="stored-program과-programmer-visible-state"></span>

[[concepts/von-neumann-architecture|Von Neumann architecture(폰 노이만 구조)]]와 연결되는 stored-program 관점에서는 instruction(명령어)과 data를 binary(이진 표현)로 memory에 둔다. 기계는 PC가 가리키는 instruction을 가져와 정해진 state 변화를 만들고 다음 PC를 선택한다. 이 추상적 순서를 실제 CPU 내부가 언제나 한 단계씩만 처리한다는 뜻으로 읽으면 안 된다. [M01 p.7] [M01 p.10]

기출 Q1은 instruction과 data의 저장 관계를 구분하는 개념을 요구한다. 여기서는 정의를 근거로 설명할 수 있다. 다만 stored-program이라는 이유만으로 운영체제가 code 영역 쓰기를 언제나 허용한다고 결론내릴 수는 없다. 자료의 보호·특권 논의와도 구분해야 한다. [M01 p.7] [M01 p.9] [EX:ca_2025_2_midterm_q01 p.2](exam_questions/ca_2025_2_midterm_q01)

**p.10의 state 그림:** 왼쪽은 `M[0]`부터 `M[N-1]`까지 주소로 고르는 memory, 오른쪽 위는 ISA가 부여한 이름으로 고르는 register, 오른쪽 아래는 현재 instruction의 memory address를 가진 PC다. 크기와 배치보다 **무엇으로 저장 위치를 지정하는지**가 중요하다. register 상자에 있는 `32b~64b`는 그림의 설명 범위이며 모든 ISA의 모든 register가 같은 폭이라는 규칙이 아니다. PC 역시 instruction 자체가 아니라 그것을 가리키는 주소다. [M01 p.10]

#### 1. State transition을 완성하는 세 질문

Instruction을 읽을 때 먼저 **어디에서 어떤 값을 읽는가**, 다음으로 **어디에 어떤 값을 쓰는가**, 마지막으로 **다음 PC는 무엇인가**를 묻는다. 세 질문 중 하나를 생략하면 상태 설명이 불완전해진다. 예를 들어 `lw`는 memory를 읽지만 memory를 변경하지 않고, `sw`는 register의 값을 memory에 쓰지만 그 source register의 값을 지우지 않는다. [M01 p.11] [M01 p.24]

편집용 수학 모델로 $S=(PC,R,M)$을 두면 instruction $I$의 의미를 $S'=T_I(S)$로 적을 수 있다. 여기서 $R$은 register 값들의 모음, $M$은 memory 내용이다. 이 모델은 이번 예제에서 관심 있는 정상 실행 상태만 모은 것으로, exception·privilege·동시 실행의 모든 세부사항을 명세한 것은 아니다. ISA가 정의하는 결과와 그 결과를 내는 회로를 분리하기 위한 표현이다. [M01 p.9-11]

p.11의 “atomic”이라는 설명은 이 입문 단계에서 명령 단위의 상태 변화를 생각하도록 돕는다. 이를 `load; add; store` 세 줄 전체가 다른 thread에 대해 하나의 atomic operation(원자적 연산)이 된다는 보장으로 확대하면 안 된다. Q18은 별도의 동기화 문제이며 reservation, 조건부 store, 반복 제어 같은 선수 개념이 더 필요하다. 여기서는 그 문제의 완전한 풀이를 현재 진도에 포함하지 않는다. [M01 p.11] [M01 p.24] [EX:ca_2025_2_midterm_q18 p.9](exam_questions/ca_2025_2_midterm_q18)

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| `lw; addi; sw` 전체가 atomic이다. | 명령 단위 추상화와 다중 명령 동기화는 다른 문제다. | [M01 p.11] |

### Machine Code(기계어), Assembly Code(어셈블리 코드), Operand(피연산자)

<span id="machine-code와-assembly-code"></span>

Machine Code(기계어)는 instruction을 binary로 표현한 것이고, Assembly Code(어셈블리 코드)는 사람이 읽도록 적은 instruction 표기다. Assembler(어셈블러)는 assembly를 machine code로 번역한다. Pseudo-instruction(의사 명령어)은 여러 machine instruction으로 확장될 수 있으므로 assembly 한 줄을 언제나 기계 명령 한 개로 세면 안 된다. p.8의 여러 ISA manual 사진은 이 programmer-facing 명세가 실제 문서로 제공된다는 점을 보여 준다. 해당 manual 전체를 읽은 것은 아니다. [M01 p.8] [M01 p.28]

<span id="instruction-class와-operand"></span>

Operand(피연산자)는 instruction이 사용하는 값 또는 그 값을 지정하는 대상이다. Arithmetic/logic instruction은 값을 계산하고, data movement는 값을 옮기고, control flow는 조건과 목표 주소에 따라 PC를 바꾼다. “결과를 저장한다”는 표현도 구체적으로 어느 register인지 어느 memory location인지 지정해야 완성된다. [M01 p.11]

자료의 operand 개수 비교는 `OP in2`, `OP inout, in2`, `OP out, in1, in2`다. 첫 형태에는 accumulator 같은 암묵적 대상이 필요하고, 두 번째는 입력과 출력이 겹치며, 세 번째는 출력과 두 입력을 명시한다. p.13의 표기는 개념 비교용으로, 모든 명령이 반드시 같은 수의 operand를 갖는다는 규칙이 아니다. [M01 p.12-13]

### Addressing mode(주소 지정 방식)와 Load-store(적재·저장)

<span id="addressing-mode와-load-store-architecture"></span>

Addressing mode(주소 지정 방식)는 memory operand(메모리 피연산자)가 있는 위치를 표현하는 방법이다. 주소를 instruction에 직접 적는지, register에서 얻는지, base에 offset을 더하는지, memory에서 포인터를 한 번 더 읽는지 구별한다. `GPR[x5]`는 register 내용, `MEM[1000]`은 주소 1000의 내용이다. 숫자 자체와 대괄호로 읽은 값을 분리해서 써야 한다. [M01 p.14-15]

Load-store는 “ALU가 memory를 전혀 필요로 하지 않는다”가 아니라 **일반 ALU instruction에 직접 memory operand를 넣지 않는다**는 구분이다. `addi`의 상수 입력은 memory operand가 아니다. Q2의 요구와 현재 자료가 직접 맞닿는 지점이며, 아래 예제에서 load/연산/store의 역할을 따로 확인한다. [M01 p.13] [M01 p.24] [EX:ca_2025_2_midterm_q02 p.2]

#### 2. Address와 Value를 분리하는 방법

`LW rt, offset(rbase)`라는 자료의 일반형은 먼저 `GPR[rbase] + offset`을 계산해 주소를 만들고, 그 주소의 memory 내용을 읽어 `GPR[rt]`에 넣는다는 뜻이다. 주소 계산이 덧셈이라고 해서 “load가 memory 데이터에 offset을 더한다”고 해석하면 틀린다. 덧셈은 **어디를 읽을지** 결정한다. [M01 p.15]

| 방식 | 목적 register에 들어갈 값 | 주소를 얻는 과정 |
|---|---|---|
| Absolute | `MEM[address]` | 명시한 주소를 사용한다. |
| Register indirect | `MEM[GPR[base]]` | register 내용이 주소다. |
| Displaced / based | `MEM[GPR[base] + offset]` | base 값에 offset을 더한다. |
| Indexed | `MEM[GPR[base] + GPR[index]]` | 두 register 값을 더한다. |
| Memory indirect | `MEM[MEM[GPR[base]]]` | 첫 memory 읽기로 다음 주소를 얻는다. |

이 표는 p.15의 **여러 ISA를 비교하는 notation**이다. 표의 `Indexed`나 `Memory indirect` 구문을 그대로 RISC-V assembler에 넣어도 된다는 뜻이 아니다. p.15의 `GRP`는 문맥상 `GPR` 오타로 바로잡아 표시했다. [M01 p.15]

RISC-V RV32I에서 기본 load/store의 주소는 base register에 sign-extended offset을 더해 계산하며 일반 산술 명령에는 register 또는 immediate(즉시값) 입력이 쓰인다. 이 부분만 공식 ISA 문서로 추가 대조했다. [RISC-V RV32I: integer operations and loads/stores](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)

#### B. Addressing mode 비교용 새 연습

이 숫자는 원자료를 그대로 옮긴 시험문제가 아니라 p.15를 이해하기 위한 편집 예제다. 모두 decimal이며 `GPR[base]=1000`, `GPR[index]=8`, `offset=4`, `MEM[1000]=2000`, `MEM[1004]=17`, `MEM[1008]=23`, `MEM[2000]=99`라 하자. 모든 접근은 유효하다고 가정한다. [M01 p.14-15]

| 읽기 방식 | 실제 계산 | 읽은 값 | Data memory 읽기 수 |
|---|---|---|---|
| Absolute 1004 | `MEM[1004]` | 17 | 1 |
| Register indirect | `MEM[1000]` | 2000 | 1 |
| Based, offset 4 | `MEM[1000+4]` | 17 | 1 |
| Indexed | `MEM[1000+8]` | 23 | 1 |
| Memory indirect | `MEM[MEM[1000]] = MEM[2000]` | 99 | 2 |

읽기 수는 instruction fetch와 cache 내부 동작을 제외한 **개념적 data memory 읽기**만 센 것이다. Register indirect의 결과 2000이 우연히 또 다른 주소로 쓸 수 있는 값이더라도, 해당 mode에서 자동으로 한 번 더 읽지는 않는다. Memory indirect를 명시했을 때만 두 번째 읽기를 한다. [M01 p.15]

#### A. 자료의 RISC-V 실행을 끝까지 추적하기

초기 상태는 `PC=0x1000`, `GPR[x10]=0x2000`, `MEM[0x2000]=41`이다. 여기서 `MEM`은 예제의 word 값을 표시하는 추상적 표기다. 유효한 주소에서 예외 없이 실행하고 다른 thread가 끼어들지 않는다고 가정한다. 세 instruction의 주소와 PC 증분은 자료에 주어진 그대로다. [M01 p.24]

```asm
0x1000: lw   x5, 0(x10)
0x1004: addi x5, x5, 1
0x1008: sw   x5, 0(x10)
```

| 완료한 단계 | 다음 PC | `GPR[x5]` | `GPR[x10]` | `MEM[0x2000]` | 직접 바뀐 데이터 |
|---|---|---|---|---|---|
| 초기 | `0x1000` | 미지정 | `0x2000` | 41 | 없음 |
| `lw` | `0x1004` | 41 | `0x2000` | 41 | x5 |
| `addi` | `0x1008` | 42 | `0x2000` | 41 | x5 |
| `sw` | `0x100c` | 42 | `0x2000` | 42 | memory |

`lw`의 주소 계산은 `0x2000 + 0`이다. 그 **주소**를 x5에 넣는 것이 아니라 그곳의 **내용 41**을 읽는다. `addi`까지 실행했을 때 memory는 여전히 41이다. 마지막 `sw`가 있어야 memory가 42가 된다. 이 세 줄에서는 다음 PC가 매번 4씩 증가하지만 branch와 다른 길이의 instruction까지 포함하는 보편 규칙으로 외우지 않는다. [M01 p.11] [M01 p.24]

#### C. 기출의 배열 저장 요구를 현재 범위로 분해하기

Q12는 조건에 따라 배열에 값을 저장하는 assembly 번역을 요구한다. 현재 자료로는 **조건이 고르는 값**, **배열의 base address**, **최종 store의 목적지**를 분리하는 연습이 가능하다. 다만 branch instruction 선택과 전체 control flow를 완성하는 일은 추가 ISA 학습이 필요하다. 원문 전체 풀이 대신 다음 새 연습으로 범위를 제한한다. [M01 p.11] [M01 p.15] [EX:ca_2025_2_midterm_q12 p.4](exam_questions/ca_2025_2_midterm_q12)

편집 예제: 이미 선택된 값이 x5에 9, 배열 base가 x10에 `0x3000`으로 들어 있다고 하자. `sw x5, 0(x10)` 뒤에는 `MEM[0x3000]=9`이고 x10은 여전히 `0x3000`이다. “배열에 9를 넣었다”를 “base register가 9로 바뀌었다”로 바꾸면 안 된다. 이 예제는 word 저장 하나만 다루며 C type 크기나 전체 조건 분기 번역을 검증한 것은 아니다. [M01 p.24]

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| `GPR[x10]`과 `MEM[GPR[x10]]`은 같다. | 전자는 register 값, 후자는 그 값을 주소로 한 memory 내용이다. | [M01 p.14-15] |

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| Load-store이면 `addi`도 불가능하다. | Immediate와 직접 memory operand는 다르다. | [M01 p.13] [M01 p.24] |

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| p.15의 모든 `LW` 구문은 RISC-V 문법이다. | ISA 비교용 notation이다. | [M01 p.15-16] |

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| 모든 instruction 뒤 PC는 항상 +4다. | 예제의 세 순차 명령에 적용된 규칙이다. | [M01 p.11] [M01 p.24] |

### Separate compilation과 Symbol resolution(심볼 해결)

<span id="3-separate-compilation에서-symbol-resolution으로"></span>

Linker(링커)는 여러 object file(목적 파일)의 symbol(심볼) 연결과 배치를 해결한다. [M01 p.18-24]

p.19의 예제는 `main.c`의 `buf[2] = {1, 2}`와 `swap.c`의 `swap()`을 분리한다. `main`은 다른 파일에 있는 `swap`을 호출하고, `swap.c`는 `extern int buf[]`로 다른 파일의 배열을 참조한다. 각각을 따로 번역하더라도 최종적으로는 “이 이름이 어느 정의를 뜻하는지” 연결해야 한다. 이것이 Symbol resolution(심볼 해결)의 역할이다. [M01 p.19-21]

| 자료 속 이름 | p.20에서 읽을 분류 | 핵심 구별 |
|---|---|---|
| `buf`, `main` in `main.c` | Global | 이 파일이 제공하는 정의다. |
| `swap` reference in `main.c` | External | 다른 파일의 정의를 연결해야 한다. |
| `buf` in `swap.c` | External | `main.c`의 배열을 참조한다. 새 배열을 하나 더 만드는 뜻이 아니다. |
| `bufp0`, `swap` in `swap.c` | Global | 외부 연결 관점에서 보이는 정의다. |
| `static int *bufp1` | Local | 파일 내부의 linker symbol이다. |
| 함수 내부 `temp` | 일반 local variable | 이 예제의 파일 간 symbol 연결 대상이 아니다. |

`bufp1`의 local symbol과 `temp`의 local variable을 같은 의미로 읽지 않는 것이 중요하다. p.20은 linker가 `temp`의 파일 간 연결을 처리하지 않는다는 점을 직접 표시한다. 이것을 debug 정보에도 `temp`라는 이름이 절대로 없다는 주장으로 확대하지는 않는다. 또한 p.19의 코드는 개념 그림이다. 현재 compiler에서 그대로 검증된 완성 C 프로젝트를 제공하는 것은 아니다. [M01 p.19-20]

그림 속 `swap()`의 데이터 흐름도 읽어 보자. `bufp0`는 첫 원소를 가리키고, 함수는 `bufp1`에 두 번째 원소의 주소를 넣는다. 이어 첫 원소의 값 1을 `temp`에 보관하고, 두 번째 값 2를 첫 위치에 쓴 다음, 보관한 1을 두 번째 위치에 쓴다. 추상적 실행 결과는 `{2, 1}`이다. `temp` 없이 첫 위치를 먼저 덮어쓰면 원래 값을 잃는다는 점과, 포인터 값은 element의 값과 다르다는 점을 동시에 보여 준다. [M01 p.19]

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| `static bufp1`과 `temp`는 linker에게 같은 local이다. | 파일 local symbol과 함수 내부 변수를 구분한다. | [M01 p.20] |

### Relocation(재배치)과 Loading(적재): 파일에서 실행 상태까지

<span id="4-relocation과-loading은-서로-다른-문제다"></span>

Relocation(재배치)은 합쳐진 배치에 맞추어 코드와 데이터의 위치 및 참조를 조정하는 단계다. `bufp0 = &buf[0]`의 핵심은 값 1을 저장하는 것이 아니라 `buf[0]`의 **주소**를 저장한다는 점이다. 따라서 배열이 어디에 놓이는지와 포인터가 담을 값은 연결되어 있다. `main`의 `swap` 호출도 실행 코드의 위치와 관계가 있다. [M01 p.19] [M01 p.21-22]

p.21의 compiler driver 예제는 여러 번역 단계와 linker를 한 명령 뒤에 묶어 보여 준다. 도식이 두 `.o`를 하나의 프로그램에 결합한다는 사실과, 임의 환경에서 같은 명령이 모든 library까지 완전히 static link한다는 주장은 다르다. 이 노트에서는 명령 실행이나 library 결합 형태를 실측하지 않았다. [M01 p.21]

Loading(적재)은 loader(로더)가 실행에 필요한 memory image(메모리 이미지)를 준비하는 단계다. p.23의 `.text`, `.rodata`, `.data`, `.bss`와 heap/stack 그림을 읽되, **파일의 section과 실행 시 segment를 동일시하지 말자**. ELF의 program header가 loadable segment를 기술한다. 파일 크기보다 memory 크기가 큰 loadable segment의 나머지는 0으로 채워진다. [M01 p.23] [ELF Program Header](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch5.pheader.html)

추가 확인: `.bss`는 실행 memory에는 공간을 차지하지만 초기화 값 전체를 파일에 저장하는 영역은 아니다. ELF에서 `SHT_NOBITS`이며 시작 시 0으로 초기화된다. 그래서 p.22-23의 `.bss` 상자를 “파일에 그만큼의 0 바이트가 들어 있다”로 읽으면 안 된다. [ELF Sections: .bss](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch4.sheader.html)

**p.22의 relocation 그림:** 왼쪽에는 system, `main.o`, `swap.o`가 각각 `.text`, `.data`, 일부 `.bss`를 가진다. 오른쪽에서는 관련 영역이 실행 파일 안에 모인다. `main()`에서 `swap()`을 부르는 참조와 `buf`를 가리키는 포인터는 최종 배치를 반영해야 한다. 화살표는 단순한 파일 복사를 넘어, 분리되어 있던 코드·데이터와 그 참조를 연결한다는 의미다. `.symtab`과 `.debug`도 표시되어 있어 실행 instruction 외에 도구용 정보가 있음을 보여 준다. [M01 p.22]

**p.23의 ELF loading 그림:** 왼쪽의 ELF header·program header·section 목록과 오른쪽의 실행 memory를 구분한다. 오른쪽은 code/read-only data, read/write data, heap, shared-library 영역, stack 등을 나눈다. stack과 heap의 화살표는 이 그림에서 증가 방향을 나타낸다. `0x08048000`, `0xc0000000`, `%sp`는 그림의 특정 32-bit 환경 예시이지 RISC-V 전체의 고정 배치가 아니다. 또한 왼쪽에 상자가 있다고 해서 그 모든 바이트가 실행 memory에 통째로 복사된다는 뜻은 아니다. [M01 p.23]

공개 그림 카드에서 원자료 그림 보기: [[page_cache/computer_architecture/lec.02/page-010|M01 p.10: State]] · [[page_cache/computer_architecture/lec.02/page-022|M01 p.22: Relocation]] · [[page_cache/computer_architecture/lec.02/page-023|M01 p.23: Loading]]. 이 세 page cache는 노트에 연결된 그림 카드이며, 원본 PDF 전체를 게시한 것은 아니다.

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| `.bss` 그림의 크기만큼 파일에 0이 저장된다. | Memory 공간과 파일 payload를 구분한다. | ELF Sections 추가 대조 |

| 흔한 오독 | 이 노트에서의 교정 | 근거 |
|---|---|---|
| Loader가 `addi`를 실행해 42를 만든다. | Loader는 memory 준비, ISA는 instruction의 실행 의미를 정한다. | [M01 p.24] |

### ISA design(ISA 설계): 확장성과 구현의 경계

<span id="5-isa를-설계한다면-무엇을-남길-것인가"></span>

p.26은 지금 당장 가능한 최적화만이 아니라 장기간의 compatibility(호환성)와 scalability(확장성)를 요구한다. 저장 용량이나 CPU·I/O 수를 확장할 여지, 서로 다른 속도로 동작하는 component, encoding에 미래 용도로 남겨 둔 비트가 예시다. 남는 비트를 당장 모두 써 버리면 현재 표현력은 늘 수 있지만 미래 확장의 선택지는 줄어든다는 것이 편집상 도출되는 trade-off다. p.26의 수명 숫자는 자료의 설계 논의이지 모든 ISA의 유효기간이 아니다. [M01 p.9] [M01 p.25-26]

General purpose(범용성)는 한 종류의 일뿐 아니라 규모와 분야가 다른 여러 application을 지원한다는 목표다. 자료는 bit pattern에 항상 문자 같은 특정 의미를 강제하지 않는 것, 일반적인 bit 연산, 세밀한 memory addressability를 그 방법으로 든다. 다만 integer와 floating-point처럼 연산이 요구하는 해석은 필요하다. ML accelerator는 범용성 일부를 특정 작업의 performance와 교환하는 설계 방향으로 제시된다. 모든 특수 장치가 모든 작업에서 더 빠르다는 뜻은 아니다. [M01 p.27]

p.17의 ISA 변화는 기술 제약, assembly programming, microprogramming, cache, compiler를 함께 보는 역사적 설명이다. RISC와 CISC를 단순한 “좋음/나쁨”으로 정리하지 않는다. p.16의 fixed-length instruction 설명은 **MIPS 사례**이며 이 표 하나로 모든 ISA의 instruction 길이를 일반화하지 않는다. [M01 p.16-17]

#### D. 새로운 Instruction을 제안할 때의 질문

### 녹음 없는 회차의 검증 한계

**STT 처리 상태:** 원본 녹음과 STT가 없으므로 보정할 STT도 없다. 교수 발언, 질문, 중요도 강조, 실제 진도 끝, 출석 당시 상황은 확인하지 못했다. STT의 “불명확 구간 0개”나 “보정 완료”로 기록하지 않는다. 앞으로 녹음 또는 검증 가능한 수업 메모가 들어오면 별도 근거로 검토해야 한다.

### 이전 강의·선수학습과 연결

[[courses/computer_architecture/lectures/2026-09-01-lecture-01|1강]]에서 ISA와 구현의 경계, stored-program(저장 프로그램) 관점, CPU·memory·I/O의 큰 구성을 다뤘다. 이번 자료는 그 경계를 구체화한다. “CPU가 프로그램을 실행한다”를 “instruction이 architectural state(구조적으로 정의된 상태)를 정해진 규칙으로 바꾼다”로 바꾸어 설명하는 단계다. [M01 p.4-10]

CPU 내부 cache(캐시) 크기나 실행 방식은 바뀔 수 있지만, 동일한 ISA 동작을 구현한다면 프로그램이 의존하는 명령의 의미는 유지되어야 한다. 단, ISA라는 이름이 같다는 말만으로 운영체제·라이브러리·확장 명령까지 다른 모든 실행 환경의 binary compatibility(바이너리 호환성)가 자동 보장되지는 않는다. 이 노트에서는 공통으로 지원하는 instruction의 의미와 구현을 구분하는 데 집중한다. [M01 p.5-6] [M01 p.9]

프로그래밍에서의 변수·배열·함수도 연결된다. 변수의 저장 위치는 register 또는 memory로 내려가고, 배열 접근은 주소 계산과 load/store로 표현된다. 다른 소스 파일에 정의된 함수나 전역 데이터는 linking 단계에서 서로 연결되어야 한다. 즉, ISA 단원 중간에 linking/loading이 나오는 이유는 “실행할 instruction과 초기 데이터가 어디서 왔는가?”를 설명하기 위해서다. [M01 p.18-24]

### 배운 개념의 연결

```text
C source
  → Compiler → Assembly → Assembler → Relocatable object
                                      + Other objects
                                           ↓ Linker
                                      Executable file
                                           ↓ Loader
                                      Initial memory/state
                                           ↓ ISA instruction semantics
                                      Next PC, registers, memory
```

위 그림의 번역·연결·적재 흐름은 p.18을, 마지막 state 변화는 p.24를 결합해 다시 그린 것이다. 특정 운영체제의 모든 startup 과정이나 dynamic linking을 전부 그린 것은 아니다. [M01 p.18] [M01 p.24]

- [[concepts/instruction-set-architecture|Instruction Set Architecture]]: state와 transformation의 계약을 정의한다.
- [[concepts/microarchitecture|Microarchitecture]]: 그 transformation을 구현하되 내부 처리 시간과 자원 배치가 달라질 수 있다.
- [[concepts/von-neumann-architecture|Von Neumann architecture]]: memory에 놓인 instruction과 data에서 실행을 출발시킨다.

복습 연결은 `state → operand → address → load/ALU/store`와 `symbol → relocation → loading → state`의 두 줄로 잡으면 좋다. 두 줄은 p.24에서 만난다. [M01 p.10-15] [M01 p.19-24]

## 핵심 요약

<span id="수업-직후-10분-복습"></span>

- ISA는 가시 상태와 명령의 의미를 정하고, microarchitecture는 이를 구현한다.
- 읽는 값·쓰는 위치·다음 PC를 추적한다. 주소를 담은 register 값과 그 주소의 memory 내용은 다르다.
- Load/store는 memory 접근과 ALU 연산을 분리한다. Immediate 입력은 그 원칙의 위반이 아니다.
- Linker는 symbol·배치를 연결하고 loader는 실행 memory를 준비한다. Instruction 실행과 구분한다.
- File section과 실행 segment, 명령 개수와 실행시간을 구분한다. 이번 범위는 자료 기반이며 실제 발화가 검증된 것이 아니다.

[M01 p.5-11] [M01 p.10] [M01 p.14] [M01 p.24] [M01 p.13] [M01 p.16] [M01 p.18-24] [M01 p.5] [M01 p.15]

## 회상·연습문제

<span id="능동회상-문제"></span>

아래는 세 단계의 편집 문제다. 기출에서 요구하는 구별을 활용했지만 시험 원문이나 제공 답안을 복제한 것은 아니다. 답을 펼치기 전에 주소·값·변경 위치를 직접 써 본다.

### 1단계: 개념 확인

**1. ISA와 microarchitecture를 “명령 의미”와 “구현”으로 구분해 설명하라.**

<details><summary>정답</summary>

ISA는 프로그램에 보이는 state와 명령의 효과를 정하고, microarchitecture는 그 효과를 실제로 구현하는 조직이다. 같은 덧셈 의미를 서로 다른 cycle 수와 내부 자원으로 구현할 수 있다. [M01 p.5-6]

</details>

**2. PC에 들어 있는 것은 instruction 자체인가, instruction의 주소인가?**

<details><summary>정답</summary>

자료의 state 그림에서 PC는 현재 instruction의 memory address를 갖는다. Instruction의 binary 내용과 그것을 가리키는 주소는 다르다. [M01 p.10]

</details>

**3. `addi x5, x5, 1`은 왜 load-store 원칙과 충돌하지 않는가?**

<details><summary>정답</summary>

1은 immediate이지 memory operand가 아니다. x5의 값과 instruction에 포함된 상수를 연산하므로 ALU가 data memory를 직접 읽는 형태가 아니다. [M01 p.13] [M01 p.24] [EX:ca_2025_2_midterm_q02 p.2]

</details>

**4. Stored-program 관점에서 instruction과 data의 관계를 말하라.**

<details><summary>정답</summary>

둘 다 binary로 memory에 저장될 수 있다. 그래서 instruction도 memory에서 fetch한다. 하지만 이것이 모든 code 영역의 쓰기 허용이나 cache의 내부 구성을 자동 결정하지는 않는다. [M01 p.7] [EX:ca_2025_2_midterm_q01 p.2](exam_questions/ca_2025_2_midterm_q01)

</details>

### 2단계: 적용과 추적

**5. 예제 A에서 `addi` 직후 PC와 x5, memory 값은 각각 무엇인가?**

<details><summary>정답</summary>

PC는 `0x1008`, x5는 42, `MEM[0x2000]`은 아직 41이다. Register의 새 값을 memory에 반영하는 `sw`는 아직 실행하지 않았다. [M01 p.24]

</details>

**6. 예제 B에서 register indirect는 2000, memory indirect는 99가 되는 이유는?**

<details><summary>정답</summary>

전자는 `MEM[1000]`을 한 번 읽어 2000을 얻는다. 후자는 그 2000을 다시 주소로 사용해 `MEM[2000]`을 읽는다. 결과가 주소처럼 보인다는 이유만으로 dereference 횟수가 자동 증가하지 않는다. [M01 p.15]

</details>

**7. 예제 C의 store가 x10까지 9로 바꾸지 않는 이유는 무엇인가?**

<details><summary>정답</summary>

x10은 주소 계산용 source register다. `sw x5, 0(x10)`의 데이터 목적지는 `MEM[GPR[x10]+0]`이며 x10이 아니다. 따라서 memory에는 9가 기록되고 base는 유지된다. [M01 p.24] [EX:ca_2025_2_midterm_q12 p.4](exam_questions/ca_2025_2_midterm_q12)

</details>

**8. `main.c`와 `swap.c`를 각각 번역했는데 왜 linking이 추가로 필요한가?**

<details><summary>정답</summary>

다른 파일의 `swap` 정의와 `buf` 정의를 참조하기 때문이다. Symbol을 대응시키고 합쳐진 배치에 맞는 코드·데이터 참조를 마련해야 한다. 별도 `.o` 생성만으로 파일 간 연결 문제가 모두 끝나지는 않는다. [M01 p.19-22]

</details>

### 3단계: 조건 변화와 설계 판단

**9. 예제 A에서 마지막 store를 생략하면 “memory를 1 증가”시킨 프로그램인가?**

<details><summary>정답</summary>

아니다. x5에는 42가 남아도 memory는 41이다. 요구사항이 어느 state location의 변화인지부터 확인해야 한다. [M01 p.24]

</details>

**10. 세 instruction을 한 새 instruction으로 묶으면 반드시 세 배 빨라지는가?**

<details><summary>정답</summary>

아니다. Instruction 수와 실행시간은 같지 않다. 새 instruction의 내부 처리, memory 접근과 clock 조건을 알아야 한다. 여기서는 ISA 효과만 명시할 수 있고 datapath 성능은 미검증이다. [M01 p.5] [EX:ca_2025_2_midterm_q14 p.6]

</details>

**11. 두 thread가 각각 41을 읽고 42를 저장할 수 있다면 전체 증가는 얼마일 수 있는가?**

<details><summary>정답</summary>

둘이 각각 한 번 증가를 의도해도 두 load가 먼저 일어나고 두 store가 모두 42를 쓰는 순서에서는 최종값이 42라 한 번만 증가한 결과가 가능하다. 이는 새로 만든 interleaving 사고실험이지 Q18의 semaphore 구현 정답이나 완전한 memory-model 분석이 아니다. 다중 명령 묶음에 별도 동기화가 필요한 이유만 확인한다. [M01 p.11] [M01 p.24] [EX:ca_2025_2_midterm_q18 p.9](exam_questions/ca_2025_2_midterm_q18)

</details>

**12. Encoding의 여분 비트를 지금 모두 사용하지 않는 설계는 무엇을 얻고 무엇을 포기하는가?**

<details><summary>정답</summary>

미래 extension을 위한 선택지와 장기 호환성을 얻는 대신, 당장 표현할 수 있는 명령이나 인자의 공간 일부를 사용하지 않을 수 있다. 자료의 open-ended design을 적용한 trade-off 설명이며 특정 ISA 확장안의 성능을 계산한 것은 아니다. [M01 p.9] [M01 p.26]

</details>

### 기출 스타일 기반 예상·변형 문제

모두 **자체 제작 문제와 학습용 채점표**다. 실제 기출·공식 정답이나 이번 시험의 출제 예측이 아니다. 이 회차는 자료 기반이므로 “현재 범위”는 PDF와 아래에 명시한 보충 설명으로 풀이 가능하다는 뜻이지 실제 수업 진도 확인이 아니다.

#### 연습 P01

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

**범위·선수:** load-store, based addressing, visible state. 현재 자료로 풀이 가능. [M01 p.10-15] [M01 p.24]  
**유형 근거:** Q2의 ALU operand 판단을 값·주소 구분과 반례 추적으로 확장한 새 문제다. Branch/encoding/pipeline은 요구하지 않는다. [EX:ca_2025_2_midterm_q02 p.2]

초기 PC=0x1000, x10=0x2000, x5=99이고 word memory 값은 MEM[0x2000]=7, MEM[0x2004]=20이다. 명령은 다음 순서로 각 4 byte다: lw x5,4(x10); addi x5,x5,3; sw x5,0(x10). 주소는 유효·정렬되어 있고 예외·동시 실행은 없다.

(a) 각 명령 후 PC, x5, x10, 두 memory 값을 추적하라.  
(b) “load의 offset 4를 읽은 데이터에 더한다”, “addi 후 memory도 23이다”, “store가 x5를 비운다”를 각각 판단하라.  
(c) addi는 load-store 원칙의 반례인가, “모든 ALU 입력은 register 두 개”라는 주장의 반례인가?

<details><summary>풀이와 학습용 채점 포인트 · 12점</summary>

| 완료한 명령 | 다음 PC | x5 | x10 | MEM[0x2000] | MEM[0x2004] |
|---|---|---:|---|---:|---:|
| lw | 0x1004 | 20 | 0x2000 | 7 | 20 |
| addi | 0x1008 | 23 | 0x2000 | 7 | 20 |
| sw | 0x100c | 23 | 0x2000 | 23 | 20 |

주소 0x2000+4에서 20을 읽고, 그 값에 3을 더한 뒤 다른 위치 0x2000에 저장한다. 따라서 (b)는 셋 다 틀리다. Offset은 읽을 주소 계산에 쓰이며 store는 source register를 비우지 않는다.  
(c) Immediate는 memory operand가 아니다. addi는 두 register만 입력으로 받는다는 주장에는 반례지만 load-store 원칙과는 양립한다. 이 표의 행은 instruction 완료 상태이며 CPU clock cycle 수가 아니다.

**채점:** 세 상태 행 6점, (b) 각 잘못의 이유 3점, immediate/memory 구별 2점, instruction/cycle 경계 1점.

</details>

#### 연습 P02

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

**범위·선수:** separate compilation, symbol resolution, relocation. 현재 자료로 풀이 가능. [M01 p.18-22]  
**일반 연습 — 관련 기출 근거 없음:** 제공 후보에 linker의 symbol 구분을 직접 묻는 문제는 없다. 중요 강의 범위를 유지하기 위한 자체 문제다.

가상의 두 파일이 있다. A.c는 외부에서 참조 가능한 배열 items와 함수 main을 정의하고 B.c의 함수 rotate를 호출한다. B.c는 extern으로 items를 참조하고 rotate를 정의하며, file-scope static pointer와 함수 내부 automatic temporary variable을 갖는다.

(a) A의 rotate 참조, B의 items 참조, B의 static pointer, 함수 내부 temporary를 p.20의 관점에서 구별하라.  
(b) 자료의 단순한 relocation 모델에서 items의 최종 주소가 0x3000에서 0x5000으로 바뀌면, items 첫 원소 주소로 초기화될 pointer의 값은 무엇을 반영해야 하는가?  
(c) Assembler, linker, loader를 “모두 파일을 붙이는 단계”라고 정리하면 무엇을 놓치는가?

<details><summary>풀이와 학습용 채점 포인트 · 10점</summary>

(a) 두 참조는 다른 파일의 정의와 연결할 external symbol 참조다. File-scope static pointer는 해당 파일의 local linker symbol이고 함수 내부 temporary는 일반 local variable이다. 뒤의 둘은 local이라는 말만 공유하며 같은 분류가 아니다. Temporary 이름이 debug 정보에도 절대 없다는 뜻은 아니다.  
(b) 이 단순 모델의 pointer는 0x5000을 반영해야 한다. 배열의 첫 데이터 값이나 옛 주소 0x3000을 그대로 쓰면 “첫 원소의 주소”라는 관계를 보존하지 못한다. 실제 relocation format/동적 linking 전부를 지정한 문제는 아니다.  
(c) Assembler는 assembly를 machine-code object로 번역하고, linker는 정의·참조와 배치를 연결하며, loader는 실행 memory 환경을 준비한다. 어떤 명령이 메모리 값을 바꾸는지는 이후 ISA 실행의 문제다.

**채점:** 네 대상의 구분 4점, relocation 결과+주소/데이터 이유 3점, 세 도구의 역할 3점.

</details>

#### 연습 P03

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

**범위·선수:** ELF file/runtime 구별, .bss와 zero initialization. 자료와 본문의 명시적 ELF 보충으로 풀이 가능. [M01 p.22-23]  
**일반 연습 — 관련 기출 근거 없음:** 제공 기출에 이 ELF loading 요구는 없다. 채점도 자체 기준이다.

한 가상 loadable segment의 file-backed 내용은 24 byte, 실행 시 필요한 memory는 40 byte다. 처음 24 byte는 파일에서 가져오고 나머지는 0으로 채우는 모델이다.

(a) 파일에서 가져올 byte 수와 zero-fill byte 수는?  
(b) 이것이 “ELF 파일 전체 크기가 24 byte이고 .bss section이 반드시 16 byte”라는 결론을 보장하는가?  
(c) .bss가 실행 공간을 차지하지만 그 초기값 전체를 파일에 저장하지 않는다는 설명과 모순되는가?

<details><summary>풀이와 학습용 채점 포인트 · 8점</summary>

(a) 24 byte를 가져오고 40−24=16 byte를 0으로 채운다.  
(b) 보장하지 않는다. 한 segment의 file/memory 크기 조건이다. ELF 전체에는 header·다른 segment/section 등이 있을 수 있으며 16 byte를 특정 section과 일대일 동일시할 정보도 없다.  
(c) 모순되지 않는다. .bss의 zero-initialized memory와 파일 payload 부재가 공존할 수 있다. Section header 같은 metadata 존재와 초기값 payload 저장도 구분한다. 이 계산은 ELF 파일을 실제 생성·실행한 실측 결과가 아니라 명시한 모델의 계산이다. [ELF Program Header](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch5.pheader.html)

**채점:** 수량과 단위 2점, 전체 파일/segment 구분 2점, section과 동일시하지 않음 2점, .bss 설명 2점.

</details>

#### 연습 P04

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

**범위·선수:** ISA extensibility, compatibility, general-purpose와 용어 경계. 현재 자료로 풀이 가능. [M01 p.16-17] [M01 p.25-29]  
**일반 연습 — 관련 기출 근거 없음:** Q14는 특정 명령의 datapath/control 설계다. 그것을 장기 호환성 출제 근거로 과장하지 않고, 이 문제는 일반 설계 연습으로 둔다.

가상 ISA의 제한된 encoding 공간을 지금 전부 사용하는 설계 A와 일부를 future use로 남기는 설계 B가 있다.

(a) A와 B의 장단점 하나씩을 설명하라. B이면 어떤 미래 확장도 자동으로 과거 binary와 호환되는가?  
(b) 특정 ML 계산용 accelerator가 모든 general-purpose workload에서 우월하다는 결론을 낼 수 있는가?  
(c) MIPS의 fixed-length 사례로 모든 RISC-V instruction이 항상 같은 길이라고 결론 내리거나 assembly 한 줄을 언제나 machine instruction 한 개로 세어도 되는가?

<details><summary>풀이와 학습용 채점 포인트 · 8점</summary>

(a) A는 현재 사용 가능한 표현을 넓히지만 미래 encoding 선택지를 줄인다. B는 현재 자원을 일부 쓰지 않는 대신 확장 여지를 남긴다. 그렇다고 호환성이 자동 보장되지는 않는다. 기존 명령의 의미, 새 기능 지원 여부와 실행 환경을 별도로 확인해야 한다.  
(b) 아니다. 특수화의 성능 이득은 대상 작업·구현 조건에 관한 것이며 범용성 일부와의 교환일 수 있다.  
(c) 둘 다 안 된다. p.16은 MIPS 사례이고, p.28의 pseudo-instruction은 여러 machine instruction으로 확장될 수 있다. 자료 사례의 범위를 전체 ISA에 일반화하지 않는다.

**채점:** 두 trade-off 2점, 호환성 조건 2점, 특수화 경계 2점, 길이/pseudo 구별 2점.

</details>

복기본은 공식 시험 원문과 정답의 정확성이 독립 검증되지 않았다. 문제 수는 과거 출제 빈도를 확정하는 통계가 아니며 동일 자료의 정리본을 별도 시험으로 중복 계산하지 않았다. 연결 문항의 실제 PDF 페이지는 Q1·Q2 p.2, Q12 p.4, Q14 p.6, Q15 p.7, Q18 p.9다.

오늘은 상태표 A를 가리고 직접 복원한다. 다음 복습에는 B의 memory 값을 바꿔 addressing mode를 다시 계산하고, `main`·`swap` 그림의 이름을 global/external/local로 나눈다. ISA Part 2 이후 Q12의 전체 번역을, datapath와 pipeline 학습 이후 Q14·Q15를 다시 풀면 현재 지식과 향후 과제를 구분할 수 있다. P&H Ch.2는 자료의 읽기 안내일 뿐 이 노트에서 해당 장 전체를 읽고 검증했다는 뜻은 아니다. [M01 p.20] [M01 p.29]

## 출처와 검증 상태



- **M01:** `lec 02.pdf`, *Instruction Set Architecture (ISA) Part 1*, 29쪽. 모든 페이지의 텍스트와 렌더링을 대조했다. 특히 텍스트 추출에서 빠지기 쉬운 p.19-23의 C code, symbol 화살표, linking/loading 그림을 직접 확인했다. 모든 `p.n`은 PDF 파일의 1-based 페이지다.
- **녹음/STT:** 없음. 실제 발화, 강조, 진도와 출석 상황을 확인한 노트가 아니다. 날짜·회차는 학기 기록의 9월 3일 2강 위치를 따른다.
- **기출:** 2025-2 컴구 중간 복기본의 전체 18문항 색인을 검토하고 선택 문항의 p.2·4·6·7·9를 원문 화면으로 대조했다. 공식성·완전한 정답 검증과는 별개다. 전체 PDF·제공 답안은 노트에 넣지 않았다. Q2·Q14에는 새 공개 문제 카드를 만들지 않았다.
