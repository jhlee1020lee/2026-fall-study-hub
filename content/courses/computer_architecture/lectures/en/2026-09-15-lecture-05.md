Learn to connect measured execution time with instruction count, CPI, clock frequency, and the limits of partial improvements.  
Then use workload assumptions to choose meaningful averages, interpret benchmark comparisons, and report performance without overstating the evidence.

## Lecture Content and Explanation

### Functional correctness and performance answer different questions

[[concepts/instruction-set-architecture|Instruction Set Architecture (ISA)]] specifies what instructions must do. **Functional correctness** means that a processor executes arithmetic, data movement, and control operations according to those specifications. **Performance** asks how efficiently the processor carries out that correct execution. The lecturer introduces performance measurement before processor implementation so that later design choices can be evaluated against a meaningful criterion. [STT 01:59] [STT 02:08] [M01 p.2]

For example, two implementations may produce the same correct result while taking different amounts of time. Correctness establishes that both perform the required computation; a performance comparison then requires the same task, an identified measurement, and comparable conditions.

The opening comparison between a processor operating at 3.7 GHz and one operating at 2-point-something GHz motivates this problem. The lecturer says the former “might be better”; this is a motivating example, not an actual benchmark result. It does not establish a general ranking between different processors. Clock frequency describes cycles per second, but completing a program also depends on the instructions executed and the cycles required for those instructions. [STT 03:30] [M01 p.6]

The important distinction is therefore between satisfying an instruction’s specification and improving the execution of a specified workload. A faster clock alone cannot demonstrate that an entire program finishes sooner.

### Latency and throughput measure different aspects of service

[[concepts/latency|Latency]] is the time between the beginning and completion of one task. [[concepts/throughput|Throughput]] is the number of tasks completed per unit time. Their units reveal their different meanings: latency might be measured in milliseconds per request, while throughput might be measured in completed requests per second. [STT 04:28] [STT 05:26] [M01 p.3]

The lecturer uses three application settings:

| Setting | Relevant observation | Metric |
|---|---|---|
| A client interacting with a network server | Time required to complete that client’s request | Latency |
| An interactive game | Delay between a keystroke and the corresponding response | Latency |
| A server processing a batch of requests | Number of requests completed during an interval | Throughput |

These examples identify what the measurement should capture. An interactive user experiences the delay of a particular action, whereas a batch-processing system may be evaluated by how much work it completes over time. [STT 05:26] [STT 06:27]

**Concurrency prevents a universal reciprocal relationship.** Suppose, in an independently constructed example, one worker completes a request in 100 ms. With requests handled sequentially and no gaps, its throughput is 10 requests/s. If five independent workers each retain that 100 ms service time and remain continuously occupied, their combined throughput is 50 requests/s. Individual service latency has not become 20 ms.

This is the distinction behind the slide’s bus-versus-race-car analogy: transporting many passengers and transporting one passenger quickly are different objectives. The lecturer connects the same distinction to multicore processors, explaining that additional cores can increase aggregate throughput when frequency cannot be increased indefinitely. [STT 07:23] [STT 08:19] [M01 p.3]

The metrics can still influence each other. A component that completes work more quickly may shorten a larger task that depends on it. However, neither an increase in throughput nor a fixed clock frequency determines individual-task latency by itself. The increase/decrease wording in the discussion at 08:19 remains **검증 필요 (verification required)**; the definitions and concurrency example do not depend on reconstructing it.

### Execution time must be defined before performance is compared

For a specified amount of work, the lecture expresses performance abstractly as

$$
\text{Performance}=\frac{1}{T}.
$$

A shorter execution time therefore corresponds to higher performance. Throughput has the form $W/T$, where $W$ is completed work. When $W$ is fixed, increasing throughput is equivalent to reducing the time needed to complete that work. If the workloads differ, this equivalence cannot be assumed. [STT 09:05] [M01 p.4]

The next question is what $T$ measures. The lecturer introduces the Unix `time` command, noting that it is also available on a Mac, to connect a software execution measurement with architectural analysis. Its reported quantities distinguish time passing from CPU time charged to the program. [STT 10:12]

| Measurement | Meaning |
|---|---|
| Elapsed time, or wall-clock time | Time from the command’s start to its completion |
| User CPU time | CPU time spent executing the program’s own code |
| System CPU time | CPU time spent executing system code on the program’s behalf, including system-call work |

The program’s reported CPU time combines user and system CPU time. Elapsed time also reflects periods during which the program is not executing on the CPU. The lecture associates the difference with other activity and I/O, but subtracting these measurements does not independently identify every cause of delay. [STT 11:12] [M01 p.4]

**Reading the command-output figure.** Page 5 shows `time yes "hello"` producing repeated terminal output. Its displayed measurements are:

```text

Sys   0m0.013s
```

The CPU time is therefore

$$
T_{\text{CPU}}=0.002+0.013=0.015\ \text{s},
$$

compared with 1.260 s of elapsed time. The arithmetic difference is 1.245 s. The figure’s third label is `Sys`; the uncertain spoken label does not override the visible output. [STT 12:12] [STT 13:07] [M01 p.5]

The practical measurement rule on page 4 is to state precisely what was measured and to measure and report wall-clock time on an unloaded system. Page 5 also supplies `man 7 time` as a reference command. A report that merely says a program took a certain number of seconds leaves an essential question unanswered: elapsed seconds or CPU seconds? ### The CPU execution-time equation connects software work to hardware

[[concepts/cpu-execution-time|CPU execution time]] can be decomposed into the amount of instruction work, its average cycle cost, and the duration of a cycle. Let $N$ be the executed instruction count, $C$ the total cycle count, and $F$ the clock frequency in cycles per second. Then

$$
\text{CPI}=\frac{C}{N},
\qquad
\text{IPC}=\frac{N}{C},
\qquad
T_{\text{CPU}}=\frac{C}{F}
=\frac{N\times\text{CPI}}{F}.
$$

Here [[concepts/cpi|CPI]] means cycles per instruction, and [[concepts/ipc|IPC]] means instructions per cycle. For the same measured execution, they are reciprocals. Both describe aggregate execution; an average need not be an integer. [STT 14:11] [STT 15:10] [STT 39:09] [M01 p.6]

**Reading the factorization on page 6.** The slide arranges execution time as

$$
T_{\text{CPU}}
=
\underbrace{\frac{\text{seconds}}{\text{cycle}}}_{\text{cycle time}}
\times
\underbrace{\frac{\text{cycles}}{\text{instruction}}}_{\text{average CPI}}
\times
\underbrace{\frac{\text{instructions}}{\text{program execution}}}_{N}.
$$

The intermediate units cancel, leaving seconds per program execution. This makes the equation more than a formula to memorize: each factor identifies a different route by which execution time can change.

The metric prefixes must remain explicit:

- A frequency of $g$ GHz is $g\times10^9$ cycles/s, so its cycle time is $1/(g\times10^9)$ seconds.
- A throughput of $m$ MIPS is $m\times10^6$ instructions/s, so its reciprocal is $1/(m\times10^6)$ seconds per instruction.

The slide abbreviates these relationships using `1/GHz` and `1/MIPS`. The scale factors above explain the units; they are not recovered wording from the uncertain speech at 15:10. [M01 p.6]

**Independently constructed calculation.** A run executes $6\times10^8$ instructions with an average CPI of 1.5 at 2 GHz:

$$
C=(6\times10^8)(1.5)=9\times10^8\ \text{cycles},
$$

$$
T_{\text{CPU}}
=\frac{9\times10^8}{2\times10^9}
=0.45\ \text{s}.
$$

The same identity can be rearranged to find a measured or required CPI:

$$
\text{CPI}=\frac{T_{\text{CPU}}F}{N}.
$$

This rearrangement connects directly to the reasoning demanded by parts (a) and (b) of the recalled 2025-2 midterm Q11: recover CPI from execution time, frequency, and instruction count, then determine the CPI needed for a target execution time. The source is a reconstruction, not a verified official examination or answer key; instructor attribution is also not independently verified. The relevant reasoning is unit conversion and solving the equation, rather than copying a numerical result. [EX:ca_2025_2_midterm_q11 p.3]

Two mistakes are especially consequential. Instruction count means instructions executed during the run, not the number of source-code lines. Also, this factorization describes CPU execution time; it is not a general identity for wall-clock time containing I/O waits.

### Instruction mix and implementation jointly determine CPI

Instructions do not necessarily have equal execution costs. The lecturer contrasts arithmetic operations using registers with data movement involving memory, recalling the earlier relationship between smaller storage structures and faster access. This motivates accounting for the kinds of instructions a program executes. It does not establish a universal rule that every arithmetic instruction is faster than every data movement instruction on every processor. [STT 16:05]

An [[concepts/instruction-mix|instruction mix]] describes the proportions of executed instruction classes. If class $i$ accounts for $N_i$ instructions with an assigned average cost $\text{CPI}_i$, then, in an additive cycle-accounting model,

$$
\text{CPI}_{\text{overall}}
=
\frac{\sum_i N_i\text{CPI}_i}{\sum_i N_i}
=
\sum_i p_i\text{CPI}_i,
\qquad
p_i=\frac{N_i}{N}.
$$

The weights are instruction-count fractions because the denominator of CPI is an instruction count. This derives the weighted average from the quantity being measured.

For an independently constructed example, suppose 80% of instructions have CPI 1 and 20% have CPI 4. Then

$$
\text{CPI}_{\text{overall}}
=0.8(1)+0.2(4)=1.6.
$$

A simple average of the two class costs would give 2.5, incorrectly treating the classes as equally frequent. Although the second class contains only 20% of instructions, it contributes

$$
\frac{0.2(4)}{1.6}=0.5
$$

of the modeled execution cycles. Instruction fraction and execution-time fraction can therefore differ substantially. This distinction matters when evaluating an optimization that affects only one class. [M01 p.6] [STT 37:12]

At 37:12, the lecturer’s example describes mathematical operations occupying 90% of the time and data movement occupying 10% of the time. These are spoken time fractions, distinct from the instruction-count weights required for average CPI. [STT 37:12] Those words are not evidence that instruction-count percentages were spoken. The equation above supplies the mathematical distinction without silently replacing the transcript.

Page 6 also maps the execution-time factors to design responsibilities:

| Factor | Influences identified in the slide | Consequence for analysis |
|---|---|---|
| Clock frequency | Semiconductor technology and microarchitecture | Changes the duration of each cycle |
| CPI | Microarchitecture and ISA | Changes the cycles required for the executed work |
| Instructions per program | ISA and compiler | Changes how much instruction work is executed |

The lecturer specifically frames processor design in this course as a way to improve the CPI-related part of execution. Compiler optimization can change instruction count even when the intended program behavior remains fixed. The comparison between a simple Hello World program and Chromium illustrates differences in instruction work, not a numerical benchmark. [STT 17:01] [STT 17:56] [STT 18:54] [M01 p.6]

These factors interact. For example, an independently constructed design change that lowers CPI by 20% but increases cycle time by 25% leaves their product unchanged:

$$
0.80\times1.25=1.
$$

With instruction count fixed, that change provides no CPU execution-time improvement. This illustrates why optimizing one factor does not establish an overall gain.

The poor-design/smaller-CPI wording at 17:56 remains **검증 필요**. The mathematical conclusion supported by the equation is that, with frequency and instruction count fixed, a lower aggregate CPI reduces CPU execution time. ### Runtime is one dimension of processor evaluation

A processor can be evaluated using energy consumption, power, implementation cost, reliability, and security as well as execution time. Page 7 introduces these dimensions to show that design choices can involve competing objectives. A design may spend more energy to finish sooner, or accept a longer runtime to reduce energy use. [STT 18:54] [STT 19:47] [M01 p.7]

For energy $E$ consumed over duration $T$, average power is

$$
P_{\text{avg}}=\frac{E}{T}.
$$

Energy measures the amount consumed; average power measures consumption per unit time. In an independently constructed comparison, a run consuming 20 J in 1 s has an average power of 20 W. Another consuming 15 J in 2 s has an average power of 7.5 W. The second run uses less energy and less average power, but takes longer. Which result is preferable depends on the evaluation objective.

### Relative performance requires the ratio in the correct direction

[[concepts/relative-performance|Relative performance]] compares two executions of the same specified work. Under the lecture’s convention, saying that $X$ is $n$ times as fast as $Y$ means

$$
n=\frac{\text{Performance}_X}{\text{Performance}_Y}
=\frac{T_Y}{T_X}.
$$

For comparable throughput measurements, the same performance ratio can be written as $\text{Throughput}_X/\text{Throughput}_Y$. The direction reverses when moving from performance to time because performance is proportional to inverse time. [STT 22:00] [STT 24:36] [M01 p.8] [M01 p.10]

A percentage increase in performance follows the same convention:

$$
X\text{ is }m\%\text{ faster than }Y
\quad\Longrightarrow\quad
\frac{\text{Performance}_X}{\text{Performance}_Y}
=1+\frac{m}{100}.
$$

**The lecture’s 50%-faster example.** Computer $X$ takes 1 s, and $Y$ is described as 50% faster. The two alternatives on page 9 distinguish reducing time by 50% from increasing performance by 50%. The course adopts the performance interpretation:

$$
\frac{T_X}{T_Y}=1.5
\quad\Longrightarrow\quad
T_Y=\frac{1}{1.5}=\frac{2}{3}\ \text{s}.
$$

If $Y$ instead took 0.5 s, its performance would be twice that of $X$: a 100% performance increase. [STT 22:43] [STT 23:41] [STT 25:23] [STT 26:22] [M01 p.9] [M01 p.10]

The ratio 1.5 is dimensionless. An uncertain spoken unit at 26:22 does not turn it into a time measurement.

For an enhanced version of a design, [[concepts/speedup|speedup]] is

$$
S=\frac{T_{\text{without enhancement}}}
        {T_{\text{with enhancement}}}.
$$

The original time belongs in the numerator. A successful reduction in time then produces $S>1$. [STT 27:22] [STT 28:21] [M01 p.11]

A useful derived relationship is

$$
\text{fractional time reduction}=1-\frac{1}{S}.
$$

Thus a speedup of 1.5 corresponds to a one-third reduction in execution time, not a one-half reduction. Keeping performance increase and time reduction separate prevents the ambiguity demonstrated by the slide.

### Amdahl’s Law limits the benefit of improving only part of a task

[[concepts/amdahls-law|Amdahl’s Law]] relates a local improvement to the improvement of the whole execution. Let $f$ be the fraction of the original execution time affected by an enhancement, and let $S_f$ be the speedup of that portion. Assume the remaining portion is unchanged and the enhancement introduces no additional overhead. [STT 28:21] [M01 p.12]

**Reading the two-bar figure on page 12.** The upper bar represents the original execution time. Its unshaded portion occupies fraction $1-f$, and its shaded portion occupies fraction $f$. In the lower bar, the unshaded portion retains its length. Only the shaded portion shrinks, from $f$ to $f/S_f$.

Consequently,

$$
T_{\text{new}}
=
T_{\text{old}}
\left((1-f)+\frac{f}{S_f}\right),
$$

and

$$
S_{\text{overall}}
=
\frac{T_{\text{old}}}{T_{\text{new}}}
=
\frac{1}{(1-f)+f/S_f}.
$$

The denominator represents the complete new execution as a fraction of the old one. Applying $S_f$ to the entire original time would incorrectly accelerate the unchanged portion.

**Independently constructed calculation.** Suppose a 10 s task spends 60% of its time in a component that becomes three times as fast. Originally, 4 s is unaffected and 6 s is eligible for improvement:

$$
T_{\text{new}}=4+\frac{6}{3}=6\ \text{s},
$$

$$
S_{\text{overall}}=\frac{10}{6}\approx1.67.
$$

A local speedup of 3 therefore produces an overall speedup of about 1.67. Even if the affected component took vanishingly little time,

$$
S_{\max}=\frac{1}{1-f}
=\frac{1}{0.4}=2.5.
$$

This bound follows from the 4 s that remains unchanged.

**Lecture-specific emphasis:** the lecturer asks students to work through the arithmetic and emphasizes improving frequently occurring or frequently used parts of a design. The quantitative interpretation is to consider their contribution to original execution time. The slide’s qualitative suggestion that local speedup matters little when $f$ is small does not mean that $S_{\text{overall}}$ is mathematically independent of $S_f$. [STT 29:17] [M01 p.12]

The recalled 2025-2 midterm Q6 connects to this reasoning by asking for a judgment about the fraction that limits an enhancement’s benefit. The appropriate approach is to identify the affected original time and the unchanged remainder, then use the equation or its limiting case. Its wording supplies a relevant conceptual demand, not evidence of this semester’s exam priorities. [EX:ca_2025_2_midterm_q06 p.2]

**Instruction count is not the Amdahl fraction.** In the earlier constructed instruction mix, the expensive class contains 20% of instructions but accounts for 50% of modeled cycles. With a fixed clock, it therefore accounts for 50% of modeled CPU time. Substituting $f=0.2$ solely from its instruction-count share would be incorrect.

A further constructed calculation illustrates the feasibility reasoning associated with Q11(c). Suppose there are $10^9$ instructions at 2 GHz, with the same 80%-at-CPI-1 and 20%-at-CPI-4 mix. The unaffected class contributes

$$
T_{\text{unaffected}}
=
\frac{0.8(10^9)(1)}{2\times10^9}
=0.4\ \text{s}.
$$

The expensive class also contributes 0.4 s, giving an original total of 0.8 s. Improving only that class cannot achieve a target below 0.4 s. To reach 0.5 s, the affected portion must fall from 0.4 s to 0.1 s, requiring a local speedup of 4 under these assumptions.

The recalled Q11(c) similarly requires checking whether improvement of one instruction class can meet a whole-program target. The central approach is to calculate the unaffected contribution first; solving for a local speedup is meaningful only after the target passes that feasibility check. These constructed values are explanatory examples, not the recalled examination’s data or an official solution. [EX:ca_2025_2_midterm_q11 p.3]

### Workload choice determines what a performance comparison means

A [[concepts/workload|workload]] identifies the applications and work used to evaluate a system. Relative performance can change with the workload because two processors need not benefit the same kinds of computation equally. Page 13 explicitly allows $X$ to outperform $Y$ on some applications while $Y$ outperforms $X$ on another. [STT 31:13] [STT 32:14] [M01 p.13]

The lecturer illustrates this with games versus research workloads, then returns to AI workloads versus games near the end. These examples explain why a machine cannot be assigned a universal performance ranking from one application’s result. [STT 31:13] [STT 46:06]

For example, suppose an independently constructed comparison finds that $X$ completes application A in 1 s and application B in 10 s, while $Y$ takes 2 s and 5 s respectively. $X$ is faster for A, but $Y$ is faster for B. Choosing a machine requires knowing which applications matter and how often they run.

A single summary number can conceal that reversal. Before reducing measurements to one number, specify what the aggregate is intended to represent. If no suitable single-number interpretation is available, retain the individual results and explain the conditions under which each matters. This is explicit reporting advice in the lecture, rather than an inference from past exams. [STT 33:15] [M01 p.13]

### Arithmetic and weighted arithmetic means represent different workload mixes

The [[concepts/arithmetic-mean|arithmetic mean]] of $n$ application runtimes is

$$
\operatorname{AM}(T)=\frac{1}{n}\sum_{i=1}^{n}T_i.
$$

Page 14 links this expression to total runtime: when the same applications run equally often, comparing their arithmetic mean times is equivalent to comparing their total times. The common divisor $n$ cancels from the ratio. [M01 p.14]

In the constructed workload above,

$$
\operatorname{AM}_X=\frac{1+10}{2}=5.5\ \text{s},
\qquad
\operatorname{AM}_Y=\frac{2+5}{2}=3.5\ \text{s}.
$$

For one run of each application, $Y$ has a speedup of

$$
\frac{5.5}{3.5}=\frac{11}{7}\approx1.57
$$

over $X$. The same ratio follows from total times of 11 s and 7 s.

The longer application contributes more to the sum. That is appropriate when the sum represents the work actually performed. The lecturer’s concern about a large outlier does not make arithmetic means generally invalid; it raises the question of whether the selected observations and frequencies represent the intended workload. [STT 35:19] [STT 36:16] [M01 p.14]

A [[concepts/weighted-arithmetic-mean|weighted arithmetic mean]] incorporates unequal run frequencies:

$$
\operatorname{WAM}(T)=\sum_{i=1}^{n}w_iT_i,
\qquad
\sum_{i=1}^{n}w_i=1.
$$

**Reading page 15’s weight definition.** Here $w_i$ is the fraction of all application runs that belong to application $i$. It is not automatically the fraction of total execution time, nor an arbitrary adjustment to suppress an inconvenient large value. The formula represents average time per application run for the specified mixture. [M01 p.15]

If A accounts for 90% of runs and B for 10%, the same constructed timings give

$$
\operatorname{WAM}_X=0.9(1)+0.1(10)=1.9\ \text{s},
$$

$$
\operatorname{WAM}_Y=0.9(2)+0.1(5)=2.3\ \text{s}.
$$

Now $X$ is faster for the stated workload mixture, with speedup $2.3/1.9\approx1.21$. No individual application timing changed; only the workload composition changed.

This explains both the use and the limitation of weighting. A weighted result is interpretable only when the weights have a defined meaning and the same workload composition is used for both machines. For application runtime, page 15 uses run-count fractions. For average CPI, the denominator requires instruction-count fractions. The lecturer’s loose description of weights as importance does not erase this distinction. [STT 37:12] [M01 p.15]

### Geometric means summarize normalized ratios

The [[concepts/geometric-mean|geometric mean]] combines positive values multiplicatively:

$$
\operatorname{GM}(x_1,\ldots,x_n)
=
\left(\prod_{i=1}^{n}x_i\right)^{1/n}.
$$

The lecturer introduces it through comparing smartphones across several benchmarks, mentioning Geekbench as one example. Each benchmark supplies a comparison against a reference machine, rather than a contribution to one application-run-time sum. [STT 38:11] [STT 39:09]

**Reading the normalization figure on page 16.** The displayed per-benchmark ratio is

$$
r_i=\frac{T_{X,i}}{T_{Y,i}},
$$

where $Y$ is the reference. The displayed aggregate is therefore

$$
G_{X/Y}
=
\left(\prod_{i=1}^{n}\frac{T_{X,i}}{T_{Y,i}}\right)^{1/n}.
$$

This is a normalized **execution-time ratio**. A value below 1 indicates that $X$ has the lower geometric mean normalized time. The slide’s accompanying speedup wording points in the opposite direction from the speedup definition used earlier. Under that definition, the geometric summary of $X$’s speedups over $Y$ is

$$
S_{X\text{ over }Y}
=
\left(\prod_{i=1}^{n}\frac{T_{Y,i}}{T_{X,i}}\right)^{1/n}
=
\frac{1}{G_{X/Y}}.
$$

The distinction preserves the displayed equation while explaining the source’s labeling inconsistency. It does not claim that a corrected ratio was spoken. [M01 p.16]

For an independently constructed pair of normalized time ratios, $0.5$ and $2$,

$$
G=\sqrt{0.5\times2}=1.
$$

One benchmark favors $X$ by a factor of two and the other favors $Y$ by the same factor. Their geometric ratio summary balances at 1. This does not prove that the machines take equal total time to execute both applications: that calculation would require the actual runtimes and workload frequencies.

The property printed at the bottom of the slide follows directly from multiplication:

$$
\frac{\operatorname{GM}(X_i)}{\operatorname{GM}(Y_i)}
=
\left(\frac{\prod_iX_i}{\prod_iY_i}\right)^{1/n}
=
\operatorname{GM}\left(\frac{X_i}{Y_i}\right).
$$

The common mistake is to treat every quantity called performance as the same type of input. Normalized ratios and raw instructions-per-cycle rates answer different aggregation questions. The recalled midterm Q5 tests this distinction by asking for a judgment about a proposed averaging method for IPC. A justified response must establish the workload and weighting assumptions; the existence of a benchmark comparison alone does not make geometric averaging appropriate for pooled raw IPC. [EX:ca_2025_2_midterm_q05 p.2]

### Harmonic means follow from total work divided by total time

A rate has a numerator representing completed work and a denominator representing the resource over which it is completed. To aggregate rates, first reconstruct those totals. The [[concepts/harmonic-mean|harmonic mean]] arises when equal amounts of work are completed at different rates. [STT 40:00] [STT 41:02] [M01 p.17]

**The lecture’s driving example.** A car travels the first 10 km at 30 km/h and the next 10 km at 90 km/h. The total distance is 20 km, while total time is

$$
T=\frac{10}{30}+\frac{10}{90}
=\frac{4}{9}\ \text{h}.
$$

Therefore,

$$
v_{\text{average}}
=
\frac{20}{4/9}
=
45\ \text{km/h}.
$$

The arithmetic mean, 60 km/h, is inappropriate for these equal-distance legs because the car spends more time at the lower speed. Page 17 places this total-distance/total-time calculation before the harmonic-mean formula, showing where the formula comes from. [M01 p.17]

For $n$ equal quantities of work, each of size $W$, processed at rates $R_i$,

$$
R_{\text{overall}}
=
\frac{nW}{\sum_iW/R_i}
=
\frac{n}{\sum_i1/R_i}
=
\operatorname{HM}(R_i).
$$

For unequal work quantities, let $w_i$ be each portion’s fraction of total work. Then

$$
R_{\text{overall}}
=
\frac{1}{\sum_iw_i/R_i},
\qquad
\sum_iw_i=1.
$$

This is the weighted harmonic mean shown on page 17. Its weights describe work fractions. For the driving analogy, they are distance fractions.

For example, an independently constructed trip with one-quarter of its distance at 30 km/h and three-quarters at 90 km/h has average speed

$$
\frac{1}{0.25/30+0.75/90}
=60\ \text{km/h}.
$$

The result differs from the lecture’s equal-distance example because the work shares differ.

The slide’s warning against arithmetic means of rates should be understood through these conditions. If equal durations were spent at two speeds, total distance divided by total time would give their arithmetic mean. The reliable method is to identify what is held equal and reconstruct the totals, rather than choose a mean solely because the values have rate units.

### Aggregate IPC requires the instruction-count assumptions

For one measured execution,

$$
\text{IPC}=\frac{N}{C}=\frac{1}{\text{CPI}}.
$$

Combining several executions requires preserving their instruction counts and cycle counts. Page 18 explicitly considers the same clock frequency and the same instruction count for each execution. These assumptions connect the preceding equal-work rate example to IPC. [STT 39:09] [STT 42:11] [M01 p.18]

Suppose each of $n$ executions contains $N$ instructions. Execution $i$ consumes $N\text{CPI}_i$ cycles, so pooled IPC is

$$
\text{IPC}_{\text{overall}}
=
\frac{nN}{\sum_iN\text{CPI}_i}
=
\frac{n}{\sum_i\text{CPI}_i}
=
\frac{1}{\operatorname{AM}(\text{CPI}_i)}.
$$

Substituting $\text{CPI}_i=1/\text{IPC}_i$ gives

$$
\text{IPC}_{\text{overall}}
=
\frac{n}{\sum_i1/\text{IPC}_i}
=
\operatorname{HM}(\text{IPC}_i).
$$

**Reading page 18’s derivation.** The successive fractions expand the arithmetic mean of CPI, remove the common division by $n$, and replace CPI by reciprocal IPC. This produces the harmonic mean of IPC. The exact derivation is supported by the slide; parts of the later spoken fraction grouping remain **검증 필요**. [M01 p.18]

The slide also equates average time with average CPI in shorthand. With common instruction count $N$ and frequency $F$, the dimensional relationship is

$$
\operatorname{AM}(T_i)
=
\frac{N}{F}\operatorname{AM}(\text{CPI}_i).
$$

Time and CPI are proportional under those conditions. Seconds and cycles per instruction are not interchangeable units.

For an independently constructed example, consider two executions with equal instruction counts and IPC values 1 and 3. Their pooled IPC is

$$
\frac{2}{1/1+1/3}=1.5.
$$

Their arithmetic mean IPC would be 2. The faster execution consumes fewer cycles for its equal share of instructions, so equal instruction counts do not imply equal cycle weights.

This provides a concrete approach to the conceptual demand in recalled Q5: identify whether the requested result is pooled IPC for equal instruction work or an aggregate of normalized benchmark ratios. The equal-work calculation supports harmonic averaging here; a blanket rule assigning geometric means to all performance measurements does not. [EX:ca_2025_2_midterm_q05 p.2]

Page 19’s amount–ratio–rate classification is useful when read with these meanings:

| Quantity being aggregated | Relevant construction | Required interpretation |
|---|---|---|
| Application time or latency observations | Arithmetic or weighted arithmetic mean | Identify the observation or run-frequency weights |
| Positive normalized benchmark ratios | Geometric mean | State the reference and the ratio direction |
| Rates for equal work quantities | Harmonic mean | Preserve equal work, or use work fractions for weighting |

The slide lists time and latency as amount examples; the lecturer additionally discusses CPI. For CPI, instruction-count weighting supplies the necessary interpretation. The classification is a guide to constructing the correct aggregate, not permission to ignore its denominator. [STT 43:12] [M01 p.19]

## Key Takeaways

- **Define the task and measurement before comparing numbers.** Latency, throughput, elapsed time, and CPU time answer different questions. [M01 p.3] [M01 p.4]
- **Use all three execution-time factors.** With instruction count $N$, average CPI, and frequency $F$, CPU time is $N\text{CPI}/F$. A change in one factor can be offset by another. [M01 p.6]
- **Keep performance ratios and time ratios in the correct direction.** A performance increase of 50% gives a speedup of 1.5 and a time reduction of one-third. [M01 p.9] [M01 p.10]
- **Measure an enhancement’s reach in original execution time.** Amdahl’s fraction is not automatically an instruction-count fraction. Unchanged work bounds the achievable gain. [M01 p.12]
- **A workload summary inherits its assumptions.** Runtime averages depend on run frequencies; CPI averages depend on instruction counts; rate aggregation depends on the work and denominator being combined. [M01 p.14] [M01 p.15] [M01 p.17]
- **Preserve the two important slide qualifications.** Page 16 displays normalized time ratios, whose reciprocal gives the corresponding speedup. Page 18 uses equal instruction counts and common frequency; its time–CPI equality is proportional shorthand. [M01 p.16] [M01 p.18]
- **Benchmarks support comparison, not universal superiority.** Retain workload diversity, measurement conditions, individual results, and an interpretable aggregation method. [M01 p.20] [M01 p.21] [M01 p.22]
