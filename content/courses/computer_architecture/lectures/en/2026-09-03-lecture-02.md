### ISA: behavior before implementation

<span id="isa-and-microarchitecture"></span>

[[concepts/instruction-set-architecture|Instruction Set Architecture]] is the contract for machine behavior a program can observe or control. The instruction set is the collection of provided commands; the broader ISA also specifies data representations, registers, instruction effects, encoding, protection, and privileged operations. The deck includes software conventions in its broader interface discussion. Do not automatically equate a software convention with a rule enforced by hardware. [M01 p.5-6] [M01 p.9] [M01 p.28]

[[concepts/microarchitecture|Microarchitecture]] is the internal organization that implements that contract. “Write the sum into a specified register” is an instruction-semantics statement. “Take this many cycles using these execution resources” is an implementation statement. The x86-64, Alder Lake, Zen 4, and cache-capacity examples on p.5 illustrate levels of description; they are not an independently updated product comparison. [M01 p.5]

<span id="reading-the-important-diagrams"></span>

Begin with the system-organization diagram on p.4. The CPU contains an ALU, Register File (RF), and cache; the memory bus connects the CPU side to DRAM and an I/O bridge. Disk, video, keyboard/mouse, and network devices appear below the I/O bus. This places program-visible CPU and memory resources inside a larger system. The GB/sec and 100MB/sec bus labels are illustrative slide annotations, not measurements or universal bandwidth guarantees. [M01 p.4]

| Misreading | Correction | Basis |
|---|---|---|
| ISA means a list of mnemonics. | Include state, representation, encoding, and behavioral rules. | [M01 p.9] |

### Stored-program execution and programmer-visible state

<span id="stored-program-model-and-programmer-visible-state"></span>

The stored-program perspective associated with [[concepts/von-neumann-architecture|Von Neumann architecture]] places instructions and data in memory as binary representations. Execution fetches the instruction addressed by the PC, applies its state transformation, and selects the next PC. This abstract order does not require every internal CPU operation to occur strictly one at a time. [M01 p.7] [M01 p.10]

Past-exam Q1 tests the conceptual relationship between instruction and data storage, so this deck supplies the relevant foundation. A separate caution is necessary: stored-program organization does not by itself grant unrestricted writes to every code region. Keep the abstract storage model separate from protection and privilege mechanisms. [M01 p.7] [M01 p.9] [EX:ca_2025_2_midterm_q01 p.2](exam_questions/ca_2025_2_midterm_q01)

**The state diagram on p.10:** the left side shows memory locations `M[0]` through `M[N-1]`, selected by address. The upper right shows registers, selected by ISA-defined names. The lower right shows the PC containing the current instruction's memory address. The essential distinction is how each location is identified, not the relative sizes of the drawn boxes. The `32b~64b` labels illustrate the diagram's scope; they are not a universal width rule for every register in every ISA. The PC contains an address, not the instruction's binary contents. [M01 p.10]

#### 1. Three questions that complete a state transition

For each instruction ask: **What values are read, and from where? What values are written, and where? What is the next PC?** Omitting any of these can leave the instruction's effect ambiguous. A load reads memory without changing that memory location. A store uses a source-register value without consuming or erasing it. [M01 p.11] [M01 p.24]

An editorial mathematical model is $S=(PC,R,M)$, with register values collected in $R$ and memory contents in $M$. The instruction $I$ acts as $S'=T_I(S)$. This deliberately models only the normal execution state needed by the example. It is not a complete specification of exceptions, privilege, concurrency, or every architectural facility. Its purpose is to distinguish the defined result from the circuitry that produces it. [M01 p.9-11]

The “atomic” wording on p.11 helps introduce instruction-level state changes. It must not be expanded into a guarantee that an entire `load; add; store` sequence is atomic relative to other threads. Q18 concerns synchronization and needs additional concepts such as reservations, conditional stores, and retry control flow. This supplement uses it only to mark that boundary, not to claim that its full solution has already been taught. [M01 p.11] [M01 p.24] [EX:ca_2025_2_midterm_q18 p.9](exam_questions/ca_2025_2_midterm_q18)

| Misreading | Correction | Basis |
|---|---|---|
| `lw; addi; sw` is automatically one atomic operation. | Instruction-level abstraction does not make a multi-instruction sequence atomic. | [M01 p.11] |

### Machine/assembly notation and instruction operands

<span id="machine-code-and-assembly-code"></span>

Machine code is the binary encoding of instructions. Assembly code is a human-readable notation translated by an assembler. A pseudo-instruction may expand to multiple machine instructions, so one assembly line does not universally imply one machine instruction. The ISA manual photographs on p.8 illustrate that the programmer-facing contract is documented; they do not imply that those manuals were read in full for this supplement. [M01 p.8] [M01 p.28]

<span id="instruction-classes-and-operands"></span>

An operand is a value used by an instruction or a specification of where to obtain that value. Arithmetic/logic instructions compute results; data-movement instructions transfer values; control-flow instructions determine the next PC from a condition or target. “Store the result” is incomplete unless the register or memory destination is identified. [M01 p.11]

The deck compares `OP in2`, `OP inout, in2`, and `OP out, in1, in2`. The first relies on an implicit destination/source such as an accumulator. In the second, an input location is also the output. The third explicitly names a destination and two inputs. The labels on p.13 are a comparative overview, not a claim that every instruction in a given ISA has one uniform operand count. Registers provide fast CPU-resident operand storage; the register-count examples on p.12 illustrate architectural choices rather than a universal count. [M01 p.12-13]

### Addressing and load/store: calculate an address, then access a value

<span id="addressing-modes-and-load-store-architecture"></span>

An addressing mode specifies how to locate a memory operand. The instruction may give an address directly, obtain one from a register, add a displacement, combine registers, or read a pointer from memory before accessing the final value. `GPR[x5]` means register contents; `MEM[1000]` means contents at memory address 1000. An address and the value obtained by dereferencing it are different objects. [M01 p.14-15]

Load-store means that ordinary ALU instructions do not directly take memory operands. It does not mean that memory is unimportant or that immediate arithmetic is forbidden. In `addi`, the constant is not fetched through a data-memory operand. This distinction directly supports Q2 and motivates the separate load, arithmetic, and store steps below. [M01 p.13] [M01 p.24] [EX:ca_2025_2_midterm_q02 p.2]

#### 2. Separate the address calculation from the value calculation

The deck's generic `LW rt, offset(rbase)` first computes `GPR[rbase] + offset` as an address, then reads memory at that address and places the value in `GPR[rt]`. The addition selects **where to read**. It does not add the offset to the loaded data. This distinction remains important even when both addresses and data are printed as ordinary numbers. [M01 p.15]

| Mode | Value placed in the destination register | How the address is obtained |
|---|---|---|
| Absolute | `MEM[address]` | Use the explicitly supplied address. |
| Register indirect | `MEM[GPR[base]]` | Use the register contents as an address. |
| Displaced / based | `MEM[GPR[base] + offset]` | Add the displacement to the base value. |
| Indexed | `MEM[GPR[base] + GPR[index]]` | Add two register values. |
| Memory indirect | `MEM[MEM[GPR[base]]]` | Read a pointer before reading the final value. |

This is the **cross-ISA comparative notation** of p.15. It is not a list of literal instruction forms that can all be passed to a RISC-V assembler. In particular, indexed and memory-indirect expressions here describe concepts, not guaranteed RISC-V syntax. The slide's `GRP` typo is rendered as `GPR` consistently. [M01 p.15]

For the additional normative check, RV32I base loads/stores calculate an address from a base register and a sign-extended offset; ordinary integer computation uses register or immediate operands. [RISC-V RV32I: integer operations and loads/stores](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html)

#### B. A new addressing-mode exercise

These numbers are an editorial exercise based on p.15, not a reproduced exam question. All numbers are decimal. Let `GPR[base]=1000`, `GPR[index]=8`, `offset=4`, `MEM[1000]=2000`, `MEM[1004]=17`, `MEM[1008]=23`, and `MEM[2000]=99`. Assume every access is valid. [M01 p.14-15]

| Mode used for the read | Calculation | Result | Data-memory reads |
|---|---|---|---|
| Absolute 1004 | `MEM[1004]` | 17 | 1 |
| Register indirect | `MEM[1000]` | 2000 | 1 |
| Based, offset 4 | `MEM[1000+4]` | 17 | 1 |
| Indexed | `MEM[1000+8]` | 23 | 1 |
| Memory indirect | `MEM[MEM[1000]] = MEM[2000]` | 99 | 2 |

The counts refer only to conceptual **data-memory reads**, excluding instruction fetch and cache-internal activity. The result 2000 of register-indirect access happens to be usable as another address, but that does not trigger another read automatically. A second dereference occurs only in the specified memory-indirect expression. This is why writing out nested brackets is more reliable than guessing from the numbers. [M01 p.15]

#### A. Trace the slide's RISC-V program completely

Initially, `PC=0x1000`, `GPR[x10]=0x2000`, and `MEM[0x2000]=41`. Here `MEM` denotes the word value used in the example. Assume valid addresses, normal execution without exceptions, and no intervening thread. The instruction addresses and sequential PC increments below come directly from the slide. [M01 p.24]

```asm
0x1000: lw   x5, 0(x10)
0x1004: addi x5, x5, 1
0x1008: sw   x5, 0(x10)
```

| Completed step | Next PC | `GPR[x5]` | `GPR[x10]` | `MEM[0x2000]` | Data changed directly |
|---|---|---|---|---|---|
| Initial | `0x1000` | Unspecified | `0x2000` | 41 | None |
| `lw` | `0x1004` | 41 | `0x2000` | 41 | x5 |
| `addi` | `0x1008` | 42 | `0x2000` | 41 | x5 |
| `sw` | `0x100c` | 42 | `0x2000` | 42 | Memory |

The load calculates `0x2000 + 0`. It writes the **contents 41**, not the **address 0x2000**, into x5. After `addi`, memory still holds 41. Only the final store makes memory hold 42. Each displayed sequential instruction advances the PC by four, but control-flow instructions and instruction-length choices must be handled according to their own definitions rather than generalized from this example. [M01 p.11] [M01 p.24]

Choosing branch instructions and completing the entire control-flow translation requires additional ISA study. The following new exercise deliberately isolates the store rather than presenting a full original-exam solution. [M01 p.11] [M01 p.15] [EX:ca_2025_2_midterm_q12 p.4](exam_questions/ca_2025_2_midterm_q12)

### Separate compilation and symbol resolution

<span id="3-from-separate-compilation-to-symbol-resolution"></span>

The C example on p.19 separates `buf[2] = {1, 2}` in `main.c` from `swap()` in `swap.c`. `main` calls a function defined elsewhere. `swap.c` uses `extern int buf[]` to refer to the array defined in another file. Separate translation can produce objects independently, but the resulting program must still connect each relevant reference to its definition. That is the symbol-resolution problem illustrated here. [M01 p.19-21]

| Name in the diagram | Classification shown on p.20 | Important distinction |
|---|---|---|
| `buf`, `main` in `main.c` | Global | Definitions provided by this file. |
| Reference to `swap` in `main.c` | External | Must connect to a definition from another file. |
| `buf` in `swap.c` | External | Refers to the existing array; does not create another array. |
| `bufp0`, `swap` in `swap.c` | Global | Definitions visible for external linking. |
| `static int *bufp1` | Local | A file-local linker symbol. |
| Function-local `temp` | Ordinary local variable | Not part of the file-to-file symbol connection in this example. |

Do not merge the meanings of “local” in `bufp1` and `temp`. The p.20 annotation says that the linker does not handle `temp` as a cross-file symbol to be resolved. It is not a claim that debugging information can never contain the name. Likewise, p.19 is an explanatory code diagram, not a complete modern C project that has been compiled and tested for this note. [M01 p.19-20]

Also trace the data in the pictured `swap()`. `bufp0` points to the first element, and the function makes `bufp1` point to the second. It preserves the first value, 1, in `temp`, copies the second value, 2, into the first location, and writes the saved 1 into the second location. The abstract result is `{2, 1}`. The temporary preserves a value that would otherwise be overwritten; the pointers identify locations rather than holding those element values themselves. [M01 p.19]

| Misreading | Correction | Basis |
|---|---|---|
| File-static `bufp1` and function-local `temp` are the same kind of linker local. | Separate a file-local symbol from an ordinary function-local variable. | [M01 p.20] |

### Relocation and loading: from files to initial execution state

<span id="4-relocation-and-loading-solve-different-problems"></span>

Relocation adjusts code/data placement and references to agree with the combined layout. In `bufp0 = &buf[0]`, the stored pointer value is the **address of the element**, not its initial data value 1. Therefore the location assigned to the array matters to the pointer. The call from `main` to `swap` also depends on connecting a reference to the relevant code. [M01 p.19] [M01 p.21-22]

The compiler-driver example on p.21 packages translation and linking behind one command. The drawing shows the two objects becoming one program. This does not establish that running the displayed command in an arbitrary environment would statically include every system library. No native command or library-linkage configuration was measured for this supplement. [M01 p.21]

Loading prepares the execution-memory environment from the executable. The `.text`, `.rodata`, `.data`, `.bss`, heap, and stack boxes on p.23 are useful, but **file sections and runtime segments are not identical categories**. ELF program headers describe loadable segments; extra memory beyond a segment's file-backed size is zero-filled. [M01 p.23] [ELF Program Header](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch5.pheader.html)

One additional check prevents a common diagram misreading: ELF `.bss` has type `SHT_NOBITS`. It contributes zero-initialized memory without storing the corresponding payload bytes in the file. Thus the `.bss` rectangle in the slides is not evidence of an equally large sequence of zero bytes on disk. [ELF Sections: .bss](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch4.sheader.html)

**The relocation diagram on p.22:** system objects, `main.o`, and `swap.o` appear on the left with their own `.text`, `.data`, and, where relevant, `.bss`. Corresponding regions are combined on the right. References such as the call from `main()` to `swap()` and the pointer to `buf` must agree with the resulting layout. The arrows therefore represent connecting code, data, and references, not just copying unrelated byte strings. The `.symtab` and `.debug` boxes also remind us that an object file can contain tool-oriented information in addition to executable instructions. [M01 p.22]

**The loading diagram on p.23:** distinguish the ELF headers and section list on the left from the runtime memory layout on the right. The latter contains code/read-only data, read/write data, heap, shared-library space, and stack, with growth arrows in this example. Addresses such as `0x08048000` and `0xc0000000`, and the `%sp` notation, belong to the illustrated 32-bit environment. They are not a fixed RISC-V memory layout. Nor does a box on the file side mean that all its bytes must be copied into runtime memory. [M01 p.23]

### ISA design: extension space and implementation boundaries

<span id="5-designing-an-isa-for-more-than-the-present-implementation"></span>

Page 26 emphasizes long-lived compatibility and scalability as well as immediate usefulness. Examples include capacity parameterization, different CPU/I/O counts, components operating at different rates, and spare encoding bits for extensions. An editorial consequence is that using all available encoding space today may increase present expressiveness while narrowing future choices. The lifetime numbers on the slide express its design discussion, not an expiration date shared by all ISAs. [M01 p.9] [M01 p.25-26]

General purpose means supporting applications with different sizes, domains, and mixtures of work. The deck motivates code-independent operations, general bit manipulation, and sufficiently fine memory addressability. Data should not always receive a special character interpretation merely because a bit pattern could represent a character; nevertheless, integer and floating-point operations require their specified interpretations. ML accelerators illustrate trading some generality for performance on a target workload. This is not a claim that every specialized device is faster on every task. [M01 p.27]

The historical discussion on p.17 connects ISA changes to technology constraints, assembly programming, microprogramming, caches, and compilers. It should not collapse into “RISC good, CISC bad.” The fixed-length encoding description on p.16 is specifically the **MIPS example**; that slide alone cannot establish one instruction length for every ISA. The market-oriented comments on p.17 remain source discussion, not independently verified current market-share findings. [M01 p.16-17]

### Connections to earlier learning

[[courses/computer_architecture/lectures/en/2026-09-01-lecture-01|Lecture 1]] introduced the ISA/implementation boundary, the stored-program perspective, and the broad CPU-memory-I/O organization. This deck makes that boundary more precise. “The CPU executes a program” becomes “each instruction changes architectural state according to a specified rule.” [M01 p.4-10]

An implementation can change cache size or execution organization while preserving the meaning of supported instructions. This does not mean that the same ISA family name guarantees compatibility across arbitrary operating systems, libraries, or unsupported instruction extensions. The distinction here concerns the common instruction contract and the internal organization that implements it. [M01 p.5-6] [M01 p.9]

Programming concepts also acquire a concrete machine interpretation. Variables occupy registers or memory. Array operations require addresses and loads/stores. Functions and global objects defined in separate source files require linking. This is why the deck discusses linking and loading in an ISA lesson: before asking how instructions execute, ask where the instructions and initial data came from. [M01 p.18-24]

The first explains an instruction's local effect; the second explains how the program and its data become available for those effects. [M01 p.10-15] [M01 p.19-24]

## Key Takeaways

<span id="10-minute-review"></span>

- ISA specifies observable state and instruction effects; microarchitecture implements them.
- Track reads, writes and next PC. A register value used as an address is not the data stored there.
- Load/store separate memory access from ALU work; an immediate operand does not violate this distinction.
- Linker resolves symbols/placement; loader prepares memory. Neither substitutes for instruction execution.
- Distinguish sections from loadable segments, and instruction count from execution time. All coverage here is material-based, not verified classroom speech.

### Stage 1: Check the concepts

**1. Distinguish ISA from microarchitecture using instruction meaning and implementation.**

<details><summary>Answer</summary>

ISA specifies program-visible state and instruction effects. Microarchitecture is the organization that produces those effects. The same addition semantics can be implemented with different resources and cycle counts. [M01 p.5-6]

</details>

**2. Does the PC contain the current instruction or the address of that instruction?**

<details><summary>Answer</summary>

In the slide's state model, the PC contains the current instruction's memory address. The binary instruction contents and the address used to fetch them are different values. [M01 p.10]

</details>

**3. Why does `addi x5, x5, 1` not violate the load-store principle?**

<details><summary>Answer</summary>

The 1 is an immediate, not a memory operand. The computation combines x5 with a constant included in the instruction, rather than directly fetching an ALU operand from data memory. [M01 p.13] [M01 p.24] [EX:ca_2025_2_midterm_q02 p.2]

</details>

**4. State the relationship between instructions and data in the stored-program view.**

<details><summary>Answer</summary>

Both can be stored as binary values in memory, so instructions can be fetched from memory. This does not by itself determine code-write permissions or the CPU's internal cache organization. [M01 p.7] [EX:ca_2025_2_midterm_q01 p.2](exam_questions/ca_2025_2_midterm_q01)

</details>

### Stage 2: Apply and trace

**5. In example A, what are the PC, x5, and memory value immediately after `addi`?**

<details><summary>Answer</summary>

The PC is `0x1008`, x5 holds 42, and `MEM[0x2000]` still holds 41. The store that copies the new register value into memory has not executed yet. [M01 p.24]

</details>

**6. Why does register-indirect access produce 2000 in example B, while memory-indirect access produces 99?**

<details><summary>Answer</summary>

The first reads `MEM[1000]` once. The second uses that result, 2000, as the address of another read. A result that resembles an address does not automatically increase the number of dereferences. [M01 p.15]

</details>

**7. Why does the store in example C not change x10 to 9?**

<details><summary>Answer</summary>

x10 supplies the base address. The data destination of `sw x5, 0(x10)` is `MEM[GPR[x10]+0]`, not x10. Memory receives 9, and the base register remains unchanged. [M01 p.24] [EX:ca_2025_2_midterm_q12 p.4](exam_questions/ca_2025_2_midterm_q12)

</details>

**8. Why is linking necessary after translating `main.c` and `swap.c` separately?**

<details><summary>Answer</summary>

The files refer to definitions of `swap` and `buf` supplied elsewhere. References must connect to the appropriate symbols, and code/data references must agree with the combined layout. Producing independent `.o` files does not finish that work. [M01 p.19-22]

</details>

### Stage 3: Change conditions and assess designs

**9. If example A omits its last store, has the program incremented memory by one?**

<details><summary>Answer</summary>

No. x5 holds 42 but memory remains 41. First identify which state location the requirement says must change. A computed register result alone does not fulfill a memory-update requirement. [M01 p.24]

</details>

**10. Must replacing three instructions with one new instruction make the program three times faster?**

<details><summary>Answer</summary>

No. Instruction count is not execution time. Internal work, memory accesses, and clock conditions still matter. The current exercise specifies the architectural effect, not a measured datapath speedup. [M01 p.5] [EX:ca_2025_2_midterm_q14 p.6]

</details>

**11. If two threads each read 41 and later store 42, what final increment is possible?**

<details><summary>Answer</summary>

If both reads occur first and both stores write 42, the final value can be 42 even though each thread intended to increment once. This is a new interleaving thought experiment, not a full memory-model analysis or the semaphore solution to Q18. It illustrates why a multi-instruction update may require separate synchronization. [M01 p.11] [M01 p.24] [EX:ca_2025_2_midterm_q18 p.9](exam_questions/ca_2025_2_midterm_q18)

</details>

**12. What is gained and sacrificed by leaving some encoding bits unused today?**

<details><summary>Answer</summary>

Reserved space preserves choices for future extensions and compatibility, while forgoing some immediate encoding capacity. This applies the slide's open-ended-design trade-off; it is not a performance calculation for a specific proposed ISA extension. [M01 p.9] [M01 p.26]

</details>

#### Practice P01

Synthetic study exercise · not an actual question, official answer, or prediction.

**Scope/prerequisites:** load-store, based addressing and visible state; current material scope. [M01 p.10-15] [M01 p.24]  
**Style evidence:** this original variation expands Q2's operand claim into an address/value trace and counterexample. No branches, encoding or pipeline timing are required. [EX:ca_2025_2_midterm_q02 p.2]

Initially PC=0x1000, x10=0x2000, x5=99, MEM[0x2000]=7 and MEM[0x2004]=20 (word values). Execute three consecutive 4-byte instructions: lw x5,4(x10); addi x5,x5,3; sw x5,0(x10). Addresses are valid/aligned; there are no exceptions or concurrent changes.

(a) Trace PC, x5, x10 and both memory values after each instruction.  
(b) Evaluate: “load adds offset 4 to the loaded data”; “memory becomes 23 immediately after addi”; “store empties x5.”  
(c) Is addi a counterexample to load-store, or to “every ALU input consists of two registers”?

<details><summary>Worked solution and study rubric · 12 points</summary>

| Completed instruction | Next PC | x5 | x10 | MEM[0x2000] | MEM[0x2004] |
|---|---|---:|---|---:|---:|
| lw | 0x1004 | 20 | 0x2000 | 7 | 20 |
| addi | 0x1008 | 23 | 0x2000 | 7 | 20 |
| sw | 0x100c | 23 | 0x2000 | 23 | 20 |

Read 20 at address 0x2000+4, add 3, then store at the different address 0x2000. All three claims in (b) are false: offset selects an address, addi changes a register, and store preserves its source register.  
(c) An immediate is not a memory operand. It refutes the “two registers only” claim, not the load-store principle. Rows describe completed architectural instructions, not CPU clock cycles.

**Rubric:** three state rows 6; reasons for the three false claims 3; immediate/memory distinction 2; instruction/cycle boundary 1.

</details>

#### Practice P02

Synthetic study exercise · not an actual question, official answer, or prediction.

**Scope/prerequisites:** separate compilation, symbol resolution and relocation; current material scope. [M01 p.18-22]  
**General practice — no relevant exam evidence:** no supplied question directly tests these linker distinctions. This original problem preserves an important source topic.

In a hypothetical A.c, externally visible items and main are defined, and rotate from B.c is called. B.c references items via extern, defines rotate, and contains a file-scope static pointer plus an automatic temporary variable inside a function.

(a) Classify A's rotate reference, B's items reference, the static pointer and the function temporary using p.20's distinctions.  
(b) In the slide's simplified relocation model, items moves from address 0x3000 to 0x5000. What must a pointer initialized to the first element's address reflect?  
(c) What is lost by calling assembler, linker and loader “file-concatenation stages”?

<details><summary>Worked solution and study rubric · 10 points</summary>

(a) The first two are external references resolved to another file's definitions. The file-scope static pointer is a local linker symbol; the function temporary is an ordinary local variable. “Local” does not make these identical, and the distinction does not prove that a temporary name can never appear in debug information.  
(b) The pointer must reflect 0x5000 in this model. Retaining 0x3000 or substituting the element's data value would not preserve the address relation. This is not a specification of every relocation format or dynamic-linking case.  
(c) The assembler translates assembly into a machine-code object; the linker connects definitions/references and placement; the loader prepares runtime memory. Subsequent ISA execution changes data according to instruction semantics.

**Rubric:** four classifications 4; relocated value and address/data reasoning 3; three tool roles 3.

#### Practice P03

Synthetic study exercise · not an actual question, official answer, or prediction.

**Scope/prerequisites:** ELF file/runtime distinction, .bss and zero initialization; solvable from the material and the explicitly cited ELF supplement. [M01 p.22-23]  
**General practice — no relevant exam evidence:** the supplied exam has no matching ELF-loading demand.

A hypothetical loadable segment has 24 file-backed bytes and requires 40 bytes in memory. Copy the first 24 from the file and zero-fill the rest.

(a) How many bytes are copied and zero-filled?  
(b) Does this prove the entire ELF file is 24 bytes or that one .bss section is exactly 16 bytes?  
(c) Is it inconsistent for .bss to occupy runtime memory without storing its complete initial-value payload in the file?

<details><summary>Worked solution and study rubric · 8 points</summary>

(a) Copy 24 bytes and zero-fill 40−24=16 bytes.  
(b) No. These are one segment's sizes. The file may contain headers and other segments/sections; the difference cannot be equated one-to-one with a particular section from the given facts.  
(c) No. Zero-initialized memory and absent initial-value payload are compatible. Section metadata is distinct from that payload. This is a calculation under stated assumptions, not an actual ELF execution experiment. [ELF Program Header](https://refspecs.linuxfoundation.org/elf/gabi4%2B/ch5.pheader.html)

**Rubric:** amounts/units 2; file/segment distinction 2; avoiding section equivalence 2; .bss explanation 2.
