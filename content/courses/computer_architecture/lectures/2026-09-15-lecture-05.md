이번 강의는 컴퓨터가 얼마나 빠른지 판단하는 기준과, 여러 실행 결과를 비교·요약하는 방법을 다룬다.  
시간·사이클·명령어 수를 연결하고, Register·Memory 자원 차이와 설계 분야별 영향을 설명하며, 부분 개선의 한계와 평균 선택의 조건을 판단하는 것이 목표다.

## 강의 내용과 설명

### Functional correctness와 Performance: 올바른 실행을 어떻게 평가할 것인가

**Functional correctness(기능적 정확성)**는 프로세서가 명령어의 명세에 맞게 동작하는 성질이다. 덧셈 명령은 정해진 방식으로 계산해야 하고, 데이터 이동 명령은 지정된 데이터를 옮겨야 하며, 제어 명령은 프로그램의 실행 순서를 올바르게 바꾸어야 한다. 앞서 다룬 **Instruction set architecture(명령어 집합 구조, ISA)**가 실행해야 할 동작을 정한다면, 프로세서 설계는 그 동작을 실제로 구현하는 문제다. [STT 01:59] [STT 02:08]

**Performance(성능)**는 올바른 실행을 전제로, 주어진 일을 얼마나 빠르게 수행하거나 일정 시간에 얼마나 많이 처리하는지를 평가한다. 정답을 내는 두 프로세서라도 같은 프로그램을 끝내는 시간은 다를 수 있다. 따라서 명령어를 실행할 수 있다는 사실만으로 설계의 우수성을 모두 설명할 수는 없다. 이번 강의는 실제 프로세서 설계를 배우기 전에, 무엇을 측정하고 어떤 기준으로 비교할지를 정하는 데 목적이 있다. [M01 p.2] [STT 02:08]

강의 도입에서는 **3.7 GHz** 프로세서가 **2점대 GHz(2 point something GHz)** 프로세서보다 나을 수도 있다는 예를 들며 “might be better”라고 표현했다. 이는 성능 측정의 필요성을 설명하기 위한 도입 예시이며, 실제 Benchmark 측정 결과가 아니다. 그러나 주파수는 성능에 영향을 주는 여러 인자 중 하나다. 서로 다른 프로세서를 비교하면서 주파수만 보고 전체 실행 시간의 우열을 확정해서는 안 된다. 이후의 [[concepts/cpu-execution-time|CPU execution time]] 식은 주파수뿐 아니라 명령어당 필요한 사이클 수와 실행되는 명령어 수도 함께 보아야 하는 이유를 설명한다. [STT 03:30] [M01 p.6]

### Latency와 Throughput: 한 작업의 시간과 여러 작업의 처리율

**Latency(지연시간)**는 한 작업이 시작해서 끝날 때까지 걸린 시간이다. 네트워크 서버라면 한 요청을 처리하는 시간, 게임이라면 사용자의 입력에 반응하는 시간이 대표적인 관심 대상이다. 사용자가 자신의 요청에 대한 결과를 기다리는 상황에서는 Latency가 작을수록 빠르게 반응한다고 느낀다. [M01 p.3] [STT 04:28] [STT 05:26]

**Throughput(처리율)**은 단위 시간에 완료한 작업의 수다. 서버가 일정 시간에 처리한 요청이나 연결의 수처럼, 개별 작업의 소요 시간보다 전체 처리량을 평가할 때 사용한다. 여러 요청을 묶어 처리하는 **Batch application(일괄 처리 응용)**에서는 이러한 처리율이 중요한 기준이 된다. [M01 p.3] [STT 05:26] [STT 06:27]

| 지표 | 측정하는 대상 | 단위의 예 | 강의에서 사용한 상황 |
|---|---|---|---|
| Latency | 한 작업의 시작부터 완료까지의 시간 | 초, 밀리초 | 게임 입력에 대한 반응, 서버의 개별 요청 |
| Throughput | 일정 시간에 완료한 작업 수 | 작업/초, 요청/초 | 여러 요청을 처리하는 서버, Batch application |

두 지표를 연결할 때는 **Concurrency(동시성)**를 고려해야 한다. 작업을 하나씩 순서대로 처리하고 작업 사이의 대기나 추가 비용이 없다면, 작업 하나에 걸리는 시간의 역수로 처리율을 구할 수 있다. 하지만 여러 작업을 동시에 진행하면 한 작업의 Latency와 전체 Throughput은 서로 다른 양이 된다. 강의에서도 여러 연결을 동시에 처리하는 웹 서버를 사용해 이 차이를 설명했다. [STT 07:23]

**이해를 위한 예시:** 요청 하나에 항상 0.1초가 걸리고, 요청이 충분히 공급된다고 하자. 요청을 하나씩 처리하면 초당 10개를 완료한다. 동일한 요청 네 개를 서로 간섭 없이 동시에 처리할 수 있다면 초당 40개를 완료할 수 있다. 각 요청의 Latency는 여전히 0.1초지만 Throughput은 네 배가 된다. 이 예시에서는 동시 처리에 따른 추가 비용과 자원 경쟁을 없다고 가정했다.

자료의 버스와 경주용 자동차 비유도 같은 구분을 돕는다. 한 사람을 목적지에 빨리 보내는 능력과 많은 사람을 일정 시간에 운송하는 능력은 동일한 평가 기준이 아니다. 강사는 프로세서의 주파수를 무한히 높일 수 없다는 한계에서 **Multicore(멀티코어)**의 도입 동기를 설명하고, 여러 Core로 Throughput을 높이는 예를 들었다. 이렇게 여러 작업을 처리할 수 있게 되었다고 해서 개별 작업의 Latency가 반드시 같은 비율로 줄어드는 것은 아니다. [M01 p.3] [STT 07:23] [STT 08:19]

그렇다고 두 지표가 완전히 무관한 것도 아니다. 전체 작업에 필요한 구성 요소의 처리율이 개선되면 그 요소를 기다리는 시간이 줄어 전체 Latency에 도움이 될 수 있다. 핵심은 개선이 어느 작업과 어느 자원에 적용되는지를 확인하는 것이다. [M01 p.3]

**오개념 주의:** Throughput을 언제나 $1/\text{Latency}$로 계산하지 않는다. 또한 주파수가 고정되어 있다는 사실만으로 Latency도 고정된다고 판단할 수 없다. 08:19의 STT에는 Latency의 증가·감소 방향이 불명확한 부분이 있어 **검증 필요**이며, 이를 명확한 인과관계로 복원하지 않는다. [[concepts/latency-throughput|Latency와 Throughput]]을 비교할 때는 개별 요청의 시간과 동시 처리되는 전체 작업량을 분리해서 읽어야 한다.

### Performance를 시간의 역수로 표현하는 조건

강의는 동일한 일을 수행하는 시간이 짧을수록 성능이 높다는 관계를 다음과 같이 표현한다. [M01 p.4] [STT 09:05]

$$
\text{Performance}=\frac{1}{\text{Time}}
$$

이 식의 역할은 서로 다른 시간값을 같은 방향의 성능 지표로 바꾸는 것이다. 같은 프로그램이 같은 입력을 처리할 때 실행 시간이 절반이 되면 Performance는 두 배가 된다. 시간이 짧을수록 좋다는 기준을, 성능값이 클수록 좋다는 기준으로 표현한 셈이다.

다만 식을 적용하기 전에 어떤 시간을 비교하는지 정해야 한다. 프로그램 전체의 완료 시간인지, CPU가 실제로 실행에 사용한 시간인지, 요청 하나의 응답 시간인지에 따라 측정값의 의미가 달라진다. 서로 다른 종류의 시간을 분자와 분모에 넣으면 계산은 가능해도 성능 비교로서의 의미가 사라진다.

Throughput과의 관계에서도 작업량을 맞춰야 한다. 동일한 작업 $J$개를 처리하는 데 걸린 시간이 $T$라면,

$$
\text{Throughput}=\frac{J}{T}
$$

이므로 $J$를 고정했을 때 시간이 짧아질수록 Throughput이 높아진다. 그러나 서로 다른 난도의 작업이나 다른 수의 작업을 비교하면서 Throughput이 높다는 이유만으로 개별 작업의 시간이 줄었다고 결론낼 수는 없다. 강의의 분모가 작아진다는 설명은 이러한 고정 작업량 조건에서 이해해야 한다. [STT 09:05] [STT 22:43]

### Elapsed time과 CPU time: 기다린 시간과 실행에 사용한 시간

**Elapsed time(경과 시간)** 또는 **Wall-clock time(실제 경과 시간)**은 프로그램의 시작부터 종료까지 외부 시계로 측정한 시간이다. 사용자가 명령을 실행한 뒤 완료를 기다린 시간에 해당한다. 반면 CPU가 해당 프로그램의 실행에 사용한 시간은 별도로 구분할 수 있다. 강의는 UNIX의 `time` 명령을 통해 소프트웨어에서 측정한 시간을 프로세서 성능 분석과 연결한다. 강사는 이 명령을 Mac에서도 실행할 수 있다고 안내했다. [M01 p.4] [STT 10:12]

**User CPU time(사용자 코드 실행 CPU 시간)**은 프로그램 자신의 코드를 실행하는 데 사용한 CPU 시간이다. **System CPU time(시스템 코드 실행 CPU 시간)**은 그 프로그램을 대신해 시스템 코드를 실행한 CPU 시간이며, 강의에서는 시스템 호출을 예로 들었다. [STT 11:12]

| `time`의 출력 항목 | 대응하는 개념 | 읽는 방법 |
|---|---|---|
| `real` | Elapsed time | 명령의 시작부터 종료까지 실제로 경과한 시간 |
| `user` | User CPU time | 프로그램 자신의 코드 실행에 사용한 CPU 시간 |
| `sys` | System CPU time | 프로그램을 위한 시스템 코드 실행에 사용한 CPU 시간 |

**자료 그림 읽기 — 반복 출력과 시간 측정:** p.5의 그림에는 `time yes "hello"`와 반복되는 `hello` 출력, 그리고 다음 측정값이 함께 제시되어 있다. 명령 문자열과 숫자를 따로 읽지 말고, 출력 작업을 수행한 전체 시간과 CPU 사용 시간을 비교해야 한다. [M01 p.5] [STT 12:12]

```text
real    0m1.260s
user    0m0.002s
sys     0m0.013s
```

자료 p.5 하단에는 더 자세한 설명을 위해 Linux에서 `man 7 time`을 참고하라는 안내도 있다. [M01 p.5]

이 실행에서 CPU time은 다음과 같다.

$$
T_{\text{CPU}}
=
T_{\text{user}}+T_{\text{system}}
=
0.002+0.013
=
0.015\text{ s}
$$

Elapsed time은 1.260초이므로 CPU time보다 훨씬 길다. 강사는 터미널에 많은 문자를 출력하는 **I/O(입출력)**를 이 차이의 원인으로 설명했다. CPU가 계산을 수행한 시간과 출력 완료를 기다리는 전체 시간이 다를 수 있다는 점이 이 사례의 학습 목적이다. I/O의 세부 동작은 이후 수업으로 미루었다. [STT 13:07]

다만 세 숫자만으로 모든 지연의 원인을 정확히 분해할 수 있는 것은 아니다. 이 사례에서 Elapsed time과 CPU time의 차이는 1.245초지만, 이를 추가 측정 없이 전부 특정 I/O 동작의 시간이라고 확정해서는 안 된다. 자료의 차이 설명은 대기와 다른 시스템 활동이 개입할 수 있다는 해석으로 읽는다. [M01 p.4]

자료가 제시한 측정 원칙은 무엇을 측정했는지 정확히 밝히고, 다른 부하가 없는 시스템에서 Wall-clock time을 측정·보고하는 것이다. 측정 조건이 달라지면 CPU 설계 자체의 차이와 실행 환경의 영향을 구분하기 어려워지기 때문이다. [M01 p.4]

**오개념 주의:** `sys`는 컴퓨터 전체에서 발생한 모든 시스템 활동의 시간이 아니다. 해당 프로그램을 대신해 수행한 시스템 코드의 CPU 시간이다. STT에서 세 번째 출력 항목을 지칭하는 표현은 불명확하지만, 그림의 실제 항목은 `sys`로 확인된다. [M01 p.5] [STT 12:12]

### CPI·IPC·MIPS·GHz를 CPU execution time으로 연결하기

**CPU execution time(CPU 실행 시간)**을 이해하려면 실행된 명령어 수, 명령어당 필요한 사이클 수, 사이클 하나의 길이를 연결해야 한다. **Clock cycle(클록 사이클)**은 프로세서 동작을 시간적으로 구분하는 기본 단위이고, 주파수는 초당 몇 사이클이 진행되는지를 나타낸다. [M01 p.6] [STT 14:11] [STT 15:10]

자료에서 사용하는 지표는 다음과 같다.

| 지표 | 영어 표기 또는 의미 | 단위 |
|---|---|---|
| CPI(명령어당 사이클 수) | cycle per instruction | cycles/instruction |
| IPC(사이클당 명령어 수) | instruction per cycle | instructions/cycle |
| MIPS(초당 백만 명령어 수) | million instruction per second | $10^6$ instructions/second |
| GHz | 초당 $10^9$ 사이클에 해당하는 주파수 단위 | $10^9$ cycles/second |
| Instruction count(실행 명령어 수) | 한 프로그램 실행에서 수행된 명령어 수 | instructions/program |

자료 p.6의 핵심 식은 단위가 소거되는 순서로 읽으면 이해하기 쉽다.

$$
\begin{aligned}
T_{\text{CPU}}
&=
\frac{\text{time}}{\text{cycle}}
\times
\frac{\text{cycles}}{\text{instruction}}
\times
\frac{\text{instructions}}{\text{program}}\\
&=
\text{Cycle time}
\times
\text{Average CPI}
\times
\text{Instruction count}
\end{aligned}
$$

명령어 수를 $N$, 주파수를 $F$ cycles/s, 평균 CPI를 $C$라고 쓰면,

$$
T_{\text{CPU}}=\frac{NC}{F}
$$

가 된다. 먼저 $N$개의 명령어를 실행하는 데 총 $NC$사이클이 필요하고, 초당 $F$사이클을 진행하므로 실행 시간은 $NC/F$초라는 뜻이다. [M01 p.6]

여기서 GHz의 배율을 빠뜨리지 않아야 한다. 주파수가 $g$ GHz라면,

$$
F=g\times10^9\text{ cycles/s},
\qquad
\text{Cycle time}
=
\frac{1}{g\times10^9}\text{ s/cycle}
$$

이다. 예를 들어 2 GHz의 Cycle time은 0.5 ns다. 자료의 `1/GHz` 표기를 초 단위 식으로 사용할 때는 $10^9$를 포함해야 한다. 마찬가지로 처리율이 $m$ MIPS라면 평균 명령어당 시간은 $1/(m\times10^6)$초다. 자료의 간략 표기를 읽을 때 수치의 역수와 단위까지 포함한 역수를 구분해야 한다. [M01 p.6]

**이해를 위한 예시:** 동일한 프로그램이 $8\times10^8$개의 명령어를 실행한다고 하자. 프로세서 A의 평균 CPI가 1.5이고 주파수가 2 GHz라면,

$$
T_A=
\frac{8\times10^8\times1.5}{2\times10^9}
=
0.6\text{ s}
$$

이다. 프로세서 B의 평균 CPI가 2이고 주파수가 3 GHz라면,

$$
T_B=
\frac{8\times10^8\times2}{3\times10^9}
=
\frac{8}{15}\text{ s}
\approx0.5333\text{ s}
$$

이다. B는 명령어당 더 많은 사이클을 사용하지만, 사이클이 더 짧아서 전체 실행 시간은 짧다. 이 예시는 CPI가 작다는 사실이나 GHz가 크다는 사실 하나만으로 전체 성능을 판단할 수 없음을 보여 준다.

**기출의 요구 능력과 연결:** 2025-2 중간고사 복기본 Q11(a)·(b)는 실행 시간·주파수·Instruction count를 이용해 CPI를 구하거나 목표 실행 시간에 필요한 CPI를 역산하도록 요구한다. 접근은 위 식을

$$
C=\frac{T_{\text{CPU}}F}{N}
$$

으로 정리하는 것이다. 숫자를 대입하기 전에 시간과 주파수의 단위를 맞추고, 문제에 적힌 명령어 수를 그대로 사용해야 한다. 예상보다 작은 CPI가 나왔다는 인상만으로 원문 수치를 바꾸면 안 된다. [EX:ca_2025_2_midterm_q11 p.3]

이 본문에 연결한 기출은 공식 원본이 아닌 **2025-2 중간고사 복기 자료**다. 원문·정답의 정확성과 교수자 동일성은 독립적으로 확인되지 않았다. 연결의 목적은 현재 강의의 계산과 판단을 적용하는 데 있으며, 현재 시험의 형식이나 출제 여부를 확정하는 근거로 사용하지 않는다.

**오개념 주의:** CPI와 IPC는 같은 실행 범위를 집계할 때 서로 역수이지만, 여러 실행에서 얻은 값을 평균할 때도 아무 평균이나 취한 뒤 역수를 계산할 수 있다는 뜻은 아니다. 또한 위의 CPU execution time 식을 I/O 대기를 포함한 Wall-clock time의 일반적인 항등식으로 사용하지 않는다. [[concepts/cpi-ipc|CPI와 IPC]]의 평균은 뒤에서 총 명령어 수와 총 사이클 수로 다시 확인한다.

### Instruction 종류와 설계 선택이 실행 시간에 미치는 영향

모든 명령어가 같은 자원을 사용하거나 같은 수의 사이클을 요구하는 것은 아니다. 강사는 **Arithmetic operation(산술 연산)**, **Data movement operation(데이터 이동 연산)**, **Branch operation(분기 연산)**을 다시 언급하며 명령어 종류에 따라 CPI가 달라질 수 있다고 설명했다. [STT 16:05]

강의에서 사용한 정성적 비교는 **Register(레지스터)**와 **Memory(메모리)**의 차이다. Register 중심의 연산과 Memory 접근을 수반하는 데이터 이동은 서로 다른 자원을 사용한다. 앞서 배운 작은 저장장치가 빠르다는 설명을 연결해, 명령어를 모두 동일한 비용의 작업으로 취급할 수 없다는 동기를 제시했다. 다만 이 설명을 모든 산술 명령이 모든 데이터 이동 명령보다 항상 빠르다는 보편적인 규칙으로 확대하지 않는다. [STT 16:05]

명령어 종류 $i$의 실행 횟수가 $N_i$, 그 종류의 평균 CPI가 $C_i$라면 전체 실행의 평균 CPI는 정의상 다음과 같다.

$$
C_{\text{avg}}
=
\frac{\text{Total cycles}}{\text{Total instructions}}
=
\frac{\sum_i N_iC_i}{\sum_i N_i}
$$

전체 명령어 수를 $N=\sum_iN_i$라고 하면,

$$
C_{\text{avg}}
=
\sum_i\frac{N_i}{N}C_i
$$

이다. 즉, 각 종류의 CPI를 그 종류가 차지하는 **명령어 개수 비중**으로 가중해야 한다.

**이해를 위한 예시:** 실행 명령어의 90%가 CPI 1인 종류이고, 나머지 10%가 CPI 5인 종류라고 가정하자.

$$
C_{\text{avg}}
=
0.9\times1+0.1\times5
=
1.4
$$

두 종류가 있다는 이유로 $(1+5)/2=3$을 계산하면, 실제로 더 자주 실행된 종류를 반영하지 못한다. 이 예시의 90%와 10%는 명령어 개수 비중으로 새로 지정한 조건이다. 강의의 37:12 발화는 시간 비중으로 표현되어 있으므로, 그것이 명령어 개수 비중으로 정확히 발화되었다고 바꾸어 기록하지 않는다. [STT 37:12]

자료 p.6은 실행 시간의 세 인자가 서로 다른 설계 영역과 관련되어 있음을 보여 준다.

| 실행 시간의 인자 | 자료가 연결한 영향 요인 | 해석 |
|---|---|---|
| 주파수와 Cycle time | Semiconductor technology(반도체 기술), `uarch` | 회로 기술과 프로세서 내부 설계가 사이클의 길이에 영향을 준다. |
| CPI | `uarch`, ISA | 명령어가 요구하는 동작과 그 동작의 구현 방식이 사이클 수에 영향을 준다. |
| Instruction count | ISA, Compiler(컴파일러) | 같은 일을 어떤 명령어열로 수행하게 만드는지가 달라질 수 있다. |

강사는 이 수업에서 프로세서 설계를 통해 주로 CPI에 해당하는 부분을 다루겠다고 설명했다. 또한 같은 프로그램도 Compiler의 최적화에 따라 실행되는 명령어 수가 달라질 수 있다고 지적했다. 따라서 Instruction count를 소스 코드의 줄 수와 동일시해서는 안 된다. `Hello world`와 Chromium의 대비는 서로 다른 프로그램의 작업 규모가 크게 다를 수 있음을 보여 준 강의 고유의 사례다. [STT 17:01] [STT 17:56] [STT 18:54]

세 인자는 서로 독립된 조절 손잡이도 아니다. 어떤 설계 변경이 CPI를 줄이면서 Cycle time을 늘릴 수 있고, 같은 작업의 명령어 수가 달라질 수도 있다. 최종 판단은 개별 인자의 변화와 함께 $NC/F$ 전체를 다시 계산해야 한다는 것이다. [M01 p.6]

**검증 필요:** 17:56의 STT에는 좋지 않은 설계와 더 작은 CPI를 연결하는 불명확한 표현이 있다. 이를 강사의 확정된 설명으로 채택하거나 반대 방향으로 복원하지 않는다. 다른 조건이 동일하면 작은 CPI가 실행 시간을 줄인다는 사실은 자료의 식에서 별도로 도출한다.

### Runtime과 Energy: 성능 비교가 여러 기준을 가질 때

**Runtime(실행 시간)**을 최소화하는 것과 **Energy(에너지)** 사용을 최소화하는 것은 서로 다른 목표다. **Power(전력)**는 에너지를 소비하는 시간적 비율이며, 자료는 다음 관계를 제시한다. [M01 p.7]

$$
\text{Power}=\frac{\text{Energy}}{\text{Time}}
$$

같은 실행 구간에서 소비한 총 Energy를 그 구간의 Time으로 나누면 평균 Power를 얻는다. 실행이 빨라졌다고 해서 Energy도 반드시 줄어드는 것은 아니다. 더 많은 에너지를 사용해 빠르게 실행하는 선택이 있을 수 있고, 실행 시간을 늘리면서 에너지 사용을 줄이는 선택도 있을 수 있다. 자료는 이를 두 기준 사이의 **Trade-off(상충관계)**로 제시한다. [M01 p.7]

**이해를 위한 예시:** 어떤 실행이 2초 동안 20 J를 소비했다면 평균 Power는 10 W다. 다른 실행이 1초 동안 15 J를 소비했다면 평균 Power는 15 W다. 두 번째 실행은 Runtime과 Energy가 모두 작지만 평균 Power는 더 크다. 따라서 빠르다, 에너지가 적게 든다, 전력이 낮다는 표현은 각각 무엇을 비교하는지 구분해서 사용해야 한다.

강사는 무거운 AI 작업을 예로 들며 Energy가 중요한 설계·연구 기준임을 언급했다. 이어 Intel 노트북과 MacBook의 Performance가 비슷하더라도 MacBook이 훨씬 효율적이고 발열 문제를 겪지 않는다고 말하며, 이를 Apple의 Energy 최적화와 연결했다. 이는 강사의 정성적 일화이며, 동일 조건에서 측정한 Benchmark나 모든 제품에 대한 검증된 성능·발열 비교 결과로 취급하지 않는다. [STT 19:47] [STT 20:46]

자료에는 **Implementation cost(구현 비용)**, **Reliability(신뢰성)**, **Security(보안)**도 추가 기준으로 나온다. 다만 강사는 이번 강의에서 Performance에 집중한다고 명시했다. 따라서 이 페이지는 성능 외의 평가 기준을 인식하기 위한 자료이며, 상세한 에너지 모델이나 보안 설계를 이번 회차에서 학습했다고 보지는 않는다. [M01 p.7] [STT 20:46]

### Relative performance와 Speedup: 비율의 방향을 먼저 정하기

**Relative performance(상대 성능)**는 기준 대상에 비해 얼마나 빠른지를 나타낸다. 컴퓨터 두 대를 비교하거나 기존 설계를 개선했을 때, 단순히 더 빠르다고 말하는 대신 비율을 사용하면 개선 정도를 표현할 수 있다. 자료 p.8은 두 컴퓨터의 속도를 비교하는 문제와 여러 프로그램의 결과를 하나의 수치로 나타내는 문제를 구분해 제시한다. [M01 p.8] [STT 22:00]

강의에서 X가 Y보다 $n$배 빠르다는 표현은 다음 정의를 따른다.

$$
n
=
\frac{\text{Performance}_X}{\text{Performance}_Y}
=
\frac{T_Y}{T_X}
$$

동일한 작업량을 비교할 때는 Throughput의 비율로도 표현할 수 있다. 시간 비율에서는 분자와 분모의 방향이 성능 비율과 반대라는 점이 핵심이다. 더 빠른 X의 실행 시간이 분모에 놓여야 $n>1$이 된다. [M01 p.10] [STT 24:36]

$m\%$ 빠르다는 표현은 Performance가 기준보다 $m\%$ 증가했다는 뜻이다.

$$
1+\frac{m}{100}
=
\frac{\text{Performance}_X}{\text{Performance}_Y}
=
\frac{T_Y}{T_X}
$$

**강의 고유 예시 — 50% faster:** X에서 1초 걸리던 프로그램을 Y가 50% 더 빠르게 실행한다고 하자. 강의의 정의에 따르면 Y의 Performance는 X의 1.5배다.

$$
\frac{T_X}{T_Y}=1.5
\quad\Rightarrow\quad
T_Y=\frac{1}{1.5}
=\frac{2}{3}\text{ s}
\approx0.6667\text{ s}
$$

반면 Y에서 0.5초가 걸린다면,

$$
\frac{T_X}{T_Y}=\frac{1}{0.5}=2
$$

이므로 Performance가 두 배, 즉 100% 증가한 것이다. 이때 실행 시간의 감소율은 50%다. **성능 증가율과 시간 감소율은 서로 다른 기준값을 분모로 사용한다.** [M01 p.9] [M01 p.10] [STT 23:41] [STT 26:22]

기존 설계에 개선을 적용했을 때 사용하는 **Speedup(성능 향상 배수)**도 같은 비율이다.

$$
S
=
\frac{T_{\text{without enhancement}}}
{T_{\text{with enhancement}}}
=
\frac{T_{\text{old}}}{T_{\text{new}}}
$$

자료 p.11에서 X는 Y를 개선한 버전이므로 $S=T_Y/T_X$다. 실행 시간이 줄면 $S>1$, 시간이 같으면 $S=1$, 오히려 길어지면 $S<1$이 된다. [M01 p.11] [STT 27:22]

**오개념 주의:** Speedup은 시간끼리 나눈 무차원 비율이다. 1.5배라는 값을 1.5초로 읽지 않는다. 또한 개선 후 시간을 개선 전 시간으로 나누면 시간의 잔존 비율을 얻으며, 위에서 정의한 Speedup의 역수가 된다.

### Amdahl’s Law: 개선하지 않은 시간이 전체 효과를 제한한다

**Amdahl’s Law(암달의 법칙)**는 작업의 일부를 개선했을 때 전체 Speedup이 얼마나 되는지를 설명한다. 동기는 단순하다. 프로그램의 특정 부분이 매우 빨라졌더라도 나머지 부분이 그대로라면, 전체 실행 시간이 같은 배수로 줄어들 수는 없다. [M01 p.12] [STT 28:21]

개선 전 전체 시간을 $T_{\text{old}}$, 그중 개선 대상이 차지하는 **시간 비중**을 $f$, 해당 부분의 Speedup을 $S_f$라고 하자. 나머지 부분의 시간과 작업 구성이 변하지 않고 추가 비용이 없다고 가정하면,

$$
T_{\text{new}}
=
T_{\text{old}}
\left((1-f)+\frac{f}{S_f}\right)
$$

이다. 따라서 전체 Speedup은 다음과 같다.

$$
S_{\text{overall}}
=
\frac{T_{\text{old}}}{T_{\text{new}}}
=
\frac{1}{(1-f)+f/S_f}
$$

**자료 그림 읽기 — 위아래 막대의 길이:** p.12의 위쪽 막대는 개선 전 시간을 나타내며, 개선하지 않는 부분 $1-f$와 개선할 부분 $f$로 나뉜다. 아래쪽 막대에서는 $1-f$의 길이가 그대로 유지되고, $f$ 부분만 $f/S_f$로 짧아진다. 그림을 읽을 때 중요한 것은 전체 막대가 $1/S_f$배가 되는 것이 아니라, 선택한 부분만 줄어든다는 점이다. [M01 p.12]

**이해를 위한 예시:** 전체 실행 시간이 100초이고 그중 20초만 개선할 수 있다고 하자. 이 부분을 10배 빠르게 만들면,

$$
T_{\text{new}}
=
80+\frac{20}{10}
=
82\text{ s}
$$

이고,

$$
S_{\text{overall}}
=
\frac{100}{82}
=
\frac{50}{41}
\approx1.22
$$

다. 개선한 부분의 Speedup은 10이지만 전체 Speedup은 약 1.22에 그친다.

반대로 원래 시간의 80%를 차지하는 부분을 두 배 빠르게 하면,

$$
T_{\text{new}}
=
20+\frac{80}{2}
=
60\text{ s},
\qquad
S_{\text{overall}}
=
\frac{100}{60}
\approx1.67
$$

이다. 국소적인 개선 배수가 더 작아도, 원래 시간을 많이 차지한 부분을 개선하면 전체 효과가 더 클 수 있다.

강사가 강조한 **Common case(자주 발생하는 경우)** 개선 원칙은 자주 발생하거나 자주 사용되는 부분에 노력을 집중하라는 설계 방향이다. 이를 계산으로 적용할 때는 그 부분이 원래 실행 시간에서 차지한 비중까지 확인해야 한다. 단순한 발생 횟수만으로 $f$를 정할 수는 없다. [M01 p.12] [STT 29:17]

개선 대상 부분을 한없이 빠르게 만들면 $f/S_f$는 0에 가까워지지만, 개선하지 않은 $1-f$는 남는다.

$$
\lim_{S_f\to\infty}S_{\text{overall}}
=
\frac{1}{1-f}
\qquad (f<1)
$$

앞의 $f=0.2$ 예시에서 이론적인 전체 Speedup의 상한은 $1/0.8=1.25$다. 개선 가능한 20초를 거의 제거하더라도 나머지 80초 때문에 전체를 두 배 빠르게 만들 수는 없다.

**기출의 요구 능력과 연결:** 복기본 Q6은 Amdahl’s Law에서 부분 개선의 효과가 어떤 비중에 의해 제한되는지를 판단하게 한다. 접근은 법칙의 이름을 기억하는 데서 끝나지 않고, 식의 $1-f$가 개선 후에도 남는다는 사실을 설명하는 것이다. [EX:ca_2025_2_midterm_q06 p.2]

**오개념 주의:** $f$가 작으면 $S_f$가 전혀 영향을 주지 않는다고 해석하지 않는다. 식에는 여전히 $f/S_f$가 있으므로 $S_f$에 따라 결과가 달라진다. 강의의 표현은 개선할 부분이 작을 때 전체 효과가 제한된다는 정성적 설명이다. [[concepts/amdahls-law|Amdahl’s Law]]는 국소적 개선과 전체 실행 시간의 관계를 구분하는 도구다.

30:18에서는 향후 **Pipeline(파이프라인)** 프로세서와 빈번한 Memory 접근을 연결하는 예고가 나왔다. 그러나 구체적인 적용은 이번에 다루지 않겠다고 했으며, Pipeline이 Memory 접근의 높은 Latency를 어떻게 개선한다는 것인지 자료에서 확립되지 않았다. 이 메커니즘은 **검증 필요**로 남기고, 다른 기법으로 바꾸어 설명하거나 이번에 설계를 배운 것으로 처리하지 않는다. [STT 30:18]

### Instruction count 비중과 시간 비중: 목표 달성 가능성을 먼저 판단하기

Amdahl’s Law의 $f$는 **개선 전 시간 비중**이다. 반면 평균 CPI를 계산할 때 사용하는 가중치는 **명령어 개수 비중**이다. 이 둘을 혼동하면 식에 들어갈 비율부터 잘못된다.

어떤 명령어 종류가 전체 명령어의 비중 $q$를 차지하고 그 종류의 평균 CPI가 $C_{\text{target}}$이라면, 동일한 주파수에서 그 종류가 차지한 시간 비중은 다음과 같이 구할 수 있다.

$$
f
=
\frac{qNC_{\text{target}}/F}{NC_{\text{avg}}/F}
=
\frac{qC_{\text{target}}}{C_{\text{avg}}}
$$

명령어 비중 $q$와 시간 비중 $f$가 같아지는 것은 해당 종류의 CPI가 전체 평균 CPI와 같을 때다. 명령어 수가 적어도 각 명령어가 많은 사이클을 사용하면 시간 비중은 커질 수 있다. 이 구분은 CPU execution time 식과 Amdahl’s Law를 함께 적용할 때 필요하다. [M01 p.6] [M01 p.12]

**이해를 위한 예시:** 전체 명령어가 $10^9$개이고 주파수가 2 GHz라고 하자. **Floating-point(부동소수점, FP)** 명령이 개수 기준 20%이며 평균 CPI는 4, 나머지 명령의 평균 CPI는 1이라고 가정한다.

$$
C_{\text{avg}}
=
0.2\times4+0.8\times1
=
1.6
$$

따라서 전체 실행 시간은,

$$
T_{\text{old}}
=
\frac{10^9\times1.6}{2\times10^9}
=
0.8\text{ s}
$$

다. FP 부분과 나머지 부분의 시간은 각각,

$$
T_{\text{FP}}
=
\frac{0.2\times10^9\times4}{2\times10^9}
=
0.4\text{ s}
$$

$$
T_{\text{other}}
=
\frac{0.8\times10^9\times1}{2\times10^9}
=
0.4\text{ s}
$$

이다. FP는 명령어 수의 20%지만 시간의 50%를 차지한다.

이제 FP 명령만 개선해 전체 실행 시간을 0.3초로 만들려 한다고 하자. 개선하지 않는 부분만 이미 0.4초가 필요하므로 목표는 불가능하다. FP 시간을 이론적으로 0에 가깝게 줄여도 전체 시간은 0.4초보다 작아질 수 없다.

동일한 판단을 CPI로도 할 수 있다. 목표 시간 0.3초에 필요한 평균 CPI는,

$$
C_{\text{required}}
=
\frac{0.3\times2\times10^9}{10^9}
=
0.6
$$

이다. 그러나 개선하지 않는 종류의 기여만 $0.8\times1=0.8$이다. 개선 대상의 기여가 음수가 될 수는 없으므로 평균 CPI 0.6은 달성할 수 없다.

**기출의 요구 능력과 연결:** 복기본 Q11(c)는 특정 명령어 종류만 개선해 목표 실행 시간을 달성할 수 있는지 검토하도록 요구한다. 위 예시는 그 판단 구조를 설명하기 위해 별도로 만든 것이며 실제 문항의 수치나 답을 재현한 것이 아니다. 먼저 개선하지 않는 부분의 시간 또는 CPI 기여를 구하고, 그것만으로 목표를 초과하는지 확인한다. 가능성을 확인하지 않고 필요한 개선 배수부터 계산하면 음수처럼 의미 없는 결과를 얻고도 놓칠 수 있다. [EX:ca_2025_2_midterm_q11 p.3]

### Workload: 무엇을 실행하느냐에 따라 성능 순위가 달라진다

**Workload(작업 구성)**는 평가할 프로그램과 입력, 그리고 여러 프로그램을 어떤 비중으로 실행하는지를 포함하는 비교 조건이다. 한 컴퓨터가 어떤 프로그램에서 빠르다고 해서 모든 프로그램에서 빠른 것은 아니다. [M01 p.13]

자료 p.13은 X가 Application A에서는 Y보다 빠르고, Application B에서는 다른 비율로 빠르며, Application C에서는 오히려 Y가 빠를 수 있다고 설명한다. 두 컴퓨터의 상대 성능은 이름만으로 정해지지 않고 실행할 작업에 따라 달라지는 것이다.

강사는 게임에서는 한 컴퓨터가 유리해도 연구 작업에서는 다른 결과가 나올 수 있다는 예를 사용했고, 말미에는 AI 작업과 게임에서 우열이 바뀔 수 있다는 설명을 반복했다. 이는 특정 제품의 검증된 우열을 제시한 것이 아니라, 비교 질문에 Workload 조건이 필요함을 보여 준 사례다. [STT 31:13] [STT 32:14] [STT 46:06]

여러 프로그램을 함께 고려할 때는 각각을 얼마나 자주 사용하는지도 중요하다. 드물게 실행하는 긴 작업 하나가 중요한 상황과, 짧은 요청을 매우 자주 처리하는 상황은 같은 평가 목적이 아니다. 따라서 한 개의 성능 수치로 요약하려면 그 수치가 어떤 Workload를 대표하는지 설명해야 한다. 이를 명확히 할 수 없다면 프로그램별 결과와 각 결과가 의미 있는 조건을 함께 제시하는 편이 낫다. [M01 p.13] [STT 33:15]

**오개념 주의:** 특정 프로그램에서 빠르다는 측정 결과를 모든 상황에서 더 좋은 컴퓨터라는 결론으로 확대하지 않는다. 뒤에서 배우는 평균들은 Workload의 의미를 없애는 방법이 아니라, 정해진 목적에 맞게 여러 값을 집계하는 방법이다.

### Arithmetic Mean: 실행 시간을 더해서 비교할 때

**Arithmetic Mean(산술평균, AM)**은 값들을 더한 뒤 개수로 나눈 것이다. 프로그램 $A_0,\ldots,A_{n-1}$의 실행 시간이 $T_0,\ldots,T_{n-1}$이라면,

$$
\operatorname{AM}(T)
=
\frac{1}{n}\sum_{i=0}^{n-1}T_i
$$

이다. 같은 프로그램 집합을 각각 한 번씩 실행한다면 총 실행 시간은 $\sum_iT_i$이므로, 두 컴퓨터의 AM을 비교하는 것은 총 실행 시간을 비교하는 것과 같다. 두 합에 동일한 $1/n$을 곱했기 때문이다. [M01 p.14]

이 해석에는 각 프로그램을 같은 횟수 실행한다는 조건이 들어 있다. 실제로 어떤 프로그램을 훨씬 자주 실행한다면, 프로그램별 실행 시간을 한 번씩만 더한 값이 실제 Workload를 대표하지 못할 수 있다.

**이해를 위한 예시:** 두 컴퓨터에서 다음과 같은 실행 시간이 측정되었다고 하자.

| 프로그램 | X의 실행 시간 | Y의 실행 시간 |
|---|---:|---:|
| $A_0$ | 1초 | 2초 |
| $A_1$ | 10초 | 6초 |

각 프로그램을 한 번씩 실행하면 X는 총 11초, Y는 총 8초가 필요하다.

$$
\operatorname{AM}_X=5.5\text{ s},
\qquad
\operatorname{AM}_Y=4\text{ s}
$$

따라서 이 실행 구성에서 Y의 X 대비 Speedup은 $11/8=1.375$다. 하지만 이 결론은 $A_0$와 $A_1$을 같은 횟수 실행하는 조건에 대한 것이다. $A_0$를 훨씬 자주 실행한다면 판단은 달라질 수 있다.

강사는 AM이 큰 값의 영향을 많이 받는다는 점을 언급했다. 실행 시간이 긴 프로그램은 합에 더 크게 기여한다. 그러나 총 시간을 평가하려는 상황에서는 그것이 실제 비용을 반영한 결과일 수 있다. 큰 값이 있다는 이유만으로 AM이 잘못되었다고 판단하거나 그 값을 임의로 약화해서는 안 된다. [M01 p.14] [STT 36:16]

### Weighted Arithmetic Mean: 가중치는 무엇의 비중인가

**Weighted Arithmetic Mean(가중 산술평균, WAM)**은 각 값이 대표하는 비중을 반영해 합산한다. 자료 p.15에서 프로그램 $A_i$의 가중치 $w_i$는 전체 프로그램 실행 횟수 중 $A_i$의 실행 횟수 비중이다. [M01 p.15]

$$
\sum_iw_i=1,
\qquad
\operatorname{WAM}(T)=\sum_iw_iT_i
$$

**자료의 수식 읽기:** p.15에서 먼저 확인할 것은 가중치의 합이 1이라는 조건이다. 그다음 각 $w_i$가 프로그램 실행 시간 $T_i$에 곱해지는 구조를 읽는다. 단순히 중요하다고 느끼는 정도를 숫자로 붙이는 것이 아니라, 여기서는 실행 횟수의 상대적 비중을 사용한다.

앞의 예시에서 $A_0$가 전체 실행의 90%, $A_1$이 10%를 차지한다고 하자.

$$
\operatorname{WAM}_X
=
0.9\times1+0.1\times10
=
1.9\text{ s}
$$

$$
\operatorname{WAM}_Y
=
0.9\times2+0.1\times6
=
2.4\text{ s}
$$

이 구성에서는 X가 더 빠르다. 실제로 $A_0$를 90번, $A_1$을 10번 실행하면 X는 190초, Y는 240초를 사용하므로 WAM의 판단과 일치한다. 앞서 동일 횟수로 실행했을 때 Y가 빨랐던 것과 모순되지 않는다. 평가한 Workload가 달라졌기 때문이다.

같은 가중치를 사용해 두 컴퓨터를 비교하면,

$$
\frac{\operatorname{WAM}_X}{\operatorname{WAM}_Y}
$$

는 그 실행 구성에서 Y가 X에 비해 갖는 Speedup이다. 분자와 분모에 서로 다른 가중치를 사용하면 같은 Workload를 비교하는 것이 아니게 된다. [M01 p.15]

평균 CPI도 가중 평균의 한 예지만, 가중치가 나타내는 대상은 다르다. 프로그램 Runtime을 평균할 때는 **프로그램 실행 횟수 비중**, 종류별 CPI를 평균할 때는 **명령어 실행 개수 비중**을 사용한다. 가중치가 무엇의 비중인지 먼저 정해야 한다. [M01 p.6] [M01 p.15] [STT 37:12]

**오개념 주의:** WAM은 큰 값을 덜 중요하게 보이도록 만드는 기법이 아니다. 실제 집계하려는 대상을 올바르게 반영하는 방법이다. 실행 횟수 비중, 명령어 개수 비중, 시간 비중을 구분하지 않은 가중 평균은 숫자를 얻더라도 의미를 해석하기 어렵다.

### Geometric Mean: 기준 대비 비율을 요약하기

**Geometric Mean(기하평균, GM)**은 양수인 값들을 곱한 뒤 그 개수만큼의 제곱근을 취한다.

$$
\operatorname{GM}(r)
=
\left(\prod_{i=0}^{n-1}r_i\right)^{1/n}
$$

성능 비교에서는 서로 다른 프로그램의 절대 시간을 그대로 섞기보다, 각 프로그램에서 기준 컴퓨터와 비교한 비율을 요약할 때 사용한다. 강사는 스마트폰 평가와 Geekbench를 예로 들며, 여러 **Benchmark(성능 평가용 작업)**에서 두 기기를 비교하는 상황을 설명했다. [M01 p.16] [STT 38:11]

**자료 그림 읽기 — p.16의 비율 방향:** 그림에 실제로 표시된 항은 다음과 같다.

$$
r_i=\frac{T_{X,i}}{T_{Y,i}},
\qquad
G=
\left(
\prod_i\frac{T_{X,i}}{T_{Y,i}}
\right)^{1/n}
$$

여기서 Y는 기준 컴퓨터다. $r_i$는 X의 실행 시간을 Y의 실행 시간으로 나눈 **Normalized execution-time ratio(정규화 실행 시간 비율)**다. 따라서 $r_i<1$이면 그 프로그램에서 X의 시간이 더 짧다. [M01 p.16]

주의할 점은 같은 페이지의 설명이 이 값을 X의 Y 대비 상대 Speedup이라고 부른다는 것이다. 앞서 정의한 X의 Speedup은 $T_Y/T_X$ 방향이므로, 표시된 시간 비율과 방향이 반대다. 이 노트에서는 그림의 식을 그대로 읽되, 시간 비율과 Speedup을 다음처럼 구분한다.

$$
G_{\text{time}}
=
\operatorname{GM}\left(\frac{T_X}{T_Y}\right),
\qquad
G_{\text{speedup}}
=
\operatorname{GM}\left(\frac{T_Y}{T_X}\right)
=
\frac{1}{G_{\text{time}}}
$$

이는 자료의 비율 방향을 설명한 것이며, 불명확한 발화를 반대 방향의 비율로 복원한 것이 아니다. [M01 p.16] [STT 39:09]

**이해를 위한 예시:** 첫 Benchmark에서 X와 Y가 각각 2초와 4초, 두 번째에서 각각 8초와 4초 걸렸다고 하자. X의 Y 대비 시간 비율은 각각 $1/2$과 2다.

$$
G_{\text{time}}=\sqrt{\frac12\times2}=1
$$

첫 작업에서 절반의 시간, 둘째 작업에서 두 배의 시간이라는 배수 관계를 GM으로 요약하면 1이다. 그러나 두 작업을 한 번씩 실행한 총 시간은 X가 10초, Y가 8초다. **비율의 GM이 1이라는 사실은 두 작업의 총 실행 시간이 같다는 뜻이 아니다.** 무엇을 요약했는지가 다르다.

자료가 함께 제시한 성질은 다음과 같다.

$$
\frac{\operatorname{GM}(X_i)}
{\operatorname{GM}(Y_i)}
=
\operatorname{GM}\left(\frac{X_i}{Y_i}\right)
$$

양수인 대응값들을 곱하는 구조에서 나오는 성질이다. 다만 이 성질이 GM을 모든 성능 측정의 올바른 평균으로 만들어 주지는 않는다. GM을 사용했다면 정규화한 대상, 기준 컴퓨터, 비율의 방향을 함께 밝혀야 한다. [M01 p.16]

### Harmonic Mean: 같은 양의 작업을 서로 다른 속도로 수행할 때

**Harmonic Mean(조화평균, HM)**은 각 값의 역수를 평균한 뒤 다시 역수를 취한 값이다.

$$
\operatorname{HM}(R)
=
\frac{n}{\sum_{i=1}^{n}1/R_i}
$$

이 식을 외우기 전에, **Rate(율)**의 평균을 총량과 총시간으로 구성하는 이유부터 이해해야 한다. 같은 거리를 느리게 이동한 구간에서는 더 많은 시간이 소요된다. 속도 숫자를 동일 비중으로 더하면 이 시간 차이를 반영하지 못한다. [M01 p.17]

**강의 고유 예시 — 두 번의 10 km 이동:** 처음 10 km를 30 km/h로, 다음 10 km를 90 km/h로 이동한다고 하자. 각 구간에서 걸린 시간은,

$$
t_1=\frac{10}{30}=\frac13\text{ h},
\qquad
t_2=\frac{10}{90}=\frac19\text{ h}
$$

이다. 따라서 평균 속도는,

$$
v_{\text{avg}}
=
\frac{\text{Total distance}}{\text{Total time}}
=
\frac{20}{10/30+10/90}
=
45\text{ km/h}
$$

다. 두 속도의 AM인 60 km/h가 아니다. 느린 구간에서 더 오래 머물렀기 때문이다. [M01 p.17] [STT 40:00] [STT 41:02]

같은 작업량 $Q$를 각각의 Rate $R_i$로 처리하면 각 작업의 시간은 $Q/R_i$다. 따라서 전체 평균 Rate는,

$$
R_{\text{overall}}
=
\frac{nQ}{\sum_iQ/R_i}
=
\frac{n}{\sum_i1/R_i}
$$

가 되어 HM이 자연스럽게 나온다.

작업량이 서로 다르면 **Weighted Harmonic Mean(가중 조화평균, WHM)**을 사용한다. 전체 작업량에서 각 부분이 차지하는 비중을 $w_i$라고 하면,

$$
R_{\text{overall}}
=
\frac{1}{\sum_iw_i/R_i},
\qquad
\sum_iw_i=1
$$

이다. 여기서 가중치는 시간 비중이 아니라 작업량 비중이다. [M01 p.17]

**이해를 위한 예시:** 전체 거리의 25%를 30 km/h, 75%를 90 km/h로 이동하면,

$$
v_{\text{avg}}
=
\frac{1}{0.25/30+0.75/90}
=
60\text{ km/h}
$$

다. 같은 속도값이라도 각 속도로 처리한 작업량이 달라지면 평균도 달라진다.

**오개념 주의:** Rate에는 어떤 상황에서도 AM을 쓰면 안 된다는 식으로 외우지 않는다. 같은 거리씩 이동한 위 예시와 달리, 30 km/h와 90 km/h로 각각 같은 시간 동안 이동했다면 평균 속도는 60 km/h다. 평균을 고르는 기준은 값의 이름만이 아니라 **같게 둔 것이 작업량인지 시간인지**다. 자료의 경고는 먼저 총량과 총시간으로 풀어 쓰라는 원칙과 함께 읽어야 한다. [M01 p.17]

### 평균 IPC: 전체 명령어 수를 전체 사이클 수로 나누기

IPC와 CPI는 같은 집계 대상에서 서로 역수다.

$$
\text{IPC}
=
\frac{\text{Instructions}}{\text{Cycles}},
\qquad
\text{CPI}
=
\frac{\text{Cycles}}{\text{Instructions}}
$$

따라서 전체 IPC를 구하는 가장 직접적인 방법은 총 명령어 수를 총 사이클 수로 나누는 것이다. 개별 실행의 IPC 값에 어떤 평균을 적용할지는 이 정의에서 도출해야 한다. [M01 p.18] [STT 39:09]

자료 p.18은 **같은 주파수와 같은 명령어 수**를 전제로 한다. 각 실행의 명령어 수가 $N$, CPI가 $C_i$라면 전체 명령어 수는 $nN$, 전체 사이클 수는 $\sum_iNC_i$다.

$$
\begin{aligned}
\text{IPC}_{\text{overall}}
&=
\frac{nN}{\sum_iNC_i}\\
&=
\frac{n}{\sum_iC_i}\\
&=
\frac{1}{\operatorname{AM}(\text{CPI})}\\
&=
\frac{n}{\sum_i1/\text{IPC}_i}\\
&=
\operatorname{HM}(\text{IPC})
\end{aligned}
$$

**자료 그림 읽기 — 역수를 취하는 대상:** p.18의 유도는 평균 CPI의 역수에서 출발해 각 CPI를 $1/\text{IPC}_i$로 바꾸고, 마지막에 HM의 정의에 도달한다. 개별 IPC의 AM을 먼저 구한 것이 아니다. STT 후반부의 분수와 CPI·IPC 명칭에는 불명확한 부분이 있으므로, 정확한 유도는 자료의 식을 근거로 읽는다. [M01 p.18] [STT 42:11]

**이해를 위한 예시:** 같은 주파수에서 두 실행이 각각 300개의 명령어를 수행한다고 하자.

| 실행 | Instruction count | IPC | 필요한 사이클 수 |
|---|---:|---:|---:|
| 첫 번째 | 300 | 1 | 300 |
| 두 번째 | 300 | 3 | 100 |

두 실행을 합하면 총 600개의 명령어를 400사이클에 수행하므로,

$$
\text{IPC}_{\text{overall}}=\frac{600}{400}=1.5
$$

다. 개별 IPC의 AM인 $(1+3)/2=2$와 다르다. 첫 번째 실행은 더 낮은 IPC로 더 많은 사이클을 사용하므로 두 IPC 값을 같은 사이클 비중으로 평균할 수 없다.

자료의 `Avg. Time = Avg. CPI` 표기도 단위까지 같은 등식으로 읽어서는 안 된다. 공통 명령어 수가 $N$, 공통 주파수가 $F$라면 정확한 관계는,

$$
\operatorname{AM}(T)
=
\frac{N}{F}\operatorname{AM}(\text{CPI})
$$

다. 자료는 공통 인자 $N/F$를 생략해 비례 관계를 간략히 표시한 것이다. 시간과 CPI가 같은 단위를 갖는다는 뜻이 아니다. [M01 p.18]

명령어 수가 서로 다르면 $N_i$를 보존해야 한다.

$$
\text{IPC}_{\text{overall}}
=
\frac{\sum_iN_i}{\sum_iN_iC_i}
=
\frac{1}{\sum_iw_i/\text{IPC}_i},
\qquad
w_i=\frac{N_i}{\sum_jN_j}
$$

따라서 이 경우에는 명령어 개수 비중을 사용한 WHM으로 연결된다.

**기출의 요구 능력과 연결:** 복기본 Q5는 IPC와 같은 성능률을 어떤 평균으로 집계해야 하는지에 관한 주장을 판단하게 한다. 이 강의의 동일 명령어 수 조건에서는 총 명령어 수와 총 사이클 수로 유도한 HM이 대응한다. 반면 여러 Benchmark에서 기준 대비 정규화한 비율을 요약하는 문제는 GM과 연결된다. IPC라는 단어만 보고 평균을 고르거나, 성능 자료라는 이유로 GM을 적용하는 것이 함정이다. [EX:ca_2025_2_midterm_q05 p.2]

자료 p.19의 **Amount(양)**, **Ratio(비율)**, Rate 구분도 이러한 집계 조건을 읽기 위한 안내다. 실행 시간처럼 더할 양은 AM 또는 WAM, 정규화한 배수 관계는 GM, 같은 작업량을 처리한 Rate는 HM 또는 WHM과 연결된다. 각 경우에 무엇을 합산하는지와 가중치가 무엇을 뜻하는지를 확인해야 한다. 강사가 CPI를 평균의 예로 사용한 부분 역시 명령어 개수 비중을 명시해야 정확해진다. [M01 p.19] [STT 43:12]

### Standard Benchmarks와 SPEC: 공통 작업으로 비교하기

사람마다 사용하는 프로그램이 다르면 서로 다른 성능 결과를 얻는다. **Standard benchmark(표준 성능 평가용 작업)**는 비교할 공통 작업을 제공해, 서로 다른 컴퓨터나 설계를 일정한 기준 아래 평가하도록 돕는다. 모든 사용자의 실제 Workload를 완벽하게 대신하는 것은 아니지만, 평가 대상을 공유할 수 있게 한다. [M01 p.20]

강의에서는 **SPEC(Standard Performance Evaluation Corporation)**가 제공하는 Benchmark 집합을 소개했다. 자료는 여러 산업 분야의 위원회가 고른 현실적이고 범용적인 **public-domain application** 집합이라고 서술하고, 사용 방식 및 기술의 변화를 반영해 갱신한다고 설명한다. 이는 자료에 실린 배경 설명이며, 모든 내용을 구두로 상세히 다루었다고 보지는 않는다. [M01 p.20] [STT 44:10]

**자료 목록 읽기 — 서로 다른 작업을 묶는 이유:** p.21에는 `CINT2006`과 `CFP2006`의 프로그램 목록이 나온다. 읽어야 할 핵심은 이름의 개수가 아니라 각 항목이 서로 다른 종류의 작업을 대표한다는 점이다. 예를 들어 압축, 컴파일, 게임, 물리 계산, 날씨 계산, 음성 인식처럼 서로 다른 작업이 함께 제시되어 있다. 한 프로그램으로 CPU의 모든 성능 특성을 대표하기 어렵기 때문에 여러 작업을 묶어 평가하는 것이다. [M01 p.21]

목록은 사용 언어와 예외도 함께 표시한다. `CINT2006`은 별도 표기가 없으면 C, `CFP2006`은 별도 표기가 없으면 F77/F90이라는 식이다. 따라서 이 페이지는 단일 알고리즘의 실행 시간표가 아니라 서로 다른 프로그램과 구현 특성을 모은 목록으로 읽어야 한다. 여기에 실린 2006 계열 사례를 현재의 최신 Benchmark 구성이라고 해석하지 않는다. [M01 p.21]

**이번 회차의 명시적 학습 안내:** 강사는 SPEC를 일반적인 배경지식으로 소개하면서 이후 이 수업에서 다시 다루지 않을 것이라고 안내했고, 해당 Benchmark 이름 자체를 시험에서 묻지 않겠다는 취지로 설명했다. 구체적인 시험명은 STT에서 불명확해 **검증 필요**다. 확인 가능한 안내는 개별 이름을 외우기보다, 연구에서 설계를 평가할 때 사용할 공통 Benchmark 집합이 존재한다는 점을 이해하라는 것이다. [STT 44:10] [STT 45:07]

이 안내는 Benchmark 개념을 생략하라는 뜻은 아니다. [[concepts/benchmarking|Benchmark]]가 어떤 Workload를 대표하는지, 무엇을 비교하는지, 결과를 어떤 비율로 요약하는지를 이해해야 앞의 성능 측정과 평균 계산도 의미를 갖는다.

### 성능 수치의 설명: 측정 목적·방법·대표성을 드러내기

성능 수치는 측정 조건과 해석 방법이 함께 있어야 평가할 수 있다. 자료 p.22는 모든 상황에 최선인 하나의 측정 방법이 있는 것이 아니라, 자신이 알고 싶은 효과에 맞는 방법을 선택해야 한다고 설명한다. [M01 p.22]

첫째, **무엇을 측정하려는지** 정해야 한다. 사용자의 기다림을 줄이려는 것인지, CPU 실행 자체를 개선하려는 것인지, 많은 요청을 처리하려는 것인지에 따라 Latency·CPU time·Throughput 중 중심 지표가 달라진다.

둘째, **실제로 무엇을 어떻게 측정했는지** 밝혀야 한다. 같은 프로그램과 입력인지, 주파수와 실행 환경이 어떤지, `real`·`user`·`sys` 중 어느 값을 사용했는지에 따라 결과가 답하는 질문이 달라진다. 측정하고 싶었던 대상과 실제로 측정한 대상을 혼동하지 않아야 한다.

셋째, **어떻게 요약했는지** 설명해야 한다. AM을 사용했다면 실행 횟수 조건, WAM을 사용했다면 가중치의 의미, GM을 사용했다면 정규화 기준과 비율 방향을 제시한다. 숫자 하나만 남기면 다른 사람이 그 값이 자신의 목적에도 적절한지 판단하기 어렵다.

넷째, **정확성과 대표성을 확인할 수 있는 원자료**를 제시할 준비가 필요하다. 일부 Workload에서 얻은 결과가 전체 사용 상황을 대표하는지, 요약 과정에서 어떤 차이가 가려졌는지 확인할 수 있어야 한다. 강사는 여러 결과가 각각 언제 의미 있는지 설명하고, 수치와 시나리오를 정직하고 투명하게 제시하라는 조언을 반복했다. [M01 p.13] [M01 p.22] [STT 33:15] [STT 46:06] [STT 48:47]

미국에 가지 말고 SNU에서 공부하라는 권유와 함께 “the president of the America these days is,”라는 미완성 언급도 있었다. 여기서 특정 인물·사건·날짜를 추론하지 않는다. [STT 34:18]

### Single-cycle processor는 다음 강의의 예고

강의 말미에는 **Single-cycle processor(단일 사이클 프로세서)**부터 실제 프로세서 설계를 배우고, 이후 일정 시간에 더 많은 명령어를 처리하도록 개선해 나가겠다는 예고가 있었다. 이번 회차에서 구체적인 실행 경로, 제어 신호, Pipeline 동작을 설계한 것은 아니다. [STT 48:47]

이번에 정리한 Latency·Throughput, CPU execution time, CPI·IPC, Speedup, Amdahl’s Law는 앞으로 그러한 설계를 평가할 때 사용할 기준이다. 어떤 설계를 배웠을 때도 먼저 올바르게 실행되는지 확인하고, 이어서 어떤 Workload에서 어떤 시간이나 처리율이 달라지는지를 계산해야 한다. 설계 이름만으로 성능 우열을 정하거나, 다음 강의의 예고를 이미 학습한 구현 지식으로 사용하지 않는다.

## 핵심 요약

- **Functional correctness(기능적 정확성)**는 명세대로 실행하는지, **Performance(성능)**는 그 실행을 얼마나 빠르게 또는 많이 처리하는지를 묻는다. 주파수만으로 전체 성능을 판정하지 않는다. [STT 02:08] [M01 p.6]
- **Latency(지연시간)**는 한 작업의 시간이고 **Throughput(처리율)**은 단위 시간의 완료 작업 수다. Concurrency가 있으면 둘을 단순한 역수 관계로 취급할 수 없다. [M01 p.3]
- **Elapsed time(경과 시간)**과 CPU time은 다르다. 강의 예시의 CPU time은 `user + sys`인 0.015초이며, 전체 경과 시간은 1.260초다. 차이의 모든 원인을 이 세 값만으로 확정하지 않는다. [M01 p.4] [M01 p.5]
- **CPU execution time**은 $T_{\text{CPU}}=NC/F$다. $N$은 Instruction count, $C$는 평균 CPI, $F$는 cycles/s 단위의 주파수다. GHz를 사용할 때는 $10^9$ 배율을 포함한다. [M01 p.6]
- **명령어별 비용과 설계 분야:** Register 중심 연산과 Memory 접근은 사용하는 자원이 달라 CPI가 달라질 수 있다. 자료는 주파수를 Semiconductor technology·Microarchitecture(`uarch`), CPI를 `uarch`·ISA, Instruction count를 ISA·Compiler와 연결한다. 이는 상호작용하는 영향 관계이며, 모든 산술 명령의 우월성이나 한 분야의 독점 책임을 뜻하지 않는다. [STT 16:05] [M01 p.6]
- **Speedup(성능 향상 배수)**은 $T_{\text{old}}/T_{\text{new}}$다. 50% faster는 성능이 1.5배라는 뜻이며, 시간은 원래의 $2/3$이 된다. [M01 p.9] [M01 p.10] [M01 p.11]
- **Amdahl’s Law(암달의 법칙)**에서 $f$는 개선 전의 **시간 비중**이다. 명령어 개수 비중과 혼동하지 않는다. $S_{\text{overall}}=1/((1-f)+f/S_f)$이며, 개선하지 않은 부분이 전체 효과를 제한한다. [M01 p.12]
- Energy, Power, Runtime은 서로 다른 양이다. 이번 강의가 Performance에 집중한다는 사실은 다른 설계 기준이 불필요하다는 뜻이 아니다. [M01 p.7]
- 성능 비교에는 Workload가 따라야 한다. Standard benchmark도 공통 비교 기준을 제공할 뿐 모든 사용 상황을 완벽하게 대표하지는 않는다. [M01 p.13] [M01 p.20] [M01 p.22]

평균은 다음과 같이 **무엇을 합치는지**에 따라 선택한다.

| 집계 대상 | 평균 | 반드시 확인할 조건 |
|---|---|---|
| 같은 횟수 실행한 프로그램들의 Runtime | Arithmetic Mean(산술평균, AM) | 동일 프로그램 집합과 동일 실행 횟수 |
| 실행 빈도가 다른 프로그램들의 Runtime | Weighted Arithmetic Mean(가중 산술평균, WAM) | 프로그램 실행 횟수 비중 |
| Benchmark별 기준 대비 정규화한 비율 | Geometric Mean(기하평균, GM) | 기준 대상과 비율의 방향 |
| 같은 작업량을 처리한 Rate | Harmonic Mean(조화평균, HM) | 동일 작업량 조건 |
| 서로 다른 작업량을 처리한 Rate | Weighted Harmonic Mean(가중 조화평균, WHM) | 작업량 비중 |

[M01 p.14] [M01 p.15] [M01 p.16] [M01 p.17] [M01 p.19]

특히 p.16의 $\operatorname{GM}(T_X/T_Y)$는 **시간 비율**이다. X의 Y 대비 Speedup으로 표현하려면 역수를 취한다. p.18의 평균 IPC 유도는 같은 주파수와 같은 명령어 수를 전제로 읽으며, `Avg. Time = Avg. CPI`는 단위까지 같은 등식이 아니라 공통 인자를 생략한 비례 관계다. [M01 p.16] [M01 p.18]

#### R01. Functional correctness와 Performance

같은 프로그램을 실행하는 두 프로세서의 Functional correctness와 Performance는 각각 어떤 질문에 답하는가? 강의의 3.7 GHz와 2점대 GHz 비교만으로 성능 우열을 확정할 수 있는가?

<details><summary>정답</summary>

Functional correctness는 명령어의 명세에 맞는 결과와 동작을 보장하는지를 묻는다. Performance는 올바른 실행을 전제로 필요한 시간이나 완료 작업 수를 비교한다. 빠르다는 사실이 잘못된 실행을 정당화하지는 않는다. [STT 02:08]

강사는 3.7 GHz가 2점대 GHz보다 나을 수도 있다는 “might be better” 예로 측정의 필요성을 열었다. 측정된 Benchmark 결과가 아니며, 전체 CPU 시간은 명령어 수와 CPI에도 의존하므로 주파수만으로 우열을 확정하지 않는다. [STT 03:30] [M01 p.6]

</details>

#### R02. Latency와 Throughput의 단위

#### R05. `real`, `user`, `sys`

<details><summary>정답</summary>

`real`은 명령의 시작부터 종료까지 경과한 시간이다. `user`는 해당 프로그램 자신의 코드 실행에 사용한 CPU time이고, `sys`는 그 프로그램을 대신해 실행한 시스템 코드의 CPU time이다. 따라서 `sys`는 관계없는 모든 프로세스의 시스템 활동을 합친 값이 아니다. [M01 p.4] [STT 11:12]

</details>

#### R06. p.5의 `time` 출력 그림

p.5에서 `real` 1.260초, `user` 0.002초, `sys` 0.013초를 읽었다. CPU time과 시간 차이를 구하고, 그림만으로 확정할 수 없는 내용을 설명하라.

그림에서는 반복되는 출력과 시간 항목을 함께 읽어야 한다. 강사는 출력 I/O를 차이의 원인으로 설명했지만, 세 숫자만으로 1.245초 전부가 특정 I/O 동작에 사용되었다고 입증할 수는 없다. [M01 p.5] [STT 12:12] [STT 13:07]

</details>

#### R07. CPU execution time과 단위

CPU execution time의 세 인자를 쓰고 CPI·IPC·MIPS·GHz의 의미를 설명하라.

<details><summary>정답</summary>

$$
T_{\text{CPU}}
=
\text{Cycle time}\times\text{Average CPI}\times\text{Instruction count}
=
\frac{NC}{F}
$$

CPI는 cycles/instruction, IPC는 instructions/cycle이다. MIPS는 초당 백만 명령어 수이며 GHz는 초당 $10^9$사이클에 해당한다. 주파수가 $g$ GHz이면 Cycle time은 $1/(g\times10^9)$초다. 이 식을 I/O 대기까지 포함한 모든 Wall-clock time에 그대로 적용하지 않는다. [M01 p.6]

</details>

#### R08. 명령어 종류와 CPI

</details>

#### R11. 50% faster

#### R12. Speedup의 방향

Speedup이 1보다 크거나 작다는 것은 각각 무엇을 뜻하는가? 단위는 무엇인가?

<details><summary>정답</summary>

$S=T_{\text{old}}/T_{\text{new}}$이므로 $S>1$이면 실행 시간이 감소했고, $S<1$이면 오히려 증가했다. 같은 단위의 시간끼리 나누므로 Speedup은 무차원 비율이다. [M01 p.11]

</details>

#### R13. p.12의 Amdahl’s Law 막대 그림

아래쪽 막대에서 그대로 남는 부분은 무엇인가? $f$가 작으면 $S_f$가 전혀 중요하지 않다는 해석은 타당한가?

<details><summary>정답</summary>

개선하지 않는 $1-f$ 부분이 그대로 남고, 개선하는 $f$ 부분만 $f/S_f$로 줄어든다.

$$
S_{\text{overall}}=\frac{1}{(1-f)+f/S_f}
$$

$f$가 작아도 식은 여전히 $S_f$에 의존한다. 다만 개선되지 않는 시간이 커서 전체 효과가 제한된다. Common case 원칙을 계산에 적용할 때는 발생 횟수뿐 아니라 원래 시간 비중을 확인한다. [M01 p.12] [STT 29:17]

</details>

#### R20. HM과 WHM

처음 10 km를 30 km/h, 다음 10 km를 90 km/h로 이동하면 평균 속도는 얼마인가? 두 속도로 이동한 거리가 다르면 무엇을 바꿔야 하는가?

<details><summary>정답</summary>

$$
v_{\text{avg}}
=\frac{20}{10/30+10/90}
=45\text{ km/h}
$$

같은 거리 조건이므로 HM과 일치한다. 거리가 다르면 각 구간의 거리 비중 $w_i$를 사용해 $1/\sum_i(w_i/v_i)$로 계산하거나 총거리/총시간을 직접 구한다. 같은 시간씩 이동한 경우까지 HM을 무조건 적용하지 않는다. [M01 p.17]

</details>

#### R21. 평균 IPC의 유도

p.18의 조건에서 전체 IPC가 HM으로 이어지는 이유를 총 명령어 수와 총 사이클 수로 설명하라.

<details><summary>정답</summary>

각 실행의 명령어 수가 $N$, CPI가 $C_i$이면,

$$
\text{IPC}_{\text{overall}}
=\frac{nN}{\sum_iNC_i}
=\frac{1}{\operatorname{AM}(\text{CPI})}
=\operatorname{HM}(\text{IPC})
$$

이다. 자료의 시간 비교에는 공통 주파수 조건도 있다. 정확한 시간 관계는 $\operatorname{AM}(T)=(N/F)\operatorname{AM}(\text{CPI})$이므로 Time과 CPI 자체가 같은 단위인 것은 아니다. [M01 p.18]

</details>

#### R22. Amount·Ratio·Rate

평균을 고를 때 Amount·Ratio·Rate라는 이름만 확인하면 충분한가?

충분하지 않다. Amount에는 AM 또는 WAM, 정규화한 Ratio에는 GM, 동일 작업량의 Rate에는 HM이 대응하지만, 무엇을 같은 양으로 두었는지와 가중치의 의미를 확인해야 한다. 애매하면 총량과 총시간, 또는 총 명령어 수와 총 사이클 수로 돌아가 계산한다. [M01 p.19]

</details>

#### R23. Standard benchmark와 SPEC

#### 연습 P01

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** CPU execution time과 목표 CPI 역산.

- **범위·학습목표:** Instruction count·CPI·주파수의 관계, 설계 인자의 상호작용, Speedup과 시간 감소율. [M01 p.6] [M01 p.10] [M01 p.11]
- **요구 능력:** 단위 변환, 식의 역산, 여러 인자의 변화 결합.
- **선수 개념:** CPU time과 Elapsed time의 구분, $T_{\text{CPU}}=NC/F$와 역산, GHz 단위 변환, 평균 CPI, Speedup·성능 증가율·시간 감소율. 모두 고정 본문에서 설명한 현재 개념이며 후속 CPU 구현 지식은 필요하지 않다.
- **접근 상태:** 현재 접근 가능.
- **스타일 근거:** Q11(a)·(b)는 주어진 실행 시간·주파수·명령어 수로 현재 및 목표 CPI를 구하게 한다. P01의 1·2번은 이 역산 구조에 새 수치를 적용한다. 3번의 성능·시간 백분율 비교와 4번의 Compiler 인자 변화는 강의에서 추가한 일반 확장이며, 원문이 그 요구를 했다는 뜻은 아니다. [EX:ca_2025_2_midterm_q11 p.3]

동일한 프로그램이 $1.2\times10^9$개의 명령어를 실행한다. A의 주파수는 2 GHz이고 CPU execution time은 0.9초다. B의 주파수는 3 GHz이며 목표 시간은 0.5초다.

1. A의 평균 CPI를 구하라.
2. B가 목표를 달성하려면 평균 CPI가 얼마여야 하는가?
3. 목표를 달성한 B의 A 대비 Speedup, 성능 증가율, 시간 감소율을 구하라.
4. 별도의 Compiler 변경이 Instruction count를 20% 줄이고 평균 CPI를 25% 늘린다. 주파수가 같다면 CPU execution time은 어떻게 변하는가?

<details><summary>풀이와 채점 포인트</summary>

A의 평균 CPI는,

$$
C_A=\frac{0.9\times2\times10^9}{1.2\times10^9}=1.5
$$

이다. B의 목표 CPI는,

$$
C_B=\frac{0.5\times3\times10^9}{1.2\times10^9}=1.25
$$

다.

B의 A 대비 Speedup은 $0.9/0.5=1.8$이므로 성능은 80% 증가한다. 시간 감소율은,

$$
\frac{0.9-0.5}{0.9}=\frac49\approx44.44\%
$$

다. 성능 증가율과 시간 감소율의 분모가 다르다.

Compiler 변경 후 시간의 비율은,

$$
\frac{T_{\text{new}}}{T_{\text{old}}}
=0.8\times1.25=1
$$

이므로 시간이 같다. 명령어 수 감소만 보고 빨라졌다고 결론낼 수 없다.

**채점 포인트, 총 5점:** GHz 변환과 식 설정 1점, 두 CPI 계산 1점, Speedup·성능 증가율 1점, 시간 감소율 1점, 인자 변화의 곱으로 상쇄 설명 1점.

</details>

#### 연습 P02

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** Instruction count 비중과 시간 비중을 구분하는 부분 개선.

- **범위·학습목표:** 평균 CPI, Amdahl’s Law, 개선하지 않는 부분이 만드는 시간 하한. [M01 p.6] [M01 p.12] [STT 29:17]
- **요구 능력:** 시간 분해, 비중 변환, 목표 달성 가능성 판단.
- **선수 개념:** $T=NC/F$, 명령어 개수에 따른 가중 평균, 개선 전 시간 비중과 Amdahl’s Law, Speedup. 모두 현재 개념이며 FP는 주어진 CPI를 갖는 명령어 종류로만 사용하므로 FP 구현 지식은 필요하지 않다.
- **접근 상태:** 현재 접근 가능.
- **스타일 근거:** Q6은 Amdahl’s Law의 개선 한계에 관한 참·거짓 판단이며, Q11(c)는 FP 명령만 개선해 전체 목표 시간을 달성할 수 있는지와 가능한 경우의 최소 개선 배수를 묻는다. P02는 이 판단을 결합해 새 CPI·명령어 비중으로 시간 비중을 도출하고, 가능한 목표와 불가능한 목표를 함께 비교하도록 구성했다. Q6 원문에 수치 계산이나 이 다단계 형식이 있었다는 뜻은 아니다. [EX:ca_2025_2_midterm_q06 p.2] [EX:ca_2025_2_midterm_q11 p.3]

명령어 수는 $10^9$개, 주파수는 2 GHz다. FP 명령은 개수 기준 25%이고 CPI는 6이다. 나머지 명령의 CPI는 1이다. FP 부분만 개선하며 명령어 수·주파수·나머지 부분의 시간은 변하지 않고 추가 비용도 없다고 가정한다.

1. 전체 평균 CPI, 전체 시간, FP 부분의 시간 비중을 구하라.
2. FP 부분을 3배 빠르게 하면 전체 시간과 Speedup은 얼마인가?
3. 전체 시간 0.3초는 가능한가?
4. 전체 시간 0.5초를 달성하려면 FP 부분이 최소 몇 배 빨라져야 하는가?

<details><summary>풀이와 채점 포인트</summary>

평균 CPI는,

$$
C_{\text{avg}}=0.25\times6+0.75\times1=2.25
$$

이고 전체 시간은,

$$
T_{\text{old}}=\frac{10^9\times2.25}{2\times10^9}=1.125\text{ s}
$$

다. FP와 나머지 부분의 시간은 각각,

$$
T_{\text{FP}}=0.75\text{ s},
\qquad
T_{\text{other}}=0.375\text{ s}
$$

다. 따라서 FP의 원래 시간 비중은 $f=0.75/1.125=2/3$이다. 명령어 개수 비중 25%와 다르다.

FP 부분을 3배 빠르게 하면,

$$
T_{\text{new}}=0.375+\frac{0.75}{3}=0.625\text{ s}
$$

이며 전체 Speedup은 $1.125/0.625=1.8$이다.

0.3초 목표는 불가능하다. 개선하지 않는 부분만 이미 0.375초가 필요하다. FP 시간을 0에 가깝게 줄였을 때 전체 Speedup의 한계는 $1.125/0.375=3$이다.

0.5초 목표에서는,

$$
0.375+\frac{0.75}{S_f}\le0.5
$$

이므로 $S_f\ge6$이어야 한다.

**채점 포인트, 총 6점:** 평균 CPI·전체 시간 1점, 두 부분의 시간 1점, 시간 비중 $2/3$ 1점, 3배 개선 결과 1점, 시간 하한에 의한 불가능성 설명 1점, 최소 개선 배수 6 도출 1점.

</details>

- **접근 상태:** 현재 접근 가능.
- **스타일 근거:** Q5는 IPC 같은 성능률의 평균에 GM이 가장 적절하다는 주장을 참·거짓으로 판정하게 한다. P03는 그 평균 선택 판단을 새 실행 기록으로 검증하도록 변형했다. 동일·상이 명령어 수의 수치 계산과 WHM 확장은 새로 구성했으며, 원문에 그런 계산 조건이 있었다는 뜻은 아니다. [EX:ca_2025_2_midterm_q05 p.2]

같은 주파수에서 두 실행의 IPC는 각각 1.5와 3이다. 두 실행을 순서대로 수행하며 추가 비용은 없다고 가정한다.

1. 각각 600개 명령어를 실행했다면 전체 IPC를 구하라.
2. 개별 IPC의 AM인 2.25가 전체 IPC와 다른 이유를 설명하라.
3. 첫 실행이 300개, 두 번째 실행이 900개 명령어를 수행했다면 전체 IPC를 다시 구하라.
4. 이 계산을 Benchmark별 정규화 비율의 GM으로 대신할 수 있는가?

<details><summary>풀이와 채점 포인트</summary>

동일 명령어 수 조건에서 필요한 사이클은 각각 $600/1.5=400$, $600/3=200$이다.

$$
\text{IPC}_{\text{overall}}
=\frac{600+600}{400+200}
=2
$$

개별 IPC를 같은 비중으로 더하면 각 실행이 사용한 사이클 수의 차이를 반영하지 못한다. 같은 명령어 수를 실행한 것이지 같은 사이클 수를 사용한 것이 아니다.

명령어 수가 달라진 경우에는,

$$
\text{IPC}_{\text{overall}}
=\frac{300+900}{300/1.5+900/3}
=\frac{1200}{500}
=2.4
$$

다. 명령어 개수 비중 $1/4$, $3/4$을 사용하는 WHM으로도 같은 값을 얻는다.

$$
\frac{1}{(1/4)/1.5+(3/4)/3}=2.4
$$

이 계산의 목적은 실제 실행들의 총 명령어 수/총 사이클 수를 구하는 것이다. 기준 컴퓨터 대비 정규화한 비율을 요약하는 GM과 집계 대상이 다르다.

**채점 포인트, 총 4점:** 사이클 수를 통한 전체 IPC 2 도출 1점, 단순 AM의 조건 불일치 설명 1점, 서로 다른 명령어 수에서 IPC 2.4 도출 1점, GM과 평가 대상 구분 1점.

</details>

**일반 연습 — 관련 기출 근거 없음**

- **출제 근거:** 이번 강의의 서버 예시와 `time` 출력 해석에서 새로 만든 연습이다.

서로 독립된 두 측정 상황이 있다.

**상황 A:** 한 명령의 측정값이 `real` 2.00초, `user` 0.03초, `sys` 0.07초다.

**상황 B:** 서버 요청 하나는 항상 0.2초가 걸린다. 요청은 충분히 공급되고, 최대 5개를 서로 간섭 없이 동시에 처리할 수 있다. 추가 비용은 없으며 지속적으로 처리한다고 가정한다.

1. 상황 A의 CPU time과 Elapsed time과의 차이를 구하라.
2. 그 차이 전부를 I/O 대기 시간이라고 보고해도 되는가?
3. 상황 B의 Latency와 Throughput을 구하라.
4. 요청을 하나씩 처리하는 서버와 비교할 때 어떤 지표가 몇 배 변했는가?

<details><summary>풀이와 채점 포인트</summary>

상황 A의 CPU time은 $0.03+0.07=0.10$초이며 시간 차이는 $2.00-0.10=1.90$초다. 그러나 이 세 값만으로 차이의 원인을 전부 특정 I/O 대기에 귀속할 수는 없다.

$$
\frac{5}{0.2}=25\text{ requests/s}
$$

다. 하나씩 처리하면 $1/0.2=5$ requests/s이므로 Throughput은 5배다. 주어진 가정에서는 각 요청의 Latency가 0.2초로 같아진다.

이 비교는 같은 요청과 충분한 공급, 간섭·추가 비용이 없다는 조건에 대한 결과다. 실제 서버에 대한 일반적인 5배 성능 보장은 아니다.

**채점 포인트, 총 4점:** CPU time·차이 계산 1점, 원인 확정의 한계 1점, 두 지표의 값과 단위 1점, 비교 조건과 지표별 변화 구분 1점.

본문에서 사용한 두 Benchmark의 시간을 다음과 같이 다시 분석한다. X와 Y는 각각 같은 입력을 올바르게 처리하며, 각 실행 시간은 반복해도 같다고 가정한다. 여러 실행은 순서대로 수행하고 실행 사이 추가 비용은 없다.

| Benchmark | X의 시간 | Y의 시간 |
|---|---:|---:|
| $A_0$ | 2초 | 4초 |
| $A_1$ | 8초 | 4초 |

1. 두 Benchmark를 한 번씩 실행하면 어느 컴퓨터가 빠르며 Speedup은 얼마인가?
2. 전체 실행 횟수의 75%가 $A_0$, 25%가 $A_1$이라면 결과가 어떻게 달라지는가?
3. 두 Benchmark의 시간 비율 $T_X/T_Y$를 같은 비중의 GM으로 요약하라.
4. GM이 1이라는 결과가 1번의 총 실행 시간 비교와 모순되는가?

<details><summary>풀이와 채점 포인트</summary>

한 번씩 실행하면 총 시간은 X가 10초, Y가 8초다. AM은 각각 5초와 4초이며, Y의 X 대비 Speedup은 $10/8=1.25$다.

실행 횟수 비중이 달라지면,

$$
\operatorname{WAM}_X=0.75\times2+0.25\times8=3.5\text{ s}
$$

$$
\operatorname{WAM}_Y=0.75\times4+0.25\times4=4\text{ s}
$$

다. 이 Workload에서는 X가 빠르며 X의 Y 대비 Speedup은 $4/3.5=8/7$이다.

두 Benchmark를 같은 비중으로 정규화해 요약하면,

$$
G_{\text{time}}
=\sqrt{\frac24\times\frac84}
=\sqrt{\frac12\times2}
=1
$$

이다. 이는 서로 반대인 배수 관계를 GM으로 요약한 결과다. 총 실행 시간의 비율이나 실행 빈도가 반영된 평균 시간과 같은 양이 아니므로 모순이 아니다.

보고할 때는 한 번씩 실행한 결과인지, 실행 빈도를 반영한 결과인지, 정규화 비율의 GM인지 구분해야 한다.

**채점 포인트, 총 5점:** 동일 횟수 비교 1점, WAM 계산 1점, 순위 변화와 Speedup 방향 1점, GM 계산 1점, 평가 대상 차이 설명 1점.

</details>

<details><summary>풀이와 채점 포인트</summary>

1. 같은 명령어 수는 같은 사이클 비용을 보장하지 않는다. R과 M은 사용하는 자원의 비중이 다르다. 강사는 작은 Register와 더 큰 Memory를 “smaller is faster”로 대비해, Register 중심 연산과 Memory 접근의 비용이 달라질 수 있음을 설명했다. 따라서 종류별 비용과 실제 명령어 비중을 고려해야 한다. 이 정성적 비교만으로 수치 CPI를 지정하거나 모든 산술 명령이 모든 데이터 이동 명령보다 항상 빠르다고 결론낼 수는 없다. [STT 16:05]

2. 자료의 대응은 다음과 같다. 이는 대표적인 영향 관계이며 배타적인 책임 배분이 아니다. [M01 p.6]

| 인자 | 자료가 연결한 분야 | 이유 |
|---|---|---|
| 주파수·Cycle time | Semiconductor technology, Microarchitecture | 반도체·회로 기술과 내부 구현이 한 사이클의 길이에 영향을 준다. |
| CPI | Microarchitecture, ISA | 명령이 요구하는 동작과 이를 구현하는 방식이 필요한 사이클 수에 영향을 준다. |
| Instruction count | ISA, Compiler | 사용할 수 있는 명령과 같은 작업을 어떤 명령어열로 만드는지가 실행 개수에 영향을 준다. |

3. 세 인자는 설계 선택으로 함께 변할 수 있으므로 한 분야가 한 인자만 독립적으로 개선한다고 볼 수 없다. Compiler는 같은 소스의 작업을 다른 명령어열로 구성할 수 있어 실행 Instruction count는 소스 코드 줄 수와 같지 않다. 명령어 수 $N$이 줄었다는 정보만으로는 변경 후 평균 CPI $C$와 주파수 $F$를 알 수 없다. 같은 작업·입력·정확성을 유지한 실행에 대해 변경 전후 $NC/F$를 비교해야 한다. $C$와 $F$가 같다는 조건까지 확인되면 $N$ 감소 비율만큼 CPU 시간이 줄지만, 그 조건이 없으면 시간 감소를 확정할 수 없다. [M01 p.6] [STT 18:54]

**채점 포인트, 총 8점:** Register·Memory 자원 및 크기 대비로 비용 차이 설명 1점, 같은 명령어 수로 같은 CPI를 보장할 수 없다는 판단 1점, 수치·보편적 우열 추론의 한계 1점, 분야 대응과 이유 각 행 1점씩 3점, Compiler와 실행 명령어 수·소스 길이 구분 1점, 인자의 상호작용과 변경 전후 $NC/F$ 비교 조건 1점.

#### 연습 P08

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** 새 관측값에서 Latency·Throughput·주파수를 분리해 비교하기.

- **범위·학습목표:** LO02의 한 작업 시간과 완료율 구분, LO03의 동시성에서 역수 관계가 일반적으로 성립하지 않는 이유 [M01 p.3] [STT 05:26] [STT 07:23], 주파수만으로 성능을 정할 수 없다는 판단 [M01 p.6].
- **요구 능력:** 지표별 변화와 목적에 따른 선택을 설명하고, 관측된 결과와 구현 원인·설계 의도를 구분한다.
- **선수 개념:** Latency·Throughput의 정의, Concurrency, ms와 초의 변환, 비율, Clock frequency의 의미. 모두 현재 개념이다.
- **접근 상태:** 이 추상적 관측값 문제는 현재 접근 가능. Q9·Q16과는 지표 판단 수준의 부분 연결이며, 원문 전체에는 후속 Pipeline·Microcoded/Hardwired CPU 구현 학습이 필요하다.
- **스타일 근거:** Q9는 파이프라이닝이 단일 명령의 실행 Latency를 개선한다는 주장을 참·거짓으로 판정하게 한다. Q16은 Microcoded multi-cycle CPU와 Hardwired pipelined CPU가 최적화하려는 주된 성능 지표를 Latency·Throughput·Clock speed 등을 고려해 설명하게 한다. [EX:ca_2025_2_midterm_q09 p.2] [EX:ca_2025_2_midterm_q16 p.8]
- **변형의 한계:** 단일 작업의 시간에 관한 주장 판정과 지표별 비교 능력만 옮겼다. 아래 요청·수치·조건은 모두 새로 만든 것이다. CPU 구현 대신 관측값을 주며, Q9·Q16의 구현 원리·설계 목표에 대한 원문 답안을 재현하지 않는다.

세 시스템 A·B·C가 같은 종류·입력의 요청을 올바르게 처리한다. 비교 가능한 지속 부하 조건에서 각 요청의 시작부터 완료까지 걸린 시간은 표의 값으로 일정하며, 같은 길이의 정상상태 관측 구간에서 완료율을 별도로 측정했다고 가정한다. 여러 요청이 동시에 진행될 수 있다. 표는 측정값만 제공하며 구현 방식·Core 수·설계 의도는 주어지지 않는다.

| 시스템 | 요청별 Latency | Throughput | 주파수 |
|---|---:|---:|---:|
| A | 100 ms | 20 requests/s | 2 GHz |
| B | 100 ms | 40 requests/s | 2 GHz |
| C | 80 ms | 16 requests/s | 3 GHz |

1. A에서 B로 바뀔 때 두 지표의 변화 배수를 구하고, “처리율이 두 배이므로 요청별 시간은 절반”이라는 주장을 판정하라.
2. 관측된 조건에서 요청 하나의 완료 시간을 최소화할 때와 단위 시간의 완료 수를 최대화할 때 각각 어느 시스템을 고르는가? C의 A 대비 Latency·Throughput 변화도 설명하라.
3. B의 Throughput을 $1/\text{Latency}$로 계산해도 되는가? 또한 C의 주파수가 가장 높다는 사실로 가장 높은 Throughput을 주장할 수 있는가?
4. 이 표만으로 B를 특정 Pipeline CPU로, C를 특정 Microcoded CPU로 식별하거나 어떤 지표를 최적화하려고 설계했는지 확정할 수 있는가?

<details><summary>풀이와 채점 포인트</summary>

1. B/A의 Latency 비율은 $100/100=1$, Throughput 비율은 $40/20=2$다. 처리율은 두 배지만 요청별 시간은 그대로다. 주어진 관측값은 두 지표를 같은 비율로 개선된다고 취급하는 주장의 반례다.

2. 관측된 요청별 시간이 가장 짧은 것은 C(80 ms), 완료율이 가장 큰 것은 B(40 requests/s)다. C/A의 Latency 비율은 $80/100=0.8$로 시간이 20% 줄었지만, Throughput 비율도 $16/20=0.8$로 완료율은 20% 줄었다. 따라서 어느 시스템이 유리한지는 비교 목적에 달려 있다.

3. B에서 $100\text{ ms}=0.1\text{ s}$이므로 그 역수는 10 requests/s로, 별도로 측정한 40 requests/s와 다르다. 동시 진행을 허용한 상황에서 개별 작업 시간과 전체 완료율은 다른 관찰 대상이다. 한 작업씩 쉬지 않고 순차 처리한다는 조건 없이 역수 관계를 적용할 수 없다. C의 주파수는 가장 높지만 측정된 Throughput은 B보다 작으므로 주파수만으로 완료율 우열을 결정할 수도 없다. [M01 p.3] [STT 07:23] [M01 p.6]

4. 확정할 수 없다. 관측값은 이 조건에서 무엇이 빨랐는지를 보여 주지만, 내부 실행 경로·제어 방식이나 설계자의 최적화 의도를 식별하지 않는다. 시스템에 원문의 CPU 구현 이름을 임의로 붙이거나, 관측된 처리율 증가의 원인을 파이프라이닝으로 복원하지 않는다. 원문 구현별 판단은 후속 학습이 필요하다. [STT 48:47]

**채점 포인트, 총 6점:** B/A 두 지표 비율과 잘못된 주장 반박 1점, 목적별 C·B 선택 1점, C/A의 두 20% 감소를 서로 다른 의미로 해석 1점, 역수값 10과 관측값 40의 차이를 동시성으로 설명 1점, 주파수만으로 처리율을 확정할 수 없다는 판단 1점, 구현·설계 의도 추론의 한계 1점.

</details>
