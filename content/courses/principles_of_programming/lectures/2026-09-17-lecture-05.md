이번 강의는 계산의 공통 구조를 함수로 재사용하고, 이동하는 함수가 원래 의미를 유지하는 원리를 다룬다.  
함수의 입력·출력 타입과 환경 연결을 함께 추적하면서, 인자를 단계적으로 받는 방식까지 연결해 학습한다.

## 강의 내용과 설명

### Function value(함수 값)와 Higher-order function(고차 함수)

**Function value는 함수를 계산 결과와 마찬가지로 복사하고, 인자로 전달하고, 반환할 수 있도록 다루는 값이다.** 정수 `3`을 다른 함수에 전달할 수 있듯이, 정수를 받아 제곱을 계산하는 함수 자체도 전달할 수 있다. 여기서 전달하는 것은 특정 입력에 대한 계산 결과가 아니라, 나중에 입력을 받아 계산할 기능이다. 자료는 이러한 관점에서 함수를 일반적인 값으로 설명한다. [M01 p.44] [M01 p.45] [STT 00:21]

함수의 타입은 어떤 입력을 받아 어떤 결과를 내는지 나타낸다. 예를 들어 `Int => Int`는 `Int` 하나를 받아 `Int`를 돌려주는 함수의 타입이고, `(Int, Int) => Int`는 두 `Int`를 받아 하나의 `Int`를 돌려주는 함수의 타입이다. 자료의 일반적인 표기에서는 입력 타입들을 `A1, …, An`, 결과 타입을 `B`로 구분한다. 도입부 STT의 불완전한 타입 낭독을 그대로 수식으로 복원하기보다는, 정확한 타입 구조는 이 자료를 기준으로 읽는다. [M01 p.45] [STT 01:18]

**Higher-order function은 함수를 인자로 받거나 함수를 결과로 반환하는 함수다.** 두 조건을 모두 만족할 필요는 없다. 함수를 받아 정수 하나를 계산하는 함수도, 정수를 받아 새로운 함수를 만들어 반환하는 함수도 이 범주에 들어간다. 함수를 단순히 본문에서 호출한다는 사실만으로 Higher-order function이 되는 것은 아니다. 자신의 입력이나 출력에서 함수를 다루는지가 기준이다. [M01 p.45]

이해를 위한 예시로, 다음 두 표현을 구분해 보자.

```scala
square(3)   // square를 3에 적용하여 정수 결과를 얻는다.
square _   // 자료의 표기: square를 함수 값으로 변환한다.
```

첫 번째는 제곱 계산을 수행하는 적용이고, 두 번째는 제곱 계산을 나중에 수행할 수 있는 값을 만드는 표현이다. 두 번째 표기의 정확한 의미는 뒤에서 함수 정의와 값의 차이를 설명할 때 다시 다룬다. 자료는 컴파일러가 필요한 변환을 자동으로 넣는 경우도 설명하므로, 실제 예제에는 `_`가 생략된 형태도 나온다. [M01 p.47] [M01 p.53]

이번 강의에서 [[concepts/higher-order-functions|Higher-order function]]을 도입한 직접적인 이유는 코드 재사용이다. 계산 방법의 공통 부분은 한 번만 작성하고, 달라지는 부분을 함수로 전달하면 여러 계산을 같은 구조로 표현할 수 있다. 교수는 본질적으로 같은 일을 하는 코드가 여러 곳에 반복되는 상황을 문제로 제시하며 이 방향으로 설명을 진행했다. 이는 이번 발화에서 확인되는 설명의 초점이며, 시험 출제에 관한 주장은 아니다. [STT 02:15] [STT 06:23]

### DRY와 재귀적인 합: 같은 구조에서 달라지는 항 찾기

**DRY(중복을 피하는 원칙)**는 자료에서 `Do not Repeat Yourself`로 제시된다. 이 강의의 예제에서는 겉으로 비슷한 줄을 무조건 없애는 것이 아니라, 동일한 계산 구조를 여러 함수에 복제하지 않도록 만드는 원칙으로 이해하면 된다. [M01 p.49]

먼저 자료의 세 함수를 비교하자. [M01 p.46]

```scala
def sumLinear(n: Int): Int =
  if (n <= 0) 0 else n + sumLinear(n - 1)

def sumSquare(n: Int): Int =
  if (n <= 0) 0 else n * n + sumSquare(n - 1)

def sumCubes(n: Int): Int =
  if (n <= 0) 0 else n * n * n + sumCubes(n - 1)
```

세 함수의 공통점은 종료 조건, 종료값, 다음 입력으로 이동하는 방법, 현재 항과 나머지 결과를 더하는 구조다. 달라지는 것은 현재 `n`에서 계산하는 항이다.

| 비교 항목 | `sumLinear` | `sumSquare` | `sumCubes` |
|---|---|---|---|
| 종료 조건 | `n <= 0` | `n <= 0` | `n <= 0` |
| 종료값 | `0` | `0` | `0` |
| 현재 항 | `n` | `n * n` | `n * n * n` |
| 다음 입력 | `n - 1` | `n - 1` | `n - 1` |
| 결합 방법 | 현재 항과 재귀 결과의 덧셈 | 현재 항과 재귀 결과의 덧셈 | 현재 항과 재귀 결과의 덧셈 |

이 표는 자료의 세 코드를 비교해 재구성한 것이다. 중요한 읽기 순서는 먼저 공통 재귀 구조를 확인하고, 마지막으로 바뀌는 항을 찾는 것이다. 함수 이름만 다르다고 별개의 알고리즘으로 받아들이면 재사용할 수 있는 구조를 놓치게 된다. [M01 p.46]

자료 코드에서 도출한 **이해를 위한 예시**로 `n = 3`을 계산하면 다음과 같다.

$$
\begin{aligned}
\operatorname{sumLinear}(3) &= 3+2+1+0=6,\\
\operatorname{sumSquare}(3) &= 3^2+2^2+1^2+0=14,\\
\operatorname{sumCubes}(3) &= 3^3+2^3+1^3+0=36.
\end{aligned}
$$

각 식의 마지막 `0`은 종료 조건에서 반환하는 값이다. 따라서 세 계산은 모두 현재 항 하나를 처리한 뒤 더 작은 문제로 이동하고, 종료값에서부터 덧셈 결과를 되돌려 받는다.

주의할 점은 **작동하는 코드와 중복이 적은 코드는 서로 다른 평가 기준**이라는 것이다. 세 함수를 각각 작성해도 계산은 가능하지만, 공통 구조를 수정할 일이 생기면 여러 곳을 함께 고쳐야 한다. 강의의 질문도 코드가 실행되는지에서 끝나지 않고, 같은 구조를 반복해서 작성하고 있는지로 이어진다. [STT 03:37] [STT 06:23]

이 구간에는 실시간 편집과 짧은 교실 응답이 섞여 있다. 편집 명령, 도구 이름, 단축키, 화면에서 바꾼 대상과 실제 실행 성공 여부는 **검증 필요**다. STT에 남은 제곱·세제곱 항의 반복도 정확한 산술 전개로 복원하지 않는다. 위 계산은 자료 코드의 설명이며, 당시 발화나 화면 결과를 교정하여 재현한 것이 아니다. [STT 03:15] [STT 03:35] [STT 03:58] [STT 05:24] [STT 06:23]

### `sum(f, n)`: 달라지는 계산을 함수 인자로 추출하기

앞의 세 함수에서 바뀌는 부분은 `n`, `n * n`, `n * n * n`이다. 이들은 모두 현재 `n`에 의존한다. 따라서 달라지는 부분을 인자로 받으려면 이미 계산된 고정 정수 하나보다, **현재 정수에서 해당 항을 계산하는 함수**가 필요하다. 강의도 바뀌는 부분이 `n`에 의존한다는 점에서 함수 인자의 타입을 도출한다. [STT 07:08] [STT 08:00]

이 역할을 하는 `f`의 타입은 `Int => Int`다. 입력은 현재 위치를 나타내는 정수이고, 출력은 그 위치에서 더할 정수 항이다. 자료는 공통 구조를 다음과 같이 작성한다. [M01 p.47]

```scala
def sum(f: Int => Int, n: Int): Int =
  if (n <= 0) 0
  else f(n) + sum(f, n - 1)

def linear(n: Int) = n
def square(n: Int) = n * n
def cube(n: Int) = n * n * n

def sumLinear(n: Int) = sum(linear, n)
def sumSquare(n: Int) = sum(square, n)
def sumCubes(n: Int) = sum(cube, n)
```

이제 `sum`은 반복해서 합을 구하는 방법을 담당하고, `f`는 각 항의 모양을 담당한다. `sum`의 재귀 호출에서 `f`를 그대로 전달하는 이유는, 남은 구간에도 같은 항 생성 규칙을 적용해야 하기 때문이다. `n`은 줄어들지만 제곱을 합한다는 계산의 종류는 바뀌지 않는다.

예를 들어 `sum(square, 3)`의 전개는 다음과 같다. 이는 자료 코드에서 도출한 이해를 위한 예시다.

```text
sum(square, 3)
= square(3) + sum(square, 2)
= 9 + square(2) + sum(square, 1)
= 9 + 4 + square(1) + sum(square, 0)
= 9 + 4 + 1 + 0
= 14
```

여기서 `square`와 `square(3)`을 혼동하면 안 된다. `sum`에 필요한 것은 남은 모든 `n`에서 사용할 수 있는 함수다. `square(3)`을 전달하면 이미 계산된 정수 `9`일 뿐이므로, `Int => Int`를 요구하는 자리를 대신하지 못한다.

또한 이 일반화된 코드는 `n <= 0`에서 바로 종료하므로 **`f(0)`을 호출하지 않는다.** 원래의 `linear`, `square`, `cube`는 모두 0에서 0을 내므로 0부터 더한다는 설명과 수치가 일치한다. 그러나 임의의 `f`를 넣을 때까지 이를 그대로 일반화하면 안 된다. 예컨대 이해를 위한 예시로 `f(x) = x + 1`을 사용하면 `sum(f, 2)`는 `f(2) + f(1) = 3 + 2 = 5`이며, `f(0)`까지 포함한 합은 아니다. [M01 p.47]

강의 중 짧은 반응과 불완전한 함수 이름 낭독은 이 일반화 과정의 교실 맥락으로 남긴다. 정확한 함수 이름이나 코드를 그 반응에서 추가로 추론하지 않는다. 확인되는 내용은 바뀌는 부분을 함수로 전달하고, 공통 패턴을 한 번만 작성한다는 설명이다. [STT 07:48] [STT 09:04] [STT 10:51] [STT 10:56]

### Anonymous function(익명 함수)과 타입을 읽는 방법

**Anonymous function은 별도의 함수 이름을 먼저 선언하지 않고 함수 값을 표현하는 방법이다.** 앞에서는 `square`를 정의한 다음 그 이름을 전달했다. 한 번 사용할 짧은 계산이라면 사용 위치에서 바로 함수 값을 만들 수 있다. 이것이 강의에서 제기한 다음 문제다. [M01 p.48] [STT 12:12]

자료의 기본 형태는 다음과 같다.

```scala
(x1: T1, ..., xn: Tn) => e
```

`=>` 왼쪽은 받을 인자들을, 오른쪽의 `e`는 그 인자들로 계산할 식을 나타낸다. 이 표현을 쓴 순간 특정 입력의 계산 결과를 얻는 것은 아니다. 입력이 주어졌을 때 `e`를 계산하는 함수 값을 만든다.

자료는 앞의 세 합을 다음처럼 표현한다. [M01 p.48]

```scala
def sumLinear(n: Int) =
  sum((x: Int) => x, n)

def sumSquare(n: Int) =
  sum((x: Int) => x * x, n)

def sumCubes(n: Int) =
  sum((x: Int) => x * x * x, n)
```

예를 들어 `(x: Int) => x * x`에서 `x`는 나중에 함수가 받을 입력이다. `sum`이 이 함수를 각 정수에 적용하면, 그때마다 해당 정수의 제곱을 얻는다. `x`는 이 Anonymous function 안에서 사용하는 이름이므로, 바깥 함수의 `n`과 반드시 같을 필요가 없다.

자료에는 인자 타입을 생략한 형태도 함께 나온다.

```scala
def sumSquare(n: Int) =
  sum((x) => x * x, n)
```

이 예제에서 `sum`은 첫 번째 인자로 `Int => Int`를 요구한다. 그 문맥이 Anonymous function의 입력과 출력 타입을 파악하는 근거가 된다. **타입을 생략한다는 것은 타입이 없어지는 것이 아니라, 코드에 모두 적지 않아도 문맥에서 알아낼 수 있다는 뜻이다.** [M01 p.47] [M01 p.48]

강의의 타입 추론 논의는 컴파일러의 능력뿐 아니라 사람의 읽기 비용을 다룬다. 타입을 명시하면 독자가 함수 본문을 분석하여 입력과 결과의 종류를 추론하는 수고를 줄일 수 있다. 다만 교수는 IDE의 타입 표시가 이런 수고를 보완할 수 있으므로, 이 논거의 비중이 개발 환경에 따라 달라질 수 있다고 한정했다. 이번의 간단한 함수 예제에서는 생략형을 사용하겠다는 설명도 이어진다. [STT 14:46] [STT 15:42] [STT 16:23] [STT 17:05]

이해를 위한 예시로, 독자가 다음 두 표현을 처음 본다고 생각해 보자.

```scala
(x: Int) => x * x
(x) => x * x
```

첫 번째는 표현 자체에 입력 타입이 적혀 있다. 두 번째는 주변 문맥도 함께 읽어야 한다. 어느 표기가 가능한지는 해당 문맥과 언어 규칙의 문제이고, 어느 표기가 읽기 쉬운지는 독자와 도구 환경까지 고려할 문제다.

STT에는 타입을 항상 적어야 한다는 식의 단정과 생략을 허용하는 설명이 함께 나타난다. 타입을 추론할 수 있어도 명시하게 하는 이유를 묻는 대목에서, 교수의 발언은 “그런데 스칼라는 무조건 쓰게 합니다.”로 기록되어 있다. 같은 구간의 “다리가 유추할 수 있으면”은 추론 주체·목적어가, “다른 많은 LPG는”은 비교한 언어·언어군이 미확정인 표현으로 남긴다. [STT 13:53] 이 단정적 발언을 모든 Scala 함수 인자에 적용되는 하나의 규칙으로 정리하지 않는다. 정확히 어떤 선언 형태를 가리켰는지, 비교한 언어가 무엇인지, 의도한 타입과 추론된 타입이 어긋나는 구체 사례는 **검증 필요**다. 이 노트에서 확인하는 생략형의 근거는 p.48의 실제 코드다. [M01 p.48] [STT 12:57] [STT 13:53] [STT 14:46]

[[concepts/anonymous-functions|Anonymous function]]의 편리함은 이름이 짧아지는 데만 있지 않다. 계산 방법을 사용하는 자리에서 바로 보여 주므로, `sum`의 공통 구조와 각 호출의 차이를 함께 읽을 수 있다는 장점이 있다.

### 구간의 `sum`과 `product`: 경계 조건까지 포함한 계산

다음 단계는 합의 범위를 `1`부터 `n`까지로 고정하지 않고, `a`부터 `b`까지 지정하는 것이다. 자료의 구간은 **양 끝을 포함**한다. `a <= b`이면 현재 `a`를 처리하고 `a + 1`로 이동하며, `a > b`이면 더 처리할 항이 없으므로 종료한다. [M01 p.49] [STT 17:40] [STT 18:21]

```scala
def sum(f: Int => Int, a: Int, b: Int): Int =
  if (a <= b) f(a) + sum(f, a + 1, b)
  else 0

def product(f: Int => Int, a: Int, b: Int): Int =
  if (a <= b) f(a) * product(f, a + 1, b)
  else 1
```

앞의 `sum(f, n)`과 달리 여기서는 작은 쪽 경계 `a`를 하나씩 증가시킨다. 방향은 달라도 구조는 같다. 현재 항을 처리하고, 더 작은 나머지 문제를 풀고, 두 결과를 결합한다.

종료값이 다른 이유는 결합 연산이 다르기 때문이다. 합은 남은 항이 없을 때 `0`을 반환해야 앞에서 계산한 값을 바꾸지 않는다. 곱은 `1`을 반환해야 앞의 곱을 보존한다. 곱의 종료값을 `0`으로 두면 마지막에 반드시 0을 곱하므로, 항이 있는 구간의 결과까지 모두 0이 된다. [M01 p.49]

자료 코드에 따른 수학적 표현은 다음과 같다.

$$
\operatorname{sum}(f,a,b)=
\begin{cases}
f(a)+\operatorname{sum}(f,a+1,b), & a\le b,\\
0, & a>b,
\end{cases}
$$

$$
\operatorname{product}(f,a,b)=
\begin{cases}
f(a)\cdot\operatorname{product}(f,a+1,b), & a\le b,\\
1, & a>b.
\end{cases}
$$

이해를 위한 예시로 `f(x) = x`, `a = 2`, `b = 4`를 사용하면 합은 `2 + 3 + 4 + 0 = 9`, 곱은 `2 × 3 × 4 × 1 = 24`다. `a = b = 4`이면 현재 항 `4`를 한 번 처리한 뒤 종료한다. 처음부터 `a = 5`, `b = 4`이면 `f`를 적용할 항이 없으므로 각각 `0`, `1`을 반환한다.

따라서 빈 구간은 무조건 오류인 것도, 두 함수가 공통으로 0을 반환하는 경우도 아니다. 이 코드의 정의에서는 합과 곱에 맞는 종료값을 갖는 정상적인 경우다. [STT 19:10]

강의의 구간 열거에는 중간 정수 하나가 빠져 있고, 연산식 낭독도 일부 손상되어 있다. 이를 교수의 발화를 완성한 목록이나 수식으로 제시하지 않는다. **모든 정수를 한 칸씩 처리한다는 설명과 `product`의 종료값 `1`은 자료 코드에 근거한다.** [M01 p.49] [STT 18:21] [STT 19:10]

### `mapReduce`: 항을 만드는 일과 결과를 결합하는 일 분리하기

구간 `sum`과 `product`를 비교하면 이번에는 두 부분이 달라진다. 하나는 현재 항과 나머지 결과를 합치는 연산이고, 다른 하나는 빈 구간의 결과다. 이 차이까지 인자로 받으면 두 함수를 하나의 공통 구조로 표현할 수 있다. [M01 p.49] [STT 19:10]

자료의 `mapReduce`는 다음 세 종류의 계산 정보를 구분한다.

| 인자 | 타입 | 역할 |
|---|---|---|
| `f` | `Int => Int` | 현재 정수에서 처리할 항을 만든다. |
| `reduce` | `(Int, Int) => Int` | 현재 항과 나머지 구간의 결과를 결합한다. |
| `inival` | `Int` | 빈 구간에서 반환할 값을 정한다. |

여기에 구간의 양 끝 `a`, `b`가 들어간다. `f`는 입력 하나를 변환하고, `reduce`는 이미 얻은 결과 두 개를 결합한다는 차이가 중요하다. 자료의 코드는 다음과 같다. [M01 p.50] [STT 20:11]

```scala
def mapReduce(
  reduce: (Int, Int) => Int,
  inival: Int,
  f: Int => Int,
  a: Int,
  b: Int
): Int = {
  if (a <= b)
    reduce(f(a), mapReduce(reduce, inival, f, a + 1, b))
  else
    inival
}
```

이 코드에서 구간을 순회하는 구조는 고정되어 있다. 각 위치에서 무엇을 계산할지는 `f`가 정하고, 그렇게 얻은 결과들을 어떤 방식으로 합칠지는 `reduce`가 정한다. 따라서 `sum`과 `product`는 다음 선택으로 얻어진다. [M01 p.50]

```scala
def sum(f: Int => Int, a: Int, b: Int): Int =
  mapReduce((x, y) => x + y, 0, f, a, b)

def product(f: Int => Int, a: Int, b: Int): Int =
  mapReduce((x, y) => x * y, 1, f, a, b)
```

이해를 위한 예시로 `f(x) = x * x`, 구간 `2`부터 `3`, `reduce(x, y) = x + y`, `inival = 0`을 택하면 다음 구조가 된다.

```text
reduce(f(2), reduce(f(3), 0))
= reduce(4, reduce(9, 0))
= reduce(4, 9)
= 13
```

여기서 `inival`은 이름만 보고 임의의 시작 숫자로 취급하면 안 된다. 선택한 연산과 의도한 계산에 맞는 값이어야 한다. 예를 들어 제곱들의 곱을 구하려면서 곱셈과 `0`을 함께 넘기면, 재귀 구조 자체는 따라가더라도 원하는 곱이 나오지 않는다.

또한 자료의 코드는 현재 항을 첫 번째 인자, 나머지 구간의 결과를 두 번째 인자로 넘긴다. 따라서 일반적인 `reduce`에 대해서는 인자 순서나 괄호 구조를 마음대로 바꾸면 안 된다. 덧셈 예제에서 익숙하다는 이유만으로 모든 결합 연산을 같은 방식으로 재배치할 수 있다고 생각하는 것이 오개념이다. [M01 p.50]

[[concepts/map-reduce|mapReduce]]가 보여 주는 재사용의 단위는 “제곱을 더하는 함수 하나”보다 크다. 항의 계산, 결과의 결합, 종료값을 각각 바꿀 수 있으면서 구간을 처리하는 공통 구조는 유지된다.

### MapReduce의 강의 사례: 큰 데이터를 나누어 처리하려는 동기

강의는 작은 정수 구간의 `mapReduce`에서 대규모 데이터 처리의 동기로 설명을 넓힌다. 이때의 핵심 질문은 데이터가 너무 많아 한 컴퓨터에 모두 담기 어렵다면, 전체 계산을 어떻게 나누어 수행할 것인가이다. 구체적인 사례로 Facebook 전체 사용자의 나이 통계와 평균 계산이 언급된다. 수억 명 규모의 데이터를 생각하면 단순히 덧셈 식을 아는 것과 데이터를 실제로 처리할 구조를 갖추는 것은 다른 문제가 된다. [STT 21:52] [STT 22:33]

강의에서 제시한 개략적인 순서는 다음과 같다.

1. 전체 데이터를 여러 서버에 나눈다.
2. 각 서버 안에서 개별 데이터에 해당하는 계산을 적용한다.
3. 그 결과들을 선택한 연산으로 결합한다.

이는 개별 항을 만드는 역할과 결과를 결합하는 역할을 분리한다는 점에서 앞의 코드와 연결된다. 다만 자료의 `Int` 구간 재귀 함수 자체가 여러 서버에서 실행되는 시스템은 아니다. 강의는 그 구조적 아이디어를 대규모 처리의 동기와 연결하고 있다. [M01 p.50] [STT 25:31]

어떤 결합 연산을 고르는지, 계산을 나누거나 재배치해도 원하는 결과가 유지되는지가 중요하다는 설명도 이어진다. 그러나 그 조건을 말하는 STT가 손상되어 있어, 이를 교수의 완전한 결합법칙·교환법칙 설명으로 복원할 수는 없다. 확인되는 한정은 **모든 처리가 이 단순한 구조에 그대로 맞는 것은 아니며 변형이 필요할 수 있다**는 것이다. [STT 26:26] [STT 27:04]

이해를 위한 작은 사례로, 한쪽에 두 개의 숫자, 다른 쪽에 세 개의 숫자가 나뉘어 있다고 생각해 보자. 각각의 항을 계산하는 규칙과 결과를 합치는 규칙을 구분하면, “어느 데이터를 어디에서 처리하는가”와 “무엇을 계산하는가”를 나누어 생각할 수 있다. 이 사례는 역할 분리를 이해하기 위한 것이며, 실제 분산 처리 절차나 강의에서 다룬 평균 계산의 완성된 구현을 제시하는 것은 아니다.

인터넷 보급, Google의 MapReduce, 이후의 공개 소프트웨어와 AI 도구를 연결하는 일화도 있었다. 이 부분은 기술적 동기를 전달하는 강의 중 부연으로 구분한다. 교수는 MapReduce와 Big data의 과거를 이야기하며 인터넷 보급으로 화제를 옮기는 대목에서 “90년대까지도 인터넷이 없었거든요.”라고 말한 것으로 STT에 기록되어 있다. 이 문장은 제공된 발언으로 보존하며, 검증된 역사적 사실로 채택하거나 외부 지식으로 연대를 고쳐 쓰지 않는다. [STT 21:52] 정확한 인터넷 보급 연대, 빠진 프로젝트·도구 이름, AI와 관련된 사건 및 성능 주장은 **검증 필요**다. 불명확한 이름을 외부 지식으로 채워 넣거나, 일화를 검증된 기술사로 바꾸지 않는다. [STT 21:52] [STT 23:31] [STT 24:32]

### Environment(환경)와 함수 코드만 이동시킬 때의 문제

**Environment는 이름을 해석하는 데 필요한 정보를 담고, 필요하면 바깥 Environment로 이어지는 연결을 갖는 계산 모델이다.** 함수 안에 적힌 이름이 무엇을 뜻하는지는 코드의 글자만으로 정해지지 않는다. 그 이름을 어느 Environment에서 찾는지도 필요하다. 강의는 Function value가 다른 위치로 전달되어도 원래 의미를 유지하려면 무엇을 함께 보존해야 하는지 묻는다. [M01 p.51] [STT 27:04]

자료의 예제는 다음과 같다. [M01 p.51]

```scala
{
  val t = 0

  val f: Int => Int = {
    val t = 10
    def g(x: Int): Int = x + t
    g _
  }

  f(20)
}
```

바깥에는 `t = 0`이 있고, `g`를 정의한 안쪽에는 `t = 10`이 있다. `g`의 본문에서 `x`는 호출할 때 받은 인자이고, `t`는 `g`가 정의된 안쪽 Environment의 값이다. 따라서 이 `g`는 입력에 10을 더하는 함수로 이해해야 한다.

p.51은 먼저 **정의 Environment를 보존하지 않고 코드만 함수 값처럼 옮기는 불충분한 모델**을 시도한다. 안쪽에서 만든 `(x) x + t`라는 코드만 `f`에 넣고, 나중에 `f`를 찾은 바깥 Environment를 기준으로 실행하면 어떤 일이 생기는지 보여 준다.

자료의 평가 도표를 단계별로 다시 읽으면 다음과 같다. [M01 p.51]

| 단계 | Environment의 정보 | 코드만 옮긴 모델의 해석 |
|---|---|---|
| 바깥 블록 | `E0`에 `t = 0` | 바깥 이름들을 보관한다. |
| 안쪽 블록 | `E1`에 `t = 10`, `g`의 코드 | `g`는 안쪽의 `t`를 사용하는 코드다. |
| 안쪽 결과 반환 | `f`에 `(x) x + t`만 저장 | 코드가 어느 Environment에서 정의되었는지 잃는다. |
| `f(20)` 적용 | `E2`에 `x = 20`, 부모를 `E0`로 연결 | `t`를 바깥에서 찾아 `0`을 얻는다. |
| 계산 | `20 + 0` | 잘못된 모델의 결과 `20` |

이 도표에서 읽어야 할 핵심은 마지막 숫자만이 아니라 **`E2`의 부모가 어디인가**이다. 부모를 `E0`로 연결했기 때문에 원래 안쪽의 `t = 10`을 잃고 바깥의 `t = 0`을 사용한다.

따라서 p.51의 `20`은 이 Scala 코드의 올바른 결과를 제시한 것이 아니다. 함수 코드만 이동시키는 모델의 결함을 드러내는 결과다. 강의에서도 원래 `g`의 의미에 따르면 `20 + 10 = 30`이어야 한다고 설명한다. [STT 31:10] [STT 32:25]

이 문제를 “안쪽 변수를 찾지 못했으니 가장 가까운 값을 아무 데서나 쓰면 된다”로 이해하면 안 된다. 함수의 의미를 보존하려면, 함수를 현재 보관하는 장소와 함수가 정의된 장소를 구분해야 한다. [[concepts/environment-model|Environment model]]에서 필요한 것은 이 차이를 표현할 추가 정보다. [STT 33:20]

### Closure(클로저): 코드와 정의 Environment를 함께 보존하기

**Closure는 함수 코드와 그 코드가 정의된 Environment를 함께 묶은 함수 값이다.** 코드만 이동시킬 때 생긴 문제를 해결하려면 함수 본문뿐 아니라, 본문 안의 이름을 원래 어디에서 찾아야 하는지도 보존해야 한다. 자료는 Function value를 이러한 Closure로 설명한다. [M01 p.52] [M01 p.53] [STT 39:05]

앞의 예제에서 `f`가 보관해야 하는 것은 단순한 `(x) x + t`가 아니라 다음과 같은 쌍이다.

```text
(E1, (x) x + t)
```

여기서 `E1`은 `g`가 정의되었고 `t = 10`이 있는 Environment다. 쌍의 순서는 자료의 표기를 따른다. 핵심은 두 요소가 함께 있다는 사실이다. [M01 p.52]

`f(20)`을 적용할 때의 과정은 다음과 같다.

1. `f`에서 함수 코드와 보존된 Environment `E1`을 얻는다.
2. 실제 인자 `20`을 `x`에 연결하는 새 Environment `E2`를 만든다.
3. `E2`의 부모를 Closure에 저장된 `E1`로 연결한다.
4. 본문 `x + t`를 계산한다.
5. `x`는 `E2`에서 `20`, `t`는 부모 `E1`에서 `10`을 얻는다.

따라서 결과는 `30`이다. [M01 p.52] [STT 32:25] [STT 41:04]

```text
E2: x = 20
  부모 → E1: t = 10
             부모 → E0: t = 0

x + t = 20 + 10 = 30
```

이 그림은 p.52의 평가 관계를 재구성한 것이다. p.51과 비교할 때 함수 본문의 `x + t`가 바뀐 것이 아니라, **새 인자 Environment가 참조하는 부모가 `E0`에서 `E1`로 바뀌었다**는 점을 읽어야 한다. `f`가 바깥에 저장되어 있어도, 호출 시 사용할 정의 Environment는 Closure 안의 정보로 결정된다.

교수는 함수 코드만 옮길 때 저장된 Environment에 따라 의미가 달라지는 문제를 설명하며, 자신은 같은 사람이어도 국적이 한국에서 북한으로 바뀌면 삶과 받는 대우가 달라진다는 가정을 들었다. STT에는 “내 국적이 한국에서 북한으로 바뀌면 내 삶은 영향을 받는 게 완전히 다르죠.”라고 기록되어 있다. 이는 함수의 의미를 해석하는 Environment가 달라질 때의 문제를 전달하기 위한 교수의 국적 변경 비유다. [STT 34:12]

교수는 이어 스페인에서 한 회사 대표와 우연히 만났을 때 서로 중국인이라고 생각해 영어로 대화하다가, 이름을 묻고 한국인임을 알게 되었다는 개인 일화를 말했다. 교수는 이를 여권이 없으면 자신의 국적을 다르게 생각할 수 있다는 설명과 연결했다. 이 내용은 교수의 개인 경험으로 한정하며 국적 집단에 관한 일반적 주장으로 확대하지 않는다. [STT 37:16]

강의는 정의 Environment의 정보를 여권에 비유한다. 사람이 다른 곳으로 이동하더라도 자신을 식별할 정보를 함께 가지고 다니듯, 함수 값도 이동하면서 정의 Environment의 정보를 가지고 다녀야 한다는 설명이다. 여러 곳을 다니는 여행 유튜버도 여권을 지녀야 한다는 비유가 이어진다. 이들은 [[concepts/closures|Closure]]의 필요성을 전달하기 위한 강의 고유의 비유이며, 코드 평가 규칙의 증명은 아니다. [STT 38:11] [STT 40:05]

구현 아이디어로는 필요한 정보들을 하나씩 전달하는 방법과, 정의 Environment를 식별하는 참조를 함께 보존하는 방법이 비교된다. 강의의 설명은 후자를 통해 원래 Environment에서 이름을 찾을 수 있다는 방향으로 진행된다. 다만 주소의 폭이나 단위, 칠판에 사용한 Environment 번호는 정확히 확인되지 않는다. 이를 특정 비트 수나 자료의 `E0`, `E1`, `E2`와 동일한 번호로 확정하지 않는다. [STT 35:09] [STT 36:20]

또한 Closure와 연결해 언급한 언어 이름, 그 언어의 사용 분야, 개인 일화 속 회사명은 **검증 필요**다. 이러한 불확실성은 코드와 정의 Environment를 함께 보존한다는 자료의 명확한 설명과 구분한다. [STT 37:16] [STT 39:05]

### 블록 종료와 Environment의 수명은 왜 다른가

Closure가 안쪽 Environment를 보존한다면, 그 블록의 계산이 끝난 뒤에도 Environment가 필요할 수 있다. **블록에서 실행이 빠져나오는 시점과 그 블록의 정보가 더 이상 필요하지 않은 시점은 같지 않을 수 있다.** 앞의 예제에서는 안쪽 블록이 끝난 뒤에야 `f(20)`을 호출하지만, 그때도 안쪽의 `t = 10`을 찾아야 한다. [M01 p.52] [STT 41:04]

이것은 단순히 값을 미리 계산해 놓았다는 이야기와 다르다. 안쪽 블록이 반환한 것은 정수 `30`이 아니라 나중에 `x`를 받을 함수 값이다. 호출 시점에 사용할 `x`는 아직 없었지만, `t`를 어디에서 찾아야 하는지는 이미 정해져 있었다. Closure가 그 연결을 유지하기 때문에 나중의 호출이 가능하다.

강의는 여기서 **Garbage collector(메모리 회수기)**가 참조되는 Environment를 유지하는 역할을 설명한다. 밖으로 전달되어 이후에도 사용할 수 있는 Closure가 어떤 Environment를 계속 참조한다면, Garbage collector는 그 Environment를 블록 종료만으로 회수하지 않고 살려 둔다. 이후 계산에서 접근할 수 있는 동안 필요한 정보를 유지해야 한다는 것이다. [STT 41:04]

이 수명 관리와 Closure의 코드·정의 Environment 결합은 **Higher-order function(고차 함수) 지원**으로 이어진다. 함수 값을 다른 함수에 인자로 전달하거나 결과로 반환하면, 정의한 블록을 벗어난 뒤에도 호출할 수 있어야 한다. Closure가 원래 Environment를 참조하고 Garbage collector가 그 참조로 여전히 필요한 Environment를 유지하므로, 나중에도 정의 당시의 변수 정보를 찾아 실행할 수 있다. 교수는 이 연결을 Higher-order function을 쉽게 지원하게 하는 기술로 설명한다. 참조가 사라지는 즉시 메모리가 회수된다는 보장은 이 발언에서 확인되지 않는다. [STT 41:04] [STT 42:00]

이해를 위한 판단 사례로, 안쪽 블록을 종료하는 순간 `E1`을 완전히 없앴다고 가정해 보자. 그러면 `f`가 `E1`을 기억하더라도 실제로 `t = 10`을 얻을 곳이 사라진다. 따라서 Closure를 설명하는 모델은 코드와 Environment의 연결뿐 아니라, 그 연결을 사용할 수 있을 만큼 정보가 유지된다는 점도 함께 요구한다.

다만 이 개념적 모델에서 **모든 Scala 지역 변수가 반드시 같은 메모리 영역에 할당된다**거나 **특정 컴파일러가 항상 동일한 저장 방식을 사용한다**고 결론 내릴 수는 없다. 강의의 비교 발화 중 구체적인 할당 방식에 관한 부분은 손상되어 있다. 여기서 확보할 학습 내용은 실행 범위를 벗어났다는 사실만으로, 반환된 함수가 필요로 하는 정보까지 즉시 불필요해지는 것은 아니라는 점이다. [STT 42:00]

### Parameterized expression(매개변수화된 식)과 Closure value의 구별

자료는 `def`로 정의한 함수를 **Parameterized expression**으로, 전달하고 반환하는 함수 값을 **Closure value**로 구분한다. 이 구분은 이미 정의된 계산을 인자에 적용하는 것과, 그 계산을 Environment와 함께 묶어 값으로 만드는 것을 나누어 설명하기 위한 것이다. [M01 p.53]

자료의 표기에서 `f _`는 Parameterized expression `f`를 함수 값으로 변환한다. Anonymous function은 처음부터 값으로 제시된다. 컴파일러가 문맥에 따라 필요한 변환을 자동으로 삽입하기도 하므로, `_`가 눈에 보이지 않는다고 언제나 변환이 없다고 판단해서는 안 된다. 반대로 아무 식 뒤에나 `_`를 붙이면 올바른 함수 값이 된다고 생각해서도 안 된다. [M01 p.53]

| 구분 | 자료에서 설명하는 역할 |
|---|---|
| `def`로 정의한 함수 | 인자를 받아 계산할 Parameterized expression |
| `f _` | `f`를 Environment와 묶인 값으로 변환하는 표기 |
| Anonymous function | 함수 값을 직접 표현하는 문법 |
| Closure value | 함수 코드와 정의 Environment를 함께 가진 값 |

이 구별은 p.51과 p.52의 `val f`를 `def f`로 바꾸면 어떻게 되는가라는 질문에도 연결된다. 다음 설명은 **자료의 질문에 대한 노트의 코드 분석**이며, 불완전한 발화를 복원한 답이나 실제 실행 확인을 뜻하지 않는다. [M01 p.51] [M01 p.52]

원래의 선언은 다음 구조다.

```scala
val f: Int => Int = {
  val t = 10
  def g(x: Int): Int = x + t
  g _
}
```

`val f`는 초기화할 때 오른쪽 블록을 평가하고, 그 결과인 Closure value를 저장한다. 이후 `f`를 사용하면 저장된 값을 이용한다.

이를 다음처럼 괄호 없는 `def f`로 바꾸면, `f`를 사용할 때 오른쪽 블록을 다시 평가하여 함수 값을 얻는다.

```scala
def f: Int => Int = {
  val t = 10
  def g(x: Int): Int = x + t
  g _
}
```

두 경우의 차이는 오른쪽 표현식을 언제 평가하고 그 결과를 어떻게 이용하는가이다. **어느 경우에도 반환된 `g`가 참조하는 `t`를 호출자의 바깥 `t = 0`으로 바꾸지는 않는다.** 이 예제에서 만들어지는 `g`의 Closure는 내부의 `t = 10`을 보존하므로 `f(20)`의 결과는 두 경우 모두 `30`이다.

따라서 `def`로 바꾸면 p.51의 잘못된 결과 `20`이 정당해진다는 해석은 틀리다. `20`의 원인은 평가 시점이 아니라 정의 Environment의 손실이다. 또한 여기의 `def f`는 괄호가 없는 선언이며, 이를 `def f()`와 같은 표기로 슬쩍 바꾸어 설명하지 않는다. 구체적인 메모리 할당 횟수나 최적화 효과까지 이 분석에서 주장하지 않는다.

### Call-by-name(이름에 의한 호출): 인자 식에도 Environment가 필요하다

**Call-by-name은 인자 식을 미리 값으로 계산해 넘기는 대신, 함수 본문에서 필요할 때 계산하도록 전달하는 방식이다.** 그런데 식만 전달하면 앞의 함수 코드와 같은 문제가 생긴다. 식이 다른 위치로 이동하면서, 그 안의 이름을 찾는 Environment가 바뀔 수 있기 때문이다. 자료는 인자 식도 Closure로 변환하여 이 문제를 해결한다고 설명한다. [M01 p.53] [STT 42:57]

이때는 다음 두 Environment를 구분해야 한다.

- 함수 본문에서 사용하는 바깥 이름은 **함수가 정의된 Environment**에서 해석한다.
- 전달된 인자 식의 이름은 **그 인자 식이 호출 위치에서 갖던 Environment**에서 해석한다.

자료의 예제는 다음과 같다. [M01 p.54]

```scala
{
  val t = 0
  def f(x: => Int) = t + x

  val r = {
    val t = 10
    f(t * t)
  }

  r
}
```

`f`의 본문 `t + x`는 바깥의 `t = 0`이 있는 곳에서 정의되었다. 반면 호출의 인자 식 `t * t`는 안쪽의 `t = 10`이 있는 곳에서 작성되었다. 같은 철자 `t`라도 두 식이 참조하는 값은 다르다. [STT 43:52]

p.54의 평가 도표에서 가장 중요한 부분은 `x`에 저장하는 정보다.

```text
x = (E1, t * t)
```

이 정보는 인자 식 `t * t`와 그 식의 호출 Environment `E1`을 묶는다. 자료는 이를 인자가 없는 함수 `() => t * t`처럼 생각할 수 있도록 주석을 붙인다. [M01 p.54]

도표를 두 경로로 나누어 읽으면 다음과 같다.

| 계산 대상 | 사용하는 Environment 관계 | 얻는 결과 |
|---|---|---|
| 함수 본문의 `t` | 인자 Environment `E2`에서 부모 `E0`로 이동 | `0` |
| 함수 본문의 `x` | `E2`에 저장된 인자 Closure를 사용 | `(E1, t * t)`를 평가 |
| 인자 식의 각 `t` | 인자 Closure가 보존한 `E1` | 각각 `10` |
| 인자 식 `t * t` | `E1`에서 계산 | `100` |
| 함수 본문 `t + x` | `0 + 100` | `100` |

따라서 마지막 `r`도 `100`이다. [M01 p.54] [STT 47:48]

```text
함수 본문의 이름 탐색:
E2: x = (E1, t * t)
  부모 → E0: t = 0

x가 필요할 때의 별도 계산:
(E1, t * t) → 10 * 10 → 100
```

이 두 번째 평가 그림은 Closure를 쓴다고 항상 같은 Environment 하나에서 모든 식을 실행하는 것이 아님을 보여 준다. 함수 본문과 인자 식은 각각 자신이 의미를 얻은 Environment를 사용한다. `E2`의 부모를 호출 위치 `E1`로 바꿔 버리면 본문의 `t`까지 `10`으로 해석하는 잘못을 저지른다. 반대로 인자 식을 `E0`에서 계산하면 `t * t`가 `0`으로 바뀐다.

이번 예제의 핵심은 결과 `100`을 외우는 것이 아니라, **본문의 `t`와 인자 식의 `t`가 서로 다른 Environment에서 해석되는 이유를 설명하는 것**이다. [[concepts/call-by-name|Call-by-name]]의 인자도 이동하는 식이므로, 의미를 보존할 Environment 정보가 필요하다.

STT의 칠판 Environment 번호는 자료의 번호와 같다고 확정하지 않는다. 또한 손상된 숫자 발화를 인자 식의 평가 횟수로 해석하거나, 잘린 평가 방식 이름을 임의로 완성하지 않는다. 위의 `E0`, `E1`, `E2`와 계산식은 p.54의 도표에 근거한다. 필요한 Environment를 함께 보존한다는 설명은 확인되지만, 뒤따르는 과거 언어 관련 일화의 정확한 주장은 **검증 필요**다. [STT 44:49] [STT 45:52] [STT 46:50] [STT 48:46]

### Currying(커링)의 동기: 일부 입력을 받아 나머지 계산을 반환하기

앞의 구간 합을 종류별로 사용하려면 다음처럼 `a`, `b`를 다시 받아 `sum`에 전달하는 함수를 작성할 수 있다. 자료는 이런 **Wrapper function(감싸는 함수)**의 반복을 다음 개선 대상으로 삼는다. [M01 p.55] [M01 p.56]

```scala
def sumLinear(a: Int, b: Int) =
  sum((n) => n, a, b)

def sumSquare(a: Int, b: Int) =
  sum((n) => n * n, a, b)

def sumCubes(a: Int, b: Int) =
  sum((n) => n * n * n, a, b)
```

여기서는 계산 종류를 정하는 함수만 달라지는데도, 각 Wrapper function에서 구간 인자 `a`, `b`를 반복해서 받아 다시 전달한다. 강의가 원하는 것은 `sum(square)`만으로 제곱을 더하는 계산을 먼저 얻고, 구간은 나중에 주는 방식이다. [STT 50:38] [STT 51:31]

그러려면 `sum`의 결과가 정수 하나여서는 안 된다. `f`만 받았을 때는 아직 범위가 없으므로 최종 합을 계산할 수 없다. 대신 나중에 `(a, b)`를 받아 합을 계산하는 함수를 반환해야 한다.

```text
한 번에 받는 방식:
(Int => Int, Int, Int) => Int

f를 먼저 받고 함수 값을 반환하는 방식:
(Int => Int) => ((Int, Int) => Int)
```

이 타입 변화는 계산을 없애는 것이 아니라 입력을 받는 단계를 나눈다. 첫 단계에서 항의 종류를 정하고, 두 번째 단계에서 실제 구간을 정한다. 반환된 함수가 먼저 받은 `f`를 계속 사용할 수 있는 이유는 앞에서 설명한 Closure다. [M01 p.56] [M01 p.57] [STT 52:27]

일반적으로 **Currying은 여러 입력을 함께 받는 함수를, 입력을 단계적으로 받으며 함수를 반환하는 형태로 바꾸는 변환**이다. 자료는 완전히 한 인자씩 받는 형태를 다음과 같이 제시한다. [M01 p.61]

```text
(T1, T2, ..., Tn) => T

        Currying
            ↓

T1 => (T2 => (... => (Tn => T) ...))
```

반대 방향의 변환은 **Uncurrying(언커링)**이다. 이미 단계적으로 받는 함수를 여러 입력을 함께 받는 형태로 바꾸는 방향이다. 강의는 이러한 변환을 반복하여 입력을 받는 단계와 묶음을 바꿀 수 있다고 설명한다. [M01 p.61] [STT 53:41] [STT 01:08:46]

`sum` 예제는 첫 인자 `f`를 분리하고, 나머지 `a`, `b`는 한 묶음으로 둔다. 따라서 Currying을 이해할 때 모든 예제가 처음부터 반드시 한 인자씩만 받는 모양이라고 생각할 필요는 없다. 일반적인 한 인자씩의 타입 변환과, 실제로 필요한 지점에서 입력 묶음을 나누는 사용 방식을 구분하면 된다.

자료는 명칭을 Haskell Brooks Curry와 연결한다. 강의의 이름 관련 일화는 손상되어 있으므로, 그 밖의 언어 이름이나 동명이인에 대한 농담을 복원하지 않는다. 명칭의 정확한 근거는 p.61이며, 타입 변환의 방향이 학습 내용의 중심이다. [M01 p.61] [STT 54:38] [STT 55:24]

[[concepts/currying|Currying]]을 단지 괄호를 여러 번 쓰는 문법으로만 이해하면 반환값의 의미를 놓친다. 각 단계가 끝났을 때 얻는 것이 최종 결과인지, 다음 입력을 기다리는 함수인지 타입으로 구별해야 한다.

### 내부의 재귀 함수 `sumF`를 반환하기

함수를 반환하는 `sum`을 만드는 직접적인 방법은 내부에 필요한 함수를 선언한 다음 그 함수 값을 반환하는 것이다. 자료에서는 내부 함수에 `sumF`라는 이름을 붙인다. [M01 p.57] [STT 56:14] [STT 57:14]

```scala
def sum(f: Int => Int): (Int, Int) => Int = {
  def sumF(a: Int, b: Int): Int =
    if (a <= b) f(a) + sumF(a + 1, b)
    else 0

  sumF
  // 자료에는 sumF _ 표기도 함께 제시된다.
}
```

바깥 `sum`과 안쪽 `sumF`의 역할을 구분하자.

| 함수 | 직접 받는 입력 | 결과 |
|---|---|---|
| `sum` | 항을 계산할 `f` | 두 정수를 받을 함수 값 |
| `sumF` | 구간의 `a`, `b` | 그 구간에서 `f`를 적용한 항들의 합 |

`sumF` 안의 재귀 호출은 `sumF(a + 1, b)`다. 바깥의 `sum`을 다시 호출하는 것이 아니라, 이미 정의된 내부 함수를 같은 계산 종류로 반복 적용한다. `f`를 재귀 호출마다 명시적으로 다시 전달하지 않는다는 점도 이전의 `sum(f, a, b)`와 다르다. [M01 p.57]

이해를 위한 예시로 다음과 같이 함수를 얻었다고 하자.

```scala
val squares = sum((n: Int) => n * n)
```

이때 `squares`는 합계 정수 하나가 아니다. 두 정수를 받아 제곱의 합을 계산할 함수다. `squares(2, 3)`을 적용하면 다음과 같이 계산한다.

```text
sumF(2, 3)
= f(2) + sumF(3, 3)
= 4 + f(3) + sumF(4, 3)
= 4 + 9 + 0
= 13
```

여기서 자연스럽게 생기는 질문은 `sumF`가 `a`, `b`만 받는데 어떻게 `f`를 아는가이다. 답은 **`f`가 사라진 것이 아니라, `sumF`의 정의 Environment 바깥에 연결되어 있기 때문**이다. 강의 후반의 질문과 추가 설명도 이 지점을 다룬다. [STT 58:45] [STT 01:00:57]

Environment의 연결을 개념적으로 따라가면 다음과 같다.

```text
나중의 sumF 호출 Environment
  a, b를 보관
       ↓ 부모
sumF가 정의된 블록 Environment
       ↓ 부모
바깥 sum 호출의 인자 Environment
  f = 전달받은 제곱 함수
```

`sumF`의 본문에서 `f`를 찾을 때 현재 인자 Environment에 없으면 부모 연결을 따라간다. 그 결과 바깥 `sum` 호출에서 받은 함수에 도달한다. 반환되는 Closure가 이 정의 관계를 보존하므로, `sum`의 계산이 끝난 뒤에도 원래 `f`를 사용할 수 있다. [STT 01:02:45] [STT 01:03:39]

이해를 위한 비교로 `sum((n: Int) => n)`에서 얻은 함수와 `sum((n: Int) => n * n)`에서 얻은 함수는 `sumF`의 코드 구조는 같아도, 연결된 `f`가 다르다. 같은 구간 `2`부터 `3`을 주면 앞의 것은 `5`, 뒤의 것은 `13`을 계산한다. 이는 코드가 같아도 Closure에 포함된 Environment 정보가 다르면 함수 값의 동작이 달라질 수 있음을 보여 준다.

따라서 `sumF`가 받는 인자가 두 개라는 사실과, 계산에 `f`까지 사용한다는 사실은 모순이 아니다. 함수가 필요로 하는 모든 정보가 매번 직접 인자로만 들어와야 하는 것은 아니다. 일부는 정의 Environment를 통해 제공된다.

이 구간의 짧은 응답과 실행을 해 보자는 발언은 논의의 맥락이다. 그것만으로 특정 화면 코드가 실제로 성공적으로 실행되었다고 판단하지 않는다. 손상된 조건식이나 미완성 반환값 설명은 자료의 코드로 교정한 발화처럼 제시하지 않는다. [STT 58:44] [STT 01:00:33] [STT 01:01:13]

### 반환된 함수의 연속 적용과 Wrapper function의 선택

함수 값을 반환한다면 그 결과에 즉시 다음 인자를 적용할 수 있다. 자료는 다음 두 표현을 비교한다. [M01 p.58]

```scala
sumSquare(3, 10) + sumCubes(5, 20)
```

```scala
sum((n) => n * n)(3, 10) +
sum((n) => n * n * n)(5, 20)
```

두 번째 표현의 첫 항을 단계별로 읽으면 다음과 같다.

1. `sum((n) => n * n)`이 제곱을 사용하는 구간 합 함수를 만든다.
2. 그 결과 함수에 `(3, 10)`을 적용한다.
3. 반환된 정수 결과를 다음 항의 결과와 더한다.

따라서 `(3, 10)`은 처음의 Anonymous function에 직접 전달되는 인자가 아니다. 그 Anonymous function은 `Int` 하나를 받는다. `(3, 10)`은 `sum`이 반환한 두 인자 함수에 적용된다. [M01 p.57] [M01 p.58] [STT 59:35]

이해를 위한 작은 예시인 다음 표현도 같은 구조다.

```scala
sum((n: Int) => n * n)(2, 3)
```

첫 번째 적용 뒤의 값은 `(Int, Int) => Int` 타입의 함수이고, 두 번째 적용 뒤의 값은 정수 `13`이다. 적용 단계마다 결과 타입을 적어 보면 긴 괄호가 무엇을 뜻하는지 분명해진다.

자주 사용하는 계산에 `sumSquare`라는 이름을 붙이는 것도 가능하고, 한 번 사용할 계산을 즉시 적용하는 것도 가능하다. 자료가 설명하는 이점은 **Wrapper function을 반드시 미리 정의할 필요가 없어진다**는 것이다. 이름을 붙이는 모든 방식이 불필요하거나 나쁘다는 뜻은 아니다. [M01 p.58]

STT에서 특정 기호를 지워도 실행된다는 설명은 화면의 삭제 대상을 확인할 수 없으므로, 이를 모든 경우의 자동 변환 규칙으로 확장하지 않는다. 연속 적용의 구조는 자료 코드로 확인하고, 기호 생략의 세부 조건은 별도로 구분한다. [STT 59:35]

### Multiple Parameter List(여러 매개변수 목록)와 자료의 변환 표기

자료는 내부 `sumF`를 직접 선언하는 대신, 함수 정의에서 인자 목록을 나누는 문법을 제시한다. 제목은 `Multiple Parameter List`이며, 예제에서는 `f`와 `(a, b)`를 서로 다른 목록에 둔다. [M01 p.59]

```scala
def sum(f: Int => Int)(a: Int, b: Int): Int =
  if (a <= b) f(a) + sum(f)(a + 1, b)
  else 0
```

재귀 호출도 정의에 맞추어 `sum(f)(a + 1, b)`라고 쓴다. 첫 목록에서는 계산 종류를, 두 번째 목록에서는 구간을 전달한다. 강의는 내부 함수와 반환을 매번 길게 적는 대신, 이런 문법으로 의도한 인자 구분을 표현할 수 있다고 설명한다. [STT 01:04:52]

그러나 자료는 두 방식이 겉으로 비슷하게 사용된다는 이유로 모든 중간 표현까지 같다고 취급하지 않는다. p.59에서는 위의 여러 목록 정의에 대해 `sum(f)`가 Parameterized expression이며, `sum(f) _`가 Closure를 만든다고 설명한다. 반면 내부 `sumF`를 값으로 반환하는 정의에서는 `sum(f)`의 결과가 이미 함수 값이다. [M01 p.59]

p.60의 비교를 표로 읽으면 다음과 같다.

| `sum`의 정의 방식 | 자료에서 `sum(f)`를 설명하는 방식 | 자료가 제시한 `sumLinear` |
|---|---|---|
| `def sum(f)(a, b): Int` | 다음 인자를 받을 Parameterized expression | `def sumLinear = sum((n) => n) _` |
| 내부 `sumF`를 반환하는 `def sum(f): (Int, Int) => Int` | 이미 반환된 Closure value | `def sumLinear = sum((n) => n)` |

자료는 각 행에서 반대쪽 `_` 사용을 잘못된 표기로 표시한다. 이 비교 도표를 읽을 때는 `_`의 유무만 외우지 말고, **그 자리에 있는 것이 아직 값으로 변환할 대상인지, 이미 반환된 함수 값인지**를 먼저 판단해야 한다. [M01 p.60]

예를 들어 내부 `sumF` 방식에서 `sum(square)`를 평가하면, `sum`의 본문이 실행되어 `sumF`의 Closure를 반환한다. 반면 자료의 여러 목록 정의는 첫 목록까지만 제시된 표현과 그 표현을 값으로 만드는 단계를 구별한다. 앞서 배운 Parameterized expression과 Closure value의 차이가 다시 등장하는 것이다.

이 설명은 **제공된 슬라이드의 Scala 표기와 구분을 해석한 것**이다. STT에는 버전에 따른 간소화가 언급되지만 정확한 버전과 자동 변환 조건은 확인되지 않는다. 따라서 p.60의 표를 모든 최신 Scala 환경의 실행 결과라고 주장하거나, 실제 컴파일러로 검증했다고 표현하지 않는다. [M01 p.53] [M01 p.60] [STT 01:05:36]

### Currying의 유연성과 함수 값을 다시 만드는 구조의 비용

인자 목록을 나누면 의미상 함께 정해지는 입력을 단계별로 제공할 수 있다. `sum`에서는 어떤 항을 더할지 먼저 정하고, 실제 구간은 나중에 정하는 방식이 자연스럽다. 강의는 이런 유연성을 설명하면서 함수 값을 만들어 반환하고 다시 적용하는 구조의 비용도 함께 언급한다. [STT 01:06:55]

p.59에는 다음 대안이 제시된다. 내부의 이름 있는 `sumF` 대신 Anonymous function을 바로 반환하는 형태다. [M01 p.59]

```scala
def sum(f: Int => Int): (Int, Int) => Int =
  (a, b) =>
    if (a <= b) f(a) + sum(f)(a + 1, b)
    else 0
```

두 방식의 차이는 재귀 호출 부분에 있다.

```text
내부 sumF 방식:
sumF(a + 1, b)

위 Anonymous function 방식:
sum(f)(a + 1, b)
```

첫 번째는 이미 내부에 정의한 `sumF`를 다시 호출한다. 두 번째는 `sum(f)`를 다시 평가하여 함수 값을 얻고, 그 결과에 `(a + 1, b)`를 적용하는 구조다. 자료가 후자를 조금 비효율적이라고 표시한 이유를 소스 수준에서 설명하면, **재귀 단계마다 함수 값을 다시 만드는 경로를 거친다**는 점을 들 수 있다. [M01 p.59]

이해를 위한 추적으로 구간에 항이 두 개 있다고 생각해 보자. 이름 있는 내부 함수는 다음 항으로 갈 때 같은 `sumF`에 새 경계만 전달한다. 위 대안은 다음 항으로 갈 때 바깥 `sum`을 통해 함수를 얻는 단계를 다시 거친다. 최종 수학적 합이 같더라도, 소스가 표현하는 중간 계산 구조는 다르다.

다만 이 차이만으로 실제 실행 시간, 메모리 사용량, 함수 객체의 물리적 생성 횟수를 확정할 수는 없다. 그러한 결과는 구체적인 구현과 최적화에 영향을 받을 수 있으며, 이번 소스에는 별도의 측정 결과가 없다. 강의 중 직접 여러 인자를 받는 방식의 비용에 관한 설명도 특정 컴파일러의 생성 코드를 검증한 증거로 취급하지 않는다. [STT 01:06:55] [STT 01:07:46]

강의에서 확인되는 사용 지침은 **실제로 중간 단계의 함수를 꺼내 쓸 의도가 있는 지점에서 인자 목록을 나누라**는 것이다. Currying을 지원한다는 이유만으로 모든 인자를 무조건 잘게 나누는 것이 목표는 아니다. 어떤 정보를 먼저 정하고 어떤 정보를 나중에 받을지라는 사용 목적이 우선한다. [STT 01:07:46]

### Anonymous function으로 일부 인자를 고정하고 묶음 바꾸기

Anonymous function은 새로운 계산을 처음부터 만드는 데뿐 아니라, 이미 있는 함수에 전달할 인자의 일부를 고정하거나 남은 입력의 묶음을 바꾸는 데도 사용할 수 있다. 강의의 마지막 구체 예제에서는 다섯 입력 중 `y = 1`, `a = 2`를 고정하고 `x`, `z`, `b`만 나중에 받는다. [M01 p.62] [STT 01:09:42] [STT 01:10:30]

원래 함수는 다음과 같다.

```scala
def foo(x: Int, y: Int, z: Int)(a: Int, b: Int) =
  x + y + z + a + b
```

자료의 첫 번째 표현은 남은 세 인자를 한 번에 받는다.

```scala
val f1 =
  (x: Int, z: Int, b: Int) => foo(x, 1, z)(2, b)
```

이제 `f1`의 사용자는 `y`와 `a`를 전달하지 않는다. Anonymous function의 본문이 그 자리에 각각 `1`, `2`를 넣기 때문이다. 고정되지 않은 세 값만 왼쪽의 인자 목록에 남는다. [M01 p.62]

자료의 두 번째 표현은 남은 자리를 `_`로 표시한다.

```scala
val f2 =
  foo(_: Int, 1, _: Int)(2, _: Int)
```

이 표기는 p.62에서 `f1`과 함께 제시되는 대안이다. `_`가 원래 함수에 있던 모든 인자를 뜻하는 것은 아니다. 여기서는 고정하지 않은 `x`, `z`, `b`의 자리에만 나타난다. 자료의 문법 설명으로 읽으며, 별도 환경에서 실행을 확인한 것으로 취급하지 않는다.

세 번째 표현은 남은 인자도 두 단계로 나눈다.

```scala
val f3 =
  (x: Int, z: Int) =>
    ((b: Int) => foo(x, 1, z)(2, b))
```

`f3`는 먼저 `x`, `z`를 받고, 그 값을 보존하면서 `b`를 받을 함수를 반환한다. 이때 안쪽 Anonymous function이 먼저 받은 `x`, `z`를 나중에도 사용할 수 있다는 점에서 다시 Closure가 필요하다. [M01 p.62]

| 표현 | 남은 입력을 받는 방식 | 자료의 적용 예 |
|---|---|---|
| `f1` | `x`, `z`, `b`를 한 번에 받음 | `f1(1, 2, 3)` |
| `f2` | 자료의 생략 표기로 같은 세 입력을 받음 | `f2(1, 2, 3)` |
| `f3` | `x`, `z`를 먼저 받고 나중에 `b`를 받음 | `f3(1, 2)(3)` |

자료의 적용 예를 대입하여 계산하면 세 경우 모두 다음 원래 함수 호출로 연결된다.

```text
foo(1, 1, 2)(2, 3)
= 1 + 1 + 2 + 2 + 3
= 9
```

결과가 같다는 사실과 입력을 받는 방식이 같다는 사실은 구분해야 한다. `f1`은 세 인자를 함께 받지만, `f3(1, 2)`는 아직 정수 `9`가 아니라 마지막 입력 `b`를 기다리는 함수다. [M01 p.62]

일부 입력을 구체적인 값으로 정해 남은 입력의 함수를 얻는 것과, 입력을 받는 단계를 나누는 Currying도 구분할 필요가 있다. 이 예제에서 `y = 1`, `a = 2`를 넣는 것은 일부 값을 고정하는 동작이고, `f3`가 `(x, z)`와 `b`를 나누어 받는 것은 적용 단계를 구성하는 동작이다.

인자 순서를 바꾸는 것도 같은 원리다. **이해를 위한 예시**로 `b`를 먼저 적고 싶다면 다음처럼 새 함수의 입력 순서와 원래 함수에 전달하는 위치를 분리할 수 있다.

```scala
val reordered =
  (b: Int, x: Int, z: Int) => foo(x, 1, z)(2, b)
```

이 새 함수는 `(b, x, z)` 순서로 입력을 받지만, 본문에서는 `foo`가 요구하는 자리에 각 값을 넣는다. Anonymous function을 사용한다고 원래 `foo`의 인자 순서가 바뀌는 것이 아니라, 새 함수가 입력과 원래 호출 사이를 연결한다. 이러한 재배치와 Currying 형태의 조정이 마지막 발화에서 확인되는 활용 방향이다. [STT 01:12:37]

### Anonymous function의 직접 재귀 제약과 내부 `def`를 통한 해결

Anonymous function의 본문에는 블록을 사용할 수 있다. 따라서 식이 길어지거나 내부 선언이 필요하다는 이유만으로 Anonymous function을 사용할 수 없다고 생각하면 안 된다. 강의의 마지막 질문은 그보다 구체적으로, **이름이 없는 문법에서 자기 자신을 어떤 이름으로 다시 부를 수 있는가**를 묻는다. [STT 01:11:14] [STT 01:12:09]

이름 있는 재귀 함수는 자신의 이름으로 다시 호출한다. 반면 `(x: T) => e`라는 표면 문법에는 그 함수 자신에게 붙여진 이름이 직접 들어 있지 않다. 이 제약을 모든 재귀 함수 값을 만들 수 없다는 주장으로 확대하면 안 된다. 자료는 내부에 이름 있는 함수를 선언하고 그 값을 반환하는 방법을 함께 설명한다. [M01 p.53]

자료는 Anonymous function을 **Syntactic sugar(기존 구조를 간결하게 나타내는 문법)**로 설명하면서 다음 대응을 제시한다.

```scala
(x: T) => e
```

```scala
{
  def noname(x: T) = e
  noname _
}
```

이 대응에는 **`e`가 `noname`을 사용하지 않는다**는 조건이 붙는다. 원래의 이름 없는 표현에 없던 자기 이름을, 설명을 위해 도입한 `noname`을 통해 몰래 추가하지 않으려는 조건이다. [M01 p.53]

한편 내부 `def`를 의도적으로 재귀 함수로 작성하고 그 값을 반환하는 구성은 가능하다. 다음은 자료의 구성 방법을 이해하기 위한 작은 예시다.

```scala
val steps: Int => Int = {
  def countDown(n: Int): Int =
    if (n <= 0) 0
    else 1 + countDown(n - 1)

  countDown _
}
```

`countDown`은 이름이 있으므로 본문에서 자신을 다시 부를 수 있다. 블록 밖에서는 그 함수 값을 `steps`로 사용한다. 예를 들어 `steps(3)`을 계산하면 `1 + 1 + 1 + 0 = 3`이 된다. 이는 새로운 이해용 예시이며, 현재 과제의 완성된 풀이가 아니다.

앞서 배운 내부 `sumF`도 같은 구분을 보여 준다. 바깥으로 반환되는 것은 함수 값이지만, 그 함수의 재귀는 내부의 이름 있는 선언을 통해 구성된다. **함수 값을 반환한다는 사실과, 구현에 이름 있는 내부 함수를 쓴다는 사실은 함께 성립한다.** [M01 p.53] [M01 p.57]

따라서 이번 내용에서 구분해야 할 것은 직접 자기 이름이 없는 Anonymous function 문법, 이름 있는 내부 재귀 함수, 그리고 그 함수를 Environment와 함께 반환한 Closure value다. 교수는 이름이 없어 syntax상 자신을 부를 방법이 없다고 설명한 직후 “이거는 재귀함수를 허용하거든요.”라고 말한 것으로 STT에 기록되어 있다. 이 문장의 지시 대상·부정 누락 여부와 앞뒤 연결은 미확정이므로, ‘허용’을 ‘불허’로 고치거나 Anonymous function의 재귀 허용 여부를 확정하는 근거로 삼지 않는다. 명확한 제약과 구성 가능성은 p.53의 설명에 근거한다. [M01 p.53] [STT 01:12:09]

마지막 제공 발화는 인자 순서와 Currying 형태를 바꾸는 활용을 언급하다 불완전하게 끝난다. 그 뒤의 설명이나 새로운 주제를 이어 쓰지 않는다. 시작 전 구간과 마지막 세그먼트 이후의 정확한 발화 여부도 오디오 대조로 확인된 상태가 아니므로 **검증 필요**로 남긴다. 이번 본문에서 다룬 자료 범위는 p.44–62이며, 이후 페이지의 주제를 실제로 배운 내용으로 덧붙이지 않는다. [STT 01:12:37]

## 강의 흐름과 연결

### Higher-order function에서 Closure와 Currying으로

강의의 출발점은 비슷한 합 계산을 여러 번 작성하는 문제다. 현재 항을 계산하는 방법을 함수로 전달하고, 이어서 결합 연산과 종료값까지 분리하면서 재사용의 범위를 넓힌다. 이 과정에서 Anonymous function은 필요한 계산을 사용 위치에서 표현하는 도구가 된다. [M01 p.46] [M01 p.47] [M01 p.48] [M01 p.50]

그다음 질문은 함수 값이 다른 위치로 전달되거나 반환되어도 의미를 유지할 수 있는가이다. Closure는 함수 코드와 정의 Environment를 함께 보존한다. 이후에도 사용할 수 있는 Closure가 참조하는 Environment를 Garbage collector가 유지하므로, 정의한 블록이 끝난 뒤에도 그 함수 값을 호출할 수 있다. 이 연결이 함수를 인자로 받거나 반환하는 고차 함수의 동작을 지원한다. [M01 p.51] [M01 p.52] [STT 41:04] [STT 42:00] 식과 Environment를 함께 보존하는 원리는 Call-by-name의 인자 식에도 적용되지만, 함수 본문과 인자 식이 사용하는 Environment를 구별해야 한다. [M01 p.53] [M01 p.54]

마지막에는 이 기반을 이용해 일부 입력을 먼저 받고, 나머지 입력을 기다리는 함수를 반환한다. Currying, 내부 `sumF`, Multiple Parameter List, Anonymous function을 이용한 인자 고정은 모두 **어떤 정보를 먼저 정하고 무엇을 나중에 받을 것인가**라는 질문으로 연결된다. [M01 p.56] [M01 p.57] [M01 p.59] [M01 p.62]

이전 회차는 [[courses/principles_of_programming/lectures/2026-09-15-lecture-04|9월 15일 강의 노트]]에서 이어 볼 수 있다. 이번 내용을 복습하기 전에는 블록의 결과값, 함수의 인자와 반환값, Environment에서 이름을 찾는 방법, 재귀의 종료 조건을 먼저 점검한다. 이는 이번 본문을 이해하기 위한 선수 개념이며, 이전 회차의 세부 진도를 새로 확정하는 표시는 아니다.

### 개념 연결 지도

- [[concepts/higher-order-functions|Higher-order function]] → 달라지는 항을 함수로 전달 → [[concepts/anonymous-functions|Anonymous function]]으로 호출 위치에서 표현 → [[concepts/map-reduce|mapReduce]]에서 결합 연산과 종료값까지 분리한다.
- [[concepts/environment-model|Environment model]] → 코드만 이동시키면 이름의 의미가 달라지는 문제 → [[concepts/closures|Closure]]로 정의 Environment를 보존한다.
- [[concepts/closures|Closure]] → [[concepts/call-by-name|Call-by-name]]의 인자 식에도 호출 위치의 Environment를 붙인다. 함수 본문의 정의 Environment와는 구별한다.
- [[concepts/closures|Closure]] → 먼저 받은 `f`를 나중에도 사용하는 내부 `sumF` → [[concepts/currying|Currying]]과 반환된 함수의 연속 적용으로 연결된다.
- [[concepts/anonymous-functions|Anonymous function]] → 일부 인자 고정·순서 변경·묶음 변경에 활용한다. 직접 자기 이름이 없는 문법의 제약은 내부의 이름 있는 재귀 함수로 함수 값을 만드는 방법과 구별한다.

## 핵심 요약

- **Higher-order function(고차 함수)**은 함수를 인자로 받거나 반환한다. 함수 값을 전달하는 것과 그 함수를 특정 입력에 적용한 결과를 전달하는 것은 다르다. [M01 p.45]
- **DRY**의 적용 순서는 공통 재귀 구조를 남기고, 달라지는 항을 `f`로 추출한 뒤, 결합 연산과 종료값까지 분리하는 것이다. `sum(f, n)`은 `n <= 0`에서 종료하므로 일반적인 `f(0)`을 포함하지 않는다. [M01 p.47] [M01 p.50]
- **Anonymous function(익명 함수)**은 함수 값을 사용하는 자리에서 표현한다. 타입 생략은 타입의 부재가 아니며, 명시적 타입의 가독성 이점과 문맥에 따른 추론 가능성을 구별한다. [M01 p.48] [STT 15:42]
- 구간 `sum`과 `product`는 양 끝을 포함한다. 빈 구간의 결과는 각각 `0`, `1`이며, `mapReduce`에서는 이를 `reduce`와 `inival`의 조합으로 표현한다. [M01 p.49] [M01 p.50]
- **Closure(클로저)**는 코드와 정의 Environment를 함께 보존한다. 함수 값을 현재 저장한 위치가 이름 탐색의 기준이 되는 것은 아니다. 이후에도 사용할 수 있는 Closure가 참조하는 Environment를 GC가 유지하므로, 블록이 끝난 뒤에도 함수를 전달·반환해 사용할 수 있다. [M01 p.52] [STT 41:04] [STT 42:00]
- **Call-by-name(이름에 의한 호출)**에서는 본문과 인자 식의 Environment를 따로 추적한다. p.54의 결과는 `0 + 10 × 10 = 100`이다. [M01 p.54]
- **Currying(커링)**은 입력을 받는 단계를 나누어 함수를 반환하도록 바꾸며, **Uncurrying(언커링)**은 반대 방향이다. 내부 `sumF`가 먼저 받은 `f`를 사용하는 근거는 Closure다. [M01 p.57] [M01 p.61]
- Multiple Parameter List의 중간 표현과 이미 반환된 Closure value를 구별한다. 인자 고정·재배치에는 Anonymous function을 사용할 수 있고, 이름 있는 내부 `def`를 통해 재귀하는 함수 값도 구성할 수 있다. `_` 표기는 자료의 Scala 문맥에 한정해 읽는다. [M01 p.53] [M01 p.59] [M01 p.60] [M01 p.62]

## 회상·연습문제

### 능동회상: 정의와 평가 근거 설명하기

#### Q01. Higher-order function의 기준은 무엇인가? — LO01

함수 안에서 다른 함수를 호출하기만 하면 Higher-order function인가? Function value로 가능한 작업도 함께 설명하라.

<details><summary>정답</summary>

함수를 인자로 받거나 함수 값을 반환해야 한다. 단지 본문에서 다른 함수를 호출한다는 사실만으로는 충분하지 않다. Function value는 복사하고, 인자로 전달하고, 결과로 반환할 수 있다. [M01 p.45]

</details>

#### Q02. 세 합 함수의 공통 구조는 무엇인가? — LO02

`sumLinear`, `sumSquare`, `sumCubes`에서 같은 부분과 다른 부분을 구분하라. 실시간 편집 중 짧은 응답은 실행 성공의 근거인가?

<details><summary>정답</summary>

`n <= 0`에서 `0`을 반환하고, `n - 1`로 재귀 호출한 결과에 현재 항을 더하는 구조가 같다. 다른 부분은 현재 항 `n`, `n * n`, `n * n * n`이다. 편집 명령·화면·실행 결과가 확인되지 않은 구간의 짧은 응답만으로 성공을 확정할 수 없다. [M01 p.46] [STT 03:37] [STT 05:24] [STT 06:23]

</details>

#### Q03. 왜 `f`는 정수가 아니라 `Int => Int`인가? — LO03

또한 p.47의 `sum(f, n)`이 항상 `f(0)`을 포함하는지 설명하라.

<details><summary>정답</summary>

현재 `n`에 따라 다른 항을 만들어야 하므로, 정수 입력을 받아 정수 항을 반환하는 함수가 필요하다. 종료 조건이 `n <= 0`이므로 `f(0)`은 적용하지 않는다. 원래 세 함수가 0에서 0을 낸다는 사실을 임의의 `f`까지 일반화하면 안 된다. [M01 p.47]

</details>

#### Q04. Anonymous function은 언제 계산되는가? — LO04

`(x: Int) => x * x`를 작성한 순간 특정 정수의 제곱이 계산되는가?

<details><summary>정답</summary>

그 표현은 입력을 받으면 제곱을 계산할 함수 값을 만든다. 특정 입력에 대한 결과는 그 함수를 실제 입력에 적용할 때 얻는다. 함수 이름을 먼저 선언하지 않아도 함수 값을 표현할 수 있다는 점이 핵심이다. [M01 p.48]

</details>

#### Q05. 타입을 명시하는 이유와 IDE에 관한 단서는 무엇인가? — LO05

<details><summary>정답</summary>

명시적 타입은 독자가 본문을 분석하여 타입을 추론하는 수고를 줄인다. 강의는 IDE가 타입을 표시하면 이 이점을 일부 보완할 수 있다고 한정한다. p.48에는 생략형도 있으므로, 손상된 STT를 근거로 모든 Scala 함수 인자에 타입을 반드시 적어야 한다고 단정하지 않는다. [STT 15:42] [STT 16:23] [STT 17:05] [M01 p.48]

</details>

#### Q06. 구간 `sum`과 `product`의 빈 구간 결과는 무엇인가? — LO06

`a = b`인 경우도 함께 설명하라.

<details><summary>정답</summary>

`a > b`이면 `sum`은 `0`, `product`는 `1`을 반환한다. `a = b`이면 그 위치의 `f(a)`를 한 번 처리하고 다음 호출에서 종료한다. 따라서 구간의 양 끝을 포함한다. [M01 p.49]

</details>

#### Q07. `mapReduce`의 세 계산 인자는 무엇인가? — LO07

<details><summary>정답</summary>

`f: Int => Int`는 현재 항을 만든다. `reduce: (Int, Int) => Int`는 현재 항과 나머지 구간의 결과를 결합한다. `inival: Int`는 빈 구간의 결과다. 합에는 덧셈과 `0`, 곱에는 곱셈과 `1`을 사용한다. [M01 p.50]

</details>

#### Q08. MapReduce의 동기로 든 강의 사례는 무엇인가? — LO08

#### Q09. 서버별 map과 reduce의 순서 및 한계는 무엇인가? — LO09

<details><summary>정답</summary>

코드만 `f`로 옮겨 정의 Environment를 잃었기 때문이다. 잘못된 모델은 호출의 인자 Environment를 바깥 Environment에 연결하여 `x = 20`, `t = 0`으로 계산한다. 이는 올바른 Closure 평가 결과가 아니다. [M01 p.51]

#### Q13. 블록 종료와 Environment의 수명이 다른 이유는 무엇인가? — LO13

#### Q14. Parameterized expression과 Closure value는 어떻게 다른가? — LO14

p.51–52의 `val f`를 괄호 없는 `def f`로 바꾸면 `f(20)`은 `20`이 되는가?

<details><summary>정답</summary>

자료는 `def`로 정의한 계산을 Parameterized expression으로, Environment와 함께 다루는 함수 값을 Closure value로 구별한다. `f _`는 자료의 함수 값 변환 표기다.

해당 예제의 `val f`는 초기화 때 블록 결과를 저장하고, 괄호 없는 `def f`는 사용할 때 블록을 다시 평가한다. 반환된 `g`는 어느 경우에도 내부 `t = 10`을 보존하므로 `f(20)`은 둘 다 `30`이다. 이는 자료의 질문에 대한 코드 분석이며, 실행 확인이나 할당 횟수에 대한 주장은 아니다. [M01 p.51] [M01 p.52] [M01 p.53]

</details>

#### Q15. Call-by-name에서 본문의 `t`와 인자 식의 `t`는 어디에서 찾는가? — LO15

<details><summary>정답</summary>

p.54의 본문 `t + x`에서 `t`는 함수 정의 Environment의 `0`이다. 인자 식 `t * t`는 호출 Environment에서 계산하므로 각 `t`는 `10`이다. 따라서 결과는 `0 + 100 = 100`이다. 인자 식에는 그 호출 Environment를 함께 보존해야 한다. [M01 p.54]

</details>

#### Q16. Currying 도입에서 `sum(linear)`로 얻고 싶었던 것은 무엇인가? — LO16

<details><summary>정답</summary>

나중에 두 구간 인자 `a`, `b`를 받아 linear 항의 합을 계산할 함수 값이다. 아직 구간이 없으므로 최종 정수 합이 아니다. 종류별 Wrapper function마다 `a`, `b`를 반복해서 받아 전달하는 코드를 줄이려는 동기다. [M01 p.56]

</details>

#### Q17. Currying과 Uncurrying의 타입 변환 방향은 무엇인가? — LO17

<details><summary>정답</summary>

Currying은 `(T1, T2, ..., Tn) => T`를 `T1 => (T2 => (... => (Tn => T)))`처럼 단계적으로 입력을 받는 형태로 바꾼다. Uncurrying은 반대 방향이다. 자료는 명칭을 Haskell Brooks Curry와 연결하지만, 손상된 강의 일화의 다른 인명이나 언어 관련 내용을 추정하지 않는다. [M01 p.61]

</details>

#### Q18. 바깥 `sum`과 내부 `sumF`는 각각 무엇을 받는가? — LO18

<details><summary>정답</summary>

바깥 `sum`은 `f: Int => Int`를 받고 함수 값을 반환한다. 내부 `sumF`는 `a`, `b`를 받아 정수 합을 계산하며, 다음 항으로 이동할 때 `sumF(a + 1, b)`로 자신을 호출한다. [M01 p.57]

</details>

#### Q19. `sumF`는 두 인자만 받는데 어떻게 `f`를 사용하는가? — LO19

<details><summary>정답</summary>


4. **새 변형:** 바깥과 안쪽의 값을 바꾸거나 입력 묶음을 달리해 본다. 결과만 맞히는 데서 끝내지 말고, 바뀐 값·그대로인 정의 Environment·다음에 받을 입력을 설명한다.
