## 수업 직후 10분 복습

이번 수업의 중심 질문은 **같은 코드를 반복해서 사용하면서 어떻게 다른 데이터에 대한 계산을 진행하는가**이다. [[concepts/명령형-프로그래밍|Imperative Programming(명령형 프로그래밍)]]은 memory(메모리) state(상태)를 갱신하면서, [[concepts/함수형-프로그래밍|Functional Programming(함수형 프로그래밍)]]은 function(함수)에 전달하는 argument(인자)를 바꾸면서 이 문제를 해결한다. 후반부에서는 functional 계산을 name(이름) 펼치기, function 본문 substitution(치환), 조건 선택이라는 규칙으로 설명했다. [STT 05:44] [STT 06:44] [STT 54:12] [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

복습할 때는 다음 여덟 가지를 먼저 자신의 말로 설명해 보자.

1. **과목의 네 부분은 두 개의 비교 축으로 나뉜다.** imperative와 functional은 계산을 표현하고 진행하는 방식의 비교이고, [[concepts/객체지향-프로그래밍|Object-Oriented Programming(객체지향 프로그래밍)]]과 [[concepts/타입-클래스|type class(타입 클래스)]]는 큰 프로그램을 추상화하고 코드를 재사용하는 방식의 비교이다. 네 가지를 모두 같은 종류의 경쟁 관계로 놓으면 과목의 구조를 잘못 이해하게 된다. [STT 01:23] [STT 17:22] [M01 p.5](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-005) [M01 p.8](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-008)

2. **imperative 반복에서는 state가, functional 반복에서는 argument가 달라진다.** 합산 [[concepts/반복문|loop(반복문)]]는 `sum`과 `i`의 저장 내용을 바꾼다. recursion(재귀)을 사용한 합산은 같은 function 본문에 `n`, `n-1`, 그다음 더 작은 value(값)를 전달한다. [STT 09:09] [STT 10:08] [STT 59:47] [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

3. **functional 코드는 수학적 정의처럼 보이면서도 실행 가능하다.** `sum(n)`을 `n <= 0`이면 `0`, `n > 0`이면 `n + sum(n-1)`로 정의하는 것은 계산 결과 사이의 관계를 나타내며, function application(함수 적용)과 conditional expression(조건식)의 evaluation(평가) 규칙을 통해 실제 결과를 얻는다. [STT 11:08] [STT 11:51] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

4. **두 계산 방식의 원리를 모두 알아야 목적에 맞게 선택하고 혼합할 수 있다.** 교수는 특히 AI가 작성한 코드의 방식을 이해하고 필요한 방향을 제시하려면 두 방식을 모두 배워야 한다고 강조했다. [STT 13:43] [STT 14:41] [M01 p.7](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-007)

5. **abstraction(추상화)과 code reuse(코드 재사용)는 서로 관련되지만 다른 목표다.** [[concepts/추상화|abstraction]]은 구현의 세부 사항을 모두 읽지 않고도 어떤 일을 하는 단위인지 이해하게 한다. [[concepts/코드-재사용|code reuse]]는 비슷한 코드를 계속 복사하지 않고 공통 부분을 다시 활용하게 한다. [STT 18:18] [STT 19:11] [STT 20:05] [M01 p.8](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-008)

6. **Scala와 Rust는 서로 다른 학습 목적을 위해 선택되었다.** Scala는 여러 계산·abstraction 방식을 함께 다루기 위한 언어이고, Rust 부분의 중심 학습 대상은 [[concepts/소유권-타입|ownership type(소유권 타입)]]을 통한 안전한 저수준 프로그래밍이다. [STT 25:16] [STT 26:15] [M01 p.9](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-009)

7. **value는 expression(식)에 포함된다.** `3`은 이미 계산이 끝난 value인 동시에 expression이고, `3 + 4`는 계산이 남아 있는 expression이다. [[concepts/평가|evaluation]]은 이러한 expression에 규칙을 적용해 계산을 진행하는 과정이며, 종료하는 경우 결과 value에 도달한다. [STT 31:07] [STT 32:05] [STT 33:05] [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012) [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013)

8. **type(타입)이 맞는 expression도 끝나지 않을 수 있다.** `sum(2)`는 기저 조건에 도달하여 `3`이 되지만, `def loop: Int = loop`의 `loop`는 펼칠 때마다 다시 자신이 된다. [[concepts/타입|type]]과 [[concepts/종료와-발산|termination(종료) 여부]]는 구분해서 판단해야 한다. [STT 01:04:33] [STT 01:06:44] [STT 01:07:05] [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

10분 동안은 앞의 항목을 읽는 데만 시간을 쓰지 말고, 마지막 3분에 `5 + b`와 `sum(2)`의 evaluation 과정을 종이에 직접 써 보자. 결과를 기억하는 것보다 **다음 단계에서 어느 부분식을 왜 바꾸는지** 설명하는 것이 이번 회차의 학습 목표에 가깝다. [STT 40:02] [STT 56:59]

## 이전 강의와의 연결

제공된 소스에는 이전 강의의 독립적인 기록이 없다. 따라서 이전 시간에 어떤 개념을 어디까지 배웠는지, 어떤 과제가 제시되었는지는 **검증 필요**이다. 이번 수업에서 과목 구성을 소개한다는 사실만으로 이전 강의의 내용을 복원하지 않는다.

확인할 수 있는 연결은 과목 전체의 구성과 이번 회차 내부의 전개이다. 자료는 Functional Programming, Object-Oriented Programming, Type Class (Type-Oriented) Programming(타입 클래스 프로그래밍), Imperative Programming의 순서로 네 부분을 배치한다. 이번 회차는 이 전체 지도를 소개한 다음, function application을 중심으로 하는 Part 1에 들어간다. [M01 p.5](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-005) [M01 p.10](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-010)

교수는 학생들이 C 계열의 대입문과 loop에 익숙하다는 전제로 imperative 합산 코드를 설명했다. 이것은 **강의에서 활용한 선행 경험의 전제**이며, 이전 강의에서 해당 내용을 가르쳤다는 증거는 아니다. [STT 09:09] [STT 10:08] [STT 26:15]

이번 회차의 학습 연결은 다음과 같다.

- 익숙한 loop의 state 변화에서 출발해, [[concepts/함수형-프로그래밍|functional 계산]]에서 argument가 수행하는 역할을 비교한다. [STT 05:44] [STT 06:44]
- [[concepts/값과-식|value와 expression]]을 구별한 뒤, [[concepts/이름-바인딩|name binding(이름 바인딩)]]으로 expression을 재사용한다. [STT 31:07] [STT 34:00] [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012)
- expression을 실행하는 [[concepts/평가|evaluation 규칙]]을 배우고, 이를 [[concepts/함수-적용|function application]]과 [[concepts/치환|substitution]]으로 확장한다. [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013) [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)
- 같은 규칙을 [[concepts/재귀|recursion]]에 적용한 뒤, 결과에 도달하는 경우와 [[concepts/종료와-발산|divergence가 일어나는 경우]]를 비교한다. [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015) [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

자료의 11페이지가 value·name·function·evaluation을 함께 묶는 이유도 이 연결에서 이해할 수 있다. 각각을 따로 외우는 대신, **function 본문이라는 expression이 name과 argument를 이용해 구성되고 평가된다**는 하나의 흐름으로 읽어야 한다. [M01 p.11](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-011)

## 핵심 개념

### 1. 계산 방식: imperative와 functional

**정의 →** [[concepts/명령형-프로그래밍|Imperative Programming]]은 state를 읽고 바꾸는 연산의 순서로 계산을 기술하고, [[concepts/함수형-프로그래밍|Functional Programming]]은 function application과 그 조합으로 계산을 기술한다.

**강의 설명 →** 교수는 이전 계산의 정보가 다음 계산으로 전달되는 통로를 비교했다. loop에서는 memory 내용이 달라지고, function에서는 argument로 받는 value가 달라진다.

**자료 근거 →** 자료는 memory 읽기·쓰기와 function application, loop와 recursion, procedural(절차적) 표현과 declarative(선언적) 표현을 대응시킨다. [STT 05:44] [STT 06:44] [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

**예시 →** 합산 loop는 `sum = sum + i`로 누적 상태를 갱신한다. recursion을 사용한 합산은 `n + sum(n-1)`로 현재 문제와 더 작은 문제의 관계를 표현한다.

**오개념 →** functional 프로그램을 실행하는 컴퓨터에 물리적 memory가 없다는 뜻이 아니다. 이번 비교의 초점은 프로그램의 계산 의미를 설명할 때 변경 가능한 memory state를 기본 요소로 삼는지에 있다.

### 2. abstraction과 code reuse

**정의 →** [[concepts/추상화|abstraction]]은 세부 구현을 하나의 역할을 가진 단위로 이해하게 하는 것이고, [[concepts/코드-재사용|code reuse]]는 이미 작성한 공통 계산을 여러 상황에 활용하는 것이다.

**강의 설명 →** 큰 프로그램을 모든 줄의 세부 사항까지 동시에 이해하기는 어렵다. 기능을 묶고, 묶인 단위 사이의 관계를 이해해야 전체 구조를 파악할 수 있다. 비슷한 구현을 복사하는 대신 일반화하고 입력을 달리하는 것도 같은 맥락에서 소개된다.

**자료 근거 →** Object-Oriented Programming과 type class의 공통 목표는 큰 소프트웨어의 모듈 구성, 코드 abstraction, code reuse다. [STT 18:18] [STT 19:11] [STT 20:05] [M01 p.8](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-008)

**예시 →** `sum(10)`과 `sum(100)`은 입력마다 새 합산 코드를 작성하지 않고 같은 function 정의를 사용한다. function 수준에서 code reuse의 동기를 확인할 수 있는 수업 예시이다.

**오개념 →** Object-Oriented Programming을 사용하면 반드시 imperative로, type class를 사용하면 반드시 functional으로만 계산해야 한다는 분류는 이번 강의의 두 축 구분과 맞지 않는다.

### 3. type, value, expression

**정의 →** 이번 도입에서 [[concepts/타입|type]]은 value들의 집합으로 설명한다. [[concepts/값과-식|value]]는 계산이 끝난 결과이고, expression은 value를 포함하여 계산을 표현하는 구조이다.

**강의 설명 →** `3`과 `3 + 4`의 차이는 숫자가 들어 있는지 여부가 아니라 계산이 남아 있는지 여부이다. `3`은 그대로 결과이고, `3 + 4`는 덧셈을 수행해야 결과가 나온다.

**자료 근거 →** `Int`, `Double`, `Boolean`의 예와 value·name·primitive operation을 조합한 expression이 제시된다. value 자체도 expression이라는 점은 STT에서 명시된다. [STT 29:54] [STT 31:07] [STT 32:05] [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012)

**예시 →** `3 + 4`는 evaluation을 통해 value `7`이 된다. `true`와 `false`는 `Boolean`에 속하는 value이다.

**오개념 →** value와 expression은 서로 겹치지 않는 두 집합이 아니다. 또한 expression이라는 이유만으로 반드시 결과 value에 도달하는 것도 아니다. 후반부의 divergence 예시가 그 한계를 보여 준다.

### 4. name binding

**정의 →** [[concepts/이름-바인딩|name binding]]은 name이 어떤 expression을 가리키는지 정하는 것이다.

**강의 설명 →** 처음에는 긴 expression을 짧은 name으로 반복해서 사용할 수 있다는 편의가 강조된다. function에 이르면 name은 아직 주어지지 않은 입력을 표현하는 장치로 역할이 확장된다.

**자료 근거 →** `a`와 `b`의 정의는 expression에 name을 붙이는 예이고, `f`의 parameter `x`는 미래의 입력을 표현하는 예이다. [STT 34:00] [STT 50:27] [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012) [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

**예시 →** `def a = 1 + (2 + 3)`에서 `a`를 평가하면 정의된 expression을 펼쳐 계산한다.

**오개념 →** 이번 `def` 예시의 name을 곧바로 value를 덮어쓰는 memory 칸으로 해석하면 안 된다. 자료에서 설명하는 연결 대상은 expression이다.

### 5. evaluation과 expression의 구조

**정의 →** [[concepts/평가|evaluation]]은 expression의 구조에 따라 규칙을 적용하면서 계산을 진행하는 과정이다. [[concepts/추상-구문-트리|AST]]는 expression이 어떤 부분식들로 구성되는지 나타내는 나무 구조이다.

**강의 설명 →** 현재 expression의 맨 위가 value인지, name인지, 연산자인지 확인한다. name이면 정의로 바꾸고, 연산자이면 operand를 왼쪽부터 value로 만든 뒤 연산한다.

**자료 근거 →** 바깥에서 안쪽으로 구조를 확인하고 operand는 왼쪽에서 오른쪽으로 평가한다는 규칙과 `5 + b` 예시가 제시된다. [STT 38:01] [STT 40:02] [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013)

**예시 →** `5 + b`에서 왼쪽 `5`는 이미 value이다. 따라서 오른쪽 `b`의 정의를 펼쳐 `27`로 만든 뒤 마지막 덧셈을 수행한다.

**오개념 →** 가장 바깥 연산자를 먼저 확인한다는 말은 그 연산의 결과를 가장 먼저 계산한다는 뜻이 아니다. 바깥 덧셈을 완료하려면 필요한 안쪽 계산이 먼저 끝나야 한다.

### 6. conditional expression

**정의 →** [[concepts/조건식|conditional expression]]은 조건의 참·거짓에 따라 두 expression 중 하나를 선택하여 평가하는 expression이다.

**강의 설명 →** 조건을 먼저 평가하고, 참이면 참인 경우의 가지를, 거짓이면 거짓인 경우의 가지를 평가한다.

**자료 근거 →** function application을 설명하기 직전에 conditional expression의 규칙을 소개하며, 이후 recursion을 사용한 합산에서 실제로 사용한다. [STT 46:26] [STT 57:49] [STT 01:00:48] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

**예시 →** `sum(0)`의 조건 `0 <= 0`은 참이므로 결과는 `0`이다. 선택되지 않은 자기 호출 쪽을 계산할 필요가 없다.

**오개념 →** conditional expression을 일반 덧셈처럼 모든 구성 요소를 먼저 계산하는 연산으로 다루면 안 된다. 가지를 선택하는 규칙 자체가 계산의 일부이다.

### 7. function application과 substitution

**정의 →** [[concepts/함수-적용|function application]]은 function에 argument를 주어 계산을 수행하는 것이고, [[concepts/치환|substitution]]은 function 본문에서 parameter가 나타내던 자리를 실제 argument value로 바꾸는 것이다.

**강의 설명 →** 이번 회차에서 사용하는 규칙은 argument expression을 먼저 value로 평가한 다음, function application을 본문으로 바꾸고 parameter를 그 value로 대체하는 것이다.

**자료 근거 →** `def f(x: Int): Int = x + a`와 중첩된 function application의 전개가 제시된다. [STT 48:47] [STT 54:12] [STT 55:06] [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

**예시 →** `f(10)`은 `x + a`에서 `x`를 `10`으로 바꾼 `10 + a`가 되고, `a`를 평가하여 `16`이 된다.

**오개념 →** parameter와 argument를 혼동하지 말자. `x`는 function 정의 안의 parameter name이고, `10`은 이 호출에서 전달된 argument value이다. 본문의 별도 name `a`까지 `10`으로 바꾸는 것은 잘못된 substitution이다.

### 8. recursion

**정의 →** [[concepts/재귀|recursion]]은 어떤 대상을 정의할 때 그 대상 자신을 사용하는 것이다. 이번 function 예시에서는 function 본문에 자기 자신에 대한 적용이 등장한다.

**강의 설명 →** recursion을 위해 새로운 실행 장치를 따로 도입하지 않는다. 이미 배운 function application과 substitution을 반복하면 같은 본문이 다른 argument로 다시 나타난다.

**자료 근거 →** 자료는 recursion을 반복을 표현하는 강력한 방법으로 소개하고, `sum(2)`의 전개를 보여 준다. [STT 56:59] [STT 59:47] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

**예시 →** `sum(2)`에서는 parameter `n`에 차례로 `2`, `1`, `0`이 들어가며, 마지막 호출에서 recursion이 이어지지 않는다.

**오개념 →** 자기 자신을 사용한다는 사실만으로 무한 반복이 되는 것은 아니다. 다음 호출의 argument가 어떻게 달라지는지와 recursion을 멈추는 조건을 함께 보아야 한다.

### 9. termination과 divergence

**정의 →** [[concepts/종료와-발산|termination]]은 evaluation이 결과 value에 도달하는 것이고, divergence는 evaluation이 끝없이 이어지는 것이다.

**강의 설명 →** 앞에서 본 계산들은 value가 되었지만, 같은 규칙으로 계속 자신을 다시 만들어 내는 expression도 작성할 수 있다. type이 맞는다는 사실은 이러한 반복을 막지 않는다.

**자료 근거 →** `def loop: Int = loop`와 끝없이 반복되는 name 펼치기가 제시된다. [STT 01:03:34] [STT 01:06:44] [STT 01:07:05] [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

**예시 →** `loop`를 정의로 바꾸면 다시 `loop`이고, 이 작업을 반복해도 정수 value가 나타나지 않는다.

**오개념 →** 실행 환경이 시간 제한으로 계산을 중단했다는 사실은 expression이 정상적으로 결과 value를 계산했다는 뜻이 아니다. 수업의 시연에서도 시간 제한에 의한 중단이 언급된다. [STT 01:05:32]

## 상세 해설

### 반복이 필요한 이유와 정보가 이동하는 방식

프로그램의 중요한 능력은 짧게 작성한 코드로 많은 계산을 수행하는 데 있다. 교수는 반복이 없다면 계산을 많이 시키기 위해 코드 자체도 계속 길게 작성해야 한다는 점에서 출발했다. 반복은 단순히 문법을 편리하게 만드는 기능이 아니라, 같은 계산 규칙을 여러 데이터에 적용하는 기본 장치이다. [STT 02:10] [STT 03:08]

그러나 같은 코드가 매번 완전히 같은 정보만 받는다면 계산의 상황이 달라지지 않는다. 반복을 이해하려면 무엇이 반복되는지와 무엇이 달라지는지를 함께 찾아야 한다. imperative 합산에서는 loop 본문이 같고, `sum`과 `i`의 내용이 달라진다. functional 합산에서는 function 본문이 같고, 매번 전달되는 `n`의 value가 달라진다. 이 대비가 초반의 패러다임 설명과 후반의 recursion 전개를 연결한다. [STT 06:44] [STT 59:47]

**핵심 비교 자료 읽기 ① — 6페이지의 두 방식과 합산 코드**

다음 표는 자료의 대비 구성을 학습용으로 재구성한 것이다. 원본의 시각적 배치를 그대로 복제한 것은 아니다. [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

| 읽어야 할 항목 | imperative 합산 | functional 합산 |
|---|---|---|
| 계산을 기술하는 기본 단위 | 저장된 value를 읽고 새 value를 쓰는 명령 | argument를 받아 결과를 만드는 function application |
| 이전 단계의 정보 | 갱신된 `sum`, `i`의 내용 | 다음 function에 전달되는 argument |
| 반복되는 부분 | `while`의 본문 | `sum`의 본문 |
| 진행을 나타내는 변화 | `i`를 감소시키고 `sum`을 갱신함 | `sum(n-1)`처럼 더 작은 입력으로 이동함 |
| 결과가 드러나는 곳 | loop가 끝난 뒤 `sum`의 저장 내용 | 전체 function application을 평가해 얻는 value |
| 자료에서 강조하는 경향 | 실행 절차와 자원 사용을 직접 드러내기 쉬움 | 계산할 대상 사이의 관계를 드러내기 쉬움 |

이 비교에서 가장 먼저 볼 곳은 두 코드에 모두 등장하는 `sum`의 **역할 차이**이다. imperative 예시의 `sum`은 누적 결과를 저장하는 위치의 name으로 설명되지만, functional 예시의 `sum`은 합산 계산을 수행하는 function의 name이다. 철자가 같아도 프로그램 안에서 수행하는 역할은 다르다. [STT 09:09] [STT 10:08]

다음으로 termination 조건을 읽는다. imperative 코드는 `i > 0`인 동안 본문을 반복한다. functional 코드는 `n <= 0`이면 즉시 `0`을 내고, 그렇지 않을 때만 recursion을 진행한다. 조건의 표면 형태는 다르지만 양쪽 모두 더할 양의 정수가 남아 있는지를 구별한다. [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

자료가 imperative에서 효율적인 코드를, functional에서 안전한 코드를 작성하기 쉽다고 설명하는 것은 비교의 방향이다. 특정 스타일이라는 이유만으로 모든 프로그램의 속도나 안전성이 자동으로 결정된다는 정리로 읽어서는 안 된다. 실제 수업의 결론도 목적에 맞게 두 방식을 섞어 사용해야 한다는 것이었다. [STT 04:51] [STT 08:12] [STT 13:43] [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

### 계산을 구성하는 문제와 큰 코드를 이해하는 문제

합산 function 하나를 실행하는 방법을 아는 것과 수많은 기능이 있는 프로그램을 이해하는 것은 다른 문제이다. function은 어떤 입력에 어떤 계산을 수행하는지 묶어 주지만, 큰 프로그램에서는 function 여러 개와 데이터 사이의 관계까지 조직해야 한다. 교수는 이 지점에서 Object-Oriented Programming과 type class를 소개했다. [STT 17:22] [STT 18:18]

abstraction의 효과는 세부 구현을 지우는 데 있는 것이 아니라, 현재 관심에 맞는 수준에서 설명할 수 있게 하는 데 있다. 합산 function을 사용하는 사람은 매번 내부의 conditional expression과 자기 호출을 전개하지 않고도, 입력 범위의 정수를 더하는 기능으로 이해할 수 있다. 더 큰 시스템에서도 이와 같은 기능 단위를 묶어 전체를 이해한다. [STT 18:18] [STT 19:11]

### value와 expression을 구별해야 실행을 설명할 수 있다

`3 + 4`를 보고 답이 `7`임을 아는 것과, `3 + 4` 자체가 이미 `7`이라는 value라고 분류하는 것은 다르다. 전자는 계산 결과를 예측한 것이고, 후자는 계산 전의 표현과 계산 후의 결과를 혼동한 것이다. evaluation 규칙은 바로 그 차이를 설명하기 위해 필요하다. [STT 31:07]

이번 도입의 관계를 간단히 적으면 다음과 같다.

value는 expression의 한 종류이다.

$$
3 + 4 \;\longrightarrow\; 7
$$

왼쪽은 덧셈이 남은 expression이고 오른쪽은 더 계산할 것이 없는 value이다. 반대로 `3`에서 시작한다면 이미 value이므로 추가 계산 없이 끝난다. 이때 value도 expression이라는 설명이 있어야, evaluation이 value에 도달했을 때 동일한 체계 안에서 멈춘다고 말할 수 있다. [STT 32:05] [STT 33:05] [STT 39:02]

type은 이 결과가 어떤 종류의 value인지 설명하는 데 사용된다. 자료에서 `Int`는 다음 범위의 32비트 정수 value들로 제시된다.

$$
\mathrm{Int}
=
\{-2147483648,\ldots,-1,0,1,\ldots,2147483647\}
$$

또한 다음과 같이 제시된다.

$$
\mathrm{Boolean}=\{\mathrm{true},\mathrm{false}\}
$$

`Double`은 64비트 floating-point(부동소수점) value로 소개된다. 이 설명을 수학의 모든 실수를 정확히 표현한다는 뜻으로 확대하지 말고, 자료가 명시한 표현 형식을 기준으로 기억하자. [STT 29:54] [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012)

### evaluation 순서는 expression의 구조를 따라 결정된다

자료의 evaluation 규칙에서 바깥에서 안쪽으로 본다는 것은 현재 expression에 어떤 규칙을 적용할지 가장 바깥 구조부터 판별한다는 뜻이다. 예를 들어 `5 + b`에서는 가장 바깥이 덧셈이므로 operand를 평가하는 규칙을 선택한다. 그러나 `b`가 아직 value가 아니므로 바깥 덧셈을 바로 완료할 수 없다. [STT 39:02] [STT 40:02]

**핵심 evaluation 도식 읽기 — 13페이지의 예시와 강의의 AST 설명**

아래는 `a`, `b`를 정의로 펼쳤을 때의 expression 구조를 재구성한 도식이다. 실제 evaluation 단계의 그림을 복제한 것이 아니라, 괄호와 연산의 결합 관계를 보여 준다. [STT 38:01] [STT 42:02] [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013)

```text
            +
           / \
          5   +
             / \
            3   *
               / \
              +   4
             / \
            1   +
               / \
              2   3
```

이 도식에서 위쪽 `+`는 전체 expression의 연산이다. 오른쪽 부분식이 아직 value가 아니므로 아래쪽으로 내려가 필요한 계산을 수행한다. 가장 깊은 `2 + 3`이 `5`가 된 다음, 그 결과가 `1 + 5`, `6 * 4`, `3 + 24`, `5 + 27`의 계산에 차례로 사용된다. [STT 43:00] [STT 43:57] [STT 44:53]

그림에서 읽어야 할 핵심은 **구조를 확인하는 방향과 연산을 완료하는 시점이 다르다**는 것이다. 바깥 구조를 먼저 확인하지만, 그 연산이 요구하는 부분식의 value가 준비되어야 결과를 계산한다. 또한 왼쪽부터 평가한다는 규칙은 글자나 숫자를 평평하게 왼쪽부터 계산한다는 뜻이 아니다. 각 연산의 왼쪽 부분식 전체와 오른쪽 부분식 전체를 구조에 따라 처리한다. [STT 40:02]

### name은 이미 있는 expression의 약칭이면서 미래의 입력을 표현하는 장치다

`a`는 이미 작성된 expression을 짧게 가리키는 name이다. 반면 다음 function의 `x`는 정의 시점에 구체적인 value가 주어지지 않은 name이다.

```scala
def f(x: Int): Int = x + a
```

function을 정의할 때는 사용자가 나중에 `3`을 줄지 `10`을 줄지 알 수 없다. 그래도 `x`라는 parameter를 이용하면 입력에 `a`를 더한다는 계산을 미리 작성할 수 있다. 교수는 이 점을 name의 더 본질적인 역할로 강조했다. [STT 48:47] [STT 50:27] [STT 51:23] [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

이 function에는 두 종류의 name 사용이 함께 있다. `x`는 현재 function이 받을 입력을 나타내고, `a`는 앞에서 정의한 다른 expression을 가리킨다. 따라서 `f(10)`을 계산할 때 수행하는 일도 구분된다. `x`는 argument value `10`으로 치환하고, `a`는 자신의 정의를 펼쳐 평가한다. 이 구별을 놓치지 않으면 function application을 무차별적인 문자 바꾸기로 오해하지 않게 된다. [STT 49:28] [STT 54:12] [STT 55:06]

본문의 return type(반환 타입) 표기도 이 맥락에서 읽을 수 있다. `: Int`는 이 function의 본문을 계산해 결과를 얻는다면 정수 type의 value라는 설명과 연결된다. 그러나 나중에 등장하는 divergence 예시 때문에, 정수 type을 적었다는 것만으로 계산이 반드시 끝난다고 해석해서는 안 된다. [STT 48:47] [STT 01:04:33]

### recursion의 작동과 termination을 함께 설명하기

recursion을 사용한 합산은 다음 관계를 코드로 표현한다.

$$
S(n)=
\begin{cases}
0 & n\leq 0\\
n+S(n-1) & n>0
\end{cases}
$$

이 수식은 자료의 function 정의를 수학적 표기로 다시 쓴 것이다. 양의 입력에서는 현재 수와 더 작은 입력의 합산 결과를 더하고, 양수가 아니면 `0`을 결과로 삼는다. [STT 10:08] [STT 12:46] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

여기서 중요한 것은 function name이 자기 본문에 등장한다는 사실만이 아니다. **더 작은 문제로 이동하는 호출**과 **추가 호출 없이 결과를 내는 경우**가 함께 있다는 점이다. 강의의 작은 비음수 정수 입력에 대해, `n > 0`인 동안 다음 argument는 `n-1`이므로 `0`을 향해 이동한다. `0`에서는 조건이 참이 되어 recursion이 선택되지 않는다. 이것이 전개 과정에서 확인할 수 있는 termination 이유이다. [STT 58:49] [STT 59:47] [STT 01:00:48]

또한 `sum(0)`에 도달한 순간 전체 계산이 모두 끝나는 것은 아니다. 그때는 바깥에 남아 있던 덧셈을 완료할 수 있는 value가 마련된다. `sum(2)`에서는 `2 + (1 + 0)`을 거쳐 최종 결과 `3`을 얻는다. 이 점을 보면 자기 호출이 진행되는 단계와, 필요한 value가 나온 뒤 바깥 계산을 완료하는 단계를 구분할 수 있다. [STT 01:00:48] [STT 01:01:42]

반대로 `loop`에서는 expression을 펼쳐도 상황이 달라지지 않는다. 계산 규칙이 없는 것이 아니라, 규칙을 적용한 뒤 다시 같은 expression에 도달한다. 따라서 divergence는 이번 계산 체계 바깥의 특별한 예외가 아니라, 동일한 evaluation 규칙을 적용했을 때 가능한 또 하나의 진행 양상이다. [STT 01:07:05] [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

## 예시·수식·코드

### 1. 이번 회차의 합산 코드 비교

아래는 자료의 imperative 예시를 들여쓰기만 정리한 것이다. 선언 등을 갖춘 완전한 프로그램이 아니라, state 갱신을 비교하기 위한 코드 조각이다. [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006)

```c
sum = 0;
i = n;

while (i > 0) {
    sum = sum + i;
    i = i - 1;
}
```

**이해를 위한 예시:** 자료의 imperative 코드에 입력 `n = 2`를 넣어 상태를 추적하면 다음과 같다. 이 표는 강의 후반의 `sum(2)`와 비교하도록 재구성한 것이다.

| 시점 | `sum`의 내용 | `i`의 내용 | 다음 동작 |
|---|---:|---:|---|
| 초기화 직후 | 0 | 2 | `i > 0`이므로 본문 수행 |
| 첫 반복 직후 | 2 | 1 | 다시 조건을 검사하고 본문 수행 |
| 둘째 반복 직후 | 3 | 0 | 조건이 거짓이므로 반복 termination |

functional 예시는 다음과 같다. 여기서 `sum`은 저장 위치가 아니라 function name이다. [M01 p.6](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-006) [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

```scala
def sum(n: Int): Int =
  if (n <= 0)
    0
  else
    n + sum(n - 1)
```

이번 회차에서 실제로 언급한 결과는 `sum(10) = 55`, `sum(100) = 5050`, `sum(123) = 7626`이다. 교수는 수학적 관계처럼 작성한 정의도 실행 가능한 코드라는 점을 이 예시들로 확인했다. [STT 11:08] [STT 11:51]

### 2. name을 펼쳐 `5 + b` 평가하기

자료에 주어진 정의는 다음과 같다. [M01 p.12](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-012)

```scala
def a = 1 + (2 + 3)
def b = 3 + a * 4
```

아래 화살표는 name 펼치기 또는 간단한 계산에 따라 expression이 바뀌는 과정을 나타낸다. value인지 확인하고 돌아오는 절차까지 모두 별도 줄로 표시한 것은 아니다.

```text
5 + b
→ 5 + (3 + a * 4)
→ 5 + (3 + (1 + (2 + 3)) * 4)
→ 5 + (3 + (1 + 5) * 4)
→ 5 + (3 + 6 * 4)
→ 5 + (3 + 24)
→ 5 + 27
→ 32
```

`a = 6`, `b = 27`이라는 중간 결과를 외우기보다, `a`의 정의 전체가 곱셈의 왼쪽 operand로 들어간다는 구조를 확인하자. name을 펼칠 때 괄호를 보존하지 않으면 원래 expression과 다른 결합 관계를 만들 수 있다. [STT 42:02] [STT 43:57] [STT 44:53] [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013)

### 3. function 본문 substitution과 중첩된 function application

앞의 `a` 정의에 이어 다음 function을 사용한다. [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

```scala
def f(x: Int): Int = x + a
```

단순한 적용에서는 다음과 같이 계산한다.

```text
f(10)
→ 10 + a
→ 10 + (1 + (2 + 3))
→ 10 + (1 + 5)
→ 10 + 6
→ 16
```

이때 `f(10)`이라는 **function application 전체**가 본문에 argument를 치환한 expression으로 바뀐다. function name만 `x + a`로 바꾸고 원래 괄호를 임의로 남기는 방식이 아니다. [STT 54:12] [STT 55:06]

자료의 중첩 예시는 다음과 같다. 여기서는 일부 name 펼치기와 산술 계산을 묶어서 적었다.

```text
5 + f(f(3) + 1)
→ 5 + f((3 + a) + 1)
→ 5 + f((3 + 6) + 1)
→ 5 + f(9 + 1)
→ 5 + f(10)
→ 5 + (10 + a)
→ 5 + (10 + 6)
→ 5 + 16
→ 21
```

바깥쪽 `f`를 적용하려면 그 argument인 `f(3) + 1`을 먼저 value로 만들어야 한다. 그러므로 안쪽 `f(3)`이 먼저 `9`가 되고, 여기에 `1`을 더한 `10`이 바깥 호출의 argument가 된다. 이것이 이번 회차에서 배운 argument evaluation 규칙의 구체적인 결과이다. [STT 55:06] [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

### 4. `sum(2)`의 recursion 전개

```text
sum(2)
→ if (2 <= 0) 0 else 2 + sum(2 - 1)
→ 2 + sum(2 - 1)
→ 2 + sum(1)
→ 2 + (if (1 <= 0) 0 else 1 + sum(1 - 1))
→ 2 + (1 + sum(1 - 1))
→ 2 + (1 + sum(0))
→ 2 + (1 + (if (0 <= 0) 0 else 0 + sum(0 - 1)))
→ 2 + (1 + 0)
→ 2 + 1
→ 3
```

이 전개는 자료의 recursion 예시를 단계가 드러나도록 정리한 것이다. 조건의 비교 결과를 별도 줄에 모두 적는 대신, 비교와 가지 선택을 한 단계에 묶은 곳이 있다. [STT 56:59] [STT 57:49] [STT 58:49] [STT 01:00:48] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

**15페이지의 전개 도식에서 읽어야 할 세 지점**은 다음과 같다.

| 확인 지점 | expression에서 보이는 변화 | 의미 |
|---|---|---|
| function 본문을 펼치는 순간 | `n`이 `2`, `1`, `0`으로 각각 바뀜 | 같은 본문을 다른 입력에 사용한다. |
| `sum(0)`의 조건 선택 | 자기 호출이 있는 가지 대신 `0`을 선택함 | 새로운 호출 없이 필요한 value를 얻는다. |
| 마지막 덧셈 | `2 + (1 + 0)`이 `3`이 됨 | 안쪽 결과를 이용해 바깥 계산을 완료한다. |

특히 `sum(0)`을 펼친 expression 안에 자기 호출이 글자로 남아 있다는 사실과, 그 호출을 실제로 평가한다는 것은 다르다. 선택되지 않은 가지에 들어 있으므로 계산하지 않는다. [STT 01:00:48]

### 5. 끝나지 않는 정의 두 가지

자료의 name recursion 예시는 다음과 같다. [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

```scala
def loop: Int = loop
```

```text
loop
→ loop
→ loop
→ ...
```

또한 강의에서 말로 제안한 자기 호출 function은 다음처럼 코드로 정리할 수 있다. function의 구체적인 표기를 보완한 것이며, 같은 입력으로 자기 자신을 다시 부른다는 내용은 STT에 근거한다. [STT 01:04:33]

```scala
def g(x: Int): Int = g(x)
```

```text
g(0)
→ g(0)
→ g(0)
→ ...
```

`sum`과 비교하면 `g`에는 더 작은 입력으로 이동하는 과정도, value로 빠져나오는 가지도 없다. `loop`는 argument조차 없이 name 펼치기만으로 같은 상황을 반복한다. 수업 중 실행 환경이 시간 제한으로 시연을 중단한 것은 이러한 expression이 결과 value를 만들어 냈다는 증거가 아니다. [STT 01:05:32] [STT 01:07:05]

## 능동회상 문제

### 1. imperative 합산과 functional 합산에서는 반복마다 달라지는 정보가 어디에 있는가?

<details><summary>정답</summary>

imperative 합산에서는 `sum`과 `i`의 저장 내용이 달라진다. loop는 같은 본문을 실행하지만 갱신된 state를 읽는다. functional 합산에서는 같은 `sum`의 본문에 전달되는 argument value가 달라진다. 강의의 핵심 비교는 정보 전달이 state 갱신을 통해 일어나는지, argument 전달을 통해 일어나는지이다. [STT 05:44] [STT 06:44] [STT 59:47]

</details>

### 2. `3`, `3 + 4`, name `b`는 각각 value인가, expression인가?

<details><summary>정답</summary>

`3`은 value인 동시에 expression이다. `3 + 4`는 덧셈이 남아 있는 expression이며, evaluation 결과가 `7`이라는 value이다. 이번 예시의 `b`도 평가할 expression이며, name에 연결된 정의를 펼쳐 계산해야 한다. value와 expression을 서로 겹치지 않는 분류로 생각하면 안 된다. [STT 31:07] [STT 32:05] [STT 36:03]

</details>

### 3. `5 + b`에서는 `5`와 `b` 중 무엇을 먼저 처리하며, 왜 `b`를 계산하는 과정이 길게 나타나는가?

<details><summary>정답</summary>

덧셈의 왼쪽 operand인 `5`를 먼저 처리한다. 다만 이미 value이므로 추가 계산 없이 끝난다. 이후 오른쪽 `b`는 name이므로 정의를 펼치고, 그 안의 `a`와 연산을 평가해야 한다. 전체 규칙은 왼쪽부터 평가하는 것이며, `b`가 먼저 선택된 것이 아니다. [STT 40:02] [STT 41:01] [M01 p.13](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-013)

</details>

### 4. 바깥 연산자를 먼저 확인하는데 왜 가장 안쪽의 `2 + 3`이 먼저 계산되는가?

<details><summary>정답</summary>

바깥 연산자를 확인하는 것은 적용할 evaluation 규칙을 고르는 단계이다. 덧셈이나 곱셈을 완료하려면 operand가 value이어야 하므로 필요한 부분식 안으로 내려간다. `2 + 3`의 양쪽은 이미 value이어서 먼저 계산할 수 있고, 그 결과가 바깥 연산에 사용된다. [STT 40:02] [STT 43:00] [STT 43:57]

</details>

### 5. `def f(x: Int): Int = x + a`에서 parameter와 argument는 어떻게 다르며, `f(10)`에서 무엇을 치환하는가?

<details><summary>정답</summary>

parameter `x`는 function 정의에서 앞으로 받을 value를 나타내는 name이다. `10`은 해당 호출에서 실제로 전달된 argument value이다. `f(10)`은 본문 `x + a`에서 `x`를 `10`으로 치환한 `10 + a`로 바뀐다. `a`는 별도 정의에 따라 평가한다. [STT 48:47] [STT 54:12] [STT 55:06] [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

</details>

### 6. `a`가 `6`으로 평가될 때 `5 + f(f(3) + 1)`의 결과는 무엇인가? 바깥 `f`의 실제 argument value도 설명하라.

<details><summary>정답</summary>

안쪽 `f(3)`은 `3 + 6 = 9`가 된다. 따라서 바깥 `f`의 argument expression `f(3) + 1`은 `10`이 된다. 바깥 `f(10)`은 `16`이고, 여기에 `5`를 더해 전체 결과는 `21`이다. 바깥 호출에는 안쪽 function name이나 계산 전의 expression이 아니라, 이번 evaluation 규칙에 따라 계산된 value `10`이 전달된다. [STT 55:06] [M01 p.14](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-014)

</details>

### 7. `sum(0)`을 펼치면 자기 호출이 있는 가지도 보인다. 그런데 왜 그 호출은 실행되지 않는가?

<details><summary>정답</summary>

조건 `0 <= 0`이 참이므로 결과 expression으로 `0`을 선택한다. conditional expression은 두 가지를 모두 먼저 계산하지 않는다. 선택되지 않은 가지에 `sum(0-1)`이 적혀 있어도 그 expression을 평가할 필요가 없다. [STT 46:26] [STT 01:00:48] [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015)

</details>

### 8. `sum(2)`가 `sum(0)`에 도달한 뒤에도 남아 있는 계산은 무엇인가?

<details><summary>정답</summary>

전체 expression에는 바깥의 덧셈이 남아 있다. `sum(0)`이 `0`이 되면 전체는 `2 + (1 + 0)`이고, 이를 `2 + 1`, 다시 `3`으로 계산한다. 기저 조건에서 얻은 value는 앞서 기다리던 계산을 마무리하는 데 사용된다. [STT 01:00:48] [STT 01:01:42]

</details>

### 9. `sum(2)`의 termination과 `loop`의 divergence를 가르는 결정적인 차이는 무엇인가?

<details><summary>정답</summary>

`sum`은 양의 입력에서 다음 argument를 감소시키고, `0`에서 recursion 없이 value를 내는 가지를 선택한다. 반면 `loop`는 정의를 펼쳐도 다시 같은 name만 나타나므로 value에 가까워지는 변화가 없다. 두 경우 모두 evaluation 규칙을 적용하지만 전개의 양상이 다르다. [M01 p.15](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-015) [M01 p.16](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-016)

</details>

### 10. `def loop: Int = loop`에 type이 적혀 있는데도 왜 정수 결과를 받지 못할 수 있는가?

<details><summary>정답</summary>

type이 맞는다는 것과 evaluation이 끝난다는 것은 별개의 성질이기 때문이다. 이 정의에서는 본문의 `loop`도 정수 type으로 설명할 수 있지만, 평가하면 같은 name이 끝없이 반복되어 실제 정수 value에 도달하지 않는다. [STT 01:06:44] [STT 01:07:05]

</details>

### 11. Object-Oriented Programming과 type class의 비교는 imperative와 functional의 비교와 어떻게 다른가?

<details><summary>정답</summary>

imperative와 functional의 비교는 계산을 무엇으로 기술하고 정보를 어떻게 전달하는지에 관한 것이다. Object-Oriented Programming과 type class의 비교는 큰 프로그램의 abstraction 단위와 code reuse를 어떻게 구성하는지에 관한 것이다. 자료는 후자의 공통 목표를 모듈 구성, abstraction, code reuse로 제시한다. [STT 17:22] [STT 18:18] [M01 p.8](https://jhlee1020lee.github.io/2026-fall-study-hub/page_cache/principles_of_programming/lecture-part1/page-008)

</details>

### 12. 교수는 AI가 코드를 작성하는 상황에서도 왜 두 계산 방식을 배워야 한다고 설명했는가?

<details><summary>정답</summary>

AI가 작성한 코드에 두 스타일이 섞여 있으면 이를 이해하려는 사람도 두 방식의 원리를 알아야 한다. 또한 특정 부분에 어떤 방식이 적절한지 판단하고 방향을 제시하려면 원리에 대한 이해가 필요하다는 설명이었다. 이는 이번 수업에서 제시한 학습 동기이며, 모든 AI의 능력에 대한 일반적인 판정으로 확대할 필요는 없다. [STT 13:43] [STT 14:41]

</details>
