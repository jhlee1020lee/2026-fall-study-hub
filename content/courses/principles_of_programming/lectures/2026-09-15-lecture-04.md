이번 강의에서는 코드 안의 이름을 어디에서 찾는지, 식을 언제 계산하는지, 함수 호출 뒤에 어떤 일이 남는지를 살펴본다.  
합 계산의 실행 과정을 추적하며, 계산 결과·저장 공간·실행 환경의 지원을 구분하는 것이 목표다.

## 강의 내용과 설명

### Block(블록)과 environment(환경): 계산과 이름의 범위를 함께 관리하기

Block은 여러 선언과 마지막 expression(식)을 하나의 계산 단위로 묶는 expression이다. 중괄호 안에 여러 줄이 있다고 해서 단순히 명령들을 담는 상자로 이해하면 부족하다. 내부 선언들이 계산에 필요한 이름을 제공하고, 마지막 expression의 값이 Block 전체의 값이 된다. 이번 강의의 도입에서는 이 내용을 이전 시간의 복습으로 짚었다. 아래의 세부 실행 설명은 그 복습을 강의자료로 보충한 것이다. [STT 01:42] [STT 02:13] [M01 p.27] [M01 p.28]

이름을 expression이나 값과 연결하는 것을 name binding(이름 연결)이라고 한다. Environment는 현재 계산에서 사용할 수 있는 이름과 그 연결 관계를 설명하는 모델이다. 중첩된 Block이나 함수 호출을 평가할 때는 해당 계산에 필요한 environment를 만들고, 이름을 찾으며, 계산이 끝나면 기다리던 계산으로 돌아온다. 따라서 코드를 읽을 때는 **무엇을 계산하는지와 그 안의 이름을 어디에서 찾는지를 함께 추적해야 한다.** [STT 02:13] [M01 p.29]

자료의 Name Scoping(이름의 유효 범위 결정) 규칙은 다음과 같다.

- Block 내부에서 정의한 이름은 그 Block 안에서 사용한다.
- 내부에 같은 이름의 정의가 있으면 외부 정의를 가린다.
- 가려지지 않은 외부 이름은 내부 Block에서도 사용할 수 있다.
- 자료에서 다루는 기본 이름 정의에서는 같은 Block에 중복 정의를 두지 않는다.
- 함수의 body(본문)는 함수가 **정의된 곳의 environment**를 기준으로 평가한다. 호출한 곳의 environment로 바꾸지 않는다. [M01 p.29]

마지막 규칙은 내부에 같은 이름이 있을 때 특히 중요하다. 다음은 p32의 코드를 읽기 좋게 정리한 것이다.

```scala
{
  val t = 0
  def f(x: Int) = t + g(x + 1)
  def g(y: Int) = y * y

  val x = f(5) + 7

  val r = {
    val t = 10
    val s = f(5)
    s - t
  }

  t + r
}
```

**자료 도식 읽기 ① — p32의 environment 실행표.** 이 도식에서 먼저 확인할 것은 `f`를 부르는 위치보다 `f`의 정의가 속한 environment다. 바깥 environment를 `E0`, `r`을 계산하는 내부 Block의 environment를 `E3`라고 보면, `E3`에는 `t = 10`이 있지만 `f`는 `E0`에서 정의되어 있다. 따라서 내부 Block에서 `f(5)`를 호출해도 `f`의 `t`는 `E0`의 `0`을 가리킨다. [M01 p.32]

| 계산 위치 | 이름을 해석하는 기준 | 계산 결과 |
|---|---|---|
| 바깥의 `f(5)` | `f`의 인자 `x = 5`, 외부 `t = 0` | `0 + g(6) = 36` |
| 바깥의 `val x` | 방금 얻은 `f(5)`의 결과 | `36 + 7 = 43` |
| 내부 Block의 `val t` | 내부에서 새로 정의한 이름 | `10` |
| 내부의 `f(5)` | 함수의 정의 environment는 여전히 `E0` | `36` |
| 내부의 `s - t` | 내부의 `s = 36`, `t = 10` | `26` |
| 마지막 `t + r` | 바깥의 `t = 0`, `r = 26` | `26` |

함수의 인자 `x`, 바깥의 `val x`, 내부와 외부의 `t`는 이름이 겹치더라도 같은 연결이 아니다. 도식은 이 차이를 environment별로 나누어 보여 준다. 특히 `g(6)`도 자신이 정의된 environment를 기준으로 평가하며, 인자 `y = 6`을 이용해 `36`을 만든다. [M01 p.32]

p32에는 주의할 표기 불일치가 있다. environment 표 안의 `f` 표현은 `g(x)`처럼 나타나지만, 같은 페이지의 코드와 실제 전개는 `g(x + 1)`을 사용한다. 위 계산은 **코드와 전개가 일치하는 `g(x + 1)`을 기준**으로 했다. 표 내부 표현의 불일치는 검증 필요로 남긴다. 또한 p29의 유사 코드와 달리 p32에는 바깥 `x` 계산에 `+ 7`이 있으므로 두 페이지의 결과를 혼합하면 안 된다. [M01 p.29] [M01 p.32]

흔한 오해는 내부 `t = 10`이 외부의 `t`를 변경한다고 생각하는 것이다. 이 예제는 기존 값을 바꾸는 동작이 아니라, 다른 범위에 같은 이름을 새로 정의한 경우다. [[concepts/block|Block]]을 읽을 때 [[concepts/environment|environment]]를 함께 추적해야 하는 이유가 여기에 있다.

자료는 `def`와 `val`의 선언 순서에도 차이가 있다고 덧붙인다. 다만 이를 모든 선언을 자유롭게 이동해도 된다는 뜻으로 받아들이면 안 된다. 이번 녹음의 도입에서 상세한 선언 순서 검사 규칙 전체를 다시 설명했다고 볼 근거는 없으므로, 여기서는 이름의 범위와 실행 environment의 복습에 초점을 둔다. [M01 p.28] [STT 02:13]

### `sqrt`의 내부 함수: 외부에 필요한 이름만 드러내기

Block은 이름을 찾는 규칙뿐 아니라 프로그램을 조직하는 데도 사용된다. `sqrt`를 호출하는 쪽에서 필요한 것은 제곱근을 구하는 기능이다. 추측값을 개선하거나 계산을 반복하는 보조 함수의 이름까지 외부에 공개할 필요는 없다. 강의에서는 보조 함수들을 `sqrt` 내부에 넣어 외부에서는 `sqrt`만 사용하도록 만드는 예제를 복습했다. [STT 02:59] [STT 03:06]

p34는 보조 함수들이 나란히 정의된 상태를 제시하고, p35는 이를 `sqrt`의 Block 안으로 옮긴다. 다음 코드는 p35의 계산 구조를 유지하고 줄바꿈을 정리한 것이다. [M01 p.34] [M01 p.35]

```scala
def sqrt(x: Double) = {
  def sqrtIter(guess: Double, x: Double): Double = {
    if (isGoodEnough(guess, x))
      guess
    else
      sqrtIter(improve(guess, x), x)
  }

  def isGoodEnough(guess: Double, x: Double) = {
    val ratio = guess * guess / x
    ratio > 0.999 && ratio < 1.001
  }

  def improve(guess: Double, x: Double) =
    (guess + x / guess) / 2

  sqrtIter(1, x)
}

sqrt(2)
```

이 코드에서는 각 내부 함수가 하나의 역할을 맡는다. `isGoodEnough`는 현재 추측값을 받아들일지 판단하고, `improve`는 새로운 추측값을 만들며, `sqrtIter`는 판단과 개선을 이어 간다. 마지막 expression인 `sqrtIter(1, x)`의 결과가 `sqrt`의 결과가 된다. `ratio` 역시 검사 함수 안에서만 필요한 중간값이므로 그 내부에 둔다. [M01 p.35]

**이해를 위한 계산 예시:** 자료의 `sqrt(2)`에서 처음 추측값은 `1`이다. 이때 `ratio`는 `1 * 1 / 2 = 0.5`이므로 제시된 조건을 만족하지 않는다. 한 번 개선하면 다음 값을 얻는다.

$$
\frac{1+2/1}{2}=1.5
$$

새 추측값의 `ratio`는 `1.5 * 1.5 / 2 = 1.125`이므로 다시 개선을 진행한다. 이 계산은 자료 코드를 따라 읽은 보충 설명이며, 이번 녹음에서 이 수치 전개를 모두 다시 수행했다는 뜻은 아니다. [M01 p.35]

여기서 배울 조직 원리는 **외부에서 사용하는 기능과 내부 구현용 이름의 범위를 구분하는 것**이다. Block 안에 넣는다고 보조 함수의 계산이 없어지는 것은 아니다. 계산은 그대로 수행하면서 이름을 사용할 수 있는 범위를 제한한다. 또한 이 복습을 제곱근 근사 방법의 수학적 유도나 모든 입력에 대한 정확성 증명까지 새로 배운 것으로 확대하지 않는다.

### Call-by-value(값에 의한 호출)와 Call-by-name(이름에 의한 호출): 인자를 언제 계산하는가

함수 호출에는 인자 expression을 계산하는 일과 함수 body를 계산하는 일이 있다. Call-by-value와 Call-by-name은 이 두 작업의 순서를 다르게 정한다. Call-by-value는 인자 expression을 먼저 값으로 만든 뒤 body를 평가한다. Call-by-name은 인자 expression을 미리 평가하지 않고, body에서 그 인자가 필요할 때 평가한다. [STT 03:06] [STT 04:11] [M01 p.17]

p17의 `square(1 + 1)` 예제를 보면 차이가 분명하다. 두 방식의 평가 과정을 설명하기 위해 `square`의 body를 `x * x`라고 두자.

```text
Call-by-value:
square(1 + 1)
→ square(2)
→ 2 * 2
→ 4

Call-by-name:
square(1 + 1)
→ (1 + 1) * (1 + 1)
→ 2 * (1 + 1)
→ 2 * 2
→ 4
```

Call-by-value에서는 `1 + 1`을 한 번 계산한 값 `2`를 사용한다. Call-by-name에서는 `x`가 사용되는 각 위치에서 인자 expression이 필요해지므로 같은 덧셈을 다시 평가한다. 이 예제의 최종값은 같지만, **최종값이 같다는 사실과 평가 과정이 같다는 사실은 다르다.** [M01 p.17] [M01 p.18]

반대로 인자를 전혀 사용하지 않는 경우에는 Call-by-name의 차이가 더 크게 드러난다. Scala 자료에서는 일반 인자를 Call-by-value로 받고, 자료형 앞에 `=>`를 붙인 인자를 Call-by-name으로 받는다. [M01 p.19]

```scala
def one(x: Int, y: => Int) = 1
```

이 함수는 body에서 두 인자를 사용하지 않는다. 그래도 `x`의 expression은 호출 전에 평가된다. `y`의 expression은 사용되지 않으므로 평가되지 않는다. 따라서 사용되지 않는다는 사실만 보고 모든 인자가 계산을 건너뛴다고 판단하면 안 된다. 인자의 선언 방식도 확인해야 한다. [M01 p.19]

이 구별은 `val`과 `def`의 이름 연결에도 이어진다.

| 자료의 표기 | 이름을 정의할 때의 동작 | 이후 이름을 사용할 때 |
|---|---|---|
| `val a = e` | `e`를 먼저 평가하고 결과를 연결한다 | 저장된 값을 사용한다 |
| `def a = e` | `e`를 즉시 평가하지 않고 정의를 연결한다 | 정의된 expression을 평가한다 |

자료는 이 차이를 이름과 값의 연결, 이름과 expression의 연결로 설명한다. 다만 이 표만으로 Call-by-name의 environment 구현까지 해결되었다고 생각해서는 안 된다. **평가 시점을 미루는 문제와 이름을 올바른 environment에서 해석하는 문제는 함께 만족해야 한다.** [M01 p.20] [STT 05:07] [STT 06:12]

[[concepts/call-by-value|Call-by-value]]와 [[concepts/call-by-name|Call-by-name]]을 비교할 때는 결과값뿐 아니라 사용하지 않는 인자의 평가 여부, 반복 사용 시 평가 횟수를 함께 살펴본다. 출력처럼 관찰 가능한 동작이 expression에 포함되면 평가 횟수의 차이도 프로그램의 동작 차이가 된다.

### Call-by-name의 environment 문제: body와 인자 expression은 출발점이 다르다

Call-by-name을 environment 표로 표현하려면 인자 자리에 값 대신 expression을 넣으면 될 것처럼 보인다. 강의에서는 먼저 이 아이디어를 제시한 뒤, 그대로는 올바른 의미를 보존하지 못한다고 설명했다. 문제는 expression 자체가 아니라 **그 expression 안의 이름을 어디에서 찾는가**에 있다. [STT 05:07] [STT 06:12]

함수 body의 외부 이름은 함수가 정의된 environment를 기준으로 해석한다. 반면 호출자가 작성한 인자 expression의 이름은 그 expression이 놓인 호출 장소의 environment를 기준으로 해석해야 한다. 이 둘을 무조건 같은 environment에서 찾으면, 같은 철자의 이름이 다른 값을 가리킬 수 있다. [STT 07:07]

다음은 이 차이를 분리해 보여 주기 위해 만든 **이해를 위한 예시**다. 녹음 중 손상된 라이브 코드를 복원한 것이 아니다.

```scala
{
  val x = 100

  def f(y: => Int): Int =
    x + y

  val answer = {
    val x = 7
    f(x + 3)
  }

  answer
}
```

`f`의 body에 있는 `x`는 `f`가 정의된 바깥 Block의 `100`이다. 그러나 인자로 전달한 `x + 3`은 내부 Block에서 작성되었으므로 그 안의 `x`는 `7`이다. 따라서 올바른 결과는 다음과 같다.

$$
100+(7+3)=110
$$

만약 인자 expression을 `f`의 정의 environment에서 그대로 평가하도록 잘못 구현한다면, 인자 안의 `x`까지 `100`으로 해석하여 `100 + (100 + 3) = 203`을 만들게 된다. 이는 위 Scala 코드의 올바른 결과가 아니라, **잘못된 environment 연결이 의미를 바꾸는 사례**다. [STT 07:07] [M01 p.29]

이 예제가 보여 주는 요구사항은 명확하다. 평가를 미루더라도 인자 expression의 이름 해석 기준을 보존해야 한다. 반면 그 요구를 어떤 구체적 실행 구조로 구현하는지는 이번 강의에서 완결하지 않았다. 강의는 해당 해결을 뒤로 미루었다. 따라서 이번 범위에서 배운 것은 environment의 구별과 단순 대입 방식의 문제이며, 후속 장의 구현 전체를 이미 배운 것으로 처리하지 않는다. [STT 08:03] [STT 16:59]

STT의 이 구간에는 `x`, `y`, 함수 이름을 가리키는 표현이 뒤섞인 부분이 있다. 개별 식별자의 정확한 라이브 배치는 검증 필요다. 위 예시는 명확히 확인되는 environment 구별을 설명하기 위한 것이며, 불명확한 발화를 대신하는 원문으로 사용하지 않는다.

### Lazy call-by-value(최초 사용 시 평가하고 결과를 재사용하는 방식)

Call-by-name은 사용하지 않는 인자를 계산하지 않지만, 같은 인자를 여러 번 사용하면 평가를 반복할 수 있다. Call-by-value는 평가한 결과를 재사용하지만, body에서 인자를 쓰지 않더라도 호출 전에 계산한다. 자료의 Lazy call-by-value는 **사용하지 않으면 계산하지 않고, 사용하게 되면 처음 한 번 계산한 결과를 재사용하는 방식**이다. [STT 09:22] [STT 11:20] [M01 p.36] [M01 p.37]

이를 구현하는 자료의 조합은 Call-by-name 인자와 `lazy val`이다. 먼저 인자를 Call-by-name으로 받아 호출 시점의 평가를 미룬다. 이어 body 내부에서 `lazy val`로 연결하면, 그 이름이 처음 필요해질 때 expression을 평가하고 결과를 저장한다. 이후에는 그 결과를 사용한다. [STT 11:20] [STT 14:16]

Environment 관점에서는 처음에는 아직 평가하지 않은 expression과 연결되어 있다가, 최초 사용 시 평가한 값을 재사용하도록 상태가 바뀐다고 이해할 수 있다. 이 설명은 개념 모델이며 실제 실행기의 저장 형식까지 확정하는 설명은 아니다. [STT 16:03]

p37의 핵심 코드는 다음과 같다.

```scala
def f(c: Boolean, i: => Int): Int = {
  lazy val iv = i

  if (c)
    0
  else
    iv * iv * iv
}

f(true,  { println("ok"); 100 + 100 + 100 + 100 })
f(false, { println("ok"); 100 + 100 + 100 + 100 })
```

이 코드에서 `c`는 어느 분기를 실행할지 정하고, `i`는 계산을 미룰 수 있는 인자다. 두 호출은 각각 별도의 실행이므로 내부의 `iv`도 서로 공유하지 않는다. [M01 p.37]

`f(true, ...)`에서는 `0`을 반환하는 분기를 선택한다. `lazy val iv = i`라는 선언을 지나갔더라도 `iv`를 실제로 사용하지 않았으므로 인자 Block을 평가하지 않는다. 따라서 `ok`도 출력되지 않는다.

`f(false, ...)`에서는 곱셈에 `iv`가 필요하다. 처음 `iv`를 사용할 때 인자 Block을 평가하여 `ok`를 한 번 출력하고, 덧셈의 결과 `400`을 얻는다. 그다음 두 번의 `iv` 사용은 저장된 `400`을 재사용한다. 결과는 다음과 같다.

$$
400\times400\times400=64{,}000{,}000
$$

`iv`를 세 번 읽지만 인자 expression의 평가는 한 번이라는 점이 핵심이다. 곱셈 연산 자체는 두 번이다. [M01 p.37]

**이해를 위한 변형 비교:** 같은 함수에서 내부 연결만 바꾼다고 하자. `i`는 계속 Call-by-name 인자로 받고, 연결 선언은 `if`보다 앞에 둔다. 정상적으로 끝나는 같은 인자 Block에 대해 출력 횟수는 다음과 같다.

| body 앞의 연결 방식 | `c = true` | `c = false` | 이유 |
|---|---:|---:|---|
| `val iv = i` | 1회 | 1회 | 선언에 도달하면 먼저 평가한다 |
| `def iv = i` | 0회 | 3회 | `iv`를 사용할 때마다 expression을 평가한다 |
| `lazy val iv = i` | 0회 | 1회 | 최초 사용 때 평가한 결과를 재사용한다 |

이 비교는 p20과 p37의 규칙을 적용한 설명용 변형이다. [M01 p.20] [M01 p.37]

Call-by-name으로 받았다는 이유만으로 평가가 끝까지 미뤄지는 것은 아니다. body 첫머리에서 `val iv = i`를 실행하면 바로 `i`가 필요해진다. 다만 이 평가 시점은 일반 Call-by-value 인자의 호출 전 평가와 정확히 같지는 않다. 여기서는 **body에 들어와 해당 `val` 선언에 도달했을 때** 평가한다. 뒤 분기에서 쓰지 않더라도 이미 수행한 평가를 취소할 수 없다는 점이 비교의 핵심이다. [STT 12:20]

또한 `lazy val`이 아직 미뤄 둔 연산을 재사용하게 해 줄 수는 있어도, 이미 실행한 연산을 되돌려 미평가 상태로 만드는 것은 아니다. 이 때문에 자료가 `i: => Int`와 `lazy val iv = i`를 함께 사용한다.

STT 15:05에는 사용 여부와 평가 횟수에 관한 부정 표현이 서로 충돌하는 부분이 있다. 그 문장의 정확한 발화는 검증 필요다. 위 결과는 **p37의 코드에서 확인되는 동작**이며 손상된 발화를 복원한 직접 인용이 아니다. [[concepts/lazy-evaluation|Lazy call-by-value]]를 공부할 때는 선언을 지나는 시점, 최초로 값을 요구하는 시점, 저장된 값을 다시 사용하는 시점을 구분한다.

### Functional Programming(함수형 프로그래밍)과 실제 자원 사용의 간극

Functional Programming은 function application(함수 적용)을 조합하여 계산을 표현한다. 반복은 Recursion(재귀), 즉 자신의 정의 안에서 자신을 다시 사용하는 방식으로 나타낼 수 있다. 반면 Imperative Programming(명령형 프로그래밍)은 메모리의 값을 읽고 바꾸는 과정을 순서대로 표현하며 반복문으로 작업을 반복한다. [M01 p.6] [M01 p.15]

강의가 이 비교를 다시 꺼낸 이유는 코드의 간결함과 실제 자원 사용 사이에 차이가 있을 수 있기 때문이다. 값을 갱신하는 반복문은 어떤 상태를 유지하는지 눈에 보이기 쉽다. 재귀로 적은 수식은 계산의 정의가 짧더라도, 실행 도중 무엇을 보존하는지는 별도로 살펴봐야 한다. 교수는 이 간극을 설명하기 위해 합을 구하는 `sum`을 사용했다. [STT 18:46] [STT 19:36]

**자료 도식 읽기 ② — p6의 두 계산 방식 비교.** 자료에 제시된 두 코드 구조를 다음처럼 대조할 수 있다.

| 읽을 부분 | Imperative Programming의 코드 | Functional Programming의 코드 |
|---|---|---|
| 계산 상태의 표현 | 현재 합과 현재 위치를 변수로 둔다 | 현재 입력에 대한 함수의 결과를 정의한다 |
| 다음 단계로 가는 방법 | 합을 갱신하고 위치를 감소시킨다 | 더 작은 입력으로 함수를 호출한다 |
| 반복을 끝내는 조건 | 반복문의 조건이 거짓이 된다 | 더 작은 호출로 내려가다가 종료 조건을 만난다 |
| 추가로 살펴볼 자원 | 유지하는 변수와 반복 횟수 | 호출 깊이와 호출 뒤 남는 계산 |

이 표는 자료의 비교 내용을 재구성한 것이다. 원본의 반복문은 합과 위치를 갱신하고, 재귀 코드는 `n + sum(n - 1)`로 같은 합을 정의한다. 읽어야 할 차이는 문법의 길이가 아니라 **다음 단계를 수행할 때 이전 단계의 무엇을 남겨 두는가**다. [M01 p.6]

p39는 `sum(10)`부터 더 큰 입력들을 시험해 보고 평가 과정에 어떤 문제가 생기는지 생각하도록 한다. p40의 함수는 다음과 같다. [M01 p.39] [M01 p.40]

```scala
def sum(n: Int): Int =
  if (n <= 0)
    0
  else
    n + sum(n - 1)
```

이 함수는 양의 `n`에 대해 `1`부터 `n`까지 더한다. 그런데 큰 입력에서 실패했다고 해서 덧셈 자체가 컴퓨터에 지나치게 어려운 작업이라고 결론 내릴 수는 없다. 계산 단계의 수, 결과를 담는 숫자의 범위, 끝나지 않은 호출을 보존하는 공간은 서로 다른 문제다. 강의에서 `BigInt`로 바꾸어도 같은 문제가 남는다고 설명한 것은 숫자 표현 문제와 호출의 자원 문제를 분리하기 위한 단서다. [STT 21:22] [STT 22:39]

이 구간의 정확한 라이브 입력·출력 수치와 실행 시간은 STT만으로 확정하기 어렵다. 강의 중의 시간 비교를 검증된 성능 측정으로 사용하지 않는다. 또한 자료의 두 스타일 비교는 학습을 위한 관점이며, 한 스타일이 모든 프로그램에서 언제나 더 빠르다는 결론을 제공하지 않는다.

강의 전환부에는 질문이 줄어든 현상을 AI 사용과 연결하는 개인적 추측도 나온다. 이는 교수의 관찰과 예상으로 구분하며, 입증된 인과관계나 이번 학기의 AI 사용 규칙으로 해석하지 않는다. [STT 17:48]

### Substitution(치환)으로 보는 Recursion: 내려갈수록 무엇이 남는가

Substitution은 함수 호출을 해당 body로 바꾸면서 인자 값을 매개변수 자리에 넣어 계산을 따라가는 방법이다. Environment를 이용해 같은 프로그램을 설명할 수도 있지만, 강의에서는 재귀가 남기는 작업을 눈으로 보기 위해 치환 전개를 선택했다. [M01 p.14] [STT 24:39]

p40의 정의에 `sum(3)`을 적용하면 다음과 같다. 이는 자료의 함수 정의와 강의의 전개를 정리한 것이다.

```text
sum(3)
→ 3 + sum(2)
→ 3 + (2 + sum(1))
→ 3 + (2 + (1 + sum(0)))
→ 3 + (2 + (1 + 0))
→ 3 + (2 + 1)
→ 3 + 3
→ 6
```

앞부분에서는 더 작은 입력의 `sum`을 계속 요청한다. 그러나 바깥의 덧셈은 사라지지 않는다. `sum(2)`를 계산하는 동안 `3 + ...`가 기다리고, `sum(1)`을 계산하는 동안에는 `2 + ...`도 기다린다. `sum(0)`의 결과를 얻고 나서야 안쪽부터 덧셈을 끝낼 수 있다. [STT 25:54] [STT 26:48] [M01 p.40]

이 구조는 p15의 `sum(2)` 전개에서도 확인할 수 있다. 재귀의 정의 자체는 단순한 식의 전개로 설명되지만, **결과를 기다리는 바깥 식이 함께 남는다**는 점을 놓치면 실행 비용을 잘못 예상하게 된다. [M01 p.15]

| 현재 계산 중인 호출 | 결과를 받은 뒤 해야 할 일 |
|---|---|
| `sum(3)`이 `sum(2)`를 기다림 | 결과에 `3`을 더한다 |
| `sum(2)`가 `sum(1)`을 기다림 | 결과에 `2`를 더한다 |
| `sum(1)`이 `sum(0)`을 기다림 | 결과에 `1`을 더한다 |
| `sum(0)` | `0`을 반환한다 |

흔한 오해는 인자가 `3, 2, 1, 0`으로 작아지므로 저장할 정보도 줄어든다고 생각하는 것이다. 입력값은 줄어들지만, 아직 끝나지 않은 호출의 수는 늘 수 있다. [[concepts/recursion|Recursion]]을 분석할 때는 작은 문제로 내려가는 방향과 남은 일이 쌓이는 방향을 구분해야 한다.

강의의 종이 비유는 바로 이 차이를 설명한다. 먼저 더할 항목들을 종이에 계속 적고 나중에 계산하려 한다면, 시간은 충분해도 기록할 공간이 먼저 부족해질 수 있다. 이때 종이는 끝나지 않은 계산을 보존하는 공간에 대응한다. 따라서 “조금 더 기다리면 해결될 문제”와 “기록할 공간이 모자란 문제”는 같은 문제가 아니다. [STT 27:56] [STT 28:55]

### continuation(이어서 수행할 계산)과 call stack(호출 스택)

Caller(호출하는 함수)가 callee(호출되는 함수)의 결과를 받은 뒤 작업을 계속해야 한다면, 호출 전의 실행 정보를 보존해야 한다. 이때 결과를 받은 뒤 이어서 수행할 계산을 continuation이라고 이해할 수 있다. `sum(n)`에서는 작은 합의 결과에 현재의 `n`을 더하는 일이 해당한다. [STT 31:08] [STT 31:49] [STT 32:41]

예를 들어 `sum(3)`이 `sum(2)`를 부른 시점에는 단순히 숫자 `3`만 잊지 않으면 되는 것이 아니다. 작은 호출이 끝난 뒤 어디로 돌아가야 하는지, 돌아가서 어떤 이름과 값을 사용해야 하는지, 받은 결과로 어떤 계산을 계속해야 하는지도 필요하다. 강의는 복귀할 코드 위치, 실행 당시의 environment, 남은 계산에 관한 정보를 함께 설명한다. [STT 32:41]

Call stack은 이러한 호출별 복귀 정보를 쌓아 보존하는 실행 구조다. `sum(3)`의 예에서는 `sum(0)`이 끝날 때까지 상위 호출들이 기다리고, 이후 가까운 호출부터 차례로 남은 일을 끝낸다. 다음은 강의의 설명을 간략히 재구성한 도식이다. [STT 33:56]

```text
계산이 내려갈 때
sum(3): 결과를 받으면 3을 더해야 함
  sum(2): 결과를 받으면 2를 더해야 함
    sum(1): 결과를 받으면 1을 더해야 함
      sum(0): 0을 반환

결과가 돌아올 때
0 → 1 → 3 → 6
```

따라서 [[concepts/continuation|continuation]]과 [[concepts/call-stack|call stack]]은 같은 단어가 아니다. Continuation은 남은 계산이라는 개념이고, call stack은 강의에서 그 계산을 재개할 정보를 저장하는 구조로 설명된다. 모든 실행기에서 모든 이름의 값이 똑같은 형태로 저장된다는 세부 구현까지 이 도식이 정하는 것은 아니다.

또 하나의 오해는 함수에 대한 코드를 여러 번 복사하기 때문에 공간이 필요하다고 생각하는 것이다. 이 설명의 초점은 동일한 함수 코드의 복제가 아니라, **각 호출이 서로 다른 상태에서 멈추어 기다리기 때문에 필요한 실행 정보**다. `sum(3)`과 `sum(2)`는 같은 함수 정의를 사용하지만 돌아와서 더해야 하는 값과 기다리는 위치가 다르다.

### Stack overflow(호출 스택 용량 초과): 전체 메모리와 호출 공간은 구별한다

Stack overflow는 끝나지 않은 호출들이 사용하는 공간이 실행 환경의 stack 용량을 넘는 문제다. 강의의 재귀적 `sum`에서는 더 작은 입력을 호출할 때마다 상위 호출의 남은 일을 보존하므로 깊이가 증가한다. 이 구조가 충분히 깊어지면 문제가 발생할 수 있다. [STT 30:10] [STT 35:32]

컴퓨터에 전체 메모리가 많이 남아 있다는 사실만으로 stack도 필요한 만큼 계속 늘어난다고 가정할 수는 없다. 강의에서는 전체 메모리와 호출 정보를 위해 정해 둔 공간을 구별한다. 종이 비유를 더 정확히 읽으면, 컴퓨터가 가진 모든 종이가 아니라 해당 작업에 사용할 수 있도록 배정된 종이가 부족한 상황에 가깝다. [STT 29:50] [STT 33:56] [STT 36:30]

자료의 `sum`에서 양의 입력 `n`을 하나씩 줄이면 종료 조건까지의 호출 깊이도 `n`에 따라 증가한다. 이는 이 함수의 구조에서 도출되는 설명이다. 따라서 작은 입력에서 결과가 맞았다는 사실만으로 큰 입력에서도 같은 방식으로 안전하게 실행된다고 결론 내릴 수 없다. [M01 p.40]

그렇다고 모든 일반 재귀를 피해야 한다는 뜻은 아니다. 강의에서는 프로그램 전체에서 가능한 깊이가 충분히 작게 제한된다고 판단할 수 있으면 간단한 재귀를 그대로 사용할 수 있다고 설명한다. 반면 입력이나 호출 깊이가 크게 늘어날 가능성이 있으면 그 비용을 고려해야 한다. [STT 37:27]

판단의 대상은 “재귀를 썼는가” 하나가 아니라 가능한 최대 깊이와 실행 환경의 제약이다. STT에 나오는 특정 호출 횟수를 모든 환경에 적용되는 안전 한도로 외워서는 안 된다. 정확한 메모리 용량과 단위가 손상된 부분도 검증 필요이며, 이를 임의의 실제 설정값으로 바꾸지 않는다.

[[concepts/stack-overflow|Stack overflow]]를 함수의 종료 여부와 혼동하는 것도 피해야 한다. `sum`에는 입력을 줄이는 구조와 종료 조건이 있다. 수학적으로 종료하는 계산이라도, 그 지점에 도달하기 전에 실행에 필요한 공간이 부족할 수 있다.

### 지우개 비유: 남은 작업 목록 대신 두 상태를 전달하기

종이 공간의 문제를 해결하는 한 가지 생각은 지금까지의 모든 기록을 유지하지 않는 것이다. 이미 계산한 결과를 하나의 누적값으로 합치고, 아직 어디까지 계산해야 하는지만 함께 적어 둔다. 다음 단계에서는 이전 두 값을 지우고 새로운 두 값으로 바꾼다. 강의의 지우개 비유는 이런 계산 방식을 설명한다. [STT 38:27] [STT 39:50] [STT 40:49]

합을 계산할 때 필요한 두 정보는 다음과 같다.

- 지금까지 계산한 누적값.
- 아직 더해야 하는 범위를 나타내는 위치.

**이해를 위한 예시:** `1 + 2 + 3 + 4`를 큰 수부터 더한다면 상태를 다음처럼 갱신할 수 있다. 이는 불명확한 라이브 숫자를 복원한 것이 아니라 같은 아이디어를 작은 입력에 적용한 예시다.

| 누적값 | 다음에 더할 수 | 상태의 의미 |
|---:|---:|---|
| 0 | 4 | 아직 아무것도 더하지 않았다 |
| 4 | 3 | `4`를 더했고 `1`부터 `3`까지 남았다 |
| 7 | 2 | `4 + 3`을 더했고 `1 + 2`가 남았다 |
| 9 | 1 | `4 + 3 + 2`를 더했고 `1`이 남았다 |
| 10 | 0 | 더할 수가 없으므로 누적값이 답이다 |

이 방식에서는 지금까지의 각 덧셈을 따로 보관할 필요가 없다. 이미 더한 수들이 결과에 기여한 내용은 누적값 안에 들어 있다. 다만 모든 문제에서 과거 정보를 이런 식으로 압축할 수 있다고 일반화하면 안 된다. 이 합에서는 이후 계산에 필요한 정보가 누적값과 남은 위치로 표현되기 때문에 가능하다.

강의에서 말하는 두 칸은 알고리즘의 핵심 상태에 대한 비유다. 실제 실행기의 모든 정보가 정확히 두 개의 저장 단위만 차지한다는 보장은 아니다. 숫자의 표현 크기와 실행 환경의 부가 정보까지 없어진다고 해석하지 않는다. [STT 40:49]

### Tail call(꼬리 호출): 호출 뒤에 계산이 남아 있는가

Tail call은 callee의 결과가 그대로 caller의 결과가 되는 위치에서의 호출이다. 그 위치를 tail position(꼬리 위치)이라고 한다. 판정 기준은 소스에서 호출이 마지막 줄에 보이는지가 아니라, **그 호출이 끝난 뒤 현재 함수가 결과에 대해 추가로 할 계산이 남는가**다. [STT 50:21] [STT 51:21]

자료의 일반 `sum`은 다음 expression을 계산한다.

```scala
n + sum(n - 1)
```

여기서는 `sum(n - 1)`의 결과가 곧바로 현재 함수의 결과가 아니다. 반환된 값에 `n`을 더해야 한다. 따라서 이 재귀 호출은 tail call이 아니다. 호출이 줄의 오른쪽 끝에 있어도 이 사실은 바뀌지 않는다. [M01 p.40] [STT 53:11]

반면 다음은 조건을 설명하기 위해 만든 **이해를 위한 예시**다.

```scala
def g(x: Int): Int =
  x + 1

def f(x: Int): Int =
  g(x)
```

`f`는 `g(x)`의 결과를 받아 별도의 계산을 하지 않고 그대로 반환한다. 따라서 `f` 안의 `g(x)`는 tail position에 있다. `g` 내부에서 덧셈을 한다는 사실은 문제가 아니다. 판단하는 것은 **`g`가 끝난 뒤 `f`에 남는 계산**이다.

강의의 반환 비유에서는 중간 함수가 결과를 받아 그대로 위로 전달하기만 한다면, 그 중간 단계를 거치지 않고 원래 기다리던 쪽으로 결과를 보낼 수 있다고 설명한다. `F100`이 `F99`의 결과를 그대로 반환하고, `F99`도 `F98`의 결과를 그대로 반환한다면, 중간 함수마다 별도의 후속 계산을 보존할 필요가 줄어든다. [STT 48:37] [STT 49:34] [STT 51:21]

Tail call optimization(꼬리 호출 최적화)은 이 성질을 이용해 불필요한 호출 정보의 누적을 피하도록 실행하는 것이다. 다만 tail position이라는 프로그램의 성질과, compiler(컴파일러) 또는 실행기가 실제로 그 성질을 이용하는지는 구별해야 한다. 강의에서도 남은 계산이 없는 형태로 작성했더라도 구현이 중간 반환 단계를 계속 쌓을 수 있다고 지적한다. [STT 51:21] [STT 52:19]

[[concepts/tail-call|Tail call]]의 핵심은 호출 대상의 이름이 아니다. 다른 함수를 부르더라도 결과를 그대로 반환하면 tail call이 될 수 있다. 자기 자신을 부르는 경우와 다른 함수를 부르는 경우의 구현 지원 차이는 뒤의 자료 예제에서 따로 확인한다.

### Tail recursion(꼬리 재귀)으로 바꾼 `sum`: 계산을 미루지 않고 인자에 반영하기

Tail recursion은 재귀 호출이 tail position에 놓이는 형태다. 일반 `sum`을 이 형태로 바꾸려면 재귀 호출이 돌아온 뒤 하던 덧셈을 다른 곳에서 처리해야 한다. 강의에서는 덧셈을 다음 호출 전에 수행하고, 계산한 누적값을 인자로 전달하는 방법을 구성했다. [STT 54:06] [STT 55:04] [STT 56:57]

p41의 코드는 다음과 같다.

```scala
import scala.annotation.tailrec

def sum(n: Int): Int = {
  @tailrec
  def sumItr(res: Int, m: Int): Int =
    if (m <= 0)
      res
    else
      sumItr(m + res, m - 1)

  sumItr(0, n)
}
```

`res`는 이미 계산한 누적값이고, `m`은 아직 더해야 하는 범위를 나타낸다. 시작 상태는 `sumItr(0, n)`이다. 처음에는 아무것도 더하지 않았으므로 누적값이 `0`이고, 아직 `1`부터 `n`까지 남아 있다. [M01 p.41]

`m > 0`이면 현재의 `m`을 누적값에 더하고, 남은 범위를 하나 줄여 다음 호출로 넘긴다.

$$
(\text{res},m)\longmapsto(\text{res}+m,m-1)
$$

`m <= 0`이면 더할 일이 없으므로 `res`를 그대로 반환한다. 기존 `sum`의 종료값이 `0`이었다고 해서 내부 함수도 `0`을 반환하면 안 된다. 이때의 `res`에는 이미 처리한 합이 들어 있기 때문이다. [M01 p.41] [STT 55:57]

**이해를 위한 전개:** p41의 코드를 `n = 4`에 적용하면 다음과 같다.

```text
sum(4)
→ sumItr(0, 4)
→ sumItr(4, 3)
→ sumItr(7, 2)
→ sumItr(9, 1)
→ sumItr(10, 0)
→ 10
```

일반 재귀의 `4 + (3 + (2 + (1 + 0)))`와 비교하면, 덧셈을 언제 수행하는지가 달라졌다. 일반 재귀는 작은 호출의 결과를 기다린 뒤 더한다. 이 코드는 다음 호출을 하기 전에 누적값을 갱신한다. `sumItr`의 인자들은 Call-by-value이므로 `m + res`와 `m - 1`을 먼저 계산하고 그 값들을 전달한다. [M01 p.19] [M01 p.41] [STT 56:57]

그 결과 `sumItr(...)`가 반환한 뒤 현재 호출에서 할 덧셈이 없다. 작은 호출의 결과가 그대로 현재 호출의 결과가 된다. 이것이 [[concepts/tail-recursion|Tail recursion]]으로 바뀐 이유이며, 인자를 두 개로 늘렸다는 사실 자체가 최적화 조건은 아니다.

이 변환이 같은 합을 계산하는 이유는 다음 관계로 확인할 수 있다. **아래 식은 자료 코드에서 도출한 설명용 불변식이며, 강의 발화를 그대로 복원한 수식은 아니다.** `n`이 음이 아닌 정수이고 계산 중 숫자 범위를 넘지 않는다고 가정한다.

$$
\text{res}+\sum_{k=1}^{m}k=\sum_{k=1}^{n}k
$$

처음에는 `res = 0`, `m = n`이므로 성립한다. 다음 상태에서는 다음 등식이 성립한다.

$$
(\text{res}+m)+\sum_{k=1}^{m-1}k
=
\text{res}+\sum_{k=1}^{m}k
$$

현재 항 `m`을 남은 합에서 누적값으로 옮겼을 뿐 전체 합은 변하지 않는다. 마지막에 `m = 0`이 되면 남은 합이 없어지므로 `res`가 원래 구하려던 합이다. 자료 코드에서 음수 입력은 첫 종료 조건에 걸려 `0`을 반환하며, 위의 합 설명은 `n >= 0`에 대한 것이다.

코드의 `@tailrec`은 의도한 tail-recursion 최적화가 가능한지 compiler가 확인하도록 하는 표기다. 자료에서는 `scala.annotation.tailrec`을 가져와 내부 함수에 붙인다. 강의는 tail recursion으로 작성하려던 의도와 실제 코드가 어긋났을 때 컴파일 오류로 알아차리기 위해 이 표기를 사용하는 것을 권한다. [M01 p.41] [STT 01:04:35] [STT 01:05:32]

예를 들어 다음은 **이해를 위한 잘못된 변형**이다.

```scala
sumItr(m + res, m - 1) + 1
```

재귀 호출이 돌아온 뒤 `1`을 더해야 하므로 원래의 tail-recursive 구조가 깨진다. `@tailrec`은 이런 계산을 자동으로 재설계하여 올바른 누적 형태로 바꾸는 장치가 아니다. 또한 표기를 생략했다고 반드시 최적화가 꺼지는 것도 아니다. 강의에서 강조한 역할은 최적화 가능한 재귀로 작성하려는 의도를 검사받는 것이다.

내부 함수 `sumItr`를 `sum`의 Block 안에 둔 구조는 앞의 `sqrt`와도 같은 원리를 사용한다. 외부에는 `sum(n)`을 제공하고, 누적값과 남은 위치를 다루는 보조 함수는 내부에 둔다. 이는 외부 호출자가 시작 누적값을 직접 정할 필요를 없앤다. [M01 p.41] [STT 01:03:37]

라이브 설명에서는 자료와 다른 인자 이름과 함수 이름이 사용되며, 일부 순서와 숫자가 불분명하다. 여기서는 자료에서 확인되는 `sumItr(res, m)`과 초기 호출 `sumItr(0, n)`을 사용했다. 이를 녹음의 정확한 식별자와 인자 순서를 복원한 것으로 보지 않는다.

### Tail call optimization의 효과와 구현 지원은 별도로 판단하기

Tail-recursive `sum`의 장점은 호출이 깊어질 때 남은 덧셈을 위한 복귀 정보를 계속 쌓지 않아도 되는 구조라는 점이다. 해당 최적화가 적용되면 반복 횟수가 늘어도 그에 비례하는 call stack을 유지할 필요가 없어진다. 그러나 `n`개의 항을 하나씩 더하는 계산 과정 자체가 사라지는 것은 아니다. [STT 40:49] [STT 51:21] [M01 p.41]

이를 다음 세 질문으로 나누어 이해할 수 있다.

| 판단 대상 | 확인할 내용 |
|---|---|
| 프로그램의 형태 | 호출 뒤에 추가 계산이 남는가? |
| 구현의 지원 | 그 형태를 실제로 최적화하는가? |
| 효과의 범위 | 줄어드는 것이 호출 저장 공간인가, 다른 자원도 포함하는가? |

첫 질문에 올바르게 답해도 둘째 질문의 답이 자동으로 정해지는 것은 아니다. 강의에서는 Python을 tail call 형태의 코드를 써도 그 최적화를 해 주지 않는 사례로 들었다. 이어 반복문이 더 읽기 쉽다는 견해와 재귀 사용에 관한 설계 취향을 소개했다. 이 부분은 **강의에서 전달한 정책 설명과 평가**로 읽어야 하며, 특정 설계자의 검증된 직접 인용이나 모든 Python 구현에 대한 독립 확인으로 확대하지 않는다. [STT 43:09] [STT 44:09] [STT 45:19]

학습상 확인할 점은 같은 상태 갱신을 반복문으로도, 인자 전달을 이용한 재귀로도 표현할 수 있다는 것이다. 어느 표현을 더 읽기 쉽다고 느끼는지는 평가의 문제이고, stack이 실제로 줄어드는지는 구현 동작의 문제다. 강의도 두 상태를 인자로 전달하는 형태가 반복문의 상태 갱신과 연결된다고 설명한다. [STT 45:53]

또한 최적화로 모든 자원 문제가 해결된다고 결론 내리면 안 된다. 이 강의에서 직접 다루는 효과는 불필요한 호출 정보의 누적으로 인한 stack 증가를 피하는 것이다. 전체 실행 시간, 다른 자료의 저장 공간, 숫자 표현 범위까지 자동으로 해결하는 성질은 아니다. [STT 01:01:52] [STT 01:02:54]

메모리 관리에 관한 후반 STT에는 기술용어를 확정하기 어려운 표현이 남아 있다. 그 부분을 특정 메모리 관리 기법의 완전한 설명으로 복원하지 않는다. 정확한 용어와 세부 주장은 검증 필요다. [STT 01:02:54] [STT 01:03:37]

### Integer overflow(정수 표현 범위 초과)는 Stack overflow와 다르다

Integer overflow는 계산 결과가 사용하는 정수 표현 범위를 벗어나는 문제다. Stack overflow는 끝나지 않은 호출을 보존할 공간의 문제다. 둘은 이름에 `overflow`가 들어가지만 초과하는 대상이 다르다. [STT 22:39] [STT 35:32] [STT 01:00:39]

후반의 Scala 시연에서는 출력값을 확인하고 디버깅하는 과정에서 integer overflow가 언급된다. 강의에서는 음수가 나오는 현상을 이 문제로 설명한다. 여기서 배울 구별은 tail recursion으로 호출 구조를 바꾸어도 숫자의 표현 범위까지 넓어지지는 않는다는 것이다. [STT 59:04] [STT 01:00:39]

| 비교 항목 | Stack overflow | Integer overflow |
|---|---|---|
| 부족하거나 초과하는 대상 | 호출 정보를 위한 공간 | 정수를 표현하는 범위 |
| 이번 강의의 연결 사례 | 깊은 일반 재귀의 `sum` | 큰 합을 계산한 뒤의 숫자 결과 |
| tail-call 최적화와의 관계 | 적용되면 해당 호출 누적을 줄일 수 있다 | 숫자 표현 범위를 자동으로 늘리지 않는다 |
| `BigInt` 언급과의 관계 | 호출 구조 자체는 그대로일 수 있다 | 숫자 표현 문제를 따로 다루려는 맥락이다 |

강의 초반의 `BigInt` 비교를 다시 보면 두 방향의 오해를 피할 수 있다. 숫자 표현을 바꾸었다고 재귀 깊이가 없어지지 않으며, 호출 저장을 줄였다고 숫자 범위 문제가 없어지지도 않는다.

다만 이번 시연의 정확한 입력과 화면 출력값은 STT만으로 완전히 확인되지 않는다. 따라서 특정 값이 관찰되었다고 새로 확정하거나 실행 시간을 측정 결과처럼 기록하지 않는다. C와 반복문을 든 비교도 숫자 범위 문제를 고려해야 한다는 취지로 읽으며, 서로 다른 언어와 자료형에서 범위 초과의 세부 결과가 모두 동일하다고 확정하지 않는다. [STT 01:00:39]

### Mutual Recursion(상호 재귀): 다른 함수를 호출해도 Tail call이 될 수 있다

Mutual Recursion은 여러 함수가 서로를 호출하는 재귀 구조다. `sum`이 `sum2`를 부르고 `sum2`가 다시 `sum`을 부르는 경우가 해당한다. Tail call의 조건은 자기 자신을 부르는지가 아니라 호출 뒤에 계산이 남는지이므로, 상호 호출에서도 tail position을 판별할 수 있다. [M01 p.42] [STT 01:06:32] [STT 01:07:23]

p42의 코드는 다음과 같다.

```scala
{
  def sum(acc: Int, n: Int): Int =
    if (n <= 0)
      acc
    else
      sum2(n + acc, n - 1)

  def sum2(acc: Int, n: Int): Int =
    if (n <= 0)
      acc
    else
      sum(2 * n + acc, n - 1)

  sum(0, 20000) // 자료의 stack overflow 사례
}
```

각 호출에서는 다음 인자 값을 먼저 계산한 뒤 다른 함수를 부른다. `sum2(...)` 또는 `sum(...)`가 끝난 뒤 현재 함수가 추가로 수행할 연산은 없다. 따라서 두 호출 모두 tail position에 있다. 그런데 자료는 이 직접적인 상호 재귀 코드에 stack overflow 사례를 표시한다. 이는 **tail position의 성립과 실제 최적화 지원을 구별해야 하는 자료상의 사례**다. 모든 환경에서 동일한 입력이 동일하게 실패한다고 일반화하는 뜻은 아니다. [M01 p.42]

이 예제를 앞의 일반 합과 혼동하면 계산 결과도 잘못 해석하게 된다. `sum`은 현재 `n`을 더하지만, `sum2`는 `2 * n`을 더한다. 함수가 바뀔 때 더하는 항의 계수도 번갈아 바뀐다.

**이해를 위한 작은 입력 전개:** 자료 코드에 `sum(0, 4)`를 적용하면 다음과 같다.

```text
sum(0, 4)
→ sum2(4, 3)
→ sum(10, 2)
→ sum2(12, 1)
→ sum(14, 0)
→ 14
```

계산한 것은 `4 + 2*3 + 2 + 2*1`이다. 일반적인 `1 + 2 + 3 + 4 = 10`과 다르다. 이 차이는 오류가 아니라 p42에 제시된 두 함수의 정의에서 나온다. [M01 p.42]

따라서 [[concepts/mutual-recursion|Mutual Recursion]]을 읽을 때는 함수 이름만 번갈아 적지 말고, 각 함수가 다음 인자를 어떻게 만드는지도 추적해야 한다. 또 자기 재귀에 사용한 `@tailrec`을 상호 재귀에도 붙이기만 하면 같은 지원을 얻는다고 추정하지 않는다.

### `TailCalls` 코드: 완료된 결과와 다음 계산을 구분하여 표현하기

p43은 p42와 같은 상호 호출 계산을 다른 표기로 제시한다. 먼저 `scala.util.control.TailCalls._`를 가져오고, 두 함수의 반환형을 `Int` 대신 `TailRec[Int]`로 적는다. 기저 결과는 `done(...)`, 다음 계산은 `tailcall(...)`로 표현하고, 바깥에서 `.result`로 최종 결과를 얻는다. [M01 p.43]

```scala
import scala.util.control.TailCalls._

{
  def sum(acc: Int, n: Int): TailRec[Int] =
    if (n <= 0)
      done(acc)
    else
      tailcall(sum2(n + acc, n - 1))

  def sum2(acc: Int, n: Int): TailRec[Int] =
    if (n <= 0)
      done(acc)
    else
      tailcall(sum(2 * n + acc, n - 1))

  sum(0, 20000).result
}
```

이 코드를 읽을 때는 계산 규칙과 실행 표현을 구별한다. `sum`에서 `n`을 더하고 `sum2`에서 `2 * n`을 더하는 규칙은 그대로다. 바뀐 부분은 결과와 다음 호출을 나타내는 방식이다. [M01 p.42] [M01 p.43]

| 표기 | 자료 코드에서의 역할 |
|---|---|
| `TailRec[Int]` | 최종적으로 `Int` 결과를 얻는 계산의 반환형 |
| `done(acc)` | 더 진행할 호출이 없이 누적값으로 끝나는 경우 |
| `tailcall(...)` | 다음 상호 호출을 이어 가는 경우 |
| `.result` | 바깥에서 해당 계산의 최종 결과를 얻는 표기 |

`done(acc)`는 다음 단계가 없다는 점에서 중요하다. 반대로 `tailcall(...)`은 아직 이어 갈 계산이 있음을 표현한다. 바깥의 `.result`는 내부의 매 단계에 붙이는 표기가 아니라 자료처럼 전체 계산의 결과를 얻는 위치에 둔다. [M01 p.43]

**이해를 위한 작은 입력 예시:** 같은 코드에서 바깥 호출을 `sum(0, 4).result`로 바꾸면 앞서 추적한 누적 규칙에 따라 `14`를 얻는 계산이 된다. 일반 합인 `10`으로 바뀌는 것이 아니다. 새로운 표기는 다른 수학적 문제를 푸는 것이 아니라, 같은 상호 호출 계산을 지원되는 방식으로 표현한다.

이 설명은 자료 코드에 나타난 표기를 읽기 위한 보충이다. STT에는 모든 이름이 또렷하게 기록되어 있지 않으므로, `TailRec`, `done`, `tailcall`, `.result` 각각을 명확히 발화했다고 주장하지 않는다. 또한 이 코드만으로 라이브러리 내부 구조나 모든 메모리 사용 특성을 새로 단정하지 않는다. [STT 01:08:18] [STT 01:11:44] [M01 p.43]

### Compiler 관련 가설: 확인된 코드 차이와 설명의 확실성을 구분하기

강의 후반에는 자기 tail recursion과 다른 함수로 향하는 tail call의 지원 차이를 왜 두는지에 관한 설명이 이어진다. 여기서는 관찰 가능한 자료의 코드 차이와 그 차이를 설명하려는 가설의 지위를 구분해야 한다. [STT 01:08:18]

자료에서 확인할 수 있는 것은 p41의 자기 재귀 코드, p42의 직접적인 상호 재귀와 stack overflow 사례, p43의 `TailCalls`를 사용한 표현이다. 반면 변환 과정에서 추가 작업이 남을 수 있다는 설명, 자기 함수의 코드를 compiler가 통제하기 더 쉬울 것이라는 설명, 개발 편의나 구현 비용에 관한 평가는 강의 중 제시한 구현 가설에 해당한다. 교수는 이 설명이 자신의 예상임을 명시했다. [M01 p.41] [M01 p.42] [M01 p.43] [STT 01:09:09] [STT 01:10:03] [STT 01:10:56]

따라서 해당 발언을 Scala의 정확한 컴파일 경로나 compiler 내부 구조에 관한 검증된 사실로 기록하지 않는다. 이 부분은 **검증 필요인 구현 가설**로 남긴다. 다른 언어들이 일반적으로 모두 같은 최적화를 자동 수행한다는 식의 일반화도 이번 자료만으로 확정하지 않는다.

그 가설의 참거짓과 별개로 프로그램에서 tail position을 판별하는 질문은 분명하다. 호출 결과를 받은 뒤 현재 함수에 추가 계산이 남는지 확인하는 것이다. 마지막 기록 구간에서도 교수는 tail call이 실행 과정에서 무엇을 하는지 이해해야 한다는 점을 다시 강조했다. 이는 강의에서 확인되는 학습상 강조이며, 특정 평가 문항이나 출제 예고를 뜻하지 않는다. [STT 01:12:25]

이번 녹음에서 유보된 것은 Call-by-name의 environment 문제를 완전히 해결하는 구현 설명이다. 후반의 마지막 기록 역시 tail call에 관한 논의이므로, 다음 장의 내용을 이미 학습한 것으로 이어 붙이지 않는다. [STT 16:59] [STT 01:12:25]

## 강의 흐름과 연결

### Block에서 인자 평가로: 이름을 찾는 위치와 계산 시점의 연결

[[courses/principles_of_programming/lectures/2026-09-08-lecture-03|이전 강의: 9월 8일 강의]]와 연결되는 출발점은 [[concepts/block|Block]]과 [[concepts/environment|environment]]다. 도입의 Block 실행과 `sqrt` 내부 함수는 이전 내용을 복습한 부분이다. 자료의 실행표와 코드는 이 복습을 구체화하는 근거이며, 각 페이지의 모든 내용을 이번에 새로 강의했다는 뜻은 아니다. [STT 01:42] [STT 02:13] [STT 03:06]

이 복습은 [[concepts/call-by-name|Call-by-name]]의 미완성 문제로 이어진다. 인자 평가를 미뤄도 이름을 해석할 environment는 보존해야 한다. 함수 body와 인자 expression의 출발점이 다르다는 점까지 설명했고, 이를 완전히 구현하는 방법은 뒤로 미뤘다. [STT 07:07] [STT 08:03] [STT 16:59]

[[concepts/lazy-evaluation|Lazy call-by-value]]에서는 질문이 평가의 **시점과 횟수**로 옮겨 간다. Call-by-name으로 평가를 미루고 `lazy val`로 최초 결과를 재사용하는 조합이 중심이다. 이후 누적형 `sum`에서도 [[concepts/call-by-value|Call-by-value]]가 다시 등장한다. 다음 호출에 넘길 누적값을 먼저 계산한다는 점이 Tail recursion의 작동과 연결된다. [M01 p.37] [M01 p.41] [STT 56:57]

### Recursion에서 Tail call로: 남겨 두는 계산의 연결

후반부의 출발점은 간결한 `sum`이 큰 입력에서 실패하는 현상이다. [[concepts/recursion|Recursion]]을 Substitution으로 펼치면 작은 호출의 결과를 기다리는 덧셈이 드러나고, 그 덧셈을 재개할 정보가 [[concepts/continuation|continuation]]과 [[concepts/call-stack|call stack]] 설명으로 이어진다. [STT 24:39] [STT 26:48] [STT 32:41]

종이 비유와 지우개 비유는 같은 합을 계산하면서도 **보존하는 정보가 달라질 수 있음**을 연결한다. 여기서 얻은 누적값과 남은 위치를 함수 인자로 전달하면 [[concepts/tail-recursion|Tail recursion]]의 구성 원리가 된다. [STT 28:55] [STT 38:27] [STT 55:04]

마지막에는 [[concepts/tail-call|Tail call]]의 조건을 자기 호출 밖으로 확장하여 [[concepts/mutual-recursion|Mutual Recursion]]을 살펴본다. 이 단계에서는 프로그램의 tail position과 실제 최적화 지원을 따로 판단해야 한다. p42와 p43의 차이는 그 구별을 읽는 자료상의 사례다. [M01 p.42] [M01 p.43]

## 핵심 요약

- **Block(블록)과 environment(환경):** Block의 마지막 expression이 전체 값을 정한다. 함수 body의 외부 이름은 함수가 정의된 environment에서 찾는다. 내부의 같은 이름이 외부 정의를 변경하는 것은 아니다. [M01 p.28] [M01 p.29]
- **내부 함수:** `sqrt`와 `sum`의 보조 함수를 Block 안에 두면 외부 호출에 필요한 기능을 유지하면서 구현용 이름의 범위를 제한한다. [M01 p.35] [M01 p.41]
- **Call-by-value와 Call-by-name:** 전자는 인자를 먼저 계산하고, 후자는 필요할 때 계산한다. 평가를 미루는 것과 올바른 environment에서 이름을 찾는 것은 별개의 요구사항이다. [M01 p.17] [STT 07:07]
- **Lazy call-by-value:** 정상적으로 끝나는 계산에서 사용하지 않으면 평가하지 않고, 사용하면 최초 결과를 재사용한다. p37의 출력 횟수는 `true`에서 0회, `false`에서 1회다. [M01 p.37]
- **Recursion과 continuation:** `n + sum(n - 1)`은 반환 후 덧셈이 남는다. 작은 입력으로 내려가는 동안에도 끝나지 않은 호출의 저장 공간은 증가할 수 있다. [M01 p.40] [STT 32:41]
- **Tail call과 Tail recursion:** 호출 결과가 그대로 현재 함수의 결과가 되는지가 기준이다. 누적형 `sum`은 덧셈을 다음 호출 전에 수행한다. `@tailrec`은 이 의도를 검사하며 임의의 재귀를 자동으로 재설계하지 않는다. [M01 p.41] [STT 01:05:32]
- **두 종류의 overflow:** Stack overflow는 호출 정보를 위한 공간의 문제이고, Integer overflow는 숫자의 표현 범위 문제다. 어느 한쪽을 해결했다고 다른 쪽도 해결되는 것은 아니다. [STT 22:39] [STT 01:00:39]
- **Mutual Recursion과 구현 지원:** 다른 함수를 부르는 호출도 tail position일 수 있다. p43의 `TailCalls` 표기는 p42의 누적 규칙을 유지한다. compiler 관련 이유 설명은 강사가 제시한 가설로 남긴다. [M01 p.42] [M01 p.43] [STT 01:10:03]

## 회상·연습문제

### 능동회상

답을 열기 전에 결과뿐 아니라 그 결과를 결정하는 규칙을 먼저 말해 본다.

#### Q01. Block 내부에서 호출한 함수는 어느 environment의 외부 이름을 사용하는가?

<details><summary>정답</summary>

함수가 정의된 environment를 기준으로 외부 이름을 찾는다. 호출 장소의 environment로 바꾸지 않는다. p32에서는 내부 `t = 10`이 있어도 `f`의 `t`는 외부의 `0`이므로 `f(5) = 36`이다.

Block 내부 계산이 끝나면 마지막 expression의 값을 기다리던 계산에 돌려준다. [M01 p.28] [M01 p.29] [M01 p.32]

</details>

#### Q02. `sqrt`의 보조 함수를 내부 Block으로 옮기면 무엇이 바뀌고 무엇을 계속 계산하는가?

<details><summary>정답</summary>

외부에는 `sqrt`를 제공하고 `sqrtIter`, `isGoodEnough`, `improve`의 이름은 내부에 제한한다. 보조 함수의 계산은 계속 수행한다. 마지막 `sqrtIter(1, x)`의 결과가 `sqrt`의 결과이며, `ratio`는 검사 함수 내부의 중간값이다. [STT 03:06] [M01 p.35]

</details>

#### Q03. 사용하지 않는 인자와 두 번 사용하는 인자는 Call-by-value·Call-by-name에서 어떻게 다른가?

<details><summary>정답</summary>

정상적으로 끝나는 인자 계산을 가정하면 Call-by-value는 body 진입 전에 한 번 평가한다. Call-by-name은 사용하지 않으면 0번, 두 번 필요해지면 두 번 평가한다.

`val`은 선언에 도달했을 때 expression을 평가한 값을 연결한다. `def`는 정의를 연결하며 이후 사용에서 expression을 평가한다. Scala 자료에서는 일반 인자가 Call-by-value이고 `=>`가 붙은 인자가 Call-by-name이다. [M01 p.17] [M01 p.18] [M01 p.19] [M01 p.20]

</details>

#### Q04. Call-by-name을 인자 자리에 expression만 넣는 방식으로 설명하면 무엇이 빠지는가?

<details><summary>정답</summary>

그 expression의 이름을 어느 environment에서 해석할지가 빠진다. 함수 body의 외부 이름은 함수의 정의 environment에서, 호출자가 작성한 인자식의 이름은 호출 장소의 environment에서 해석해야 한다.

이번 강의는 이 구별을 설명했지만 완전한 구현 방법은 뒤로 미뤘다. [STT 07:07] [STT 08:03] [STT 16:59]

</details>

#### Q05. Lazy call-by-value에서 최초 사용 전후로 무엇이 달라지는가?

<details><summary>정답</summary>

최초 사용 전에는 평가를 미뤄 둔다. 처음 필요해지면 expression을 평가하고 결과를 저장하며, 이후 사용에서는 그 값을 재사용한다. 한 번도 사용하지 않으면 평가하지 않는다.

저장된 결과의 재사용은 해당 `lazy val` 연결에 관한 것이다. 서로 다른 함수 호출이 만든 모든 연결이 하나의 결과를 공유한다는 뜻은 아니다. [M01 p.37]

</details>

#### Q06. p37의 `lazy val iv = i`를 `val iv = i` 또는 `def iv = i`로 바꾸면 출력 횟수는 어떻게 되는가?

<details><summary>정답</summary>

`i`는 계속 Call-by-name으로 받고, 연결 선언은 `if` 앞에 있다고 가정한다.

| 연결 | `c = true` | `c = false` |
|---|---:|---:|
| `val iv = i` | 1회 | 1회 |
| `def iv = i` | 0회 | 3회 |
| `lazy val iv = i` | 0회 | 1회 |

`val`은 선언 도달 시 평가하고, `def`는 사용 때마다 평가하며, `lazy val`은 최초 결과를 재사용한다. 이 결과는 자료 코드의 동작이다. STT 15:05의 손상된 부정 표현을 복원한 발화가 아니다. [M01 p.20] [M01 p.37]

</details>

#### Q07. 간결한 recursive `sum`이 큰 입력에서 실패하면 어떤 세 질문을 나눠야 하는가?

<details><summary>정답</summary>

계산 단계가 얼마나 필요한지, 숫자가 표현 범위에 들어가는지, 끝나지 않은 호출을 저장할 공간이 충분한지 나눈다.

Functional Programming의 짧은 정의만으로 실행 공간을 판단할 수 없다. `BigInt`로 숫자 표현을 바꾸어도 대기 중인 호출 구조는 그대로일 수 있다. [M01 p.6] [M01 p.39] [STT 19:36] [STT 22:39]

</details>

#### Q08. `sum(3)`을 Substitution으로 펼칠 때 무엇이 쌓이며, 종이 비유는 어떤 실패를 설명하는가?

<details><summary>정답</summary>

`3 + sum(2)`에서 바깥의 `3 + …`가 남고, 다음에는 `2 + …`, 이어 `1 + …`도 결과를 기다린다. 기저값을 얻은 뒤 안쪽부터 덧셈을 끝낸다.

종이 비유는 시간이 충분하더라도 끝나지 않은 작업을 기록할 공간이 먼저 부족할 수 있음을 설명한다. [M01 p.40] [STT 26:48] [STT 28:55]

</details>

#### Q09. continuation과 call stack은 어떻게 구별하는가?

<details><summary>정답</summary>

Continuation은 결과를 받은 뒤 이어서 수행할 계산이다. Call stack은 강의에서 호출별 복귀 정보를 쌓아 보존하는 구조로 설명된다.

보존할 정보에는 돌아갈 코드 위치, caller의 environment, 받은 결과로 계속할 작업이 포함된다. 같은 함수 정의를 사용하더라도 각 호출의 대기 상태는 다를 수 있다. [STT 32:41] [STT 33:56]

</details>

#### Q10. 일반 Recursion을 사용할 때 왜 최대 입력과 실행 환경을 함께 확인해야 하는가?

<details><summary>정답</summary>

가능한 호출 깊이가 실행 환경의 stack 용량 안에 충분히 제한되어야 하기 때문이다. 작은 입력에서 성공하거나 컴퓨터 전체 메모리가 많다는 사실만으로 깊은 호출의 안전성이 보장되지 않는다.

수학적으로 종료하는 함수도 종료 조건에 도달하기 전에 Stack overflow가 발생할 수 있다. 강의의 특정 호출 횟수를 보편적 안전 한도로 외우지 않는다. [STT 35:32] [STT 37:27]

</details>

#### Q11. 지우개 비유의 두 상태는 무엇이며, 두 상태만 있다는 말의 한계는 무엇인가?

<details><summary>정답</summary>

이미 계산한 누적값과 아직 계산해야 할 범위를 나타내는 위치다. 이전 상태를 다음 상태로 바꾸어 대기 덧셈 목록을 계속 늘리지 않는다는 뜻이다.

실제 실행 전체가 정확히 두 개의 저장 단위만 사용하거나 숫자의 표현 크기까지 사라진다는 보장은 아니다. [STT 38:27] [STT 40:49]

</details>

#### Q12. Tail call을 판별하는 기준은 무엇이며, 다른 함수를 불러도 성립하는가?

<details><summary>정답</summary>

호출이 끝난 뒤 현재 함수에 추가 계산이 남는지를 본다. callee의 결과를 그대로 반환하면 tail position의 호출이다. 다른 함수를 불러도 성립할 수 있다.

`n + sum(n - 1)`에서는 반환 후 `n`을 더하므로 해당 호출은 tail call이 아니다. 자기 재귀 호출에 이 조건이 성립하는 형태가 Tail recursion이다. [STT 51:21] [STT 53:11] [STT 01:06:32]

</details>

#### Q13. `sumItr(res, m)`의 시작·전이·종료 상태를 설명하라.

<details><summary>정답</summary>

시작은 `sumItr(0, n)`이다. `m > 0`이면 새 누적값 `m + res`와 새 위치 `m - 1`을 먼저 계산하여 전달한다. `m <= 0`이면 `res`를 반환한다.

숫자 범위를 넘지 않는 음이 아닌 입력에서는 다음 관계가 유지된다.

$$
res+\sum_{k=1}^{m}k=\sum_{k=1}^{n}k
$$

이는 자료 코드에서 도출한 설명용 관계다. [M01 p.41]

</details>

#### Q14. `@tailrec`은 무엇을 보장받으려는 표기인가?

<details><summary>정답</summary>

의도한 Tail recursion 최적화가 가능한 코드인지 compiler가 검사하도록 한다. 조건을 충족하지 못하면 컴파일 오류로 의도와 코드의 불일치를 확인한다.

임의의 재귀 알고리즘을 올바른 누적형으로 바꾸는 기능이 아니다. 표기가 없다는 사실만으로 최적화가 반드시 꺼진다고 단정해서도 안 된다. [M01 p.41] [STT 01:05:32]

</details>

#### Q15. Tail position에 호출을 쓰면 모든 자원 문제가 해결되는가?

<details><summary>정답</summary>

실제 구현이 해당 호출을 최적화해야 stack 누적을 줄일 수 있다. 적용되더라도 계산 단계의 수, 다른 자료의 저장 공간, 숫자 표현 범위가 모두 해결되는 것은 아니다.

Python과 코드 가독성에 관한 부분은 강사가 전달한 정책 설명과 평가로 구분한다. 이를 모든 구현의 동작이나 특정 설계자의 검증된 직접 인용으로 확대하지 않는다. [STT 43:09] [STT 45:53] [STT 01:02:54]

#### Q16. Tail recursion으로 바꾼 뒤 숫자 결과가 이상하면 Stack overflow라고 판단해도 되는가?

<details><summary>정답</summary>

#### Q17. p43의 `TailRec[Int]`, `done`, `tailcall`, `.result`는 각각 무엇을 나타내는가?

| `def iv = i` | 0회 / `0` | 3회 / `64000000` |
| `lazy val iv = i` | 0회 / `0` | 1회 / `64000000` |

반환값의 계산은 다음과 같다.

$$
400^3=400\times400\times400=64{,}000{,}000
$$

```text

→ 3 + sum(2)
→ 3 + (2 + sum(1))
→ 3 + (2 + (1 + sum(0)))
→ 3 + (2 + (1 + 0))
→ 6
```

| B | 이번 강의에서 Call-by-name의 environment 문제를 해결하는 구현 전체를 완성했다. |
| C | Scala의 정확한 컴파일 과정 때문에 상호 Tail call이 지원되지 않는 이유가 증명되었다. |
| D | 학생 질문 감소의 원인이 AI 사용이라는 인과관계가 확인되었다. |
| E | 마지막 기록 구간에서 p44 이후의 후속 장까지 강의한 것이 확인된다. |
| F | Tail call의 작동을 이해해야 한다는 강조가 있었으므로 특정 시험 문항의 출제가 확정된다. |

3. **새 변형:** 이번 강의의 학습 동기와 남은 질문을 세 문장 이내로 다시 작성하라. 개인 숙달도나 출제 확률은 포함하지 않는다.

<details><summary>풀이와 채점 포인트</summary>

코드의 호출 위치와 상태 전이는 자료를 따라 판단할 수 있다. 그러나 특정 구현이 그 구조를 어떻게 변환하고 왜 지원 범위를 정했는지는 별도의 근거가 필요한 질문이다.

- **A — 현재 근거로 설명 가능:** body는 정의 environment, 인자식은 호출 장소의 environment를 기준으로 이름을 해석해야 한다는 구별이 설명된다. [STT 07:07]
- **B — 현재 근거로 확정 불가:** 문제의 요구사항은 설명했지만 완전한 구현 해결은 뒤로 미뤘다. [STT 16:59]
- **C — 강사의 가설로 한정:** 강사는 해당 구현 이유를 자신의 예상으로 제시했다. 정확한 컴파일 경로나 내부 구조가 검증되었다고 고쳐 쓰지 않는다. [STT 01:10:03]
- **D — 강사의 개인적 예측으로 한정:** 질문 감소와 AI 사용의 관련성을 추측했으며 인과관계를 입증한 것은 아니다. [STT 17:48]
- **E — 현재 근거로 확정 불가:** 마지막 기록도 Tail call 논의다. 후속 장의 강의 완료를 추가하지 않는다. [STT 01:12:25]
- **F — 현재 근거로 확정 불가:** 개념 이해에 대한 강조와 실제 출제 예고는 다르다. [STT 01:12:25]

세 문장 답안의 예시는 다음과 같다.

함수로 간결하게 표현한 계산이 실제 실행에서 어떤 정보를 보존하는지 이해하는 것이 후반 설명의 동기다. 일반 `sum`과 누적형 `sum`을 비교하여 남은 계산과 stack 사용을 연결했다. Call-by-name의 완전한 environment 구현과 compiler 관련 가설의 사실 확인은 남은 질문이다.

**채점 포인트**

- 강사가 가설로 제시한 설명을 확정 사실로 바꾸지 않았는가?
- 현재 배운 environment 구별을 유보된 구현과 함께 보존했는가?
- 학습 동기를 실제 강의 설명에 연결했는가?
- 마지막 기록 이후의 진도, 인과관계, 시험 예고를 만들어 내지 않았는가?
