이번 강의는 Virtual Memory(가상 메모리)가 Process마다 독립적인 주소 공간을 제공하면서 Physical Memory(물리 메모리)를 공유하고 관리하는 원리를 다룬다.  
주소 변환, Cache, Page 교체를 연결한 뒤, 공유 변수 예제와 Core i7 도식에서 실제 접근 경로를 따라간다.

## 강의 내용과 설명

### Memory의 주소 범위와 Physical Memory의 용량

Memory(메모리)를 이해하는 출발점은 주소로 각 Byte(바이트)를 선택할 수 있는 거대한 배열이라는 모델이다. 프로그램은 Memory address(메모리 주소)를 통해 데이터를 지정하고, Load(적재)는 메모리 내용을 Register(레지스터)로 가져오며, Store(저장)는 Register의 내용을 메모리에 기록한다. 자료의 `ld`와 `sd` 예시는 이러한 이동 방향을 보여준다. STT 도입부의 명령어 설명은 일부 불완전하므로 정확한 발화를 복원하지 않고, 자료에서 확인되는 의미로 구분한다. [STT 01:07] [M03 p.4]

Pointer(포인터)가 표현할 수 있는 주소 범위와 실제 장착된 Physical Memory(물리 메모리)의 용량은 서로 다르다. 각 주소가 한 Byte를 가리키는 전체 64-bit 주소 모델에서는 다음과 같은 범위를 표현할 수 있다.

$$
2^{64}\text{ bytes}=16\text{ EiB}
$$

이는 프로그램이 그만큼의 DRAM을 실제로 보유한다는 뜻이 아니다. 강의는 laptop의 메모리 증설이 쉽지 않은 경우와 PC의 memory module을 교체하는 경우를 대비하며, 현실의 물리 용량이 주소 표현 범위보다 훨씬 작다는 문제를 제시한다. 자료의 `16 exabytes`는 여기서 이진 단위를 명확히 하여 16 EiB로 적었다. [STT 01:55] [STT 02:52] [M03 p.5]

문제는 여러 Process(프로세스)가 동시에 실행되면 더 뚜렷해진다. 각 Process에는 instruction이 놓이는 `.text`, 데이터를 위한 `.data`, 동적으로 확보한 데이터를 위한 Heap(힙), 지역 데이터 등을 위한 Stack(스택)이 있다. 이전 자료의 메모리 배치 그림은 global variable이 놓이는 `.data`·`.rodata`·`.bss`, local variable을 위한 user stack, 동적 할당을 위한 heap을 구분한다. 이번 강의에서는 이 배치를 출발점으로, 여러 Process의 영역을 하나의 Physical Memory에 어떻게 수용할지로 질문을 확장한다. [STT 03:50] [M01 p.11] [M03 p.6]

따라서 “주소를 표현할 수 있다”, “그 주소가 해당 Process에 사용 가능하다”, “그 주소의 데이터가 지금 DRAM에 있다”는 서로 다른 주장이다. 주소의 bit 수만으로 실제 저장 공간이나 접근 가능 여부까지 판단해서는 안 된다.

### Virtual Memory와 Indirection: 주소와 실제 위치를 분리하기

[[concepts/virtual-memory|Virtual Memory]](가상 메모리)는 Physical Memory를 추상화하여 각 Process에 자신의 메모리 공간을 제공하는 방식이다. Virtual Address(가상 주소, VA)는 Process가 사용하는 주소이고, Physical Address(물리 주소, PA)는 실제 물리 위치를 지정하는 주소다. 자료는 Virtual Memory와 Physical Memory, VA와 PA를 각각 대응시킨다. [M03 p.10]

이 구조가 필요한 이유에는 용량뿐 아니라 Protection(보호)과 Sharing(공유)이 있다. 서로 무관한 Process가 다른 Process의 데이터를 마음대로 접근해서는 안 되지만, 협업하는 Process에는 특정 데이터를 함께 사용할 방법이 필요하다. 기본적인 분리와 선택적인 공유를 동시에 제공해야 한다. [STT 04:48] [M03 p.7]

이를 가능하게 하는 원리가 [[concepts/indirection|Indirection]](간접 참조)이다. Process가 사용하는 주소와 실제 저장 위치 사이에 Mapping(대응 관계)을 두면, Process가 보는 공간의 모양을 유지하면서 아래쪽 물리 배치를 관리할 수 있다. p.8 그림에서 여러 virtual memory 상자는 각각의 Process에 속하지만, 아래의 physical memory는 공통이다. 가운데 mapping mechanism이 두 층을 연결한다. [STT 05:47] [M03 p.8]

강의에서는 이를 설명하기 위해 networking 비유를 사용했다. 서로 다른 주소 체계를 사용하는 LAN들을 연결할 때 상위의 IP address와 하위의 MAC address를 구분한다는 설명이다. 구체적으로 각 NIC가 자신의 48-bit MAC address를 갖는다는 예를 들었다. [STT 05:47] 여기서 가져올 핵심은 **상위에서 사용하는 주소 체계와 실제 하위 대상의 주소 체계를 분리한다**는 점이다. IP·MAC 관련 비유는 강의 중 설명이며, 메모리 변환이 networking과 동일한 프로토콜로 작동한다는 뜻은 아니다. 불분명한 주소 종류의 반복이나 중간 표현은 검증 필요다. [STT 05:47] [STT 06:46]

Virtual machine에 관한 비유도 같은 방향이다. 실제 장치 위에 논리적인 구성을 제공하더라도, 그 안에서 필요한 기능을 사용할 수 있다면 사용자에게 하나의 실행 환경처럼 보일 수 있다. Virtual Memory에서도 Process는 자신의 주소로 데이터를 접근하지만, 실제 접근을 수행하려면 뒤에서 VA를 PA로 변환해야 한다. [STT 08:47] [STT 09:46] [STT 10:25]

Private memory(전용 메모리 공간)를 제공한다는 말은 공유가 불가능하다는 뜻이 아니다. 기본적으로 서로 분리된 공간을 제공하고, 필요한 일부 영역만 Shared memory(공유 메모리)로 설정할 수 있다. 이 선택적인 연결을 실제로 구현하는 것이 다음의 Page 단위 Mapping이다. [STT 07:47]

### Page와 Page Table: Byte마다 변환표를 만들지 않는 이유

[[concepts/page-table|Page table]](페이지 테이블)은 VA와 PA 사이의 Mapping을 저장하는 자료구조다. 모든 Byte를 독립적으로 관리하면 대응 관계가 너무 많아지므로, 메모리를 일정 크기의 Page(페이지)로 나누어 변환한다. 강의에서는 보통의 예로 4 KB, 더 큰 Page의 예로 2 MB와 1 GB를 언급한다. 뒤의 bit 계산에서는 각각의 크기를 이진 단위로 해석한다. [STT 11:52] [M03 p.12]

주소를 Page 단위로 보면 두 부분이 필요하다.

- Virtual page number(가상 페이지 번호, VPN): 어느 virtual page에 속하는가.
- Offset(내부 위치): 그 Page의 시작점에서 몇 Byte 떨어져 있는가.

Page table은 기본 모델에서 VPN을 입력으로 받아 Physical page number(물리 페이지 번호, PPN)를 돌려준다. 표의 한 항목은 Page table entry(페이지 테이블 항목, PTE)다. 실제 PTE에는 Mapping 외에 상태와 권한 정보도 들어가지만, 우선 번호 사이의 대응부터 이해하면 된다. [STT 12:46] [STT 15:22] [M03 p.15]

p.12–13의 그림은 virtual page의 순서와 physical page의 배치가 같을 필요가 없음을 보여준다. 예를 들어 VPN 0은 PPN 2로, VPN 1은 PPN 1로, VPN 2는 PPN 5로 연결된다. Virtual space에서 이웃한 두 Page가 Physical Memory에서도 이웃해야 하는 것은 아니다. 그림의 색과 화살표는 같은 데이터가 어느 physical page에 놓였는지를 나타내며, 번호가 같다는 이유만으로 대응 관계를 정하면 안 된다. [M03 p.12] [M03 p.13]

각 Process는 자신의 Page table을 갖는다. 그러므로 VPN이라는 숫자만으로는 물리 위치를 결정할 수 없다. **어느 Process의 Page table에서 조회하는 VPN인가**까지 알아야 한다. [STT 11:52] [STT 17:16]

### VA-to-PA Translation: Page Number와 Page Base를 구분하기

[[concepts/address-translation|Address translation]](주소 변환)은 VA가 속한 Page를 찾아 PPN으로 바꾸고, Page 내부의 Offset을 유지하여 PA를 구성하는 과정이다. Virtual page와 physical page의 크기가 같은 모델에서 Page size를 $PS$라고 하면 다음과 같이 분리한다.

$$
VPN=\left\lfloor\frac{VA}{PS}\right\rfloor,\qquad
Offset=VA\bmod PS
$$

Page table $PT$가 PPN을 반환한다면 최종 식은 다음과 같다.

$$
PA=PT[VPN]\times PS+Offset
$$

곱셈이 필요한 이유는 PPN이 Byte 주소가 아니라 Page의 번호이기 때문이다. $PPN\times PS$가 해당 physical page의 시작 주소, 즉 Page base가 된다. [M03 p.14] [M03 p.15]

강의의 작은 예에서는 $PS=\texttt{0x100}=256$ bytes이고, 변환할 VA는 `0x233`이다.

| 단계 | 계산 | 의미 |
|---|---|---|
| VPN 분리 | `0x233 / 0x100 = 2`의 정수 몫 | VPN 2 선택 |
| Offset 분리 | `0x233 % 0x100 = 0x33` | Page 내부에서 `0x33` Byte 떨어짐 |
| Page table 조회 | VPN 2 → PPN 5 | 물리 Page 번호 획득 |
| Page base 계산 | `5 × 0x100 = 0x500` | PPN 5의 시작 주소 |
| PA 구성 | `0x500 + 0x33 = 0x533` | 최종 Byte 주소 |

p.14 그림의 노란 virtual page에서 노란 physical page로 이어지는 화살표를 따라가면, Page 번호는 2에서 5로 바뀌지만 작은 표식의 Page 내부 위치는 유지된다. 이것이 Offset 보존의 의미다. [STT 13:47] [STT 14:24] [M03 p.14]

**자료 수식에 대한 설명상의 보정이 두 곳 필요하다.** 첫째, p.14는 mask 결과를 곧바로 VPN 2처럼 표기하지만, 실제 계산은 다음과 같다.

```text
0x233 & 0xF00 = 0x200
(0x233 & 0xF00) >> 8 = 0x2
0x233 & 0x0FF = 0x33
```

즉 상위 부분을 남기는 mask와, 남은 bit를 번호로 만드는 shift는 구분해야 한다. 이 mask는 해당 작은 예의 주소 범위를 대상으로 한 것이다. [M03 p.14]

둘째, p.15의 인쇄식 `PA = PT[VA / PS] + VA % PS`는 같은 페이지에서 $PT$를 VPN→PPN으로 정의한 것과 맞지 않는다. $PT$가 PPN을 돌려주면 $PS$를 곱해야 한다. 반대로 $PT$가 이미 Byte 단위 Page base를 반환한다고 정의했다면 Offset만 더하는 식이 가능하다. **표의 반환값이 번호인지 주소인지 확인하는 일이 수식 암기보다 먼저다.** [M03 p.15]

이 보정은 자료의 정의와 예제 계산을 일치시키기 위한 노트상의 설명이다. STT의 불완전한 나눗셈·나머지 설명이나 Page 번호 표현을 정확한 발화로 복원했다는 뜻은 아니며, 해당 발화는 검증 필요로 남는다. [STT 13:47] [STT 15:22] [STT 16:16]

### MMU·PTBR·TLB: 변환하는 장치와 변환 정보를 구분하기

Memory Management Unit(메모리 관리 장치, MMU)은 VA-to-PA translation을 수행하는 hardware다. Page table은 Main memory(주기억장치)에 놓인 자료구조이고, MMU는 그 표를 이용해 주소를 변환한다. 따라서 MMU와 Page table은 같은 물건이 아니다. [STT 17:16] [M03 p.16]

Page table base register(페이지 테이블 기준 레지스터, PTBR)는 변환표 탐색을 시작할 위치를 제공한다. 자료의 Intel 예제에서는 이 역할을 하는 Register를 `CR3`라고 부른다. p.16 그림에서 Page table을 나타내는 작은 표가 Physical Memory 안에 있고, MMU 쪽에는 `PTBR = 0x800`이 표시되어 있다. 이는 표 전체가 Register 하나에 들어간다는 뜻이 아니라, 표의 시작점을 Register로 지정한다는 뜻이다. [STT 18:05] [M03 p.16]

주소를 변환할 때마다 Main memory의 Page table을 반복해서 읽어야 한다면, 데이터 하나를 가져오기 위해 추가 메모리 접근이 계속 발생한다. 이를 줄이는 장치가 [[concepts/tlb|TLB]](주소 변환 정보를 저장하는 캐시)다. TLB는 자주 사용하는 PTE의 변환 정보를 보관하며, Cache hit(캐시 적중)가 나면 저장된 Mapping을 사용한다. 표 전체를 담는 것이 아니라 자주 참조되는 일부 변환을 유지한다. [STT 19:02] [STT 19:55]

구분해야 할 대상은 다음과 같다.

| 대상 | 역할 |
|---|---|
| Page table | Process의 Mapping과 관련 상태를 담는 자료구조 |
| PTBR·`CR3` | Page table 탐색의 출발점 제공 |
| MMU | 주소 변환과 관련 검사를 수행하는 hardware |
| TLB | 최근 사용되는 주소 변환 정보를 빠르게 재사용 |

TLB에 들어 있는 것은 프로그램의 정수 값이나 문자 그 자체가 아니다. “이 VPN의 데이터는 어느 PPN을 통해 접근하는가”에 관한 정보다. 실제 데이터의 Cache는 뒤에서 별도로 다룬다.

2024-2 중간고사 Q4(f)는 TLB의 목적을 설명하도록 요구한다. 이 요구에는 “빠른 Cache다”라는 말보다, **어떤 정보를 저장하며 어떤 Page table 접근을 줄이는가**를 설명하는 방식으로 접근할 수 있다. 과거 문항과의 연결은 현재 강의 개념의 적용 범위를 보여주는 것이며, 현재 학기의 출제 범위나 교수자 동일성을 확정하지 않는다. [EX:sp_2024_2_midterm_q04 p.9]

### Memory Hierarchy: 속도·용량·비용을 함께 고려하기

[[concepts/memory-hierarchy|Memory hierarchy]](메모리 계층)는 작고 빠른 저장 장치와 크고 상대적으로 느린 저장 장치를 함께 사용하는 구성이다. 위쪽 장치만으로 전체 용량을 채우지 못하는 이유는 용량과 비용에 있다. 강의는 소수의 Registers, SRAM 기반 CPU cache, 더 큰 DRAM, local storage와 remote storage를 차례로 설명한다. [STT 19:55] [STT 20:56] [M03 p.17]

p.17의 피라미드에서는 위로 갈수록 작고 빠르며 Byte당 비용이 높고, 아래로 갈수록 크고 Byte당 비용이 낮아지는 경향을 읽어야 한다. 오른쪽 설명은 각 계층이 아래쪽에서 무엇을 가져오는지 보여준다. Registers는 word를, CPU cache는 cache line을, Main memory는 저장 장치에서 가져온 데이터를 보관한다.

| 계층의 예 | 강의에서 설명한 특징 | 해석할 때의 한정 |
|---|---|---|
| Registers | CPU 가까이에 있으며 수가 적고 매우 빠름 | 전체 메모리를 대신할 만큼 크지 않음 |
| SRAM cache | 빠른 접근을 제공하지만 큰 용량은 비쌈 | 모든 cache level의 지연이 같지는 않음 |
| DRAM | 수십 GB 등 더 큰 용량을 제공 | 강의의 수십 ns·약 100 cycles는 비교용 설명 |
| SSD | 기계적 탐색 없이 flash에 접근 | 강의에서는 microsecond 규모로 대비 |
| HDD | Seek time·rotational delay 같은 기계적 비용 | 강의에서는 millisecond 규모로 대비 |
| Remote storage | network를 통해 데이터에 접근 | local storage보다 언제나 느리다는 규칙은 아님 |

구체적인 비교에서 강의는 Registers를 1 cycle 미만, SRAM 기반 CPU cache를 1 cycle 또는 몇 cycles 수준으로 설명하고, DRAM을 약 100 cycles로 대비했다. [STT 19:55] [STT 20:56] [STT 23:48]

이 수치들은 강의에서 규모를 비교하기 위해 사용한 예이며, 모든 장치에 적용되는 측정 결과가 아니다. 따라서 이를 모든 L1·L2·L3 cache의 동일한 지연이나 공통 상한으로 해석해서는 안 된다. 또한 피라미드 왼쪽의 `L0`–`L5`는 전체 hierarchy의 층 번호다. 그 안의 CPU `L1/L2/L3 cache` 명칭과 혼동하면 그림의 “L3”가 Main memory인지 CPU cache인지 잘못 읽게 된다. [STT 21:58] [STT 23:48] [STT 24:46] [M03 p.17]

### Storage Disaggregation: 멀리 있다는 사실만으로 속도를 결정할 수 없다

강의는 hierarchy 그림을 설명하면서 Storage disaggregation(저장 자원 분리) 사례를 덧붙인다. Compute node에는 CPU와 memory를 두고, disk storage는 network 너머에 모아 놓는 구성이다. OS에는 disk를 사용하는 것처럼 보이지만, 실제 I/O 데이터는 network를 통과한다. [STT 22:55]

이 구조의 동기는 저장 장치를 한곳에서 관리하고 교체하며 규모를 조정하기 쉽다는 데 있다. 각 compute node의 내부 장치를 따로 관리하는 대신 storage를 모아 두면, 고장이나 용량 변화에 대응하는 방식도 달라진다. 이 사례는 앞의 Indirection과도 연결된다. 사용하는 쪽에 제공되는 장치의 모습과 실제 데이터가 이동하는 경로가 반드시 같지는 않다. [STT 22:55] [STT 23:48]

강의에서는 network가 빨라지면 remote에서 데이터를 가져오는 편이 어떤 local disk보다 빠른 경우도 있다고 설명했다. 그러므로 피라미드에서 local storage가 remote storage보다 위에 있다는 이유만으로 절대적인 속도 순서를 만들면 안 된다. 장치 종류와 연결 조건을 함께 봐야 한다. [STT 24:46] [STT 25:38]

다만 STT의 network 전송률 단위와 remote swap에 관한 일부 표현은 불명확하다. 정확한 속도나 특정 시스템의 구성을 확정하는 근거로 쓰지 않으며 **검증 필요**다. Tape의 보급 정도를 언급한 문장 역시 이 자료만으로 확정하지 않는다.

### Locality of Reference: 작은 Cache가 효과적인 이유

[[concepts/locality|Locality of Reference]](참조 지역성)는 프로그램의 접근이 모든 위치에 균등하게 분산되기보다 시간이나 주소상 가까운 곳에 집중되는 경향이다. 자료에서는 두 가지를 구분한다. [M03 p.18]

- Temporal locality(시간 지역성): 최근 참조한 항목을 가까운 미래에 다시 참조하는 경향.
- Spatial locality(공간 지역성): 주소가 가까운 항목들을 시간적으로 가깝게 참조하는 경향.

p.18의 배열 합산 코드는 data와 instruction 양쪽에서 이 차이를 보여준다. 아래는 자료에 제시된 계산 구조이며, 배열 범위가 유효하고 합이 사용한 정수형의 표현 범위를 벗어나지 않는 상황을 전제로 읽는다.

```c
sum = 0;
for (i = 0; i < n; i++)
    sum += a[i];
return sum;
```

`sum`은 매 반복에서 다시 사용되므로 Temporal locality를 보인다. 반면 각각의 `a[i]`를 한 번씩만 읽더라도, 곧 이웃한 `a[i + 1]`을 읽으므로 배열 접근에는 Spatial locality가 있다. “같은 원소를 다시 읽지 않는다”는 이유만으로 locality가 없다고 판단해서는 안 된다. [STT 27:33] [STT 28:34] [M03 p.18]

Instruction도 메모리에 저장된 데이터라는 관점에서 생각할 수 있다. Loop 안의 instruction들이 반복 실행되면 Temporal locality가 있고, branch가 없는 구간에서 이어지는 instruction들을 실행하면 Spatial locality가 있다. 따라서 locality는 변수 값에만 적용되는 성질이 아니다. [STT 28:34] [STT 29:32]

[[concepts/cache|Cache]](캐시)는 더 크고 느린 장치의 데이터 중 일부를 보관하는 작고 빠른 저장 공간이다. Locality가 있으면 전체 데이터보다 훨씬 작은 부분만 빠른 계층에 유지해도 많은 접근을 처리할 수 있다. 이것이 모든 메모리를 Registers처럼 만들지 않고도 성능을 얻는 이유다. [STT 30:31] [M03 p.19]

자료 p.19에서는 Level $k$의 저장 장치를 바로 아래 Level $k+1$의 Cache로 보는 관계로 일반화한다. 이 관점에서 Registers는 L1/L2 cache와 Main memory에서 가져온 데이터 일부를 보관하는 Cache이고, Main memory는 disk 데이터의 Cache, local disk는 remote storage 파일의 Cache 역할을 한다. 즉 Cache라는 역할은 CPU cache에만 한정되지 않고 여러 계층 사이에서 반복된다. [STT 30:31] [STT 31:27] [M03 p.19]

예를 들어 이해를 위한 상황으로, 큰 데이터 파일 중 현재 처리하는 작은 구간을 여러 번 사용한다고 하자. Cache에 파일 전체가 없어도 그 구간이 남아 있다면 반복 접근의 비용을 줄일 수 있다. 반대로 접근이 계속 새로운 먼 위치로 이동하면 같은 크기의 Cache로 얻는 효과는 작아질 수 있다. Locality는 프로그램의 경향이지, 모든 접근에서 반드시 성립하는 보장은 아니다. 강의에서도 이러한 한정을 명시했다. [STT 26:35]

### Cache Block과 Hit·Miss: 무엇을 한 번에 가져오는가

Cache는 필요한 Byte 하나만 따로 관리하기보다 Block(블록) 단위로 데이터를 보관하고 이동시키는 경우가 많다. CPU cache에서 사용하는 이 단위를 Cache line(캐시 라인)이라고도 부른다. p.20 그림의 아래 계층은 Block 0–15를 보유하고, 위 계층은 그중 4·9·10·3만 보유한다. 그림의 양방향 화살표는 두 계층 사이의 복사가 Block 단위로 이루어진다는 뜻이다. [STT 32:27] [M03 p.20]

Fixed-sized block(고정 크기 블록)은 위치와 크기를 관리하기 쉬워 hardware cache에 적합하다. Variable-sized block(가변 크기 블록)은 저장 대상의 크기에 맞춰 공간을 사용할 수 있지만 관리가 복잡해진다. 강의의 web cache 사례에서는 image 전체를 보관하는 경우를 가변 크기의 예로 들었다. [STT 32:27] [STT 33:27] [M03 p.21]

전송 단위는 하위 장치에 접근하기 위해 드는 비용과도 관련된다. 접근을 시작하는 데 큰 비용이 들면, 작은 양을 반복해서 가져오는 것보다 한 번에 더 큰 묶음을 가져올 동기가 생긴다. 자료는 Register의 4·8-byte word, CPU cache의 32·64-byte Block, Main memory의 보통 4 KB Page, remote storage에서 가져오는 file을 대비한다. 이들은 계층별 예시이며, CPU가 64-bit라는 사실만으로 모든 Cache line 크기가 결정되는 법칙은 아니다. [STT 33:27] [STT 34:27] [STT 35:28] [M03 p.21]

특히 **64 bytes는 여기서 Cache line 하나의 크기이지 Cache 전체 용량이 아니다.** 전체 용량은 얼마나 많은 line을 보관하는지도 알아야 계산할 수 있다.

요청한 Block이 해당 Cache에 있으면 hit이고, 없으면 Cache miss(캐시 부적중)다. p.22에서 Block 10 요청은 위 계층에 있으므로 hit다. Block 13 요청은 위 계층에서는 miss지만 아래 계층에는 있으므로, 아래에서 가져올 수 있다. 같은 요청도 어느 계층을 기준으로 보느냐에 따라 hit·miss 판정이 달라진다. [STT 35:28] [M03 p.22]

Miss 이후에는 두 질문이 남는다. 새 Block을 어디에 둘 것인가가 Placement(배치) 문제이고, 허용된 자리가 가득 찼다면 무엇을 내보낼 것인가가 Eviction(축출) 또는 Replacement(교체) 문제다. 아래 계층에서 데이터를 찾았다는 사실만으로 Cache 관리가 끝나는 것은 아니다. [STT 36:23]

### Cold·Capacity·Conflict Miss를 원인으로 구별하기

자료는 Cache miss를 세 가지 원인으로 구분한다. 이 분류는 단순히 “없어서 miss”라고 말하는 데서 더 나아가, 왜 없게 되었는지 설명하기 위한 것이다. [M03 p.23]

**Cold miss 또는 Compulsory miss(최초 접근 부적중)**는 Block을 처음 참조하여 아직 가져오지 않았기 때문에 발생한다. 처음 실행하는 code 구간이나 처음 접근하는 배열의 Block이 강의의 예다. Cache가 충분히 크더라도, 아직 가져오지 않은 데이터의 최초 접근은 이 문제를 겪을 수 있다. [STT 36:23] [STT 37:23]

**Capacity miss(용량 부족 부적중)**는 현재 활발하게 사용하는 Block들의 집합인 Working set(작업 집합)을 Cache에 함께 담을 수 없을 때 발생한다. 강의는 1000-byte Cache로 1200-byte 배열을 오가며 처리하는 예를 든다. 한쪽을 가져오느라 다른 쪽을 내보냈는데 다시 필요해지는 상황에서, 총용량 부족이 반복 miss의 원인이 된다. 최초 접근이라는 이유와 반복 접근 중 공간 부족이라는 이유를 구분해야 한다. [STT 37:23] [STT 38:15]

**Conflict miss(배치 충돌 부적중)**는 전체 용량만으로 설명되지 않는 위치 제한 때문에 발생한다. Block을 Cache 어디에나 둘 수 있게 하면 찾는 회로가 복잡해질 수 있으므로, 주소로 후보 위치를 제한하는 방법을 사용한다. [STT 38:15] [STT 39:15]

자료의 예에서는 Block $i$의 위치를 $i\bmod4$로 정한다.

$$
0\bmod4=0,\qquad 8\bmod4=0
$$

위치 0에 Block 하나만 들어갈 수 있다고 가정하면, `0, 8, 0, 8, …` 접근은 두 Block이 서로를 계속 내보내는 결과를 만든다. 첫 접근 이후에도 다른 위치가 남아 있는데 같은 위치만 다투기 때문에 miss가 반복된다. [STT 39:15] [STT 40:13] [M03 p.23]

여기서는 **위치 하나에 Block 하나만 보관한다는 조건**이 핵심이다. 이 예는 사실상 Direct-mapped(직접 사상) 조건으로 읽어야 한다. Set-associative cache(집합 연관 캐시)에서 같은 Set(집합)에 여러 Way(저장 후보 자리)가 있고 두 Block을 함께 담을 수 있다면, 같은 반복 접근이 반드시 계속 miss를 일으키지는 않는다. STT의 넓은 set-associative 표현을 근거로 모든 associativity에 같은 결과를 적용하면 안 된다.

### Optimal Replacement와 LRU: 미래 대신 과거를 이용하기

Cache가 가득 찬 상태에서 새 Block을 가져오려면 Victim(축출 대상)을 골라야 한다. Optimal eviction policy(최적 축출 정책)는 다시 사용하지 않을 Block을 내보내거나, 다음 사용이 가장 먼 미래에 있는 Block을 내보내는 방식이다. 문제는 실제 프로그램의 미래 접근 순서를 일반적으로 알 수 없다는 점이다. Branch와 입력에 따라 이후 실행이 달라질 수 있다. [STT 41:06] [STT 41:55] [M03 p.24]

[[concepts/lru|Least recently used]](가장 오래 사용되지 않은 항목 우선, LRU)는 미래 대신 과거의 사용 순서를 이용한다. 최근에 사용한 항목은 남기고, 가장 오랫동안 사용하지 않은 항목을 내보낸다. 오래 사용하지 않은 항목은 가까운 미래에도 덜 필요할 것이라는 추정이다. 이 추정이 언제나 맞는 것은 아니며, 강의에서도 가정이 틀릴 수 있음을 언급했다. [STT 42:45] [STT 43:47] 동시에 강의는 LRU가 전형적인 프로그램에서 매우 잘 작동한다고 평가했다. 이 평가는 모든 접근 패턴에서 Optimal eviction policy와 같은 결과를 낸다는 보장은 아니다. [STT 43:47]

Queue(큐)로 사용 순서를 표현한다면 앞쪽을 오래 사용하지 않은 항목, 뒤쪽을 최근 사용한 항목으로 정할 수 있다. 새 항목은 뒤에 넣고, 기존 항목에 접근했을 때도 뒤로 옮긴다. Victim은 앞에서 고른다. 방향을 반대로 정해도 되지만 삽입·갱신·축출의 관계가 일관되어야 한다. [STT 44:10] [STT 46:30]

**이해를 위한 예시:** 세 Block을 담는 Cache의 순서가 오래된 쪽부터 `A → B → C`라고 하자. 여기서 A에 hit하면 LRU 순서는 `B → C → A`가 된다. 이후 D를 넣어야 하면 B를 내보낸다. A는 가장 먼저 들어왔더라도 방금 사용되었기 때문이다.

이 예가 보여주는 차이는 **hit에서도 순서를 갱신한다**는 점이다. 삽입 시점만 따라가며 먼저 들어온 것을 내보내는 FIFO와 LRU는 다르다. 강의의 명확한 후속 설명도 접근할 때 기존 항목의 위치를 갱신하는 부분을 짚는다. 중간의 짧은 학생 응답과 불명확한 Queue 연산 표현은 검증 필요이며, 특정 자료구조 구현을 완성한 답변으로 재구성하지 않는다. [STT 44:53] [STT 45:22] [STT 46:30]

### Reference Bit와 Second Chance: 정확한 LRU의 관리 비용 줄이기

LRU의 개념이 간단하다고 관리 비용까지 작은 것은 아니다. 정확한 순서를 유지하려면 메모리 접근마다 해당 항목을 찾아 위치를 바꾸어야 한다. Page 단위로 관리하더라도 그 Page 안의 변수를 읽거나 쓸 때마다 순서 갱신이 필요해진다. 강의는 Queue와 Pointer를 관리하는 추가 작업이 원래 접근보다 비싸질 수 있다는 점을 설명한다. [STT 47:17] [STT 48:15]

이를 줄이는 방법으로 Reference bit(참조 비트), 또는 Access bit(접근 비트)를 이용한다. Hardware는 Page가 접근되었다는 사실을 bit 하나에 기록하고, OS는 필요할 때 이 정보를 이용한다. 모든 Page의 정확한 최근 사용 순서를 매 순간 유지하는 방식보다 관리할 정보가 적다. [STT 49:15]

[[concepts/clock-page-replacement|Clock·Second chance]](시계·두 번째 기회) 방식의 강의상 절차는 다음과 같다.

1. 메모리가 부족해지면 Page들을 순서대로 살펴본다.
2. Reference bit가 0이면 축출 대상으로 선택한다.
3. Reference bit가 1이면 0으로 지우고 이번에는 남겨 둔다.
4. 다음 Page로 이동한다.
5. 남겨 둔 Page가 다시 접근되면 hardware가 bit를 다시 1로 만든다.

[STT 50:15] [STT 51:15]

**이해를 위한 예시:** P·Q·R을 순서대로 검사하며 bit가 각각 `1, 1, 0`이고, 검사 중 새로운 접근이 없다고 하자. P는 0으로 바꾸고 통과하며 Q도 같은 처리를 한다. R은 0이므로 Victim이 된다. 다음 검사 전에 P가 다시 사용되면 P의 bit는 다시 1이 될 수 있다.

여기서 bit 0은 “한 번도 사용한 적이 없다”는 뜻이 아니다. 이전에 지운 이후 접근이 기록되지 않았다는 식으로 읽어야 한다. 또한 bit 하나는 모든 Page 사이의 최근 사용 순서를 담지 못하므로 Second chance는 **LRU의 근사**이며 정확한 LRU와 같은 Victim을 항상 선택하지는 않는다.

### Compiler·Hardware·OS가 맡는 Cache 관리의 차이

Cache라는 공통 원리를 사용하더라도 관리 주체와 허용되는 비용은 다르다. 자료는 Registers, CPU cache, disk의 Cache로서 Main memory를 구분한다. [M03 p.25]

| 관리 대상 | 관리 주체 | 강의에서 설명한 이유와 방식 |
|---|---|---|
| Registers에 유지할 값 | Compiler(컴파일러) | 코드 분석과 Register allocation으로 반복적인 메모리 접근을 줄임 |
| CPU L1/L2/L3 cache | Hardware | 빠른 조회를 위해 주소 기반의 정해진 위치 선택 구조 사용 |
| Main memory의 Page와 교체 | OS(운영체제) | 비싼 disk 접근을 줄이기 위해 LRU 계열 근사 등 정책 사용 |

Register allocation(레지스터 할당)은 어떤 값을 Register에 유지하고 언제 다른 값을 가져올지 결정하는 과정이다. 강의에서는 함수 내부의 코드 분석으로 값을 재사용하면 메모리에서 다시 가져오는 횟수를 줄일 수 있다고 설명한다. [STT 51:15] [STT 52:12]

CPU cache의 조회는 매우 자주 일어나므로 빠르게 수행할 수 있는 구조가 중요하다. 반면 disk 접근은 메모리 접근보다 훨씬 비싸므로, OS가 Page 선택에 어느 정도 관리 비용을 들여도 비싼 I/O를 줄일 여지가 있다. 이 차이가 계층별 관리 방식의 차이를 설명한다. [STT 53:10] [STT 54:08]

다만 “정해진 조회 구조를 사용한다”는 설명을 모든 메모리 접근의 실제 시간이 동일하다는 뜻으로 받아들이면 안 된다. Hit인지 miss인지, 어느 아래 계층까지 가야 하는지에 따라 수행하는 작업이 달라진다.

### Address Space Isolation과 Shared Memory를 같은 Page Table로 구현하기

Address space isolation(주소 공간 격리)은 Process마다 다른 Page table을 사용하여 각자의 주소 공간을 구분하는 것이다. p.27에서는 실행 중인 Process의 Page table을 PTBR가 가리킨다. 동일한 VPN 2라도 Process A에서는 PPN 7, Process B에서는 PPN 5로 연결된다. VA 숫자가 같아도 참조 대상이 다를 수 있는 이유다. [STT 54:08] [M03 p.27]

[[concepts/shared-memory|Shared memory]]는 반대로 서로 다른 Process의 PTE가 같은 physical page를 가리키도록 구성한다. p.28의 공유 그림에서는 두 가지 경우를 비교할 수 있다.

| Process A의 Mapping | Process B의 Mapping | 읽어야 할 의미 |
|---|---|---|
| VPN 1 → PPN 1 | VPN 1 → PPN 1 | 같은 VPN으로 같은 physical page 공유 |
| VPN 4 → PPN 6 | VPN 6 → PPN 6 | 서로 다른 VPN으로 같은 physical page 공유 |

두 번째 행의 화살표를 따라가면 A와 B의 virtual 위치는 다르지만 끝점은 같은 PPN 6이다. 공유 여부를 결정하는 것은 VA 숫자의 일치가 아니라 **실제로 같은 physical page에 도달하는가**다. [STT 55:05] [M03 p.28]

p.27의 격리 예와 p.28의 공유 예는 Mapping 상태가 다른 그림이다. 한쪽 표의 값을 다른 그림으로 가져와 계산하면 안 된다. Page table 문제에서는 항상 현재 제시된 표를 기준으로 해야 한다.

2024-2 중간고사 Q4(e)는 공유 Page가 두 Process에서 같은 VPN을 가져야 하는지를 판단하도록 요구한다. 풀이 접근은 두 VA를 직접 비교하는 것이 아니라, 각자의 Page table을 통해 같은 PPN에 도달할 수 있는지 설명하는 것이다. 앞의 두 번째 행이 그 판단을 뒷받침하는 강의 예다. [EX:sp_2024_2_midterm_q04 p.9]

### Virtual Address Space의 크기와 실제 상주 Page 수

Virtual address space(가상 주소 공간)의 크기는 현재 Physical Memory에 상주하는 데이터의 양과 다르다. p.29의 그림에서는 Process A·B·C가 각각 7개의 virtual pages를 보지만, 전체 physical memory에는 11개의 Page만 있다. 이 그림의 Page size는 앞의 작은 예와 같은 `0x100` bytes다. [STT 56:00] [M03 p.29]

$$
\text{Process 하나의 virtual space}
=7\times\texttt{0x100}
=\texttt{0x700}\text{ bytes}
$$

$$
\text{세 Process의 virtual space 합}
=21\times\texttt{0x100}
=\texttt{0x1500}\text{ bytes}
$$

$$
\text{Physical Memory}
=11\times\texttt{0x100}
=\texttt{0xB00}\text{ bytes}
$$

그림을 읽을 때는 virtual space의 모든 칸이 각각 별도의 physical page와 연결되어 있지 않다는 점을 봐야 한다. 주소 공간 전체에 대해 같은 크기의 DRAM을 미리 확보하는 모델이 아니다. 또한 Physical Memory 안에는 프로그램 데이터뿐 아니라 각 Process의 Page table도 놓여 있다. [M03 p.29]

이 도식은 21개의 모든 virtual pages가 동시에 서로 다른 physical pages에 상주한다는 뜻이 아니다. Page table이 어느 Process의 주소 공간에 어떻게 노출되는지에 관한 STT의 불명확한 표현도, 모든 OS에 적용되는 보편적인 Mapping 규칙으로 확장하지 않는다. [STT 56:00]

### Flat Page Table의 규모와 Multi-level Page Table의 동기

64-bit Byte 주소 전체를 4 KiB Page로 나누면 가능한 VPN의 수는 다음과 같다.

$$
\frac{2^{64}}{2^{12}}=2^{52}
$$

p.30은 이 거대한 virtual space와 훨씬 작은 Physical Memory를 대비한다. 실제로 필요한 데이터가 작더라도, 가능한 VPN마다 항목을 가진 하나의 거대한 배열을 Process마다 만드는 것은 부담이 크다. [STT 57:02] [M03 p.30]

강의 후반 Core i7 도식은 **48-bit VA와 4 KiB Page**라는 별도의 구체적인 모델을 사용한다. 여기서는 Offset이 12 bits이므로 VPN은 36 bits다.

$$
48=36+12,\qquad
\text{가능한 VPN 수}=2^{36}
$$

주소 공간의 Byte 용량은 다음과 같다.

$$
2^{48}\text{ bytes}=256\text{ TiB}
$$

따라서 256 TiB의 주소 공간과 $2^{36}$개의 Page를 구분해야 한다. STT의 Page 수와 용량을 오가는 불명확한 자기정정은 **검증 필요**이며, “256조 Page”라는 설명으로 사용하지 않는다. [STT 57:02] [STT 58:01] [M03 p.40]

**이해를 위한 계산:** 가능한 VPN마다 8-byte PTE를 하나씩 두는 flat table을 가정하면 크기는 다음과 같다.

$$
2^{36}\times8
=2^{39}\text{ bytes}
=512\text{ GiB}
$$

이는 8-byte entry라는 가정을 넣어 도출한 예시이며, 강의에서 이 수치를 직접 말했다는 뜻은 아니다. 작은 프로그램에까지 이런 표를 하나씩 두는 것이 비효율적이라는 점을 보여준다. 강의는 `ls`·`cat`처럼 작은 프로그램을 예로 들며 이 규모 문제를 제기한다. [STT 58:57]

[[concepts/multilevel-page-table|Multi-level page table]](다단계 페이지 테이블)은 거대한 단일 배열 대신 여러 단계의 표를 따라가도록 구성하는 접근이다. 이번 강의에서는 그 필요성과, 후반 도식의 9-bit씩 네 단계로 나누는 변환을 설명한다. 각 단계의 구체적인 연결은 TLB miss 경로에서 다시 확인한다. [STT 59:51] [STT 01:25:41]

### Page Sharing과 Copy on Write의 예고 범위

Page를 공유하는 동기에는 협업뿐 아니라 불필요한 복제를 줄이는 목적도 있다. 강의는 여러 Process가 `libc`의 `printf` 같은 공통 기능을 사용한다는 사례를 들며, 같은 내용을 Process마다 별도로 보관하지 않으려는 요구를 설명한다. [STT 59:51]

여기서는 “공통 코드가 놓인 Page를 여러 주소 공간에서 이용할 수 있다”는 원리를 이해하는 것이 핵심이다. 이것을 곧바로 모든 library 데이터가 공유된다거나, 이름이 같은 모든 변수가 같은 physical page를 쓴다는 뜻으로 확장하면 안 된다.

자료에는 Lazy copy(지연 복사)와 [[concepts/copy-on-write|Copy on write]](쓰기 시 복사, COW)가 제시되어 있지만, 강의에서는 후속 설명을 예고하는 수준이다. 쓰기 시점의 세부 처리 절차까지 이번에 완전히 배웠다고 보지 않는다. 뒤의 `fork` 설명에서도 “Process의 메모리가 논리적으로 분리된다”는 의미와 “모든 physical page를 즉시 복사한다”는 특정 구현을 구분해야 한다. [STT 01:00:47] [M03 p.30]

### On-demand Paging: Physical Memory를 Cache처럼 사용하기

[[concepts/demand-paging|On-demand paging]](요구 시 페이징)은 필요한 Page가 접근될 때 메모리에 가져오는 방식이다. 활발한 Process들이 요구하는 데이터가 DRAM에 모두 들어가지 않으면 일부 Page를 disk에 보관하고, Physical Memory에는 현재 필요한 일부를 유지할 수 있다. 이 관점에서 Physical Memory도 아래 저장 장치의 Cache처럼 작동한다. [STT 01:01:21] [M03 p.31]

p.31의 Process A가 `0x233`에 접근하는 경우를 보자. Page size가 `0x100`이므로 VPN은 2, Offset은 `0x33`이다. 그러나 이번 그림의 VPN 2는 PPN 5를 가리키지 않는다. PTE에는 disk로 나간 상태와 그 위치가 표시되어 있다. 앞의 정상 변환 그림과 **다른 상태의 예**다. [STT 01:02:15] [M03 p.31]

이때 발생하는 [[concepts/page-fault|Page fault]](페이지 폴트)는 이 예에서 필요한 Page가 현재 상주하지 않아 발생하는 사건이다. 강의의 처리 흐름은 다음과 같다.

1. CPU가 필요한 Page를 현재 Mapping으로 사용할 수 없어 fault가 발생한다.
2. 해당 접근을 진행할 수 없으므로 Process의 실행이 일시 중단된다.
3. OS가 필요한 physical 공간을 확보한다. 공간이 부족하면 다른 Page를 교체할 수 있다.
4. Disk에서 필요한 Page를 읽어 Physical Memory에 넣는다.
5. PTE를 갱신한다.
6. Fault를 일으킨 instruction을 다시 실행한다.

[STT 01:03:13] [STT 01:04:09]

핵심은 OS가 데이터를 준비한 뒤 **같은 instruction을 다시 실행할 수 있다**는 점이다. 이 예는 복구 가능한 nonresident-page fault다. 모든 Page fault가 Process 종료를 뜻하지 않는다.

2024-2 중간고사 Q4(a)–(d)는 Page table을 이용한 주소 판단과 demand paging 설명을 연결한다. 이 유형에서는 VPN·Offset 계산 뒤에 entry의 유효성을 먼저 확인해야 한다. 해당 원문에는 invalid entry에 PA 답을 함께 적은 부분과 VPN 행의 중복 표기가 있으므로, 제공 답안의 모양을 일반 규칙으로 외우면 안 된다. 유효한 resident Mapping이 확인되지 않은 상태에서 PPN처럼 보이는 수치를 곧바로 실제 접근 가능한 PA로 확정하지 않는다. [EX:sp_2024_2_midterm_q04 p.8]

같은 대문항의 뒤쪽 allocator 문제는 별도다. Page 단위 translation을 배웠다는 사실만으로 Heap Block의 header·footer와 병합까지 배운 것은 아니므로, 이 연결은 주소 변환·paging·sharing·TLB에 해당하는 소문항으로 제한한다.

### File-backed Page의 축출: 내보낼 때마다 쓰는 것은 아니다

Page 교체에서 Victim을 골랐다고 항상 disk에 다시 써야 하는 것은 아니다. File-backed page(파일 내용에 대응하는 페이지)가 원본을 읽어 온 뒤 수정되지 않았다면, 메모리의 사본을 버려도 나중에 같은 file에서 다시 읽을 수 있다. [STT 01:05:59]

반대로 메모리에서 변경한 내용이 아래 저장 장치에 보존되어 있지 않다면, 그 사본을 그냥 버리면 변경 내용이 사라진다. 강의에서는 이러한 경우 disk에 써서 내용을 보존해야 한다고 설명한다. 따라서 Page 교체는 Victim 선택뿐 아니라 **다시 가져올 원본이 있는가, 변경을 보존해야 하는가**도 함께 고려한다. [STT 01:05:06] [STT 01:05:59]

**이해를 위한 예시:** 파일에서 읽은 한 Page를 검색에만 사용했다면 메모리 사본을 버린 뒤 다시 읽을 수 있다. 같은 Page를 수정했다면 변경된 내용을 보존할 방법 없이 버릴 수는 없다. 두 상황은 같은 양의 physical 공간을 비우더라도 필요한 I/O가 다르다.

이 설명은 강의 중 Page replacement의 비용을 구체화한 내용이다. 후속 자료에 있는 Dirty bit의 모든 세부 배치까지 이번에 설명했다는 뜻은 아니다.

### Memory Access Permissions: Mapping이 있어도 모든 접근이 허용되지는 않는다

Memory access permissions(메모리 접근 권한)은 Page에 대해 어떤 동작을 허용할지 정하는 정보다. PTE는 PPN뿐 아니라 Read(읽기), Write(쓰기), Execute(실행) 등의 허용 여부도 표현한다. 주소를 변환할 수 있다는 사실과 원하는 동작을 해도 된다는 사실은 다르다. [STT 01:06:53] [M03 p.32]

p.32에서 VPN 2는 PPN 7로 연결되지만 권한은 `R`뿐이다. `RDX`가 그 Page 안의 주소를 담고 있을 때 다음과 같은 Store는 Write를 요구한다.

```asm
mov %rax, (%rdx)
```

CPU는 대상 Page가 Read-only(읽기 전용)라는 것을 확인하고 Exception(예외)을 발생시킨다. 그림의 강조점은 값이 얼마나 증가했는지가 아니라, **Store라는 접근 종류와 PTE의 권한이 맞지 않는다**는 데 있다. [STT 01:07:38] [M03 p.32]

강의에서는 이 잘못된 Write의 결과를 OS가 Process를 종료하는 것으로 단순화하여 설명한다. 이는 앞의 정상적인 paging에서 Page를 읽어 온 뒤 instruction을 재실행하는 경우와 구분해야 한다. 하나는 현재 상주 여부의 문제이고, 다른 하나는 요청한 동작의 허용 여부 문제다. [STT 01:08:38]

Stack의 실행 허용과 관련된 발화에는 불분명한 부분이 있다. Page별 실행 권한을 구분한다는 범위는 자료로 확인되지만, 그 발화를 근거로 특정 공격 기법이나 자세한 보안 절차까지 만들어 설명하지 않는다. 해당 세부 표현은 검증 필요다.

### `mmap`과 `fork`: 공유 영역을 만든 뒤 Process를 나누기

강의는 이전의 `layout.c` 예제로 돌아와, 주소가 같아 보이는데 어떤 변수는 독립적이고 어떤 변수는 공동으로 바뀌는 이유를 설명한다. 이 코드를 읽을 때는 선언 위치만 보지 말고, **실제 데이터를 담는 영역을 어떻게 만들었는가**를 함께 봐야 한다. [STT 01:08:38] [M03 p.34]

자료의 공유 구조체에는 Semaphore(세마포어) `m`과 정수 `shared_int`가 들어 있다. `shared`는 이 구조체를 가리키는 Pointer다. `mmap`은 `sizeof(struct __shared)`만큼의 영역을 요청하며 다음 속성을 지정한다.

| 코드의 속성 | 예제에서의 의미 |
|---|---|
| `PROT_READ \| PROT_WRITE` | 읽기와 쓰기가 가능한 Mapping |
| `MAP_ANONYMOUS` | 이 예에서 file을 데이터 원본으로 지정하지 않는 Mapping |
| `MAP_SHARED` | Process 사이에서 공유되는 Mapping |
| `shared == MAP_FAILED` 검사 | Mapping 실패 여부 확인 |

자료에서는 이어서 `sem_init(&shared->m, 1, 1)`로 Semaphore를 초기화하고 `shared_int`를 0으로 설정한다. 이번 강의에서는 Semaphore를 우선 Lock(잠금)처럼 이해하도록 설명한다. [STT 01:09:37] [STT 01:10:28] [M03 p.34]

그 뒤 `fork`를 호출하여 Process를 만든다. 원본 반복문은 자식이 생성되면 그 자식이 반복문을 빠져나가고, 부모 쪽은 남은 수를 조정하는 형태다. 강의에서 든 `nproc = 2`의 경우에는 추가 Process 하나가 생성된다. 각 Process는 자신의 실행 흐름과 별도의 주소 공간을 갖지만, 앞서 만든 shared Mapping은 함께 사용한다. [STT 01:10:28] [STT 01:11:27] [STT 01:12:18]

예제의 동작 범위에는 Process별 `delay`, 반복 사이의 `sleep(delay)`, Mapping 실패 처리도 포함된다. 이들은 실행 간격과 오류 처리를 읽는 데 필요한 코드 문맥이다. 다만 이 제공 예제에서 현재 과제의 요구사항·제출 절차·완성 구현을 도출하지는 않는다. 여기서 다루는 것은 공유 영역의 생성과 Process별 상태의 구분이다.

### Pointer 변수는 Private이면서 가리키는 대상은 Shared일 수 있다

Pointer를 이해할 때는 Pointer 자체를 저장하는 공간과 그 Pointer가 가리키는 대상을 나누어야 한다. M01의 Pointer 그림에서도 `ap`라는 Pointer 변수는 자신의 주소에 저장되어 있고, 그 안에는 다른 변수의 주소가 들어 있다. **주소를 담는 변수 역시 메모리 어딘가에 놓인 별도의 객체다.** [M01 p.14]

`layout.c`의 `shared`도 같은 구조다. 이름이 `shared`라고 해서 그 Pointer 변수 자체가 shared Mapping 안에 있는 것은 아니다. p.35–36은 다음과 같이 구분한다. [STT 01:13:20] [STT 01:15:22]

| 대상 | Process A | Process B | 공유 여부 |
|---|---|---|---|
| `global_int`와 Pointer 변수 `shared`가 있는 VPN 2 | PPN 1 | PPN 7 | Process별 private 상태 |
| `shared`가 가리키는 `m`, `shared_int`가 있는 VPN 3 | PPN 2 | PPN 2 | 같은 physical page 공유 |

[M03 p.35] [M03 p.36]

p.36 그림에서는 두 Process의 VPN 2에서 나오는 화살표가 서로 다른 physical pages로 향한다. 반면 VPN 3의 두 화살표는 공통 PPN 2에 모인다. 따라서 Pointer를 보관하는 위치가 private이어도, 그 안의 주소를 따라가면 shared object에 도달할 수 있다. [STT 01:16:26] [STT 01:17:18]

여기서 같은 변수명이나 같은 VA가 같은 physical 저장 위치를 보장하지 않는다. 반대로 Pointer 변수의 저장 위치가 다르다는 사실만으로 그 안에 들어 있는 주소 값까지 반드시 다르다고 결론내려서도 안 된다. STT의 모호한 “결과가 다르다”는 표현은 저장 위치와 Pointer 값 중 어느 것을 지칭하는지 검증 필요다. [STT 01:13:20]

또한 `fork`의 private 상태를 설명하는 그림을 모든 physical page가 호출 즉시 복사된다는 보장으로 읽으면 안 된다. 여기서는 서로의 private 변경이 독립적이라는 의미와 명시적으로 shared인 영역의 의미를 구분한다.

### Shared Counter와 Semaphore: 같은 데이터를 보는 것과 안전하게 바꾸는 것

공유는 여러 Process가 같은 데이터에 도달하게 한다. Synchronization(동기화)은 그 데이터를 함께 변경할 때 실행을 조정한다. 두 문제는 연결되지만 같지는 않다. [STT 01:11:27] [STT 01:14:20]

예제에서 `global_int`는 각 Process의 private 변수이므로 독립적으로 증가한다. 반면 `shared_int`는 같은 physical page에 있어 두 Process의 증가가 같은 값에 반영된다. 자료는 공유 증가 구간을 다음처럼 보호한다.

```c
sem_wait(&shared->m);
shared->shared_int++;
sem_post(&shared->m);
```

[M03 p.34] [M03 p.37]

강의에서는 `sem_wait`와 `sem_post`를 각각 잠금과 해제에 대응시켜 설명한다. 중요한 점은 정수만 shared인 것이 아니라 **잠금에 사용하는 `m`도 두 Process가 함께 사용하는 영역에 있다**는 것이다. 그래야 같은 정수의 변경을 같은 잠금으로 조정할 수 있다. [STT 01:14:20]

p.37의 표에서는 양쪽 `global_int`가 각자 진행하고, 가운데 `shared_int`는 두 Process의 작업을 합쳐 진행한다. 이 표는 특정 실행 예를 보여주며 Process들이 언제나 같은 순서로 번갈아 실행한다는 보장은 아니다. Process별 지연과 실행 순서에 따라 관찰 순서는 달라질 수 있다. [M03 p.37]

**이해를 위한 예시:** 모든 초기값이 0이고, 잠금 연산이 정상적으로 수행되며, A가 3번·B가 2번의 증가를 완료했다고 하자. A의 private counter는 3, B의 private counter는 2이고, 함께 보호한 shared counter는 5다. 이는 작은 유한 횟수의 개념 예시이며 원본 무한 반복 프로그램 전체의 실행 결과를 예측한 것은 아니다.

이 예제에서 Semaphore를 사용했다는 이유만으로 Semaphore 내부 구현이나 여러 조건을 기다리는 복잡한 동기화 문제까지 다룬 것은 아니다. 현재 이해해야 할 범위는 공유 데이터의 위치와 그 변경 구간을 함께 보호하는 이유다.

### Core i7 Memory System: Data Cache와 TLB의 두 계층

후반부는 제공된 Core i7 예제를 통해 지금까지의 개념을 한 구조 안에 배치한다. 이 예제는 네 개의 CPU Core로 구성되며, 강의의 설명과 p.39의 `Core x4` 표기가 이에 대응한다. [STT 01:18:04] [M03 p.39] 강의는 이를 과거 Core i7의 예로 소개하므로, 그림의 용량과 bit 수를 모든 현재 CPU의 사양으로 일반화하면 안 된다. [STT 01:18:04] [M03 p.39]

p.39 그림에서 왼쪽은 instruction·data를 저장하는 Cache 경로이고, 오른쪽은 주소 변환 정보를 저장하는 TLB 경로다.

| 구성 요소 | 자료에 제시된 크기와 구성 | 구분 |
|---|---|---|
| L1 d-cache | 32 KB, 8-way | Data를 저장 |
| L1 i-cache | 32 KB, 8-way | Instruction을 저장 |
| L2 unified cache | 256 KB, 8-way | Core별로 instruction·data를 함께 수용 |
| L3 unified cache | 8 MB, 16-way | 모든 Core가 공유 |
| L1 d-TLB | 64 entries, 4-way | Data 접근의 주소 변환 |
| L1 i-TLB | 128 entries, 4-way | Instruction 접근의 주소 변환 |
| L2 unified TLB | 512 entries, 4-way | 통합된 주소 변환 Cache |

[M03 p.39]

그림의 Core 경계와 공유 영역의 경계를 함께 읽으면 L2가 Core별이고 L3가 공통이라는 설명을 이해할 수 있다. L1 instruction·data Cache가 나뉘어 있다는 사실과 L1 instruction·data TLB가 나뉘어 있다는 사실도 별개로 확인해야 한다. [STT 01:18:58] [STT 01:19:39]

강의에서는 branch가 없는 instruction 접근이 대체로 순차적이라는 점을 data 접근과 대비한다. 또한 그림에는 DDR3 memory controller와 QuickPath interconnect가 있으며, memory controller의 총 bandwidth는 32 GB/s로 제시된다. 이는 그림 속 예제의 연결과 용량을 설명하는 수치다. [STT 01:20:40] [M03 p.39]

가장 중요한 구분은 TLB가 “어디로 변환되는가”를 보관하고, Data cache가 “그 위치의 내용은 무엇인가”를 보관한다는 점이다. 둘 다 Cache이지만 저장하는 대상이 다르다.

### TLB의 Tag·Set Index: 36-bit VPN을 32+4로 나누기

p.40의 모델은 48-bit VA와 4 KiB Page를 사용한다. Virtual page offset(가상 페이지 내부 위치, VPO)은 12 bits이고 VPN은 나머지 36 bits다.

$$
VA=\underbrace{VPN}_{36\text{ bits}}
\;\Vert\;
\underbrace{VPO}_{12\text{ bits}}
$$

여기서 $\Vert$는 bit열을 이어 붙인다는 뜻이다. Page 내부 위치는 바뀌지 않으므로 TLB 조회에서는 VPN에 대한 변환을 찾는다. [STT 01:21:26] [M03 p.40]

L1 d-TLB는 64 entries, 4-way다. 따라서 Set 수는 다음과 같다.

$$
\text{Set 수}=\frac{64}{4}=16=2^4
$$

이 16개 Set 중 하나를 고르는 TLB index(집합 선택 인덱스, TLBI)에 4 bits가 필요하다. 나머지 32 bits는 TLB tag(항목 식별 태그, TLBT)다.

$$
VPN=\underbrace{TLBT}_{32\text{ bits}}
\;\Vert\;
\underbrace{TLBI}_{4\text{ bits}}
$$

[STT 01:22:13] [M03 p.40]

TLBI로 Set 하나를 선택한 뒤, 그 Set의 네 Way에서 유효한 항목의 tag를 비교한다. 일치하면 해당 변환을 찾은 것이고, 이 모델에서는 40-bit PPN을 얻는다. 같은 Set에 들어오는 변환을 **최대 네 개** 보관할 수 있다는 뜻이지, Set 하나가 네 개의 주소만 표현할 수 있다는 뜻은 아니다. 강의에서도 개수를 “최대”라는 의미로 정정했다. [STT 01:23:13] [STT 01:23:55] [STT 01:24:41]

Tag와 index를 혼동하면 “Set 번호가 맞으니 hit”라고 잘못 판단하기 쉽다. 같은 Set으로 들어오는 VPN이 많기 때문에 Set을 고른 뒤 tag와 유효성을 확인해야 한다. STT의 VPN 분해를 설명하는 숫자 표현 일부는 불명확하므로, 36=32+4라는 관계는 그림을 기준으로 이해한다.

2025-1 중간고사 Q4(a)–(d)는 다른 주소 폭·Page size·TLB 구성에서 같은 판단을 요구한다. 현재 배운 원리로 접근할 수 있지만 Core i7의 12·36·32·4라는 숫자를 그대로 옮기면 안 된다. 문제에 주어진 Page size로 Offset을 먼저 구하고, 전체 entries를 Way 수로 나누어 Set 수를 구한 뒤 tag를 정하는 순서가 필요하다. [EX:sp_2025_1_midterm_q04 p.11] [EX:sp_2025_1_midterm_q04 p.12]

### TLB Miss와 Page-table Walk: 변환 Cache에 없다는 뜻

TLB miss는 필요한 주소 변환이 TLB에 없다는 뜻이다. 이것만으로 데이터가 disk에 있거나 Page fault가 발생한다고 판단할 수 없다. Page table에는 정상적인 resident Mapping이 있을 수 있다. [STT 01:24:41] [STT 01:25:41]

제공 모델에서는 36-bit VPN을 네 개의 9-bit 부분으로 나누어 Multi-level page table을 따라간다.

$$
36=9+9+9+9
$$

`CR3`가 첫 표의 위치를 제공하고, 첫 9 bits로 그 표의 항목을 선택한다. 선택한 항목을 통해 다음 표에 도달하고, 다음 9 bits로 다시 항목을 고른다. 이를 네 단계에 걸쳐 수행하여 최종 PPN을 얻는다. 한 단계에서 9 bits를 사용하므로 선택 가능한 항목 수는 $2^9=512$개다. [M03 p.40] [M03 p.41]

변환을 얻으면 TLB에 저장하여 다음 접근에서 재사용할 수 있다. 따라서 다음 두 사건을 구별해야 한다.

| 상황 | 의미 | 필요한 처리 |
|---|---|---|
| TLB miss, resident Mapping 존재 | 변환 Cache에만 정보가 없음 | Page-table walk로 변환을 얻음 |
| 필요한 Page가 nonresident | 현재 물리 Page로 접근할 수 없음 | OS의 Page 준비와 Mapping 갱신 필요 |

2025-1 중간고사 Q4(d)는 TLB hit 여부와 Page fault 여부를 따로 판단하도록 요구한다. 한 Cache의 miss를 곧바로 전체 메모리 접근의 실패로 바꾸지 않고, 다음 단계의 유효한 Mapping을 확인하는 것이 핵심이다. [EX:sp_2025_1_midterm_q04 p.13]

자료 버전의 번호 체계도 주의해야 한다. M03 p.41은 탐색의 위쪽을 L1, 아래쪽 최종 표를 L4로 표시하며, M03 p.42–43의 제목도 이에 맞춘다. M02의 해당 제목과 큰 Page의 level 표기는 다르므로 두 버전의 번호를 한 그림에 섞으면 안 된다. 이번 강의에서 확인되는 설명은 네 단계와 9-bit 분할까지이며, 뒤의 모든 PTE flag와 directory별 세부 사항을 끝까지 배웠다는 뜻은 아니다. [M02 p.42] [M02 p.43] [M03 p.41] [M03 p.42] [M03 p.43]

### Data Cache의 Tag·Index·Offset: 변환한 주소로 내용을 찾기

PPN을 얻으면 보존된 Offset과 합쳐 PA를 구성한다. Physical page offset(물리 페이지 내부 위치, PPO)은 이 모델에서 VPO와 같고, 크기는 12 bits다.

$$
PA=\underbrace{PPN}_{40\text{ bits}}
\;\Vert\;
\underbrace{PPO}_{12\text{ bits}}
$$

따라서 p.40에서 사용하는 PA는 총 52 bits다. 이것은 CPU가 실제로 그 주소 범위만큼의 DRAM을 장착했다는 뜻이 아니라, 그림의 물리 주소 표현 폭이다. [STT 01:26:40] [M03 p.40]

L1 d-cache에서는 이 PA를 다시 세 부분으로 해석한다.

| 필드 | 크기 | 역할 |
|---|---:|---|
| Cache tag(캐시 식별 태그, CT) | 40 bits | 선택한 Set 안에서 원하는 physical Block을 식별 |
| Cache index(캐시 집합 인덱스, CI) | 6 bits | 64개 Set 중 하나 선택 |
| Cache offset(캐시 내부 위치, CO) | 6 bits | 64-byte line 내부의 Byte 위치 선택 |

이 Cache에는 Set마다 8개의 line이 있으므로 데이터 용량은 다음과 같다.

$$
64\text{ sets}\times8\text{ lines/set}\times64\text{ bytes/line}
=32768\text{ bytes}
=32\text{ KiB}
$$

[STT 01:27:34] [M03 p.40]

CI는 Set을 고르고, CT는 그 Set의 여덟 Way에서 유효한 tag가 일치하는지 확인하는 데 쓰인다. Hit이면 CO를 통해 필요한 Byte 위치를 선택한다. 한 line이 64 bytes라고 해서 프로그램이 매번 64 bytes 전체를 결과로 받는 것은 아니다. 예를 들어 문자 하나를 읽는다면 그 안의 한 Byte가 필요하다. [STT 01:28:34]

L1 miss이면 아래쪽 L2·L3·Main memory 경로에서 내용을 찾아야 한다. 여기서도 TLB hit와 L1 data-cache hit를 구분해야 한다. 주소 변환을 빨리 얻었더라도 데이터 자체가 L1에 있다는 보장은 없다. 반대로 TLB에 변환이 없었다는 사실만으로 데이터도 반드시 모든 Cache에 없다고 결론내릴 수 없다. [M03 p.40]

그림의 배선도 중요하다. 오른쪽 CI와 CO에 연결되는 12 bits는 변환 전후에 보존되는 Page offset에서 온다. PPN 쪽 40 bits는 physical tag를 제공한다. 따라서 강의가 PA를 얻고 Cache를 확인하는 순서로 설명했다고 해서, **모든 Cache index 동작이 반드시 주소 변환 완료까지 기다린다**고 단정하면 안 된다. 강의 말미에도 동시 조회 가능성과 virtual address를 사용하는 Cache를 언급하지만, 그 상세 설계를 모두 전개하지는 않는다. [STT 01:29:21] [STT 01:29:55] [M03 p.40]

### End-to-end Translation을 하나의 주소로 따라가기

**이해를 위한 예시 — 강의 도식의 구조를 사용하여 새로 만든 수치 예시다.** 실제 기출이나 공식 답안의 재현이 아니다. p.40과 동일한 48-bit VA, 4 KiB Page, 16-set·4-way TLB, 64-set·8-way·64-byte L1 d-cache를 사용한다고 하자. 모든 필요한 권한이 허용되어 있고 다음 유효한 항목이 존재한다고 가정한다.

- TLB의 Set `0x9`에 tag `0x12345678` → PPN `0xABCDE`인 항목이 있다.
- L1 d-cache의 Set `0x2A`에 physical tag `0xABCDE`인 line이 있다.
- 그 line의 Byte offset `0x3C`에 값 `0x7E`가 들어 있다.

VA가 `0x123456789ABC`이면 먼저 Page 내부의 하위 12 bits를 분리한다.

```text
VPN = 0x123456789
VPO = 0xABC
```

VPN의 하위 4 bits가 TLBI이고 나머지가 TLBT이므로 다음과 같다.

```text
TLBI = 0x9
TLBT = 0x12345678
```

가정한 유효한 TLB 항목이 일치하므로 PPN은 `0xABCDE`다. Offset을 유지하여 PA를 구성한다.

$$
PA=\texttt{0xABCDE}\times\texttt{0x1000}+\texttt{0xABC}
=\texttt{0xABCDEABC}
$$

이제 같은 PA를 Data cache의 형식으로 나눈다.

```text
CT = 0xABCDE
CI = 0x2A
CO = 0x3C
```

가정한 Set과 tag가 일치하므로 L1 hit이고, 한 Byte를 읽는 접근이라면 offset `0x3C`, 즉 열 번째가 아닌 **0부터 세어 60인 위치**의 값 `0x7E`를 얻는다. 여기서 `0x3C = 60`이라는 단위 확인까지 해야 한다. TLB에서는 VPN의 변환을 찾았고, Data cache에서는 변환된 위치의 내용을 찾았다는 차이가 하나의 주소에서 드러난다. [M03 p.40]

2025-2 중간고사 Q4는 이러한 연속 판단을 요구한다. VA의 VPN·VPO 분리, TLB의 Set·tag 및 hit 판정, Page table의 유효성 확인, PA 구성, Cache의 index·tag·offset과 반환 Byte 판단을 연결하는 구조다. 풀이에서는 각 표를 건너뛰지 않고, 현재 단계에서 무엇이 확인되었는지 구분해야 한다. 특히 tag가 맞더라도 유효하지 않은 항목을 hit로 사용하면 안 된다. [EX:sp_2025_2_midterm_q04 p.9] [EX:sp_2025_2_midterm_q04 p.10] [EX:sp_2025_2_midterm_q04 p.11]

반면 2025-1 중간고사 Q4(e)–(f)의 Data cache 계산은 앞선 주소 변환 소문항과 **다른 주소 폭과 Block 크기**를 지정한다. 앞 소문항에서 계산한 필드 폭을 그대로 이어 쓰지 말고 조건을 다시 읽어야 한다. Cache의 전체 line 수와 Way 수로 Set 수를 구하고, Block 크기로 CO를 구한 뒤 남는 주소 bits를 CT로 정하는 원리는 동일하다. [EX:sp_2025_1_midterm_q04 p.13] [EX:sp_2025_1_midterm_q04 p.14]

이번 녹음은 이 End-to-end 설명을 마친 뒤 해당 지점부터 다시 이어가겠다는 말로 끝난다. 따라서 후속 자료의 세부 PTE bit 전체와 Canonical address space의 두 영역을 이번 시간에 모두 설명한 내용으로 추가하지 않는다. 강의에서 다룬 주소 변환 경로와 자료에만 더 자세히 제시된 내용을 구분하여 읽어야 한다. [STT 01:29:55]

## 핵심 요약

- **Virtual Memory와 실제 용량:** 주소 표현 범위, Process가 사용할 수 있는 Mapping, 현재 상주 데이터의 양은 서로 다르다. Private address space와 선택적 Sharing은 함께 제공할 수 있다.
- **Address translation:** 같은 Page size에서 VPN을 PPN으로 바꾸고 Offset을 보존한다. `PT`가 PPN을 반환한다면 다음 식을 사용한다. [M03 p.15]

$$
PA=PT\!\left[\left\lfloor VA/PS\right\rfloor\right]\times PS+(VA\bmod PS)
$$

- **역할 구분:** Page table은 Mapping 자료구조, MMU는 변환 hardware, `CR3`는 탐색 시작점, TLB는 변환 정보의 Cache다. Data cache는 실제 내용을 보관한다.
- **Cache의 효과와 한계:** Locality가 작은 Cache의 효과를 만들지만, 최초 접근·용량 부족·배치 충돌은 서로 다른 miss 원인이다. Cache line 크기와 전체 Cache 용량도 구분한다.
- **Replacement:** LRU는 hit에서도 최근 사용 순서를 바꾼다. Reference-bit 기반 Second chance는 관리 비용을 줄인 근사이며, 정확한 LRU와 같지 않다.
- **Paging과 Protection:** Nonresident Page는 준비 후 재실행할 수 있다. Read-only Page에 대한 Store는 권한 문제다. TLB miss만으로 어느 쪽도 확정할 수 없다.
- **공유 예제:** Pointer 변수의 저장 공간이 private이어도 대상은 shared일 수 있다. Shared counter의 변경은 함께 공유하는 Semaphore로 보호한다.
- **제공 Core i7 모델:** VA는 36+12 bits, VPN의 TLB 분해는 32+4 bits, PA는 40+12 bits, Data cache 분해는 40+6+6 bits다. 이 수치들은 해당 도식의 조건이다. [M03 p.40]
- **범위의 끝:** COW는 예고 수준이며, 후속 자료의 전체 PTE flag와 Canonical address space 세부를 이번 강의에서 모두 배운 것으로 보지 않는다. [STT 01:00:47] [STT 01:29:55]

#### Q01. Memory의 주소 범위와 실제 용량

64-bit Byte 주소가 표현하는 범위는 얼마인가? 그 범위를 표현하는 Pointer가 있으면 같은 용량의 DRAM이 필요한가? Load와 Store의 방향도 설명하라.

<details><summary>정답</summary>

전체 64-bit Byte 주소 모델의 범위는 $2^{64}$ bytes, 즉 16 EiB다. 이는 실제 DRAM 용량을 뜻하지 않는다. Load는 Memory의 내용을 Register로, Store는 Register의 내용을 Memory로 옮긴다. 도입부의 불완전한 발화는 정확한 명령어 설명으로 복원하지 않는다. [M03 p.4] [M03 p.5]

#### Q02. Indirection과 Private·Shared Memory

#### Q03. Page Table과 수식의 단위

#### Q04. MMU·Page Table·CR3·TLB

#### Q05. Memory Hierarchy와 Storage Disaggregation

빠른 Registers·SRAM만으로 전체 저장 공간을 구성하지 않는 이유는 무엇인가? Storage를 network 너머에 모으는 동기와 속도 비교의 한정도 설명하라. 강의가 비교용으로 든 Registers·SRAM cache·DRAM의 cycle 규모는 무엇이며, 어떻게 한정해서 읽어야 하는가?

<details><summary>정답</summary>

Registers·SRAM은 큰 용량을 확보하기 어렵고 비용이 높다. 더 큰 DRAM과 storage를 함께 사용해야 한다. 강의는 Registers를 1 cycle 미만, SRAM cache를 1 cycle 또는 몇 cycles, DRAM을 약 100 cycles로 대비했다. 이는 비교용 설명이며 모든 cache level·장치의 동일한 지연이나 공통 상한이 아니다. [STT 19:55] [STT 20:56] [STT 23:48] Storage disaggregation은 저장 장치의 집중 관리·교체·규모 조정을 쉽게 하려는 구조다. OS에 disk처럼 보여도 I/O는 network를 통과할 수 있다. Local과 remote의 속도 순서는 장치와 연결 조건에 달렸으며, 불명확한 STT의 network 전송률 단위는 검증 필요다. [M03 p.17] [STT 22:55] [STT 25:38]

#### Q06. Data·Instruction의 Locality

배열 합산 Loop에서 `sum`, 연속 배열 원소, 반복되는 instruction은 각각 어떤 Locality를 보이는가? 이것이 작은 Cache의 효과와 어떻게 연결되는가? 계층 사이에서 반복되는 Cache 관계를 Registers·Main memory·local disk의 사례로 설명하라.

<details><summary>정답</summary>

`sum`의 반복 사용은 Temporal locality, 연속 배열 원소 접근은 Spatial locality다. Loop instruction의 반복 실행에는 Temporal locality가 있고, 연속 instruction 실행에는 Spatial locality가 있다. 접근이 일부 위치에 집중되면 전체 데이터보다 작은 Cache로도 많은 요청을 처리할 수 있다. 다만 모든 프로그램에서 같은 효과를 보장하지는 않는다. [M03 p.18] [M03 p.19]

Level $k$가 Level $k+1$의 Cache라는 관계가 반복된다. Registers는 L1/L2 cache와 Main memory 데이터의 일부를, Main memory는 disk 데이터의 일부를, local disk는 remote files를 보관하는 Cache로 설명된다. [STT 30:31] [STT 31:27] [M03 p.19]

</details>

#### Q07. Block·Hit·Miss·Placement

Fixed-sized block과 Variable-sized block의 차이는 무엇인가? 상위 Cache에서 miss, 하위 계층에서 hit가 난 뒤에는 어떤 결정을 해야 하는가?

#### Q08. 세 종류의 Cache Miss

Cold·Capacity·Conflict miss를 원인으로 구별하라. `0, 8, 0, 8` 접근이 modulo 4 배치에서 계속 miss가 된다는 설명에는 어떤 조건이 필요한가?

<details><summary>정답</summary>

Cold miss는 최초 접근, Capacity miss는 Working set을 함께 담지 못하는 총용량 부족, Conflict miss는 허용된 배치 위치의 충돌 때문이다. 0과 8은 모두 위치 0에 대응한다. 그 위치가 Block 하나만 보관해야 서로 계속 축출한다. 같은 Set에 두 Block을 함께 보관할 Way가 있다면 최초 miss 이후 hit가 가능하다. [M03 p.23]

</details>

#### Q09. Optimal·LRU·FIFO

Optimal replacement와 LRU가 사용하는 정보는 어떻게 다른가? 오래된 순서가 `A → B → C`일 때 A에 hit하면 LRU Queue는 어떻게 바뀌는가? 전형적인 프로그램에 대한 강의의 LRU 평가는 무엇이며, 이것이 모든 접근 패턴에서 Optimal과의 일치를 보장하는가?

<details><summary>정답</summary>

Optimal은 미래의 다음 사용 시점을 이용하지만 LRU는 과거의 최근 사용 순서를 이용한다. A에 hit하면 LRU 순서는 `B → C → A`가 된다. 이후 교체 대상은 B다. 삽입 순서만 유지하는 FIFO는 hit 때문에 순서를 바꾸지 않는다. 강의는 전형적인 프로그램에서 LRU가 매우 잘 작동한다고 평가하면서도 그 가정이 틀릴 수 있다고 한정했다. 따라서 모든 접근 패턴에서 Optimal과 같다는 보장은 아니다. [STT 43:47] 불명확한 교실 문답에서 특정 Queue 구현 코드를 복원할 수는 없다. [M03 p.24] [STT 46:30]

</details>

#### Q10. Reference Bit와 Second Chance

#### Q22. Data Cache와 Offset 배선

|---|---:|---:|

A에 hit하면 LRU 순서는 `B → C → A`가 된다. D를 넣을 때 B를 내보내고 `C → A → D`가 된다. FIFO는 hit로 삽입 순서를 바꾸지 않으므로 A를 내보낸다.

주어진 미래에서는 B가 다시 사용되지 않으므로 Optimal도 B를 고른다. 이번 선택이 일치해도 두 정책이 같은 것은 아니다. LRU는 미래를 알지 못하고 과거 사용 순서를 이용한다.

이 추적은 명시한 Queue 규칙을 적용한 것이며, 불명확한 교실 문답을 구현 코드로 복원한 결과가 아니다.

**채점 포인트:** LRU 갱신·Victim 2점, FIFO 차이 1점, Optimal 판단 1점, 일반화 한정 2점.

</details>

3. PA와 CT·CI·CO의 bit 수 및 값을 구하라.
4. Data-cache hit 여부와 반환 Byte를 구하라.

<details><summary>풀이와 채점 포인트</summary>

Page size가 $2^8$ bytes이므로 VPO와 PPO는 8 bits다. VPN은 $20-8=12$ bits, PPN은 $16-8=8$ bits다.

TLB는 $16/4=4$ Sets이므로 TLBI는 2 bits, TLBT는 $12-2=10$ bits다.

```text
VPN  = 0x3B
VPO  = 0x6D
TLBI = 0x3
TLBT = 0xE
```

Tag가 같아도 Valid가 0이므로 TLB miss다. 그러나 Page table에 허용된 resident Mapping이 있으므로 Page fault는 발생하지 않는다.

$$
PA=\texttt{0x52}\times\texttt{0x100}+\texttt{0x6D}

$$

```text
CT = 0x0A4
CI = 0x6
CO = 0xD
```

Set 6에 유효한 tag A4가 있으므로 Data-cache hit다. Offset D, 즉 0부터 세어 13인 위치의 Byte `0x7B`를 반환한다.

새 변형에서는 TLB miss·Page fault 없음이라는 판정과 PA는 그대로다. Data cache는 miss로 바뀌므로 하위 계층에서 내용을 찾아야 한다. 무효 line에 남은 `0x7B`를 반환값으로 사용할 수 없으며, 하위 데이터가 주어지지 않았으므로 실제 반환 Byte는 확정할 수 없다.

**채점 포인트:** 필드 폭 3점, TLB 유효성·Page fault 구분 2점, PA 1점, Cache 필드·반환 Byte 2점, 새 변형의 한정 2점.

### 자료 보정과 검증 필요 사항
