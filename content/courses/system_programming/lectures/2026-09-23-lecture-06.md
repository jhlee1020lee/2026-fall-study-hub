2026년 9월 23일 수업은 Memory abstraction(메모리 추상화)을 통해 C 코드의 주소·저장 공간·실행 동작을 연결하고, 이를 Dirtree 과제의 요구사항으로 이어 간다.  
앞의 설명을 바탕으로 무엇이 저장되고 변경되는지 추적한 뒤, 작은 계산과 명세 판정 문제로 이해를 확인한다.

## 강의 내용과 설명

### [[concepts/memory-abstraction|Memory abstraction(메모리 추상화)]]: 같은 주소가 같은 데이터를 뜻할까?

이번 강의의 출발점은 C 코드에 적힌 Function(함수)과 Variable(변수)이 실행 중 어디에 존재하는지를 관찰하는 것이다. Function도 컴파일된 Instruction(명령어)이 Memory(메모리)에 놓여 실행되므로 Memory address(메모리 주소)를 가진다. 실행 중인 프로그램을 Process(프로세스)라고 하며, PID(Process ID, 프로세스 식별자)로 실행 주체를 구별한다. [STT 03:43] [STT 04:42]

자료의 `layout.c`는 Function인 `foo`, `bar`, `main`, Global variable(전역 변수), Local variable(지역 변수), Array(배열), Pointer(포인터)의 주소를 나란히 출력한다. 여기서 중요한 것은 주소 숫자를 외우는 것이 아니라 다음 세 가지를 구별하는 것이다.

- 코드와 데이터가 서로 어떤 영역에 놓이는가?
- 같은 프로그램을 다시 실행했을 때 주소가 유지되는가?
- 서로 다른 Process에서 주소 숫자가 같으면 데이터도 공유되는가?

도입 코드의 `shared`는 Semaphore(세마포어)와 `shared_int`를 포함하는 Structure(구조체)를 가리킨다. Semaphore는 공유 데이터에 접근할 때 Locking(잠금)이 필요하다는 동기로 등장한다. 전체 공유 구현은 이번 회차에서 완성하지 않았으며, `layout.c`의 전체 소스 설명은 다음 강의로 예고되었다. [M01 slide 4] [STT 02:55] [STT 13:08]

`&foo`는 Function `foo`의 주소를 명시적으로 얻는 식이다. Function을 가리키는 Pointer가 필요한 문맥에서는 `foo`라는 Function name만 사용해도 같은 Function을 가리키는 값으로 사용되므로, 주소를 얻기 위해 항상 `&`를 써야 하는 것은 아니다. M01 slide 4는 `&foo`·`&bar`·`&main`을 사용하고, 강의는 `&`를 생략하는 사용을 Array name의 주소 사용에 비유한다. 주소를 가리키는 식과 `foo()`처럼 Function을 호출하는 식은 구별해야 한다. [M01 slide 4] [STT 04:42] [STT 05:36]

이 비유가 Function을 가리키는 Pointer와 `int *`처럼 데이터 객체를 가리키는 Pointer를 같은 종류로 취급한다는 뜻은 아니다. 자료의 `printf` 주소 출력은 해당 실행환경의 관찰 예시이며, Function을 가리키는 Pointer의 `%p` 출력이나 데이터 객체 Pointer로의 형변환이 모든 C 환경에서 통용된다는 근거로 일반화하지 않는다. STT 05:36의 정확한 변환 설명은 **검증 필요**이며, 위 개념 설명으로 불명확한 발화를 복원한 것은 아니다.

#### ASLR과 반복 실행 주소

ASLR(Address Space Layout Randomization, 주소 공간 배치 무작위화)은 실행 주소를 예측하기 어렵게 만드는 기법이다. 자료의 ASLR 비활성화 예시는 여러 번 실행해도 Function과 Variable의 주소가 반복된다. ASLR이 적용된 예시는 비슷한 모양의 주소에서도 높은 자릿수 등이 달라진다. 주소 끝부분이 비슷하다는 이유만으로 전체 주소가 같다고 판단하면 안 된다. [M01 slide 5] [M01 slide 6]

강의에서 설명한 보안 동기는 고정된 Function이나 Variable의 주소를 아는 것이 다른 취약점의 악용을 도울 수 있다는 점이다. 따라서 주소 예측을 어렵게 만드는 것이 의미가 있다. 다만 ASLR 자체가 모든 취약점을 제거하거나 모든 공격을 막는다는 뜻은 아니다. [STT 07:36] [STT 08:34]

#### Private state와 Shared memory

[[concepts/virtual-memory|Virtual memory(가상 메모리)]]에서는 주소를 **어느 Process의 주소 공간에서 해석하는지**가 중요하다. 두 Process에서 같은 숫자의 Virtual address(가상 주소)가 출력되어도, 그 주소가 각각의 독립된 데이터를 가리킬 수 있다.

M01 slide 7의 출력 그림은 이 차이를 직접 보여 준다. 그림의 두 실행 주체를 편의상 Process A와 B로 부르면, 관찰된 일부 순서는 다음과 같다.

| 실행 주체 | 자기 `global_int` | `shared_int` |
|---|---:|---:|
| A | 0 | 0 |
| B | 0 | 1 |
| A | 1 | 2 |
| A | 2 | 3 |
| B | 1 | 4 |

`global_int`는 각 Process에서 따로 증가한다. A가 자기 값을 바꿔도 B의 값이 함께 바뀌지 않는다. 반면 `shared_int`는 양쪽 실행에 걸쳐 증가한 상태가 이어진다. 그림 전체에서는 공유 값이 0부터 7까지 이어지는 모습을 볼 수 있다. **같은 주소 숫자**와 **실제로 공유되는 상태**는 별개의 판단 대상이다. [M01 slide 7] [STT 10:15] [STT 11:09] [STT 12:08]

이때 Shared memory(공유 메모리)는 IPC(Inter-process communication, 프로세스 간 통신)를 위한 수단으로 소개되었다. 실제 공유 여부는 주소가 우연히 같은지로 결정되지 않고, 해당 영역을 공유하도록 구성했는지에 달려 있다. 이번 회차는 이러한 격리와 공유의 관찰까지 다룬다. Virtual address를 Physical address(물리 주소)로 변환하는 상세 절차는 후속 학습 범위다. [STT 10:15] [STT 42:29]

### Variable name은 데이터를 가리키는 Label이다

Variable 선언은 Type(자료형)에 맞는 저장 공간과 그 데이터를 편리하게 참조할 Name(이름)을 연결한다. 자료의 설명에서 Name은 주소를 대신 사용하는 Label(표지)이다. 프로그래머가 매번 숫자 주소를 직접 쓰지 않아도 Compiler(컴파일러)가 이름과 저장 위치를 연결한다. [M01 slide 9] [STT 13:08]

자료의 단순화된 예시는 다음과 같다.

| Variable | 시작 주소 | 저장된 값 |
|---|---:|---:|
| `a` | 16 | 5 |
| `b` | 20 | 7 |
| `c` | 24 | 그림에서 미지정 |

이 그림에서 `a`를 읽는다는 것은 주소 16부터 `a`의 Type에 해당하는 데이터를 읽는다는 뜻이다. `a`에 대입하면 그 저장 위치의 내용이 바뀐다. 이름 자체가 정수 5인 것도 아니고, 이름 자체가 항상 주소 16인 것도 아니다. 그림은 이름·주소·내용의 관계를 설명하기 위한 특정 배치다. [M01 slide 10]

또한 이 예시처럼 Variable이 선언 순서대로 연속 배치된다고 일반화하면 안 된다. 강의에서도 연속 배치를 보장하지 않는다고 설명했다. 계산 과정은 보통 Memory에서 Register(레지스터)로 값을 가져와 연산하는 흐름으로 이해하면 된다. Memory끼리 직접 연산할 수 없다는 강의 표현은 이 설명의 맥락으로 읽어야 하며, 모든 Architecture(아키텍처)의 모든 명령어에 적용되는 절대 규칙으로 확대하지 않는다. [STT 14:01]

### [[concepts/memory-layout|Memory layout(메모리 배치)]]: 코드, Global variable, Heap, Stack

Memory layout을 나누는 이유는 데이터의 역할, 접근 권한, 생성 시점이 서로 다르기 때문이다. M01 slide 11의 그림은 주소 0이 아래에 있고 높은 주소가 위에 있는 형태다. 아래쪽에는 실행 파일과 관련된 영역, 중간에는 Heap(힙)과 Memory-mapped region(메모리 매핑 영역), 위쪽에는 User stack(사용자 스택)과 Kernel virtual memory(커널 가상 메모리)가 표시된다.

#### `.text`, `.rodata`, `.data`, `.bss`

그림 옆 코드의 배치를 연결하면 다음과 같다.

| 영역 | 자료 예시에서의 역할 | 읽을 때 주의할 점 |
|---|---|---|
| `.text` | `foo` 같은 Function의 실행 명령어 | Function도 주소를 가진다. |
| `.rodata` | `const int b = 7` 같은 Read-only data(읽기 전용 데이터), String literal(문자열 리터럴)의 전형적 배치 | 데이터를 가리키는 Pointer의 위치와 구별한다. |
| `.data` | `int a = 5`처럼 초기값을 보존해야 하는 Writable data(쓰기 가능한 데이터) | 모든 실제 배치를 initializer 유무만으로 판정하지 않는다. |
| `.bss` | 자료의 Global `int c`처럼 별도의 초기값 내용을 실행 파일에 일일이 담지 않는 영역 | 실행 중 저장 공간이 필요 없다는 뜻이 아니다. |

[M01 slide 11] [STT 15:07] [STT 16:05] [STT 18:01]

Read-only라는 구분은 물리적인 Memory 소자가 본질적으로 다른 물질이라는 뜻이 아니다. 운영체제와 CPU가 접근 권한을 관리한다. 쓰기가 허용되지 않은 영역을 변경하려 하면 접근 위반이 감지되어 Process가 종료될 수 있다. 따라서 물리적으로 데이터를 저장할 수 있는 장치라는 사실과, 현재 Process에 해당 쓰기가 허용된다는 사실을 구별해야 한다. [STT 17:04] [STT 18:01]

`.data`와 `.bss`를 나누는 동기는 실행 파일의 저장 공간과 연결된다. `a = 5`라면 실행 시 5라는 값을 재현할 정보가 필요하다. 반면 큰 Global array의 내용을 파일에 원소별로 모두 저장하지 않고 필요한 영역의 크기를 나타내면 파일 공간을 절약할 수 있다. **실행 파일에 초기 내용 전체를 저장하지 않는 것과, 실행 시 Memory를 사용하지 않는 것은 다르다.** [STT 18:57] [STT 19:54]

강의 밖 공식 보충: 명시적 initializer가 없는 static storage duration의 산술형 객체는 0으로 초기화된다. [S01 §6.7.9p10, WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

이 구분은 2024-2 중간 Q5(d)의 `.data`·`.bss` 차이와 공간 절약 이유를 설명하는 요구에 직접 연결된다. 접근 방법은 “어디에 놓이는가”에서 멈추지 않고 “파일에 어떤 정보를 저장해야 하는가”까지 설명하는 것이다. 같은 대문항의 Linking·Loading 계산까지 이번 회차 범위로 포함하는 것은 아니다. [EX:sp_2024_2_midterm_q05 p.12]

#### Heap, mapped region, Stack의 그림 읽기

그림의 Run-time heap(실행 중 힙)은 `malloc`으로 확보하는 데이터와 연결된다. `brk`는 그림에서 Heap의 끝을 나타낸다. Shared library(공유 라이브러리)는 별도의 mapped region과 연결되어 있다. 강의는 작은 allocation과 큰 allocation이 놓이는 위치가 달라질 수 있다고 설명했지만, 크기별 allocator의 정확한 내부 경로까지 제시한 것은 아니다. [M01 slide 11] [STT 20:52]

User stack은 Function 호출과 Local variable을 설명하는 데 사용된다. 그림의 화살표와 강의의 Intel 예시에서는 Stack이 높은 주소에서 낮은 주소 방향으로 자란다. 여기서 다음 두 대상을 분리해서 보아야 한다.

```c
char *m = malloc(10);
```

이 자료 코드에서 `m`은 주소를 저장하는 Local pointer이고, `malloc(10)`이 확보한 10-byte 영역은 별도의 동적 저장 공간이다. `m`의 위치와 `m`이 가리키는 위치가 같을 필요는 없다. [M01 slide 11] [STT 21:47]

초반에는 Function parameter(함수 매개변수)도 Stack에 놓인다고 설명하지만, 후반 자료에는 parameter를 Register로 전달하는 실제 명령어가 나온다. 따라서 Memory layout 그림을 모든 Local variable과 모든 parameter가 언제나 Stack에 실체화된다는 규칙으로 읽지 않는다. 구체적인 전달 위치는 뒤에서 보는 호출 규약과 코드에 따라 판단한다. [STT 22:48] [M01 slide 44]

2024-2 중간 Q1(d)는 Function의 주소, Global constant를 가리키는 주소, Local pointer 자체의 주소를 구별하고 주소 종류를 판단하게 한다. 먼저 출력식이 **무엇의 주소인지** 식별한 뒤 해당 실행환경의 Memory layout에 연결해야 한다. 주소의 자릿수나 숫자 크기만 보고 영역을 찍는 접근은 불충분하다. [EX:sp_2024_2_midterm_q01 p.3]

### [[concepts/pointers|Pointers]]: 자기 주소, 저장된 주소, 가리키는 값

Pointer는 Memory address를 값으로 담는 Variable이다. 따라서 Pointer를 읽을 때는 세 층을 구별해야 한다.

1. Pointer object 자체가 놓인 주소
2. Pointer object 안에 저장된 주소 값
3. 그 주소가 가리키는 대상의 값

M01 slides 14–15는 이 관계를 작은 숫자 주소로 그린 개념도다.

```c
int a = 5;
int *ap = &a;
int **app = &ap;
```

| Object | Object 자신의 주소 | 저장된 값 | 한 번 따라가면 |
|---|---:|---:|---|
| `a` | 16 | 5 | 정수 데이터 |
| `ap` | 28 | 16 | `a` |
| `app` | 4 | 28 | `ap` |

`&ap`는 28이고 `ap`의 값은 16이다. `*ap`는 그 주소의 정수 값 5를 읽는다. `app`에는 `ap`의 주소 28이 들어 있으므로 `*app`는 Pointer object인 `ap`를 가리키고, `**app`는 최종적으로 `a`의 값에 접근한다. [M01 slide 14] [M01 slide 15]

이 그림의 핵심은 `app → ap → a`라는 두 단계 관계다. STT에 섞여 있는 `app`의 주소 표현은 그림과 일치하지 않는 부분이 있으므로, 위 숫자는 **슬라이드의 명확한 배치**를 기준으로 읽는다. [STT 23:44] [STT 24:43]

**이해를 위한 예시**로, 위 상태에서 `*app = &b`를 실행한다고 생각해 보자. 바뀌는 것은 `app` 자신의 주소도, `a`의 값도 아니다. `app`가 가리키는 Pointer object인 `ap`에 `b`의 주소를 저장한다. 이후 `**app`는 `b`에 접근한다. 대입문 왼쪽에 `*`가 몇 개 붙었는지를 세는 데서 끝내지 말고, 실제로 어떤 Object가 대입 대상이 되는지 따라가야 한다.

이러한 추적은 2024-2 중간 Q1(b)의 요구와 연결된다. Pointer-to-pointer(포인터를 가리키는 포인터) 대입 문제에서는 정수 값의 변화와 Pointer 연결의 변화를 별도 표로 기록하면 실수를 줄일 수 있다. 해당 시험의 다른 소문항에 있는 입력 형식 불일치 코드를 안전한 Pointer 사용 예제로 함께 받아들이지는 않는다. [EX:sp_2024_2_midterm_q01 p.2]

도입의 `shared`에도 같은 구분을 적용한다. `sizeof(shared)`는 Pointer object의 크기이고, `sizeof(*shared)`는 가리키는 Structure의 크기다. 강의 환경에서 전자는 8 bytes로 설명되었지만, 그것만으로 후자의 크기를 결정할 수는 없다. [STT 05:36] [STT 06:37]

### [[concepts/dynamic-memory-allocation|Dynamic allocation(동적 할당)]]과 Array의 저장 공간

`int *A;`라는 선언은 주소를 담을 Pointer variable을 만드는 것이다. 이것만으로 1,024개의 `int`를 저장할 공간이 생기지는 않는다. M01 slides 16–17은 Pointer의 저장 공간과 실제 데이터 block을 두 위치에 그려 이 차이를 보여 준다.

자료에서 `A` 자신의 주소는 `0xffffc1a4`이다. 이어 다음 allocation을 수행하면 반환된 시작 주소가 `A`에 저장된다.

```c
A = (int *)malloc(sizeof(int) * 1024);
```

이 그림의 조건은 `sizeof(int) = 4`이므로 필요한 공간은 다음과 같다.

$$
4 \times 1024 = 4096\text{ bytes} = \texttt{0x1000}\text{ bytes}
$$

그림에서 반환된 시작 주소는 `0x56550004`이다. 따라서 다음 두 문장은 서로 다르다.

- `A`는 `0xffffc1a4`에 놓인 Pointer object다.
- `A`에 저장된 주소 값은 `0x56550004`다.

[M01 slide 16] [M01 slide 17]

Array element(배열 원소)는 Type 크기만큼 연속 배치된다. 이 자료의 주소 계산은 다음과 같다.

| Element | 시작 주소 계산 | 결과 |
|---|---|---|
| `A[0]` | 시작 주소 | `0x56550004` |
| `A[1]` | 시작 주소 + 4 bytes | `0x56550008` |
| `A[2]` | 시작 주소 + 8 bytes | `0x5655000c` |
| `A[1023]` | 시작 주소 + 4,092 bytes | `0x56551000` |

마지막 원소의 시작 주소와 block의 끝도 구별해야 한다. 마지막 `int`는 4 bytes를 차지하므로, 확보한 영역 바로 다음 주소는 `0x56551004`이다. STT의 allocation 수치가 불명확한 부분을 복원한 것이 아니라, 슬라이드에 명시된 크기와 주소로 계산한 결과다. [M01 slide 17] [STT 24:43]

#### Partial initializer와 `malloc`의 차이

자료의 다음 두 경우는 처음 세 문자가 같아도 나머지 저장 공간의 초기 상태가 다르다.

```c
char buf[512] = {'A', 'B', 'C'};

/* 별도의 allocation 예시 */
char *p = malloc(512 * sizeof(char));
p[0] = 'A';
p[1] = 'B';
p[2] = 'C';
```

위 코드는 자료의 핵심 부분이며, `p`에 대한 설명은 allocation이 성공한 경우를 전제로 한다. `buf`에는 Partial initializer(부분 초기화 목록)가 있으므로 나머지 원소가 0으로 초기화된다. 따라서 `buf[3]`은 0이다. 강의의 질문에서도 Pointer의 null과 문자 원소의 숫자 0을 구별했다. [M01 slide 19] [STT 26:45] [STT 27:45]

반면 `p`가 가리키는 영역에는 직접 쓴 `p[0]`, `p[1]`, `p[2]`만 지정한 값이 들어 있다. 그 사실만으로 `p[3]`도 0이라고 보장할 수 없다. 강의의 “random”이라는 설명은 그 값을 믿을 수 있는 난수로 활용하라는 뜻이 아니다.

강의 밖 공식 보충: `malloc`이 확보한 객체의 초기값은 indeterminate(미정)이다. [S01 §7.22.3.4p2, WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

강의는 0으로 채운 allocation이 필요할 때 `calloc`을 언급하고, 사용이 끝나면 `free`해야 한다고 설명했다. Process 종료 시 운영체제가 자원을 회수한다는 설명은 실행 중 필요 없어진 allocation을 계속 방치해도 된다는 뜻이 아니다. 프로그램이 오래 실행되는 동안 불필요한 allocation을 유지하면 Memory leak(메모리 누수)이 누적될 수 있다. [STT 28:44]

### [[concepts/sizeof|sizeof]]와 `read`: 주소와 길이는 별도 정보다

Array와 Pointer가 헷갈리는 이유는 Array 이름을 많은 식에서 첫 Element의 주소처럼 사용하기 때문이다. 그러나 **주소로 사용되는 식의 성질**과 **Array object의 정체성**은 다르다.

자료의 `char *p`에서 `p[0]`는 첫 문자의 값이고, `&p[0]`는 그 문자의 주소다. `p`에 저장된 주소 값과 `&p[0]`는 같다. `buf`도 일반적인 사용 문맥에서는 첫 원소를 가리키는 주소로 사용되지만, `buf[0]` 자체가 주소인 것은 아니다. [M01 slide 18] [M01 slide 19]

이 차이가 가장 분명하게 드러나는 곳이 `sizeof`다.

| 선언 | `sizeof`가 측정하는 대상 | 강의 예시의 결과 |
|---|---|---:|
| `char buf[512]` | Array 전체 | 512 bytes |
| `char *buf` | Pointer object | 8 bytes |
| `char buf` | 문자 하나 | 1 byte |

`read`는 데이터를 써 넣을 주소와 최대 byte 수를 별도 인자로 받는다. 따라서 자료의 다음 두 코드는 길이를 표현하는 방식이 다르다.

```c
char buf[512];
read(fd, buf, sizeof(buf));
```

```c
#define BUFSIZE 512
char *buf = malloc(BUFSIZE * sizeof(char));
read(fd, buf, BUFSIZE * sizeof(char));
```

두 번째 코드에서 `sizeof(buf)`를 쓰면 확보한 block의 길이가 아니라 Pointer 크기를 전달한다. `BUFSIZE` 같은 Named constant(이름 있는 상수)를 allocation과 `read`에 함께 사용하면 두 위치의 길이 표현을 일관되게 유지할 수 있다. 위 코드는 주소·길이 구별을 위한 자료 조각이며, 전체 I/O 오류 처리를 갖춘 프로그램은 아니다. [M01 slide 20] [STT 29:40] [STT 30:40]

문자 하나를 읽을 때는 다음과 같이 그 문자의 주소가 필요하다.

```c
char ch;
read(fd, &ch, sizeof(ch));
```

`ch`는 문자 값이고 `&ch`는 데이터를 저장할 위치다. 잘못된 인자가 컴파일 과정에서 어떻게 처리되는지는 도구 설정에 따라 달라질 수 있다. 강의의 GCC800 언급은 이러한 실수를 경계하는 수업 맥락이며, 컴파일되었다는 사실만으로 인자가 올바르다고 판단하면 안 된다. [STT 30:40] [STT 31:35]

2025-1 중간 Q1(a)는 Object 자체와 Dereference(역참조) 식의 `sizeof`가 각각 어떤 Type의 크기를 뜻하는지 판단하게 한다. 접근 순서는 “식의 Type 확인 → 그 환경의 Type 크기 적용”이다. Pointer에 allocation 길이가 자동으로 저장되어 있다고 생각하는 것이 대표적인 함정이다. [EX:sp_2025_1_midterm_q01 p.2]

### [[concepts/data-types|Data types(자료형)]]와 실행환경의 약속

Machine level(기계 수준)에서는 정수·주소·부동소수점 같은 Scalar data(스칼라 데이터)와 Vector data(벡터 데이터)를 다룬다. 자료는 1·2·4·8-byte 정수 데이터, 4·8·10·16-byte 부동소수점 데이터 등을 제시한다. C의 Array와 Structure라는 조직을 CPU가 소스 선언 그대로 이해하는 것은 아니다. Compiler가 연속된 bytes와 각 부분의 위치를 정해 기계 수준 접근으로 바꾼다. [M01 slide 22] [STT 31:35] [STT 32:17]

Array는 같은 Type의 원소를 반복하고, Structure는 서로 다른 Type의 Member(멤버)를 함께 묶을 수 있다. 이러한 Composite data structures(복합 자료구조)의 의미를 기계가 처리할 수 있게 만드는 것이 크기와 Offset(시작 위치로부터의 거리)이다.

이번 강의의 중심 환경은 **x86-64 Linux**다. 우선 익히라고 명시한 Type 크기는 다음과 같다.

| C Type | x86-64 Linux 중심 예시 | IA32 자료 예시 |
|---|---:|---:|
| `char` | 1 | 1 |
| `short` | 2 | 2 |
| `int` | 4 | 4 |
| `long` | 8 | 4 |
| `float` | 4 | 4 |
| `double` | 8 | 8 |
| Pointer | 8 | 4 |

단위는 bytes다. 이는 강의가 사용하는 환경의 값이며, CPU가 64-bit라는 이유만으로 모든 운영체제와 Compiler에서 같은 배치를 보장하는 표가 아니다. [M01 slide 23] [STT 37:11] [STT 41:29]

자료의 `long long`, `long double`, 128-bit 정수에는 취소선이 표시되어 있고, 강의에서는 역사적 배경과 제한된 학습 초점을 설명했다. `long long`은 32-bit 환경에서도 더 큰 정수를 다루려는 맥락에서, `long double`은 과거 부동소수점 처리와 x87의 맥락에서 언급되었다. 강의는 별도 Coprocessor(보조 프로세서)에서 부동소수점 연산을 처리하던 역사를 x87과 연결한다. 이때 **값을 표현하는 크기와 저장 공간 전체 크기를 구별해야 한다.** 자료의 x86-64 예시에서는 `long double`의 값 표현이 10 bytes이고, 정렬용 여유 공간 6 bytes를 더해 저장 공간은 16 bytes다. 따라서 `sizeof(long double)`이 16이라고 해서 값 표현 자체가 128 bits라는 뜻은 아니다. IA32 자료의 `10/12`도 값 표현 10 bytes와 저장 공간 12 bytes를 구별하는 표기다. 이는 자료의 특정 환경에 대한 설명이며 모든 `long double` 구현의 공통 규칙이 아니다. STT의 비트 수 발화는 **검증 필요**이고, 여기서 80 bits는 자료의 10 bytes를 환산한 값이다. [M01 slide 23] [M01 slide 26] [M01 slide 27] [M01 slide 29] [STT 35:14] [STT 36:13] 드문 Type의 모든 예외를 지금 암기하라는 요구는 아니지만, 이 설명 자체를 삭제하거나 Alignment 전체가 시험 범위 밖이라고 해석할 근거도 없다. [M01 slide 23] [STT 34:15] [STT 35:14] [STT 36:13] [STT 43:27]

실행 코드와 이미 컴파일된 Library가 함께 동작하려면 Type 배치와 parameter 전달에 대한 약속이 맞아야 한다. 자료는 이를 ABI와 연결한다. 이 노트에서는 자료에서 명확하지 않은 약어 풀이를 덧붙이지 않고, **Compiler와 Binary 사이의 배치·호출 규약**이라는 역할에 집중한다. [M01 slide 30] [STT 40:32] [STT 44:25] [STT 52:04]

### [[concepts/data-alignment|Data alignment(데이터 정렬)]]: 크기뿐 아니라 시작 위치도 중요하다

K-byte aligned라는 말은 데이터의 첫 byte 주소가 K로 나누어떨어진다는 뜻이다.

$$
\text{start address} \bmod K = 0
$$

4-byte Alignment를 요구하는 `int`라면 주소 0, 4, 8, 12 등은 조건을 만족하고, 1, 2, 3, 5 등은 만족하지 않는다. 여기서 Alignment는 출력 표의 왼쪽·오른쪽 맞춤과 다른 개념으로, **Memory 안에서 Object가 시작할 수 있는 위치에 관한 규칙**이다. [M01 slide 24] [STT 41:29]

동기는 Memory access(메모리 접근)의 경계와 연결된다. 자료는 시스템에 따라 일정 크기의 정렬된 묶음으로 접근한다고 설명한다. 데이터 하나가 이런 경계를 가로지르면 접근이 나뉘어 비효율적일 수 있다. 강의는 Atomicity(원자성)와 Page(페이지) 경계 문제도 함께 언급했다. 여기서 쓰기의 Atomicity는 값 전체의 변경이 중간 상태 없이 하나의 동작처럼 관찰되는 성질이다. **이해를 위한 예시**로, 경계를 가로지르는 값의 쓰기가 두 번의 Memory access로 나뉘는 상황을 생각해 보자. 두 접근 사이의 상태가 관찰될 수 있다면, 일부는 새 값이고 나머지는 이전 값인 상태가 드러날 수 있어 값 전체를 한 번에 갱신한 것으로 볼 수 없다. 이것이 분할 접근을 피하려는 동기가 성능뿐 아니라 Atomicity와도 연결되는 이유다. 다만 정렬을 만족한다는 사실만으로 모든 연산의 Atomicity가 보장되는 것은 아니다. 다만 모든 Unaligned access(정렬되지 않은 접근)가 언제나 같은 수의 추가 명령어를 요구하거나 같은 원자성 결과를 낸다고 일반화하면 안 된다. [M01 slide 25] [STT 38:39] [STT 42:29]

강의의 MIPS·SPARC·일부 ARM·Power 비교는 Architecture에 따라 정렬 제약이 다를 수 있다는 사례다. 또 운영체제와 컴파일 규약도 영향을 준다. 따라서 “내 CPU에서 접근이 수행되었다”와 “다른 환경의 ABI에도 맞는다”는 서로 다른 판단이다. [STT 39:37] [STT 40:32]

자료의 x86-64 중심 표에서는 흔한 Primitive data type(기본 자료형)의 크기와 Alignment가 같은 경우가 많다. 그러나 이 관계를 모든 Type과 환경에 적용할 수는 없다. IA32 Linux 자료에서는 8-byte `double`과 `long long`의 Alignment가 4이고, 대응하는 Windows 열에는 8이 제시된다. `long double`도 별도의 예외가 있다. M01 slide 26의 Windows 열을 근거로 모든 Windows 환경의 `long` 크기까지 8이라고 확정하지 않는다. 그 부분의 환경별 해석은 검증 필요다. [M01 slide 26] [M01 slide 27]

Page 경계를 넘는 접근은 Virtual address의 변환 문제와도 연결되지만, Page table(페이지 테이블)을 이용한 상세 변환 계산은 이번 회차에서 뒤로 미뤘다. 이 자리에서는 경계를 넘는 데이터가 추가 처리를 요구할 수 있다는 동기까지 이해하면 된다. [STT 42:29] [STT 43:27]

### `size.c`와 `varalign.c`: Offset과 Padding을 직접 읽기

Padding(정렬을 위해 비워 두는 공간)은 Object나 Member를 적절한 주소에서 시작하게 하기 위해 삽입되는 간격이다. 크기만 더했을 때 다음 Member의 Alignment를 만족하지 않으면 빈 공간이 생긴다.

#### `dummy`와 `data` 사이의 거리

M01 slide 28의 `size.c`는 `INFO(t)`라는 Macro(매크로)를 사용해 다음 형태를 여러 Type에 반복한다.

```c
struct {
    char dummy;
    double data;
} s;
```

위 코드는 `t`가 `double`인 경우의 핵심 배치다. 자료의 Macro는 Type 이름, `sizeof(t)`, `data`가 Structure 시작에서 얼마나 떨어졌는지를 출력한다. `#t`는 Type 이름을 문자열로 표시하는 데 사용된다. Macro expansion(매크로 확장)은 이런 반복 패턴을 줄이지만, 이해할 때는 한 Type에 대한 구체적인 코드로 펼쳐 보면 된다. [M01 slide 28] [STT 45:24] [STT 46:17] [STT 47:15]

중요한 점은 자료의 `OFS`가 **Padding만 측정하지 않는다**는 것이다.

$$
\operatorname{OFS}(\text{data})
=
\text{data의 시작 주소}
-
\text{Structure의 시작 주소}
$$

`dummy`가 1 byte이고 다음 `data`가 8-byte Alignment를 요구한다면, 그 사이에 Padding 7 bytes가 들어간다. 그러나 `OFS(data)`는 `dummy`의 1 byte까지 포함하므로 8이다. [STT 48:09] [STT 49:08] [STT 50:07]

자료의 두 실행 결과는 다음 차이를 보여 준다.

| Type | `-m64`: Size / Alignment | `-m32`: Size / Alignment |
|---|---:|---:|
| `char` | 1 / 1 | 1 / 1 |
| `short` | 2 / 2 | 2 / 2 |
| `int` | 4 / 4 | 4 / 4 |
| `long` | 8 / 8 | 4 / 4 |
| `long long` | 8 / 8 | 8 / 4 |
| `float` | 4 / 4 | 4 / 4 |
| `double` | 8 / 8 | 8 / 4 |
| `long double` | 16 / 16 | 12 / 4 |
| `void *` | 8 / 8 | 4 / 4 |

[M01 slide 29]

이 표에서 `double`은 두 실행 모두 Size가 8이지만 Alignment는 다르다. 따라서 Size와 Alignment는 별도 속성으로 읽어야 한다. 표는 해당 자료의 컴파일 결과이며, 모든 환경의 기본 Compiler 설정을 설명하는 표가 아니다.

#### Hexadecimal 주소와 실제 빈 공간

`varalign.c`는 Variable의 주소와 이전 Variable이 끝나는 위치를 비교한다. 자료 코드의 관찰 방식은 다음 계산이다.

$$
\text{gap}
=
\text{현재 시작 주소}
-
\text{이전 시작 주소}
-
\text{이전 Object 크기}
$$

M01 slide 32의 주소는 Hexadecimal(16진수)이다. 공통된 높은 자릿수를 생략해 끝부분만 보면 다음과 같다.

| 연속된 배치 | 계산 | Padding |
|---|---|---:|
| `int` `0x40` → `char` `0x44` | `0x44 - 0x40 - 4` | 0 |
| `char` `0x44` → `short` `0x46` | `0x46 - 0x44 - 1` | 1 |
| `short` `0x46` → `long long` `0x48` | `0x48 - 0x46 - 2` | 0 |
| `char` `0x51` → `float` `0x54` | `0x54 - 0x51 - 1` | 2 |
| `char` `0x58` → `double` `0x60` | `0x60 - 0x58 - 1` | 7 |
| `double` `0x60` → `long double` `0x70` | `0x70 - 0x60 - 8` | 8 |

[M01 slide 31] [M01 slide 32]

예를 들어 `0x60 - 0x58`은 십진수 8이다. 여기에 앞의 `char`가 차지한 1 byte를 제외해야 Padding 7이 나온다. 주소 차이 전체를 Padding이라고 부르면 한 Object의 크기를 중복 계산하게 된다.

Compiler는 대상 ABI에 맞춰 이러한 배치를 만든다. 프로그래머가 고수준 C를 작성할 때 모든 간격을 직접 배치하지는 않지만, System·Assembly 수준에서 코드를 읽을 때는 결과를 이해해야 한다. 이 출력은 특정하게 컴파일된 Global variable 배치이며, 전역 선언 순서가 항상 보장된다는 증거는 아니다. [M01 slide 30] [STT 51:07] [STT 52:04]

### [[concepts/arrays|Arrays]], [[concepts/struct|Structures]], [[concepts/union|Unions]]의 배치

세 자료구조는 여러 데이터를 묶지만, 저장 공간을 사용하는 방식이 다르다. Array는 같은 크기의 Element를 반복하고, Structure는 Member를 순서대로 배치하며, Union(공용체)은 Member들이 같은 저장 공간을 겹쳐 사용한다.

#### Array: 같은 간격으로 반복되는 Element

`T name[N]`에서 한 Element의 크기를 $s_T$라고 하면 다음 관계가 성립한다.

$$
s_T = \operatorname{sizeof}(T), \qquad
\text{Array 전체 크기} = N s_T
$$

시작 주소를 byte 단위 숫자 $x$로 표현하면, 유효한 index $i$에 대한 시작 주소는 다음과 같다.

$$
\operatorname{address}(name[i]) = x + i s_T
$$

[M01 slide 34] [STT 54:26]

이 식은 **byte 주소 계산**이다. C의 `name + i`는 이미 `T`의 크기를 반영하는 Pointer arithmetic(포인터 산술)이므로, 같은 뜻을 표현하려고 무조건 `name + i * sizeof(T)`라고 쓰면 이동 크기가 다시 곱해질 수 있다. Element index와 byte Offset을 구별해야 한다.

#### Structure: Member 사이와 끝의 Padding

Structure의 Member는 선언 순서로 겹치지 않게 놓이지만, 각 Member의 Alignment 때문에 중간에 Padding이 들어갈 수 있다. 따라서 뒤 Member의 주소는 앞 Member들의 크기뿐 아니라 그 사이 Padding까지 포함해 계산한다. [M01 slide 35] [M01 slide 36]

M01 slide 37의 핵심 그림은 다음 Structure의 Array를 확대한다.

```c
struct S2 {
    double v;
    int i[2];
    char c;
} a[10];
```

자료의 조건은 `double` 8 bytes, `int` 4 bytes, `char` 1 byte이며, 가장 큰 Alignment 요구는 8이다.

| 구성 요소 | Structure 시작으로부터의 Offset | 크기 |
|---|---:|---:|
| `v` | 0 | 8 |
| `i[0]` | 8 | 4 |
| `i[1]` | 12 | 4 |
| `c` | 16 | 1 |
| Tail padding(끝 패딩) | 17–23 | 7 |

Member 데이터만 합하면 17 bytes다. 그러나 전체 Structure 크기를 17로 두면 다음 Array element가 8-byte Alignment를 만족하지 못할 수 있다. 따라서 다음 Element에서도 Alignment가 유지되도록 전체 크기를 8의 배수인 24로 맞춘다.

$$
8 + 4 + 4 + 1 = 17,\qquad
\operatorname{sizeof}(\texttt{struct S2}) = 17 + 7 = 24
$$

그림의 `a[0]`, `a[1]`, `a[2]`는 각각 시작점에서 0, 24, 48 bytes 떨어져 있다. 이 간격을 Array stride(배열 원소 간 간격)로 읽으면 된다. 따라서 위 선언의 Array `a`는 Element 10개를 가지며, 전체 크기는 이 조건에서 $10 \times 24 = 240$ bytes다. [M01 slide 37] [STT 56:23] [STT 57:22]

그림에서 7-byte 회색 부분은 빠진 Member가 아니라 다음 Structure를 올바르게 배치하기 위한 Tail padding이다. `sizeof(Structure)`를 Member 크기의 단순 합으로 생각하면 Structure array 전체 크기와 뒤 원소의 주소까지 함께 틀리게 된다.

2024-2 중간 Q1(a)와 2025-1 중간 Q1(b)는 Structure 크기, Array 전체 크기, Member 위치, Pointer의 이동 단위를 함께 판단하게 한다. 풀이에서는 먼저 Member Offset 표와 최종 Structure 크기를 확정하고, 그다음 Array element의 시작 위치를 계산한다. 시험에 제시된 배치 계산을 일반화할 때도 Type 크기와 Alignment 가정을 먼저 확인해야 한다. [EX:sp_2024_2_midterm_q01 p.2] [EX:sp_2025_1_midterm_q01 p.2]

#### Union: 모든 Member가 Offset 0에서 시작

Union에서는 모든 Member가 동일한 시작 위치를 공유한다. Structure처럼 Member 크기를 차례로 더해 별도 공간을 확보하지 않는다. 자료의 겹친 사각형 그림에서 각 Member의 시작 주소가 모두 $x$인 이유다. Union의 Alignment는 Member 중 가장 큰 Alignment 요구를 만족해야 한다. [M01 slide 38] [M01 slide 39]

**이해를 위한 예시**로, 자료의 Type 조건에서 `double`과 `int`를 Member로 갖는 Union을 생각하면 두 Member는 모두 Offset 0에서 시작한다. Member별로 8과 4를 더해 12 bytes가 필요하다고 계산하는 것은 Structure식 사고를 잘못 적용한 것이다.

강의 밖 공식 보충: Union 끝에도 Padding이 가능하므로 최대 Member 크기와 `sizeof`를 항상 동일시하지 않는다. [S01 §6.7.2.1p17, WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

자료의 “최대 Member 크기”라는 요약은 공유 저장 공간의 동기를 설명하는 말로 읽되, Alignment 조건까지 없애는 공식으로 사용하지 않는다.

### [[concepts/parameter-passing|Parameter passing(매개변수 전달)]]: 값의 복사와 주소 값의 복사

Caller(호출하는 함수)는 다른 Function을 호출하는 쪽이고, Callee(호출되는 함수)는 호출을 받는 쪽이다. Caller의 데이터가 호출 뒤 바뀌는지를 판단하려면 Callee가 받은 것이 무엇이며 대입 대상이 어디인지 추적해야 한다. [M01 slide 41]

자료의 Pass by value(값 전달) 예시는 다음과 같다.

```c
int foo(int a, int b)
{
    a = 2 * a;
    return a + b;
}
```

Caller의 `x = 5`, `y = 6`을 인자로 전달하면 Callee는 각각의 값 복사본을 받는다. `a`가 10으로 바뀌어도 Caller의 `x`는 5다. 반환값은 $10 + 6 = 16$이다. [M01 slide 42]

주소를 전달하는 자료 예시는 다음과 같다.

```c
int foo2(int *a, int b)
{
    *a = 2 * *a;
    return *a + b;
}
```

이번에는 Caller가 `&x`와 `y`를 전달한다. Callee가 받은 `a`도 주소 값의 복사본이지만, `*a`는 Caller의 `x`에 접근한다. 따라서 `*a = 2 * *a`를 수행하면 `x`가 10이 되고 반환값은 역시 16이다. 두 경우는 반환값이 같아도 Caller에 남기는 효과가 다르다. [M01 slide 43] [STT 59:22]

슬라이드의 Pass by reference(참조 전달)라는 표현은 이 주소를 통한 원본 변경 효과를 설명한다. C에 별도의 parameter 전달 기법이 추가된다는 뜻으로 읽지 않는다. **주소도 복사되는 값이고, 그 주소를 따라가면 원본 데이터에 접근할 수 있다**는 것이 핵심이다.

#### `foo2`의 Load–연산–Store 추적

M01 slide 44의 Assembly(어셈블리) 예시는 위 동작을 명령어 수준에서 보여 준다. 자료의 호출 상태에서 `%rdi`는 `x`를 가리키는 주소를, `%esi`는 `b`의 값 6을 담는다.

```asm
mov  (%rdi), %eax
add  %eax, %eax
mov  %eax, (%rdi)
add  %esi, %eax
ret
```

| 명령어 | 수행하는 일 | 예시 상태 |
|---|---|---|
| `mov (%rdi), %eax` | `%rdi`가 가리키는 Memory에서 `int`를 Load(읽기) | `%eax = 5` |
| `add %eax, %eax` | 읽은 값을 두 배로 계산 | `%eax = 10` |
| `mov %eax, (%rdi)` | 계산값을 같은 Memory 위치에 Store(쓰기) | Caller의 `x = 10` |
| `add %esi, %eax` | `b`를 더해 반환값 구성 | `%eax = 16` |
| `ret` | Caller로 복귀 | 반환값 16 |

[M01 slide 44] [STT 01:00:25] [STT 01:01:24]

세 번째 명령어는 `%rdi` 자체를 10으로 바꾸지 않는다. `%rdi`에 담긴 주소가 가리키는 Memory를 바꾼다. 괄호가 있는 `(%rdi)`와 Register 자체인 `%rdi`를 구별하는 것이 이 코드 추적의 중심이다.

#### Array argument는 전체 Array 복사가 아니다

M01 slides 45–46에서 Caller의 Array는 `x[2] = 2`인 상태다. 시작 위치를 전달받은 Callee가 다음 대입을 수행하면 Caller에서도 `x[2]`가 5가 된다.

```c
a[2] = 5;
```

자료에서 `int` 크기는 4 bytes이므로 index 2의 byte Offset은 다음과 같다.

$$
2 \times 4 = 8\text{ bytes}
$$

이에 대응하는 명령어는 다음과 같다.

```asm
movl $0x5, 0x8(%rdi)
```

이 명령어는 `%rdi + 8` 위치에 5를 **저장**한다. Array 전체를 Callee 쪽에 복사하는 것도 아니고, 8번째 원소를 고르는 것도 아니다. 슬라이드의 Array location 전달은 첫 원소를 가리키는 Pointer value의 복사로 이해한다. [M01 slide 45] [M01 slide 46] [STT 01:02:17]

### [[concepts/command-line-arguments|Command line parameters(명령행 매개변수)]]와 `argc`, `argv`

명령행에서 받은 입력은 `main`의 `argc`와 `argv`로 이어진다. `argc`는 argument 수이고, `argv`는 각 argument 문자열을 가리키는 `char *`들의 Array로 설명된다. 즉, `argv`를 보면 먼저 Pointer 하나를 고르고, 그 Pointer를 통해 문자열에 접근한다. [M01 slide 47] [STT 01:03:22]

자료의 일반적인 실행 예시에서는 `argv[0]`가 프로그램 이름이다. `i = 0`부터 `i < argc`까지 순회하면 전달된 각 문자열을 볼 수 있다. 여기에서도 “Pointer들의 Array”와 “각 Pointer가 가리키는 문자열”은 별도 대상이다.

강의 밖 공식 보충: `argc`는 음이 아니며, 프로그램 이름 설명은 `argc > 0`일 때 적용된다. [S01 §5.1.2.2.1p2, WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

따라서 슬라이드의 `argc >= 1` 설명은 보통의 명령행 예시로 읽는다. 이어지는 Dirtree 과제에서는 이 argument들이 Option(옵션), Pattern(패턴), 탐색 대상 Directory(디렉터리) 목록으로 해석된다.

### [[concepts/directory-traversal|Directory traversal(디렉터리 순회)]]: Dirtree가 처리하는 일

Dirtree는 Directory 안의 Entry(항목)를 재귀적으로 방문하고, 정렬된 목록과 Metadata(메타데이터)를 출력한 뒤 통계를 만드는 도구다. 강의에서 제시한 학습 목적은 File system(파일 시스템) 순회, 파일 정보 조회, 정확한 출력 형식, 오류 처리, C의 문자열·Pattern 처리를 함께 연습하는 것이다. [M02 slide 2] [M02 slide 3] [STT 01:06:20]

전체 동작은 다음 책임으로 나뉜다.

1. 각 탐색 대상 Directory를 방문한다.
2. Directory 안의 Entry를 수집해 정렬한다.
3. 조건에 맞는 Entry의 이름과 정보를 출력한다.
4. 대상별 Summary(요약 통계)를 만든다.
5. 대상이 여러 개이면 Aggregate statistics(전체 합산 통계)를 출력한다.

각 Directory에서는 Directory가 일반 파일보다 먼저 나오고, 이름순으로 정렬한다. 특수 Entry `.`와 `..`는 제외한다. 자료는 정렬을 위한 `dirent_compare()`가 제공된다고 안내한다. 모든 하위 항목을 하나의 평평한 목록으로 모아 전체 이름순으로 출력하는 방식과 구별해야 한다. [M02 slide 5] [M03: Dirtree Specification → Operation]

명령행 형식은 다음과 같다.

```text
dirtree [Options] [Directories]
```

| 항목 | 의미 |
|---|---|
| `-d <depth>` | 최대 탐색 깊이 지정 |
| `-f <pattern>` | 이름에 적용할 Pattern 지정 |
| `-h` | 도움말 표시 |
| Directory 목록 | 하나 이상 지정할 수 있으며, 생략하면 현재 Directory 사용 |

`-d`와 `-f`는 함께 사용할 수 있고 둘 다 생략할 수도 있다. README는 탐색 대상 Root directory(최상위 대상 디렉터리)를 최대 64개까지 받는다고 명시한다. 이 한도는 자료 보충이며 모든 숫자가 강의에서 낭독되었다는 뜻은 아니다. [M02 slide 4] [M03: Dirtree Specification → Command line arguments]

### Dirtree의 Metadata, 출력 폭, 통계

출력은 단순히 이름만 나열하는 것이 아니다. Depth(깊이)에 따라 두 칸씩 Indentation(들여쓰기)을 늘리고, 이름 오른쪽에는 정해진 열에 정보를 배치한다. 강의에서 열의 세부 설명 일부를 건너뛰었으므로, 다음의 정확한 Type·폭 규정은 M02와 README에 근거한 자료 보충을 포함한다. [STT 01:08:16] [STT 01:09:12]

#### Metadata와 File type

User와 Group은 파일의 소유 주체를 나타내며 `user:group` 형태로 표시한다. File size(파일 크기)는 bytes 단위 크기이고, Disk blocks(디스크 블록 수)는 파일이 디스크에서 차지하는 block 수다. 이 둘은 단위와 의미가 다르므로 같은 값으로 취급하면 안 된다. [M02 slide 7]

| File type(파일 종류) | 표시 문자 |
|---|---|
| Regular file(일반 파일) | 공백 |
| Directory | `d` |
| Symbolic link(심볼릭 링크) | `l` |
| FIFO(named pipe, 이름 있는 파이프) | `f` |
| Socket(소켓) | `s` |

Character device(문자 장치)와 Block device(블록 장치)는 이 과제에서 Regular file로 취급한다. 이는 현재 과제의 단순화 규정이다. [M02 slide 7] [M03: Dirtree Specification → Output → Detailed information]

#### M02 slide 11의 출력 표 읽기

M02 slide 11에는 위쪽의 필드 규칙 표와 아래쪽의 열 위치 눈금이 함께 있다. 읽을 때는 **폭**, **좌우 정렬**, **초과 처리**를 별개로 확인해야 한다.

README는 전체 행 길이를 100 characters로 제시하고, 파일 이름의 encoding(문자 인코딩)을 UTF-8로 한정한다. **이해를 위한 ASCII 예시**로, Depth 3이면 Indentation은 6칸이다. 54-byte 필드에서 이름에 남는 공간은 48 bytes다. 이름까지 합해 정확히 54 bytes라면 그대로 출력하고, 길어서 `...`를 붙여야 한다면 그 세 점도 필드 폭 안에 포함되어야 한다.

README는 Total size와 Total blocks가 `int` 범위를 넘을 수 있으므로 충분한 Type을 사용하도록 안내한다. 전체 Path 길이의 별도 overflow 처리는 요구하지 않고 `MAX_PATH_LEN`을 사용하도록 하며, 필요한 경우 그 값을 조정할 수 있다고 한다. #### 대상별 Summary와 Aggregate statistics

각 Root에는 Header(머리 출력), Entry 목록, Footer(끝 출력)와 한 줄 통계가 있다. 여러 Root를 지정했을 때만 마지막 Aggregate block이 붙는다. 출력에 Root가 보인다는 이유만으로 Root 자체를 Entry 합계에 추가하지 않는다. [M02 slide 8] [M02 slide 10]

README의 한 자료 예시에서는 두 대상의 Size가 각각 9,192 bytes와 14 bytes이므로 합계가 다음과 같다.

$$
9192 + 14 = 9206\text{ bytes},\qquad 16 + 0 = 16\text{ blocks}
$$

다른 자료 예시에서는 Regular file 4개, Link 2개, Pipe 1개, Socket 1개이므로 Total entries는 8이다. Size는 $3086 + 500 = 3586$ bytes, Blocks는 $16 + 16 = 32$다. **Total entries 항목은 Aggregate에만 나오며, 대상별 한 줄 Summary의 항목으로 추가하지 않는다.** [M03: Dirtree Overview] [M03: Dirtree Specification → Output → Per-directory summary & Aggregate statistics]

개수 표현도 출력 계약의 일부다. 정확히 1일 때만 Singular(단수형)를 쓰고, 0 또는 2 이상이면 Plural(복수형)를 쓴다. 예를 들어 0은 `files`, 1은 `file`이다. 수치가 맞아도 이런 문법과 공백이 다르면 요구한 출력과 일치하지 않을 수 있다. [M02 slide 9]

### Depth limit과 Name filtering은 서로 다른 조건이다

Depth limit은 **얼마나 깊이 방문할 것인지**, Name filtering(이름 필터링)은 **어떤 Entry를 상세 출력하고 통계에 포함할 것인지**를 결정한다. 둘을 같은 조건처럼 취급하면 하위의 일치 항목을 놓치거나 제외된 항목을 통계에 더하는 오류가 생긴다.

#### Root는 Depth 0이다

Root 자체는 Depth 0, 바로 아래 Entry는 1, 그 아래는 2다. `-d`가 지정한 깊이까지의 Entry만 표시·탐색하며, 깊이 때문에 생략한 Entry는 대상별 Summary와 Aggregate 모두에서 제외한다. 허용값은 1–20이고 기본값은 20이다. [M02 slide 12] [M02 slide 15] [STT 01:12:01] README는 Skeleton의 `MAX_DEPTH`가 20으로 정의되어 있다고 명시하며, 강의와 M02도 이 Macro를 사용하도록 안내한다. 이번 과제에서는 20보다 깊은 경우를 지원할 필요가 없다. [M03: Option 1: Depth limit → Examples, Notes] [M02 slide 15] [STT 01:12:01]

README의 자료 예시에서는 Root 아래의 `b`가 Depth 1, `b` 아래의 Directory `c`와 File `f`가 Depth 2, `c` 아래의 `d`가 Depth 3이다.

| 설정 | 포함되는 주요 Entry | File / Directory 수 |
|---|---|---|
| `-d 1` | `b` | 0 / 1 |
| `-d 2` | `b`, `c`, `f` | 1 / 2 |
| `-d 3` | 위 항목과 `d` | 1 / 3 |

자료의 `# depth N` 표시는 설명용 주석이며 실제 출력 요구가 아니다. STT에는 Root를 0이라고 설명한 뒤 2라고 말한 부분도 있어 검증 필요지만, M02와 README의 명시 규칙은 Root 0으로 일치한다. [M02 slide 13] [M02 slide 14] [M03: Option 1: Depth limit → Examples] [STT 01:11:03]

#### Basename과 Partial matching

Pattern은 전체 Path가 아니라 Basename(경로의 마지막 이름)에 적용한다. Partial matching(부분 일치)이므로 이름 안의 연속된 일부 문자열이 맞아도 성공하고, Case-sensitive(대소문자 구별)이다. 이름 `abc`는 Pattern `b`에 맞지만, 부모 이름에 `abc`가 포함되어 있고 현재 Basename이 `def`라면 그것만으로 `abc` Pattern에 맞지는 않는다. [M02 slide 17] [STT 01:12:54]

일치한 Entry는 상세 정보와 통계에 포함한다. 비일치 File은 제외하지만, **비일치 Directory는 Depth 제한 안에서 계속 탐색한다.** 아래쪽에 일치하는 Descendant(하위 항목)가 있을 수 있기 때문이다. [M02 slide 18] [STT 01:13:52]

| Directory의 상태 | 출력 | 통계 |
|---|---|---|
| 자기 이름이 일치 | 상세 정보 포함 | 포함 |
| 자기 이름은 비일치지만 하위에 일치 항목이 있음 | 이름과 Indentation만 표시 | 그 Directory 자체는 제외 |
| 자기 이름도 비일치하고 하위에도 일치 항목이 없음 | 해당 비일치 Subtree(하위 트리)를 생략 | 제외 |

Root는 README에서 Filter(필터) 적용 예외로 지정되어 있다. 비일치 Ancestor(상위 항목)의 이름을 보여 주는 목적은 일치한 항목이 트리 어디에 있는지 전달하는 데 있다. **화면에 보이는 모든 이름이 통계에 포함되는 것은 아니다.** [M03: Option 2: File name filtering → Handling directory entries]

M02 slide 21의 자료 그림에서는 `a?c`를 적용했을 때 `aXc`, `abc`, `axc`가 남는다. 비일치 Directory인 `subdir1`은 그 아래 `aXc`로 이어지는 경로를 보여 주기 위해 이름만 표시된다. 결과는 3 files, 0 directories, 3 bytes, 24 blocks다. 이름만 보이는 `subdir1`의 크기나 개수를 더하면 안 된다. 이 상세 예시들은 강의에서 건너뛴 자료 보충이다. [M02 slide 21] [STT 01:14:44]

**자료 간 충돌:** README의 정식 Filtering 규칙과 강의·M02는 비일치 Directory도 계속 탐색한다고 설명한다. 그러나 README의 `Implementation` 일부 항목은 비일치 Directory를 탐색하지 말라고 적는다. 두 지시는 내부적으로 충돌한다. 위 설명은 강의와 명시적인 Matching 규칙에 따른 것이며, README 전체가 일관되다고 간주하지 않는다. [M03: Your Task → Implementation]

### [[concepts/pattern-matching|Pattern matching(패턴 일치)]]의 연산자와 오류 경계

현재 과제는 범용 Regular expression(정규 표현식) 전체를 구현하는 과제가 아니다. 자료에 정의된 세 기능과 지원 범위를 먼저 고정해야 한다.

| 연산자 | 현재 과제의 의미 |
|---|---|
| `?` | 임의의 문자 정확히 하나 |
| `*` | 바로 앞 문자 또는 Group(그룹)의 0회 이상 반복 |
| `()` | 여러 Pattern 요소를 하나의 Group으로 묶음 |

[M02 slide 19] [M03: Option 2: File name filtering → Supported operators]

`a(bc)*d`에서는 `bc`가 반복 단위다. 0회이면 `ad`, 1회이면 `abcd`, 2회이면 `abcbcd`가 된다. `*`를 독립적으로 임의 문자열 전체를 받아들이는 기호라고 생각하면 현재 과제 규칙과 달라진다. [STT 01:14:44]

자료의 다른 예시도 같은 방식으로 분해할 수 있다.

| 자료 Pattern | 구조 읽기 | 일치하는 부분 문자열의 예 |
|---|---|---|
| `a?c` | `a` + 임의 한 문자 + `c` | `abc`, `axc` |
| `ab*` | `a` + `b`의 0회 이상 반복 | `a`, `ab`, `abb` |
| `(ab)*c` | `ab` Group의 반복 + `c` | `c`, `abc`, `ababc` |
| `ab?(de)*f` | `ab` + 임의 한 문자 + `de` 반복 + `f` | `abcf`, `abXdef` |
| `abc?d*(ef)` | `abc` + 임의 한 문자 + `d` 반복 + `ef` | `abcXef`, `abcXddef` |

[M02 slide 20] [M03: Option 2: File name filtering → Pattern matching examples]

마지막 예시의 `(ef)`에는 `*`가 붙어 있지 않으므로 `ef`가 0회 이상 반복된다는 뜻이 아니다. Group으로 묶는 일과 반복시키는 일은 별도 연산이다.

README의 두 번째 Pattern 자료에서는 Filtering 전 7 files와 2 directories가 있고, `(ab)*c`를 적용하면 6 files가 남는다. `b(ab)*c`로 바꾸면 이름 `c`가 제외되어 5 files가 남는다. 후자의 `abc`는 이름 전체가 Pattern과 같은 모양이어서가 아니라, 내부의 `bc`가 `b` + Group 0회 + `c`로 일치하기 때문에 남는다. 비일치 Ancestor는 이때도 통계에서 제외된다. [M03: Option 2: File name filtering → Pattern matching examples]

Pattern은 Shell(명령 해석기)이 먼저 해석하지 않도록 인용부호로 감싸 전달한다. README의 최대 길이는 끝의 `\0`을 포함해 64이다. `?`, `*`, 괄호를 연산자가 아닌 문자 그대로 취급해야 하는 경우는 요구하지 않는다. [M03: Option 2: File name filtering → Supported operators]

#### Invalid pattern과 미지원 범위

Invalid pattern(문법이 잘못된 패턴)은 다음과 같이 분류할 수 있다.

| 문제 | 자료 예시 | 이유 |
|---|---|---|
| 빈 전체 Pattern | 빈 문자열 | 전체 Pattern에 요소가 없음 |
| 빈 Group | `a()b` | Group 내부에 요소가 없음 |
| 선행 대상 없는 `*` | `*abc` | 반복할 앞 요소가 없음 |
| 연속된 `*` | `a**b` | 유효한 문자·Group 뒤에 붙는 규칙 위반 |
| 괄호 순서·균형 오류 | `a)bc(`, `(abc` | Group을 올바르게 구성하지 못함 |

[M02 slide 22]

STT의 `a*b` 관련 발화는 표기가 불명확하므로 그것 자체를 금지하는 규칙으로 채택하지 않는다. 슬라이드의 명확한 Invalid 예시는 `a**b`다. [STT 01:15:40]

Group 내부에 `*`가 적용되는 경우와 Nested group(중첩 그룹)은 채점에 포함하지 않는 별도 범위다. 이것을 모든 Invalid 입력과 같은 범주로 합치면 안 된다. “문법 오류로 검출해야 하는 입력”과 “지원하지 않아도 되는 복잡한 입력”을 나누어 읽어야 한다. [M02 slide 23] [M03: Error handling]

Invalid pattern을 발견하면 다음 메시지를 `stderr`에 출력한다.

```text
Invalid pattern syntax
```

`stdout`에 출력하는 것이 아니며, README는 Directory listing이나 통계 없이 종료하도록 한다. 자료는 제공 `panic()`의 사용을 안내한다. [M02 slide 24] [M03: Error handling]

오류 채점 범위에는 자료상 긴장이 있다. README는 Invalid pattern만 오류 채점 대상이라고 하며, 권한 거부·없는 Path·탐색 중 삭제나 이름 변경·allocation 실패 등을 제외한다. 반면 마지막 배점표에는 더 넓은 표현인 `Error and overflow handling` 5점이 있다. 두 표현의 정확한 점수 대응은 **검증 필요**이며, 이 노트가 임의로 새 채점 규칙을 정하지 않는다. [M02 slide 33] [M03: Error handling]

#### 제공 Pseudocode가 보여 주는 사고방식

M02 slide 25의 Pseudocode(의사 코드)는 `*`만을 다루는 불완전한 Hint(힌트)다. 두 층의 역할을 보여 준다는 점이 중요하다.

- 바깥 `match`는 문자열의 여러 시작 위치에서 일치를 시도한다.
- `submatch`는 특정 시작점에서 Pattern을 맞춰 본다.
- 반복을 만났을 때 0회로 넘기는 가능성과, 한 번 이상 소비하는 가능성을 나누어 생각한다.

이는 Partial matching과 Recursion(재귀)의 관계를 설명한다. 자료 코드에는 비어 있는 처리 부분이 있고, `?`, Group, 문자열 끝의 경계 조건까지 모두 해결한 완성본이 아니다. [M02 slide 25] [STT 01:16:37] [STT 01:17:34]

2025-2 중간 Q2 역시 여러 시작 위치의 탐색과 재귀적 종료 조건을 요구하지만, **그 문항의 `*`는 임의 길이의 알파벳 문자열을 받는 독립 Wildcard(와일드카드)**다. 현재 과제의 “바로 앞 요소 반복”과 의미가 다르다. 또한 그 문항에는 처음의 Pattern과 대상 문자열이 비어 있지 않다는 가정이 있다. 따라서 연결은 탐색 책임과 종료 조건을 분석하는 방식에 한정되는 **부분 연결**이다. 기출의 코드나 답을 현재 matcher의 구현으로 옮길 수 없다. [EX:sp_2025_2_midterm_q02 p.5]

### Dirtree의 설계 책임과 Memory 관리

다음 내용은 주로 README의 운영·구현 안내를 보충한다. 완성 코드를 제시하는 대신, 각 부분이 어떤 책임을 가지는지를 구별한다.

README는 Skeleton code(골격 코드)를 보기 전에 먼저 전체 흐름을 설계해 보라고 권한다. 이후 Skeleton을 수정하거나 처음부터 작성할 수 있다. 제시된 큰 책임 구분은 다음과 같다.

| 부분 | 책임 |
|---|---|
| `main()` | 여러 Root의 처리 순서, Header·Summary·Aggregate 관리 |
| `process_dir()` | Directory 열기, Entry 수집·정렬·처리, 하위 탐색, 닫기 |
| `print_formats` | 정해진 출력 형식 |
| `struct summary` | 대상별·전체 통계 표현 |
| `get_next()` | 특수 Entry를 제외하며 다음 Entry를 읽는 보조 기능 |
| `dirent_compare()` | 정렬 비교 |
| `syntax()`와 argument parsing | 명령행 형식 해석 |

[M03: Your Task → Design] [M03: Your Task → Implementation] [M03: Hints → Skeleton code]

이는 README가 설명하는 역할이다. 앞서 확인한 Filtering 관련 구현 안내의 충돌은 이 표만으로 해결되지 않는다. 또한 실제 Skeleton 내부가 이 설명과 어떻게 대응하는지까지 확인한 것으로 해석하지 않는다.

#### Entry 수와 Recursion depth를 함께 보아야 하는 이유

README는 한 Directory의 Entry 수에 상한을 두지 않는다. 따라서 “아주 큰 고정 배열 하나면 충분하다”는 가정은 요구사항과 맞지 않는다. Entry 수가 용량을 넘으면 Out-of-bounds access(범위 밖 접근)가 발생할 수 있다.

큰 Local array를 재귀 Function 안에 두는 경우에는 깊이도 중요하다. **이해를 위한 단순 예시**로, 호출마다 큰 배열을 하나 유지한 채 하위 호출로 내려가면 이전 호출의 배열이 남아 있는 동안 다음 호출의 배열도 필요하다. 한 번의 호출에서 사용량이 괜찮아 보여도 깊이가 늘면 Stack 사용량이 누적된다.

이 때문에 README는 Entry 수와 Depth를 함께 고려하고, 불필요한 Memory 사용을 피하며, 더 이상 필요하지 않은 Dynamic allocation을 해제하도록 요구한다. 이 부분은 앞에서 배운 Stack·Heap·`free`가 과제 설계와 직접 만나는 지점이다. [M03: Your Task → Implementation, Memory usage]

#### Library call을 목적별로 구별하기

자료가 제시한 Library call(라이브러리 호출)은 다음 역할로 정리할 수 있다.

| 목적 | 호출 | 자료가 설명하는 역할 |
|---|---|---|
| 문자열 비교 | `strcmp()` | 두 문자열 비교 |
| 제한된 문자열 복사 | `strncpy()` | 지정 길이까지 복사 |
| 문자열 복제 | `strdup()` | 복제한 저장 공간을 사용 후 `free()` |

[M02 slide 29] [M03: Hints → C library calls]

특히 `stat()`은 Link를 따라 대상의 Metadata를 얻는 반면, `lstat()`은 Link를 따라가지 않는다. 어떤 정보를 출력하려는지 먼저 생각해야 적절한 조회를 고를 수 있다. 위 표는 각 API의 역할 요약이며 전체 계약을 대체하지 않는다. 자료도 개별 문서를 읽도록 안내한다.

### File system에서 Memory abstraction으로

강의는 File system 학습 다음에 Memory abstraction으로 넘어간다고 소개한다. 이전 회차는 [[courses/system_programming/lectures/2026-09-21-lecture-05|9월 21일 한국어 노트]]와 [[courses/system_programming/lectures/en/2026-09-21-lecture-05|September 21 English notes]]에서 이어 볼 수 있다. 이번 회차에서 연결을 만드는 질문은 **“파일에서 읽은 데이터를 어느 주소에, 몇 bytes만큼 저장하는가?”**이다. `read`의 주소·길이 인자를 이해하려면 Pointer와 Array의 차이가 필요하고, Directory entry를 저장하려면 Dynamic allocation과 Structure layout을 함께 이해해야 한다. ## 핵심 요약

- **주소를 읽을 때는 대상부터 정한다.** Pointer 자신의 주소, 저장된 주소, 가리키는 값은 서로 다르다. 서로 다른 Process의 같은 Virtual address도 공유 상태를 보장하지 않는다.
- **Memory layout은 역할과 실행 시점을 구별하는 지도다.** 실행 파일에 초기 내용을 저장하는 문제, 실행 중 공간을 확보하는 문제, 접근 권한은 각각 다른 판단이다.
- **Array와 Pointer는 같은 Object가 아니다.** 주소처럼 사용되는 Array 식이 있어도 `sizeof(Array)`와 `sizeof(Pointer)`의 의미는 다르다. `read`에는 저장 위치와 byte 수를 따로 전달한다.
- **크기와 Alignment는 별도 조건이다.** 강의의 x86-64 Linux 중심 값은 `char/short/int/long = 1/2/4/8`, `float/double = 4/8`, Pointer 8 bytes다. 다른 환경에는 해당 ABI의 조건을 적용한다.
- **Structure 계산은 Member 크기의 합에서 끝나지 않는다.** Member 사이 Padding과 Tail padding을 반영해야 Array stride까지 맞는다. Union은 Member들이 같은 시작 위치를 공유한다.
- **C의 주소 전달도 주소 값의 복사다.** Caller의 데이터를 바꾸는 것은 복사된 Pointer를 통한 Store다. `%rdi`와 `(%rdi)`를 구별한다.
- **Dirtree에서는 방문·표시·집계를 나눠 판단한다.** 비일치 Directory도 Depth 안에서는 탐색하며, 일치한 하위 항목을 보여 주기 위한 Ancestor 이름은 통계에서 제외한다.
- **과제 명세에는 운영 조건도 포함된다.** 출력 폭, 오류 메시지, 허용 Library, 평가환경, 제출 형식을 함께 확인한다. 현재 안내된 마감은 **2026년 10월 9일 금요일 21:00**이다. [M02 slide 32] [M03: Important Dates]

### 1단계: 개념을 설명하며 회상하기

#### 1. Function과 Variable의 주소를 출력하면 무엇을 관찰할 수 있는가?

반복 실행 주소와 두 Process의 주소를 비교할 때 각각 무엇을 판단할 수 있고, 무엇은 판단할 수 없는가?

<details><summary>정답</summary>

Function의 코드와 Variable의 데이터가 놓인 위치를 관찰할 수 있다. 반복 실행 주소 비교는 ASLR의 효과를 이해하는 단서지만, 특정 실행 결과만으로 모든 보안 효과를 증명하지는 못한다. 두 Process의 같은 주소 숫자만으로 공유 여부를 결정할 수도 없다. 공유 여부는 한쪽 변경이 다른 쪽에서 같은 상태의 변화로 관찰되는지와 공유 구성에 따라 판단한다. [M01 slide 4] [M01 slide 6] [M01 slide 7]

</details>

#### 2. Variable name, Type, 주소, 값은 어떤 관계인가?

선언 순서가 저장 순서를 보장하는지도 설명하라.

<details><summary>정답</summary>

Name은 데이터를 참조하는 Label이고, Type은 필요한 저장 공간의 크기와 데이터 해석에 관계한다. 주소는 저장 위치이며 값은 그 위치의 내용이다. 자료의 연속 배치는 예시이므로 일반 Variable이 선언 순서대로 인접한다고 보장할 수 없다. 강의의 계산 설명은 Memory에서 Register로 값을 가져와 연산하는 흐름이다. [M01 slide 9] [M01 slide 10] [STT 14:01]

</details>

#### 3. `.bss`가 실행 파일 공간을 절약한다는 말은 실행 중 Memory도 필요 없다는 뜻인가?

Heap, mapped region, Stack과 parameter의 위치도 함께 설명하라.

<details><summary>정답</summary>

아니다. 초기 내용 전체를 실행 파일에 저장하지 않는 것과 실행 중 저장 공간이 필요한 것은 별개다. 자료는 Run-time heap, `brk`, Shared library의 mapped region, User stack을 구별한다. 그림의 Intel 환경에서는 Stack이 높은 주소에서 낮은 주소로 자란다. 후반 자료가 parameter를 Register로 전달하므로 모든 parameter가 Stack에 놓인다고 일반화하지 않는다. [M01 slide 11] [M01 slide 44]

</details>

#### 4. `p`, `&p[0]`, `p[0]`, `&p`는 어떻게 다른가?

`p`가 유효한 문자 block의 시작을 가리킨다고 가정하라.

<details><summary>정답</summary>

`p`와 `&p[0]`는 첫 문자의 주소 값을 나타내고, `p[0]`는 그 문자의 값이다. `&p`는 주소를 저장하는 Pointer object 자체의 주소다. Pointer-to-pointer는 이 Pointer object의 주소를 저장하여 연결을 한 단계 더 따라가게 한다. [M01 slide 15] [M01 slide 18]

</details>

#### 5. Partial initializer, `malloc`, `sizeof`, `read`를 함께 사용할 때 무엇을 구별해야 하는가?

<details><summary>정답</summary>

부분 초기화된 Array의 나머지 원소와, `malloc` 뒤 일부 원소에만 대입한 block의 나머지는 같은 초기 상태를 보장하지 않는다. `sizeof`는 Array 전체와 Pointer object를 구별하여 적용한다. `read`의 두 번째 인자는 저장 주소이고 세 번째 인자는 byte 수다. 단일 문자에는 그 문자의 주소가 필요하며, 동적 저장 공간은 사용이 끝나면 `free`한다. [M01 slide 19] [M01 slide 20] [STT 28:44]

</details>

#### 6. Size, Alignment, Offset, Padding은 어떻게 다른가?

`size.c`의 `dummy`와 `data`를 이용하여 설명하라.

<details><summary>정답</summary>

Size는 Object가 차지하는 크기, Alignment는 시작 주소가 만족해야 하는 조건이다. Offset은 기준 시작점부터의 거리이고, Padding은 배치 조건을 맞추기 위한 간격이다. `OFS(data)`에는 앞의 `dummy` 1 byte와 그 뒤 Padding이 함께 포함된다. Machine은 C Structure 선언 자체보다 Compiler가 정한 bytes와 Offset을 통해 데이터에 접근한다. [M01 slide 22] [M01 slide 28] [M01 slide 29]

</details>

#### 7. Array, Structure, Union의 주소 계산은 어떻게 다른가?

<details><summary>정답</summary>

Array element의 byte Offset은 index와 Element 크기의 곱이다. Structure는 선언 순서의 Member 크기와 Padding을 반영하고, 전체 크기는 다음 Array element의 Alignment도 만족해야 한다. Union의 Member들은 모두 Offset 0에서 겹치며 최대 Member Alignment 요구를 만족해야 한다. [M01 slide 34] [M01 slide 36] [M01 slide 39]

</details>

#### 8. 반환값이 같아도 Caller의 최종 상태는 다를 수 있는가?

Array argument와 `argv`도 Pointer 관점에서 설명하라.

<details><summary>정답</summary>

그렇다. 값 복사본만 수정한 경우와 주소를 따라 Caller의 원본을 수정한 경우는 반환값이 같아도 원본의 상태가 다를 수 있다. Array argument는 자료 예시에서 시작 위치의 Pointer value를 전달한다. `argv`는 문자열 자체 하나가 아니라 각 문자열을 가리키는 Pointer들의 Array이며, 주어진 `argc` 범위에서 각 인자를 읽는다. [M01 slide 42] [M01 slide 43] [M01 slide 46] [M01 slide 47]

</details>

#### 9. Dirtree의 Directory는 언제 상세 출력되고 언제 통계에 포함되는가?

<details><summary>정답</summary>

Depth 안에서 자기 이름이 Pattern에 맞는 Directory는 상세 출력되고 통계에도 포함된다. 자기 이름은 맞지 않지만 하위에 일치 항목이 있으면 이름만 표시하고 그 Directory 자체는 집계하지 않는다. 하위에도 일치 항목이 없는 비일치 Subtree는 생략한다. Root는 Filter 예외이며, Depth 때문에 제외한 Entry는 두 종류의 통계 모두에서 제외한다. [M02 slide 15] [M02 slide 18] [M03: Option 2: File name filtering → Handling directory entries]

</details>

#### 10. Dirtree에서 정확한 숫자만 출력하면 요구사항을 충족하는가?

<details><summary>정답</summary>

아니다. Depth당 두 칸 Indentation, 필드 폭·정렬·절단, File type 표시, 대상별 Header·Footer·Summary도 맞아야 한다. 여러 Root일 때만 Aggregate를 출력하고, Total entries는 Aggregate에만 둔다. 개수가 1이면 Singular, 0이나 2 이상이면 Plural을 사용한다. [M02 slide 6] [M02 slide 9] [M02 slide 11] [M03: Dirtree Specification → Output]

</details>

#### 11. `*`의 의미, Invalid pattern, 지원 제외 범위, 제공 Hint는 어떻게 구별하는가?

<details><summary>정답</summary>

현재 과제의 `*`는 바로 앞 문자나 Group의 0회 이상 반복이다. 빈 Pattern·빈 Group·잘못된 `*`·잘못된 괄호는 Invalid pattern이며, Group 내부의 `*`와 Nested group은 별도의 지원 제외 범위다. 오류는 지정 메시지를 `stderr`에 내고 목록·통계 없이 종료한다. 제공 Hint는 여러 시작점의 탐색과 한 시작점의 검사 역할을 보여 주지만 완성된 matcher는 아니다. [M02 slide 19] [M02 slide 22] [M02 slide 23] [M02 slide 25] [M03: Error handling]

</details>

#### 12. 설계·Library·Test 환경을 구별해야 하는 이유는 무엇인가?

<details><summary>정답</summary>

`main`의 여러 Root 관리와 `process_dir`의 한 Directory 처리는 책임이 다르다. Entry 수에는 상한이 없고 재귀 호출은 Stack 사용을 누적시킬 수 있다. Library도 문자열 비교·복사·형식 출력, Directory 열기·읽기·닫기, Metadata와 소유자 이름 조회, 정렬의 역할로 나누어 선택한다. `stat`과 `lstat`의 Link 처리 차이를 확인하고, 외부 matcher와 `scandir`는 사용하지 않는다. 개발환경이 달라도 최종 확인은 평가환경인 Bacchus VM에서 한다. 다음 Type의 Size/Alignment는 `char` 1/1, `int` 4/4, `double` 8/8이다. Member는 선언 순서대로 놓이고, 조건을 만족하는 최소 Padding을 사용하며, Structure 전체 크기는 최대 Member Alignment의 배수로 맞춘다.

```c
struct Packet {
    char tag;
    int count;
    double value;
    char mark;
};
```

1. Member Offset과 `sizeof(struct Packet)`을 구하라.
2. 이 Structure 3개로 된 Array의 크기와, Array 시작에서 index 1 원소의 `value`까지의 byte Offset을 구하라.
3. Member 순서를 `double value`, `int count`, `char tag`, `char mark`로 바꾸면 전체 크기는 어떻게 달라지는가?

<details><summary>풀이와 채점 포인트</summary>

원래 순서의 배치는 다음과 같다.

| 부분 | Offset | 크기 |
|---|---:|---:|
| `tag` | 0 | 1 |
| 내부 Padding | 1–3 | 3 |
| `count` | 4 | 4 |
| `value` | 8 | 8 |
| `mark` | 16 | 1 |
| Tail padding | 17–23 | 7 |

따라서 Structure 크기는 24 bytes다.

$$
\text{Array 크기}=3\times24=72\text{ bytes}
$$

$$
\text{index 1의 value Offset}=1\times24+8=32\text{ bytes}
$$

순서를 바꾸면 `value`, `count`, `tag`, `mark`의 Offset은 각각 0, 8, 12, 13이다. 사용한 마지막 byte 다음 위치는 14이므로 Tail padding 2 bytes를 더해 전체 크기는 16이 된다.

이 계산은 Array 시작점을 기준으로 한 숫자 Offset 계산이다. 임의의 서로 다른 C Object 사이 Pointer 뺄셈이 언제나 허용된다는 예제가 아니다.

**채점 포인트:** Member Alignment와 끝 Alignment를 모두 적용했는가, Element 크기를 확정한 뒤 Array 위치를 계산했는가.

</details>

2. **호출 B 한 번을 나타내는** 다음 Assembly에서 `%rdi`가 `x`의 주소, `%esi`가 3을 담는다고 할 때 각 단계의 변화를 설명하라.

```asm
mov  (%rdi), %eax
add  %eax, %eax
mov  %eax, (%rdi)
add  %esi, %eax
ret
```

3. 별도의 4-element `int` Array에서 `a[3] = 9`를 수행한다. `int`가 4 bytes라면 시작 주소로부터 몇 bytes 떨어진 곳에 쓰는가?

<details><summary>풀이와 채점 포인트</summary>

호출 A는 복사본을 14로 바꾸고 17을 반환하지만 Caller의 `x`는 7이다. 호출 B도 17을 반환하나 Caller의 `x`는 14가 된다.

Array index 3의 byte Offset은 다음과 같다.

$$
3\times4=12\text{ bytes}
$$

이에 해당하는 형태는 `movl $9, 12(%rdi)`이며, 12번째 Element를 고르는 것이 아니다.

`argv[1]`은 문자열 `"red"`의 시작을 가리키는 Pointer이고, 그 첫 문자는 `'r'`이다. 세 Pointer와 각 Pointer가 가리키는 문자열을 별도로 그리면 된다.

5. Outer match는 여러 시작 위치를 시도하고, submatch는 한 시작점에서 일치를 검사한다. `*`의 0회 반복을 먼저 고려하는 것은 앞 요소를 소비하지 않고 나머지를 맞출 가능성이 있기 때문이다. 제공 코드는 일부 처리가 비어 있는 `*` 중심 Hint이므로 다른 연산자나 모든 경계 조건까지 완성되었다고 볼 수 없다.

오류 채점은 README의 Invalid pattern 한정 문구와 배점표의 `Error and overflow handling` 사이에 표현 차이가 있다. 이 문제의 문법 판정으로 그 배점 대응까지 확정하지 않는다.

**채점 포인트:** `*`를 임의 문자열 Wildcard로 바꾸지 않았는가, Partial matching과 대소문자를 적용했는가, 문법 오류·지원 제외·미완성 Hint를 구별했는가.

</details>

<details><summary>풀이와 채점 포인트</summary>

1. README는 먼저 흐름을 설계하도록 권한다. `main`은 여러 Root와 Header·Summary·Aggregate를 관리하고, `process_dir`는 한 Directory의 Entry 처리와 재귀 방문·닫기를 담당한다. 보조 기능도 `print_formats`, `struct summary`, `get_next`, `dirent_compare`, `syntax`처럼 역할을 구별한다.

3. 제시한 단순 모델에서 배열만의 동시 사용량은 다음과 같다.

$$
12\times64=768\text{ KiB}
$$

다른 호출 정보까지 고려하면 전체 Stack 사용량은 이보다 더 필요할 수 있다. 실제 Stack 한도가 주어지지 않았으므로 이 숫자만으로 반드시 overflow한다고 단정하지는 않는다.

**채점 포인트:** 함수별 책임을 설명했는가, Entry 수와 재귀 깊이를 모두 고려했는가, API 이름을 목적·자원 해제 책임과 연결했는가. 완성된 traversal이나 matcher 구현을 제시하는 문제는 아니다.

</details>
