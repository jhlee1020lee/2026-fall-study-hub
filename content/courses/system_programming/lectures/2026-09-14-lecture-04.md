이번 강의는 Unix filesystem(유닉스 파일시스템)의 이름·속성·권한을 연결하고, Unix I/O(유닉스 입출력)로 파일을 열고 사용하는 과정을 다룬다.  
파일 이름, Inode, 실행 권한의 주체, File descriptor를 구분하면서 자료의 예시를 다시 설명하고 새로운 조건에 적용하는 것이 목표다.

## 강의 내용과 설명

### Unix filesystem(유닉스 파일시스템)과 Mount point(마운트 지점)

여러 저장 장치를 사용하더라도 하나의 경로 체계로 파일에 접근할 수 있다는 것이 Unix filesystem의 출발점이다. **Root(루트)**인 `/` 아래에 **Directory(디렉터리)**를 배치하고, 다른 filesystem을 특정 Directory에 연결한다. 이 연결을 **Mount(마운트)**라고 하며, 연결 지점인 Directory가 Mount point다. 강의는 이를 Windows의 drive 구분과 대비했다. 여기서 하나의 Root를 사용한다는 말은 모든 데이터가 하나의 물리 장치에 저장된다는 뜻이 아니다. 서로 다른 filesystem이 하나의 Directory tree 안에 나타난다는 뜻이다. [STT 02:34] [STT 03:32] [M01 p.11]

강의의 `extern` 예시는 Mount가 기존 파일을 어떻게 보이게 하는지 설명한다.

1. `mkdir extern`으로 Directory를 만든다.
2. `echo "hello" > extern/hello`로 그 안에 파일을 만든다. 이 예시의 출력에는 `hello` 뒤의 줄바꿈이 포함되므로 6 bytes다.
3. `extern`에 `tmpfs`를 Mount한다.
4. 같은 `extern`을 조회해도 이제 새로 연결된 filesystem의 내용이 보인다.
5. 그 안에 `extern`이라는 파일을 만든다.
6. `umount extern`으로 연결을 해제하면 원래의 `hello`가 다시 보인다. [STT 04:42] [STT 05:42] [STT 09:21] [M01 p.11]

**M01 p.12의 그림에서 읽어야 할 것은 Directory 이름과 그 이름을 통해 도달하는 filesystem의 차이**다. `share`에서 나가는 화살표는 host의 `vboxsf`로 이어지고, Mount 이후 `extern`에서 나가는 화살표는 `tmpfs`로 이어진다. 원래 `extern` 아래의 `hello`는 흐리게 표시되어 있다. 이는 파일의 삭제가 아니라 Mount에 의한 가림을 나타낸다. 그림에 표시된 `/dev/shm`을 기존 Directory의 bind mount 명령으로 바꾸어 해석해서는 안 된다. [M01 p.12] ([M01 원본 PPTX](https://jhlee1020lee.github.io/2026-fall-study-hub/materials/system_programming/03.IO.Unix.Filesystem.Concepts.pptx))

`ls -1`의 마지막 글자는 소문자 `l`이 아니라 숫자 `1`이며, 이름을 한 줄에 하나씩 보여 주는 옵션이다. 이 출력 형식은 Mount 원리와 별개의 문제지만, 예시의 명령을 정확히 읽는 데 필요하다. [STT 03:48] [STT 04:42]

강사는 `tmpfs`를 설명하면서 임시 파일의 이름 충돌, 여러 process가 데이터를 공유하는 메모리 공간, 재부팅 후 사라지는 메모리 기반 파일을 동기로 들었다. 다만 모든 임시 Directory가 `tmpfs`라는 뜻은 아니며, 언급된 메모리 용량을 모든 시스템의 고정값으로 외우면 안 된다. 임시 파일을 만드는 API의 이름과 일부 메모리 관련 발화는 **검증 필요**다. 이 부분은 자료로 확인되는 Mount 동작과 구분하여 남긴다. [STT 06:55] [STT 07:53] [STT 08:32]

개념 연결: [[concepts/unix-filesystem|Unix filesystem]] · [[concepts/mount-point|Mount point]]

### Mount option과 Access time(접근 시간)의 비용

Mount는 Directory를 연결하는 것뿐 아니라 그 filesystem에서 허용할 동작을 정하는 수단이기도 하다. 강의의 Mount·Unmount 예시는 `sudo`를 사용하며, 해당 작업에 필요한 Root privilege(관리자 권한)를 전제로 한다. 인자 없이 `mount`를 실행한 출력에서는 연결된 filesystem과 그 속성을 확인한다. [STT 11:28] [STT 15:27] [M01 p.13]

| Mount option | 자료에서 설명하는 의미 | 구분해야 할 점 |
|---|---|---|
| `ro` | Read-only(읽기 전용)로 사용 | 읽기가 가능하다는 사실과 쓰기가 가능하다는 사실은 다르다. |
| `noatime` | Access time인 `atime` 갱신 억제 | 읽기 자체의 허용 여부를 바꾸는 옵션은 아니다. |
| `relatime` | 시간 관계에 따라 `atime` 갱신을 제한 | 슬라이드의 조건은 설명용 요약이다. |
| `noexec` | 프로그램 실행 제한 | Directory를 통과하는 `x` permission과 구분한다. |
| `nosuid` | Set user/group ID 효과 제한 | 개별 파일의 special bit와 filesystem의 정책을 함께 봐야 한다. |
| `nodev` | Device file(장치 파일)의 기능 제한 | 파일 이름이 보인다는 것과 장치로 작동한다는 것은 다르다. |
| `size` | 예시 filesystem의 최대 크기 제한 | 모든 filesystem에 공통인 용량 보장은 아니다. |
| `iocharset` | 파일 이름의 문자셋 설정 | 파일 내용 전체의 문자 인코딩을 일괄 지정한다는 뜻은 아니다. |

표의 근거는 M01 p.13이다. 특히 `relatime`은 `atime`과 `mtime`·`ctime`의 비교로 요약되어 있으므로, 그 한 줄을 전체 정책 명세로 취급하지 않는다. [M01 p.13]

강사가 `atime`을 설명한 동기는 **읽기에도 추가적인 상태 갱신 비용이 생길 수 있다**는 점이다. 파일 내용을 읽은 뒤 접근 시각까지 저장하려면 내용 읽기 외의 작업이 필요하다. 그래서 접근 시각이 중요하지 않은 환경에서는 갱신을 줄이는 정책을 사용할 수 있다. 다만 모든 `read`가 언제나 `atime`을 갱신한다고 일반화해서는 안 된다. 실제 갱신 여부를 설명할 때에는 Mount option을 함께 확인해야 한다. [STT 12:32]

이해를 위한 예시로, 어떤 파일이 Read-only filesystem에 있다면 파일 자체의 쓰기 permission만 보고 수정 가능하다고 판단할 수 없다. 개별 파일의 속성과 그 파일이 속한 filesystem의 정책은 서로 다른 층에서 제약을 건다. 이 구분은 뒤의 `noexec`·`nosuid` 검사에도 이어진다. [M01 p.13] [M01 p.32] [M01 p.33]

### `ls -l`로 읽는 Metadata(메타데이터)와 세 가지 시간

Metadata는 파일의 내용 자체와 구분되는 속성 정보다. `ls -l`은 이를 사람이 읽기 좋은 열로 보여 준다. M01 p.14의 표에서는 왼쪽부터 File type(파일 종류)과 Permission(접근 권한), Hard link count(하드 링크 수), Owner(소유자), Group(그룹), byte 단위 크기, 수정 시각, 파일 이름을 읽는다. 맨 왼쪽의 type 문자는 뒤의 아홉 permission 자리와 역할이 다르다. [STT 16:15] [M01 p.14]

Group은 여러 사용자가 협업 파일에 접근하는 동기로 소개되었다. 파일의 Owner에게 주는 권한과 Group에 주는 권한을 따로 정하면, Group 구성원이 공통 자료를 읽거나 수정하게 할 수 있다. **Other(그 밖의 사용자)**는 해당 Owner·Group 구분 밖의 대상을 나타낸다. [STT 17:13] [STT 18:10]

시간 정보는 다음처럼 구분한다.

| 시간 | 의미 | 해석상 주의점 |
|---|---|---|
| `atime` | Access time | 갱신 정책에 Mount option이 관여한다. |
| `mtime` | Modification time(내용 수정 시간) | 파일 내용이 수정된 시각과 관련된다. |
| `ctime` | Change time(상태 변경 시간) | Metadata·상태 변경과 관련되며 Creation time이 아니다. |

강의에서 `ctime`을 Metadata 변경과 연결한 설명은 바로 뒤의 내용 쓰기 예시와 함께 읽어야 한다. 파일에 데이터를 추가하면 내용뿐 아니라 크기 같은 Metadata도 바뀔 수 있으므로 `mtime`과 `ctime`이 함께 갱신될 수 있다. 따라서 “내용을 바꾸면 `mtime`만 바뀐다”거나 “`ctime`은 파일 생성 시각이다”라는 해석은 부정확하다. [STT 16:15] [STT 17:13]

`ls -l`의 크기 열도 파일 종류에 따라 읽어야 한다. 뒤에서 볼 Symbolic link의 크기는 대상 파일 내용의 크기와 같지 않다. 열의 위치를 외우는 데서 멈추지 말고, **어느 객체의 어떤 속성을 표시하고 있는지**를 확인해야 한다. [M01 p.14] [M01 p.15]

### Hard link(하드 링크)와 Symbolic link(심볼릭 링크)

두 link는 서로 다른 이름으로 같은 대상에 접근하려는 **Aliasing(별칭 부여)** 목적을 공유하지만, 연결을 표현하는 방식은 다르다. **Inode(아이노드)**는 파일의 Metadata 등을 담는 구조이며, 파일 이름은 Directory entry(디렉터리 항목)를 통해 해당 Inode와 연결된다. Hard link는 동일한 Inode를 가리키는 또 다른 이름이다. 파일 내용을 복사하여 별도 객체를 만드는 작업이 아니다. [STT 19:10] [STT 19:19] [STT 20:16] [M01 p.15]

반면 Symbolic link는 **Soft link(소프트 링크)**라고도 부르며, 자신만의 Inode를 가진 별도 파일에 Target pathname(대상 경로명)을 담는다. 일반적인 파일 열기에서는 이 pathname을 따라 Target에 접근한다. Link 자체를 다루거나 따라가기를 제한하는 API 동작도 언급되었으므로, 모든 API가 언제나 같은 방식으로 따라간다고 일반화하지 않는다. [STT 21:10] [STT 22:03]

| 비교 항목 | Hard link | Symbolic link |
|---|---|---|
| 생성 명령 | `ln` | `ln -s` |
| 연결 구조 | 같은 Inode를 공유 | 별도 Inode에 Target pathname 저장 |
| 파일 내용·Metadata | 동일한 파일의 내용·Metadata를 봄 | Link 자체와 Target의 속성을 구분해야 함 |
| Filesystem 경계 | 강의의 일반 모델에서는 넘을 수 없음 | Pathname으로 다른 filesystem의 Target을 표현 가능 |
| Directory 연결 | 일반적인 임의 Hard link 생성은 제한 | Directory를 Target으로 지정 가능 |
| Target 이름 삭제 | 남은 Hard link로 같은 파일에 접근 가능 | Target이 사라진 Broken link가 남을 수 있음 |

[M01 p.15]

M01 p.15의 출력에서는 `hello.txt`와 `helloworld.txt`가 같은 크기를 보이고 Hard link count가 함께 2가 된다. `testing`은 맨 왼쪽 type이 `l`이며, `testing -> test.txt`처럼 Target이 표시된다. 여기서 `testing`의 크기는 Target의 내용 크기가 아니라 Link가 저장하는 pathname과 관련된다. [M01 p.15]

기출에서는 이 차이를 단순한 명칭 비교보다 **참조 구조의 차이**로 설명하도록 요구한다. 2024년 2학기 표기의 중간고사 Q3(a)는 두 link의 연결 방식을 비교하고, 2025년 2학기 표기의 Q3(a)는 왜 Target Inode의 Hard link count와 Symbolic link를 같은 방식으로 세지 않는지 묻는다. 풀이의 출발점은 “이름이 하나 추가되었다”가 아니라 “같은 Inode를 참조했는가, 별도 파일에 pathname을 기록했는가”다. 두 문항은 현재 범위에서 접근할 수 있다. 과목·담당교수 정보 중 파일명에 의존하는 항목은 독립 확인되지 않았으므로, 현재 강사의 출제 성향 근거로 사용하지 않는다. [EX:sp_2024_2_midterm_q03 p.6] [EX:sp_2025_2_midterm_q03 p.7]

### Link를 통한 수정과 삭제: 같은 내용이 보이는 이유

강사는 Link의 사용 동기로 저장 공간 비용과 많은 Dataset 파일을 다른 Directory에서 이용하는 상황을 들었다. 약 3,000개 파일을 별도 위치에서도 같은 이름으로 사용하려면, 내용을 모두 복제하는 대신 Alias를 구성할 수 있다는 설명이다. Symbolic link의 pathname 추적에는 추가 작업이 있지만, 이 언급을 측정된 성능 수치나 모든 상황에서의 Hard link 우위로 바꾸어서는 안 된다. Directory 연결이나 filesystem 경계처럼 표현하려는 관계도 선택에 영향을 준다. [STT 24:31] [STT 25:15]

M01 p.16에서는 `helloworld.txt`를 통해 내용을 덧붙인 뒤 `hello.txt`와 `helloworld.txt`를 각각 읽는다. 두 이름은 같은 Inode를 가리키므로 같은 수정 결과가 보인다. **두 복사본이 자동으로 동기화된 것이 아니라, 애초에 같은 파일을 두 이름으로 보고 있는 것**이다. [STT 26:13] [M01 p.16]

M01 p.17에서는 `testing`을 통해 내용을 덧붙인다. 일반적인 접근이 Symbolic link의 pathname을 따라가기 때문에 Target인 `test.txt`의 내용이 바뀐다. 이후 두 이름으로 읽으면 같은 Target 내용이 보이지만, `testing` 자체가 보관하는 pathname과 그 크기는 Target 내용과 별개다. [STT 27:10] [M01 p.17]

삭제 이후의 차이는 더 분명하다.

| 자료의 동작 | 남는 객체 | 이후 접근 |
|---|---|---|
| `hello.txt` 삭제 | 같은 Inode를 참조하는 `helloworld.txt` | 남은 이름으로 내용 읽기 가능 |
| `test.txt` 삭제 | Target pathname을 담은 `testing` | Link는 남지만 Target을 여는 작업은 실패 |

[M01 p.18]

첫 경우에는 남은 Hard link의 count가 1로 줄어든다. 둘째 경우에는 **Broken link(대상이 끊어진 링크)**가 된다. Symbolic link의 존재는 Target의 존재를 보장하지 않는다는 뜻이다. 또한 Hard link count는 이름에 의한 참조를 설명하는 값이므로, 마지막 이름 삭제에 관한 설명을 열린 모든 handle의 수명까지 설명한 것으로 확대하지 않는다. [STT 27:31] [M01 p.18]

자료의 수정 후 출력에는 크기가 14와 22로 표시되어 있다. 이는 슬라이드에 실린 값이며, 제시된 `printf` 표기의 byte 계산을 새로 실행해 확인한 결과로 취급하지 않는다. 본문에서는 같은 Inode의 크기가 함께 보인다는 관계와 Link 자체의 크기가 다르다는 관계를 학습한다. [M01 p.16] [M01 p.17]

### File type과 Hidden file(숨김 파일), Directory 자체의 조회

파일 이름이나 확장자만으로 Unix의 File type을 판정하지 않는다. `ls -l`의 첫 글자는 다음과 같은 종류를 구분한다. 이 표는 이번 회차에서 다시 확인한 종류 목록이며, 각 장치나 통신 방식의 내부 동작을 모두 학습했다는 뜻은 아니다. [STT 27:31] [STT 28:26] [M01 p.19]

| 첫 글자 | File type |
|---|---|
| `-` | Regular file(일반 파일) |
| `d` | Directory |
| `l` | Symbolic link |
| `p` | Named pipe(이름 있는 파이프), FIFO |
| `s` | Socket(소켓) |
| `c` | Character device file(문자 장치 파일) |
| `b` | Block device file(블록 장치 파일) |

Unix에서 이름이 `.`으로 시작하는 항목은 일반적인 목록에서 숨겨진다. `ls -la`의 `-a`는 이 항목들도 포함하여 보여 준다. Hidden file은 표시 관례이지 접근 보호 장치가 아니다. 이름 앞에 점을 붙였다는 이유만으로 다른 사용자의 접근이 차단되지는 않는다. [M01 p.20] [M01 p.27]

특별한 Directory entry인 `.`은 현재 Directory를, `..`은 Parent directory(부모 디렉터리)를 가리킨다. `cd ..`가 부모로 이동하는 명령인 이유도 이 의미와 연결된다. [M01 p.20]

`ls -l sample`과 `ls -ld sample`은 관찰 대상부터 다르다. 전자는 `sample` 내부의 항목들을 나열하고, 후자는 `sample`이라는 Directory 자체의 Metadata를 보여 준다. 따라서 Directory 자체의 Permission이나 Hard link count를 확인하려면 `-d`가 필요한 상황을 구분해야 한다. [STT 28:26] [M01 p.21]

### Directory의 Hard link count와 `2 + N` 모델

M01 p.21의 예시에서 `sample`의 Hard link count는 4이고, 그 안의 `dir1`과 `dir2`는 각각 2다. 핵심은 Directory 내부의 일반 파일 개수를 세는 것이 아니라, **어떤 Directory entry가 해당 Directory를 가리키는지** 추적하는 것이다. [STT 29:25] [M01 p.21]

강의가 사용하는 전통적인 Directory 모델에서는 다음 참조를 센다.

- 부모 안에서 해당 Directory를 가리키는 이름 entry가 하나 있다.
- Directory 자신의 `.`이 자신을 가리킨다.
- 직속 Subdirectory(하위 디렉터리)마다 그 안의 `..`이 부모인 이 Directory를 가리킨다.

따라서 직속 Subdirectory가 $N$개라면 이 모델의 Hard link count는 다음과 같다.

$$
L = 1 + 1 + N = 2 + N
$$

`sample`에는 `dir1`과 `dir2`가 있으므로 $L=2+2=4$다. 더 내려가는 Subdirectory가 없는 `dir1`과 `dir2`는 각각 기본 두 참조를 가진다. 이것이 슬라이드의 숫자 4와 2를 설명하는 과정이다. [STT 30:24] [STT 31:21] [M01 p.21]

이해를 위한 예시로, 같은 모델에서 직속 Subdirectory가 4개인 Directory의 count는 6이다. 그 안에 일반 파일을 하나 더 만든다고 해서 그 파일이 부모 Directory의 Inode를 참조하는 것은 아니므로, 이를 단순히 7로 계산하지 않는다. 또한 직속 Subdirectory와 그 아래의 더 먼 후손을 모두 합산해서도 안 된다.

2025년 2학기 표기의 중간고사 Q3(b)는 주어진 Directory 구조에서 같은 참조 계산을 요구한다. 풀이에서는 기본 두 참조와 각 Subdirectory의 `..`을 개별적으로 설명해야 한다. 이 연결은 현재 접근 가능하지만, `2+N`을 모든 filesystem 구현에서 반드시 관찰되는 수치라고 일반화하지 않는다. [EX:sp_2025_2_midterm_q03 p.7]

특수 entry인 `.`·`..`의 존재는 사용자가 Directory에 임의의 Hard link를 만들어도 된다는 의미가 아니다. 앞서 배운 일반적인 Directory Hard link 제한과 함께 이해해야 한다. [M01 p.15] [M01 p.21]

### Filesystem Hierarchy Standard(파일시스템 계층 표준, FHS)

Root 아래에 많은 Directory가 있어도 용도를 찾을 수 있도록 배치 관례를 제공하는 것이 FHS다. 강사는 전체 목록을 암기하기보다 주요 위치를 살펴보라고 안내했다. 따라서 목표는 경로 문자열을 전부 외우는 것이 아니라, 프로그램·설정·장치·변동 데이터가 어디에 놓이는지 구분하는 것이다. [STT 31:21] [STT 32:26] [M01 p.22] [M01 p.23]

| Directory | 제공 자료의 역할 설명 |
|---|---|
| `/` | 전체 계층의 Root |
| `/bin`, `/sbin` | 부팅 또는 시스템 운영에 필요한 주요 실행 파일 |
| `/boot` | Boot loader와 Kernel |
| `/dev` | 장치를 나타내는 파일 |
| `/etc` | 시스템 전체 설정 |
| `/home` | 사용자 Home directory |
| `/root` | 관리자 계정의 Home directory |
| `/lib`, `/lib64` | 주요 실행 파일이 사용하는 System library |
| `/media`, `/mnt` | 저장 매체 등을 연결하는 Mount point |
| `/opt` | 추가 응용 소프트웨어 |
| `/proc` | Process·Kernel 정보를 제공하는 Virtual filesystem |
| `/sys` | Device driver·Kernel 정보와 설정 |
| `/run` | 실행 중 변하는 데이터 |
| `/tmp`, `/var/tmp` | 임시 파일 |
| `/usr` | 프로그램·공유 데이터 등을 배치하는 추가 계층 |
| `/var` | 실행에 따라 변하는 파일 |

[M01 p.23] [M01 p.24]

**M01 p.23~25의 표는 경로를 용도와 대응시키는 방식으로 읽는다.** 예를 들어 C Header(헤더)인 `stdio.h`를 찾는 동기는 `/usr/include` 행과 연결되고, 명령어가 검색되는 위치를 이해하는 동기는 `/usr/bin`과 `PATH` 설명으로 이어진다. `/usr`를 개별 사용자의 Home directory와 혼동하면 이 배치를 이해하기 어렵다. [STT 33:26] [M01 p.25]

`/usr` 아래에서는 `bin`·`sbin`이 실행 파일, `include`가 C Header, `lib`·`lib64`가 Library를 담는다. `libexec`는 다른 프로그램이나 script를 통해 실행되는 보조 파일, `local`은 해당 시스템에 특화된 자료, `share`는 응용 프로그램의 공유 데이터, `src`는 Source code를 위한 위치로 제시된다. [M01 p.25]

`/var`의 표는 데이터가 **왜 변하는지**에 따라 읽을 수 있다. `cache`는 응용 프로그램의 Cache data, `lib`는 Persistent state data(유지되는 상태 데이터), `lock`은 사용 중인 자원을 추적하는 Lock file(잠금 파일), `log`는 System log(시스템 기록), `mail`은 서버의 Mailbox file(메일함 파일), `spool`은 처리 대기 작업을 위한 위치다. `/var/db`는 Gentoo 배포판의 Portage가 사용하는 Configuration file(설정 파일)·Source file(소스 파일)의 위치로 제시된다. `/var/run`은 Runtime variable data(실행 중 변하는 데이터)를 위한 위치이며, 자료의 FHS 3.0 주석은 이를 `/run`에 매핑한다고 설명한다. `/var/tmp`는 Temporary file(임시 파일)의 위치다. 배포판·FHS 주석이 포함된 자료 당시의 표이므로 모든 시스템의 동일한 실제 배치로 단정하지 않는다. [M01 p.26]

이번 회차에서 특히 설명된 `/proc`는 고정된 디스크 파일의 모음으로만 이해하면 안 된다. 파일처럼 열고 읽는 인터페이스를 통해 실행 중인 Process·Kernel 정보를 얻는다는 점이 중요하다. 파일 인터페이스를 사용한다고 해서 그 내용이 반드시 저장 장치의 고정된 byte에서 오는 것은 아니다. [STT 32:26] [STT 33:26] [M01 p.24]

Home directory는 User-specific files(사용자별 파일)를 두는 곳이다. M01 p.27은 `~`를 `/home/<USER>`의 축약으로 표시한다. `<USER>`는 예시 사용자 이름을 넣는 자리이며, 이 배치를 모든 계정의 고정 Home 경로로 일반화하지 않는다.

자료의 Home 표에서 `.cache`는 User cached data(사용자 캐시 데이터), `.config`는 User-specific configuration(사용자별 설정), `.local`은 User local data(사용자 로컬 데이터)를 위한 위치이며 `bin`·`lib`·`share`를 예로 든다. `ls ~/.config`는 사용자 설정 Directory의 내부 항목을 조회하는 예시다. `.mozilla`, `.ssh`, `.vim`은 각각 Mozilla·SSH·Vim의 Application-specific configuration(응용 프로그램별 설정) 예시이며, Home에는 사용자가 직접 만든 Directory와 파일도 놓인다. [M01 p.27]

강사는 `.ssh`를 로그인 설정과 SSH key의 예로 언급했다. Hidden name이라는 성질과 보안상 적절한 Permission을 갖추는 일은 별개다. FHS의 버전·날짜와 세부 배치는 제공 슬라이드 당시의 설명으로 취급한다. [STT 34:33] [M01 p.27]

개념 연결: [[concepts/filesystem-hierarchy-standard|Filesystem Hierarchy Standard]]

### Permission의 `rwx`: File과 Directory에서 달라지는 의미

Permission의 기본 구조는 Owner·Group·Other라는 세 대상에 Read(읽기), Write(쓰기), Execute(실행)를 배정하는 것이다. `ls -l`의 아홉 자리는 `rwx` 세 묶음이며, 그 앞의 한 글자는 File type이다. [STT 35:27] [M01 p.29]

**M01 p.29의 색상 도식은 가로와 세로를 함께 읽어야 한다.** 가로로는 첫 세 자리가 Owner, 다음 세 자리가 Group, 마지막 세 자리가 Other에 대응한다. 각 묶음 내부에서는 `r`, `w`, `x`가 각각의 동작을 나타낸다. 앞의 `d`까지 묶어서 네 자리 permission으로 해석하면 안 된다. [M01 p.29]

Regular file과 Directory는 같은 글자를 사용해도 제어하는 동작이 다르다.

| Permission | Regular file | Directory |
|---|---|---|
| `r` | 파일 내용을 읽기 | 내부 이름 목록을 읽기 |
| `w` | 파일 내용을 수정하기 | Entry를 추가·삭제하는 등 목록을 변경하기 |
| `x` | 프로그램으로 실행하기 | Directory에 진입하거나 경로를 통과하기 |

[STT 36:28] [STT 37:34] [M01 p.29]

Directory에서 `x`와 `r`은 같은 권한이 아니다. 강의 중 처음에는 진입 조건이 혼동되게 들리는 대목이 있지만, 이어서 `x`로 진입할 수 있어도 `r`이 없으면 목록을 볼 수 없다는 구분을 설명한다. 따라서 “목록을 볼 수 없음”과 “경로를 통과할 수 없음”을 같은 실패로 처리하지 않는다. [STT 36:28]

또한 Directory의 `w`는 내부 파일의 내용 수정 권한을 한꺼번에 부여한다는 뜻이 아니다. Directory 자체의 내용이 이름 entry들의 목록이라는 점에서 생성·삭제와 연결된다. 실제 작업에는 경로 통과와 다른 제약도 관여하므로, `w` 하나만 있으면 모든 변경이 가능하다고 확대하지 않는다. [STT 37:26] [STT 37:34]

이해를 위한 예시로, 파일 내용을 읽을 권한이 있다는 사실만으로 그 파일의 이름을 마음대로 삭제할 수 있다고 결론내릴 수 없다. 내용 접근과 Directory entry 변경은 관찰해야 하는 객체가 다르며, 뒤에서 다룰 Sticky bit도 후자의 제한과 연결된다. [M01 p.29] [M01 p.31]

### `chmod`의 Symbolic mode와 Octal mode

`chmod`는 파일의 Permission을 변경한다. **Symbolic mode(기호 방식)**에서는 `u`, `g`, `o`로 대상을 지정하고 `+`와 `-`로 권한을 추가하거나 제거한다. 강의의 `chmod g+w test.txt`는 기존 설정 전체를 새로 쓰는 대신 Group의 Write permission을 추가한다. [STT 38:22] [M01 p.30]

**Octal mode(8진수 방식)**는 `rwx`의 세 bit를 한 자리로 표현한다. 각 자리를 Read·Write·Execute 순서로 읽으면 다음과 같다.

$$
r=4,\qquad w=2,\qquad x=1
$$

따라서 `chmod 750 script.sh`의 세 자리는 다음 권한을 뜻한다.

| 대상 | Octal | 세 bit | Permission |
|---|---:|---|---|
| Owner | 7 | `111` | `rwx` |
| Group | 5 | `101` | `r-x` |
| Other | 0 | `000` | `---` |

[STT 39:17] [STT 40:17]

강의의 script 예시는 내용에 `ls -l`이 들어 있어도 Execute permission이 없으면 직접 실행이 거부된다는 점을 보여 준다. 프로그램의 내용이 실행 가능한 명령처럼 보인다는 사실과 파일에 실행 권한이 있다는 사실은 별개다. [M01 p.30]

**자료 교정:** M01 p.30에서 `chmod 750`의 대상은 `script.sh`인데 마지막 출력의 파일 이름은 `test.txt`로 표시된다. 이 불일치는 원본의 한계로 남긴다. `750`의 bit 해석은 설명할 수 있지만, 마지막 출력 전체를 동일 파일에 대한 검증된 실행 기록으로 다시 만들지는 않는다. 세부 옵션을 확인할 때에는 강의에서 안내한 `man 1 chmod`를 참조하는 방식이 적절하다. [STT 41:03] [M01 p.30]

개념 연결: [[concepts/file-permissions|File permissions]] · [[concepts/chmod|chmod]]

### Sticky bit(스티키 비트)와 `stat`의 Mode 정보

여러 사용자가 파일을 만드는 공유 Directory에서는 일반적인 Write permission만으로 충분하지 않은 문제가 생긴다. 각 사용자가 임시 파일을 만들 수 있어야 하더라도 다른 사용자의 파일 이름까지 자유롭게 바꾸거나 삭제하게 하고 싶지는 않다. Sticky bit는 이 상황에서 Directory 내부 파일의 이름 변경·삭제 주체를 추가로 제한한다. [STT 41:49] [M01 p.31]

자료는 Sticky bit가 설정된 Directory에서 해당 파일을 이름 변경하거나 삭제할 수 있는 주체를 다음과 같이 설명한다.

- 파일의 Owner
- Directory의 Owner
- Privileged user/process(특권 사용자·프로세스)

이는 그 동작에 대한 추가 제한이다. Sticky bit 하나가 필요한 모든 Permission을 대신 부여하거나 파일 내용의 Read·Write를 직접 보호하는 것은 아니다. [STT 42:41] [M01 p.31]

M01 p.31의 목록에서는 마지막 위치의 `t`로 Sticky bit를 확인한다. 프로그램에서 조회하는 `struct stat`에는 `S_ISVTX`로 연결되는 Mode 정보가 있다. 강사는 `S_IRWXU`, `S_IRWXG` 같은 Macro(매크로)도 소개했고, Owner의 `rwx`를 나타내는 `00700`을 예로 들었다. 숫자를 모두 외우기보다는 필요한 정의를 찾아보라는 취지다. [STT 43:30] [STT 44:33]

`stat` 계열은 Inode와 관련된 정보를 조회하고 결과를 `struct stat`에 담는 문맥에서 등장한다. 시간 정보, Inode 번호, `st_mode` 등을 조회한다는 점이 현재 범위다. 참고 대상으로 `man 2 stat`과 `man 7 inode`가 제시된다. [STT 45:48] [STT 46:21] [M01 p.31]

**검증 필요:** 이 구간에서 열거된 `stat` 변형의 정확한 이름과 Sticky bit의 숫자 발화는 명확하지 않다. 이를 추정하여 강사의 정확한 API 설명으로 복원하지 않는다. 또한 강의 후반 요약에서 Sticky bit를 피하라는 듯이 들리는 표현은 앞의 공유 Directory 보호 설명과 충돌한다. 따라서 Sticky bit 자체가 위험하다는 결론을 내리지 않는다. [STT 43:30] [STT 45:48] [STT 65:32]

### World-writable directory와 `noexec`의 보안 동기

**World-writable directory(모두에게 쓰기가 허용된 디렉터리)**는 여러 사용자가 파일을 놓을 수 있는 공간이다. 여기에서 놓인 프로그램을 실행하는 동작까지 허용되면, 침해된 프로그램이 추가 실행 파일을 배치하는 데 이용할 수 있다는 것이 강의의 보안 동기다. M01 p.32는 침해된 Webserver가 임시 공간에 script를 쓰고 실행하는 상황을 예로 든다. [STT 47:04] [M01 p.32]

프로그램에서 확인하는 두 조건의 층을 구분해야 한다.

- `S_IWOTH`는 파일의 Mode에서 Other의 Write permission을 확인하는 bit다.
- `fstatfs()`와 `ST_NOEXEC`는 filesystem의 실행 제한을 확인하는 예시다. [M01 p.32]

Directory의 `x`는 경로 통과와 관련되고, Mount option인 `noexec`는 실행 정책과 관련된다. 이름이 모두 실행과 연관되어 보이더라도 같은 제어가 아니다. 공유 Directory를 사용할 수 있게 하는 것과 그 filesystem의 실행 정책을 정하는 것을 따로 생각해야 한다. [M01 p.29] [M01 p.32]

강의의 실행 제한 설명을 모든 공격 경로나 우회를 차단한다는 보장으로 읽어서는 안 된다. World-writable 여부나 `ST_NOEXEC` 한 항목만으로 프로그램의 취약성·안전성이 완전히 판정되는 것도 아니다. 여기서 배우는 것은 부적절한 설정을 찾아볼 동기와 Metadata 검사 위치다. [STT 48:00] [M01 p.32]

### SUID·SGID와 Real identity, Effective identity

**SUID(Set user ID, 실행 시 사용자 ID 설정)**와 **SGID(Set group ID, 실행 시 그룹 ID 설정)**는 프로그램 실행 시 권한 주체를 바꾸는 동작과 연결된다. 강의는 사용자가 직접 접근할 수 없는 제출 Directory에 과제를 전달하는 프로그램을 동기로 들었다. 사용자의 일반 권한을 무조건 넓히는 대신, 필요한 작업을 수행하는 프로그램에 한정하여 다른 권한 주체를 사용하려는 것이다. [STT 14:38] [STT 52:22] [M01 p.33]

여기서는 두 identity를 구분한다.

- **Real user/group(실제 사용자·그룹)**: Process를 시작한 원래 주체.
- **Effective user/group(유효 사용자·그룹)**: 실행 중 권한 검사에 사용되는 주체. [M01 p.35]

M01 p.34의 데모에서는 `devel`이 `wai`를 실행한다. 처음에는 Real과 Effective 정보가 모두 일치한다. 이후 파일 소유권을 `tester:users`로 바꾸고 SUID를 켜는 `4755`를 적용한 뒤 다시 실행한다.

| 항목 | 변경 전 | 소유권 변경 후 `4755` 적용 |
|---|---|---|
| Real user | `devel` | `devel` |
| Real group | `devel` | `devel` |
| Effective user | `devel` | `tester` |
| Effective group | `devel` | `devel` |

[M01 p.34]

**이 출력의 핵심은 Effective user만 바뀐다는 점**이다. 파일의 소유 Group을 `users`로 바꾸었다는 사실만으로 실행 Process의 Effective group도 `users`가 되는 것은 아니다. 이 예시는 SUID를 설정했으며 SGID까지 함께 켠 예시가 아니다. [STT 50:37] [STT 51:21]

자료는 `4755`에 SUID, `2755`에 SGID, `6755`에 두 bit를 연결한다. 일반 Permission과 special bit를 나누어 읽고, Metadata에서는 `S_ISUID`·`S_ISGID`, filesystem 정책에서는 `ST_NOSUID`를 확인한다. SUID가 있다는 사실만으로 누구나 실행할 수 있다거나 항상 Root가 된다고 해석해서는 안 된다. 실행 가능 여부에는 다른 조건도 필요하며, 권한 주체는 해당 파일의 Owner와 연결된다. [M01 p.33] [M01 p.34]

2025년 2학기 표기의 중간고사 Q3(e)는 이러한 권한 주체와 높은 권한을 가진 실행 파일의 위험을 설명하도록 요구한다. 현재 배운 범위로는 Real·Effective 구분과 취약한 실행 파일이 높은 권한으로 동작할 때의 위험을 연결할 수 있다. 반면 특정 시스템에서 어떤 프로그램이 실제로 SUID를 사용하는지는 그 시스템의 설정 확인이 필요하다. 제공 답안의 프로그램 목록이나 Root 관련 표현을 모든 Linux 환경의 고정 규칙으로 옮기지 않는다. [EX:sp_2025_2_midterm_q03 p.8]

자료에 있는 모든 신뢰된 Root 소유 실행 파일에 SUID·SGID가 필요하다는 취지의 문구도 보편 규칙으로 채택하지 않는다. [M01 p.33]

개념 연결: [[concepts/suid-sgid|SUID and SGID]] · [[concepts/real-effective-identity|Real and effective identity]]

### `getpwuid`·`getgrgid`와 문자열의 수명

사용자·Group 정보는 숫자 ID와 이름을 구분한다. 예제에서는 `getuid()`, `geteuid()`, `getgid()`, `getegid()`로 ID를 조회한 뒤, 사람이 읽을 이름을 얻기 위해 `getpwuid()`와 `getgrgid()`를 사용한다. 각각 `struct passwd`의 `pw_name`, `struct group`의 `gr_name`을 읽는 흐름이다. [STT 53:17] [M01 p.35]

강사가 강조한 부분은 이름을 얻는 방법 자체보다 **반환 저장소의 재사용**이다. 반환된 구조체는 Static storage(정적 저장소)에 놓일 수 있으며, 같은 API를 다시 호출하면 앞서 얻은 내용이 갱신될 수 있다. 따라서 첫 호출에서 얻은 pointer를 그대로 보관했다고 해서 그 문자열의 내용이 독립적으로 보존되는 것은 아니다. [STT 53:51] [STT 55:01]

예제의 처리 순서는 다음과 같다.

1. Real user의 ID로 이름을 조회한다.
2. `strdup()`로 그 이름을 별도 문자열에 복사한다.
3. Effective user의 ID로 다시 조회한다.
4. 두 이름을 출력한다.
5. 복사하여 소유한 문자열은 사용 후 `free()`한다. [M01 p.35]

Group도 같은 원리로 처리한다. 여기서 해제 대상은 복사 문자열이며, 조회 함수가 돌려준 Static storage를 새로 할당받은 객체처럼 취급하지 않는다.

**자료 코드의 실패 경로에는 한계가 있다.** M01 p.35는 `user`, `euser`, `group`, `egroup`을 초기화하지 않은 채 조회 성공 시에만 값을 대입한다. 조회 실패 시 뒤의 조건식이나 `free()`가 안전하다는 보장은 없다. 초기화되지 않은 pointer 사용은 C의 Undefined behavior(정의되지 않은 동작)로 이어질 수 있으며, `strdup()` 실패도 완전하게 처리하지 않는다. 이는 원본 코드의 한계이지 강의에서 초기화와 실패 처리를 모두 구현했다는 뜻이 아니다. [M01 p.35]

이해를 위한 코드 검토에서는 성공한 호출만 순서대로 읽지 말고, 각 조회가 실패했을 때 변수에 어떤 값이 남는지도 확인해야 한다. 이 관점이 “이름을 복사하는 이유”와 “복사한 메모리를 안전하게 관리하는 조건”을 연결한다.

### Directory scan으로 SUID·SGID 설정 살펴보기

M01 p.28은 보안 검사 코드를 미리 보여 주고, p.36에서 전체 흐름을 설명한다. **File descriptor(파일 디스크립터, fd)**는 열린 대상에 후속 작업을 요청할 때 사용하는 식별자다. 이 예제에서는 Directory를 열어 얻은 `DIR *`에서 `dirfd()`로 fd를 가져와 내부 항목의 Metadata를 조회한다. [STT 55:01] [M01 p.28] [M01 p.36]

자료 코드는 다음 순서로 읽는다.

1. `opendir(name)`으로 Directory를 연다.
2. `dirfd(d)`로 Directory의 fd를 얻는다.
3. `getNext(d)`로 entry를 하나씩 가져온다. 이 함수는 자료의 보조 함수이며 구현이 제시되지 않았다.
4. `fstatat()`에 Directory fd, entry 이름, `AT_SYMLINK_NOFOLLOW`를 전달하여 Link를 따라가지 않는 Metadata 조회를 요청한다.
5. `S_ISREG(sb.st_mode)`로 Regular file인지 검사한다.
6. Root 사용자 소유와 SUID, 또는 Root Group 소유와 SGID가 결합되었는지 검사한다.
7. `fstatfs()`로 확인한 filesystem에 `ST_NOEXEC`·`ST_NOSUID`가 모두 없는지 검사한다. [STT 55:56] [STT 56:49] [M01 p.36]

파일의 특권 조건은 다음과 같은 논리 구조다. 아래 식은 원본의 의도를 설명하기 위해 조건을 재배치한 것으로, 전체 scanner 구현이 아니다.

```c
S_ISREG(sb.st_mode) &&
(
    ((sb.st_uid == 0) && (sb.st_mode & S_ISUID)) ||
    ((sb.st_gid == 0) && (sb.st_mode & S_ISGID))
)
```

Filesystem 조건은 다음과 같다.

```c
!(dsb.f_flags & (ST_NOEXEC | ST_NOSUID))
```

두 flag 중 **하나라도** 존재하면 괄호 안의 bitwise AND 결과는 0이 아니므로 바깥의 부정 결과는 거짓이다. 따라서 이 조건은 두 제한이 모두 없을 때만 참이다. 두 flag 중 하나가 없으면 충분하다고 읽으면 논리가 달라진다. [M01 p.36]

강의의 위험 시나리오는 높은 권한으로 실행되는 프로그램에 Buffer overflow(버퍼 오버플로) 같은 취약성이 있으면 권한 문제가 커질 수 있다는 것이다. 검사 결과가 그 취약성의 존재 자체를 증명하는 것은 아니다. [STT 57:37]

원본은 오류 처리를 생략했다고 명시하며, 불완전한 괄호와 생략부도 포함한다. `getNext()`의 구현을 임의로 복원해서는 안 된다. Directory fd로 조회한 filesystem 정책만으로 각 entry의 실제 Mount 관계, 실행 가능성, 취약성을 모두 판정할 수도 없다. 이 코드는 **검사하려는 속성들의 조합을 배우는 예시**로 읽는다. [M01 p.36]

### Extended file attributes(확장 파일 속성, xattrs)

Owner·Group·Other만으로 권한을 정하면 특정 사용자 한 명에게만 별도의 접근을 주려는 요구를 표현하기 어렵다. 강사는 Group에 속하지 않은 사용자에게만 Read permission을 주고 싶은 상황에서 확장 기능으로 넘어갔다. [STT 58:36]

xattrs는 파일에 추가 Metadata를 저장하는 확장 방식이며, **Key/value pair(키·값 쌍)**를 사용한다. Key의 형태는 `namespace.attribute`다. 자료는 **Access Control List(접근 제어 목록, ACL)**도 이러한 확장 Metadata와 연결하여 설명한다. [STT 59:33] [M01 p.37]

| Namespace(이름 공간) | 자료의 설명 |
|---|---|
| `security` | SELinux 같은 Kernel module이 보안 기능에 사용 |
| `system` | Kernel이 시스템 객체를 저장하는 데 사용 |
| `trusted` | `CAP_SYS_ADMIN` capability를 가진 Process에 제한 |
| `user` | MIME type, MD5 값, 문자 인코딩 등 추가 정보 저장 |

[STT 60:11] [M01 p.37]

`user` Namespace의 예시는 xattrs가 접근 권한만을 위한 기능은 아니라는 점을 보여 준다. 파일의 내용은 그대로 두고, 그 파일을 설명하는 별도의 Metadata를 붙일 수 있다.

**자료 표현의 한계:** M01 p.37에서 POSIX ACL이 사용자·Group·Other에만 제한된다는 식의 문장은 전통적인 Mode bit의 한계와 확장 ACL을 구분해서 읽어야 한다. 바로 다음 자료가 특정 사용자를 지정하는 ACL을 보여 주기 때문이다. 또한 슬라이드에서 값을 문자열로 설명했다고 해서 모든 확장 Metadata를 text-only로 제한하는 일반 규칙을 만들지 않는다. [M01 p.37] [M01 p.38]

개념 연결: [[concepts/extended-file-attributes|Extended file attributes]] · [[concepts/access-control-list|Access Control List]]

### Extended ACL로 특정 사용자에게 Read permission 추가하기

M01 p.38은 예시 filesystem의 xattrs 지원을 살핀 뒤 ACL을 설정하는 순서다. 슬라이드의 명령과 출력은 다음과 같다.

```console
$ mount | grep "/ "
/dev/sda4 on / type ext4 (rw,noatime)
$ cat /proc/fs/ext4/sda4/options | grep xattr
user_xattr
```

첫 출력에서 `/`에 연결된 장치가 `/dev/sda4`이고 filesystem이 ext4임을 확인한 뒤, 그에 대응하는 `/proc/fs/ext4/sda4/options`에서 `user_xattr`를 찾는다. 이는 자료의 환경에서 확인한 옵션이며, 모든 filesystem에 같은 경로가 존재하거나 이 한 줄이 ACL 지원·유효 권한 전체를 보장한다는 뜻은 아니다. 특정 사용자 항목의 추가 결과는 뒤의 `setfacl`·`getfacl` 예시로 확인한다. [STT 60:54] [STT 61:20] [M01 p.38]

그다음 `file.txt`를 만들고 `chmod 640`을 적용한다. 기본 Permission은 Owner가 `rw-`, Group이 `r--`, Other가 `---`다. 여기에서 특정 사용자에게 Read permission을 추가한다.

```sh
setfacl -m u:svn:r file.txt
getfacl file.txt
```

`svn`은 자료의 예시 계정 표기다. STT에서 불명확하게 들리는 이름을 새로 복원한 것이 아니다. [STT 62:42] [M01 p.38]

M01 p.38의 출력에서 읽어야 할 변화는 두 가지다. `ls -l`에는 Permission 뒤에 `+`가 나타나고, `getfacl`에는 `user:svn:r--`이라는 특정 사용자 항목이 나타난다. 기본 세 범주만 읽는 것으로는 이 추가 권한을 충분히 파악할 수 없다는 뜻이다.

출력에는 `mask::r--`도 있다. 이 행을 지워서 단순화하지는 않지만, 이번 STT에서 Mask의 전체 계산 규칙을 설명했다고 볼 근거는 부족하다. 현재는 추가 사용자 항목과 함께 Mask 행이 존재한다는 점까지 확인한다. [M01 p.38]

이해를 위한 비교로, 특정 사용자를 위해 Other 전체에 Read permission을 주는 것과 Named user 항목을 추가하는 것은 권한을 받는 대상의 범위가 다르다. 강의의 동기는 필요한 사용자에게만 추가 접근을 표현하는 데 있다. [STT 58:36] [M01 p.38]

### `user.checksum.md5`: Metadata 저장과 내용 검증의 구분

M01 p.39에서는 `md5sum`으로 얻은 값을 xattr에 저장한다. Key는 `user.checksum.md5`이며, `user`가 Namespace, `checksum.md5`가 Attribute name(속성 이름)이다. 점이 여러 개 있다고 해서 각각을 별도의 Namespace로 나누지 않는다. [STT 63:44] [M01 p.39]

동작의 역할은 다음과 같이 구분된다.

| 도구·옵션 | 예시에서 하는 일 |
|---|---|
| `md5sum` | 파일 내용으로부터 MD5 값 계산 |
| `setfattr -n ... -v ...` | 지정한 Key에 Value 저장 |
| `getfattr file.txt` | Attribute 이름 목록 확인 |
| `getfattr -n user.checksum.md5 file.txt` | 지정한 Attribute의 Value 확인 |

[STT 63:44] [STT 64:31] [M01 p.39]

핵심은 **계산한 값을 Metadata로 기록하는 일과 현재 파일 내용을 다시 검사하는 일이 다르다**는 점이다. 파일 내용이 나중에 바뀌었다고 해서 저장된 xattr 값이 자동으로 다시 계산된다는 근거는 없다. 저장된 값을 읽어 오는 작업만으로 현재 내용의 무결성이 보장되지도 않는다.

같은 페이지에는 `setfattr -x`로 Attribute를 제거한 뒤 지정 조회가 해당 속성의 부재를 보고하는 예시도 있다. 다만 현재 STT에서는 Value 읽기까지 확인되므로, 제거 단계는 **자료 보충 예시**로 구분한다. 이를 강사가 실제로 끝까지 실행한 절차로 서술하지 않는다. [M01 p.39]

### Unix I/O(유닉스 입출력)와 System call(시스템 호출)

앞에서는 파일의 이름·속성·권한을 배웠고, 이제 프로그램이 실제 접근을 요청하는 인터페이스를 다룬다. Unix I/O는 Kernel이 제공하는 낮은 수준의 입출력 인터페이스이며 System call로 구현된다. Regular file, Directory, 장치, Pipe, Socket 등 서로 다른 대상을 일관된 방식으로 다루려는 설계다. [STT 66:26] [STT 67:07] [M02 p.4]

기본 흐름은 대상을 열어 fd를 얻고, 이후 작업에 그 fd를 전달한 뒤, 사용을 마치면 닫는 것이다. 다만 같은 인터페이스를 사용한다는 사실이 모든 대상에서 모든 연산을 지원한다는 뜻은 아니다. 강사도 일부 대상에는 특정 작업을 적용할 수 없다는 제한을 설명했다. [STT 68:01] [M02 p.4]

System call은 일반적인 C 함수 호출과 역할이 다르다. `strlen()`이나 `strcat()` 같은 Library function(라이브러리 함수)은 사용자 영역에서 필요한 계산을 수행하는 예로 등장한다. 반면 System call은 Kernel에 서비스를 요청한다. 강사는 Display에 출력하려는 프로그램이 장치의 복잡한 조작을 직접 수행하지 않아도 된다는 편의성과, 임의의 하드웨어 접근을 중재하는 보호를 동기로 설명했다. [STT 73:33] [STT 74:31]

**C standard library(표준 C 라이브러리)의 Wrapper(호출을 감싸는 함수)**는 이 요청을 C 함수 형태로 사용할 수 있게 한다. 필요한 System call 번호와 인자를 준비하여 Kernel 진입을 수행하는 역할이다. 이것을 단순히 Kernel 함수의 주소로 분기하는 일반 함수 호출과 동일시하지 않는다. [STT 75:25] [STT 76:19] [STT 77:18]

`FILE`을 사용하는 **Standard I/O(표준 입출력)**는 Unix I/O 위에서 추가 기능을 제공하는 계층으로 소개된다. 따라서 System call Wrapper와 `FILE` 기반 인터페이스를 모두 같은 층이라고 보면 안 된다. 이번 회차에서는 이 관계를 세우며, 세부 Buffering(버퍼링) 동작은 후속 범위다. [STT 66:26]

**검증 필요:** Kernel 진입 instruction의 정확한 이름과 일부 전달 과정은 STT가 불명확하다. 또한 약 300개라는 System call 수 언급은 설명용 대략적 수치이며 고정된 전체 목록의 크기로 외우지 않는다. [STT 76:19] [STT 78:14]

### File descriptor와 Current file position(현재 파일 위치)

fd는 Process 안에서 열린 대상의 참조를 식별하는 **음이 아닌 정수**다. 파일 이름을 대신하는 전역 번호가 아니다. 다른 Process가 같은 fd 숫자를 갖더라도 참조 대상은 다를 수 있으며, 반드시 달라야 하는 것도 아니다. M02 p.6의 단정적인 표현은 STT의 가능성 표현과 함께 읽어야 한다. [STT 68:01] [STT 70:01] [M02 p.6]

파일을 열거나 만들 때 얻은 fd는 이후 작업에서 대상을 지정하는 데 쓰인다. Socket 생성도 fd를 얻는 예로 언급된다. 그러나 대상 식별과 그 대상의 현재 위치는 다른 개념이다. [STT 69:00]

**M02 p.5의 도식은 다음에 접근할 byte가 어디인지 보여 준다.** 파일의 byte들이 $B_0,B_1,\ldots,B_{k-1},B_k,B_{k+1},\ldots$로 나열되어 있고, Current file position의 화살표는 $B_k$를 가리킨다. 이미 지나온 영역과 다음 접근 영역의 경계를 읽어야 하며, $B_{k-1}$을 다음 byte로 착각하면 안 된다. [M02 p.5] ([M02 원본 PPTX](https://jhlee1020lee.github.io/2026-fall-study-hub/materials/system_programming/04.IO.Direct.and.Buffered.IO.pptx))

위치를 가진 Regular file에서 읽기·쓰기는 현재 위치에서 시작하고, 실제 진행한 만큼 위치가 앞으로 이동한다. 강사는 10 bytes를 읽은 다음 다시 읽을 때 매번 처음 10 bytes를 반복하지 않도록 위치를 유지한다는 동기를 설명했다. [STT 69:00] [STT 70:01]

이해를 위한 예시로, 현재 위치가 4이고 6 bytes를 성공적으로 읽었다면 다음 위치는 10이다. 이어서 3 bytes를 성공적으로 읽으면 다음 위치는 13이다.

$$
k_{\text{next}} = k_{\text{current}} + n_{\text{transferred}}
$$

여기서 $n_{\text{transferred}}$는 실제 전달된 양이다. 이 식은 현재 설명하는 위치 기반 파일 모델에 해당하며, 모든 Socket이나 Device에 동일한 위치 개념이 있다고 주장하지 않는다. Descriptor 공유에 따른 위치 문제는 슬라이드에서 예고되지만, 공유 관계의 세부 동작은 이번 회차에서 확정하지 않는다. [M02 p.5]

개념 연결: [[concepts/file-descriptor|File descriptor]] · [[concepts/file-offset|Current file position]]

### Standard descriptor와 `write`의 대상·Buffer·길이

강의의 일반적인 시작 환경에서는 다음 세 fd가 이미 열려 있다. 자료는 이들이 기본적으로 Terminal(터미널)에 연결된 상태를 설명하며, Terminal은 입력과 화면 출력을 묶어 다루는 추상화로 소개된다. [STT 70:57] [M02 p.6]

| fd | 이름 | 역할 |
|---:|---|---|
| 0 | `STDIN_FILENO` | Standard input(표준 입력) |
| 1 | `STDOUT_FILENO` | Standard output(표준 출력) |
| 2 | `STDERR_FILENO` | Standard error(표준 오류) |

이 이름들은 `unistd.h`에 제시된다. 다만 이 연결은 Redirect(재지정)되거나 닫힐 수 있는 관례적인 시작 상태이지, 모든 Process에서 영원히 유지되는 불변 상태는 아니다. [M02 p.6]

강사는 `printf()`가 최종적으로 출력할 문자열을 만드는 일과 Unix I/O로 보내는 일을 연결했다. `write`의 인자는 **어디로 보낼지 나타내는 fd**, **보낼 데이터가 있는 Buffer(버퍼)**, **보낼 byte 길이**로 읽는다. Standard output이라면 관례적인 대상 fd는 1이다. [STT 71:53] [STT 72:49]

다음은 인자의 의미를 설명하기 위해 새로 만든 예시다. 실제 실행 결과나 일반적인 전체 출력 보장을 뜻하지 않는다.

```c
char message[] = "OK\n";
ssize_t sent = write(STDOUT_FILENO, message, 3);
```

세 번째 인자의 3은 `O`, `K`, 줄바꿈의 세 bytes를 뜻한다. 배열에는 문자열을 끝내는 `\0`도 있지만 이 호출이 요청하는 출력 범위에는 포함하지 않았다. `sent`는 요청량을 다시 적어 둔 변수가 아니라 호출 결과를 받는 변수다. 모든 경우에 요청량만큼 출력된다고 가정하는 완성된 I/O 코드는 후속 내용이 필요하다. [M02 p.7] [STT 72:49]

2024년 2학기 표기의 중간고사 Q2는 정수를 문자 배열로 만든 뒤 Unix I/O로 보내는 구현 문제다. 이번 강의와 직접 연결되는 부분은 **출력 대상과 이미 만든 문자열의 유효 길이를 구분하는 판단**이다. 전체 정수 변환에는 C pointer·배열·정수 나눗셈이 추가로 필요하므로 문항 전체는 부분 연결로 둔다. 풀이에 접근할 때에는 숫자 변환, 문자열 순서, 출력할 byte 범위를 나누어 확인해야 하며, 제공된 부호 반전 방식도 정수 범위 전체에서 안전하다고 받아들이지 않는다. [EX:sp_2024_2_midterm_q02 p.4] [EX:sp_2024_2_midterm_q02 p.5]

또한 `printf()` 한 번이 언제나 `write()` 한 번과 대응한다고 결론내리지 않는다. 이번 설명은 계층 관계와 인자의 의미를 연결한 것이며, 실제 호출 횟수에 영향을 주는 Buffering 상세는 아직 후속 범위다. [STT 71:53]

### Unix I/O API 표와 Platform type의 조회

M02 p.7의 API 표는 개별 함수를 모두 구현하는 예제가 아니라 **작업별 분류표**다. 다음과 같이 무엇을 하려는 호출인지부터 구분한다.

| Operation(작업) | 대표 API | 자료에 나열된 관련 항목 |
|---|---|---|
| Open and create | `open`, `creat` | `openat` |
| Read and write | `read`, `write` | `pread`, `readv`, `pwrite`, `writev` |
| Positioning(위치 변경) | `lseek` | `llseek`, `lseek64` |
| Close | `close` | 열린 참조의 사용 종료 |
| Remove from filesystem | `remove` | `unlink`, `unlinkat`, `rmdir` |

[M02 p.7]

이 표를 근거로 모든 C API가 Kernel System call 하나와 일대일로 대응한다고 단정하지 않는다. 또한 `read`·`write`의 모든 오류 조건, 부분 전달 처리, 각 변형의 세부 계약을 이번 회차에서 모두 설명했다고 확대하지 않는다.

표에 등장하는 `off_t` 같은 이름은 Platform(플랫폼)에 따른 차이를 type 이름 뒤로 감추는 역할을 한다. 강사는 해당 환경의 실제 정의를 알아보는 방법으로 **Preprocessing(전처리)** 결과를 조사했다. [STT 78:14] [STT 80:11]

자료의 명령 구조는 다음과 같다. 아래는 슬라이드의 검색 패턴을 인용부호로 묶어 설명한 예시이며, 현재 환경에서 실행해 얻은 출력은 아니다.

```sh
echo '#include <stdlib.h>' | gcc -E - | grep -w '_*off_t'
```

`echo`가 만든 C source 한 줄을 Pipe(파이프)로 넘기고, `gcc -E -`는 표준 입력을 받아 전처리한다. Header가 포함하는 다른 Header까지 처리하면서 모인 선언 중에서 `grep`으로 관심 type을 찾는 방식이다. `-E`는 전처리 단계까지 수행한다는 뜻이며 실행 파일을 만드는 시연이 아니다. [STT 79:10] [STT 80:51] [M02 p.7]

강의에서는 해당 환경의 `off_t`가 `long`으로 이어지는 정의를 설명했다. 이것을 모든 Platform에서의 고정 type·고정 크기로 외우면 추상화의 목적을 놓친다. Embedded system의 16-bit 언급도 차이가 가능하다는 동기를 위한 가정이며 지원 규격 보장은 아니다. 불명확한 내부 `typedef` 식별자는 복원하지 않는다. [STT 80:11] [STT 81:56]

### `open`의 Pathname, Flags, Mode

`open()`은 Kernel에 파일 접근을 준비하겠다고 알리고, 성공하면 이후 작업에 사용할 fd를 돌려준다. **Pathname(경로명)**은 대상 이름과 위치, **Flags(동작 플래그)**는 접근 방식·File status(파일 상태)·생성 요청, **Mode(생성 권한 모드)**는 새 파일의 Permission과 관련된다. 이 세 역할을 섞지 않는 것이 중요하다. [STT 83:07] [STT 85:02] [M02 p.8]

M02 p.8은 `O_RDONLY`와 `O_APPEND`를 Flag의 구체적인 예로 든다. `O_RDONLY`는 Read-only(읽기 전용) 접근을, 쓰기 접근과 함께 사용하는 `O_APPEND`는 Append(파일 끝에 덧붙이는 쓰기)를 지정한다. 따라서 앞의 기본 Current file position 설명도 해당 Flag와 함께 읽어야 하며, 이를 새 파일의 Permission을 정하는 Mode와 혼동하지 않는다. 이 페이지는 Flag 예시와 Manual 참조를 제공하므로, 세부 위치 처리나 동시 쓰기의 보장까지 이번 강의에서 설명한 것으로 확대하지 않는다. [M02 p.8]

M02 p.3의 예시는 다음 조합을 사용한다. 아래 코드는 원본의 곡선 따옴표를 일반 C 따옴표로 정리한 설명용 표현이다.

```c
int fd = open("unix.io",
              O_CREAT | O_WRONLY,
              S_IRWXU | S_IRGRP);
```

`O_CREAT`는 필요할 때 생성하도록 요청하고, `O_WRONLY`는 이 호출의 쓰기 접근 방식을 나타낸다. 마지막의 `S_IRWXU | S_IRGRP`는 새 파일에 요청하는 Mode로서 Owner의 `rwx`와 Group의 `r`를 표현한다. **열린 fd의 접근 방식과 생성되는 파일의 Permission은 같은 인자가 아니다.** 이 예시만으로 최종 Permission에 관여하는 모든 생성 정책까지 설명했다고 보지는 않는다. [M02 p.3] [M02 p.8]

M02 p.8에는 두 인자와 세 인자를 받는 `open` 형태가 나란히 표시된다. 강사는 이를 C++식 Overloading(오버로딩)으로 해석하지 말고, `printf()`처럼 **Variable parameter(가변 인자)**를 받는 선언과 연결했다. 전처리 결과의 `...`가 이 점을 보여 준다. [STT 83:38] [STT 84:11] [M02 p.8]

개념을 드러내는 선언 형태는 다음과 같다.

```c
int open(const char *pathname, int flags, ...);
```

추가 Mode는 새 파일 생성과 관련된 경우에 필요하다. 모든 `open` 호출에 세 번째 인자가 항상 의미 있다고 생각하거나, 슬라이드의 두 형태를 같은 이름의 별개 C 함수 선언으로 그대로 복사하면 안 된다. [STT 85:02] [STT 85:54]

관련 Header로 `sys/types.h`, `sys/stat.h`, `fcntl.h`가 제시되며, 구체적인 Flag와 Mode 조건은 Manual을 확인하도록 안내한다. STT의 마지막 암기 관련 문장은 대상이 명확하지 않으므로 모든 상수의 숫자값을 외우라는 요구로 확대하지 않는다. [M02 p.8]

### `creat`, `errno`, 실패를 확인하는 코드

`creat()`는 철자에 마지막 `e`가 없는 API 이름이다. 강의는 `open()`으로 생성 기능을 표현할 수 있어도 이전 프로그램과의 호환을 위해 이 API가 남아 있다고 설명한다. 이름에 관한 일화는 농담으로 등장하므로, 불명확한 발화를 역사적 직접 인용으로 복원하지 않는다. [STT 85:54] [STT 86:49]

`open`·`creat`는 성공하면 fd를 반환하고 실패하면 `-1`을 반환한다. `errno`는 실패 이유를 알아보는 오류 상태와 연결되며, `perror()`는 이를 사람이 읽을 오류 메시지로 보고하는 예시에 등장한다. STT의 전역 변수라는 표현만으로 thread 사이의 공유 방식까지 단정하지 않는다. [STT 86:49] [STT 87:44] [M02 p.8]

M02 p.9의 위쪽 Code box는 `/etc/hosts`를 `O_RDONLY`로 열고, 음수 반환값이면 오류를 보고한 뒤 실패로 종료한다. 아래쪽 Code box는 `creat()`로 `log`를 만들며 Owner의 Read·Write에 해당하는 `S_IRUSR | S_IWUSR`를 사용한다. 두 box는 서로 다른 예시다. 중복된 `fd` 선언을 가진 하나의 완성 프로그램으로 합쳐서는 안 된다. [M02 p.9]

다음은 첫 번째 Code box의 판단 구조만 풀어 쓴 표현이다. 선행 선언·Header 등을 포함한 전체 프로그램은 아니다.

```c
fd = open("/etc/hosts", O_RDONLY);

if (fd < 0) {
    perror("Cannot open file");
    exit(EXIT_FAILURE);
}
```

반환값을 먼저 저장한 뒤 실패를 검사하므로, 실패했는데도 유효한 fd를 얻었다고 가정하는 일을 피한다. 여기에서 오류 보고보다 먼저 이해할 것은 **성공 시 얻는 값과 실패 표시가 어떻게 구분되는지**다. [M02 p.9]

**발화 해석 주의:** Read-only로 연 예시 뒤에 쓰기와 관련된 표현이 나오지만, 이를 `O_RDONLY` fd에도 쓰기가 허용된다는 주장으로 해석하지 않는다. 해당 설명에서 실제 쓰기 시연은 확인되지 않는다. 원본의 곡선 따옴표도 검증된 C 실행 코드와 구분한다. [STT 87:44] [STT 88:33] [M02 p.9]

### `close`와 File descriptor 재사용

`close(fd)`는 해당 열린 참조의 사용을 마쳤음을 Kernel에 알린다. 성공 시 0, 실패 시 `-1`을 반환한다. 성공 시 fd를 돌려주는 `open`이나 전달한 byte 수와 관련된 `read`·`write`의 반환값과 구분해야 한다. [STT 88:33] [M02 p.10]

```c
#include <unistd.h>

int close(int fd);
```

M02 p.11은 반환값을 검사하고 실패하면 `perror()`와 `EXIT_FAILURE`를 사용하는 보조 예시다. 다만 이 페이지의 코드 전체를 실제로 차례대로 설명했는지는 확인되지 않으므로, 생략된 선행 처리까지 강의 내용으로 복원하지 않는다. [M02 p.11]

강사는 `open`이 Process에서 사용 가능한 가장 작은 fd를 반환한다는 성질을 설명했다. 0·1·2만 열려 있고 다른 fd가 없다면 다음 성공한 `open`은 3을 받을 수 있다. 이 결과는 초기 상태를 전제로 하므로 모든 Process의 첫 `open` 결과가 항상 3이라는 뜻은 아니다. [STT 89:33]

이 성질은 **Double close(중복 닫기)**를 단순한 오류보다 위험하게 만든다. 이해를 위한 구체화로, 하나의 Process에서 여러 thread가 다음 순서로 동작한다고 하자.

| 순서 | 동작 | fd 3의 의미 |
|---|---|---|
| 1 | 처음에 파일 A가 fd 3으로 열려 있음 | 파일 A에 대한 열린 참조 |
| 2 | Thread A가 `close(3)` 수행 | 3이 사용 가능한 번호가 됨 |
| 3 | Thread B가 다른 파일을 열어 fd 3을 받음 | 새 파일 B에 대한 참조 |
| 4 | Thread C가 예전 값을 믿고 `close(3)` 수행 | 파일 B의 참조를 닫을 수 있음 |

이 예시는 강의의 A·B·C 순서를 숫자로 구체화한 것이며, 실제 실행 기록은 아니다. [STT 90:21] [M02 p.10]

닫힌 번호가 아직 재사용되지 않았다면 다시 닫는 작업은 오류가 될 수 있다. 그러나 재사용된 뒤에는 같은 숫자가 이미 다른 파일을 뜻한다. 따라서 “이미 닫았으니 다시 닫아도 오류만 날 것”이라는 가정은 성립하지 않는다. **fd 숫자는 영구적인 파일 identity가 아니며, 현재 그 숫자가 가리키는 참조를 기준으로 해석된다.** [M02 p.10]

이번 회차는 이 재사용 문제를 설명한 뒤 종료된다. 따라서 M02 뒤쪽의 상세 `read`·`write` 처리, Short count, Buffering 모드와 Standard I/O 구현을 이번 시간에 완료한 내용으로 이어 붙이지 않는다. [STT 90:21]

## 강의 흐름과 연결

### Unix filesystem에서 Unix I/O로 이어지는 질문

[[courses/system_programming/lectures/2026-09-09-lecture-03|이전 강의(9월 9일)]]의 기본 Unix filesystem 개념에서 출발해, 이번에는 **어떤 경로로 파일에 도달하고, 누구의 권한으로 접근하며, 열린 대상을 프로그램이 어떻게 식별하는가**를 순서대로 구체화했다. 이전 회차와의 연결은 강의 시작의 회고로 확인되며, 이전 자료 전체를 이번 시간에 다시 설명한 것으로 보지는 않는다. [STT 02:34]

전반부에서는 Mount point와 Link를 통해 **이름과 실제 대상의 관계**를 다뤘다. 같은 이름 아래 다른 filesystem이 나타날 수도 있고, 서로 다른 이름이 같은 Inode를 가리킬 수도 있다. 이어 Permission·SUID·SGID를 통해 **대상을 찾는 일과 접근이 허용되는 일**을 구분했다. xattrs와 ACL은 기본 Permission만으로 표현하기 어려운 추가 정보와 접근 요구를 연결했다. [M01 p.12] [M01 p.15] [M01 p.29] [M01 p.37]

후반부에서는 이 구조를 이용하는 프로그램의 관점으로 이동했다. `open`에서 받은 File descriptor로 작업 대상을 지정하고, Current file position으로 다음 접근 위치를 추적하며, `close`로 사용을 종료한다. 마지막의 Double close 사례는 **같은 숫자가 계속 같은 파일을 뜻하지는 않는다**는 점을 보여 주며 강의를 마무리한다. [M02 p.5] [M02 p.8] [M02 p.10]

### Concept 연결 지도

다음 연결은 본문에서 설명한 관계를 찾아가는 지도다.

- [[concepts/unix-filesystem|Unix filesystem]] → [[concepts/mount-point|Mount point]] → [[concepts/filesystem-hierarchy-standard|Filesystem Hierarchy Standard]]: 하나의 경로 계층에 filesystem을 연결하고 주요 위치의 용도를 찾는다.
- [[concepts/inode|Inode]] ↔ [[concepts/hard-link|Hard link]] · [[concepts/symbolic-link|Symbolic link]]: 이름이 같은 객체를 직접 참조하는지, pathname을 담은 별도 파일을 거치는지 비교한다.
- [[concepts/file-permissions|File permissions]] → [[concepts/chmod|chmod]] → [[concepts/suid-sgid|SUID and SGID]] → [[concepts/real-effective-identity|Real and effective identity]]: 허용 동작의 설정에서 실행 중 권한 주체의 구분으로 이어진다.
- [[concepts/extended-file-attributes|Extended file attributes]] → [[concepts/access-control-list|Access Control List]]: 추가 Metadata를 저장하는 구조와 특정 사용자에게 접근을 표현하는 사례를 연결한다.
- [[concepts/standard-io|Standard I/O]] → [[concepts/unix-io|Unix I/O]] → [[concepts/system-call|System call]]: 추가 기능을 제공하는 계층에서 Kernel 서비스 요청으로 내려간다.
- [[concepts/file-descriptor|File descriptor]] ↔ [[concepts/file-offset|Current file position]]: 열린 대상의 식별과 그 대상 안에서 다음에 접근할 위치를 구분한다.

### 그림·표를 이용한 복습 지점

**M01 p.12 — Mount 전후의 경로 연결.** `share`와 `extern`에서 나가는 화살표의 목적지를 각각 찾는다. Mount 뒤 흐리게 표시된 `hello`와 새 filesystem의 `extern`을 구분하면, 삭제 없이도 같은 Directory 이름으로 보이는 내용이 달라지는 이유를 확인할 수 있다. [M01 p.12]

**M01 p.29 — Permission의 두 가지 분류.** 가로의 묶음은 Owner·Group·Other이고, 묶음 안의 색상은 `r`·`w`·`x`다. 맨 앞의 type 문자를 제외한 뒤 아홉 자리를 읽어야 한다. 아래 설명과 함께 File의 실행과 Directory의 경로 통과를 비교한다. [M01 p.29]

**M02 p.5 — 다음 접근 위치.** Current file position의 화살표는 $B_k$를 가리킨다. $B_{k-1}$까지의 영역과 다음 접근이 시작될 영역의 경계를 먼저 찾고, 실제 전달량만큼 위치를 이동시키는 계산으로 연결한다. File descriptor를 가리키는 화살표와 위치 화살표를 같은 의미로 읽지 않는다. [M02 p.5]

**M01 p.34·p.38 — 변경 전후 출력 비교.** SUID 예시에서는 Real 정보가 유지되는 동안 어느 Effective 항목이 달라졌는지 찾는다. ACL 예시에서는 `+` 표시와 추가 사용자 항목을 함께 확인한다. 두 표 모두 한 줄의 설정 명령보다 **설정이 어느 속성에 반영되었는지**를 읽는 연습에 적합하다. [M01 p.34] [M01 p.38]

### 이번 회차에서 확인되는 강조점

강사는 약 3,000개 Dataset 파일의 Alias, 제한된 제출 Directory에 접근하는 프로그램, 연속 이름 조회에서의 저장소 재사용, fd가 다른 파일에 재사용되는 상황을 구체적인 동기로 사용했다. 이는 이번 회차에서 확인되는 예시이며, 측정된 성능 우위나 시험 출제 가능성을 뜻하지 않는다. [STT 25:15] [STT 52:22] [STT 53:51] [STT 90:21]

FHS는 전체 목록 암기보다 주요 용도를 살펴보도록 안내했고, Permission Macro와 API의 세부 사항은 Manual이나 실제 선언을 찾아보는 방법을 보여 주었다. 따라서 복습도 **개념을 설명하는 능력과 필요한 정의를 찾는 능력**을 함께 확인한다. [STT 32:26] [STT 41:03] [STT 44:33] [STT 79:10]

## 핵심 요약

- **Mount point:** 다른 filesystem을 Directory에 연결한다. 기존 내용이 가려지는 것은 삭제와 다르며, 파일 Permission과 Mount option은 서로 다른 제약이다. [M01 p.12] [M01 p.13]
- **Metadata:** `ls -l`은 File type·Permission·Hard link count·Owner·Group·크기·시간·이름을 보여 준다. `ctime`은 생성 시각이 아니며, 내용 쓰기로 `mtime`과 함께 바뀔 수 있다. [M01 p.14] [STT 17:13]
- **Hard link와 Symbolic link:** 같은 Inode의 여러 이름과, Target pathname을 담은 별도 파일을 구분한다. 수정 결과가 함께 보이는 이유와 Target 삭제 이후의 결과도 이 구조에서 도출한다. [M01 p.15] [M01 p.18]
- **Directory와 FHS:** `ls -ld`는 Directory 자체를 관찰한다. 강의의 Directory 모델에서 Hard link count는 $2+N$이며, FHS는 용도에 맞는 위치를 찾는 기준이다. [M01 p.21] [M01 p.23]
- **Permission과 Sticky bit:** File 내용 접근, Directory entry 변경, 경로 통과는 별개다. Sticky bit는 공유 Directory의 이름 변경·삭제 주체를 추가로 제한한다. [M01 p.29] [M01 p.31]
- **SUID·SGID:** Real identity와 Effective identity를 구분한다. SUID만 설정한 예시에서 Effective group까지 바뀌었다고 추정하지 않는다. [M01 p.34] [M01 p.35]
- **이름 조회와 검사 코드:** Static storage의 재사용 때문에 필요한 문자열을 복사한다. 조회 실패·할당 실패·생략된 오류 처리를 따로 검토하며, Directory scan 결과를 완전한 보안 판정으로 읽지 않는다. [M01 p.35] [M01 p.36]
- **xattrs와 ACL:** 기본 Permission 밖의 접근 요구와 추가 Metadata를 표현한다. 저장된 checksum 값을 읽는 작업은 현재 파일 내용을 다시 검증하는 작업과 다르다. [M01 p.37] [M01 p.38] [M01 p.39]
- **Unix I/O:** C Wrapper, Kernel System call, `FILE` 기반 Standard I/O의 역할을 구분한다. File descriptor는 Process 안의 참조 식별자이고, Current file position은 다음 접근 위치다. [M02 p.4] [M02 p.5] [M02 p.7]
- **`open`과 `close`:** Flags는 접근·생성 방식, Mode는 새 파일의 Permission과 관련된다. 반환값을 확인하고, 닫힌 fd 번호가 재사용될 수 있다는 점까지 고려한다. [M02 p.8] [M02 p.9] [M02 p.10]

### 일차 강의 개념 회상

#### Q01. Mount point 아래의 파일이 보이지 않으면 삭제되었다고 판단해도 되는가?

자료의 `extern` 예시를 Mount 이전·이후·Unmount 이후로 나누어 설명하라. `ls -1`과 `echo "hello"`의 줄바꿈도 함께 확인하라.

<details><summary>정답</summary>

Mount 이후에는 연결된 filesystem의 내용이 그 Directory 이름 아래에서 보인다. 기존 파일은 가려졌으며, 예시에서는 Unmount 후 다시 나타난다. `ls -1`은 한 줄에 한 이름을 표시한다. 예시의 `echo "hello"`는 줄바꿈까지 포함하여 6 bytes를 출력한다. [STT 04:42] [STT 09:21] [M01 p.11] [M01 p.12]

</details>

#### Q02. `ro`, `noatime`, `noexec`, `nosuid`는 각각 무엇을 제한하는가?

`atime` 설명에 Mount option이 필요한 이유와 `nodev`·`size`·`iocharset`의 역할도 구분하라.

<details><summary>정답</summary>

`ro`는 쓰기, `noatime`은 Access time 갱신, `noexec`는 실행, `nosuid`는 SUID/SGID 효과를 제한한다. 접근 시각의 갱신에는 비용이 들며 실제 갱신 여부는 정책에 영향을 받는다.

자료에서 `nodev`는 Device file의 기능 제한, `size`는 예시 filesystem의 최대 크기, `iocharset`은 파일 이름의 문자셋과 연결된다. `relatime`의 한 줄 설명은 전체 정책 명세가 아니다. [STT 12:32] [M01 p.13]

</details>

#### Q03. `ls -l`의 크기·시간·Owner·Group은 어떻게 읽어야 하는가?

`mtime`과 `ctime`이 함께 바뀔 수 있는 이유를 설명하라.

<details><summary>정답</summary>

크기는 표시 대상의 byte 단위 속성이며, Owner와 Group은 Permission을 해석할 주체 구분에 사용된다. Group은 협업 파일의 접근을 공유하는 동기로 소개되었다.

`mtime`은 내용 수정, `ctime`은 Metadata·상태 변경과 관련된다. 내용 쓰기로 파일 크기 같은 속성도 바뀌면 두 시간이 함께 갱신될 수 있다. `ctime`을 Creation time으로 해석하지 않는다. [STT 16:15] [STT 17:13] [M01 p.14]

</details>

#### Q04. Hard link와 Symbolic link를 Inode와 Target pathname으로 비교하라.

<details><summary>정답</summary>

Hard link는 같은 Inode를 참조하는 다른 이름이다. Symbolic link는 별도 Inode를 가진 파일에 Target pathname을 담는다. 따라서 Symbolic link 자체의 크기는 Target 내용의 크기와 다를 수 있다.

강의의 일반 모델에서 Hard link는 filesystem 경계를 넘지 못하고 Directory에 대한 임의 생성도 제한된다. Symbolic link는 pathname으로 그런 대상을 표현할 수 있지만 Broken link가 남을 수 있다. [M01 p.15]

</details>

#### Q05. Link를 통한 수정과 원래 이름 삭제의 결과는 어떻게 다른가?

대량 Dataset의 Alias 동기와 연결하라.

<details><summary>정답</summary>

Hard link를 통한 수정은 같은 Inode의 파일 내용을 바꾸므로 다른 Hard link로 읽어도 같은 결과가 보인다. Symbolic link를 통한 일반적인 접근은 Target pathname을 따라간다.

원래 이름을 삭제해도 남은 Hard link로는 접근할 수 있지만, Symbolic link의 Target이 없어지면 Link 자체만 남을 수 있다. 대량 파일을 여러 위치에서 이용하는 Alias의 동기와 연결되지만, 모든 상황의 성능 우위를 보장하지는 않는다. [STT 25:15] [M01 p.16] [M01 p.17] [M01 p.18]

</details>

#### Q06. File type 문자와 `ls -l`, `ls -la`, `ls -ld`를 구분하라.

Hidden file은 접근 보호를 받는 파일인가?

<details><summary>정답</summary>

첫 문자의 `-`, `d`, `l`, `p`, `s`, `c`, `b`는 각각 Regular file, Directory, Symbolic link, Named pipe, Socket, Character device file, Block device file을 나타낸다.

`ls -l`에 Directory를 주면 내부 항목을, `ls -ld`는 Directory 자체의 속성을 본다. `-a`는 점으로 시작하는 이름도 포함한다. Hidden name은 표시 관례이며 접근 보호를 대신하지 않는다. `.`은 현재 Directory, `..`은 부모다. [M01 p.19] [M01 p.20] [M01 p.21]

</details>

#### Q07. 직속 Subdirectory가 두 개인 Directory의 Hard link count를 어떻게 설명하는가?

<details><summary>정답</summary>

강의의 전통적인 모델에서는 부모 안의 이름 entry 하나와 자신의 `.` 하나가 기본 두 참조다. 직속 Subdirectory마다 그 안의 `..`이 부모를 한 번 더 참조한다.

따라서 $2+2=4$다. 일반 파일 개수나 모든 후손 Directory를 더하지 않으며, 이 수식을 모든 filesystem의 보편적인 관측값으로 보장하지 않는다. [STT 30:24] [M01 p.21]

</details>

#### Q08. FHS의 주요 경로와 Home directory 항목은 어떤 역할을 하는가?

`/proc`, `/usr/include`, `/var/log`를 구분하라. 자료의 `/var/db`·`/var/run` 설명, `~` 표기, Home의 `.cache`·`.config`·`.local`·응용 프로그램별 설정도 용도와 연결하라. 이 배치를 모든 시스템에 그대로 적용해도 되는가?

<details><summary>정답</summary>

`/proc`는 Process·Kernel 정보를 파일 인터페이스로 제공하고, `/usr/include`는 C Header, `/var/log`는 System log의 위치다. `/etc`의 시스템 전체 설정과 Home의 사용자별 파일·설정을 구분한다.

M01 p.26에서 `/var/db`는 Gentoo의 Portage가 사용하는 Configuration·Source file의 위치다. `/var/run`은 Runtime variable data를 담으며, 자료의 FHS 3.0 주석은 `/run`에 매핑한다고 설명한다.

M01 p.27은 `~`를 예시 Home 경로 `/home/<USER>`의 축약으로 표시한다. `.cache`는 User cached data, `.config`는 User-specific configuration, `.local`은 User local data(`bin`·`lib`·`share`)다. `.mozilla`·`.ssh`·`.vim`은 각각 Mozilla·SSH·Vim의 설정 예시이며, 사용자 생성 파일·Directory도 Home에 놓인다. `ls ~/.config`는 해당 설정 Directory 내부를 조회한다. Hidden name 자체는 접근 보호가 아니다.

학습 목표는 전체 목록 암기보다 필요한 위치를 용도로 찾는 것이다. 배포판·FHS 주석과 예시 Home 경로를 모든 시스템·계정의 고정 배치로 일반화하지 않는다. [STT 32:26] [STT 34:33] [M01 p.24] [M01 p.25] [M01 p.26] [M01 p.27]

</details>

#### Q09. Directory의 `rwx`와 `chmod 750`을 설명하라.

`chmod g+w`와는 어떻게 다른가?

<details><summary>정답</summary>

Directory의 `r`은 이름 목록 읽기, `w`는 entry 추가·삭제 같은 변경, `x`는 진입·경로 통과와 관련된다. 내부 파일의 내용 Permission과는 별개다.

`750`은 Owner `rwx`, Group `r-x`, Other `---`다. `g+w`는 기존 설정에 Group의 Write permission을 추가한다. 자료의 마지막 파일명 불일치는 실제 실행 결과로 보정하여 외우지 않는다. [M01 p.29] [M01 p.30]

</details>

#### Q10. Sticky bit가 제한하는 작업과 주체는 무엇인가?

`struct stat` 및 Manual 참조와 연결하라.

<details><summary>정답</summary>

Sticky bit가 설정된 Directory에서는 내부 파일의 이름 변경·삭제 주체를 파일 Owner, Directory Owner, 특권 주체로 추가 제한한다. 파일 내용의 Read·Write를 직접 제어하거나 필요한 다른 Permission을 대신 부여하지 않는다.

자료는 목록의 `t`, Mode의 `S_ISVTX`, `man 2 stat`, `man 7 inode`를 연결한다. 불명확한 숫자 발화와 `stat` 변형 이름은 검증 필요로 남긴다. [STT 41:49] [STT 43:30] [M01 p.31]

</details>

#### Q11. World-writable directory와 `noexec`는 왜 함께 등장했는가?

<details><summary>정답</summary>

여러 사용자가 파일을 놓을 수 있는 공간에서 실행까지 허용되면, 침해된 프로그램이 추가 실행 파일을 배치하는 데 이용할 수 있다는 보안 동기였다.

`S_IWOTH`는 파일 Mode의 Other Write permission, `ST_NOEXEC`는 filesystem의 실행 제한과 연결된다. Directory의 `x`와 같은 제어가 아니며, 하나의 flag로 모든 공격 가능성이나 안전성을 판정할 수는 없다. [STT 47:04] [M01 p.32]

</details>

#### Q12. 파일 Owner와 Group을 바꾼 뒤 SUID만 설정하면 어떤 identity가 변하는가?

<details><summary>정답</summary>

자료의 `4755` 예시는 실행 전 Real user/group과 Effective user/group이 모두 `devel`인 조건이다. 실행 후 Real 정보는 유지되고 Effective user만 파일 Owner인 `tester`로 바뀐다. SGID가 없으므로 Effective group은 실행 전 값인 `devel`을 유지한다.

파일의 소유 Group을 변경했다는 사실만으로 SGID의 실행 효과까지 생기지 않는다. SUID가 설정되었다고 항상 Root가 되는 것도 아니며 파일 Owner와 실행 조건을 확인해야 한다. [STT 51:21] [M01 p.34] [M01 p.35]

</details>

#### Q13. `getpwuid`·`getgrgid` 결과의 이름을 왜 복사하는가?

어떤 메모리를 `free`해야 하는가?

<details><summary>정답</summary>

반환 저장소는 다음 동일 API 호출에서 재사용될 수 있다. 이전 이름을 보존하려면 `strdup`로 별도 문자열을 복사한다.

사용 후 해제할 대상은 복사하여 소유한 문자열이다. 조회 함수의 Static storage 자체를 새로 할당받은 메모리처럼 해제하지 않는다. 자료 코드에는 pointer 초기화와 실패 처리의 한계가 있으므로 성공 경로만으로 안전성을 판단하지 않는다. [STT 53:51] [STT 55:01] [M01 p.35]

</details>

#### Q14. Directory scan 예시는 어떤 순서로 잠재적 위험 설정을 찾는가?

<details><summary>정답</summary>

Directory를 열고 fd를 얻은 뒤 entry를 반복 조회한다. `fstatat`와 `AT_SYMLINK_NOFOLLOW`로 entry Metadata를 얻고, Regular file 여부와 Root 소유·SUID 또는 Root Group·SGID의 조합을 확인한다. 이어 검사한 filesystem에 `ST_NOEXEC`와 `ST_NOSUID`가 모두 없는지 본다.

`getNext`는 구현이 생략된 보조 함수다. 오류 처리와 문법의 생략이 있고, 검사 결과가 취약성이나 실제 실행 가능성 전체를 증명하지는 않는다. [M01 p.36]

</details>

#### Q15. xattrs의 Key와 네 Namespace는 어떤 역할을 하는가?

<details><summary>정답</summary>

Key는 `namespace.attribute` 형태다. 자료는 `security`를 보안 Kernel module, `system`을 Kernel의 시스템 객체, `trusted`를 `CAP_SYS_ADMIN` capability가 있는 Process, `user`를 MIME type·checksum·문자 인코딩 등의 추가 정보와 연결한다.

xattrs는 Permission만을 위한 기능이 아니며, 자료의 문자열 예시를 모든 Value의 보편적 형식 제한으로 확대하지 않는다. [STT 59:33] [M01 p.37]

</details>

#### Q16. 기본 Mode가 `640`인 파일에 특정 사용자 ACL을 추가하기 전후에 무엇을 확인하는가?

자료의 xattrs 지원 조회 경로와 그 한계, ACL 변경 후 확인할 출력을 설명하라.

<details><summary>정답</summary>

자료는 `mount | grep "/ "`의 출력에서 Root에 연결된 `/dev/sda4`와 ext4를 확인한 뒤, `cat /proc/fs/ext4/sda4/options | grep xattr`로 `user_xattr`를 찾는다. 이 경로는 예시 환경에 해당하며, 그 한 줄만으로 모든 filesystem의 ACL 지원·유효 권한을 보장하지 않는다.

`640`은 Owner `rw-`, Group `r--`, Other `---`다. `setfacl -m u:svn:r file.txt`로 Named user의 Read 항목을 추가한 뒤, `ls -l`의 `+`와 `getfacl`의 `user:svn:r--`을 확인한다. 출력의 `mask::r--`도 관찰하되 Mask 계산 전체는 이번 범위로 확대하지 않는다. [STT 60:54] [STT 61:20] [STT 62:42] [M01 p.38]

</details>

#### Q17. `user.checksum.md5`의 저장과 현재 내용 검증은 왜 다른가?

<details><summary>정답</summary>

`user`가 Namespace이고 `checksum.md5`가 Attribute name이다. `md5sum`은 내용을 바탕으로 값을 계산하고, `setfattr`는 그 값을 Metadata에 저장한다. 기본 `getfattr` 예시는 이름 목록, `-n` 조회는 지정한 값을 보여 준다.

파일 내용이 바뀌어도 저장된 값이 자동으로 다시 계산된다는 근거는 없다. Attribute 제거는 같은 페이지의 자료 보충 예시이며 실제 발화로 확인된 전체 시연은 아니다. [STT 63:44] [M01 p.39]

</details>

#### Q18. System call, C Wrapper, Standard I/O의 역할을 구분하라.

<details><summary>정답</summary>

System call은 Kernel에 서비스를 요청한다. C Wrapper는 그 요청을 C 함수 형태로 사용하도록 번호·인자 전달 등을 감싼다. `FILE` 기반 Standard I/O는 Unix I/O 위에서 추가 기능을 제공한다.

API 표는 열기·읽기/쓰기·위치 변경·닫기·이름 제거를 분류한다. 모든 C API가 Kernel 호출 하나와 일대일로 대응하거나, 모든 대상이 모든 연산을 지원한다는 뜻은 아니다. [STT 66:26] [STT 73:33] [M02 p.4] [M02 p.7]

</details>

#### Q19. File descriptor와 Current file position은 무엇이 다른가?

현재 위치가 4이고 실제로 6 bytes를 읽었다면 다음 위치는 얼마인가?

<details><summary>정답</summary>

File descriptor는 Process 안에서 열린 참조를 식별하는 음이 아닌 정수다. 다른 Process의 같은 숫자와 대상이 같을 수도, 다를 수도 있다.

위치를 가진 Regular file에서 Current file position은 다음 접근 byte를 나타낸다. 예시의 다음 위치는 $4+6=10$이다. 이 위치 모델을 모든 Socket·Device에 적용하거나, 요청량이 항상 실제 전달량과 같다고 가정하지 않는다. [M02 p.5] [M02 p.6]

</details>

#### Q20. Standard descriptor와 `write`의 세 인자를 설명하라.

문자열 끝의 `\0`도 항상 출력해야 하는가?

<details><summary>정답</summary>

일반적인 시작 환경에서 0·1·2는 각각 Standard input·Standard output·Standard error다. 이들은 재지정되거나 닫힐 수 있다.

`write`는 fd로 대상, Buffer로 데이터의 시작 위치, 길이로 보낼 byte 범위를 지정한다. 문자열 끝의 `\0`을 반드시 포함해야 하는 것은 아니다. `printf` 한 번과 `write` 한 번의 일대일 대응도 이번 설명으로 보장되지 않는다. [STT 72:49] [M02 p.6] [M02 p.7]

</details>

#### Q21. `gcc -E -`를 이용한 `off_t` 조회는 무엇을 확인하는 과정인가?

<details><summary>정답</summary>

`#include`가 있는 C source를 표준 입력으로 전달하고 전처리하여, Header를 거쳐 모인 선언에서 관심 type을 찾는 과정이다. `-E`는 전처리 단계까지 수행한다는 뜻이며 실행 파일 생성 시연이 아니다.

해당 환경의 실제 정의를 찾는 것이 목적이다. 자료의 `long` 설명을 모든 Platform의 고정 type·크기로 외우지 않으며, 불명확한 내부 식별자는 복원하지 않는다. [STT 79:10] [STT 81:56] [M02 p.7]

</details>

#### Q22. `open`의 Pathname·Flags·Mode를 구분하라.

`O_RDONLY`와 쓰기 접근에 함께 사용하는 `O_APPEND`는 각각 무엇을 지정하는가? 두 인자·세 인자 표기가 C++식 Overloading을 뜻하는가?

<details><summary>정답</summary>

Pathname은 대상 경로와 이름, Flags는 접근·File status·생성 요청, Mode는 새 파일의 Permission과 관련된다. `O_RDONLY`는 Read-only 접근, 쓰기 접근과 함께 사용하는 `O_APPEND`는 Append를 지정한다. 이 Flags를 생성 Permission으로 읽지 않는다.

두 호출 형태는 가변 인자 선언과 연결된다. C++식 Overloading으로 해석하거나 두 선언을 별도 C 함수처럼 복사하지 않는다. 추가 Mode는 생성과 관련된 경우에 필요하다. 세부 Flag 조건은 Manual 참조 대상이며, Append의 상세 위치 처리·동시 쓰기 보장까지 이번 회차에서 학습했다고 확대하지 않는다. [STT 84:11] [STT 85:54] [M02 p.8]

</details>

#### Q23. `creat`가 남아 있는 이유와 `open`·`creat`의 실패 처리 흐름은 무엇인가?

<details><summary>정답</summary>

강의는 `open`으로 생성 기능을 표현할 수 있어도 기존 프로그램과의 호환을 위해 `creat`가 남아 있다고 설명했다.

성공하면 fd, 실패하면 `-1`을 반환한다. 예제는 음수 반환값을 검사하고 `perror`로 오류를 보고한 뒤 실패로 종료한다. `errno`는 실패 이유와 연결된다. Read-only `open`과 Owner Read·Write Mode의 `creat`는 서로 다른 Code box다. [STT 85:54] [M02 p.8] [M02 p.9]

</details>

#### Q24. Double close가 단순한 오류 반환으로 끝나지 않을 수 있는 이유는 무엇인가?

<details><summary>정답</summary>

닫힌 fd 번호가 다른 `open`에 재사용되면 같은 숫자가 새 파일의 참조가 된다. 이전 값을 믿고 다시 `close`하면 그 새 참조를 닫을 수 있다.

`close`는 성공 시 0, 실패 시 `-1`을 반환한다. 이미 닫힌 숫자가 아직 비어 있는 경우와 다른 참조에 재사용된 경우를 구분해야 한다. 이번 강의는 이 위험을 설명한 뒤 종료된다. [STT 89:33] [STT 90:21] [M02 p.10]

</details>

### 기출 스타일 기반 예상·변형 문제

아래 문제는 모두 **이해를 위해 새로 만든 연습**이다. Q 문제로 개념을 회상한 뒤, 실제 기출의 요구 능력이 확인되는 경우에만 그 판단 구조를 적용한다. 원문 재현이나 출제 예측이 아니다. '관련 기출 근거 없음'은 제공 색인에서 해당 요구 구조를 확인하지 못했다는 뜻이며, 이 경우 강의 기반 일반 연습으로 구분한다. 부분 연결은 각 문제에 연결되는 판단과 추가 선수를 따로 명시한다.

#### 연습 P01

**새로 만든 연습 — Hard link와 Symbolic link의 참조 추적**

- **범위·학습목표:** LO04·LO05. Inode 공유, Target pathname, 이름 삭제 이후의 접근. [M01 p.15] [M01 p.18]
- **요구 능력·선수 개념:** 이름과 객체를 구분하고 상태 변화를 추적한다. Directory entry와 Inode가 선수 개념이며 **현재 접근 가능**하다.
- **스타일 근거:** 2024년 표기의 Q3(a)는 두 Link의 참조 방식 비교, 2025년 표기의 Q3(a)는 Hard link count와 Symbolic link의 차이를 요구한다. 이를 **Target 이름 삭제 후 같은 이름으로 다른 파일을 만드는 상황**으로 변형했다. [EX:sp_2024_2_midterm_q03 p.6] [EX:sp_2025_2_midterm_q03 p.7]

하나의 filesystem에 내용이 `OLD`인 Regular file `data`가 있다. 처음 Hard link count는 1이다. 다음 작업은 모두 성공하며, 다른 이름 변경이나 동시 작업은 없다.

1. `backup`을 `data`의 Hard link로 만든다.
2. `view`를 Target pathname이 `data`인 Symbolic link로 만든다.
3. `data`라는 이름을 삭제한다.
4. 같은 위치에 내용이 `NEW`인 새로운 Regular file `data`를 만든다.

3단계 직후와 4단계 직후에 `backup`과 `view`로 읽는 결과를 설명하라. 처음 파일의 Hard link count도 추적하라.

<details><summary>풀이와 채점 포인트</summary>

1. `backup` 생성으로 처음 Inode의 Hard link count는 2가 된다.
2. `view`는 별도 Inode에 pathname을 저장하므로 처음 Inode의 Hard link count를 늘리지 않는다.
3. `data` 삭제 후 처음 Inode의 count는 1이다. `backup`은 `OLD`를 읽지만, `view`는 Target 이름을 찾지 못해 접근에 실패한다.
4. 새 `data`는 처음 파일과 다른 객체다. `backup`은 여전히 `OLD`를 읽고, 일반적인 Symbolic link 따라가기로 `view`를 열면 새 `data`의 `NEW`를 읽는다.

**채점 포인트:** 같은 Inode 공유 1점, Symbolic link가 count를 늘리지 않는 이유 1점, 삭제 직후 결과 1점, 같은 pathname의 재생성이 기존 Hard link의 대상을 바꾸지 않는다는 설명 1점.

</details>

#### 연습 P02

**새로 만든 연습 — Directory 구조와 Hard link count**

- **범위·학습목표:** LO07. `.`·`..`과 직속 Subdirectory의 참조. [STT 30:24] [M01 p.21]
- **요구 능력·선수 개념:** 참조가 향하는 Directory를 세어 계산한다. Directory entry와 $2+N$ 모델이 선수 개념이며 **현재 접근 가능**하다.
- **스타일 근거:** 주어진 Directory 구조에서 count와 이유를 설명하는 요구를, 직속 자식·더 먼 후손·일반 파일을 구분하는 문제로 변형했다. [EX:sp_2025_2_midterm_q03 p.7]

강의의 전통적인 Directory 모델을 사용한다. `top`의 직속 Subdirectory는 `alpha`, `beta` 두 개이며, `alpha` 안에는 `child` 하나가 있다. `top`에는 일반 파일 하나와 `alpha`를 가리키는 Symbolic link도 있다.

`top`, `alpha`, `beta`의 Hard link count를 구하라. 이어 `top`에 직속 Subdirectory `gamma`를 추가하면 무엇이 달라지는가?

<details><summary>풀이와 채점 포인트</summary>

$$
L_{\mathrm{top}}=2+2=4,\qquad
L_{\mathrm{alpha}}=2+1=3,\qquad
L_{\mathrm{beta}}=2+0=2
$$

`child`의 `..`은 `alpha`를 가리키므로 `top`의 count에 직접 더하지 않는다. 일반 파일과 Symbolic link도 `top`의 Inode를 참조하는 직속 Subdirectory의 `..`을 추가하지 않는다.

`gamma`를 만들면 그 안의 `..`이 `top`을 가리켜 `top`의 count가 5가 된다. `alpha`와 `beta`의 count는 그대로다.

**채점 포인트:** 초기 세 값 2점, 직속 자식과 후손 구분 1점, `gamma` 추가에 따른 참조 설명 1점. 모든 filesystem에서 반드시 같은 수치가 나온다고 일반화하면 안 된다.

</details>

#### 연습 P03

**새로 만든 연습 — SUID와 Effective identity**

- **범위·학습목표:** LO12. SUID·SGID와 Real·Effective user/group. [STT 51:21] [M01 p.34] [M01 p.35]
- **요구 능력·선수 개념:** Permission bit가 바꾸는 identity를 구분하고 위험을 조건부로 설명한다. Owner·Group과 실행 Permission이 선수 개념이며 **현재 접근 가능**하다.
- **스타일 근거:** SUID의 권한 주체와 높은 권한으로 실행되는 프로그램의 위험을 설명하는 요구를, 두 Mode의 identity 비교로 변형했다. 특정 실제 프로그램의 설정 목록을 묻는 부분은 사용하지 않는다. [EX:sp_2025_2_midterm_q03 p.8]

독립적인 두 실행 모두, 실행 전 Process의 Real user와 Effective user는 A이고 Real group과 Effective group은 G라고 가정한다. 실행 파일의 Owner·Group은 B·H이며, B는 Root가 아니다. 실행 파일은 일반적인 실행 가능한 binary이고, 실행 Permission이 있으며 SUID·SGID 효과를 막는 조건은 없다고 가정한다.

독립적인 두 경우인 `4755`와 `6755`에서 실행 직후의 Real user/group과 Effective user/group을 비교하라. 이 프로그램에 취약성이 있다는 추가 조건이 생겨도 곧바로 Root 권한 획득이라고 단정할 수 없는 이유는 무엇인가?

<details><summary>풀이와 채점 포인트</summary>

| Mode | Real user | Real group | Effective user | Effective group |
|---|---|---|---|---|
| `4755` | A | G | B | G |
| `6755` | A | G | B | H |

`4755`는 SUID만, `6755`는 SUID와 SGID를 함께 설정한 경우다. Real 정보는 시작 주체를 유지한다.

취약한 프로그램이 다른 주체의 권한으로 실행되면 그 권한 범위에서 문제가 커질 수 있다. 그러나 이 조건의 Owner B는 Root가 아니므로 SUID의 존재만으로 Root 권한이라고 결론내릴 수 없다. 취약성의 존재와 실제 악용 가능성도 별도 판단이다.

**채점 포인트:** Real 정보 유지 1점, 두 Effective 조합 2점, 파일 Owner의 권한과 Root를 구분한 설명 1점.

</details>

#### 연습 P04

**새로 만든 연습 — `write`의 대상과 유효 길이**

- **범위·학습목표:** LO20. Standard output, Buffer, byte 길이. [STT 72:49] [M02 p.6] [M02 p.7]
- **요구 능력·선수 개념:** 표시할 문자 범위와 배열 저장 공간을 구분한다. C 문자 배열과 문자열 끝의 `\0`이 선수 개념이다. 이 연습은 **현재 접근 가능**, 원래 정수 변환 문항 전체는 **부분 연결**이다.
- **스타일 근거:** 정수를 문자열로 구성한 뒤 출력 대상과 길이를 선택하는 요구 중 마지막 I/O 판단을 사용한다. 정수 변환을 이미 끝낸 배열로 조건을 바꾸었다. [EX:sp_2024_2_midterm_q02 p.4] [EX:sp_2024_2_midterm_q02 p.5]

각 문자가 1 byte인 환경이고 Standard output이 정상적으로 열려 있다. 다음은 전체 프로그램이 아닌 인자 확인용 코드다.

```c
char buf[] = "-408\n";
ssize_t sent = write(/* 대상 */, buf, /* 길이 */);
```

`-408`과 줄바꿈만 보내도록 빈칸을 정하라. 배열의 저장 공간과 요청 출력량은 각각 몇 bytes인가? 호출이 요청한 전체 bytes를 성공적으로 보냈다고 추가 가정하면 `sent`는 얼마인가? 줄바꿈을 제외한 새 변형에서는 길이를 어떻게 바꾸는가?

<details><summary>풀이와 채점 포인트</summary>

```c
ssize_t sent = write(STDOUT_FILENO, buf, 5);
```

`-`, `4`, `0`, `8`, 줄바꿈이 출력할 5 bytes다. 배열에는 마지막 `\0`도 있으므로 저장 공간은 6 bytes다. 전체 전달 성공을 추가 가정했으므로 이 경우 `sent`는 5다.

줄바꿈 없이 `-408`만 보내는 변형의 길이는 4다. 일반적으로 요청량만으로 반환값을 확정하지는 않는다. 완전한 부분 전달·오류 처리 반복문은 이번 연습의 범위가 아니다.

**채점 포인트:** Standard output 선택 1점, 요청량 5와 저장 공간 6 구분 1점, 성공 가정과 반환값 구분 1점, 변형 길이 4 계산 1점.

</details>

#### 연습 P05

**새로 만든 연습 — Filesystem 관찰 결과의 해석**

- **범위·학습목표:** LO01·LO02·LO03·LO06·LO08. Mount, 시간 Metadata, Hidden name, FHS. [M01 p.12] [M01 p.13] [M01 p.14] [STT 17:13] [M01 p.20] [M01 p.24] [M01 p.25]
- **요구 능력·선수 개념:** 관찰한 사실과 그 사실만으로 결론낼 수 없는 내용을 구분한다. 기본 Directory와 Permission이 선수 개념이며 **현재 접근 가능**하다.
- **일반 연습 — 관련 기출 근거 없음**

다음은 서로 독립적인 관찰이다. 각 해석을 교정하고 필요한 확인 대상을 제시하라.

1. Mount 뒤 기존 파일이 보이지 않으므로 파일이 삭제되었다.
2. 파일을 성공적으로 읽었는데 `atime`이 그대로이므로 읽기는 실제로 수행되지 않았다.
3. 쓰기가 허용된 별도 파일에 내용을 덧붙여 크기가 바뀌었으므로 `mtime`만 바뀔 수 있다.
4. 이름이 `.config`이므로 다른 사용자의 접근은 자동으로 차단된다.
5. 실행 중인 Process 정보와 C Header는 같은 종류의 파일 정보이므로 같은 위치에서 찾으면 된다.

<details><summary>풀이와 채점 포인트</summary>

1. Mount에 의해 기존 내용이 가려졌을 수 있다. 연결된 filesystem과 Mount 전후의 관찰 대상을 확인한다.
2. `noatime`·`relatime` 같은 갱신 정책을 확인해야 한다. 시각이 그대로라는 사실만으로 성공한 읽기를 부정할 수 없다.
3. 내용과 함께 크기 같은 Metadata도 변하므로 `ctime`이 함께 갱신될 수 있다.
4. Hidden name은 표시 관례다. 접근 가능성은 실제 Permission 등의 조건을 확인해야 한다.
5. 자료에서 실행 중인 Process·Kernel 정보는 `/proc`, C Header는 `/usr/include`와 연결된다. 파일 인터페이스를 공유해도 정보의 성격과 배치가 같지는 않다.

```c

```

조회가 실패했을 때 무엇이 문제인가? 별도 문자열 복사를 하지 않고 `p->pw_name`만 보관한 뒤 `getpwuid`를 다시 호출하는 대안에는 어떤 문제가 있는가? 최소한 확인해야 할 수정 사항을 설명하라.

<details><summary>풀이와 채점 포인트</summary>

조회가 실패하면 `saved`에 값이 대입되지 않는다. 이후 조건식에서 초기화되지 않은 pointer를 읽는 것부터 안전하지 않으며 Undefined behavior로 이어질 수 있다. `"n/a"`라는 대체 문자열이 있다는 사실만으로 실패 경로가 안전해지지 않는다.

`saved`를 먼저 `NULL`로 초기화하고, 조회 실패와 `strdup` 실패를 각각 처리해야 한다. 성공적으로 복사한 문자열은 사용 후 `free`한다.

반면 `p->pw_name`의 pointer만 보관하면 다음 조회가 Static storage를 재사용할 수 있어 이전 이름이 독립적으로 보존되지 않는다. Static storage 자체를 `free`할 대상으로 바꾸어 생각해서도 안 된다.

open("audit", O_CREAT | O_WRONLY, S_IRWXU | S_IRGRP);

4. 아래 별도 `open` 호출이 실패한 경우를 처리하도록 빈칸을 채워라. 성공 반환값과 실패 표시, `errno`와 `perror`의 역할을 설명하라. `close`의 성공·실패 반환값은 `open`과 어떻게 다른가?

```c
int fd = open("audit", O_RDONLY);
if (/* 실패 조건 */) {
    /* 오류 보고 */
    /* 실패로 종료 */
}
/* 성공한 fd를 사용하는 다음 단계 */
```

<details><summary>풀이와 채점 포인트</summary>

1. `"audit"`는 Pathname이고, `O_CREAT | O_WRONLY`는 필요시 생성과 쓰기 접근을 요청한다. `S_IRWXU | S_IRGRP`는 새 파일에 요청하는 Owner `rwx`·Group `r--`·Other `---`, 즉 `0740`이다. 최종 Permission의 모든 생성 정책까지 이 인자로 확정하지 않는다. `O_RDONLY`는 Read-only 접근, 쓰기 접근에 함께 쓰는 `O_APPEND`는 Append를 지정하는 Flags이며 생성 Permission인 Mode와 다르다. 세부 Flag 조건은 Manual 참조 대상이다. 3. 강의는 `open`으로 생성 기능을 표현할 수 있어도 기존 프로그램과의 호환을 위해 `creat`가 남아 있다고 설명했다. 기능이 겹친다는 사실만으로 기존 인터페이스를 호환 고려 없이 제거할 근거가 되지는 않는다. [STT 85:54] [STT 86:49]
4. 실패 분기를 다음처럼 구성할 수 있다. 이 역시 전체 프로그램은 아니다.

```c
int fd = open("audit", O_RDONLY);
if (fd < 0) {
    perror("Cannot open audit");
    exit(EXIT_FAILURE);
}
/* 성공한 fd를 사용하는 다음 단계 */
```

`open`은 성공하면 음이 아닌 fd, 실패하면 `-1`을 반환한다. 반환값을 먼저 검사하고 실패 시 `errno`에 연결된 이유를 `perror`로 보고한 뒤 실패로 종료하므로, 유효한 fd를 얻었다고 가정한 다음 단계로 진행하지 않는다. 구체적인 오류 번호·문구는 주어지지 않았으므로 만들어 내지 않는다. `close`는 성공 시 0, 실패 시 `-1`이며 성공 시 fd를 반환하는 `open`과 구분한다. 성공만 가정한 추적 문제가 실제 코드에서 반환값 검사를 생략할 근거는 아니다. [STT 86:49] [STT 87:44] [M02 p.8] [M02 p.9] [M02 p.10]

#### 연습 P11

**새로 만든 연습 — fd 할당의 부분 기출 연결과 수명 추적**

- **범위·학습목표:** LO19·LO24. Current file position, 가장 작은 사용 가능한 fd, Double close. [M02 p.5] [M02 p.6] [M02 p.10] [STT 89:33] [STT 90:21]
- **요구 능력·선수 개념:** 열린 번호의 상태와 현재 위치를 추적한다. fd·실제 전달량·`open`·`close`가 선수 개념이며 **현재 접근 가능**하다. 원문 전체에는 `dup`의 동작이라는 **후속 선수**가 필요하다.
- **스타일 근거 — 부분 연결:** 2025년 1학기 표기 기말 Q1(b), PDF p.2는 `dup`을 포함한 순서 뒤 `open`의 반환 fd를 묻는다. 현재 연결하는 판단은 **가장 작은 사용 가능한 fd를 찾는 원리**다. 이를 A·B 파일의 닫기·재열기 순서로 변형했다. 아래 위치 계산과 Double close는 강의에서 도출한 일반 적용이며 해당 기출이 직접 묻는 항목은 아니다. [EX:sp_2025_1_final_q01 p.2]

한 Process에는 처음에 fd 0·1·2만 열려 있다. 명시된 작업 외의 fd 할당·닫기나 동시 작업은 없고, 표시한 열기·읽기·닫기는 모두 성공한다.

1. 위치를 가진 Regular file A를 열고 반환 fd를 변수에 보관한다. 시작 위치는 0이다.
2. 실제로 4 bytes를 읽는다.
3. A의 fd를 닫는다.
4. 다른 Regular file B를 연다.
5. 이전 변수의 숫자를 그대로 사용하여 다시 `close`한다.

각 단계에서 번호가 어떤 참조를 뜻하는지 추적하라. A를 열 때와 B를 열 때의 반환 fd, A의 읽기 직후 위치, 마지막 `close`의 대상을 구하고 이유를 설명하라.

<details><summary>풀이와 채점 포인트</summary>

A의 `open`은 가장 작은 사용 가능한 fd인 3을 반환한다. 실제로 4 bytes를 읽은 뒤 A의 위치는 $0+4=4$다. `close(3)` 이후 번호 3이 사용 가능해지고, 다음 B의 `open`이 3을 받는다. 마지막의 오래된 숫자를 이용한 `close(3)`은 B의 참조를 닫는다.

fd 숫자는 영구적인 파일 identity가 아니다. 위치 계산에는 요청량이 아니라 실제 전달량을 사용했다. 이 문제는 `dup`이나 공유 위치의 동작을 요구하지 않으며, 원문 전체를 현재 범위에서 해결한 것으로 보지 않는다. [M02 p.5] [M02 p.10] [STT 89:33] [STT 90:21]

**채점 포인트:** 최소 가용 번호에 따른 A·B의 fd 3 할당·재사용 1점, 실제 전달량에 따른 위치 4 계산 1점, 마지막 닫기의 대상 B와 참조 변경 이유 1점. 총 3점.

</details>
