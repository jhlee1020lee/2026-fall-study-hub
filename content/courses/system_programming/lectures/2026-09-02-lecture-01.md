### 1. System Programming의 목적과 C·Linux의 선택

<a id="sp01-explanations"></a>



이 과목은 operating system(운영체제) 내부를 직접 구현하는 수업이라기보다, OS가 application(응용 프로그램)에 제공하는 API(응용 프로그래밍 인터페이스)와 system call(시스템 호출)을 이용해 system-level software를 작성하는 방법을 배우는 수업이다. Operating Systems 과목이 kernel(커널) 내부에 초점을 둔다면 System Programming은 이미 존재하는 OS와 program이 만나는 외부 경계를 다룬다. [STT 05:21-06:06] [M04 slide 3]

수업 언어로 C를 선택한 이유는 C가 assembly language(어셈블리어)에 가깝고 pointer(포인터)를 통해 memory(메모리)를 byte(바이트) 단위로 다룰 수 있으며, OS가 제공하는 low-level API와 직접 연결되기 때문이다. Python이 쓸모없다는 뜻이 아니라, abstraction(추상화) 아래쪽을 관찰하기에는 C가 더 적합하다는 의미다. [STT 40:28-43:28] [M04 slide 28-31]

<a id="1-application에서-hardware까지"></a>

### 2. Application에서 hardware까지

첫 시간의 가장 중요한 기술적 구분은 library function(라이브러리 함수)과 system call이다. `printf()`는 library function이고, format string(서식 문자열)을 해석해 출력 문자열을 만든 뒤 최종적으로 `write()` system call을 호출한다. 실제 device에 접근할 권한은 OS에 있으므로 user-level code는 system call을 통해 OS의 서비스를 요청한다. 반면 `strlen()`이나 수학 함수처럼 OS 서비스 없이 user level에서 계산만으로 끝나는 library function도 있다. [STT 01:08:31-01:12:09] [M04 slide 49]

```text
application code
   ↓ library call: printf()
C runtime library
   ↓ system call: write()
operating system kernel
   ↓ privileged device access
display / file / terminal
```

`printf()` 자체가 화면 hardware를 직접 바꾸는 것은 아니다. library가 format을 처리하고 OS가 device 접근을 수행한다. `stdout`은 기본적으로 terminal에 연결되지만 redirection(재지정)을 사용하면 file로 연결될 수도 있다. 따라서 같은 `printf()` 호출도 standard output(표준 출력)의 연결 상태에 따라 다른 대상으로 출력된다. [STT 01:09:20-01:11:08]

Library function/system call 구분은 [2025-2 중간 Q3(d)](exam_questions/sp_2025_2_midterm_q03)의 I/O 성능 비교로 이어진다. 오늘은 두 층의 역할을 설명할 수 있어야 하고, 실행시간을 답하려면 이후에 buffering(버퍼링)과 system call 횟수를 추가로 배워야 한다. 함수 이름만 보고 항상 빠르다고 단정하거나, library 호출 한 번을 system call 한 번으로 세면 안 된다. 이 문항의 성능 결론은 출력 대상·buffering·실행 조건까지 검토하는 후속 복습으로 남긴다. [EX:sp_2025_2_midterm_q03 p.8](exam_questions/sp_2025_2_midterm_q03) [M04 slide 49]

**오개념 점검.** `printf()`를 system call이라고 바로 부르면 library가 수행하는 format 처리 단계를 놓친다.

### 3. C의 역사·설계와 structured programming(구조적 프로그래밍)

<a id="sp01-design"></a>

C는 BCPL·B를 거쳐 Unix의 OS와 도구를 작성하는 데 쓰였고, 강의는 C99를 기준으로 한다. 이 역사에서 남길 질문은 연도 암기보다 “assembly보다 추상적이면서도 machine-level 기능을 효율적으로 다룰 언어가 왜 필요했는가?”다. Efficiency over portability라는 설계 방향 때문에 같은 C 문장도 type 크기나 환경 의존 사항을 점검해야 한다. [M04 slide 45–48] [STT 01:01:37–01:05:04]

Structured programming(구조적 프로그래밍)은 기능을 function으로 나누어 세부 구현을 한 이름 뒤에 숨기고, 프로그램을 function들의 상호작용으로 읽는다. Object-oriented programming(객체 지향 프로그래밍)은 상태와 interface를 가진 object들의 상호작용으로 복잡도를 다룬다. 둘의 공통 목적은 큰 프로그램의 세부를 한꺼번에 기억하지 않고도 이해하는 것이다. [M04 slide 46] [M04 slide 50] [STT 01:00:51–01:01:37] [STT 01:13:59]

### 4. 작은 device와 cloud의 서로 다른 역할

현대 computer의 세 흐름은 작아지고 강력해지는 device, 생활 전반으로 퍼지는 device, 여러 server를 묶는 cloud 규모의 확대다. 작은 client와 큰 server 집합은 같은 서비스를 서로 다른 위치에서 담당할 수 있다. Datacenter 사진은 “한 프로그램의 array” 그림이 아니라 많은 machine이 들어가는 서비스 infrastructure를 보여준다. 강의에 제시된 특정 회사의 대수·투자액은 당시 슬라이드의 사례이며 C 언어의 보편적 성질이나 현재 수치로 사용하지 않는다. [M04 slide 36–43] [STT 47:03–54:41]

<a id="2-gcc800이-강제하는-compiler컴파일러-discipline"></a>

### 5. gcc800의 compiler(컴파일러) 검사와 실습 환경

강의의 `gcc800`은 별도의 compiler가 아니라 다음과 같은 option을 묶은 macro다. [M04 slide 49]

```bash
gcc -Wall -Werror -pedantic -std=c99 "$@"
```

- `-Wall`: 흔한 warning을 활성화한다.
- `-Werror`: warning을 error로 취급해 build를 멈춘다.
- `-pedantic`: GNU extension에 기대지 않고 표준 C 규칙을 엄격하게 검사한다.
- `-std=c99`: C99 표준을 기준으로 compile한다.

핵심은 “warning이 있어도 실행되면 된다”가 아니라, compiler가 제공하는 정보를 이용해 문제를 일찍 제거하는 습관을 만드는 것이다. local computer에서 동작하더라도 lab machine에서 compile·실행되지 않으면 채점할 수 없으므로 최종 test 환경을 동일하게 맞춰야 한다. [STT 20:32] [STT 01:12:29-01:13:18]

**오개념 점검.** `-Werror`는 warning을 없애 주는 option이 아니라 warning이 남은 build를 실패하게 한다.

<a id="3-type은-memory를-읽는-계약이다"></a>

### 6. Type(자료형)·memory(메모리)·address(주소)

이 강의는 x86-64, 64-bit OS를 가정한다. [M04 slide 51]

| 선언 | 의미 | 강의 가정에서의 크기 |
|---|---|---:|
| `char c` | character 또는 1-byte integer | 1 byte |
| `int x` | integer | 4 bytes |
| `long x` | long integer | 8 bytes |
| `float x` | single-precision floating point | 4 bytes |
| `double x` | double-precision floating point | 8 bytes |
| `void *p` | type이 아직 정해지지 않은 address(주소) | 8 bytes |

pointer가 담는 것은 대상 전체가 아니라 address다. `int *p`를 dereference(역참조)하면 그 address부터 `int` 크기만큼을 integer로 해석한다. `void *k`는 address만 보존할 뿐 해석할 type이 없으므로 `*k`는 유효한 값 표현이 되지 않는다. [STT 01:16:42-01:27:24]

보충(C 언어 규칙): `k`가 실제 `int` 객체를 가리킨다면 `int *p = k;`처럼 대입할 때 암시적으로 변환할 수 있고, `(int *)k`처럼 명시적으로 cast할 수도 있다. 중요한 것은 변환 후 type이 실제 객체에 맞는지다. [GNU C Reference: Void Pointers](https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Void-Pointers.html)

**오개념 점검.** `void *`는 “아무 값이나 저장하는 변수”가 아니라 아직 pointee type이 정해지지 않은 address를 담는다.

<a id="4-array와-pointer를-같다고-외우면-생기는-오류"></a>

### 7. Array(배열)·pointer(포인터)와 sizeof의 대상

```c
double pi[5][2];
int *p;
void *k;
```

`pi`가 expression에서 첫 element의 address처럼 변환되는 경우가 있어도, 선언된 type은 pointer가 아니라 `double[5][2]`다. 이 때문에 `sizeof(pi)`는 pointer 크기 8이 아니라 array 전체 크기 80을 반환한다. 반면 `sizeof(p)`와 `sizeof(k)`는 pointer 자체의 크기인 8이다. [STT 01:21:23-01:25:40]

C의 array(배열)와 pointer는 비슷하게 사용할 수 있는 순간이 있지만 같은 type(자료형)은 아니다. `double pi[5][2]`의 `sizeof(pi)`는 전체 array의 크기인 `5 × 2 × 8 = 80` bytes다. `void *`는 객체의 주소를 구체적인 pointee type(가리키는 대상의 자료형) 없이 보관한다. 값을 읽으려면 실제 객체에 맞는 pointer type으로 변환해야 한다. C에서는 적절한 pointer 변수에 대입하는 암시적 변환도 가능하므로 cast(명시적 형 변환)가 항상 필요한 것은 아니다. [STT 01:20:27-01:27:24] [M04 slide 52-53]

[2025-1 중간 Q1(a)](exam_questions/sp_2025_1_midterm_q01)는 여러 `sizeof` 표현에서 객체·pointee·string literal의 크기를 구분하도록 요구한다. 현재 1강의 array/pointer 구분이 바로 이 판단의 기초다. 풀이 순서는 **선언 type 확인 → 크기를 재는 대상 확인 → 강의 환경의 크기 대입**이다. 문자 수와 array storage 크기를 섞지 않고, string literal의 마지막 null character(널 문자)도 센다. [Q1(b)](exam_questions/sp_2025_1_midterm_q01)의 structure padding(구조체 패딩)과 [Q1(c)](exam_questions/sp_2025_1_midterm_q01)의 memory section(메모리 영역) 전체는 이후 개념이 필요하므로 같은 [Q1](exam_questions/sp_2025_1_midterm_q01)이라도 학습 범위를 구분한다. [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01) [M04 slide 51-54]

**오개념 점검.** array가 expression에서 address처럼 사용된다고 해서 array의 type 자체가 pointer로 바뀌는 것은 아니다.

<a id="5-string-literal과-writable-array"></a>

### 8. String literal(문자열 리터럴)과 writable array(수정 가능한 배열)

```c
char *a = "hello world";
char b[20] = "SNU CSE00800";

// a[0] = 'H';  // compile될 수 있지만 실행 중 실패할 수 있음
b[0] = 's';     // writable array element 변경
```

첫 선언은 `a`에 string literal의 시작 address를 넣는다. 둘째 선언은 20 bytes의 array를 확보하고 initializer의 문자를 array에 복사한다. “둘 다 문자열처럼 출력된다”는 사용상의 유사성이 “둘의 storage와 type이 같다”는 뜻은 아니다. [STT 01:32:05-01:35:40]

String(문자열)에서도 이 차이가 중요하다. `char *s = "hello world";`에서 `s`가 가리키는 string literal(문자열 리터럴)을 수정하면 C에서 undefined behavior(정의되지 않은 동작)가 발생한다. 일반적으로 read-only 영역에 놓여 program이 crash할 수 있지만, crash가 보장되는 것은 아니다. `char s[20] = "SNU CSE00800";`은 writable array(수정 가능한 배열)를 만들고 문자들을 복사해 초기화하므로 array element를 변경할 수 있다. [STT 01:29:10-01:35:40] [M04 slide 54]

#### 1. 기출 유형 변형: 같은 문자열처럼 보여도 같은 객체가 아니다

개념 학습용으로 새로 만든 예제이며 실제 과제의 작성·debugging을 대신하지 않는다. 강의의 x86-64 Linux 환경에서 object pointer 크기는 8 bytes라고 가정한다.

```c
char word[8] = "os";
const char *literal = "os";
char *alias = word;

alias[0] = 'O';
```

| 표현/객체 | 결과 또는 상태 | 판단 근거 |
|---|---|---|
| `sizeof(word)` | 8 | 선언된 array의 전체 storage |
| `sizeof(literal)` | 8, 강의 환경 가정 | 문자열 길이가 아닌 pointer 객체 크기 |
| `sizeof("os")` | 3 | 문자 2개와 마지막 null character |
| `sizeof(*alias)` | 1 | pointee type이 `char` |
| `word`가 담는 문자열 | `Os` | `alias`를 통해 같은 writable array 변경 |
| `literal`이 가리키는 문자열 | `os` | 별도의 string literal을 변경하지 않음 |

Array 크기·pointer 크기·문자열 길이는 서로 다른 질문이다. `sizeof`의 결과는 `size_t`이므로 C99에서 출력할 때는 `%zu`를 사용한다. 위 예제는 크기가 고정된 array이며 VLA에 대한 일반화는 하지 않는다. [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01) [M04 slide 52-54] [C99 보충 근거: N1256 §6.4.5, §6.5.3.4, §7.19.6.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)

**오개념 점검.** string literal 수정은 undefined behavior이며 compiler가 항상 막아 주는 오류가 아니다. runtime protection에 따른 crash는 가능한 결과 중 하나다.

### 9. Constants(상수)와 structure(구조체)

<a id="sp01-control"></a>

자료는 constants를 만드는 세 방법을 소개한다. Macro는 preprocessing에서 이름을 치환하고, `const int`는 수정할 수 없게 선언된 객체이며, `enum`은 이름 있는 정수 상수를 제공한다. 사용 목적이 비슷해도 이 세 문법의 모든 성질이 같다고 생각해서는 안 된다. Array는 같은 type의 원소를 모으고, structure는 서로 다른 type의 member를 함께 둘 수 있다. Structure의 전체 크기를 단순한 member 크기의 합이라고 단정하는 padding 계산은 아직 별도 학습 사항이다. [M04 slide 52] [M04 slide 54] [STT 01:18:40–01:19:34] [STT 01:36:25]

<a id="6-expression과-statement"></a>

### 10. Expression(식)·statement(문)와 control flow(제어 흐름)

대부분의 expression은 평가되어 value를 만들지만, `void` 반환 함수 호출처럼 값을 만들지 않는 expression도 있다. `2`, `2 + 3`, 값을 반환하는 function call뿐 아니라 assignment(대입)도 expression이다. `i = 10`은 memory를 바꾸는 side effect(부수 효과)를 수행하면서 동시에 value 10을 만든다. 그래서 assignment operator의 right associativity(우결합성)에 따라 다음 문장이 성립한다. [STT 01:37:21-01:40:08] [STT 01:42:07]

```c
i = j = 0;
```

먼저 `j = 0`이 평가되어 value 0을 만들고, 그 value가 `i`에 대입된다. statement는 실행 순서에 놓이는 command이며 보통 semicolon으로 끝난다.

Control flow에서 `while`은 본문 전에 조건을 확인하고 `do … while`은 본문을 실행한 후 확인하므로 처음 조건이 거짓이어도 후자는 한 번 실행한다. `for`는 초기화·조건·갱신을 함께 드러낸다. `continue`를 만나면 남은 본문을 건너뛰되 `for`의 갱신식은 실행하고 다음 조건을 검사한다. `break`는 가장 안쪽 loop 또는 switch를 빠져나온다. `goto`는 지정 label로 이동하며, 강의에서는 중첩 loop 탈출이나 공통 오류 처리의 맥락을 언급했다. Compound statement는 중괄호로 묶은 실행 단위다. [M04 slide 56–61] [STT 01:40:08–01:42:07]

### 11. Fahrenheit 예제와 readability(가독성)

M04 slide 62와 63은 같은 Fahrenheit–Celsius 계산을 불명확한 이름과 의미 있는 이름·comment로 대비한다. 계산은 $C=(5.0/9.0)(F-32.0)$이며 `lower=0`, `upper=300`, `step=20`으로 설정한 inclusive loop는 0과 300을 모두 포함해 16회 실행한다. Float 계산이 필요한데 `5/9`를 쓰면 integer division 결과 0으로 시작하는 오류가 생긴다. 이름을 잘 붙이는 일은 계산 결과를 바꾸지 않으면서 독자가 의도를 확인할 수 있게 한다. [M04 slide 62–63] [STT 01:43:03]

### 12. 선택 보충 · 주소 복사와 pointer 변수 참조

[2025-2 중간 Q1(b)](exam_questions/sp_2025_2_midterm_q01)는 pointer가 어느 객체를 가리키는지 문장마다 갱신하는 문제다. `q`가 pointer 변수 `p`의 주소를 갖는 경우, `p`가 바뀌면 `*q`로 읽는 주소도 바뀐다. 반대로 `r = p`는 그 순간의 주소 값을 복사하므로 나중에 `p`만 움직여도 `r`까지 움직이지는 않는다. 아래 추적 예제는 이 차이를 연습하는 보충이다. 다중 pointer의 상세한 연산은 다음 회차의 정식 학습과 다시 연결한다. [EX:sp_2025_2_midterm_q01 p.3](exam_questions/sp_2025_2_midterm_q01)

#### 2. 기출 유형 변형: 주소 값 복사와 pointer 변수 참조 추적

다음은 [2025-2 Q1(b)](exam_questions/sp_2025_2_midterm_q01)의 요구 능력을 연습하기 위해 새로 만든 보충 예제다. 아직 다중 pointer가 익숙하지 않으면 표를 보며 준비하고 이후 pointer 강의에서 다시 풀어본다. [EX:sp_2025_2_midterm_q01 p.3](exam_questions/sp_2025_2_midterm_q01)

```c
int a[3] = {3, 6, 9};
int *p = a;
int **q = &p;
++p;
**q += 2;
int *r = p;
++p;
*r += *p;
```

<details><summary>힌트</summary>

`q`는 array element가 아니라 pointer 변수 `p`를 가리킨다. `r`은 대입 당시 `p`의 주소 값을 보관한다. 각 문장을 끝낸 시점의 `p`, `r`, `a`를 따로 적는다.

</details>

<details><summary>풀이</summary>

| 문장 실행 직후 | `p`가 가리키는 원소 | `r`이 가리키는 원소 | `a` |
|---|---|---|---|
| 첫 `++p` | `a[1]` | 아직 선언 전 | `{3, 6, 9}` |
| `**q += 2` | `a[1]` | 아직 선언 전 | `{3, 8, 9}` |
| `r = p` | `a[1]` | `a[1]` | `{3, 8, 9}` |
| 둘째 `++p` | `a[2]` | `a[1]` | `{3, 8, 9}` |
| `*r += *p` | `a[2]` | `a[1]` | `{3, 17, 9}` |

모든 접근은 같은 array의 유효한 원소에 한정된다. `q`에 새 주소를 대입하지 않아도 `*q`가 읽는 것은 현재 `p`의 값이다. 반면 `r`은 마지막까지 `a[1]`을 가리킨다. 객체 관계와 문장별 상태를 대조한 풀이이며, 실제 C compiler 실행 결과라고 주장하지 않는다.

</details>

## 회상·연습문제

<a id="능동회상-문제"></a>

1. System Programming과 Operating Systems 과목의 초점 차이는 무엇인가?
<details><summary>정답</summary>

전자는 OS가 application에 제공하는 API와 system call을 이용하는 외부 경계에, 후자는 kernel 내부 구조와 구현에 더 초점을 둔다.

</details>

2. `printf()`와 `write()`는 각각 어느 층에 있는가?
<details><summary>정답</summary>

`printf()`는 C library function이고 `write()`는 OS가 제공하는 system call이다.

</details>

3. `double pi[5][2]`에서 `sizeof(pi)`가 80인 이유는 무엇인가?
<details><summary>정답</summary>

`pi`의 선언 type이 pointer가 아니라 double 10개로 이루어진 array이며 double 하나가 8 bytes이기 때문이다.

</details>

4. `void *k`를 곧바로 dereference할 수 없는 이유는 무엇인가?
<details><summary>정답</summary>

address에서 몇 bytes를 어떤 type으로 해석할지 정해지지 않았기 때문이다.

</details>

5. `char *s = "hello"`와 `char s[20] = "hello"`의 수정 가능성 차이를 설명하라.
<details><summary>정답</summary>

전자는 string literal을 가리키므로 문자를 수정하면 undefined behavior다. 후자는 writable character array를 초기화하므로 array element를 수정할 수 있다.

</details>

6. `i = j = 0`은 어떤 순서로 평가되는가?
<details><summary>정답</summary>

assignment가 right-associative이므로 `j = 0`이 먼저 평가되고 그 결과 0이 `i`에 대입된다.

</details>

7. `gcc800`에서 `-Wall`과 `-Werror`는 각각 어떤 역할을 하는가?
<details><summary>정답</summary>

`-Wall`은 흔한 문제에 대한 warning을 활성화하고, `-Werror`는 남아 있는 warning을 error로 취급해 build를 실패시킨다. 따라서 실행 파일이 만들어졌다는 사실만으로 코드를 판단하지 않고 compiler 진단을 먼저 해결하게 한다. [M04 slide 49]

</details>

8. `printf()`의 출력을 file로 redirect했을 때에도 library와 OS의 역할 구분은 유지되는가?
<details><summary>정답</summary>

유지된다. C library는 format을 처리하고, OS는 system call을 통해 실제 출력을 수행한다. 바뀌는 것은 standard output이 연결된 대상으로, terminal 대신 file에 연결되면 같은 `printf()` 호출의 결과가 file로 전달된다. [STT 01:09:20-01:11:08]

</details>

### 기출 연계 3단계 확인

9. **개념 확인:** `sizeof(word)`와 `sizeof(literal)`을 구하기 전에 각각 무엇의 type을 확인해야 하는가?
<details><summary>정답</summary>

`word`는 선언된 array의 type을, `literal`은 pointer 변수 자체의 type을 확인한다. pointer가 가리키는 문자열의 길이로 pointer 크기를 정하지 않는다. [M04 slide 52-54]

</details>

10. **기출 유형 적용:** [2025-1 Q1(a)](exam_questions/sp_2025_1_midterm_q01)의 유형에서 `sizeof("abc")`와 `char *p`의 `sizeof(p)`를 같은 방식으로 세면 왜 틀리는가? 문자열을 바꾼 연습 질문이며 원문 정답 복사가 아니다. [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01)
<details><summary>힌트</summary>

한쪽은 array이고 다른 쪽은 pointer 객체다.

</details>
<details><summary>정답</summary>

`"abc"`는 마지막 null character까지 포함한 `char[4]`이므로 크기가 4다. `p`는 pointer 객체이므로 강의 환경 가정에서 8이다. 문자열 길이가 바뀌어도 pointer 객체의 크기가 함께 바뀌지는 않는다.

</details>

11. **새 변형·보충:** 위 pointer 추적 예제에서 `int *r = p;`를 둘째 `++p` 뒤로 옮기면 마지막 array는 어떻게 달라지는가? [EX:sp_2025_2_midterm_q01 p.3](exam_questions/sp_2025_2_midterm_q01)
<details><summary>힌트</summary>

`r`에 복사되는 주소가 어느 시점의 `p`인지 확인한다.

</details>

<details><summary>정답</summary>

`**q += 2` 뒤 `a`는 `{3, 8, 9}`다. 둘째 `++p` 뒤에 대입하면 `r`과 `p`는 모두 `a[2]`를 가리킨다. 마지막 `*r += *p`는 같은 원소의 현재 값 9를 더하므로 `{3, 8, 18}`이 된다. 기존 예제와 대입 시점만 바뀌었으므로 주소 복사 시점이 핵심 차이다.

</details>

12. **오개념 점검:** 기출 해설에 string literal 수정 시 crash한다고 적혀 있다면, crash하지 않은 실행은 안전한 C program이라는 증거인가? [EX:sp_2025_1_midterm_q01 p.3](exam_questions/sp_2025_1_midterm_q01)
<details><summary>정답</summary>

아니다. String literal을 수정하는 것은 undefined behavior다. 특정 환경의 crash 관찰과 C의 보장은 다르다. 원문 답안을 일반 규칙으로 복사하지 않는다. [C99 N1256 §6.4.5](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)

</details>

### 기출 스타일 기반 예상·변형 문제

모두 **새로 만든 개념 연습**이다. 실제 기출·실제 assignment의 해결 코드·교수 예상문제가 아니며 출제 여부를 보장하지 않는다. 기출의 요구 능력만 참고하고 강의에 있었던 비기출 주제도 연습한다. 아래 해설·배점은 독립적으로 작성한 자기 점검 기준이다. 환경 크기는 명시한 가정 안에서만 사용하고 undefined behavior의 출력값은 확정하지 않는다.

#### 연습 P01 · Type, storage와 string의 차이

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

<a id="sp01-p1"></a>

**자체 제작 문제.** 실제 기출 또는 출제 보장 문항이 아니다.

범위: 현재 접근 가능. 강의의 `sizeof(int)=4`, object pointer 크기 8이라는 x86-64 Linux 가정을 사용한다. [M04 slide 51–54] 스타일 근거: [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01). 새 객체와 문자열을 사용한다.

`int readings[2][3] = {{1,2,3},{4,5,6}};`, `char label[7] = "cpu";`, `const char *text = "cpu";`가 있다. (a) 세 객체와 `"cpu"` 각각의 크기를 구하라. (b) `label[0]='C';` 뒤 문자열과 `sizeof(label)`을 답하라. (c) 별도의 `char *raw="cpu";`를 통해 `raw[0]='C';`를 실행하려 할 때 결과를 어떻게 분류해야 하는가? (d) 문자열 길이와 storage 크기가 다른 이유를 설명하라.

<details><summary>풀이·정답·채점 포인트 (10점)</summary>

`sizeof(readings)=2*3*4=24`, `sizeof(label)=7`, `sizeof(text)=8`, `sizeof("cpu")=4`다. 마지막 값은 문자 세 개와 null character를 포함한다.

`label`은 writable array이므로 문자열은 `Cpu`가 되고 storage는 여전히 7 bytes다. 초기 문자열 길이가 array capacity를 다시 정하지 않는다. `text`는 문자열을 담은 객체가 아니라 주소를 담은 pointer 객체다.

`raw[0]='C'`는 string literal 수정을 시도하므로 undefined behavior다. Crash 또는 특정 출력값을 정답으로 확정하지 않는다. `const char *`를 쓰는 이유는 이런 쓰기 시도를 type 수준에서 표현하지 못하게 하는 데 있다.

채점: 네 크기 4점, 수정 후 값·크기 2점, UB 분류와 crash 비보장 2점, 길이/객체 구분 2점.

</details>

#### 연습 P02 · Expression의 값과 loop의 상태 변화

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

<a id="sp01-p2"></a>

**자체 제작 문제.** 실제 기출 또는 출제 보장 문항이 아니다.

범위: 현재 접근 가능. [M04 slide 55–61] [STT 01:37:21–01:42:07] **일반 연습 — 관련 기출 근거 없음.** 제공 pointer 추적과 달리 이번 문제는 실제 첫 수업의 assignment·loop 규칙을 연습한다.

다음은 새로 만든 독립 코드 조각이다. 최종 `total`, `last`를 구하고 `continue`, `break`, assignment expression의 역할을 설명하라.

```c
int total = 0, last = -1;
for (int i = 0; i < 7; ++i) {
    if (i == 3) continue;
    if (i == 5) break;
    total += (last = i);
}
```

추가로 `int n=0;` 다음 `while(n<0){++n;}`와 `do{++n;}while(n<0);`를 각각 별도로 실행하면 어떤 차이가 있는가?

<details><summary>풀이·정답·채점 포인트 (10점)</summary>

합산한 `i`는 0,1,2,4다. `i=3`에서는 남은 본문을 건너뛰고 `++i`를 실행한다. `i=5`에서는 loop를 종료하여 assignment까지 도달하지 않는다. 따라서 `total=7`, `last=4`다.

`last=i`는 `last`를 바꾸는 side effect와 value `i`를 모두 갖는다. 그 value가 `total`에 더해진다. 서로 다른 객체를 순서대로 갱신하는 코드이며 같은 객체의 여러 unsequenced 변경을 넣지 않았다.

처음 조건이 거짓이므로 `while`의 본문은 0회이고 `n=0`이다. `do … while`은 먼저 한 번 실행하므로 `n=1`이다.

채점: 실제 합산 항·total 3점, last 1점, continue와 break 2점, expression의 값과 효과 2점, 두 loop의 차이 2점.

</details>

#### 연습 P03 · Library와 OS 경계를 설명하기

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

<a id="sp01-p3"></a>

**자체 제작 문제.** 실제 기출 또는 출제 보장 문항이 아니다.

범위: 현재의 층 구분은 접근 가능. I/O buffering 비용 계산은 후속 범위다. [M04 slide 49] [STT 01:08:31–01:12:09] 스타일 참고: I/O 방식을 이유와 함께 비교하는 [EX:sp_2025_2_midterm_q03 p.8](exam_questions/sp_2025_2_midterm_q03). 원문 성능 문제 대신 새 주장들을 분석한다.

한 프로그램이 `strlen("ab")`로 길이를 구하고, `printf("%d\n", 2)`로 출력한다. (a) 두 함수는 library function인가, system call인가? (b) format 해석과 실제 출력 대상 접근의 역할을 나누어 설명하라. (c) stdout이 terminal에서 file로 redirect되면 `printf`가 system call로 바뀌는가? (d) `printf` 두 번이면 `write`도 반드시 두 번이라고 할 수 있는가?

<details><summary>풀이·정답·채점 포인트 (8점)</summary>

둘 다 library function이다. 길이 계산은 user level에서 수행할 수 있고, `printf`는 format과 인자를 해석하는 library 역할을 맡는다. 실제 출력 서비스는 OS 경계와 이어지며 강의는 그 연결을 `write`로 설명한다.

Redirection은 stdout의 대상을 바꾸는 것이므로 함수의 층 분류는 바뀌지 않는다. Library 호출 수와 system call 수가 일대일이라고는 할 수 없다. 정확한 호출 시점·묶음·비용은 이후 buffering과 실행 조건을 확인해야 한다. 현재 수업의 층 구분만으로 실행시간이나 `write` 횟수를 만들어내지 않는다.

채점: 두 분류 2점, 두 역할 2점, redirection 2점, 호출 횟수의 조건 한계 2점.

</details>

#### 연습 P04 · C와 개발환경의 선택을 원인으로 설명하기

자체 제작 연습 · 공식 문항·정답·출제 예측이 아님.

<a id="sp01-p4"></a>

**자체 제작 문제.** 실제 기출 또는 출제 보장 문항이 아니다.

범위: 현재 접근 가능. [M04 slide 3,14–15,28–31,45–50] **일반 연습 — 관련 기출 근거 없음.** C 역사·설계·환경을 기출 빈도 때문에 생략하지 않기 위한 사례 문제다.

한 팀이 저수준 OS interface를 사용하는 프로그램을 만든다. 개발자는 “C는 assembly보다 높은 수준이므로 모든 machine에서 type 크기와 library가 같다”, “내 computer에서 실행됐으니 lab test는 필요 없다”, “함수로 나누면 큰 프로그램의 세부를 기억할 필요가 줄어든다”라고 말한다. 각 주장을 평가하고 C를 쓰는 이유·portability 한계·검증환경·structured programming을 연결해 네 문장으로 설명하라. 작은 client와 여러 cloud server가 함께 있는 서비스가 왜 모순된 구성이 아닌지도 답하라.

<details><summary>풀이·정답·채점 포인트 (10점)</summary>

첫 주장은 틀리다. C는 assembly를 상당 부분 대체하는 표현력을 제공하면서 machine-level 접근을 허용하지만, 그것이 모든 환경의 type 크기와 library까지 같다는 보장은 아니다. 강의의 64-bit Linux 수치는 그 환경 가정으로 읽는다.

둘째도 틀리다. Local coding 결과를 실제 채점 lab의 compiler·library·실행 환경에서 확인해야 한다. Compiler 경고와 실행 결과를 모두 확인하는 습관이 필요하다.

셋째는 설계의 목적에 맞다. 잘 정의한 function의 목적·interface를 통해 내부 세부를 추상화하고, 전체를 function 간 상호작용으로 이해할 수 있다. 이것이 모든 함수의 오류를 자동으로 없앤다는 뜻은 아니다.

Client는 사용자 가까이에서 입력·표시를 맡고 여러 server는 서비스를 제공할 수 있다. Device의 소형화와 server 규모의 확대는 서로 다른 위치와 역할을 설명하므로 동시에 나타날 수 있다.

채점: C의 이유/한계 3점, lab 검증 2점, function 추상화 3점, client/cloud 연결 2점.

</details>

Fahrenheit를 32부터 68까지 18씩 늘리며 $C=(5.0/9.0)(F-32.0)$을 계산한다. (a) 입력 값·출력 값·반복 횟수를 구하라. (b) `5.0/9.0`를 `5/9`로 바꾸면 무엇이 달라지는가? (c) `a,b,c,d,e` 대신 입력온도·출력온도·범위·간격을 드러낼 이름과 함수 목적 comment 한 줄을 제안하라.

<details><summary>풀이·정답·채점 포인트 (8점)</summary>

채점: 세 입력/출력과 횟수 3점, integer division 설명 2점, 역할별 명명 2점, 목적 comment 1점.
