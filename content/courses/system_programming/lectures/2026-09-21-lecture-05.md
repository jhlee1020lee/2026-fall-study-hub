이번 강의는 파일의 이름과 관리 정보를 조회하는 방법에서 출발해, 열린 파일의 상태를 공유하고 입출력 대상을 바꾸는 원리를 연결한다.  
읽기·쓰기 결과를 단계별로 추적하면서 Binary data(바이너리 데이터)를 줄이나 문자열로 해석할 때 생기는 문제까지 확인한다.

## 강의 내용과 설명

### File metadata와 inode: 파일에 관한 정보는 어디에 있는가

**File metadata(파일 메타데이터)**는 파일의 내용 자체가 아니라 그 파일의 성질을 설명하는 정보다. 자료에는 filename(파일 이름), file type(파일 유형), file size(파일 크기), 접근 권한, 내용과 상태가 바뀐 시각 등이 예로 제시된다. 강의는 지난 시간에 다룬 `struct stat`을 다시 보면서, 프로그램이 파일의 크기나 소유자 같은 정보를 어떻게 얻는지 복습한다. [STT 00:41] [M01 p.3] [M01 p.4]

이때 **inode(아이노드)**, filename, `struct stat`을 구별해야 한다. 자료의 파일시스템 모형에서 inode는 파일의 관리 정보를 담는 내부 단위이고, filename은 그 파일을 포함하는 **directory(디렉터리)**에 저장된다. `struct stat`은 프로그램이 관련 metadata를 조회했을 때 결과를 받는 C 구조체다. 따라서 `struct stat`을 파일 이름과 내부 저장 구조 전체를 그대로 담은 객체라고 생각하면 안 된다. [STT 01:48] [M01 p.4] [M01 p.5]

자료 p.5의 구조체는 필드 이름을 모두 외우기보다 **각 필드가 무엇을 세고 어떤 단위를 사용하는지** 읽어야 한다.

| 필드 | 의미 | 구별할 점 |
|---|---|---|
| `st_mode` | 파일 유형과 접근 권한 | 파일의 크기를 나타내는 값이 아니다. |
| `st_nlink` | hard links(하드 링크)의 수 | 뒤에서 배우는 열린 파일의 `refcnt`와 다르다. |
| `st_uid` | 소유자의 user ID | 파일을 현재 열어 둔 프로그램의 수가 아니다. |
| `st_gid` | 소유 group ID | 파일의 접근 권한 비트와 별도 정보다. |
| `st_size` | 파일 크기, byte 단위 | 할당된 저장 공간의 양과 구별한다. |
| `st_blksize` | 파일시스템 I/O에 권장되는 block 크기 | 파일에 할당된 block의 개수가 아니다. |
| `st_blocks` | 할당된 512-byte block의 수 | 값 자체의 단위는 byte가 아니라 block 개수다. |

[STT 00:41] [M01 p.5]

**이해를 위한 예시:** 어떤 조회 결과가 `st_size = 1000`, `st_blocks = 8`이라고 하자. 첫 값은 파일 크기가 1,000 byte라는 뜻이고, 두 번째 값이 나타내는 할당량은 다음과 같다.

$$
8 \times 512 = 4096\ \text{bytes}
$$

두 값이 다른 것은 서로 다른 양을 측정하기 때문이다. 이 예시는 특정 파일시스템의 할당 정책을 확정하기 위한 것이 아니라, `st_size`와 `st_blocks`의 의미와 단위를 분리하기 위한 것이다. 이번 도입부에서는 이 구별을 복습했으며, 자료 p.6의 세부 저장 방식까지 모두 새로 설명했다고 볼 근거는 없다. [STT 00:41] [M01 p.5]

`st_dev`, `st_ino`, `st_rdev`와 시각 관련 필드도 자료에 표시되어 있지만, 이번 녹음에서 각각을 상세히 설명한 것은 아니다. 특히 p.5의 `st_mtim` 주석은 access time으로 적혀 있으나, 같은 자료 p.7은 이를 파일 내용의 modification 시각과 연결한다. **노트의 자료 대조상 `st_mtim`을 access time으로 암기해서는 안 되며, p.5의 해당 주석은 표기 오류로 구별해야 한다.** 이는 잘못 들린 발화를 복원한 것이 아니다. [M01 p.5] [M01 p.7]

이 구별은 [[concepts/file-metadata|File metadata]]와 [[concepts/inode|inode]]를 연결하는 출발점이다. 흔한 오개념은 “파일에 관한 정보이므로 filename도 inode 안에 있어야 한다”는 것이다. 강의가 분리한 것은 **파일을 이름으로 찾는 관계**와 **찾은 파일의 성질을 관리하는 정보**다. [STT 01:48] [M01 p.4]

기출과는 부분적으로 연결된다. 2025년 2학기 중간 Q3(a–b)는 inode와 hard links, directory의 참조 관계를 설명하도록 요구한다. 이번 강의의 filename/inode 구별과 `st_nlink`는 그 출발점이지만, 구체적인 링크 생성 규칙과 directory 참조 수 계산까지 이번 복습만으로 모두 배웠다고 볼 수는 없다. 해당 문항에 접근할 때는 이름의 개수, inode의 링크 수, 열린 파일의 참조 수를 먼저 구분하고, 추가 링크 규칙을 확인해야 한다. [EX:sp_2025_2_midterm_q03 p.7]

### inode와 data 위치: 직접 가리키기와 다른 block을 거치기

파일의 크기와 소유자를 아는 것만으로 파일 내용을 읽을 수 있는 것은 아니다. 실제 data가 저장된 위치도 찾아야 한다. 강의는 filename의 저장 위치를 설명한 뒤, inode와 관련된 **pointer(포인터)**가 data 위치를 가리킨다는 이야기를 덧붙인다. 이 부분은 슬라이드에 상세한 그림이 없는 **STT 중심의 보충 설명**이다. [STT 02:19] [STT 02:32]

보존할 핵심은 두 가지 접근 관계다.

- 어떤 경우에는 pointer가 실제 data가 있는 block을 직접 가리킨다.
- 다른 경우에는 pointer가 중간 block을 가리키고, 그 block 안의 항목들이 실제 data 위치를 가리킨다.

중간 단계를 두면 하나의 관리 지점에서 더 많은 data 위치를 표현할 수 있다는 관계를 이해할 수 있다. 다만 녹음의 파일 크기 조건에는 서로 맞지 않는 표현이 남아 있고, 중간 대상을 지칭하는 말도 불명확하다. 따라서 특정 파일시스템의 정확한 pointer 개수나 단계 수를 여기서 확정하면 안 된다. [STT 02:32]

**이해를 위한 예시:** 종이에 직접 적힌 보관함 위치를 보고 물건을 찾는 경우와, 먼저 위치 목록이 있는 보관함을 열고 그 목록을 따라 물건을 찾는 경우를 생각할 수 있다. 이 비유는 접근 단계의 차이만 보여 준다. 실제 inode의 배치나 최대 파일 크기를 계산하는 모형은 아니다.

이 설명을 앞의 `struct stat`과 연결할 때도 주의가 필요하다. 파일 내부 관리에 data 위치 정보가 필요하다는 것과, 사용자에게 반환되는 `struct stat`에 그 pointer들이 모두 들어 있다는 것은 다른 주장이다. 자료의 `struct stat` 선언에는 그러한 pointer 배열이 제시되지 않는다. **구체적인 내부 배치, 크기 경계, 불명확한 중간 대상의 정확한 명칭은 검증 필요**로 남긴다. [M01 p.3] [STT 02:19] [STT 02:32]

### `stat` family: 어떤 파일의 metadata를 조회하는가

**`stat` family**는 조회하려는 파일을 지정하고 metadata를 받는 API 묶음이다. 같은 metadata 조회라도 프로그램이 가지고 있는 것이 pathname(경로명)인지, 이미 열린 **file descriptor(파일 서술자)**인지에 따라 적절한 함수가 달라진다. 또한 **symbolic link(심볼릭 링크)** 자체를 조사할지, 그것이 가리키는 대상을 조사할지도 구별해야 한다. [STT 03:00] [M01 p.8]

자료 p.8의 API 표는 반환 구조체보다 **파일을 지정하는 인자와 링크 처리의 차이**를 중심으로 읽으면 이해하기 쉽다.

| API | 파일을 지정하는 방식 | 이번 범위의 핵심 |
|---|---|---|
| `stat(pathname, &sb)` | pathname | 경로로 지정한 대상의 metadata를 조회한다. |
| `lstat(pathname, &sb)` | pathname | symbolic link를 따라가지 않는다는 차이가 있다. |
| `fstat(fd, &sb)` | 이미 열린 file descriptor | 경로 문자열 대신 열린 대상을 기준으로 조회한다. |
| `fstatat(dirfd, pathname, &sb, flags)` | directory descriptor와 pathname | 열린 directory를 기준으로 상대 이름을 다루는 데 유용하다. |
| `statx(dirfd, pathname, flags, mask, &sx)` | directory descriptor, pathname, 추가 선택 인자 | extended file status(확장 파일 상태)를 조회하는 API로 소개된다. |

[STT 03:00] [STT 04:54] [M01 p.8]

예를 들어 프로그램이 이미 파일을 열어 `fd`를 가지고 있다면, `fstat`은 그 열린 대상을 지정하는 방법이다. 반면 directory를 순회하며 얻은 이름을 조사하려면, directory descriptor와 그 이름을 결합하는 `fstatat`이 자연스럽다. 함수 선택은 단순히 이름이 비슷한 API를 외우는 문제가 아니라, **현재 확보한 참조가 무엇인지 판단하는 문제**다.

강의는 `fstatat`이 `stat`과 `lstat`의 기능을 포괄한다고 소개한다. 그러나 그것이 모든 호출에서 인자를 그대로 바꿔 끼워도 된다는 뜻은 아니다. `flags`라는 선택 인자가 존재하며, 이번 자료와 발화에서는 모든 설정과 대체 호출법을 상세히 전개하지 않았다. `statx`도 확장 정보를 얻는다는 소개까지만 확정하고, 개별 확장 필드를 이번에 배운 목록으로 추가하지 않는다. [STT 04:54] [M01 p.8]

흔한 오개념은 `fstat`을 “파일 이름을 더 빠르게 처리하는 `stat`” 정도로 생각하는 것이다. 핵심은 속도 비교가 아니라 **pathname을 다시 해석하는 방식과 이미 열린 descriptor를 사용하는 방식의 차이**다. 이 선택 관계를 [[concepts/stat-family|stat family]]와 [[concepts/file-descriptor|File descriptor]]의 연결로 이해한다.

### Relative pathname과 `fstatat`: 경로 해석의 기준을 명시하기

**Absolute path(절대 경로)**는 `/`에서 시작하는 경로이고, **relative path(상대 경로)**는 어떤 directory를 기준으로 해석하는 경로다. 강의에서는 `./`와 `../`로 시작하는 예를 든다. 다만 모든 relative path가 반드시 이 두 표기로 시작해야 하는 것은 아니다. 단순한 이름도 상대적으로 해석할 수 있다. [STT 03:59]

자료 p.9의 directory 그림은 들여쓰기와 가지의 연결을 읽는 연습에 적합하다. 그림에서 `a` 아래에 `b`가 있고, `b` 아래에는 `c`와 `f`가 있다. `d`는 `c` 아래에 있다. 따라서 `d`와 `f`는 같은 부모 아래의 항목이 아니다. 다른 가지에서는 `dir1` 아래에 `seventyfive`, `dir2` 아래에 `three`와 `seven`, `dir3` 아래에 `five`와 `twentytwo`가 배치된다. [M01 p.9]

**그림을 이용한 이해 예시:** 기준 directory가 그림의 `b`라면 `c/d`는 `c`를 거쳐 `d`로 내려가는 관계이고, `f`는 `b`의 바로 아래 항목이다. 여기서 이름 문자열만 보고는 충분하지 않다. **어디를 기준으로 그 이름을 해석하는지**가 함께 있어야 한다.

이것이 `fstatat`의 directory descriptor가 필요한 이유와 연결된다. 강의는 directory가 이동하는 등의 변화가 있으면, 먼저 metadata를 조회한 대상과 나중에 경로를 통해 접근하는 대상이 달라질 수 있다는 동기를 제시한다. Directory를 먼저 열고 그 descriptor를 상대 이름의 기준으로 사용하면, 프로그램이 의도한 기준을 명시할 수 있다. [STT 03:59] [STT 04:54]

```c
fstatat(dd, entry_name, &sb, 0);
```

이 호출에서 `dd`는 열린 directory의 descriptor이고, `entry_name`은 그 directory를 기준으로 조사할 이름이다. 뒤의 `statter.c`는 이 관계를 실제 directory 순회와 연결한다. [M01 p.11]

다만 “directory descriptor를 사용했으므로 모든 경로 경쟁 문제를 해결했다”는 결론은 성립하지 않는다. 이번 강의는 **기준 directory를 먼저 확보하는 동기와 사용 방식**을 소개한 것이다. 안전한 경로 접근을 위한 모든 조건과 완성된 구현은 제시되지 않았다. STT의 불명확한 지시어나 절대·상대 경로 전환 표현을 새로운 보안 규칙으로 확장하지 않는다. [[concepts/pathname|Pathname]]의 해석 기준과 [[concepts/stat-family|fstatat]]의 인자 관계까지만 분명하게 연결한다.

### `DIR*`와 directory API: 순회 객체와 descriptor를 구별하기

Directory 안의 항목을 하나씩 조사하려면, 현재 어디까지 읽었는지 관리하면서 다음 항목을 얻는 인터페이스가 필요하다. 자료는 이를 위해 `opendir`, `readdir`, `closedir`, `dirfd`, `mkdir`를 제시한다. [STT 05:42] [M01 p.10]

여기서 **`DIR*`는 C library가 관리하는 directory 순회 객체를 가리키는 포인터**다. 정수 file descriptor와 같은 값이 아니다. `opendir`로 directory를 열면 library 객체를 통해 순회를 진행할 수 있고, 그 아래의 descriptor가 필요할 때 `dirfd`를 사용한다. [STT 06:28]

| API | 받는 대상 | 역할 |
|---|---|---|
| `opendir(name)` | directory 이름 | 순회에 사용할 `DIR*`를 얻는다. |
| `readdir(dir)` | `DIR*` | 다음 directory entry(디렉터리 항목)를 얻는다. |
| `dirfd(dir)` | `DIR*` | 열린 directory의 정수 descriptor를 얻는다. |
| `closedir(dir)` | `DIR*` | directory 사용을 끝내고 관련 자원을 정리한다. |
| `mkdir(pathname, mode)` | pathname과 `mode` | directory를 생성한다. |

[M01 p.10]

`readdir`가 돌려주는 것은 `struct dirent*`이며, 예제는 여기서 `e->d_name`으로 항목의 이름을 사용한다. 이 이름을 얻는 단계와 그 항목의 metadata를 조회하는 단계는 별개다. 이름은 `readdir`, metadata는 `fstatat`을 통해 얻는 식으로 역할이 이어진다. [M01 p.11]

`closedir`는 `DIR*`를 더 이상 사용하지 않을 때 호출하며, 강의에서는 그 내부 descriptor도 닫힌다고 설명한다. 이 관계를 `fopen`과 `fclose`에 비유하지만, `DIR*`와 `FILE*`가 같은 종류의 객체라는 뜻은 아니다. 둘 다 library가 관리하는 객체를 사용한다는 공통점을 설명한 것이다. [STT 08:15]

**이해를 위한 예시:** 이미 열린 directory에서 항목 이름 하나를 얻었다고 하자. 그 이름의 파일 크기를 알고 싶다면 `DIR*`를 정수처럼 `fstat`에 넘기는 것이 아니라, `dirfd`로 얻은 descriptor와 항목 이름을 `fstatat`에 전달하는 관계를 생각해야 한다.

자료에는 관련 header인 `<dirent.h>`, `<sys/types.h>`가 표시되어 있고, `fdopendir`와 `mkdirat`도 변형 API로 나열된다. 그러나 이 변형들의 세부 동작을 이번 발화에서 모두 설명한 것으로 취급하지 않는다. 말미 p.24에서는 `opendir → readdir → dirfd → closedir`의 역할이 다시 정리된다. [M01 p.10] [M01 p.24]

### `statter.c`: 이름을 읽고, metadata를 조회하고, 오류를 구별하기

자료 p.11의 `statter.c`는 앞에서 배운 directory 순회와 metadata 조회를 결합한다. 출력 목표는 **각 directory entry의 이름과 `st_size`를 보여 주는 것**이다. 이 코드는 하나의 긴 프로그램으로 외우기보다, 열기·순회·조회·오류 판별·정리의 역할을 나누어 읽는 것이 좋다. [STT 07:25] [STT 08:15] [M01 p.11]

첫 단계는 조사할 directory를 선택하는 것이다.

```c
DIR *dir = opendir(argc > 1 ? argv[1] : ".");
```

첫 command-line argument(명령행 인자)가 있으면 `argv[1]`을 사용하고, 없으면 current directory(현재 디렉터리)를 뜻하는 `"."`을 사용한다. `opendir` 결과가 `NULL`이면 directory를 열지 못한 것이므로 오류를 출력하고 종료한다. “인자가 없으면 무엇을 여는가”는 STT의 끊긴 문장을 추측한 것이 아니라 표시된 코드로 확인하는 내용이다. [M01 p.11]

열기에 성공하면 `dirfd(dir)`로 `dd`를 얻고, `readdir(dir)`로 항목을 하나씩 가져온다. 각 항목에 대해서는 다음 관계가 핵심이다.

```c
struct stat sb;
int result = fstatat(dd, e->d_name, &sb, 0);
```

`dd`가 기준 directory를 지정하고, `e->d_name`이 그 안의 항목을 지정한다. 조회에 성공하면 이름과 `sb.st_size`를 출력한다. 어떤 항목의 조회가 실패하면 그 오류를 보고하지만, 표시된 코드는 바로 전체 순회를 중단하지 않고 다음 항목으로 진행한다. [STT 08:15] [M01 p.11]

**자료의 코드와 출력 창에서 함께 읽을 부분**은 다음과 같다.

| 코드의 단계 | 출력·동작에서 확인할 점 |
|---|---|
| directory 선택 | 인자가 있는 실행과 없는 실행의 기준이 다르다. |
| `readdir` | 출력 행은 directory entry를 순회한 결과다. |
| `fstatat` | 각 행의 크기는 해당 항목에 대한 metadata 조회 결과다. |
| `perror` | directory 열기, 개별 조회, 순회 오류를 구별해 보고한다. |
| `closedir` | 순회가 끝나면 열린 directory의 사용을 정리한다. |

[M01 p.11]

특히 `errno`의 사용은 단순 장식이 아니다. `readdir`의 `NULL` 반환을 보았을 때, 정상적으로 끝에 도달한 것인지 오류인지 구별해야 한다. 그런데 순회 본문에서 실행한 `fstatat` 등의 오류값이 남아 있으면, 그것을 마지막 `readdir`의 오류로 잘못 해석할 수 있다. 예제는 첫 `readdir` 전과 각 반복의 끝에서 `errno = 0`을 두고, 반복문이 끝난 뒤 값을 검사한다. [M01 p.11]

**이해를 위한 예시:** 중간 항목 하나의 `fstatat`이 실패하여 오류값이 생겼다고 하자. 이후 나머지 항목을 정상적으로 처리하고 순회가 끝났는데도 예전 오류값이 남아 있다면, directory 순회 자체가 실패했다고 오판할 수 있다. 예제의 초기화는 이런 오류의 출처를 섞지 않기 위한 흐름이다. 그렇다고 모든 함수가 성공할 때 자동으로 `errno`를 0으로 만든다는 뜻은 아니다.

자료의 출력에는 크기가 0인 항목도 있고, 4,096 등 다른 값도 있다. 이는 예제 실행에서 얻은 metadata이지 모든 directory의 고정 크기를 나타내는 표가 아니다. 또한 표시된 코드는 일부 오류를 보고한 뒤에도 마지막에 `EXIT_SUCCESS`를 반환한다. 따라서 **오류 메시지의 존재와 프로그램 전체의 종료 상태도 같은 것으로 취급하면 안 된다.** [M01 p.11]

### Descriptor table, open file table, v-node table의 역할

프로그램은 `read`나 `write`에 작은 정수를 넘기지만, **kernel(커널)**은 그 번호가 어느 열린 파일 상태에 연결되는지 알아야 한다. 자료 p.13은 이를 세 층으로 나누어 보여 준다. [STT 09:15] [STT 10:13] [M01 p.13]

| 층 | 자료에서의 범위 | 담당하는 정보 |
|---|---|---|
| **Descriptor table(서술자 테이블)** | process(프로세스)마다 하나 | 해당 process의 descriptor 번호와 열린 파일 항목의 연결 |
| **Open file table(열린 파일 테이블)** | 여러 process가 공유할 수 있음 | 열린 파일 항목별 file position과 reference count |
| **v-node table** | 자료에서는 모든 process가 공유하는 층으로 표현 | 파일의 메모리상 metadata: 접근 정보, 크기, 유형 등 |

[M01 p.13]

**File position(파일 위치)**은 그 열린 파일을 어디까지 읽거나 썼는지 나타내는 상태이고, **reference count(참조 수)**는 자료의 모형에서 해당 열린 파일 항목을 참조하는 연결의 수를 나타낸다. 그림의 `File pos`와 `refcnt`는 가운데 open file table 항목에 들어 있다. 오른쪽 v-node에는 file size와 file type이 들어 있다. [STT 11:13] [M01 p.13]

**그림 p.13을 읽는 순서**는 왼쪽 번호에서 출발해 화살표를 따라가는 것이다. 예시의 descriptor 1은 terminal(터미널) 쪽 열린 파일 항목으로, descriptor 4는 disk file 쪽 항목으로 이어진다. 프로그램은 번호 1이나 4를 사용하지만, 대상과 현재 위치의 의미는 그 뒤의 연결에서 결정된다.

그림에는 다음 standard I/O(표준 입출력) 번호도 표시되어 있다.

| 이름 | descriptor 번호 |
|---|---:|
| standard input(표준 입력), `stdin` | 0 |
| standard output(표준 출력), `stdout` | 1 |
| standard error(표준 오류), `stderr` | 2 |

[M01 p.13]

이 구분은 앞의 `st_nlink`와 `refcnt`를 혼동하지 않게 해 준다. `st_nlink`는 파일의 hard links에 관한 metadata이고, 그림의 `refcnt`는 **열린 파일 항목을 공유하는 관계**를 나타낸다. 파일의 이름을 새로 만드는 일과 이미 열린 파일 항목에 descriptor를 하나 더 연결하는 일은 다르다.

STT에는 open file table도 process마다 하나라는 표현이 남아 있지만, 이는 p.13의 도식과 충돌한다. **노트에서는 확인 가능한 도식에 따라 descriptor table과 공유 가능한 open file table을 구별한다.** 충돌한 발화가 정확히 무엇이었는지는 검증 필요이며, 이를 올바른 문장으로 복원했다고 주장하지 않는다. [STT 10:13] [M01 p.13]

강의는 socket, socket pair, pipe도 descriptor와 관련된 대상으로 짧게 언급한다. 이 언급은 descriptor가 일반 disk file에만 쓰이는 개념이 아니라는 배경을 제공하지만, 각각의 생성·통신 절차까지 이번에 배운 것은 아니다. [[concepts/file-descriptor|File descriptor]]에서 [[concepts/open-file-table|Open file table]]로 이어지는 관계를 먼저 확실히 이해해야 한다. [STT 09:15]

### File descriptor passing과 `fork`: process가 달라도 열린 상태를 공유할 수 있다

**File descriptor passing(파일 서술자 전달)**은 다른 process가 같은 열린 파일 항목을 참조하도록 연결하는 것이다. 여기서 중요한 것은 정수 하나의 전달과 열린 파일의 공유가 다르다는 점이다. [STT 11:13] [STT 12:11]

각 process에는 자기 descriptor table이 있다. 따라서 한 process에서 유효한 숫자를 다른 process에 알려 주는 것만으로, 상대가 같은 파일을 열어 둔 상태가 되지는 않는다. 공유가 성립하려면 수신 process의 descriptor도 **같은 open file table 항목**으로 연결되어야 한다. 강의는 이때 해당 항목의 reference count가 증가한다고 설명한다. [STT 12:11]

**이해를 위한 예시:** process A의 descriptor 5가 어떤 항목을 가리킨다고 하자. process B에게 숫자 `5`를 메시지 내용으로 전달하는 것과, B의 descriptor가 A와 같은 항목을 참조하도록 만드는 것은 별개의 일이다. B에서 할당된 번호가 우연히 5일 수도 있고 다른 번호일 수도 있다. 공유의 기준은 숫자의 동일성이 아니라 연결 대상의 동일성이다.

STT에서 전달·수신 함수를 지칭하는 표현은 정확한 API 이름으로 확인되지 않는다. 따라서 특정 socket 함수나 전달 구조체를 이 강의의 구현으로 덧붙이지 않는다. 이번 범위는 **번호가 process마다 의미를 갖는다는 점과, 공유가 kernel의 연결 관계라는 점**이다.

`fork`도 같은 항목을 여러 process가 참조하게 되는 상황으로 소개된다. 강의에서는 자신의 process를 복제하여 **parent process(부모 프로세스)**와 **child process(자식 프로세스)**가 생기고, 이후 각자 실행한다고 설명한다. `fork`의 결과에 따라 조건문으로 다른 작업을 선택할 수 있다는 입문적 설명도 있다. [STT 12:11] [STT 13:09]

열려 있던 descriptor의 상태는 child에 이어지지만, 두 process가 descriptor table 하나를 통째로 공동 소유한다고 이해해서는 안 된다. 각자의 table에서 **상속된 descriptor들이 같은 open file table 항목을 참조하는 관계**가 핵심이다. 따라서 열린 파일 항목의 상태를 공유하고 reference count가 증가할 수 있다. [STT 13:09] [M01 p.13]

Memory가 개념적으로 복사된다는 설명도 나오지만, 실제 메모리 복제 방식, 정확한 반환값, 실행 순서와 종료 처리는 이후 학습 범위다. 이번의 공유 설명만으로 parent와 child의 출력 순서를 확정할 수는 없다.

### 같은 파일을 두 번 `open`하는 것과 `dup`하는 것은 다르다

**같은 파일을 참조한다는 사실만으로 file position까지 공유하는 것은 아니다.** 이 차이를 보여 주는 것이 자료 p.14와 p.17의 대비다. [STT 14:07] [STT 15:08]

p.14에서는 같은 filename으로 `open`을 두 번 호출한다. 왼쪽의 두 descriptor는 **서로 다른 open file table 항목**으로 연결되고, 그 두 항목이 오른쪽의 동일한 v-node로 이어진다. 각 열린 항목에는 자기 file position이 있고, 그림의 `refcnt`는 각각 1이다. [M01 p.14]

반면 `dup(oldfd)`는 기존 descriptor와 같은 항목을 참조하는 새 descriptor를 만든다. 새 항목에 현재 위치를 복사해 놓는 동작이 아니라, **같은 항목에 연결을 하나 더 만드는 동작**이다. 따라서 이후 한쪽에서 위치가 바뀌면 다른 쪽에서도 같은 위치 상태를 사용한다. [M01 p.16] [M01 p.17]

| 비교 | 같은 파일을 `open` 두 번 | `open` 후 `dup` |
|---|---|---|
| descriptor | 서로 다른 번호 | 서로 다른 번호 |
| open file table 항목 | 별개 | 동일 |
| file position | 각각 독립 | 공유 |
| 자료의 reference count | 두 항목이 각각 1 | 한 항목이 1에서 2로 증가 |
| 파일 내용·metadata의 대상 | 같은 파일일 수 있음 | 같은 파일 |

[M01 p.14] [M01 p.17]

**그림 p.17에서 특히 볼 부분**은 아래쪽의 두 화살표다. 새 descriptor가 생긴 뒤에도 가운데 열린 파일 항목은 하나이며, 그 안의 `refcnt`가 2가 된다. p.14에서 가운데 상자가 두 개였던 것과 비교하면, “파일 공유”라는 말이 서로 다른 층의 공유를 가리킬 수 있음을 알 수 있다.

**이해를 위한 예시:** 내용이 `WXYZ`인 파일을 별도로 두 번 열고 각각 한 byte씩 읽으면, 두 항목은 각자의 시작 위치에서 읽을 수 있다. 반대로 한 번 연 descriptor를 `dup`한 뒤 두 descriptor로 차례로 읽으면, 첫 읽기가 공유 위치를 전진시키므로 두 번째 읽기는 다음 byte를 대상으로 한다. 모든 열기와 읽기가 성공하며, 중간에 다른 읽기나 위치 변경이 없다는 조건의 예시다.

`dup`가 반환하는 번호는 **사용하지 않는 descriptor 중 가장 작은 번호**다. p.17은 0·1·2가 사용 중인 상태에서 `open`이 3을 얻고, `dup`가 4를 얻는 그림이다. 변수 이름 `fd2`의 값이 4라는 뜻이지, `fd2`가 숫자 descriptor 2라는 뜻은 아니다. [STT 20:11] [STT 22:11] [M01 p.17]

2025년 1학기 기말 Q1(b)는 `close`, `dup`, `open`을 차례로 실행한 뒤 반환되는 번호를 판단하게 한다. **현재 접근 가능한 연결**은 이 번호 할당 부분이다. 풀이에서는 사용 중인 번호와 빈 번호를 호출마다 갱신한 뒤, 다음 호출이 선택할 가장 작은 빈 번호를 찾는다. 변수 이름에 붙은 숫자나 직전 반환값에 1을 더하는 방식으로 추측하면 안 된다. 같은 Q1의 process 상태나 `exec` 관련 소문항까지 이번 강의 범위로 확대하지 않는다. [EX:sp_2025_1_final_q01 p.2]

자료 p.16의 `fileno(FILE *stream)`는 stream에 대응하는 descriptor를 얻는 항목이다. `dup`처럼 descriptor를 새로 복제하는 역할과 구별한다. `dup3`는 강의에서 계열의 이름으로 언급되었지만 세부 옵션은 이번 범위에 포함하지 않는다. [STT 15:08] [M01 p.16]

### I/O redirection과 `dup2`: 번호를 유지하면서 연결 대상을 바꾸기

**I/O redirection(입출력 재지정)**은 프로그램이 사용하는 standard I/O의 연결 대상을 바꾸는 것이다. 프로그램이 descriptor 1로 출력한다는 코드를 유지해도, 그 번호가 terminal 대신 파일 쪽 열린 항목을 가리키도록 만들 수 있다. [STT 16:06] [STT 17:56]

자료 p.15의 shell(셸) 예시는 연결 방향을 보여 준다.

```sh
ls > output.txt
ls | sort -R
cat < input.txt
```

- `>`는 `ls`의 standard output을 파일에 연결한다.
- `|`는 앞 프로그램의 출력을 다음 프로그램의 standard input으로 연결한다.
- `<`는 파일 내용을 `cat`의 standard input으로 공급한다.

여기서 **piping(파이프로 연결하기)**의 핵심은 한 process의 출력과 다른 process의 입력 사이의 연결이다. `sort`의 옵션 의미나 완성된 pipeline 실행 절차는 이번 설명의 핵심으로 추가하지 않는다. [STT 17:04] [M01 p.15]

지정한 번호의 연결을 바꾸는 API가 `dup2(oldfd, newfd)`다. 성공하면 `newfd`가 `oldfd`와 같은 open file table 항목을 참조하게 된다. 이미 다른 대상을 참조하던 `newfd`라면 그 기존 연결을 교체한다. **인자 방향은 기존 대상을 제공하는 쪽이 `oldfd`, 연결을 바꿀 번호가 `newfd`다.** [STT 21:11] [M01 p.16]

자료 p.18의 핵심 코드는 다음 두 줄이다.

```c
fd = open("output.txt", O_WRONLY, 0);
dup2(fd, STDOUT_FILENO);
```

이 자료 예시는 파일 열기와 복제가 성공한다고 놓고 연결을 설명한다. `O_WRONLY`는 쓰기용 열기를 나타낸다. 표시된 코드에는 파일 생성이나 기존 내용 제거를 위한 flag가 없으므로, 이 두 줄이 항상 새 파일을 만들거나 파일을 비운다고 설명해서는 안 된다. [M01 p.18]

**그림 p.18을 읽으면** `dup2` 전에는 descriptor 1과 `fd`가 다른 곳을 향한다. 호출 후에는 descriptor 1의 화살표가 `fd`와 같은 열린 항목으로 향하고, 그 항목의 `refcnt`가 2가 된다. 이후 프로그램이 `write(1, ...)`을 호출하면 첫 인자는 여전히 1이지만, 출력 대상은 새로 연결된 파일이다. **숫자 1이 숫자 3으로 바뀌는 것이 아니라, 번호 1이 가리키는 대상이 바뀐다.** [M01 p.18]

자료의 상황처럼 `fd`가 3이고, 복제 후 그 번호를 더 이상 사용할 필요가 없다면 3을 닫을 수 있다. 1의 연결이 남아 있으므로 파일을 계속 사용할 수 있다. 단, 이 설명은 두 번호가 서로 다른 그림의 상황을 전제로 한다. [STT 18:53] [STT 21:11]

강의는 `dup2` 대신 **빈 번호를 이용하는 방식**도 설명한다. 0·1·2와 파일을 가리키는 3이 열린 상태에서 1을 닫으면, 1이 가장 작은 빈 번호가 된다. 그 직후 다른 descriptor 할당이 끼어들지 않는 예시에서 `dup(3)`을 호출하면 반환값은 1이다. 이로써 1과 3이 같은 열린 항목을 가리키게 된다. [STT 18:53] [STT 20:11]

이는 lowest-unused-FD 규칙이 왜 유용한지 보여 준다. 강의자는 이 설명을 프로젝트의 번호 할당 제약과 연결한다. 다만 `dup2`·`dup3`의 도입 시점에 관한 이야기는 강의자의 역사 설명이며, 제공 자료로 연대기를 독립 확인한 사실로 취급하지 않는다. 앞부분에서 `dup`의 인자가 없다는 말은 뒤에서 **한 인자를 받는다고 명시적으로 정정된다.** [STT 20:11]

2024년 2학기 중간 Q3(c)도 descriptor를 닫고 복제한 뒤 출력 대상을 설명하는 구조다. 이번 강의와 직접 연결되는 판단은 **빈 번호의 재사용과 standard output의 재연결**이다. 접근할 때는 먼저 descriptor 연결을 완성한 뒤 출력 함수를 살펴본다. `printf`가 있다는 이유로 terminal 출력이라고 단정하거나, 재지정 후의 출력을 standard output 자체가 아닌 별개 통로라고 생각하면 안 된다. 다만 stream의 buffering과 실제 출력 시점은 추가로 구별해야 한다. [EX:sp_2024_2_midterm_q03 p.6]

STT에는 standard output을 0으로 지칭하거나, p.18의 파일을 읽기용으로 연다고 말하거나, 교체 대상을 standard input이라고 부르는 부분이 있다. **여기서의 정확한 번호와 방향은 p.13·p.18의 코드와 도식에 근거한다.** 불명확한 발화 자체는 검증 필요로 남긴다.

### `fwfd1.c`: 세 번의 `open` 뒤 두 descriptor만 위치를 공유한다

자료 p.19는 내용이 `System Programming`인 파일을 세 번 연 뒤, `dup2(fd2, fd3)`을 수행하는 예제다. 코드의 인자 경로는 `argv[1]`에서 받고, 세 번의 `open` 실패 여부를 검사한다. 다음은 분석에 필요한 핵심 부분이다. [STT 23:11] [M01 p.19]

```c
fd1 = open(fname, O_RDONLY, 0);
fd2 = open(fname, O_RDONLY, 0);
fd3 = open(fname, O_RDONLY, 0);

dup2(fd2, fd3);

read(fd1, &c1, 1);
read(fd2, &c2, 1);
read(fd3, &c3, 1);
```

이 예제를 풀 때는 `fd1`, `fd2`, `fd3`를 숫자 1·2·3으로 읽지 않는다. 이들은 반환된 descriptor를 저장하는 **변수 이름**이다.

처음 세 번의 `open`은 각각 별도의 열린 항목을 만든다. 설명을 위해 그 항목을 A, B, C라고 부르자. 처음에는 `fd1 → A`, `fd2 → B`, `fd3 → C`이고, 각 position은 0이다. `dup2(fd2, fd3)` 이후에는 `fd3`가 기존 C 대신 B를 참조한다. A와 B의 position은 여전히 서로 독립이다. [STT 24:11] [M01 p.19]

| 단계 | 참조하는 항목 | 읽기 전 position | 얻는 byte | 읽기 후 position |
|---|---|---:|---|---:|
| `read(fd1, &c1, 1)` | A | 0 | `S` | A = 1 |
| `read(fd2, &c2, 1)` | B | 0 | `S` | B = 1 |
| `read(fd3, &c3, 1)` | B | 1 | `y` | B = 2 |

[M01 p.19]

첫 번째 읽기가 A의 위치를 바꿔도 B에는 영향을 주지 않는다. 그래서 두 번째 읽기 역시 `S`를 얻는다. 반면 두 번째와 세 번째 읽기는 B를 공유하므로, 세 번째 읽기는 그다음 byte인 `y`를 얻는다. 결과는 `c1 = S`, `c2 = S`, `c3 = y`다. [STT 25:10] [M01 p.19]

핵심 오개념은 두 가지다. 첫째, 같은 filename이므로 처음부터 position도 하나라고 생각하는 것이다. 둘째, `dup2`가 현재 position의 숫자만 별도 항목에 복사한다고 생각하는 것이다. 실제 자료의 모형은 **열린 항목 자체를 공유하는 관계**이며, 이후 읽기의 위치 변화도 함께 보인다.

이 계산은 모든 관련 호출이 성공하고 각 `read`가 한 byte를 읽는다는 예제 조건에 따른다. 표시된 코드가 모든 읽기 실패나 자원 정리를 완비한 프로그램이라고 보지는 않는다. 또한 `y`는 슬라이드의 코드와 출력으로 확인되는 결과이며, 불명확한 STT에 새로 복원한 발화가 아니다.

### `fwfd2.c`: `O_APPEND`와 공유 position을 따로 추적하기

자료 p.20은 파일 내용이 바뀌는 위치와 열린 항목의 position을 함께 추적하게 한다. 여기서 **append(끝에 덧붙이기)**는 기존 파일의 끝에서 쓰는 동작이며, `O_APPEND`를 사용한 열린 항목과 일반적인 쓰기 위치를 사용하는 항목을 구분해야 한다. [STT 25:37] [M01 p.20]

다음 코드는 자료의 알고리즘을 읽기 쉽게 옮긴 핵심 부분이다. 문자열 앞의 추출 공백을 제거하고 C 코드에 맞는 보통 따옴표를 사용했다. `fname`과 descriptor 변수는 준비되어 있고, 모든 호출이 성공하며 각 `write`는 요청한 byte 수를 전부 쓴다고 가정한다.

```c
fd1 = open(fname, O_CREAT | O_TRUNC | O_RDWR,
           S_IRUSR | S_IWUSR);
write(fd1, "CSAP", 4);

fd3 = open(fname, O_APPEND | O_WRONLY, 0);
write(fd3, "M1522", 5);

fd2 = dup(fd1);
write(fd2, "SNU", 3);
write(fd3, "800", 3);
```

[M01 p.20]

처음 열기의 `O_CREAT`는 필요하면 파일을 생성하는 선택이고, `O_TRUNC`는 기존 파일을 이 예제의 빈 상태로 시작하게 한다. `O_RDWR`는 읽기와 쓰기가 가능한 열기이며, 생성 시 사용할 소유자 읽기·쓰기 권한으로 `S_IRUSR | S_IWUSR`가 전달된다. 이후 `fd3`는 **별도의 `open`**으로 얻으며 `O_APPEND | O_WRONLY`를 사용한다. [M01 p.20]

`fd1`의 열린 항목을 A, `fd3`의 열린 항목을 B라고 하자. `fd2 = dup(fd1)` 이후 `fd2`도 A를 참조한다.

| 단계 | 파일 내용 | A의 position: `fd1`·`fd2` | B의 position: `fd3` | 파일 크기 |
|---|---|---:|---:|---:|
| 처음 열기 | 빈 내용 | 0 | 아직 없음 | 0 |
| `CSAP` 4 byte 쓰기 | `CSAP` | 4 | 아직 없음 | 4 |
| B에서 `M1522` 덧붙이기 | `CSAPM1522` | 4 | 9 | 9 |
| `fd2 = dup(fd1)` | `CSAPM1522` | 공유 위치 4 | 9 | 9 |
| `fd2`로 `SNU` 쓰기 | `CSAPSNU22` | 7 | 9 | 9 |
| B에서 `800` 덧붙이기 | `CSAPSNU22800` | 7 | 12 | 12 |

[M01 p.20]

가장 중요한 순간은 `M1522`를 쓴 직후다. 파일 크기는 9가 되었지만, **별도 항목 A의 position은 여전히 4**다. 파일 크기가 커졌다는 사실이 모든 열린 항목의 position을 끝으로 이동시키지는 않는다. [STT 26:36] [M01 p.20]

따라서 A를 공유하는 `fd2`가 `SNU` 세 byte를 쓰면, position 4부터 있던 `M15`를 덮는다.

```text
position: 0 1 2 3 4 5 6 7 8
쓰기 전:  C S A P M 1 5 2 2
쓰기 후:  C S A P S N U 2 2
```

세 byte만 썼으므로 뒤의 `22`는 남는다. 기존 내용 가운데 일부를 덮는 쓰기가 파일 전체를 새 문자열의 길이로 자르는 것은 아니다. 이어 B를 사용하는 `fd3`의 쓰기는 당시 파일의 끝에 `800`을 붙여, 최종적으로 `CSAPSNU22800`을 만든다. [STT 27:28] [STT 27:47] [M01 p.20]

`O_APPEND`는 “처음 열 때만 위치를 끝으로 옮긴다”는 의미로 축소해서도 안 되고, “같은 파일의 다른 열린 항목도 모두 append 상태가 된다”는 의미로 확대해서도 안 된다. 이 예제에서는 append용 B와 position 4를 유지하던 A를 끝까지 따로 추적해야 한다.

2025년 2학기 중간 Q3(c)는 `dup`, 위치 변경, 일부 descriptor의 `close`, 부분 쓰기를 결합하여 파일 내용의 변화를 설명하게 한다. 여기서 전이할 수 있는 풀이 방식은 **descriptor 연결 → 공유 position → 덮어쓸 byte 구간 → 남는 내용** 순서다. 이번 p.20과 기출 모두 문자열만 이어 붙여 계산하면 틀리기 쉽다. 다만 기출의 `lseek` 인자와 위치 기준까지 포함한 완전한 풀이는 그 동작을 추가 확인해야 하므로, 이번 쓰기 예제와 완전히 동일한 범위라고 분류하지 않는다. [EX:sp_2025_2_midterm_q03 p.7]

### Unix I/O: 정수 descriptor로 수행하는 작업들

**Unix I/O**는 이 강의에서 정수 descriptor를 중심으로 파일을 열고, byte를 읽고 쓰고, 위치를 바꾸고, 닫는 인터페이스로 정리된다. `stat`처럼 pathname을 통해 metadata를 조회하는 함수도 같은 요약에 포함된다. [STT 28:40] [M01 p.22]

| 작업 | API | 입력·대상을 읽는 관점 |
|---|---|---|
| 열기·생성 | `open`, `creat` | pathname과 열기 방식, 필요한 생성 정보 |
| 읽기 | `read` | descriptor, 데이터를 받을 buffer, 요청 byte 수 |
| 쓰기 | `write` | descriptor, 내보낼 buffer, 요청 byte 수 |
| 위치 변경 | `lseek` | descriptor, 이동량, 위치 기준 |
| metadata 조회 | `stat` | pathname과 결과를 받을 `struct stat` |
| 닫기 | `close` | 사용을 끝낼 descriptor |

[M01 p.22]

**Buffer(버퍼)**는 읽거나 쓸 데이터를 메모리에서 담아 두는 공간이다. 예를 들어 `read(fd1, &c1, 1)`은 `fd1`로 지정한 대상에서 한 byte를 요청하고, 그것을 `c1`의 공간에 받는 호출이다. `write(fd2, "SNU", 3)`은 전달한 메모리에서 세 byte를 쓰도록 요청한다. 앞의 추적 예제에서 문자열 길이보다 **명시된 byte 수**를 확인해야 했던 이유가 여기에 있다. [M01 p.19] [M01 p.20] [M01 p.22]

자료 p.22의 `open` 선언에서 대괄호로 표시한 `mode`는 조건에 따라 필요한 인자가 있다는 설명용 표기다. C 코드를 작성할 때 그 대괄호를 그대로 넣는 문법이 아니다. 자료는 관련 header로 `<unistd.h>`, `<fcntl.h>`, `<sys/types.h>`, `<sys/stat.h>`를 제시하고, system call(시스템 호출)의 manual section 2를 안내한다. [M01 p.22]

```sh
man -S 2 open
```

여기서의 요약은 API마다 어떤 종류의 일을 하는지 구별하기 위한 것이다. 모든 flag와 오류 처리, 반환 조건을 이번 말미에 새로 상세히 배운 것으로 확대하지 않는다. 앞의 예제들도 요청량만큼의 읽기·쓰기가 성공한다는 조건을 두고 계산했으며, 실제 프로그램의 반환값 검사는 별개의 구현 과제다.

### Standard I/O: `FILE*` stream과 상태 확인

**Standard I/O**는 `<stdio.h>`의 **stream(스트림)** 객체인 `FILE*`를 중심으로 사용하는 library 인터페이스다. 정수 descriptor를 직접 넘기는 Unix I/O나 `DIR*`로 directory를 순회하는 API와는 프로그램이 다루는 객체가 다르다. [STT 28:40] [M01 p.23]

| 기능 | Standard I/O API | 중심 객체·정보 |
|---|---|---|
| stream 열기 | `fopen` | pathname과 mode 문자열에서 `FILE*`를 얻음 |
| 데이터 읽기·쓰기 | `fread`, `fwrite` | `FILE*`, 원소 크기 `size`, 원소 수 `nmemb` |
| 대기 중인 출력 처리 | `fflush` | stream의 출력 buffering과 연결 |
| 파일 끝·오류 상태 확인 | `feof`, `ferror` | stream이 기록한 상태 |
| 위치 변경 | `fseek` | stream의 파일 위치 |
| 위치 저장·복원 | `fgetpos`, `fsetpos` | `fpos_t`로 표현되는 위치 정보 |
| stream 닫기 | `fclose` | stream 사용과 관련 자원 정리 |

[M01 p.23]

**이해를 위한 예시:** `fread`의 원소 크기가 4이고 원소 수가 3이라면, 요청하는 데이터 양은 $4 \times 3 = 12$ byte다. 반환값의 단위까지 무조건 byte라고 생각하면 안 된다. 자료의 선언은 `read`의 `count`와 `fread`의 `size`, `nmemb`가 서로 다른 형태로 요청량을 표현함을 보여 준다. [M01 p.22] [M01 p.23]

`feof`와 `ferror`도 실제 읽기 동작과 구별한다. 이들은 stream의 상태를 확인하는 항목이지, 다음 읽기의 결과를 미리 확정해 주는 함수로 이해해서는 안 된다. 또한 `fflush`라는 함수가 있다는 사실만으로 모든 출력이 각 호출 직후 동일한 시점에 보인다고 가정할 수 없다.

자료 p.23은 위치 저장·복원 함수를 축약하여 표시한다. 본문에서는 이를 `fgetpos`와 `fsetpos`로 풀어 적되, STT의 불명확한 말미에서 두 함수 이름을 모두 명확히 발음했다고 주장하지 않는다. Standard I/O와 directory library 함수의 사용법을 찾는 안내는 manual section 3이다. [M01 p.23] [M01 p.24]

**`fseek` 선언의 노트 측 정정:** p.23의 반환형 `off_t`는 잘못된 표기다. Baseline 이후 별도로 제공된 [Linux man-pages `fseek(3)`](https://man7.org/linux/man-pages/man3/fseek.3.html)에 따르면 선언은 `int fseek(FILE *stream, long offset, int whence);`이며, 성공 시 0, 오류 시 -1을 반환한다. 반환값을 이동한 위치로 읽으면 안 된다. 이는 자료의 선언을 교정하는 보충 근거이며, 강의 발화나 새로운 학습 단원은 아니다.

[[concepts/unix-io|Unix I/O]]와 [[concepts/standard-io|Standard I/O]]를 비교할 때는 함수 이름의 앞에 `f`가 붙는지만 보지 말고, **정수 descriptor인지 `FILE*`인지, 요청량과 상태를 어느 계층에서 다루는지**를 구별해야 한다.

### Binary data와 line-oriented I/O: 실행되는 것과 의미가 맞는 것은 다르다

**Binary data(바이너리 데이터)**는 임의의 byte를 포함할 수 있으므로, 그것을 text의 줄이나 문자열로 해석해도 된다는 보장이 없다. 강의는 숫자와 이미지 내용을 예로 들고, 자료는 object code(목적 코드), JPEG, GIF도 제시한다. [STT 28:40] [M01 p.25]

**Line-oriented I/O(줄 단위 입출력)**는 newline(줄바꿈)을 의미 있는 경계로 사용한다. 그러나 이미지나 수치 데이터 안의 어떤 byte가 우연히 newline 값과 같다고 해서, 그곳이 데이터 형식상 한 줄의 끝이라는 뜻은 아니다. 함수 호출이 실행된다는 사실과 데이터를 의도한 단위로 처리했다는 사실은 다르다. [STT 29:37] [M01 p.25]

자료 p.25의 비교는 다음처럼 읽는다.

| 자료에서 비교한 환경·형식 | newline 표기 | byte 값 |
|---|---|---|
| Linux, Mac OS X | `LF`, `\n` | `0x0A` |
| Windows 및 강의가 예로 든 HTTP 표기 | `CR+LF`, `\r\n` | `0x0D 0x0A` |

[M01 p.25]

이 표는 newline을 나타내는 관례의 차이를 설명한다. 모든 binary 파일의 해당 byte가 자동 변환된다는 뜻도, 모든 프로토콜 데이터가 text line으로 이루어진다는 뜻도 아니다. Windows와 HTTP의 `CR+LF` 비교는 STT에서도 나오지만, 일부 운영체제명과 byte 값을 말하는 구간은 불명확하므로 정확한 표기는 자료에 근거한다. [STT 29:37] [STT 30:28]

**이해를 위한 예시:** 어떤 binary 데이터의 중간에 `0x0A`가 들어 있다고 하자. 이를 `fgets`로 읽으면 해당 byte를 줄 경계로 취급하는 동작이 개입한다. 데이터 형식이 정한 단위가 고정 길이의 수치 묶음이었다면, 이렇게 나눈 결과는 원래의 의미 단위와 맞지 않을 수 있다.

자료는 `fgets`, `scanf`, `printf`를 binary 처리의 주의 목록에 함께 둔다. 여기서 구별할 점은 `fgets`의 줄 경계 해석과 `scanf`·`printf`의 형식에 따른 text 해석이다. 이를 **Standard I/O 전체가 binary data를 처리할 수 없다는 주장으로 읽으면 안 된다.** 같은 자료가 앞에서 제시한 `fread`, `fwrite`처럼 크기와 개수를 지정하는 인터페이스도 있기 때문이다. [M01 p.23] [M01 p.25]

STT에는 line-oriented I/O를 사용하라는 긍정형 문장이 남아 있지만, 주변 설명과 p.25의 주의 사항에 맞지 않는다. 노트에서는 이를 조용히 반대 문장으로 복원하지 않고, 자료에 근거해 **임의의 binary bytes를 줄로 해석할 때 생기는 문제**를 설명한다.

### String functions와 zero byte: binary 길이는 `strlen`으로 알 수 없다

**String functions(문자열 함수)**는 C 문자열의 종료 규칙을 전제로 동작한다. 자료 p.25는 byte 값 0을 특별한 문자열 종료로 취급한다는 점을 `strlen`, `strcpy`와 연결한다. [STT 30:28] [M01 p.25]

Binary data에서는 값 0도 정상적인 내용일 수 있다. 따라서 첫 zero byte를 만났다는 사실이 전체 binary 데이터의 끝을 의미하지 않는다. 반대로 유효한 문자열 종료가 없는 메모리를 문자열 함수에 넘겼을 때 안전하게 처리된다고 보장할 수도 없다. 강의의 “호출은 될 수 있다”는 취지를 모든 buffer에서의 안전성 보장으로 확대하면 안 된다.

**이해를 위한 예시:** 다음 배열은 다섯 byte의 데이터를 담는다.

```c
char payload[] = {
    0x41, 0x00, 0x42, 0x0A, 0x43
};
```

배열의 전체 크기는 5 byte지만, C 문자열로 해석하면 첫 byte 다음의 `0x00`에서 끝난다. 따라서 이 배열에 대한 `strlen(payload)`는 1이다. 실제로 뒤에 존재하는 `0x42`, `0x0A`, `0x43`이 사라진 것이 아니라, **문자열 해석이 그 부분을 길이에 포함하지 않는 것**이다. [M01 p.25]

같은 이유로 `strcpy`를 임의 binary 데이터의 복사 도구로 사용하면, 첫 zero byte 뒤의 데이터까지 모두 복사한다는 요구를 충족하지 못할 수 있다. 데이터의 실제 길이를 알고 처리하는 문제와 문자열 종료 규칙을 따르는 문제를 분리해야 한다.

이 예시는 앞의 newline 문제와도 연결된다. `0x0A`를 특별한 줄 경계로 볼지, `0x00`을 문자열 끝으로 볼지는 **데이터를 해석하는 규칙**이다. [[concepts/binary-io|Binary data와 I/O]]에서는 byte 값이 존재한다는 사실과 그 값에 text 의미를 부여한다는 판단을 구별해야 한다. binary 처리의 핵심은 특정 함수 이름을 무조건 금지하는 것이 아니라, 사용한 인터페이스의 해석 규칙이 데이터 형식과 맞는지 확인하는 것이다.

p.13에서는 **position과 file size가 놓인 층**을 비교한다. Position은 열린 항목의 상태이고, file size는 파일의 metadata 쪽에 있다. 이 구별을 유지해야 p.20에서 append로 파일이 커져도 다른 열린 항목의 position이 그대로 남는 이유를 설명할 수 있다. [M01 p.13] [M01 p.20]

### 이번 회차에서 직접 확인되는 학습 초점

강의자는 같은 파일을 두 번 열었을 때의 공유 여부를 질문하고, 가장 작은 미사용 descriptor를 선택하는 규칙을 프로젝트의 제약과 연결한다. 이어 두 코드 예제로 position과 파일 내용의 변화를 추적한다. 이는 현재 발화와 자료에서 확인되는 활동이며, 과거 시험의 출제 빈도나 이번 시험의 우선순위를 뜻하지 않는다. [STT 14:07] [STT 20:11] [M01 p.19] [M01 p.20]

### 1단계: 개념 확인

#### Q01. `struct stat`의 size, blocks, links와 filename은 어떻게 구별하는가?

<details><summary>정답</summary>

`st_size`는 파일 크기를 byte로 나타내고, `st_blocks`는 할당된 512-byte block의 수를 나타낸다. `st_nlink`는 hard links의 수이며 열린 항목의 reference count가 아니다. Filename은 파일을 포함하는 directory에 저장되는 이름으로 구별한다.

도입부에서 함께 복습한 정보에는 `st_uid`, `st_gid`, 유형·권한을 나타내는 `st_mode`도 있다. `st_blksize`는 권장 I/O block 크기이며 할당 block 수가 아니다. [STT 00:41] [STT 01:48] [M01 p.4] [M01 p.5]

</details>

#### Q02. Data-location pointer 설명에서 확실한 관계와 검증이 필요한 부분은 무엇인가?

<details><summary>정답</summary>

Pointer가 data block을 직접 가리키는 관계와, 다른 block 안의 항목을 거쳐 data를 가리키는 관계가 소개되었다.

정확한 pointer 개수, 중간 단계 수, 파일 크기 경계, 특정 파일시스템의 내부 배치는 확정되지 않는다. 이 설명을 `struct stat`이 내부 pointer 배열을 모두 반환한다는 주장으로 바꾸어서도 안 된다. [STT 02:19] [STT 02:32]

</details>

#### Q03. `stat`, `lstat`, `fstat`, `fstatat`, `statx`는 어떤 기준으로 선택하는가?

<details><summary>정답</summary>

- `stat`: pathname으로 대상의 metadata를 조회한다.
- `lstat`: symbolic link 자체를 조사하는 구별이 필요할 때 사용한다.
- `fstat`: 이미 열린 file descriptor를 기준으로 조회한다.
- `fstatat`: 열린 directory의 descriptor와 pathname을 함께 사용한다.
- `statx`: extended file status를 위한 API로 소개되었다.

Relative path에는 기준 directory가 필요하다. `fstatat`의 기준을 명시하는 동기는 이해할 수 있지만, 모든 경로 경쟁 문제를 해결하는 완성된 보안 구현을 배운 것은 아니다. 개별 `flags`와 확장 필드의 세부 내용도 이번 설명만으로 채우지 않는다. [STT 03:00] [STT 03:59] [STT 04:54] [M01 p.8]

</details>

#### Q04. `DIR*`로 directory를 다룰 때 API는 어떻게 이어지는가?

<details><summary>정답</summary>

`opendir`로 `DIR*`를 얻고, `readdir`로 entry를 읽는다. 열린 directory의 정수 descriptor가 필요하면 `dirfd`를 사용한다. 작업이 끝나면 `closedir`로 정리한다. Directory 생성은 `mkdir`의 역할이다.

`DIR*`는 정수 descriptor가 아니다. 자료에 나열된 `fdopendir`, `mkdirat`은 변형 API이며, 이번 발화에서 세부 동작까지 설명된 것으로 취급하지 않는다. [STT 05:42] [STT 06:28] [M01 p.10] [M01 p.24]

</details>

#### Q05. `statter.c`는 무엇을 출력하며, 왜 `errno`를 초기화하는가?

<details><summary>정답</summary>

첫 인자가 있으면 그 directory를, 없으면 코드에 지정된 `"."`을 연다. 이름은 `readdir`이 반환한 entry의 `e->d_name`에서 가져오고, 파일 크기는 `fstatat`이 채운 `sb.st_size`에서 가져와 함께 출력한다.

`readdir`가 `NULL`을 반환했을 때 정상 종료와 오류를 구분하려면, 이전 `fstatat` 등의 오류값이 남지 않아야 한다. 따라서 예제는 다음 `readdir` 전에 `errno`를 0으로 만들고 순회 종료 후 검사한다. 개별 조회 실패와 순회 자체의 실패, 프로그램의 최종 종료 상태도 서로 구별한다. [M01 p.11]

</details>

#### Q06. Descriptor table, open file table, v-node table에는 각각 무엇이 있는가?

<details><summary>정답</summary>

Descriptor table은 process마다 descriptor 번호를 열린 항목에 연결한다. Open file table 항목은 file position과 reference count를 가지며 여러 descriptor가 공유할 수 있다. V-node 쪽은 file size, type 등 파일의 메모리상 metadata를 나타낸다.

자료의 standard input, standard output, standard error 번호는 각각 0, 1, 2다. Descriptor는 disk file뿐 아니라 강의에서 짧게 언급한 socket이나 pipe와도 관련된다. [STT 09:15] [M01 p.13]

</details>

#### Q07. File descriptor passing과 `fork`는 왜 단순한 번호 복사로 설명할 수 없는가?

<details><summary>정답</summary>

숫자의 의미는 각 process의 descriptor table에서 정해진다. 다른 process가 같은 열린 항목을 사용하려면 그 process의 descriptor도 해당 항목으로 연결되어야 한다. 송신·수신 번호가 같거나 다르다는 사실만으로 공유 여부를 판단할 수 없다.

`fork`의 입문적 설명에서도 parent와 child는 각자 실행하고 각자의 descriptor table을 가지지만, 상속된 descriptor는 같은 열린 항목을 참조한다. 정확한 실행 순서와 후속 process 제어는 이 공유 관계만으로 결정할 수 없다. [STT 11:13] [STT 12:11] [STT 13:09]

</details>

#### Q08. 같은 파일을 두 번 `open`하는 것, `dup`하는 것, `fileno`를 호출하는 것은 어떻게 다른가?

<details><summary>정답</summary>

독립적인 두 `open`은 같은 파일을 대상으로 하더라도 별개의 열린 항목과 position을 만든다. `dup`는 기존 열린 항목을 참조하는 새 descriptor를 만들어 position을 공유한다.

`fileno`는 `FILE*`에 대응하는 descriptor를 얻는 함수다. `dup`처럼 새로운 descriptor를 복제하는 동작으로 이해하면 안 된다. [M01 p.14] [M01 p.16] [M01 p.17]

</details>

#### Q09. Shell 예시의 `>`, `|`, `<`는 각각 어느 방향의 연결인가?

<details><summary>정답</summary>

`>`는 프로그램의 standard output을 파일로, `|`는 앞 process의 출력을 다음 process의 standard input으로, `<`는 파일을 프로그램의 standard input으로 연결한다.

이 연결 방향을 아는 것만으로 완전한 shell이나 pipeline 실행 절차를 모두 배운 것은 아니다. [STT 16:06] [STT 17:04] [M01 p.15]

</details>

#### Q10. `close(1)` 뒤의 `dup(3)`이 1을 반환하려면 어떤 조건이 필요한가?

<details><summary>정답</summary>

Descriptor 3이 유효하고, 1이 가장 작은 미사용 번호이며, 그 사이 다른 descriptor 할당이 끼어들지 않는다는 조건이 필요하다. `dup`는 기존 descriptor 하나를 인자로 받는다. 인자가 없다는 앞선 발언은 이어지는 발언에서 정정되었다.

자료 p.17에서 변수 `fd2`의 값이 4인 것도 같은 규칙의 예다. 변수 이름의 숫자는 실제 descriptor 번호가 아니다. [STT 18:53] [STT 20:11] [M01 p.17]

</details>

#### Q11. `dup2(fd, STDOUT_FILENO)` 뒤 `write(1, ...)`은 어디로 향하는가?

<details><summary>정답</summary>

Descriptor 1이 `fd`와 같은 열린 항목을 참조하므로, `fd`가 가리키던 대상으로 향한다. 숫자 1 자체를 다른 숫자로 바꾸는 것이 아니다.

자료처럼 `fd`가 3이라면 복제 성공 후 3을 닫아도 1의 연결은 남는다. p.18의 `O_WRONLY`만으로 파일 생성이나 기존 내용 제거까지 수행한다고 추측해서는 안 된다. [M01 p.18]

</details>

#### Q12. `fwfd1.c`의 결과가 `S`, `S`, `y`인 이유는 무엇인가?

<details><summary>정답</summary>

`fd1`은 독립적인 position 0에서 `S`를 읽는다. `fd2`도 자기 position 0에서 `S`를 읽지만, `dup2(fd2, fd3)` 이후 `fd3`와 같은 열린 항목을 공유한다. 따라서 뒤이은 `fd3`의 읽기는 공유 position 1의 `y`를 얻는다.

이 결과는 슬라이드의 코드와 출력에서 확인되는 것이며, 불명확한 발화를 복원한 결과가 아니다. [M01 p.19]

</details>

#### Q13. `fwfd2.c`에서 `SNU` 뒤에 `22`가 남는 이유는 무엇인가?

<details><summary>정답</summary>

별도의 append 쓰기로 내용이 `CSAPM1522`가 되어도, `fd1`의 position은 4다. 이를 공유하는 `fd2`가 세 byte를 쓰므로 `M15`만 `SNU`로 바뀌고 뒤의 `22`는 남는다.

이후 별도 append 항목을 사용하는 `fd3`가 당시 파일 끝에 `800`을 붙인다. 최종 내용은 `CSAPSNU22800`이다. [STT 27:28] [STT 27:47] [M01 p.20]

</details>

#### Q14. Unix I/O와 Standard I/O의 기능 목록을 객체 중심으로 구분해 보라.

<details><summary>정답</summary>

Unix I/O 요약에는 `open`·`creat`, `read`·`write`, `lseek`, `stat`, `close`가 있다. 정수 descriptor가 중심이지만, `stat`처럼 pathname을 받는 조회도 포함된다.

Standard I/O는 `FILE*`를 중심으로 `fopen`, `fread`·`fwrite`, `fflush`, `feof`·`ferror`, `fseek`, `fgetpos`·`fsetpos`, `fclose`를 정리한다. `feof`와 `ferror`는 상태 확인이며 다음 읽기의 성공 여부를 미리 알려 주는 함수가 아니다.

자료는 system call에 manual section 2, Standard I/O와 directory library 함수에 section 3을 안내한다. [M01 p.22] [M01 p.23] [M01 p.24]

</details>

#### Q15. Binary data에 `0x0A`가 있으면 한 줄의 끝이라고 보아도 되는가?

<details><summary>정답</summary>

데이터 형식이 그런 의미를 정하지 않았다면 그럴 수 없다. Line-oriented I/O가 해당 값을 경계로 취급하더라도, 그것이 원래 데이터의 의미 있는 경계라는 보장은 없다.

자료는 LF를 `0x0A`, CR+LF를 `0x0D 0x0A`로 비교한다. 이 비교를 모든 binary byte의 자동 변환 규칙으로 확대하지 않는다. [STT 29:37] [M01 p.25]

</details>

#### Q16. `strlen`과 `strcpy`를 임의 binary 데이터의 길이 측정·복사에 그대로 쓰면 어떤 문제가 있는가?

<details><summary>정답</summary>

이 함수들은 zero byte를 C 문자열의 끝으로 해석한다. Binary 데이터 안의 zero byte는 정상적인 내용일 수 있으므로, 그 뒤에 데이터가 남아 있어도 문자열 처리에서는 종료된다.

반대로 유효한 종료가 없는 buffer를 문자열 함수에 넘겨도 안전하다고 보장할 수 없다. 크기를 지정하는 `fread`·`fwrite`가 있으므로 이 문제를 Standard I/O 전체의 한계로 일반화하지 않는다. [M01 p.23] [M01 p.25]

</details>

Redirection 구현과 가장 작은 미사용 descriptor 규칙은 과제 맥락과 연결되지만, redirection 과제의 정확한 식별자는 불명확하다. 완전한 구현에는 뒤에서 다룰 추가 기법이 필요하다고 설명한다. API 도입 연대기에 관한 언급도 제공 자료로 독립 확인된 역사로 바꾸지 않는다. [STT 00:41] [STT 20:11] [STT 27:47] [STT 31:28]

#### Q18. Metadata 조회 뒤 directory가 이동하거나 pathname이 바뀔 수 있다면, 왜 directory를 먼저 열어 descriptor를 상대 경로의 기준으로 사용하는가?

<details><summary>정답</summary>

Metadata를 조회한 뒤 같은 경로 문자열을 다시 해석하는 사이에 directory가 이동하거나 pathname이 달라지면, 나중 접근에서 처음 의도한 것과 다른 대상을 찾을 수 있다. Directory를 먼저 열고 그 descriptor를 상대 이름의 기준으로 사용하면, 경로 문자열에만 의존하지 않고 이미 열린 directory를 조회의 기준으로 유지할 수 있다. 이것이 강의에서 제시한 동기다. [STT 03:59] [STT 04:54]

**채점 포인트:** 호출마다 빈 번호를 갱신하기, `dup`의 한 인자와 공유 대상 구별, 기본 결과 `1, 0, 4`, 변형 결과 2.

| `b` | `X` | 공유 항목 2 |

- **범위:** `O_APPEND`, 독립 `open`, `dup`, 부분 덮어쓰기. [STT 25:37] [STT 27:47] [M01 p.20]
- **요구 능력:** 파일 내용과 entry별 position을 함께 추적하기.
- **선수 개념:** 쓰기 가능한 descriptor, byte count, 공유 position.

```c
write(a, "LM", 2);
int b = open(name, O_WRONLY | O_APPEND);
write(b, "3456", 4);
int c = dup(a);
write(c, "QR", 2);
write(b, "!", 1);
```

2. 최종 파일 내용과 position을 구하라.

<details><summary>풀이와 채점 포인트</summary>

기본 문제에서 `a`·`c`는 같은 열린 항목을 공유한다. `b`는 같은 파일을 대상으로 하지만 별도의 append 항목이다.

| 동작 | 파일 내용 | `a`·`c`의 position | `b`의 position |
|---|---|---:|---:|
| `a`로 `LM` 쓰기 | `LM` | 2 | 아직 없음 |
| `b`로 `3456` 쓰기 | `LM3456` | 2 | 6 |
| `c`로 `QR` 쓰기 | `LMQR56` | 4 | 6 |
| `b`로 `!` 쓰기 | `LMQR56!` | 4 | 7 |

`QR`은 position 2부터 두 byte만 덮으므로 `56`은 남는다. 최종 크기는 7 byte다.

변형에서는 `c`의 독립 position이 0이므로 `QR`이 처음의 `LM`을 덮는다. 마지막 append 후 내용은 `QR3456!`이다. Position은 `a = 2`, `c = 2`, `b = 7`이다.

**채점 포인트:** 파일 크기 증가와 독립 position 유지의 구별, 두 byte만 덮기, append를 당시 끝에 배치하기, `dup`를 독립 `open`으로 바꾼 효과.

3. **새 변형:** 이미 `FILE*`가 있으며 그에 대응하는 descriptor만 알고 싶다. `dup`와 `fileno` 중 무엇을 선택하는가? 실제로 모든 데이터가 처리되었는지도 이 요청량만으로 확정할 수 있는가?

<details><summary>풀이와 채점 포인트</summary>

열기·생성은 `open`·`creat`, stream 열기는 `fopen`, directory 열기는 `opendir`에 연결된다.

두 요청량은 모두 12 byte다.

$$
\texttt{fread의 요청량} = 3 \times 4 = 12\ \text{bytes}
$$

다만 `read`는 byte 수 하나를 사용하고, `fread`는 원소 크기와 원소 수로 요청량을 나타낸다. 요청량만으로 실제 완료량을 확정하지 않으며 반환값과 상태 확인이 필요하다.

대응 descriptor를 얻는 역할은 `fileno`다. `dup`는 새 descriptor를 만드는 다른 동작이다.

기능을 이어서 분류하면 descriptor의 읽기·쓰기·위치 변경·닫기는 `read`, `write`, `lseek`, `close`이고, pathname의 metadata 조회는 `stat`이다. Stream 쪽은 `fread`·`fwrite`, `fflush`, `feof`·`ferror`, `fseek`, `fgetpos`·`fsetpos`, `fclose`로 정리한다. Directory 순회와 정리는 `readdir`, `dirfd`, `closedir`다.

**채점 포인트:** 여는 객체의 구별, 요청량 12 계산, 요청과 완료의 차이, `fileno`와 `dup` 구별, 기능별 API 대응.

</details>

#### 연습 P11

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**일반 연습 — 관련 기출 근거 없음**

- **접근 상태:** 현재 접근 가능.

다음은 길이가 6 byte로 알려진 데이터다.

```c
char payload[] = {
    0x41, 0x0A, 0x42, 0x00, 0x43, 0x44
};
```

1. 자료의 LF와 CR+LF는 각각 어떤 byte로 표시되는가?
2. `strlen(payload)`의 값은 무엇인가? 전체 binary 데이터 길이와 일치하는가? `0x0A`가 있다는 사실만으로 데이터 형식상의 줄 경계를 확정할 수 있는가?
3. **새 변형:** 배열의 `0x00`을 0이 아닌 값으로 바꾸고 배열 안에 다른 zero byte도 없다고 하자. 계속 `strlen`으로 길이를 구해도 되는가?

<details><summary>풀이와 채점 포인트</summary>

LF는 `0x0A`, CR+LF는 `0x0D 0x0A`다.

원래 배열에서 첫 zero byte 앞에는 세 byte가 있으므로 `strlen(payload)`는 3이다. `0x0A`도 zero byte는 아니므로 문자열 길이에 포함된다. 실제 binary 데이터 길이는 주어진 조건대로 6 byte다.

데이터 형식이 줄 경계를 정하지 않았다면 `0x0A`에 text line의 의미를 부여할 수 없다. 줄 단위 함수가 경계로 취급하는 것과 원래 데이터의 의미는 별개다.

변형에는 배열 안에 문자열 종료가 없으므로, 이 배열을 정상적인 종료 문자열로 가정해 `strlen`을 호출해서는 안 된다. 배열 밖에서 종료를 찾게 되는 접근은 안전하다고 보장할 수 없다. 길이가 알려진 binary 처리는 그 길이를 명시하여 다루어야 하며, `fread`·`fwrite` 같은 Standard I/O도 그 용도로 사용할 수 있다.

**채점 포인트:** LF·CR+LF 표기, 길이 3과 6의 구별, newline의 의미와 값 구별, 종료 없는 배열의 문제, Standard I/O 전체에 대한 잘못된 일반화 방지.

</details>

| Pointer 배치·전달 API·과제 식별자·종료 발언 | 확인되지 않은 세부 사항은 검증 필요로 남긴다. Quiz 문항이나 누락된 수업 발화를 만들지 않는다. |

**S01 — 별도 사실 보충:** [Linux man-pages `fseek(3)`](https://man7.org/linux/man-pages/man3/fseek.3.html)은 baseline 이후의 보충 자료다. `fseek`의 반환형은 `int`이며 성공 0, 오류 -1을 반환한다는 선언 정정에만 사용했다. 이를 이동한 위치를 반환하는 함수로 해석하지 않는다.

STT의 실용적 보정은 음성을 새로 청취하여 모든 발화를 복구한 결과가 아니다. 전체 음성의 누락 여부를 확인한 감사도 아니므로, 짧은 불명확한 발언이나 시작·끝의 빈 부분을 확정적으로 보충하지 않는다.

### 기출 연결 검토

**기출 연결 검토:** 전체 후보에서 현재 본문과 연결되는 소문항을 골라, descriptor 번호 할당과 출력 재지정은 직접 연결하고 inode·링크 수 및 `lseek`를 포함한 쓰기는 부분 연결로 구분했다. Directory 순회, 오류 구분, data-location pointer의 한계, binary 데이터의 해석에는 적절한 직접 스타일 근거를 붙이지 않고 일반 연습을 유지했다.

기출은 요구 능력의 짧은 요약에만 사용했다. 원본 시험지와 제공 답안은 재배포하지 않으며, P01–P11은 각각 조건을 정해 새로 만든 연습이다.
