## Lecture Content and Explanation

### Arrays and pointers: conversion does not erase the object
`int a[10]` creates an array object containing ten ints. In many expressions, `a` converts to a pointer to its first element: `a+i` corresponds to `&a[i]`, and `*(a+i)` to `a[i]`. The array itself is not a separate pointer variable. Consequently, `a++` cannot reassign the array's beginning, whereas a separate `int *p=a;` can be advanced with `p++` within the permitted range.

`sizeof a` measures the whole array, and `&a` forms a pointer to the whole array. Array initialization also differs from initializing a pointer with an address. These contexts explain why replacing “array” with “pointer” everywhere produces wrong types and sizes. As material-based review of earlier pointer arithmetic, if `p=&a[2]`, then `p+3` points to `a[5]`: three means three elements, not three bytes. All accesses still require an existing, valid element.

### Array arguments pass an address value
In `find_largest(int a[], int n)`, the parameter is adjusted to a pointer type. Calling `find_largest(b,10)` therefore passes the address of the first element rather than copying ten element values. The cost of passing that argument does not grow with the array's length. The function's subsequent work, such as visiting all elements to find the largest, can still grow with the number of elements.

The local parameter and the caller's array give access to the same element storage. Writing `a[0]` can change the caller's `b[0]`. Assigning a different address to the local pointer parameter does not, however, reassign a pointer variable belonging to the caller. Passing a pointer by value and allowing access to the pointed-to object are compatible ideas.

### const, actual copies and slices
The declaration `find_largest(const int a[], int n)` restricts modification of elements through that parameter. It does not make the original array immutable through every possible access path. The lecturer connected read-only access to `strlen` and used a C++ const-member-function analogy; the analogy does not make all C and C++ const rules identical.

A student asked about automatically copying all the elements. Passing a structure containing an array by value was discussed as a different case from an array parameter. An actual copy requires storage and work; declaring a parameter with brackets does not request one. Some student wording remains unclear, but the distinction between these mechanisms is retained.

`find_largest(&b[5],10)` supplies a slice starting at original element 5 and ending at original element 14. The callee treats the supplied address as its local index zero. This is valid only if the caller actually has all ten elements from that starting point.

### Pointer storage does not allocate a target
`int a[10];` reserves element storage, so a subsequent `*a=0;` initializes the first int. `int *a;` reserves only the pointer object. It does not provide an initialized target address for `*a=0;`. Declaring the pointer and arranging the pointed-to object's storage are separate tasks.

The lecturer discussed operating-system protection: an access to an invalid or protected address may terminate the process. Student questions brought up virtual addresses, permissions and the possibility of an accidentally accessible address. At the C language level, an uninitialized automatic pointer is not safe to read or dereference, and undefined behavior does not mean “always crashes.” A run that happens to continue is not evidence that the operation was valid.

### Double pointers: update the arrows after every statement
A double pointer can modify a pointer object, which then changes the int reached through a second dereference. Begin with:

```c
int i, j;
int *p = &i, *q = &j;
int **k = &p;
```

| Statement completed | i | j | p points to | q points to | k points to |
|---|---:|---:|---|---|---|
| `*p=1; *q=2;` | 1 | 2 | i | j | p |
| `*k=q;` | 1 | 2 | j | j | p |
| `k=&q;` | 1 | 2 | j | j | q |
| `*k=&i;` | 1 | 2 | j | i | q |
| `*p=3;` | 1 | 3 | j | i | q |
| `**k=4;` | 4 | 3 | j | i | q |

At first `*k` denotes `p`, so `*k=q` copies q's address value into p. After `k=&q`, `*k` instead denotes q. The final `**k=4` follows q to i, giving `i=4` and `j=3`. Continuing to follow the original diagram without updating k is the characteristic error.

### Read declarators outward from the identifier
Postfix `[]` and `()` bind more tightly than `*`, and parentheses can change that grouping. Start at the identifier, respect the grouping, and identify each array, function or pointer layer rather than counting stars.

| Declaration | Meaning |
|---|---|
| `int *p[10];` | Array of ten pointers to int |
| `int (*p)[10];` | Pointer to an array of ten ints |
| `int *(*p)[10];` | Pointer to an array of ten int pointers |
| `int (*pf)(void);` | Pointer to a function taking no arguments and returning int |
| `int *pf(void);` | Function returning an int pointer |
| `int (*pf[10])(void);` | Array of ten pointers to functions taking no arguments and returning int |
| `int pf[](void);` | Invalid attempt to declare an array of functions |

Functions can be addressed by function pointers, and those pointer objects can be array elements. A function itself cannot be an array element.

### Separate type, sizeof and evaluated access
Assume the course model of 4-byte ints and 8-byte pointers. Determine the expression's type before calculating its size:

| Declaration | `sizeof(A)` | Type and size of `*A` | Type and size of `**A` |
|---|---:|---|---|
| `int A1[3];` | 12 | int, 4 | Invalid: an int cannot be dereferenced again |
| `int *A2[3];` | 24 | int pointer, 8 | int, 4 |
| `int (*A3)[3];` | 8 | int[3], 12 | int, 4 |

For this fixed-size array type, `sizeof(*A3)` determines a type's size without evaluating its operand. A result of 12 does not establish that an uninitialized A3 can actually be dereferenced safely. Conversely, the danger of evaluating an uninitialized pointer does not mean every `sizeof` involving its name must crash. This statement concerns fixed-size types, not all variable-length-array cases.

### Array assignment differs from assigning one element
Consider a validly initialized example:

```c
int A[3] = {1, 2, 3}, B[3] = {4, 5, 6};
int (*A3)[3] = &A, (*B3)[3] = &B;
int *pA;
/* *A3 = *B3; */  /* invalid array assignment */
**A3 = **B3;       /* copy the first int only */
pA = *A3;         /* obtain the first element's address */
```

The commented statement attempts to assign one whole array to another and is invalid. The next statement makes A equal to `{4,2,3}`, not `{4,5,6}`. Finally the array expression `*A3` converts to the address of A's first element, which pA stores. Matching types alone does not make an array a modifiable lvalue suitable for assignment.

### Unix files expose bytes; applications interpret them
The regular-file model is a sequence of bytes. In a file containing `a` through `z`, the first byte has offset 0 and the last has offset 25. An application interprets those bytes as text, a picture or records; the operating system does not impose every application's higher-level format.

Unix extends file-like interfaces to directories, devices and sockets. Examples included `/dev/sda`, `/dev/input/mice` and `/dev/tty`, along with kernel-information interfaces under `/proc` and `/sys`. Reading such a path need not retrieve bytes previously stored as an ordinary disk file. The kernel-memory example motivates permissions and restricted exposure; it does not promise the same device path exists or is accessible on every current machine. A terminal is an interface used to interact with the system, not the kernel itself.

### inode metadata, directory names and devices
An inode represents file metadata such as type, size and permissions. A name, inode number and file contents are distinct. A directory associates names with references to inodes; metadata and content then describe the referenced object. The question about where the name belongs helps separate these roles. An illustrative inode number is not a formula for computing a disk address.

Character devices were introduced using keyboards and mice as byte-stream examples, and block devices using disks as block-oriented examples. `ls -l` uses `c` and `b` to indicate these kinds. This introductory distinction should not be strengthened into a universal claim that every character device forbids positioning or that every block device supports unrestricted operations.

### Named FIFOs connect processes
FIFO means first in, first out. A named pipe has a filesystem name that processes can open to communicate. The existence of that entry does not mean the transmitted data accumulates as the contents of an ordinary disk file; the kernel carries the communication data.

The material illustrates `mkfifo abc`, a reader using `gzip -c < abc > abc.gz`, and a writer using `cat document.txt > abc`. The compressor consumes bytes from the FIFO and writes compressed output to a separate regular file. A reader can wait for input, making ordering and background execution relevant.

The printed `&;` combination is invalid Bash syntax, as a syntax-only check confirmed. The shape of `-c` also matters. These commands are explained as the material's intended data flow; they were not executed as a FIFO demonstration for this note. Unclear live-demo speech is not evidence that a particular output file was successfully produced or removed in a particular order.

### Sockets and file descriptors
A Unix-domain socket supports bidirectional communication between processes on the same system: both sides can send and receive. This contrasts with the illustrated one-way FIFO flow. [STT 55:05] [M02 slide 8] The lecturer distinguished this from TCP/IP sockets used between remote systems. Combining a slide's Unix-domain heading with its broader network discussion must not turn a local Unix-domain socket into a remote-machine transport. Some remarks about how much detail was deferred remain unclear.

Operations such as open, create, read, write and close provide a common interface. A file descriptor is a small integer handle used by a process for an opened object. A pathname supplies a name for lookup, an inode describes file metadata, and a descriptor is the process's handle for using the open object. These are not interchangeable identifiers. Not every object supports seeking: a pipe's sequential stream cannot simply be repositioned like an ordinary seekable file. The small-integer descriptor definition is technical explanatory supplementation, not recovered verbatim speech.

### Lab1 Decommenter: understand the transformation contract
The assignment reads from `stdin`, transforms comment-containing C-like input and writes to `stdout`; diagnostic output belongs on `stderr`. Shell redirection supplies input and captures output. This section explains requirements, not an implementation of the assignment.

Distinguish block comments `/* ... */` from line comments `// ...`. Block comments do not nest. Comment markers inside string literals or character constants remain part of those quoted contents; escapes affect whether a quote ends them. Replacing comments with a space prevents neighboring tokens from being joined, while preserving newlines maintains the required line structure. Merely searching for every visible `/*` or `//` is therefore insufficient.

Precisely, replace each comment with one space while retaining its newlines. Inside quotes, preserve a backslash and the following character together instead of treating that following character as a closing quote or comment delimiter. An escaped quote therefore does not end the quoted state. The form `./decomment < input.c > output.c 2> error.txt` routes stdin, stdout and stderr separately. [M04 p.3] [M04 p.4] [M04 p.5] [M04 p.8]

### Lab1 boundary cases and errors
For this assignment, newlines inside strings or character constants and unterminated quoted input are preserved without errors or warnings. The task is not a full C compiler. An unterminated block comment instead requires a diagnostic naming its starting line, such as `Error: line 2: unterminated comment`, on stderr and an `EXIT_FAILURE` result. Other cases return `EXIT_SUCCESS`.

The material's visible `s` and `n` stand for a space and newline, not literal letters to output. Thus `abc/*def*/ghi` becomes `abc ghi`, and `"def/*ghi*/jkl"` remains quoted content. In `abc/*def/*ghi*/jkl*/mno`, the first closing `*/` ends the comment; the remaining `jkl*/mno` must not be deleted as though comments nested.

Input lines can be arbitrarily long. The final input line ends with a newline, and backslash-newline pairs are excluded by the specification. These are assignment assumptions, not properties of all C source. The material's broad suggestion that a multicharacter constant is always a compiler error is also too strong: C99 permits an implementation-defined value. **Q01. How do array conversion, sizeof and pointer movement differ?**

<details>
<summary>Answer</summary>

An array owns element storage; in many expressions it converts to a pointer to its first element. sizeof array measures all elements and &array points to the entire array. A separate pointer can advance; the array name cannot be reassigned with ++.
