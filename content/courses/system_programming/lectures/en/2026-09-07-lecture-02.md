**Definition:** `getchar` produces either a character value or the special result `EOF`.

**Lecture framing and evidence:** The instructor repeatedly asked why a one-byte input character requires an `int` result, then focused on the need for an additional distinguishable value. [STT 02:43] [STT 06:35] [M01 p.4]

### 2. Word counting: remember only the history that matters

**Definition:** A DFA records a finite state and selects its next state from the current state and input.

**Lecture framing and evidence:** For word counting, the necessary history is whether the scanner is inside or outside a word. The increment belongs to the transition into a word. [STT 14:43] [STT 15:09] [M01 p.12]

**Worked example:** `a   b` produces two `OUT → IN` transitions and therefore two words.

<a id="sp02-dfa"></a>

The lecture defines a word operationally as a maximal sequence of non-space characters. Consequently, punctuation can belong to a word: `blue!` is one word under this definition. This is a scanner specification, not a claim about linguistic word boundaries. [STT 14:04] [M01 p.11]

**Reading the DFA figure.** M01 page 12 has two circles. The incoming arrow selects `Outside Word` as the initial state. Each circle has a self-loop, and two arrows connect the circles. Only the arrow from `Outside Word` to `Inside Word` carries a counting action.

The complete transition rule for this example is:

| Current state | Input classification | Next state | Counter change |
|---|---|---|---:|
| `OUT` | Space | `OUT` | 0 |
| `OUT` | Non-space | `IN` | +1 |
| `IN` | Space | `OUT` | 0 |
| `IN` | Non-space | `IN` | 0 |

This placement solves several boundary cases simultaneously. Leading spaces do nothing. Multiple spaces between words do nothing beyond the first transition to `OUT`. A final word is counted even if the input ends without trailing whitespace. [M01 p.12] [M01 p.17]

The useful invariant is that, after processing a prefix, the count equals the number of word beginnings encountered in that prefix:

$$
W=\sum_{k=1}^{n}
\mathbf{1}\!\left[
s_{k-1}=\mathrm{OUT}
\;\land\;
c_k\text{ is non-space}
\right].
$$

This equation is an editorial formalization of the slide’s action rule, not reconstructed speech.

M01 page 13 extends the idea to recognizing `SNUCSE` and the integer-shaped pattern `0` or `[+-]?[1-9][0-9]*`. The first diagram includes fallback transitions and an explicit note about omitted transitions. The second distinguishes an optional sign, a nonzero initial digit, subsequent digits, and the separate zero case. Neither diagram is a complete specification of all C integer syntax. [STT 17:05] [STT 17:46] [M01 p.13]

The instructor linked DFA thinking to the decomment assignment: design the relevant states before implementing comment removal. That connection supports a design method; it does not supply a complete assignment implementation. [STT 19:40]

Read accepting states together with the end-of-input condition. For a whole-input match to the slide's integer pattern, visiting an accepting state after a digit does not accept an input that later contains a forbidden character. Omitted transitions must be supplied consistently with the intended language, not arbitrarily treated as self-loops. This clarification comes from the retrospective visual comparison with the original diagram. [M01 p.13]

#### 1. Original example: classify characters and count words in the same input

The following notation represents seven input characters. `\t` means one tab and `\n` means one newline:

```text

```

|---|---|---|---:|

### 3. Make the program’s intended structure visible

**Definition:** Named constants expose meaning; function comments describe purpose; defensive checks expose violations of intended program state.

**Lecture framing and evidence:** The progression from numeric states to `enum`, comments, and a guarded `default` was a deliberate code-improvement exercise. [M01 p.14] [M01 p.16] [M01 p.17]

**Worked example:** `state = OUT` expresses an initial condition more clearly than `state = 1`.

<a id="sp02-intent"></a>

The initial word counter uses `0` and `1` as states. The program can work, but a reader must infer what those values mean. The instructor emphasized that collaborators, and even the original author later, should not have to reconstruct this mapping. [STT 21:39] [STT 22:32] [M01 p.14]

M01 page 15 introduces three naming mechanisms:

| Mechanism | Meaning in the lecture | Important distinction |
|---|---|---|
| `enum DFAState { IN, OUT };` | Names the two state values | Enumeration constants suit this `switch` example. |
| `#define IN 0` | Replaces a macro name during preprocessing | The replacement must itself be suitable for its use. |
| `const int IN = 0;` | Declares a const-qualified integer object | It is not interchangeable with an enumeration constant in every C context. |

The question about `const int` in a `case` label remained unresolved during 31:14–33:09: **검증 필요** for the classroom conclusion. The independent C99 clarification is that an ordinary `const int` object is not an integer constant expression for a `case` label. Enumeration constants and suitable constant macros can satisfy that requirement. This clarification must not be attributed to a recovered answer in the recording. [C99 consolidated draft N1256, §6.6 ¶6 and §6.8.4.2 ¶3](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)

The completed example also adds a function comment and an assertion in `default`. The comment states the function’s purpose rather than narrating each branch. The assertion exposes a state outside the intended `IN`/`OUT` set. [M01 p.16] [M01 p.17] [M01 p.18]

The course-specific emphasis is explicit: write comments for functions, consider `default` when writing `switch`, and design the algorithm before coding. Standard background supplies the broader interpretation: an assertion expresses an invariant expected of correct execution. Assertions can be disabled, so they should not be mistaken for unconditional input validation.

#### 2. Reconstructed lecture code: implement the transition table

This version follows M01 page 17. Assume the educational input’s word count fits in `int`. The `return 1` in `default` is an editorial addition that preserves termination if assertions are disabled.

```c
#include <stdio.h>
#include <ctype.h>
#include <assert.h>

enum DFAState { IN, OUT };

/* Count whitespace-separated words from stdin and print the count. */
int main(void)
{
    int c;
    int nWords = 0;
    enum DFAState state = OUT;

    while ((c = getchar()) != EOF) {
        switch (state) {
        case IN:
            if (isspace(c))
                state = OUT;
            break;

        case OUT:
            if (!isspace(c)) {
                state = IN;
                nWords++;
            }
            break;

        default:
            assert(0);
            return 1;
        }
    }

    printf("%d\n", nWords);
    return 0;
}
```

There is exactly one increment location. It corresponds to `OUT → IN`; the `IN` branch merely detects departure from a word. [M01 p.17]

| Tempting conclusion | Correct interpretation |
|---|---|
| `enum`, `#define`, and `const int` are interchangeable everywhere. | Their language roles differ; the C99 `case`-label issue requires that distinction. |

**Definition:** Preprocessing, compilation, assembling, and linking transform source into an executable through different intermediate representations.

**Lecture framing and evidence:** The instructor emphasized understanding what each stage contributes rather than memorizing every command. [STT 35:43] [STT 43:12] [M01 p.21]

**Worked example:** `hello.o` can contain a call requiring an external implementation even though machine code has already been generated.

<a id="sp02-build"></a>

| Stage | Input → output | Main contribution | What remains unresolved in the example |
|---|---|---|---|
| Preprocessing | `hello.c` → `hello.i` | Processes includes and macros; removes comments from the resulting source representation | The library function’s implementation is still separate. |

### 5. Pointers: distinguish names, stored values, and addresses

**Definition:** A pointer object stores a pointer value. Dereference designates the object reached through that value.

**Lecture framing and evidence:** The lecture separated the name, stored value, and address of a variable, then used diagrams to show how `*p` accesses the target. [STT 46:44] [M02 slide 6] [M02 slide 11]

**Worked example:** With `int i = 1; int *p = &i;`, assigning `*p = 2` changes `i`.

<a id="sp02-pointers"></a>

The lecture describes a variable through its name, its value, and the address of its storage. A pointer introduces another object whose stored value identifies a target. [STT 46:44] [M02 slide 3]

The memory figure on M02 slide 4 separates the address column from the contents column. Slide 5 then uses the first byte’s address to identify a multi-byte variable. Slide 6 replaces the numerical address with an arrow from `p` to `i`. The arrow means that `p` stores a value designating `i`; it does not mean that `p` contains a copy of `i`. [M02 slide 4] [M02 slide 5] [M02 slide 6]

Referenced type matters. An `int *` designates an integer object; a `double *` designates a double object. The lecture explains this through the size and interpretation of the accessed data. Its four-byte `int`, eight-byte `double`, and eight-byte pointer are environment assumptions, not universal consequences of the spelling of those types. [STT 49:47] [STT 50:48]

The declaration examples introduce several distinct structures:

| Declaration | Reading |
|---|---|
| `int *p;` | `p` is a pointer to `int`. |
| `int **p;` | `p` is a pointer to a pointer to `int`. |
| `int (*p)[10];` | `p` is a pointer to an array of ten integers. |
| `int *p[10];` | `p` is an array of ten pointers to integers. |

[M02 slide 7]

Start with the identifier and respect parentheses and the binding of `[]`. The brief introduction of `int **` does not establish that the extended double-pointer exercises later in the deck were taught.

Pointer initialization and target initialization are separate:

```c
int i;
int *p = &i;
```

This establishes where `p` points. It does not initialize the value of `i`. Assigning `*p = 2` initializes or changes the target; reading `*p` first would read the still-uninitialized integer. The lecture itself notices the missing initialization in the displayed example. [STT 57:10] [M02 slide 9] [M02 slide 10]

The virtual-memory discussion explains why an address-space model does not authorize arbitrary memory access. A process needs suitable mappings and permissions. A theoretical address range is not a promise that every address is backed by usable memory. Allocation and protection were motivations introduced here; page-table mechanics were deferred. [STT 59:49] [STT 01:00:50] [STT 01:01:46]

The instructor repeatedly asked what an invalid operation might look like when executed. Those questions are useful for understanding faults, but the absence of a fault cannot establish valid C behavior.

#### Check the distinction

| Tempting conclusion | Correct interpretation |
|---|---|
| Declaring `int *p` initializes a valid target. | It declares the pointer object; its value and any target’s value need separate attention. |
| Printing an uninitialized pointer is necessarily harmless. | Evaluating an indeterminate pointer is not a valid inspection technique. |
| If `p` is initialized, `*p` must contain an initialized value. | Initializing an address does not initialize the designated object. |

### 6. Pointer assignment and `scanf`: locate the destination object

**Definition:** Pointer assignment copies an address value; assignment through a pointer changes its target.

**Lecture framing and evidence:** The contrast between `q = p` and `*q = *p` leads directly to the question of where `scanf` stores input. [STT 01:05:59] [M02 slide 14] [M02 slide 15]

**Worked example:** If `p = &i`, both `scanf("%d", &i)` and `scanf("%d", p)` designate `i`.

<a id="sp02-assignment"></a>

The paired diagrams on M02 slides 13–14 make two different effects visible.

With `q = p`, the arrow from `q` changes. Both pointers may then designate the same object. Assigning through either pointer changes that shared target.

With `*q = *p`, the arrows remain where they were. The value read through `p` is stored into the object designated by `q`. [STT 01:05:03] [STT 01:05:59] [M02 slide 13] [M02 slide 14]

This distinction gives the correct interpretation of `%d` input. `scanf` needs a pointer to a suitable `int` object into which it can store the converted value.

| Expression, assuming `int i; int *p = &i;` | Meaning as a `%d` destination |
|---|---|
| `&i` | Address of the integer object |
| `p` | The same destination address |
| `&p` | Address of the pointer object; type `int **`, unsuitable here |

[M02 slide 15]

The lecture’s wrong-`&p` discussion describes how a four-byte write might affect storage reserved for an eight-byte pointer without immediately crossing an OS protection boundary. That is an explanation of a possible machine observation under the stated environment. The call still violates the required destination type and has undefined behavior. [STT 01:09:39] [STT 01:10:34] [STT 01:11:26]

**Exam connection.** The 2024 fall midterm Q1(c) asks students to reason about input directed into pointer storage and subsequent interpretations of that storage. Its provided output predictions must not be treated as portable C guarantees. [EX:sp_2024_2_midterm_q01 p.3]

A disciplined approach is:

1. Identify the actual destination object.
2. Compare its type with the format conversion’s requirement.
3. Establish the language-level validity boundary.
4. Discuss any requested machine observation only under explicit assumptions.

The trap is concluding that writable memory makes every typed operation on it valid. The original variant below instead uses a correctly typed destination while preserving the useful pointer-versus-pointee reasoning.

The first assignment copies an integer value; the second copies an address. The input therefore changes `x`. This original variant practices the destination reasoning relevant to the historical `scanf` question without reproducing its invalid storage manipulation. <a id="8-returned-pointers-and-object-lifetime"></a>

### 7. Returned pointers: follow the target’s lifetime

**Definition:** A returned pointer must designate an object whose lifetime permits its subsequent use.

**Lecture framing and evidence:** Two similar maximum-selection functions differ critically in whether they return an incoming pointer or the address of a local integer parameter. [STT 01:12:20] [M02 slide 16] [M02 slide 17]

**Worked example:** Returning `&a[n/2]` can designate a live element of a caller-owned array when the array and index satisfy the function’s preconditions.

<a id="sp02-lifetime"></a>

M02 slide 16 compares the values reached through two incoming pointers and returns one of those pointer values. The caller’s integers remain the targets. The function’s local pointer parameters can cease to exist without destroying the caller-owned integers. [M02 slide 16]

Slide 17 changes the parameters to integers passed by value and returns the address of one of those local parameter objects. Those objects do not survive the function’s return. The result cannot provide valid subsequent access to them. [M02 slide 17]

The classroom explanation uses stack allocation and reclamation to motivate the distinction. The decisive language-level question is object lifetime, not whether the same bytes remain mapped or happen to contain an old value. The fixed stack-size remark in the transcript must not be generalized into a universal limit. [STT 01:15:22] [STT 01:16:12] [STT 01:17:12]

The middle-element function supplies the constructive alternative:

```c
int *find_middle(int a[], int n)
{
    return &a[n / 2];
}
```

Its intended preconditions are a live array with at least `n` elements and `n > 0`. For positive `n`, `n/2` identifies a valid element; for an even length, it selects the higher-indexed of the two central elements. The lecture explains that this call passes access to the array rather than copying every element. [STT 01:18:48] [M02 slide 18]

The fuller consequences of array parameters on M02 slides 26–29 remain later material.

#### 5. Original variant: modify a caller-owned object through a returned pointer

```c
/* Return a pointer to the larger of two live int objects. */
int *larger(int *a, int *b)
{
    return (*a > *b) ? a : b;
}

int main(void)
{
    int x = 4, y = 9;
    int *chosen = larger(&x, &y);

    *chosen = 12;
    return 0;
}
```

The comparison selects the pointer to `y`, so the final assignment changes `y` to `12`. The local pointer parameters disappear when `larger` returns, but the caller’s integers remain alive. With equal values, this particular comparison selects the second pointer. [M02 slide 16]

| Tempting conclusion | Correct interpretation |
|---|---|
| Returning a local address is safe until the bytes change. | Object lifetime, not leftover bytes, determines whether access is valid. |
| A fixed stack limit applies to every program. | Limits depend on the execution environment and configuration. |

### 8. Pointer arithmetic: movement has a type and a boundary

**Definition:** Pointer arithmetic moves in units of the referenced type. Array expressions often convert to pointers, but the array object retains its own type.

**Lecture framing and evidence:** The final discussion combines element movement, subtraction, comparison, `sizeof`, and the inability to increment an array name. [M02 slide 21] [M02 slide 23] [M02 slide 25]

**Worked example:** Within one suitable array, `&a[5] - &a[1]` gives an element distance of four.

<a id="sp02-arithmetic"></a>

For a valid operation on a pointer of type `T *`, moving by $k$ elements corresponds to:

$$
\text{byte displacement}=k\times\operatorname{sizeof}(T).
$$

This describes the unit of a permitted operation. It does not authorize arbitrary address arithmetic. [M02 slide 20] [M02 slide 21]

The diagram on M02 slide 21 should be read as a sequence:

| Statement | Target of `p` | Target of `q` |
|---|---|---|
| `p = &a[2];` | `a[2]` | Not yet established |
| `q = p + 3;` | `a[2]` | `a[5]` |
| `p += 6;` | `a[8]` | `a[5]` |

Changing `p` later does not move `q`. The assignment to `q` copied a pointer value; it did not create a continuously updated relationship between the variables.

Slide 22 reverses the direction: starting with `p = &a[8]`, `q = p - 3` selects `a[5]`, and `p -= 6` selects `a[2]`. The extracted code and the diagram support the same movement despite the rendered slide’s imperfect code layout. [M02 slide 22]

For pointers to elements of the same array, with a representable result:

$$
p=\&a[i],\quad q=\&a[j]
\quad\Longrightarrow\quad
p-q=i-j.
$$

Thus the result measures elements, not bytes. Subtracting pointers into unrelated arrays is not legitimized by compilation or by the possibility of subtracting their displayed address numbers. [M02 slide 23]

For `p = &a[5]` and `q = &a[1]`, the slide’s `p <= q` is false and `p >= q` is true. However, the blanket wording about “same array” should not be applied identically to `==` and `!=`: equality and relational ordering have different rules. [M02 slide 24]

One-past-the-end formation is also distinct from access. A suitable pointer just beyond the last element can be formed and used as a boundary; it cannot be dereferenced as an additional element.

- `(char *)p + 1` converts first and advances one byte.
- `(char *)(p + 1)` advances one integer first and then converts.

### 9. Arrays, conversion, and `sizeof`

<a id="sp02-arrays"></a>

An array declaration reserves storage for its elements. An ordinary use of the array expression can supply a pointer to the first element, but this conversion does not replace the array object with a pointer object. [M02 slide 25]

For `int a[10]; int *p = a;`, under the lecture’s four-byte-`int`, eight-byte-pointer assumptions:

| Expression | What it denotes or measures | Result or type |
|---|---|---|
| `a` in an ordinary converted expression | Pointer to the first element | `int *` |
| `a+i` | Address of element `i` | Corresponds to `&a[i]` |
| `*(a+i)` | Element `i` | Corresponds to `a[i]` |
| `sizeof(a)` | Entire array | 40 bytes |
| `sizeof(p)` | Pointer object | 8 bytes |
| `sizeof(*p)` | Referenced integer type | 4 bytes |
| `&a` | Pointer to the entire array | `int (*)[10]` |

[STT 01:31:49] [STT 01:32:14] [STT 01:33:06] [M02 slide 25]

`&a` and the first element’s address concern the beginning of the same storage, but they have different pointer types and different referenced units.

Likewise, `int a[] = {1, 2};` is initialization at declaration. It does not imply that a later array assignment is allowed. The invalid `a++` example on slide 25 demonstrates that the array name is not an incrementable pointer variable.

A separate `p` can advance through elements, but the displayed sentinel loop still requires a terminating value within valid bounds. Being able to increment a pointer does not prove that an unbounded traversal is safe.

**Exam connection.** The 2025 spring midterm Q1(a) distinguishes `sizeof` applied to basic objects, a dereference expression, and a string literal. The useful method is **declared type → operand of `sizeof` → applicable size assumptions**. [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01)

This does not make an actual read through an uninitialized pointer valid, nor should it be generalized to every variable-length-type case. The trap is answering “pointer size” whenever a pointer variable appears somewhere in the expression.

#### 6. Original variant: combine element movement, assignment, and size

Assume `sizeof(int) == 4` and the relevant pointer size is eight bytes.

```c
#include <stdio.h>
#include <stddef.h>

int main(void)
{
    int a[6] = {4, 8, 12, 16, 20, 24};
    int *p = a + 1;
    int *q = p + 3;

    *q = *p + 1;

    printf("%d %td\n", a[4], q - p);
    printf("%zu %zu %zu\n",
           sizeof(a), sizeof(p), sizeof(*p));
    printf("%p\n", (void *)q);

    return 0;
}
```

`p` designates `a[1]`, and `q` designates `a[4]`. The assignment stores $8+1=9$ into `a[4]`. Consequently, the first two output lines are determined by the trace and stated size assumptions:

```text
9 3
24 8 4
```

The final address representation is not fixed. The code uses `%zu` for `size_t`, `%td` for `ptrdiff_t`, and `%p` with a `void *` argument for the object pointer. These results were checked through arithmetic and state tracing, not native C execution. [M02 slide 21] [M02 slide 23] [M02 slide 25]

## Key Takeaways

<a id="10-minute-review"></a>

<a id="core-concepts"></a>

This lecture connects readable C programs to the machinery that builds and executes them. Its central habit is to identify what each operation actually acts on: a character value, a state transition, a function declaration, a pointer object, or the object reached through that pointer.

1. **Preserve the complete result of `getchar`.** Store it in `int` so that character values remain distinguishable from `EOF`. The essential issue is the extra outcome beyond the character range; `EOF` is not universally `-1`. [STT 06:35] [STT 07:28] [M01 p.4]
2. **Make character-processing intent visible.** ASCII numbers explain representation, character constants improve readability, and `isalpha`, `isdigit`, and `isspace` express classification directly. [STT 12:25] [STT 13:16] [M01 p.6] [M01 p.9] [M01 p.10]
3. **Count word beginnings.** With states `OUT` and `IN`, increment the counter only when a non-space character causes `OUT → IN`. Repeated spaces and additional characters inside one word must not increase the count. [STT 15:09] [M01 p.12]
4. **Expose the design in the code.** Use meaningful state names, explain what each function accomplishes, and consider unexpected states explicitly. These were lecture-specific expectations, including the importance of function comments for coursework. [STT 25:24] [STT 28:36] [M01 p.17] [M01 p.18]
5. **Separate the four build stages.** Preprocessing produces C source for compilation; compilation produces assembly; assembling produces an object file; linking connects the required implementations. A declaration of `printf` does not supply its definition. [M01 p.21] [M01 p.22] [M01 p.24] [M01 p.25]
6. **Distinguish the pointer from its pointee.** `q = p` changes the address stored in `q`; `*q = *p` copies a value into the object already designated by `q`. This distinction also determines where `scanf` writes. [STT 01:05:59] [M02 slide 14] [M02 slide 15]
7. **Check lifetime and bounds before access.** A returned pointer is useful only while its target remains alive. Pointer arithmetic operates in elements and must remain within the permitted array bounds. [M02 slide 17] [M02 slide 18] [M02 slide 23]
8. **An array is not a pointer variable.** Ordinary array conversion, `sizeof(a)`, `&a`, and the invalid expression `a++` reveal different aspects of the array’s type. [STT 01:32:14] [STT 01:33:54] [M02 slide 25]

#### Practice P01 · One input, different classification rules

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p1"></a>

**Newly authored.** Scope: current character processing and word counting. The ASCII input is `@b5\tC0\n`; each escape sequence denotes one character. Assume the C locale for `ctype.h`. [M01 p.4] [M01 p.6] [M01 p.10–12] [STT 06:35] **General practice — no relevant exam evidence**: advanced Unix I/O candidates are not direct evidence for this elementary classification task.

(a) Count letters, digits, other characters, and words. (b) Explain why EOF must be checked before classification and which type should preserve the result of `getchar()`. (c) In an 8-bit-byte environment, what distinction is endangered by first converting both byte value `0xff` and EOF to `char`? (d) Distinguish passing a buffer element `char ch` to `ctype.h` from passing a checked `getchar()` result.

<details><summary>Detailed solution and grading points · 10 points</summary>

The letters are `b,C`: 2. The digits are `5,0`: 2. The others are `@,\t,\n`: 3. These total 7 characters; EOF is not counted. There are 2 words, `@b5` and `C0`, because a word is a maximal non-whitespace run. A punctuation character such as `@` can belong to a word under this definition.

Preserve the return value in `int c` and classify only when `c != EOF`. All 256 byte values and a separate EOF indication must remain distinguishable; EOF need not be hard-coded as `-1`. Narrowing to `char` first can merge a character with the termination indication or fail to preserve that indication.

C99 requires a `ctype.h` argument to be EOF or a value representable as `unsigned char`. For a general buffer element use, for example, `isalpha((unsigned char)ch)`. A checked `getchar()` result retained as `int` preserves the returned character value; do not narrow it to `char` first. This standards-based clarification does not reconstruct uncertain speech. [C99 TC3 §7.4 and §7.19.7.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)

Grading: character categories and total, 3; word definition and count, 2; EOF and representation argument, 3; `ctype.h` argument domain, 2.

#### Practice P02 · DFA transitions and accepting states

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p2"></a>

**Newly authored.** Scope: current word counting and the slide's integer-shape recognizer, not the complete C integer grammar or recursive pattern matching. [M01 p.11–13] [STT 15:09–19:40] **General practice — no relevant exam evidence**: recursive/string candidates do not share this elementary DFA-tracing objective.

(a) Trace each character of ` go\tgo\n!`, recording state and increment actions. Why is no trailing space needed? (b) Require the **entire input** to match `0` or `[+-]?[1-9][0-9]*`. Classify `0,+7,-20,+0,07,+,7x`. Which of the start, after-sign, after-zero, and after-nonzero-digit states should be accepting? (c) May omitted transitions in the diagram all be filled in as self-loops?

<details><summary>Detailed solution and grading points · 12 points</summary>

Start in `OUT`. The initial space leaves it there. The first `g` enters `IN` and increments to 1; `o` keeps that state. Tab returns to `OUT`; the next `g` enters `IN` and increments to 2, and `o` keeps that state. Newline returns to `OUT`; `!` enters `IN` and increments to 3. Counting entries rather than exits removes the need for a trailing space.

Accept `0,+7,-20`. Reject `+0` because a sign must be followed first by 1–9 under this particular pattern. Reject `07` because the single-zero alternative has extra input, `+` because it lacks a digit, and `7x` because a forbidden character remains.

The start and after-sign states are not accepting. The single-zero state and the state reached after the first nonzero digit accept at end of input. Additional characters after the single zero must be rejected; after a nonzero first digit, only 0–9 may repeat. Merely visiting an accepting state earlier must not cause the whole input `7x` to be accepted.

Transitions must implement the intended language. Treating omitted edges as a complete specification, or arbitrarily filling them with self-loops, can recognize a different language. This answer newly spells out the whole-input rules for the pattern shown on the slide.

Grading: word-count transitions, 4; seven classifications with reasons, 4; acceptance and whole-input condition, 3; interpretation of omitted transitions, 1.

#### Practice P03 · Named states, comments, and error paths

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p3"></a>

**Newly authored.** Scope: current named constants, comments, and defensive programming, plus a **separate C99 verification** of the question left unresolved in class about `const int`. [M01 p.14–18] [STT 31:14–33:09] **General practice — no relevant exam evidence**.

Consider three independent alternatives: `enum { OUT=0, IN=1 };`; macros `#define OUT 0` and `#define IN 1`; and `const int OUT=0, IN=1;`. (a) Which support `case OUT:` in strict C99? (b) Write a purpose-oriented comment for a word-counting function. (c) What is an active `default: assert(0);` intended to detect in `switch(state)`? Should normal whitespace input enter that path? (d) Why can a transition error remain after numeric states are given names?

<details><summary>Detailed solution and grading points · 10 points</summary>

An enumerator is an integer constant, and these macros expand to integer literals, so the first two alternatives work. An ordinary `const int` object's name is not a C99 integer constant expression, so the third cannot directly serve as that case label. Preventing modification and meeting a particular constant-expression rule are different properties. Do not rewrite this independent verification as the conclusion reached during class. [C99 TC3 §6.6 ¶6 and §6.8.4.2](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf)

For example: `/* Count maximal runs of non-whitespace characters in standard input. */` This states the purpose and the definition of a word. Merely saying “increment the variable” describes an implementation step without adequately explaining the function's purpose.

The active assertion exposes a logic error that sends an invalid state value to `default`. Whitespace is normal input and belongs in the transitions of valid states. State validation and input classification are different checks. One assertion does not guarantee detection of every error, or detection when assertions are disabled.

Names improve readability but do not automatically repair an erroneous increment on `IN → IN`. The transition table and boundary inputs still require independent checking.

Grading: three alternatives and C99 reasoning, 4; purpose comment, 2; assertion versus normal-input distinction, 3; readability versus correctness, 1.

#### Practice P04 · Identify what each intermediate file still lacks

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p4"></a>

**Newly authored.** Scope: current build stages and declaration versus definition. [M01 p.21–27] [STT 35:43–45:48] Style evidence: explaining linker roles in [EX:sp_2025_2_midterm_q05 p.12]. Only the need to obtain an external implementation is current scope; relocation-address calculations and PLT/GOT require later prerequisites.

`main.c` declares `int scale(int);` and contains an actual call to `scale(3)`. Its definition, `int scale(int x) { return 2*x; }`, exists only in `helper.c`. (a) Match `main.i,main.s,main.o` and the executable to their producing stages. (b) With no other definition provider, can `main.o` alone complete ordinary executable linking? What does adding `helper.o` resolve? (c) Explain where `gcc -E`, `gcc -S`, and `gcc -c` stop. (d) Why do `gcc800` warning options serve a different role from the linker?

<details><summary>Detailed solution and grading points · 10 points</summary>

Preprocessing produces `main.i` from `main.c`; compilation produces `main.s`; assembly produces `main.o`; linking combines the required object files and libraries into an executable. A declaration provides call-type information but does not create the implementation's body.

Given a remaining actual call and no other provider, `main.o` alone cannot resolve external `scale`. Adding `helper.o` supplies its definition. An object file containing machine language is not evidence that every required external implementation is present.

`-E` stops after preprocessing, `-S` after assembly-language output, and `-c` after object-file generation without linking. The lecture's `gcc800` script bundles warning and rule-checking options. An absence of warnings does not supply a missing function definition.

Grading: four stages and artifacts, 4; declaration/definition and external implementation, 3; three stopping options, 2; warnings versus linking, 1. No later relocation calculation is required.

#### Practice P05 · Trace both the changed object and its lifetime

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p5"></a>

**Newly authored.** Scope: current pointer assignment, `scanf`, and returned-target lifetime. [M02 slide 13–18] Style evidence: state tracing in [EX:sp_2025_2_midterm_q01 p.3](exam_questions/sp_2025_2_midterm_q01) and input-destination diagnosis in [EX:sp_2024_2_midterm_q01 p.3]. Long multi-level-pointer traces and machine-specific outputs of invalid calls are excluded.

Start with `int i=4, j=9; int *p=&i, *q=&j;`, then execute `*q=*p; q=p; *q=7;`. (a) Record values and pointer targets after each statement. (b) If a subsequent `scanf("%d", p)` successfully converts input 12 and returns 1, what changes? How should the alternative `scanf("%d", &p)` be classified? (c) State when the following returned pointers may be used by the caller.

```c
int *choose(int *a, int *b) {
    return *a >= *b ? a : b;
}
int *bad_choose(int a, int b) {
    return a >= b ? &a : &b;
}
```

<details><summary>Detailed solution and grading points · 12 points</summary>

After `*q=*p`: `i=4,j=4,p→i,q→j`. After `q=p`, the integers are unchanged and both pointers target `i`. After `*q=7`: `i=7,j=4`. Copying an address and copying the referenced value are different assignments.

The valid input call writes 12 into `i`, giving `i=12,j=4`. In contrast, `&p` is the address of the pointer object and has type `int **`, not the `int *` required by `%d`. This mismatch is undefined behavior; neither a fixed number nor a guaranteed crash is an answer.

Both arguments to `choose` must point to valid initialized `int` objects. Its returned pointer may be used while its selected target remains alive. The return type alone does not guarantee those conditions. The value parameters of `bad_choose` are separate local objects whose lifetimes end when the function returns. Reading those objects through the returned address is not valid. Apparently retained memory contents provide no guarantee.

Grading: stepwise values and targets, 5; valid-input result, 2; invalid `scanf` type and UB classification, 2; lifetime conditions for both functions, 3. The invalid examples are not to be executed merely to compare observed outputs.

</details>

#### Practice P06 · Declarations, sizes, and permitted boundaries

Synthetic study exercise · not an actual question, official answer, or prediction.

<a id="sp02-p6"></a>

**Newly authored.** Scope: current declarations, array conversion, and pointer arithmetic. Assume `sizeof(int)=4` and 8-byte object pointers for the types used here. [M02 slide 7] [M02 slide 21–25] Style evidence: type-and-size classification in [EX:sp_2025_1_midterm_q01 p.2](exam_questions/sp_2025_1_midterm_q01). Do not generalize these ABI assumptions to all C environments.

```c
int a[4] = {2, 4, 6, 8};
int *p = a + 1, *q = a + 3;
int (*row)[4] = &a;
int *slots[4] = {a, a+1, a+2, a+3};
```

(a) Explain the types of `row,slots`, then find `sizeof(a),sizeof(p),sizeof(*row),sizeof(slots)`. (b) Find `q-p`, and then `*p` after `p+=2`. (c) Independently classify forming `a+4`, reading `*(a+4)`, forming `a+5`, subtracting a pointer into a different array, and `a++`.

<details><summary>Detailed solution and grading points · 12 points</summary>

`row` points to an `int[4]` array; `slots` is an array of four `int *` elements. Parentheses change how `*` and `[]` bind. The sizes are 16, 8, 16, and 32 bytes respectively. `sizeof(*row)` determines the size of a fixed array type rather than performing an ordinary value read.

`q-p=3-1=2` counts elements, not bytes. After `p+=2`, `p=a+3`, so `*p=8`; it now targets the same element as `q`.

Forming `a+4` is permitted as a one-past pointer, but no element exists there to read. Forming `a+5` already violates the arithmetic boundary. Subtraction involving a different array is not a valid array-element distance calculation. `a++` is not permitted because an array is not a modifiable pointer variable. A separate pointer increment also requires checking its resulting position and any later dereference.

Grading: declarations and sizes, 5; distance and value after movement, 2; five boundary classifications with reasons, 5. Plausible numerical addresses do not establish C validity.

</details>
