## Lecture Content and Explanation

### File metadata: what `struct stat` describes

[[concepts/file-metadata|File metadata]] describes a file rather than its contents. The lecture begins by revisiting `struct stat`, emphasizing ownership, hard-link count, protection and file type, file size, and allocated storage. These fields answer different questions: who owns the file, what kind of object it is, how access is controlled, and how its logical size relates to storage allocation. [STT 00:41] [M01 p.3] [M01 p.5]

| Field | Meaning in the lecture | Important distinction |
|---|---|---|
| `st_mode` | File type and protection information | It contains more than access permissions alone. |
| `st_nlink` | Number of hard links | This is a filesystem metadata count, distinct from the open-file reference counts discussed later. |
| `st_uid`, `st_gid` | Owner and group identifiers | These describe ownership rather than the process currently accessing the file. |
| `st_size` | Total file size in bytes | Logical file size is not the number of allocated blocks. |
| `st_blocks` | Number of allocated 512-byte blocks | Multiply by 512 to express this allocation measure in bytes. |
| `st_blksize` | Preferred block size for filesystem I/O | This is a separate quantity from the 512-byte accounting unit of `st_blocks`. |

The distinction between size and allocation matters even before studying particular filesystem layouts. For example, if a hypothetical metadata result contains `st_size = 700` and `st_blocks = 8`, the logical size is 700 bytes, while the reported allocation measure is:

$$
8 \times 512 = 4096\text{ bytes}.
$$

This example illustrates the fields’ units; it does not establish a universal allocation rule. A program should use the field that answers its actual question rather than treating all three size-related fields as interchangeable. [M01 p.5]

### Filenames, directory entries, and inodes describe different relationships

An [[concepts/inode|inode]] represents filesystem information associated with a file. A [[concepts/directory-entry|directory entry]] provides a naming relationship within a directory. The lecture explicitly separates these two ideas: the filename belongs to the containing directory’s information, rather than being a filename field inside the inode. [STT 01:48] [M01 p.4]

This explains why “information about a file” need not all reside in one place. A directory supplies a name through which a file can be found; the inode supplies information about the file reached through that name. The metadata slide uses file type, size, permissions, and timestamps to illustrate the latter role. [M01 p.4]

As a conceptual example, suppose a directory entry associates the name `report` with a particular file. The name answers “which entry should be looked up in this directory?” The inode-related information answers questions such as “what is the file’s size?” Keeping these questions separate prevents a common mistake: assuming that a file’s current name is an intrinsic field of every object used to represent that file.

This distinction provides a **partial connection** to the 2025-2 midterm’s questions about inode link counts and directory references. Those questions require reasoning about which relationships contribute to a count. This lecture establishes the name/inode distinction and identifies `st_nlink`, but it does not fully develop the directory-link counting model required by every subpart. The useful approach is to identify the referenced object before counting relationships; the trap is to count visible names without establishing what each name references. [EX:sp_2025_2_midterm_q03 p.7]

### Data-location pointers: the conceptual role of indirection

The lecture adds a short discussion of how a filesystem locates a file’s data. The supported idea is that location information can involve pointers to data blocks, and that reaching data may require following entries in an intermediate block. This is a conceptual introduction to [[concepts/indirection|indirection]], preserved from the transcript even though the supplied slides do not develop a particular pointer layout. [STT 02:19] [STT 02:32]

The two relationships can be represented schematically:

```text
Direct access:
file-location information -> data block

Indirect access:
file-location information -> block containing pointers -> data block
```

The intermediate block contains information used to locate data. It should not automatically be interpreted as a directory containing filenames. The distinction is about an extra level of reference, not about adding another pathname component.

For example, if one pointer leads directly to a data block, following it reaches the data location immediately. If another pointer leads to a block of pointers, a relevant entry in that block must be followed before reaching the data. This explains the mechanism without assuming any particular number of pointers or maximum file size.

### Choosing a metadata API and anchoring relative names

#### Why an open directory can serve as a reference point

An absolute pathname starts from the filesystem root. A relative pathname is interpreted from a reference directory. The lecture gives `./` and `../` forms as examples; a relative name does not have to begin with either prefix. [STT 03:59]

The directory tree on slide 9 makes the hierarchy concrete. Under `a`, the directory `b` contains `c` and `f`; `c` in turn contains `d`. The slide also shows separate branches containing `seventyfive`, `three`, `seven`, `five`, and `twentytwo`. Its purpose here is to illustrate parent-child relationships, not to establish that every displayed name was spoken. [M01 p.9]

Consider an open directory corresponding to the tree’s `b` node. Relative to that directory:

- `c/d` traverses through `c` to `d`.
- `f` selects the sibling entry beside `c`.

The starting directory is essential to interpreting both names. With `fstatat`, a directory descriptor can provide that starting point for a relative lookup. The later `statter.c` example uses exactly this relationship: an open directory descriptor plus a name returned from that directory. [M01 p.9] [M01 p.11]

The lecturer motivates this design by discussing changes to directories between looking up information and performing another operation. Anchoring operations to an already-open directory helps express which directory is intended even when pathname relationships change. This is an introduction to directory-relative access, not a proof that one `fstatat` call eliminates every race or guarantees that a later operation reaches an unchanged entry. [STT 03:59] [STT 04:54]

### Directory traversal: the `DIR *` lifecycle and the `statter.c` example

A [[concepts/directory-stream|directory stream]] is a library-managed object used to enumerate directory entries. The `DIR *` returned by `opendir` is distinct from the integer descriptor used by descriptor-based interfaces. The lecture stresses this distinction when explaining that the library object has an underlying open directory descriptor. [STT 05:42] [STT 06:28]

The API table on slide 10 describes a lifecycle rather than a collection of interchangeable calls. [M01 p.10]

| Operation | API | Role |
|---|---|---|
| Open a directory stream | `opendir(name)` | Obtain a `DIR *` for enumeration |
| Read an entry | `readdir(dir)` | Obtain the next `struct dirent *` |
| Retrieve the descriptor | `dirfd(dir)` | Obtain the underlying directory descriptor |
| Close the stream | `closedir(dir)` | Finish using the directory stream and close its underlying descriptor |
| Create a directory | `mkdir(pathname, mode)` | Create a directory with a supplied mode argument |

The table also lists `fdopendir` and `mkdirat` as variants. Their names belong to the displayed material, but the recording does not provide a detailed walkthrough of their behavior. The later directory API slide repeats `opendir`, `readdir`, `dirfd`, and `closedir`, reinforcing the same abstraction boundary. [M01 p.10] [M01 p.24]

A useful way to read the lifecycle is:

```text
directory name
    -> opendir
    -> DIR *
    -> repeated readdir calls
    -> closedir
```

When a descriptor-based operation is needed during traversal, `dirfd` supplies the bridge from the library object to its descriptor. It does not turn the `DIR *` itself into an integer or create an unrelated directory traversal. [STT 06:28]

#### Reading the directory code as a sequence of decisions

Slide 11’s `statter.c` combines directory enumeration with metadata lookup. It is particularly important because it explains why the previous APIs belong together. [STT 07:25] [STT 08:15] [M01 p.11]

The opening expression is:

```c
opendir(argc > 1 ? argv[1] : ".")
```

If a directory argument is supplied, the program uses it. Otherwise, it opens the current directory. A `NULL` result leads to an error report and immediate failure. After a successful open, `dirfd(dir)` obtains the descriptor used for subsequent entry-relative metadata requests.

The central lookup is:

```c
fstatat(dd, e->d_name, &sb, 0)
```

Each argument connects to an earlier concept:

- `dd` identifies the directory already opened.
- `e->d_name` supplies the name of an entry returned by `readdir`.
- `sb` receives the metadata.
- The final argument supplies the flags used in this displayed example.

The program therefore does not need to treat each returned name as though it were relative to an unrelated working directory. The open directory and the entry name remain connected. On a successful lookup, the program prints the entry’s name and `st_size`. [M01 p.11]

The sample output contains entries such as `opt`, `sys`, `proc`, `.`, and `..`, together with sizes. Those numbers are results from the displayed run. They are not universal sizes for directories, and the program is not computing the recursive total size of every file beneath each directory.

#### Why the `errno` resets belong to the algorithm

The loop continues while `readdir` returns a non-`NULL` entry. A `NULL` return requires an additional distinction: enumeration may have ended normally, or an error may have occurred. The displayed code uses `errno` to support that distinction. [M01 p.11]

Its sequence is:

1. Set `errno` to zero before enumeration.
2. Read an entry.
3. Attempt `fstatat` for that entry.
4. Report an entry-specific failure or print the metadata.
5. Reset `errno` before the next enumeration call.
6. After `readdir` returns `NULL`, inspect `errno` for an enumeration error.
7. Call `closedir`.

The reset inside the loop prevents an earlier operation’s error value from being mistaken for a later `readdir` failure. For example, suppose one entry’s metadata lookup fails and sets `errno`. If traversal subsequently reaches its ordinary end, a stale error value must not be interpreted as evidence that enumeration itself failed.

This also separates **entry-level failure** from **traversal-level failure**. The displayed program reports an individual `fstatat` failure and continues. Its final return remains `EXIT_SUCCESS` after the traversal path, so an error message does not by itself imply a failure exit status in this teaching example. [M01 p.11]

The lecture compares this cleanup pattern with opening and closing a standard I/O stream. The objects differ, but both require attention to the lifetime of a library-managed resource and its underlying open file. [STT 08:15]

### Kernel file management: descriptor numbers, open-file entries, and vnodes

A [[concepts/file-descriptor|file descriptor]] is an integer used by a process to identify an open resource. Understanding its behavior requires following the references behind that integer.

Slide 13 presents three layers. Read its arrows from left to right: a descriptor-table slot points to an open-file entry, which in turn refers to the file’s in-memory metadata representation. [STT 09:15] [STT 10:13] [M01 p.13]

| Layer | Role in the diagram | Relevant state |
|---|---|---|
| Descriptor table | Associates a process’s descriptor numbers with open-file entries | Per-process descriptor references |
| Open file table | Represents open instances that can be shared | File position and reference count |
| V-node table | Represents in-memory metadata for files | Information such as access, size, and type |

The example connects descriptor 1 to a terminal and descriptor 4 to a disk file. It labels the conventional standard descriptors as 0 for standard input, 1 for standard output, and 2 for standard error. The important mechanism is the reference chain, not the particular numbers chosen for the additional open file. [M01 p.13]

The file position belongs to the open-file entry in this model. Consequently, deciding whether two operations share a position requires identifying whether their descriptors reach the **same open-file entry**. Merely knowing that two descriptors exist, or that they reach the same disk file, is insufficient.

The diagram’s open-file reference count must also be kept separate from `st_nlink`. The former concerns references to an open instance; the latter is the hard-link count reported as file metadata. Similar terminology does not make them the same counter. [M01 p.5] [M01 p.13]

### Independent `open` calls: one file can have multiple positions

An [[concepts/open-file-table|open-file entry]] represents an open instance, rather than merely the identity of a disk file. This distinction explains the lecture’s explicit question about opening the same filename twice: the two calls produce separate open-file entries, each with its own position. [STT 14:07] [STT 15:08]

Slide 14 makes the difference visible. Two descriptor-table arrows lead to two separate open-file entries. Each entry contains its own file position and is shown with reference count 1. Their outgoing arrows converge on the same vnode. [M01 p.14]

```text
descriptor a -> open-file entry A, position A -> same file
descriptor b -> open-file entry B, position B -> same file
```

For a small worked illustration, assume an ordinary file contains `WXYZ`, both opens succeed, and each requested read returns one byte. Reading once through the first open obtains `W` and advances position A. Reading once through the second open also obtains `W`, because position B has not moved.

The shared file contents and the separate positions describe different layers. A common misconception is that opening the same file again must resume wherever the earlier descriptor stopped. The diagram shows why that inference fails.

The lecturer then introduces descriptor duplication as a different operation: it can deliberately make another descriptor refer to an existing open-file entry. That changes the relationship being traced, even though the underlying file might be unchanged. [STT 15:08]

### Sharing across processes: descriptor passing and introductory `fork`

Descriptor numbers are local to a process’s descriptor table. Therefore, [[concepts/file-descriptor-passing|file descriptor passing]] cannot be explained as simply sending an integer to another process. The receiving process needs a descriptor that refers to the intended open-file entry. [STT 11:13] [STT 12:11]

Suppose process A uses descriptor 5. Sending the number `5` as ordinary data does not establish what descriptor 5 means in process B. Actual descriptor passing establishes a reference in B to the shared open-file entry. The resulting descriptor number in B may differ from A’s number; numerical difference is not itself a requirement.

In the lecture’s model, the extra reference increases the open-file entry’s reference count. The shared object—and therefore its position—is the central fact. **Verification needed (검증 필요):** the transcript does not establish the exact messaging API names. #### What the introductory `fork` discussion establishes

The lecturer presents [[concepts/fork|`fork`]] as creating a child process from the current process. Memory is described as conceptually copied, and the child inherits descriptor information. Parent and child then execute independently and can choose different paths based on the result of `fork`. [STT 12:11] [STT 13:09]

For open files, the essential relationship is:

```text
parent descriptor table -> shared open-file entry
child descriptor table  -> shared open-file entry
```

The processes have distinct descriptor tables, while inherited references can lead to the same open-file entry. This is different from claiming that both processes jointly own one descriptor table.

As a conceptual example, suppose a shared open-file entry is positioned before the first byte of `JKLM`. If the parent completes a one-byte read first, the shared position advances. A subsequent one-byte read by the child uses that advanced position. This conditional sequence illustrates sharing; it does not predict which process will run first.

### `dup`: another descriptor for the same open-file entry

[[concepts/dup|Descriptor duplication]] creates another descriptor referring to an existing open-file entry. In particular, `dup(oldfd)` takes one descriptor argument and returns a new descriptor. The two descriptor numbers share the file position because they reach the same entry. [STT 15:08] [STT 21:11] [M01 p.16]

Slide 17 illustrates the operation in two stages:

```c
fd = open("file.txt", O_RDONLY, 0);
fd2 = dup(fd);
```

Assume descriptors 0, 1, and 2 are occupied and every call succeeds. The open obtains descriptor 3. The duplication obtains descriptor 4, the lowest unused descriptor in this example. Both arrows then lead to the same open-file entry, and the displayed reference count changes from 1 to 2. [M01 p.17]

The variable named `fd2` holds the value 4 here. Its name does **not** mean numeric descriptor 2. This distinction also matters in the later examples, where `fd1`, `fd2`, and `fd3` are variable names rather than promises about descriptor allocation.

A read through either duplicated descriptor advances the same position. Closing one descriptor removes that reference; the other descriptor can still provide access to the shared open-file entry. Duplication neither copies the file’s bytes nor creates the independent position produced by another `open`. [STT 18:53] [STT 21:11]

The adjacent API table lists `fileno(FILE *stream)`, which retrieves the descriptor associated with a standard I/O stream. Retrieving an existing descriptor and duplicating a descriptor are different operations. `dup3` is mentioned in the recording as another family member, without a developed explanation of its options. [M01 p.16] [STT 15:08]

#### Why the lowest unused number matters

The lecturer explains an earlier redirection technique using a gap in the descriptor table. Under the stated arrangement, descriptors 0, 1, 2, and 3 are occupied, with 3 referring to the desired output file:

```c

```

After descriptor 1 is closed, it is the lowest unused number. The duplication therefore occupies slot 1 and makes it refer to the same open-file entry as descriptor 3. This reasoning assumes that the calls succeed and no intervening operation occupies the free slot. [STT 18:53] [STT 20:11]

### Read tracing: three opens followed by `dup2`

Slide 19’s `fwfd1.c` combines independent opens with descriptor replacement. Its input file contains `System Programming`. The program opens that file three times, then changes one of the resulting connections. [STT 23:11] [STT 24:11] [M01 p.19]

The essential sequence is:

```c
fd1 = open(fname, O_RDONLY, 0);
fd2 = open(fname, O_RDONLY, 0);
fd3 = open(fname, O_RDONLY, 0);

/* The slide checks the three open results before proceeding. */

dup2(fd2, fd3);

read(fd1, &c1, 1);
read(fd2, &c2, 1);
read(fd3, &c3, 1);
```

For the trace, assume all calls succeed and each read returns one byte. Initially, the three opens produce three independent positions. After `dup2(fd2, fd3)`, the connection previously held by `fd3` is replaced: `fd2` and `fd3` now share one open-file entry, while `fd1` remains independent.

| Operation | Position used | Byte obtained | Position afterward |
|---|---:|---|---:|
| `read(fd1, &c1, 1)` | Independent position 0 | `S` | `fd1`’s position becomes 1 |
| `read(fd2, &c2, 1)` | Shared position 0 | `S` | The `fd2`/`fd3` position becomes 1 |
| `read(fd3, &c3, 1)` | Shared position 1 | `y` | The shared position becomes 2 |

Thus the displayed output is:

```text
c1 = S, c2 = S, c3 = y
```

The first two reads both obtain `S` because they use different open-file entries, each initially at position zero. The third read obtains `y` because the preceding read through `fd2` advanced the entry shared with `fd3`. [STT 25:10] [M01 p.19]

Two mistakes lead to different, incorrect traces. Treating all three opens as sharing a position makes the first reads appear consecutive. Treating `dup2` as another independent open makes the final read appear to restart at zero. Tracking entry identity before tracking positions avoids both errors.

### Write tracing: independent append state and a duplicated nonappend position

Slide 20’s `fwfd2.c` adds an important distinction: one open-file entry writes from its current position, while a separately opened entry uses `O_APPEND`. The lecture walks through the resulting overwrite and append operations. [STT 25:37] [STT 26:36] [STT 27:47] [M01 p.20]

The following excerpt preserves the displayed algorithm while using ordinary C quotation marks:

```c

           S_IRUSR | S_IWUSR);

write(fd1, "CSAP", 4);

fd3 = open(fname, O_APPEND | O_WRONLY, 0);
write(fd3, "M1522", 5);

fd2 = dup(fd1);
write(fd2, "SNU", 3);

write(fd3, "800", 3);
```

Assume a regular file, successful calls, complete writes of the requested lengths, and no other writer. These assumptions define the slide’s trace; the excerpt is not a complete error-handling program.

The first open creates or truncates the file and permits reading and writing. After the first write, the contents are `CSAP`, and the nonappend entry’s position is 4.

The second open creates a different open-file entry for the same file. Its `O_APPEND` behavior places each write at the then-current end of the file. Writing `M1522` extends the contents to `CSAPM1522`, but it does not advance the first entry’s independent position. [STT 25:37] [M01 p.20]

### Binary data and C strings: the special meaning of a zero byte

A [[concepts/c-string|C string]] uses a zero byte as its terminator. Binary data can contain that same byte as ordinary data. Therefore, the end of a C string and the end of a binary payload are different boundaries. [STT 30:28] [M01 p.25]

Consider this small, independently constructed object:

```c
char sample[] = {'A', '\0', 'B', '\n'};
```

The array occupies four bytes. Interpreted as a C string, it ends at its second element, so `strlen(sample)` is 1. The remaining `B` and newline are still part of the array object; the string-length operation does not count them.

```text
Array extent:       A | NUL | B | LF
C-string content:   A
```

The same distinction affects copying. A string-copy operation follows a terminator-based contract rather than an explicit binary-payload length. It is therefore unsuitable as a general replacement for copying a specified number of bytes. [M01 p.25]

The statement that a string function can still execute on some binary content is not a universal safety guarantee. A string operation requires a valid string within accessible storage. If that requirement is absent, searching for a terminator can exceed the object’s bounds. The safe lesson is to retain an explicit length for arbitrary binary data instead of inferring its extent from the first zero byte.

## Key Takeaways

- **Identify the relationship being measured.** A filename, an inode’s hard-link count, and an open-file entry’s reference count describe different relationships. [M01 p.4] [M01 p.5] [M01 p.13]
- **Keep the directory and its entry names connected.** `readdir` supplies names; `dirfd` and `fstatat` allow those names to be interpreted relative to the directory already opened. [M01 p.11]
- **Track open-file entries before tracking offsets.** Independent `open` calls have separate positions; duplicated or inherited references can share one position. [M01 p.14] [M01 p.17]
- **Redirection changes a connection.** `dup2(oldfd, newfd)` changes what `newfd` references. A program can continue using descriptor 1 after its output destination changes. [M01 p.18]
- **Overwrite and append are distinct operations.** In slide 20, the duplicated nonappend entry overwrites three existing bytes, while the independent append entry writes at the current EOF. [M01 p.20]
- **Choose an interface by its contract.** Integer descriptors, `FILE *`, and `DIR *` represent different interfaces; their functions are not interchangeable. [M01 p.22] [M01 p.23] [M01 p.24]
- **Preserve explicit binary lengths.** Newline and NUL bytes can be ordinary payload data. Text-line boundaries and C-string termination do not determine an arbitrary binary record’s extent. [M01 p.25]
- **Keep evidence boundaries visible.** Slide-based calculations clarify the note; they do not recover uncertain speech, establish unseen quiz questions, or complete deferred implementation topics.

#### Practice P05 — Allocate into gaps

A fictional format defines each record as exactly six bytes. One record is:

```text
41 0A 00 42 0D 0A
```
