## Lecture Content and Explanation

### Byte-addressed memory and the need for Virtual Memory

In the course’s basic model, memory is a large array of bytes, and an address identifies a position in that array. A load transfers memory contents into a register; a store transfers a register’s contents to memory. The opening slide illustrates these operations with `ld` and `sd`. This abstraction lets a programmer reason about addresses without first deciding which physical memory module contains the data. [M03 p.4] [STT 01:07]

An address’s representational range is different from the amount of installed DRAM. A full 64-bit byte-address space contains

$$
2^{64}\text{ bytes}=16\text{ EiB}.
$$

This is the binary quantity described approximately as “16 exabytes” in the slides. It does not mean that a machine has that much RAM, that a process uses every address, or that every representable pointer value is valid to dereference. The lecture motivates this distinction through familiar machines with tens of gigabytes of memory and the practical difficulty of expanding their physical capacity. The instructor contrasts the difficulty of upgrading laptop memory with replacing memory modules on a desktop PC motherboard. [STT 02:52] The laptop and desktop discussion supplies motivation, rather than a specification for all computers. [M03 p.5] [STT 01:55] [STT 02:52]

Memory management must also accommodate multiple processes. Each process has instructions and data organized into regions such as `.text`, `.data`, heap, and stack. The earlier layout figure places executable code and read-only data separately from writable global data, the run-time heap, and the user stack. Its arrows describe a process’s virtual layout; they do not require those regions to occupy matching contiguous regions of physical RAM. [M01 p.11] [M03 p.6] [STT 03:50]

For example, two processes can each have a stack and a variable called `counter`. The operating system must arrange their storage while preventing one process from freely accessing the other’s private data. Yet cooperating processes may need access to a common object. Thus **protection and sharing are simultaneous requirements**: isolation by default must coexist with deliberately shared regions. [M03 p.7] [STT 04:48]

[[concepts/virtual-memory|Virtual Memory]] addresses these requirements by separating the process-visible memory abstraction from its physical implementation. ### Indirection: separating an address from its physical destination

[[concepts/indirection|Indirection]] inserts a mapping between a name or address used by a client and the underlying resource that implements it. For memory, the process uses a **Virtual Address (VA)**, while the mapping mechanism determines the corresponding **Physical Address (PA)**. Changing the mapping can change physical placement without requiring the process to use a different addressing model. [M03 p.8] [M03 p.10] [M03 p.11]

The lecture develops this idea through a networking analogy. Heterogeneous local networks can use different addressing schemes, while the IP layer provides a common addressing framework above them. The instructor distinguishes IP addresses from the 48-bit MAC addresses associated with NICs. The useful connection is the separation between an upper-level address and a lower-level delivery mechanism; the analogy does not imply that memory translation and network forwarding use identical algorithms. [STT 05:47] [STT 06:46]

The slide’s indirection figure shows several private virtual memory spaces feeding into a common mapping mechanism and physical memory. “Private” describes the process’s address-space view. It does not prohibit selected mappings from reaching shared physical storage. A process ordinarily operates within its own memory space, while explicitly established shared regions permit cooperation. [M03 p.8] [STT 07:47]

The virtual-machine comparison makes a related point about abstraction: a logical machine can provide a useful machine interface even though its implementation depends on an underlying physical machine. Similarly, virtual memory provides addressable storage through translation. “Virtual” therefore does not mean that the program’s data are imaginary or that accesses need no physical implementation. [STT 08:47] [STT 09:46]

A simple conceptual example is a process that accesses a variable through VA `4100`. The VA alone does not identify its physical location; the process’s mapping must be consulted. The transcript’s incomplete numerical translation at this point is **검증 필요**, so no particular PA is attributed to that opening example. [STT 10:25] [STT 10:55]

### Pages and the VPN-to-PPN mapping

A [[concepts/page-table|page table]] records mappings at **page** granularity. Instead of independently relocating every byte, the system divides virtual and physical memory into pages and translates the page number while retaining the location within the page. The lecture gives 4 KiB as the ordinary example and mentions larger 2 MiB and 1 GiB pages. These sizes belong to the examples being discussed; they are not interchangeable within a single calculation. [STT 11:52] [M03 p.21]

For a page size $PS$, an address separates into a **Virtual Page Number (VPN)** and a **Virtual Page Offset (VPO)**:

$$
VPN=\left\lfloor\frac{VA}{PS}\right\rfloor,
\qquad
VPO=VA\bmod PS.
$$

In the simplified table model, the VPN selects an entry, and the entry supplies a **Physical Page Number (PPN)**. One such record is a **Page Table Entry (PTE)**. [M03 p.12] [M03 p.15] [STT 12:46]

The mapping figure gives examples including:

| VPN | PPN |
|---:|---:|
| 0 | 2 |
| 1 | 1 |
| 2 | 5 |
| 5 | 9 |
| 6 | 0 |

The colored pages in the adjacent figure make the essential point visible: virtual ordering need not match physical ordering. Virtual page 0 can reside in physical page 2, while virtual page 6 resides in physical page 0. Pages that appear adjacent in a process’s address space need not be adjacent in physical memory. [M03 p.12] [M03 p.13]

A page table therefore answers a mapping question, not a question about the value stored in an ordinary program variable. Looking up VPN 2 and obtaining PPN 5 does not return the data requested by the program. It identifies the physical page from which those data can subsequently be accessed.

### Translating `0x233`: page number, page base, and offset

The lecture’s toy translation uses **256-byte pages**, so $PS=\texttt{0x100}$. This small model should remain separate from the later Core i7 example with 4 KiB pages. [M03 p.14] [STT 13:47]

For VA `0x233`:

$$
VPN=\left\lfloor\frac{\texttt{0x233}}{\texttt{0x100}}\right\rfloor=2,
\qquad
VPO=\texttt{0x233}\bmod\texttt{0x100}=\texttt{0x33}.
$$

The page table maps VPN 2 to PPN 5. Physical page 5 begins at

$$
5\times\texttt{0x100}=\texttt{0x500}.
$$

Adding the unchanged offset gives

$$
PA=\texttt{0x500}+\texttt{0x33}=\texttt{0x533}.
$$

The figure shows a marked position inside virtual page 2 and the corresponding position inside physical page 5. The page changes, but the relative position inside it does not. Offset preservation here depends on the equal virtual and physical page sizes assumed by the model. [M03 p.14] [STT 14:24] [STT 15:22]

Two printed expressions require **note-side qualifications**:

- On page 14, masking `0x233` with `0xF00` produces `0x200`, not the integer page number 2. For the depicted address, `(0x233 & 0xF00) >> 8` produces 2. Masking isolates a field; shifting moves that field into the position needed to interpret it as a number.
- On page 15, `PT` is defined as a VPN-to-PPN table, but the displayed PA expression omits multiplication by the page size. If `PT` returns a page number, the consistent formula is:

$$
PA=
PT\!\left[\left\lfloor\frac{VA}{PS}\right\rfloor\right]\times PS
+(VA\bmod PS).
$$

If a differently defined table returned a **physical page base address**, its result could instead be added directly to the offset. These two table conventions must not be mixed. [M03 p.14] [M03 p.15]

The transferable method is to determine the fields and then check the entry’s state before accepting a physical mapping. ### MMU, PTBR, CR3, and the cost of translation

The **Memory Management Unit (MMU)** is the hardware that performs address translation. The page table is a data structure stored in main memory and maintained by the operating system. These are cooperating components, not two names for the same object. [M03 p.16] [STT 17:16]

The **Page Table Base Register (PTBR)** identifies where the relevant page-table structure begins. In the Intel example, the corresponding register is **CR3**. The figure places the page table inside physical memory and shows the MMU holding its starting address. It does not depict the entire page table stored inside one register. [M03 p.16] [STT 18:05]

Translation is on the path of ordinary memory access. If accessing one program value repeatedly required several additional accesses to page-table memory, the cost would be substantial. A [[concepts/tlb|Translation Lookaside Buffer (TLB)]] reduces that overhead by caching translation information for recently useful pages. A TLB hit supplies a cached translation without repeating the full page-table lookup. [STT 19:02] [STT 19:55]

For example, accesses to two different bytes within one virtual page have the same VPN. Once that page’s translation is cached, another access within the page may reuse it. Their offsets differ, but their page mapping does not. Whether the requested **data** are also cached is a separate question.

The lecture’s performance argument concerns avoided translation work. It does not establish a numerical TLB hit rate. The uncertain frequency wording in the transcript remains **검증 필요**.

The 2024–2 midterm Q4(f) asks for the TLB’s purpose. A complete explanation connects the stored information to the avoided operation: cached page translations reduce repeated accesses to the process’s page table. Saying only that a TLB is “fast memory” omits the relevant mechanism, while describing it as a cache of program data confuses two different caches. [EX:sp_2024_2_midterm_q04 p.9]

### Memory hierarchy, storage technology, and remote-storage exceptions

A [[concepts/memory-hierarchy|memory hierarchy]] combines storage technologies with different capacities, costs, and access times. The hierarchy figure places registers at the top, followed by SRAM CPU caches, DRAM main memory, local secondary storage, and remote secondary storage. Moving downward generally increases capacity and decreases cost per byte, while access becomes slower. [M03 p.17]

The figure uses two numbering systems. Its broad hierarchy levels include registers, DRAM, and storage, while **L1/L2/L3 cache** names refer specifically to CPU cache levels. The diagram’s hierarchy label “L3” beside main memory does not turn DRAM into the CPU’s L3 cache.

The lecture’s comparisons include cycle-scale register/cache operations, roughly tens of nanoseconds for DRAM, microsecond-scale SSD access, and millisecond-scale HDD access. These are illustrative orders of magnitude from the lecture, not measurements or universal latency guarantees. HDDs have mechanical seek and rotational delays; SSDs remove those mechanical operations but still have access costs. [STT 19:55] [STT 20:56] [STT 23:48] [STT 24:46]

The motivation for a hierarchy follows directly. Storing everything in registers or SRAM would be prohibitively expensive and difficult to scale. A system instead uses a small amount of fast storage to serve useful portions of a much larger memory and storage system.

The instructor extends the slide with **compute/storage disaggregation**. A compute node supplies CPU and memory, while storage is consolidated elsewhere and reached over a network. The OS can see a disk-like interface even though the actual I/O crosses the network. The stated operational motivations are easier centralized maintenance, replacement, and capacity adjustment. [STT 22:55] [STT 23:48]

This leads to a lecture-specific qualification: local storage is not invariably faster than remote storage. A sufficiently capable network and remote storage service can outperform a slower local device. The hierarchy is therefore a useful design pattern, not an absolute ordering of every possible device. ### Temporal and spatial locality in data and instructions

[[concepts/locality|Locality of reference]] describes patterns that make a small fast cache useful.

**Temporal locality** is the tendency to reuse recently accessed items. **Spatial locality** is the tendency to access nearby addresses close together in time. The instructor explicitly treats these as tendencies that depend on the program, rather than guarantees for every access stream. [M03 p.18] [STT 26:35]

The slide’s array-sum loop connects both forms of locality to concrete operations:

```c
sum = 0;
for (i = 0; i < n; i++)
    sum += a[i];
return sum;
```

For this illustration, assume that the array has at least `n` accessible elements and that the arithmetic remains within the chosen type’s range.

- `sum` is used repeatedly across iterations: temporal locality.
- Consecutive array elements are visited in succession: spatial locality.
- The loop’s instructions execute repeatedly: temporal locality in instruction access.
- Instructions within a sequential part of the loop occupy nearby addresses and execute in sequence: spatial locality in instruction access. [M03 p.18] [STT 27:33] [STT 28:34] [STT 29:32]

Reading each array element only once does not eliminate locality. Reuse of the same element is unnecessary for spatial locality; nearby elements can benefit from being brought into a cache together. Conversely, the repeated source-level use of `sum` does not imply that every iteration loads it from DRAM. The compiler may retain it in a register.

The code is supported by the slide. It is not a reconstruction of the transcript’s garbled code-reading fragments.

A **cache** stores a subset of data from a larger, slower level. Locality explains why that subset can satisfy many requests. A program may have a large total address space while repeatedly using a much smaller group of instructions and data. [M03 p.19] [STT 30:31]

The course applies this relationship broadly: registers hold values obtained from the memory hierarchy, main memory holds data associated with storage, and local storage can hold files obtained remotely. The general model is that level $k$ caches useful contents from level $k+1$. Its benefit depends on the access pattern; simply adding a cache does not guarantee that a workload will use it effectively. [STT 31:27]

### Cache blocks, transfer granularity, hits, and misses

A **cache block**, or **cache line** in the CPU-cache discussion, is a unit stored and transferred by the cache. The block-transfer figure shows level $k$ holding blocks 4, 9, 10, and 3 from a larger level containing blocks 0 through 15. The upper level contains a subset, and movement between levels occurs in block-sized units. [M03 p.20]

Fixed-size blocks simplify management, making them suitable for fast hardware structures. Variable-size cached objects can use storage efficiently but require more complicated management. The lecture uses a web image stored as a whole object as a variable-size example. [M03 p.21] [STT 32:27] [STT 33:27]

Transfer sizes differ across the hierarchy. The course examples include an 8-byte register word, a 64-byte CPU cache line, a 4 KiB memory page, and an entire remotely obtained file. A larger transfer can help amortize a slow device’s access-start cost. However, address width alone does not dictate line size: a 64-bit CPU does not imply a universal 64-byte cache-line rule. Nor is a 64-byte line the total capacity of the cache. [M03 p.21] [STT 34:27] [STT 35:28]

A **hit** occurs when the requested block is present in the cache being considered. A **miss** occurs when it is absent there. In the source figure, requesting block 10 hits at level $k$, whereas requesting block 13 misses there but can be satisfied at level $k+1$. Thus hit or miss is always relative to a particular level. [M03 p.22] [STT 35:28]

After a miss, two decisions arise:

1. **Placement:** which location may hold the incoming block?
2. **Replacement:** if an eligible location is occupied, which existing block should be evicted?

These decisions are related but different. Knowing where a block is allowed to go does not necessarily determine which resident block should leave. [STT 36:23]

### Compulsory, capacity, and conflict misses

The lecture distinguishes three explanations for cache misses. [M03 p.23]

A **cold**, or **compulsory**, miss occurs because a block has not previously been brought into the cache through an earlier access. The first execution of a code region or the first traversal of an array supplies an intuitive example. It is not evidence that the cache is too small. [STT 36:23] [STT 37:23]

A **capacity miss** arises when the active collection of blocks, the **working set**, cannot fit in the cache. The lecture contrasts a 1200-byte array with a 1000-byte cache. If the computation repeatedly needs more of the array than the cache can retain, previously loaded blocks must be fetched again. The capacity comparison explains the pressure, but the exact miss count still depends on access order, block size, and replacement policy. [STT 37:23] [STT 38:15]

A **conflict miss** results from placement restrictions. Suppose a cache has four slots and block $i$ must occupy slot $i\bmod4$. Then

$$
0\bmod4=8\bmod4=0.
$$

If slot 0 can hold only one block, the sequence `0, 8, 0, 8` behaves as follows:

| Access | Previous contents of slot 0 | Result | New contents |
|---:|---|---|---|
| 0 | Empty | Compulsory miss | 0 |
| 8 | 0 | Compulsory miss; evict 0 | 8 |
| 0 | 8 | Conflict miss; evict 8 | 0 |
| 8 | 0 | Conflict miss; evict 0 | 8 |

Other slots cannot help because these two blocks are restricted to slot 0. The mapping simplifies the search location but can cause repeated displacement. [M03 p.23] [STT 38:15] [STT 39:15] [STT 40:13]

The **single-slot assumption is essential**. This example is effectively direct mapped. In a set-associative cache with enough ways in that set, blocks 0 and 8 could coexist. The transcript’s broad use of “set associative” must not be interpreted as saying that every associativity produces the same thrashing trace.

### Optimal replacement and LRU: prediction from access history

A replacement policy chooses a victim when a new block needs occupied space. The conceptual **optimal policy** evicts a block that will never be used again, or otherwise the block whose next use lies furthest in the future. This provides a useful ideal, but arbitrary program behavior depends on branches and inputs, so future accesses are generally unavailable to an online replacement mechanism. [M03 p.24] [STT 41:06] [STT 41:55]

[[concepts/lru|Least Recently Used (LRU)]] uses past access order as a predictor. It evicts the block whose most recent access is oldest. Its assumption is that recently used items are more likely to be needed again soon. The instructor describes LRU as effective for many ordinary access patterns while acknowledging that this prediction can be wrong. That observation is not a proof that LRU is optimal for every workload. [STT 42:45] [STT 43:47]

The classroom queue discussion gives a concrete implementation model. With the most recently used item at the tail:

- Add a newly admitted item at the tail.
- On a hit to an existing item, move that item to the tail.
- When a victim is needed, remove the item at the head.

The head/tail convention could be reversed, provided insertion, access updates, and eviction remain consistent. [STT 44:10] [STT 46:30]

For a new illustrative trace, suppose a three-block cache contains `A, B, C` from least to most recently used. Accessing `A` changes the order to `B, C, A`. If `D` then arrives, LRU evicts `B`, leaving `C, A, D`.

If the order were updated only when blocks entered the cache, it would track arrival order instead. That is FIFO behavior, not LRU. **Updating recency on hits is the specific point the instructor emphasizes in the clear follow-up explanation.** [STT 46:30]

Several intervening student responses and queue-operation phrases are **검증 필요**. They do not establish a particular student answer, a specific deque implementation, or exact pointer-manipulation instructions.

### Why exact LRU is expensive, and how second chance approximates it

The difficulty with exact LRU is not its definition but the cost of maintaining the required order. Every relevant access can change recency. Even at page granularity, reading or writing a variable on a page may require updating that page’s position. A straightforward queue implementation entails bookkeeping that can be excessive on a time-critical memory-access path. [STT 47:17] [STT 48:15]

The lecture introduces a cheaper hardware contribution: an **access bit**, also called a **reference bit**, associated with a page. Hardware marks the page as referenced when it is accessed. Software can later inspect and clear that bit. A single bit records less information than a complete recency ordering, but is cheaper to update. [STT 49:15]

The [[concepts/page-replacement|clock or second-chance algorithm]] scans candidate pages:

1. If the reference bit is 0, select the page as a victim.
2. If the reference bit is 1, clear it to 0 and give the page another chance.
3. Continue scanning. An intervening access can set a cleared bit back to 1. [STT 50:15] [STT 51:15]

For example, let the scan begin at page A with reference bits `A=1`, `B=1`, and `C=0`, and assume no accesses occur during this short scan. A receives another chance and becomes 0; B receives another chance and becomes 0; C is selected for eviction.

A reference bit of 0 means that the page lacks a recorded reference since the relevant clearing point. It does not mean the page has never been used. Likewise, two pages with bit 1 are not ordered by recency. **Second chance approximates LRU; it does not preserve exact LRU information.**

### Different cache levels have different managers

The lecture assigns responsibility according to the level being managed. [M03 p.25]

| Storage being managed | Main manager in the lecture model | Relevant decision |
|---|---|---|
| Registers | Compiler | Which values remain in registers |
| CPU L1/L2/L3 caches | Hardware | Where blocks are searched for, admitted, and replaced |
| Main memory as a cache for storage | Operating system | Which pages remain resident and which are reclaimed |

Compiler **register allocation** uses code analysis to reduce unnecessary memory traffic. For example, retaining a loop accumulator in a register avoids repeatedly retrieving that value from lower levels. CPU cache hardware instead needs fast lookup mechanisms, such as selecting a set from address bits. [STT 51:15] [STT 52:12]

The OS can justify more substantial page-management work because avoiding a slow storage access can save far more time than the management consumes. The lecture’s millisecond-versus-nanosecond comparison motivates that tradeoff; it does not specify one universal storage-to-memory latency ratio. [STT 53:10] [STT 54:08]

The use of a fixed hardware lookup structure also does not mean every memory operation has the same latency. A hit, a lower-level miss, and a page fault still have very different consequences.

### Address-space scale, multilevel tables, and avoiding duplication

The cost of translation includes storage for the mapping structures themselves. Under the full 64-bit byte-address model with 4 KiB pages:

$$
\frac{2^{64}}{2^{12}}=2^{52}
$$

possible virtual pages exist, approximately $4.5\times10^{15}$. The slide contrasts this scale with a much smaller physical memory. Its 4 GiB physical-memory illustration contains $2^{20}$ pages of 4 KiB each. [M03 p.30]

The later Core i7 teaching model uses a **48-bit VA**, not all 64 bits, and a 12-bit page offset:

$$
48-12=36\text{ VPN bits}.
$$

Consequently,

$$
2^{48}\text{ bytes}=256\text{ TiB},
\qquad
\frac{2^{48}}{2^{12}}=2^{36}\text{ possible virtual pages}.
$$

The address-space size is measured in bytes; the page count is a separate quantity. The transcript’s numerical self-correction around this distinction remains **검증 필요** and should not be taught as “256 trillion pages.” [STT 57:02] [STT 58:01]

A flat table with one entry for every possible VPN would require $2^{36}$ entries. As a **derived illustration**, assuming 8 bytes per entry gives

$$
2^{36}\times8=2^{39}\text{ bytes}=512\text{ GiB}.
$$

That result is a calculation added to explain the scale problem, not a number attributed to the instructor’s speech. A small program such as `ls` or `cat` should not require a fully populated mapping array of that size. This motivates a [[concepts/multilevel-page-table|multilevel page table]], whose structure can represent used regions without requiring one enormous flat array for the entire possible space. [STT 58:01] [STT 58:57] [STT 59:51]

The same engineering discussion includes avoiding unnecessary duplication. Many processes use common library functionality such as `printf`; maintaining separate physical copies of every common library page would waste memory when sharing is appropriate. [M03 p.30] [STT 59:51]

**Lazy copy** and **copy on write (COW)** are named and deferred for later explanation. Their appearance does not establish that the full COW mechanism was taught in this recording. ### On-demand paging and recoverable page faults

[[concepts/demand-paging|On-demand paging]] allows a needed page to be brought into physical memory when an access requires it. When active programs demand more resident memory, some contents can be kept on storage instead of occupying DRAM continuously. This permits continued execution with a smaller resident physical footprint, although accessing nonresident data is expensive. [M03 p.31] [STT 01:00:47] [STT 01:01:21]

The paging figure revisits VA `0x233`, but with a **different mapping state** from the earlier translation example. Process A’s VPN 2 is now marked as paged out, with disk index 0 in the teaching diagram. It does not currently provide the resident VPN-2-to-PPN-5 mapping used earlier. [M03 p.31] [STT 01:02:15]

The lecture describes the recovery sequence:

1. An instruction accesses the nonresident page and triggers a page fault.
2. The process cannot complete that access immediately.
3. The OS obtains a suitable physical frame, reclaiming pages if necessary.
4. The needed contents are read from storage into physical memory.
5. The mapping information is updated.
6. The faulting instruction is executed again and can now access the resident page. [STT 01:03:13] [STT 01:04:09]

The lecture mentions a clock-like replacement approach and notes that reclamation can free enough pages to relieve pressure, rather than necessarily evicting exactly one page. This describes the taught mechanism and motivation, without establishing the precise implementation of every current OS. [STT 01:03:13] [STT 01:05:06]

A [[concepts/page-fault|page fault]] is therefore not automatically a fatal error. In this example it is a recoverable event used to obtain valid data that are temporarily nonresident.

### Clean file-backed pages and dirty data have different eviction costs

Choosing a victim does not automatically require writing its contents to disk. A **clean file-backed page** contains an unchanged copy of data available in a file. Its resident copy can be discarded because the same contents can be read again later. [STT 01:05:06] [STT 01:05:59]

| Page state | Consequence of discarding its RAM copy |
|---|---|
| Unmodified copy of existing file contents | The file can supply those contents again |
| Contains modifications absent from its backing storage | Discarding without preservation would lose changes |

The second page’s modified, or **dirty**, contents must be preserved appropriately before its physical storage can be reused. The lecture explains this through writing modified data to disk. [STT 01:05:59]

### TLB lookup: VPN, tag, set index, and ways

The end-to-end figure assumes a 48-bit VA and 4 KiB pages. Its initial split is:

$$
VA=\underbrace{VPN}_{36\text{ bits}}
\;\Vert\;
\underbrace{VPO}_{12\text{ bits}},
$$

where $\Vert$ denotes concatenation. The 12-bit offset selects a byte within a $2^{12}$-byte page. [M03 p.40] [STT 01:21:26]

For the depicted L1 TLB, the 36-bit VPN is divided into:

- **TLBI:** a 4-bit TLB set index.
- **TLBT:** a 32-bit TLB tag.

Four index bits select one of $2^4=16$ sets. Each set has four ways, giving

$$
16\times4=64\text{ entries}.
$$

The set index identifies where to search; tag comparison identifies whether one of that set’s valid entries represents the requested translation. Four-way associativity means that up to four translations assigned to the set can reside there simultaneously. [M03 p.40] [STT 01:22:13] [STT 01:23:13] [STT 01:23:55]

For a new numerical illustration, let the VPN be `0x12345`. Under this figure’s split:

```text

TLBT = VPN >> 4  = 0x1234
```

The lookup searches set 5 for a valid matching tag `0x1234`. A valid matching entry supplies the PPN. The fact that several entries occupy set 5 does not make all of them matches.

### A TLB miss leads to a page-table walk, not necessarily a page fault

If the translation is absent from the TLB, the depicted mechanism uses the page tables. The 36-bit VPN supplies four 9-bit indices:

$$
36=9+9+9+9.
$$

Starting from CR3, the walk uses successive indices to select entries leading toward the final mapping. Each 9-bit index can select among 512 entries. Once the translation has been obtained, it can be cached in the TLB for later accesses to the page. [M03 p.40] [STT 01:25:41]

A **TLB miss** means the translation cache did not provide the mapping. A **nonresident-page fault** means that the requested page is not currently available in physical memory in the relevant mapping state. These conditions must be checked separately.

For example, suppose the TLB has no matching valid entry, but the page-table walk finds a permitted resident mapping. The translation is obtained without reading the page from disk. The TLB can be refilled, and the data access can proceed.

### Physical data-cache lookup and the complete address path

After translation, the depicted 40-bit PPN combines with the unchanged 12-bit offset:

$$
PA=\underbrace{PPN}_{40\text{ bits}}
\;\Vert\;
\underbrace{PPO}_{12\text{ bits}},
\qquad PPO=VPO.
$$

This gives a **52-bit physical address in the supplied example**. It identifies the data’s physical location, but retrieving the data may still be satisfied by a CPU cache. [M03 p.40] [STT 01:26:40]

The L1 data cache splits that physical address into:

| Field | Width | Function |
|---|---:|---|
| CT | 40 bits | Compare the physical tag within the selected set |
| CI | 6 bits | Select one of 64 sets |
| CO | 6 bits | Select a byte position within a 64-byte line |

Each set has eight ways. The data capacity is therefore

$$
64\text{ sets}\times8\text{ lines/set}\times64\text{ bytes/line}
=32768\text{ bytes}
=32\text{ KiB}.
$$

This calculation concerns stored data bytes; it does not count tag and other metadata storage. [M03 p.40] [STT 01:27:34]

A line contains 64 bytes, but a program need not request all 64 at once. The lecture uses a character-sized access to motivate the byte offset. CO identifies the relevant position within the selected line; it is not the set index or the physical page number. An L1 miss sends the request toward L2, L3, and main memory as shown in the figure. - VA is `0x000012345ABC`.
- VPN `0x12345` has a valid, readable translation to PPN `0x2F`.
- The access reads one byte.
- The selected data-cache set contains a valid line with the required physical tag.

The address decomposes as follows:

$$
VPN=\texttt{0x12345},
\qquad
VPO=\texttt{0xABC}.
$$

The TLB fields are the previously derived set index `0x5` and tag `0x1234`. Translation produces

$$
PA=\texttt{0x2F}\times\texttt{0x1000}+\texttt{0xABC}

$$

The data-cache fields are then:

```text
CT = PA >> 12          = 0x2F
CI = (PA >> 6) & 0x3F = 0x2A
CO = PA & 0x3F        = 0x3C
```

## Key Takeaways

- **An address-space size is not a DRAM requirement.** Representable addresses, valid mappings, and resident pages are different quantities.
- **Translation changes the page number while preserving the offset under the stated equal-page-size model.** A PPN must be converted to a page base before adding that offset.
- **The MMU, page table, CR3, and TLB have distinct roles.** A TLB caches translations; a data cache stores contents.
- **Locality makes small fast storage useful, but does not guarantee a particular hit rate.** Placement restrictions, working-set size, and access order still matter.
- **LRU tracks accesses, including hits.** Second chance records less information and approximates recency.
- **Sharing depends on physical destinations.** Equal virtual addresses do not prove sharing, and different virtual addresses do not prevent it.
- **Nonresidency and permission failure require different reasoning.** Clean file-backed data may be discarded and reread; modified data need preservation.

<details><summary>Worked answer and grading points</summary>

The requested page is nonresident, so the access triggers a page fault and cannot complete until the required contents become resident.

The OS obtains a frame, preserves any victim contents that require preservation, reads the requested page, updates the mapping, and permits the faulting instruction to be retried.

After recovery, the mapping identifies the resident contents and the read is permitted by the scenario’s assumptions. The same instruction can therefore complete its access. This is recoverable nonresidency, not a reason to conclude that every fault must terminate the process.

**Grading points:** Identify the nonresident-page fault; acquire a frame with necessary victim preservation before reuse; include page-in and mapping update before retry; explain why the permitted access can then succeed.

</details>

#### Practice P13 — A new end-to-end translation and cache lookup

**Newly authored synthetic exercise — not an actual past question or official answer**

**Scope:** LO32–LO34: address fields, TLB lookup, resident-page fallback, PA construction, and data-cache lookup. [M03 p.40] [STT 01:24:41] [STT 01:25:41] [STT 01:27:34]  
**Required skill:** Derive fields from dimensions and make separate hit/fault decisions.  
**Prerequisites:** Binary/hexadecimal, powers of two, associativity, valid bits, and page offsets.  
**Access:** Currently approachable under this simplified model.  
**Style basis:** The field and validity judgments transfer the structure of 2025–1 midterm Q4; the connected translation-to-data chain transfers 2025–2 midterm Q4. All dimensions, addresses, entries, and byte contents below are new. [EX:sp_2025_1_midterm_q04 p.11] [EX:sp_2025_1_midterm_q04 p.13] [EX:sp_2025_2_midterm_q04 p.9] [EX:sp_2025_2_midterm_q04 p.10] [EX:sp_2025_2_midterm_q04 p.11]

Assume:

- Byte-addressed memory and a one-byte permitted read.
- A 20-bit VA, an 18-bit PA, and 256-byte pages.
- A TLB with eight total entries, two ways per set.
- A data cache with 32 total lines, two ways per set, and 16 bytes per line.
- Request VA: `0x12A6D`.
- TLB set 2 has a valid entry with tag `0x19` and an invalid entry with tag `0x4A`.
- The page table maps VPN `0x12A` to resident, readable PPN `0x2C`.
- Data-cache set 6 has a valid line with tag `0x2C`. At byte offset $j$, for $0\leq j<16$, that line contains byte value `0x90 + j`. Its other way has a different tag.

Derive the address fields, TLB result, page-fault result, PA, cache result, and returned byte.

**Variations:**

1. The matching TLB entry becomes valid and supplies PPN `0x2C`; everything else is unchanged.
2. Instead, there is no valid matching TLB entry and the page-table entry describes a nonresident page. Can the original PA and byte result still be used immediately?

<details><summary>Worked answer and grading points</summary>

A 256-byte page requires eight offset bits, leaving 12 VPN bits. The TLB has

$$
8/2=4\text{ sets},
$$

so TLBI has two bits and TLBT has ten.

For the requested VA:

```text
VPN  = 0x12A
VPO  = 0x6D
TLBI = 0x12A mod 4 = 0x2
TLBT = 0x12A / 4   = 0x4A
```

The tag match is invalid, so the TLB misses. The page-table mapping is resident and readable, so this miss does **not** require a nonresident-page fault.

The PA is

$$
PA=\texttt{0x2C}\times\texttt{0x100}+\texttt{0x6D}
=\texttt{0x2C6D}.
$$

The data cache has $32/2=16$ sets, giving four index bits. Its 16-byte lines require four offset bits. The remaining ten PA bits form the tag.

```text
CT = 0x2C
CI = 0x6
CO = 0xD
```

The specified line is valid and matches, so the data-cache lookup hits. Offset `0xD` is decimal 13; the returned byte is `0x9D`.

The data capacity is

$$
32\times16=512\text{ bytes},
$$

excluding metadata.

In variation 1, translation becomes a TLB hit; the PA and returned byte remain unchanged. In variation 2, the nonresident mapping must be resolved before an immediately usable PA and data result can be asserted. The earlier resident-state result cannot simply be reused.

This exercise uses a simplified page-table lookup. It does not transfer its dimensions into the lecture’s four-level Core i7 model.

**Grading points:** Field derivation from dimensions; valid-bit check despite matching tag; separate TLB and residency decisions; correct PA; correct cache fields and byte; state-sensitive variation answers.

</details>

#### Practice P15 — Preserve victim contents and distinguish forbidden access

**Newly authored synthetic exercise — not an actual past question or official answer**

**Scope:** LO26–LO27: clean file-backed page discard, preservation of modified victim contents, and permissions on a resident page. [STT 01:05:06] [STT 01:05:59] [M03 p.32] [STT 01:06:53] [STT 01:07:38]

**General practice — no relevant exam evidence**

Assume a permitted read targets a mapped page whose required contents are on storage. A frame must be reclaimed. Candidate C is an unchanged copy of a recoverable file page; candidate D contains modifications absent from its backing copy.

1. If C is selected, must its contents be written out? What changes if D is selected?
2. **Variation:** The requested page is now resident but read-only, and the operation is a store. Would another page-in solve the problem?

<details><summary>Worked answer and grading points</summary>

C can be discarded without writing a new copy because its contents remain recoverable. D’s modifications must be preserved before frame reuse; otherwise data would be lost.

</details>
