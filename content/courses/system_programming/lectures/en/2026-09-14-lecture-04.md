## Lecture Content and Explanation

### A unified filesystem tree and mount points

A Unix filesystem presents files through a directory tree rooted at `/`. Additional filesystems can be attached to directories within that tree. The attachment operation is **mounting**, and the directory where the attachment occurs is a **mount point**. The lecture contrasts this arrangement with Windows drive letters: one visible root can lead to several underlying filesystems and storage devices. It does not imply that all files occupy one physical disk. [STT 02:34] [STT 03:32] [M01 p.11]

The `extern` example demonstrates what mounting changes:

1. Create a directory named `extern`.
2. Create `hello` inside it using `echo "hello" > extern/hello`.
3. Mount a `tmpfs` filesystem at `extern`.
4. List `extern` again. The listing now shows the newly mounted filesystem.
5. Create a file named `extern` in that mounted filesystem.
6. Unmount it. The original `hello` becomes visible again. [STT 04:42] [STT 05:42] [STT 09:21] [M01 p.11]

The initial `echo` example writes six bytes under the example’s character encoding: five letters followed by a newline. The command `ls -1` uses the digit `1`, meaning one name per output line; it is different from the lowercase `l` in `ls -l`. These details explain the displayed commands without changing the mounting mechanism. [STT 03:48] [STT 04:42]

### Mount options and the cost of access-time updates

A mounted filesystem has policies as well as a location. Mount options can restrict operations or change metadata-update behavior. The lecture’s mount and unmount commands use `sudo`, with the required privileges assumed for that demonstration. Running `mount` without additional arguments displays mounted filesystems and their options. [STT 11:28] [STT 15:27] [M01 p.13]

| Option | Meaning in the supplied material | Interpretation boundary |
|---|---|---|
| `ro` | Read-only access | A file’s write permission does not override a read-only filesystem. |
| `noatime` | Suppress access-time updates | This changes metadata-update behavior, not whether reading is permitted. |
| `relatime` | Restrict access-time updates using timestamp relationships | The slide gives a simplified condition, not a complete policy specification. |
| `noexec` | Restrict program execution | Distinguish this filesystem policy from directory traversal permission. |
| `nosuid` | Restrict SUID/SGID effects | File mode bits and filesystem policy must be considered together. |
| `nodev` | Prevent device files from functioning as devices | A visible device-file name does not by itself establish usable device access. |
| `size` | Set a maximum size for the example filesystem | The displayed limit is configuration-specific. |
| `iocharset` | Specify the character set used for filenames | This is not a declaration of the encoding of every file’s contents. |

[M01 p.13]

The annotation on p.13 relates `relatime` to whether `atime` precedes `mtime` or `ctime`. It should be read as the slide’s explanation of conditional updating. It is insufficient evidence for reconstructing every condition implemented by a particular system.

The instructor’s main motivation is that **reading can incur metadata work in addition to obtaining file contents**. Recording the latest access time may require another state update. A policy that reduces unnecessary access-time updates can therefore reduce associated work. The statement that reading updates `atime` must be understood alongside the mount policy; it is not an unconditional claim about every read operation. [STT 12:32]

As an illustrative application, suppose a file’s mode grants its owner write permission, but the filesystem is mounted read-only. The mode describes permission at the file level, while `ro` imposes a filesystem-level restriction. Looking at only one layer would produce an incomplete access decision. The same distinction later matters when interpreting `noexec` and `nosuid`. [M01 p.13] [M01 p.32] [M01 p.33]

### Reading metadata with `ls -l`

**Metadata** describes a file’s properties rather than its application data. The annotated listing on M01 p.14 separates the fields into file type and permissions, hard-link count, owner, group, size in bytes, modification time, and filename. The first character identifies the file type; the following nine ordinary permission positions serve a different purpose. [STT 16:15] [M01 p.14]

Group ownership is introduced through collaboration. A group can contain several users, and group permissions can let those users read or modify shared files. The owner, group, and other categories therefore distinguish who receives each set of permissions. “Other” refers to users outside the applicable owner/group distinction. [STT 17:13] [STT 18:10]

The three timestamps discussed in the lecture answer different questions:

| Timestamp | What it concerns | Common misunderstanding |
|---|---|---|
| `atime` | Access to the file | Assuming every read necessarily updates it, regardless of policy |
| `mtime` | Modification of file contents | Assuming content writes affect no other metadata |
| `ctime` | Change to file status or metadata | Reading the initial `c` as “creation” |

[STT 16:15] [STT 17:13]

For example, appending data changes the contents and may change the file’s size. The operation can therefore update both `mtime` and `ctime`. The instructor’s description of `ctime` as metadata-related must be retained together with this subsequent explanation. It would be misleading to reduce it to “content changes affect only `mtime`.” [STT 17:13]

The size field also requires an object-aware interpretation. A regular file’s content size and a symbolic link’s stored pathname length describe different objects. Reading the correct column is only the first step; the next is identifying whose metadata the listing displays. [M01 p.14] [M01 p.15]

### Hard links and symbolic links

A **hard link** is another directory entry referring to the same inode. An **inode** contains file metadata and identifies the underlying file object within the filesystem. The filename belongs to the directory-entry relationship; creating another hard link does not create an independent copy of the file’s contents or metadata. [STT 19:19] [STT 20:16] [M01 p.15]

A **symbolic link**, also called a **soft link**, is a separate file with its own inode that stores a target pathname. Ordinary file opening follows that pathname to reach the target. The lecture also mentions that API behavior can restrict following links, so “every operation always follows every symbolic link” would be too broad. [STT 21:10] [STT 22:03]

Both mechanisms support aliasing, but their reference structures differ:

| Property | Hard link | Symbolic link |
|---|---|---|
| Creation command | `ln` | `ln -s` |
| Relationship to the target | Another name sharing the target inode | A separate file storing a target pathname |
| Metadata | Shared metadata of the same file | Link metadata is distinct from target metadata |
| Filesystem boundary | Cannot cross it in the lecture’s ordinary model | A pathname can designate a target in another filesystem |
| Directory targets | Arbitrary directory hard-link creation is restricted | Directories can be symbolic-link targets |
| Target-name removal | Another hard link can keep the file accessible | The symbolic link can remain with a missing target |

[M01 p.15]

In the slide example, `hello.txt` and `helloworld.txt` share an inode and both display a hard-link count of 2. The entry `testing -> test.txt` instead has type `l` and stores the pathname `test.txt`. Its displayed size of 8 corresponds to that pathname, not to the contents of the target file. [M01 p.15]

### Updating and removing names through links

The instructor motivates aliases with storage costs and a dataset containing roughly 3,000 files that should also be accessible from another directory. Aliasing can express that relationship without duplicating every file’s contents. Symbolic-link resolution adds pathname-following work, whereas hard links share the inode directly. This qualitative observation is not a measured performance guarantee; filesystem boundaries and directory-linking requirements also affect the choice. [STT 24:31] [STT 25:15]

M01 p.16 appends through `helloworld.txt` and then reads through both hard-linked names. Both show the modified content because they identify the same file. There is no synchronization process maintaining two copies. [STT 26:13] [M01 p.16]

M01 p.17 performs the corresponding operation through `testing`. The ordinary access follows its stored pathname, so the contents of `test.txt` change. Reading through either name then reaches those target contents. The symbolic link itself continues to store a pathname; its own size does not become the target’s content size. [STT 27:10] [M01 p.17]

Removing names exposes the difference more clearly:

| Operation in the material | What remains | Subsequent observation |
|---|---|---|
| Remove `hello.txt` | `helloworld.txt` still references the shared inode | The remaining name can still be used to read the file. |
| Remove `test.txt` | `testing` still stores the target pathname | Opening the missing target through the link fails. |

[M01 p.18]

The remaining hard link has a count of 1. The symbolic link becomes a **dangling link**: the link exists, but the target named by its contents does not. Thus, checking that a symbolic link exists does not establish that its target can be opened. [STT 27:31]

The slide listings show post-update sizes of 14 and 22. Those are values printed in the supplied material, not newly reproduced execution results. The precise relationship between the displayed `printf` syntax and those byte counts remains a source limitation. The supported lesson is that hard-linked names show the same underlying size, while a symbolic link’s own size is separate. [M01 p.16] [M01 p.17]

Likewise, the discussion of decreasing hard-link counts concerns references through names. It does not establish the complete lifetime rules for files that also have open handles. That broader issue should not be silently inferred from the deletion example.

### Why the directory link count is `2 + N` in the lecture model

M01 p.21 displays a hard-link count of 4 for `sample`, which contains two subdirectories, `dir1` and `dir2`. Each child displays a count of 2. The task is to count directory entries that refer to an inode, rather than simply counting the entries stored inside a directory. [STT 29:25] [M01 p.21]

In the conventional model used here, a directory receives:

1. One reference from its name in the parent directory.
2. One reference from its own `.` entry.
3. One additional reference from the `..` entry of each immediate subdirectory.

For $N$ immediate subdirectories, the resulting count is

$$
L = 1 + 1 + N = 2 + N.
$$

For `sample`, the two child `..` entries supply the additional two references, giving $L=4$. A child with no subdirectories has the two baseline references and therefore a count of 2 in this example. [STT 30:24] [STT 31:21] [M01 p.21]

A newly constructed illustration makes the distinction explicit: under the same model, four immediate subdirectories produce a count of 6. Adding an ordinary file inside the directory does not make the count 7, because the ordinary file’s directory entry refers to that file’s inode, not the parent directory’s inode. More distant descendants must not be counted as though each supplied a direct `..` reference to the original directory.

The indexed 2025 second-semester midterm Q3(b) asks for this kind of reference counting from a stated directory structure. A justified answer identifies the two baseline references and the contribution of each immediate child. The reasoning is accessible from this lecture, but the numerical model must remain tied to the stated filesystem assumptions. [EX:sp_2025_2_midterm_q03 p.7]

Neither the existence of `.` and `..` nor the formula authorizes arbitrary directory hard links. These special entries coexist with the ordinary restriction discussed earlier. The formula is also not a guarantee that every filesystem implementation exposes exactly the same observable count. [M01 p.15] [M01 p.21]

### File and directory permissions

The ordinary permission field contains three `rwx` groups, ordered as owner, group, and other. Each group describes permissions for its corresponding category. The preceding file-type character is not a fourth permission category. [STT 35:27] [M01 p.29]

The meaning of a permission depends on the object:

| Permission | Regular file | Directory |
|---|---|---|
| `r` | Read its contents | Read the names in its listing |
| `w` | Modify its contents | Modify directory entries, such as creating or removing names |
| `x` | Execute it as a program | Enter or traverse the directory during pathname resolution |

[STT 36:28] [STT 37:34] [M01 p.29]

The directory distinction is a lecture-specific emphasis. The instructor’s initially ambiguous wording is followed by the explanation that `x` can permit entering a directory even when the absence of `r` prevents listing its names. “Cannot list this directory” and “cannot traverse this directory” are therefore different conditions. [STT 36:28]

Directory write permission concerns the directory’s entries. It does not automatically grant write permission to every file’s contents. Conversely, being able to read a file’s contents does not automatically imply permission to remove its name from the parent directory. The relevant objects differ. Actual entry changes also depend on traversal and other applicable restrictions; `w` alone should not be presented as sufficient for every operation. [STT 37:26] [STT 37:34]

As an illustrative case, a shared directory may allow users to create names while an individual file inside it remains protected against content modification by its own mode. That division of responsibility is why both directory metadata and file metadata matter. The sticky bit adds another restriction on certain directory-entry changes.

### Changing permissions with symbolic and octal `chmod`

`chmod` changes file mode permissions. **Symbolic mode** identifies the affected category with `u`, `g`, or `o`, then uses an operation such as `+` or `-` to add or remove a permission. The lecture’s `chmod g+w test.txt` adds group write permission while retaining the other ordinary permission settings shown in the example. [STT 38:22] [M01 p.30]

**Octal mode** expresses each `rwx` group as three bits:

$$
r=4,\qquad w=2,\qquad x=1.
$$

The value for a category is the sum of the enabled bits. Thus, `chmod 750 script.sh` has the following interpretation:

| Category | Octal digit | Bits | Permissions |
|---|---:|---|---|
| Owner | 7 | `111` | `rwx` |
| Group | 5 | `101` | `r-x` |
| Other | 0 | `000` | `---` |

[STT 39:17] [STT 40:17]

The script example contains the command `ls -l`, but direct execution initially fails because the script lacks execute permission. Having text that represents commands is different from possessing permission to execute the file in the demonstrated way. The permission calculation explains the purpose of the later `750` setting. [M01 p.30]

**Material correction:** the command changes `script.sh`, but the final listing on p.30 names `test.txt`. The mismatch belongs to the source. The octal interpretation is valid, but the final listing must not be silently rewritten into a verified execution record for the script. [M01 p.30]

### The sticky bit and mode information from `stat`

The **sticky bit** addresses a problem in shared writable directories: users may need to create temporary files without being allowed to rename or delete other users’ entries freely. In the supplied material, the added restriction permits the relevant rename or deletion only by the file owner, the directory owner, or a privileged user or process. Other necessary access conditions still apply. [STT 41:49] [STT 42:41] [M01 p.31]

This is a restriction on entry removal and renaming, not a substitute for controlling access to file contents. For example, enabling the sticky bit on a shared temporary directory does not by itself change whether someone can read or write the bytes of an individual file.

The listing on M01 p.31 shows `t` in the final ordinary execute position. At the program level, the slide connects the sticky bit with `S_ISVTX` in mode information available through `struct stat`. It also points to `man 2 stat` and `man 7 inode`. [M01 p.31]

The instructor introduces symbolic macros including `S_IRWXU` and `S_IRWXG`, with `00700` as the owner-`rwx` example. The emphasis is on finding and interpreting definitions rather than memorizing all numeric encodings. [STT 44:33] [STT 45:48] [STT 46:21]

### World-writable directories and filesystem execution policy

A **world-writable directory** permits entry changes by the “other” category, subject to applicable restrictions. The lecture asks why allowing broadly writable temporary space and allowing execution from its filesystem can create security concerns. M01 p.32 illustrates a compromised webserver placing a script in temporary storage and subsequently executing it. This is a motivation for checking configuration, not evidence that every such directory is exploitable. [STT 47:04] [M01 p.32]

The material identifies two distinct inspection points:

- `S_IWOTH` concerns the other-write bit in file mode information.
- `fstatfs()` and the slide’s `ST_NOEXEC` flag concern filesystem execution policy. [M01 p.32]

As an illustrative reading of the configuration, detecting broad directory write permission should prompt inspection of the filesystem policy and the intended use of that directory. It does not justify inferring the presence of a vulnerable executable from the permission bit alone.

### SUID, SGID, and real versus effective identity

**SUID** and **SGID** connect program execution with an executable file’s owning user or group. The instructor motivates this through a submission program that needs to place work in a directory ordinary users cannot directly modify. The intended distinction is between granting a user unrestricted access and allowing a particular program to perform a controlled operation with another identity. [STT 14:38] [STT 52:22] [M01 p.33]

M01 p.33 supplies this historical example:

```text
devel@csapvm $ ls -l /usr/bin/sudo
-rwsr-xr-x 1 root root 204320 Sep  1 16:17 /usr/bin/sudo
```

The file is owned by `root`, and `s` in the owner-execute position marks SUID. It illustrates execution with the file owner’s effective user identity, subject to execution permissions and filesystem policy. The pathname, mode, size, and displayed `Sep  1 16:17` timestamp describe the slide’s installation; no year is shown. This is historical source output, not a current system check or a guarantee about every installation. [M01 p.33]

Two identity concepts are essential:

- **Real user/group identity** identifies the original user and group under which the process was started in the lecture’s example.
- **Effective user/group identity** identifies the user and group used for the process’s execution permissions in that example. [M01 p.35]

M01 p.34 demonstrates this with the example accounts `devel` and `tester`. Initially, `devel` runs `wai`, and the real and effective identities agree. The executable is then assigned ownership `tester:users` and mode `4755`, after which `devel` runs it again.

| Identity | Initial run | Run after ownership change and `4755` |
|---|---|---|
| Real user | `devel` | `devel` |
| Real group | `devel` | `devel` |
| Effective user | `devel` | `tester` |
| Effective group | `devel` | `devel` |

[M01 p.34]

**The important observation is that only the effective user changes.** Changing the file’s group ownership to `users` does not, by itself, make the executing process’s effective group become `users`. The demonstrated special bit is SUID; this is not a demonstration of enabling SGID as well. [STT 50:37] [STT 51:21]

The slide associates `4755` with SUID, `2755` with SGID, and `6755` with both. It connects the corresponding metadata bits to `S_ISUID` and `S_ISGID`, and filesystem suppression of their effects to `ST_NOSUID`. Ordinary execution permissions and filesystem policy still matter. A SUID bit does not establish that every user can execute the file, nor that execution necessarily acquires root identity: the owning identity must be examined. [M01 p.33] [M01 p.34]

**Exam connection.** The indexed 2025 second-semester midterm Q3(e) asks about SUID’s meaning, examples, and the security consequences of privileged executables. The current lecture supports explaining the effective identity and why a vulnerability in a program running with greater privilege can have more serious consequences. ### File descriptors and the current file position

A **file descriptor** is a nonnegative integer identifying an open-file reference within a process. It is not a global number assigned permanently to a filename. Two processes can both have descriptor 10 while referring to different objects; they are not required to refer to different objects merely because the processes differ. The STT’s qualified wording is more precise than the categorical sentence on M02 p.6. [STT 68:01] [STT 70:01] [M02 p.6]

The lecture mentions opening a file, creating a file, and creating a socket as ways of obtaining descriptors. Once obtained, the descriptor identifies the target of later operations. [STT 69:00]

**Reading the position diagram.** Page 5 of the source-bound PDF rendering of [04.IO.Direct.and.Buffered.IO.pptx](https://jhlee1020lee.github.io/2026-fall-study-hub/materials/system_programming/04.IO.Direct.and.Buffered.IO.pptx) lays out bytes as $B_0,B_1,\ldots,B_{k-1},B_k,B_{k+1},\ldots$. The current-position arrow points to $B_k$, the next byte at which the depicted access begins. It does not point to the previously consumed byte $B_{k-1}$. The descriptor arrow identifies the opened object, while the position arrow identifies a location within it. [M02 p.5]

For a regular seekable file in this model, reading or writing starts at the current position and advances it by the amount transferred. The instructor motivates this by reading ten bytes and then reading another ten: retaining position avoids restarting from the first byte or supplying the offset again on every call. The instructor also notes wanting to move the write position to the end of a regular file. This motivates explicit positioning as well as automatic advancement; the detailed seeking rules remain deferred. [STT 69:00] [STT 70:01]

A newly constructed numerical example uses the same mechanism. If the current position is 4 and a read successfully transfers 6 bytes, the next position is 10. A subsequent successful transfer of 3 bytes moves it to 13:

$$
k_{\text{next}}=k_{\text{current}}+n_{\text{transferred}}.
$$

The quantity added is the amount actually transferred, not an unconditional assumption about every requested amount. This is an explanation of the position-based file model; it does not impose a seekable offset on every socket or device.

The slide also flags subtleties when descriptors are shared. The current lecture establishes the need to track position but does not complete the rules for descriptor duplication and shared offsets. Those later mechanisms must not be inferred from the diagram alone. [M02 p.5]

## Key Takeaways

- **A pathname, an inode, and a descriptor answer different questions.** Mounting affects pathname visibility; hard links share an inode; descriptors identify current open references within a process.
- **Read metadata in relation to its object.** A symbolic link’s size concerns its stored pathname, directory permissions concern names and traversal, and `ctime` is not creation time.
- **Access decisions involve several layers.** File mode, directory permissions, sticky restrictions, effective identity, ACL entries, and filesystem policy must not be collapsed into one permission bit.
- **The SUID example changes effective user identity.** File group ownership alone does not reproduce an SGID effect, and SUID does not invariably mean root.
- **Storage and reference lifetimes matter.** A later lookup can reuse returned storage; a later opening can reuse a closed descriptor number.
- **Extended metadata records information explicitly.** Storing a checksum does not arrange automatic recomputation, and listing an attribute name does not retrieve its value.
- **Use interfaces and definitions precisely.** `open` flags differ from creation mode, variadic calls differ from C++ overloading, and unfamiliar platform types should be investigated rather than guessed.
- **The supplied STT ends with descriptor reuse and `close`.** Detailed transfer recovery, shared-offset rules, and Standard I/O buffering remain subsequent study topics.
