## Lecture Content and Explanation

### Memory addresses belong to a process

[[concepts/memory-abstraction|Memory abstraction]] explains how a running program sees and uses memory. The lecture begins with a concrete question: where do functions and variables actually reside? The `layout.c` example prints addresses of functions, global variables, local variables, arrays, pointers, and a field intended for shared storage. A function has an address because its compiled instructions occupy memory; a variable has storage whose location can also be observed. A running instance of a program is a [[concepts/process|process]], identified by its process ID. [STT 01:32] [STT 03:43] [STT 04:42] [M01 slide 4]

Read the example’s output by separating three kinds of information:

- A function address identifies compiled code.
- An object address, such as `&global_ptr`, identifies the pointer variable’s own storage.
- A pointer value, such as `global_ptr`, identifies the location to which that pointer currently refers.

The shared structure contains a semaphore and `shared_int`. The semaphore introduces the motivation for coordinating access to shared state, but this session does not establish a complete synchronization or shared-memory implementation. The instructor explicitly leaves the full opening program for a later lecture. [STT 02:55] [STT 13:08] [M01 slide 4]

**Source comparison: repeated executions and ASLR.** Slides 5 and 6 show address listings from separate executions. Without [[concepts/aslr|Address Space Layout Randomization]], the displayed addresses repeat. With ASLR, corresponding addresses change between runs, including higher address digits. The security motivation is to make useful code and data locations harder to predict when an attacker also has another vulnerability to exploit. This is a protection mechanism, not a guarantee that every attack becomes impossible. The uncertain exploit wording in the STT does not establish a particular attack technique. [STT 06:37] [STT 07:36] [STT 08:34] [M01 slide 5] [M01 slide 6]

**Source figure: private state versus shared state.** Slide 7 prints output from two processes. Their `global_int` variables have the same numeric virtual address, yet each process maintains its own value. Meanwhile, the displayed `shared_int` sequence progresses across output from both processes.

| Observation in the source figure | Interpretation |
|---|---|
| Both processes display the same numeric address for `global_int` | The number alone does not establish shared storage |
| One process advances its private counter while the other retains its own counter value | Private state is independent |
| The shared counter advances through the combined output sequence | Both processes observe state deliberately configured for sharing |

A [[concepts/virtual-address|virtual address]] is interpreted within a process’s address space. Therefore, “address 10 in process A” and “address 10 in process B” need not identify the same underlying storage. Conversely, shared storage requires an actual sharing arrangement; equal printed numbers do not create one. [STT 09:18] [STT 10:15] [STT 11:09] [STT 12:08] [M01 slide 7]

The immediate learning target is this distinction between numeric addresses, private state, and shared state. Page-table translation, TLB lookup, and detailed paging calculations remain later topics. The lecture’s references to translation across page boundaries do not establish that those mechanisms were taught here. [STT 42:29] [STT 43:27]

### Variables, memory regions, and executable storage

A variable declaration connects a type and a name. In the lecture’s storage model, the compiler allocates space appropriate to the type and associates the name with that storage. The name lets the programmer refer to data without manually remembering its address. [STT 13:08] [M01 slide 9]

**Source example.** Slide 10 places three integers at illustrative addresses:

| Variable | Address | Stored value |
|---|---:|---:|
| `a` | 16 | 5 |
| `b` | 20 | 7 |
| `c` | 24 | Unspecified in this illustration |

Reading `a` means obtaining the value stored at its assigned location. The lecture connects this to a load–compute–store view: bring data into a register, perform arithmetic, and write a result when necessary. The example does **not** guarantee that separately declared variables always occupy consecutive addresses or follow declaration order. Likewise, its description of register-based computation should not become a universal claim that every architecture forbids every memory-to-memory instruction. [STT 14:01] [M01 slide 10]

[[concepts/memory-layout|Process memory layout]] adds another question: what role does each region serve?

**Source figure: the memory map on slide 11.** Read the diagram from lower toward higher addresses:

| Region shown | Role in the lecture example |
|---|---|
| `.text` | Compiled instructions, including function bodies |
| `.rodata` | Read-only data, illustrated by a global constant and string literals |
| `.data` | Writable global data whose initializer must be represented |
| `.bss` | Global storage that need not carry an explicit block of initializer bytes in the executable |
| Run-time heap | Dynamically allocated storage; the diagram marks its boundary with `brk` |
| Memory-mapped region | Includes mapped shared libraries |
| User stack | Run-time call-related storage; the diagram shows downward growth |
| Kernel virtual memory | A distinct high-address region in the displayed process map |

These are logical regions with different purposes and access permissions. The lecture stresses that ordinary DRAM does not itself recognize a C variable as “constant.” The OS and CPU support the protection that can reject a write to a read-only region. [STT 15:07] [STT 16:05] [STT 17:04] [STT 18:01] [M01 slide 11]

The distinction between `.data` and `.bss` also explains executable size. An initializer such as the source example’s `a = 5` must be represented so the value can be established. A large global array without explicit element initializers does not require the executable to contain a separately stored byte for every element merely to reserve its run-time storage. Separating that storage saves file space. This is a contrast between **file representation and run-time storage**, not a claim that `.bss` occupies no memory when the program runs. [STT 18:57] [STT 19:54]

*Post-baseline qualification (S01): static arithmetic objects without explicit initializers start at zero.* [WG14 N1570 §6.7.9](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

The heap and stack descriptions also require context. The lecture notes that allocation size can affect where dynamically allocated storage appears, and that libraries can be mapped into memory. It does not establish a complete allocator policy or a precise threshold for choosing a mapping. The Intel example’s stack grows toward lower addresses. Earlier language placing parameters on the stack must be read together with the later assembly examples, which pass parameters in registers. [STT 20:52] [STT 21:47] [STT 22:48] [M01 slide 44]

**Exam connection.** The 2024 Fall midterm Q1(d) asks students to classify addresses associated with a function, a constant, and a local pointer, and to distinguish virtual from physical addresses. ### Pointer storage, pointer values, and levels of indirection

A [[concepts/pointers|pointer]] is a variable that contains an address. Consequently, a pointer has both **its own location** and **the address value stored there**. Dereferencing follows the stored address to another object. [STT 22:48] [STT 23:44] [M01 slide 13]

**Source figure: `a`, `ap`, and `app`.** Slides 14–15 illustrate:

```c
int a = 5;
int *ap = &a;
int **app = &ap;
```

| Object | Its own address in the diagram | Its stored value |
|---|---:|---:|
| `a` | 16 | 5 |
| `ap` | 28 | 16 |
| `app` | 4 | 28 |

Following the diagram gives:

- `ap` contains 16, the address of `a`.
- `*ap` denotes `a`, whose value is 5.
- `app` contains 28, the address of `ap`.
- `*app` denotes the pointer object `ap`.
- `**app` denotes the integer object `a`.

The distinction matters whenever code changes a pointer through a pointer-to-pointer. Updating `*app` changes where `ap` points; updating `**app` changes the integer reached through it. The STT’s conflicting address wording at 24:43 is **검증 필요**; the values above come from the slide diagram. [STT 24:43] [M01 slide 14] [M01 slide 15]

**New explanatory example: moving a pointer versus changing an element.**

```c
int values[3] = {4, 8, 12};
int *p = values;
int **pp = &p;

(*pp)++;
**pp = 9;
```

Initially, `p` points to `values[0]`. Because `*pp` denotes `p`, `(*pp)++` advances that pointer to `values[1]`. The following assignment changes `values[1]` to 9. The array becomes `{4, 9, 12}`; `pp` still points to the same pointer object `p`.

This example uses separate statements so that each update can be traced without ambiguity. A reliable tracing method records pointer targets and stored data in separate columns.

**Exam connection.** The 2024 Fall midterm Q1(b) requires following assignments through multiple pointer levels. The 2025 Fall midterm Q1(b) additionally combines pointer movement with array-element updates. Both transfer directly to this tracing method: identify the object named by the left-hand side before applying each assignment. Confusing `p`, `*p`, and `**pp` loses the distinction between changing an address and changing data. [EX:sp_2024_2_midterm_q01 p.2] [EX:sp_2025_2_midterm_q01 p.3]

The same separation applies to the opening shared structure. In the lecture’s target environment, `sizeof(shared)` measures the pointer object, whereas `sizeof(*shared)` measures the structure it points to. The latter is not automatically the pointer size. Function-address expressions also appear in the opening example: `foo` and `&foo` are used to refer to the function’s location in that context. This does not make a function, an array, and a pointer object interchangeable kinds of objects. [STT 05:36] [STT 06:37] [M01 slide 4]

### Dynamic allocation, initialization, and buffer sizes

[[concepts/dynamic-memory-allocation|Dynamic memory allocation]] separates the lifetime and size of a requested storage block from the declaration of the pointer used to reach it. Declaring `int *A` creates a pointer object; it does not itself allocate space for 1,024 integers. [M01 slide 16]

**Source figure: the allocation on slide 17.** The slide uses:

```c
int *A;
A = (int *)malloc(sizeof(int) * 1024);
```

Under its explicit assumption that `sizeof(int) == 4`, the requested allocation is:

$$
1024 \times 4 = 4096\ \text{bytes} = \texttt{0x1000}\ \text{bytes}.
$$

The pointer object `A` is shown at `0xffffc1a4`. It stores `0x56550004`, the starting address of a separate allocated block.

| Expression | Address in the source example |
|---|---|
| `&A` | `0xffffc1a4` |
| `&A[0]` | `0x56550004` |
| `&A[1]` | `0x56550008` |
| `&A[2]` | `0x5655000c` |
| `&A[1023]` | `0x56551000` |

The last element begins at:

$$
\texttt{0x56550004} + 1023 \times 4
= \texttt{0x56551000}.
$$

Its four bytes end immediately before `0x56551004`, the end of the allocation. Thus, the last element’s **starting address** differs from the allocation’s **end address**. These numbers are slide evidence, not a reconstruction of the garbled spoken quantities. [STT 24:43] [M01 slide 17]

#### Array expressions do not turn array objects into pointer objects

For a pointer `p` to an array’s first element:

- `p[0]` denotes the first element.
- `&p[0]` is its address.
- `p` contains that same starting address.

An array expression such as `buf` also supplies the address of its first element in many expression contexts. Nevertheless, an array object and a pointer object remain different. The difference becomes immediately visible with `sizeof`. [STT 25:42] [M01 slide 18]

**Source code comparison.**

```c
char buf[512] = {'A', 'B', 'C'};
```

Here, the first three elements receive the listed characters, and the remaining elements are initialized to zero. In particular, `buf[3]` is zero. The lecture’s classroom question distinguishes the character value zero from a null pointer. [STT 26:45] [STT 27:45] [M01 slide 19]

By contrast, the source’s dynamically allocated buffer is explicitly assigned only at indices 0, 1, and 2. Those assignments do not initialize the remaining bytes.

*Post-baseline qualification (S01): `malloc` supplies storage whose initial value is indeterminate.* [WG14 N1570 §7.22.3.4](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

The practical conclusion is to initialize data before relying on its contents. Uninitialized storage is not a dependable random-number source. The lecture mentions `calloc` when zero-filled allocation is needed, and `free` when an allocation is no longer required. It also distinguishes releasing resources during execution from the OS reclaiming a process’s resources when it ends: eventual process cleanup does not prevent a long-running program from accumulating unused allocations. [STT 28:44] [M01 slide 19]

#### `read` needs a destination address and a byte count

The buffer examples connect pointers to the earlier I/O material. The second argument of `read` identifies writable storage; the third specifies the requested number of bytes. [STT 29:40] [M01 slide 20]

| Buffer declaration | Appropriate destination expression | Relevant capacity expression |
|---|---|---|
| `char buf[512];` | `buf` | `sizeof(buf)` |
| `char *buf = malloc(512 * sizeof(char));` | `buf` | The separately tracked allocation capacity |
| `char buf;` | `&buf` | `sizeof(char)` |

For the array, `sizeof(buf)` is 512. For the pointer in the target 64-bit example, `sizeof(buf)` is 8 regardless of the requested 512-byte allocation. Passing that pointer size as the requested read length would describe eight bytes, not the whole allocated block.

The slide therefore uses a named constant such as `BUFSIZE` consistently in both allocation and reading. This keeps the capacity visible without pretending the pointer stores it. For a single character, `buf` is the character value and `&buf` is the destination address. The lecture’s compiler-warning discussion reinforces that successful compilation alone does not establish that an argument denotes the intended storage. [STT 30:40] [STT 31:35] [M01 slide 20]

**Exam connection.** The 2025 Spring midterm Q1(a) asks what different `sizeof` operands actually measure. Its directly relevant demand is to distinguish an object’s type, a pointer’s type, and the type reached by dereferencing. Write down that type first, then apply the stated platform assumptions. Do not use allocation length as a substitute for pointer size. [EX:sp_2025_1_midterm_q01 p.2]

### Machine data types, alignment, and the target ABI

At machine level, instructions operate on supported scalar and vector data. Slide 22 lists integer data of 1, 2, 4, or 8 bytes (including data values and addresses), floating-point data of 4, 8, 10, or 16 bytes, and vector data. A C array or structure is a higher-level organization that the compiler implements through byte layout and access offsets. The machine does not interpret a C structure declaration as a self-describing record. [STT 31:35] [STT 32:17] [M01 slide 22]

[[concepts/abi|ABI]] conventions connect this representation to compiled code. Type sizes, alignment, argument passing, and library compatibility depend on the target environment, not simply on the phrase “64-bit CPU.” [STT 40:32] [STT 41:29] [STT 44:25] [M01 slide 30]

**Source table: the main target sizes.**

| Type | x86-64 Linux example | IA32 example |
|---|---:|---:|
| `char` | 1 byte | 1 byte |
| `short` | 2 bytes | 2 bytes |
| `int` | 4 bytes | 4 bytes |
| `long` | 8 bytes | 4 bytes |
| `float` | 4 bytes | 4 bytes |
| `double` | 8 bytes | 8 bytes |
| Pointer | 8 bytes | 4 bytes |

The lecture specifically asks students to internalize the common `char`, `short`, `int`, `long`, `float`, `double`, and pointer sizes, while focusing on x86-64 Linux. It does not ask students to memorize every platform’s table. These are source-bound target values, not universal C guarantees. [STT 37:11] [STT 41:29] [M01 slide 23]

The historical discussion explains why less common rows exist. `long long` addresses the need for wider integers in older environments; `long double` is discussed through extended floating-point representation and storage padding.

The lecture connects `long double` to the x87 floating-point coprocessor tradition and the later integration of floating-point hardware into the CPU. In the shown Linux examples, the extended value uses ten bytes, while its storage occupies 12 bytes on IA32 or 16 bytes on x86-64. The extra two or six bytes are padding, not additional precision. The corresponding alignment requirements are four and 16 bytes. These are the displayed platform conventions; the uncertain spoken bit count remains **검증 필요**. [STT 35:14] [STT 36:13] [M01 slide 23] [M01 slide 26] [M01 slide 27] [M01 slide 29]

Slide 23 visibly strikes through `long long`, `long double`, and the 128-bit integer row, and the lecturer limits attention to the unusual `long double` exception. That narrows the immediate memorization focus; it does not erase the alignment topic or establish an exam exclusion. [STT 34:15] [STT 36:13] [STT 43:27] [M01 slide 23]

[[concepts/data-alignment|Alignment]] constrains an object’s starting address. A $K$-byte-aligned address is divisible by $K$:

$$
\text{address} \bmod K = 0.
$$

For a four-byte alignment requirement, addresses 0, 4, 8, and 12 satisfy the condition; addresses 1, 2, and 3 do not. **Size** measures occupied storage, while **alignment** constrains permissible starting positions. They often coincide in the target table but are different properties. [STT 38:04] [STT 41:29] [M01 slide 24]

The lecture motivates alignment through access boundaries. A datum spanning access units can require split handling, with possible performance and atomicity implications. A datum spanning pages can also involve more complicated address translation. These are reasons to respect alignment, not guarantees that every unaligned access has the same cost, faults, or atomicity behavior. [STT 38:39] [STT 42:29] [M01 slide 25]

In the lecture’s historical comparison, MIPS, SPARC, older ARM, and Power illustrate **required** alignment, whereas IA32/x86-64 illustrate **advised** alignment: an unaligned access may still execute, with the concerns above. The MIPS example describes a crash when alignment is violated. This comparison concerns the discussed machine contexts, not every generation or instruction in those families. OS-specific binary conventions also govern parameter passing and local storage. [STT 38:04] [STT 39:37] [STT 40:32] [M01 slide 24]

**New explanatory example.** Suppose a boundary-crossing write is implemented as two separately observable updates, with no guarantee that the whole write is atomic. After the first part changes but before the second changes, an observer could see a mixture of new and old parts. The complete value has therefore not changed as one indivisible action. This explains the lecture’s atomicity concern, conditional on the hardware access behavior; alignment alone is not a universal atomicity guarantee. [STT 38:39] [M01 slide 25]

The source’s IA32 table gives a useful counterexample to “alignment always equals size”: an eight-byte `double` has four-byte alignment in the displayed Linux configuration, while the Windows comparison gives eight-byte alignment. The x86-64 table must not be read as proving that every 64-bit Windows type has the same size as its Linux counterpart. That broader interpretation is **검증 필요**. [M01 slide 26] [M01 slide 27]

### Measuring alignment and reading compiler-inserted gaps

The `size.c` example makes alignment visible by placing a one-byte member before a member of the type being examined:

```c
struct {
    char dummy;
    T data;
};
```

This is the source’s structural pattern, with `T` standing for the macro’s selected type. `INFO(t)` generates this pattern repeatedly, prints the type name using `#t`, prints `sizeof(t)`, and computes the location of `data` relative to the structure’s start. Macro expansion reduces repetition; it does not change what the resulting structure means. [STT 45:24] [STT 46:17] [M01 slide 28]

The crucial interpretation is:

$$
\operatorname{offset}(\texttt{data})
=
1\ \text{byte for dummy}
+
\text{padding after dummy}.
$$

For an eight-byte-aligned `long`, `data` begins at offset 8: one byte belongs to `dummy`, and seven bytes are padding. Calling the entire offset “eight bytes of padding” would be wrong. The source’s `OFS` expression measures an address difference, not padding alone. [STT 47:15] [STT 48:09] [STT 49:08] [M01 slide 28]

**Source table: comparing the two compiled outputs.**

| Type | `-m64`: size / reported offset | `-m32`: size / reported offset |
|---|---:|---:|
| `char` | 1 / 1 | 1 / 1 |
| `short` | 2 / 2 | 2 / 2 |
| `int` | 4 / 4 | 4 / 4 |
| `long` | 8 / 8 | 4 / 4 |
| `long long` | 8 / 8 | 8 / 4 |
| `float` | 4 / 4 | 4 / 4 |
| `double` | 8 / 8 | 8 / 4 |
| `long double` | 16 / 16 | 12 / 4 |
| `void *` | 8 / 8 | 4 / 4 |

The output labels the third column “ALIGNMENT.” In this particular probing structure, the offset exposes the demonstrated alignment convention. The two binaries show why type size and alignment must be recorded separately. [STT 50:07] [STT 51:07] [M01 slide 29]

The compiler normally inserts necessary gaps according to the target ABI. Programmers encounter these details directly when interpreting assembly, sharing binary layouts, or calculating offsets. [STT 52:04] [M01 slide 30]

**Source output: `varalign.c`.** Slides 31–32 inspect the gap between consecutive displayed objects using:

$$
\text{gap}
=
\text{current address}
-
\text{previous address}
-
\text{previous object size}.
$$

Using only the common addresses’ hexadecimal suffixes:

| Previous object | Next object | Gap calculation | Padding |
|---|---|---|---:|
| Four-byte `int` at `0x40` | `char` at `0x44` | `0x44 - (0x40 + 4)` | 0 |
| `char` at `0x44` | `short` at `0x46` | `0x46 - (0x44 + 1)` | 1 |
| `char` at `0x51` | `float` at `0x54` | `0x54 - (0x51 + 1)` | 2 |
| `char` at `0x58` | `double` at `0x60` | `0x60 - (0x58 + 1)` | 7 |
| Eight-byte `double` at `0x60` | `long double` at `0x70` | `0x70 - (0x60 + 8)` | 8 |

The subtraction is hexadecimal: `0x60 - 0x59` is seven bytes. The `int` at `0x40` occupies `0x40` through `0x43`; the next byte is `0x44`. These observations describe the displayed compiled layout. They do not guarantee declaration-order placement for arbitrary global variables. [STT 53:00] [STT 53:53] [STT 54:26] [M01 slide 31] [M01 slide 32]

### Arrays, structures, and unions: calculating storage correctly

[[concepts/arrays|Arrays]] place equal-sized elements consecutively. If each element occupies $s_T$ bytes and the array has $N$ elements, then:

$$
\operatorname{sizeof}(\text{array}) = N s_T.
$$

If $x$ denotes the starting **byte address**, element $i$ starts at:

$$
\operatorname{address}(i) = x + i s_T.
$$

This is byte-address arithmetic. In a C expression involving a `T *`, adding `i` already advances by `i` elements; do not multiply by `sizeof(T)` again when using typed-pointer arithmetic. [STT 54:26] [STT 55:25] [M01 slide 34]

[[concepts/struct|Structure layout]] preserves member order while allowing padding between members. Each member begins at a location satisfying its alignment requirement. The structure may also need padding at the end so that consecutive structures in an array remain correctly aligned. [STT 56:23] [M01 slide 35] [M01 slide 36]

**Source figure: `S2` and its array stride.**

```c
struct S2 {
    double v;
    int i[2];
    char c;
} a[10];
```

Under the slide’s sizes and alignments:

| Component | Byte offset | Size |
|---|---:|---:|
| `v` | 0 | 8 |
| `i[0]` | 8 | 4 |
| `i[1]` | 12 | 4 |
| `c` | 16 | 1 |
| Tail padding | 17 | 7 |

The payload occupies:

$$
8 + 4 + 4 + 1 = 17\ \text{bytes}.
$$

The largest member alignment is eight. Rounding the total extent up to the next suitable multiple gives:

$$
\operatorname{sizeof}(\texttt{struct S2})
=
8\left\lceil\frac{17}{8}\right\rceil
=
24\ \text{bytes}.
$$

The diagram expands `a[1]` to show why its final seven bytes are necessary. Successive elements begin at byte offsets 0, 24, 48, and 72. Consequently, the ten-element array occupies $10 \times 24 = 240$ bytes. A 17-byte stride would misalign the next element’s `double`. [STT 57:22] [M01 slide 37]

A [[concepts/union|union]] uses a different organization: all members start at offset zero and overlap the same storage. Its alignment must satisfy the most demanding member. The slide’s maximum-member-size formula expresses the sharing idea; member sizes are not added as though the union were a structure. [STT 58:23] [M01 slide 38] [M01 slide 39]

*Post-baseline qualification (S01): a union may have trailing padding; maximum member size alone is not a universal exact-size rule.* [WG14 N1570 §6.7.2.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

**New explanatory comparison.** Under the target layout conventions, a union containing a `double` and an `int` places both at offset zero and needs storage suitable for the larger member. A structure containing those members places them at distinct offsets and may add tail padding. The difference is overlapping storage versus separate member storage, not merely different spelling.

**Exam connection.** The 2024 Fall midterm Q1(a) and 2025 Spring midterm Q1(b) require distinguishing whole-array size, single-structure size, pointer size, member offsets, and address increments. The lecture supplies the essential method:

1. Establish the target sizes and alignments.
2. Draw member offsets, including internal and tail padding.
3. Determine the array stride.
4. Identify the type of any pointer being advanced.
5. Keep byte offsets separate from typed-pointer increments.

The trap is to sum payload sizes and immediately use that sum as `sizeof(struct)`, or to interpret every `+1` as a one-byte increment. Only the relevant layout and type reasoning is transferred here; unusual casts and address expressions in historical questions do not become general portability guarantees. [EX:sp_2024_2_midterm_q01 p.2] [EX:sp_2025_1_midterm_q01 p.2]

### Function calls copy values, including pointer values

In [[concepts/parameter-passing|parameter passing]], the **caller** invokes a function and the **callee** receives its arguments. The lecture contrasts copying an ordinary value with copying an address through which the original object can be accessed. [STT 58:23] [STT 59:22] [M01 slide 41]

**Source comparison: the same return value, different effects.**

| Version | Argument received by the callee | Effect on the caller’s `x`, initially 5 | Return value when `y` is 6 |
|---|---|---:|---:|
| Integer parameter | Copy of `x` | `x` remains 5 | 16 |
| Pointer parameter | Copy of `&x` | `x` becomes 10 | 16 |

In the value version, doubling the local parameter does not modify the caller’s integer. In the pointer version, the callee doubles the integer reached by dereferencing the copied address. [M01 slide 42] [M01 slide 43]

The slides call the second behavior “pass by reference.” For C, read that phrase as a description of the effect achieved through a pointer: **the pointer value is still copied**. It does not introduce a separate C parameter-passing mechanism. [STT 59:22] [M01 slide 43]

**Source code and assembly trace.**

```c
int foo2(int *a, int b)
{
    *a = 2 * *a;
    return *a + b;
}
```

The source assembly is:

```asm
mov (%rdi), %eax
add %eax, %eax
mov %eax, (%rdi)
add %esi, %eax
ret
```

For the slide’s `*a == 5` and `b == 6`:

| Instruction | Meaning | Result |
|---|---|---|
| `mov (%rdi), %eax` | Load the integer at the address in `%rdi` | `%eax = 5` |
| `add %eax, %eax` | Double the loaded value | `%eax = 10` |
| `mov %eax, (%rdi)` | Store through the address in `%rdi` | Caller’s integer becomes 10 |
| `add %esi, %eax` | Add `b` | `%eax = 16` |
| `ret` | Return using the example’s convention | Returned value is 16 |

The parentheses in `(%rdi)` denote memory access through the register’s address. The store changes the pointee; it does not replace `%rdi` with 10. This is also direct evidence that the earlier stack-based explanation of parameters was not a universal placement rule. [STT 01:00:25] [STT 01:01:24] [M01 slide 44]

#### Array arguments connect pointer passing to byte offsets

The array example passes its starting location rather than copying all ten elements. The callee’s assignment `a[2] = 5` therefore changes the caller’s third element from 2 to 5. [M01 slide 45]

With four-byte integers, index 2 means a byte offset of:

$$
2 \times 4 = 8.
$$

The source instruction is:

```asm
movl $0x5, 0x8(%rdi)
```

It stores the immediate value 5 at the address `%rdi + 8`. It is a store, not a load, and the offset is eight bytes rather than “eight times two.” The unclear spoken wording does not change the visible instruction’s operation. [STT 01:02:17] [M01 slide 46]

#### Command-line arguments are an array of string pointers

The same pointer model explains:

```c
int main(int argc, char *argv[])
```

`argc` gives the argument count, while `argv` provides pointers to argument strings. The slide’s loop accesses entries while `i < argc`; its ordinary invocation example treats `argv[0]` as the program name. [STT 01:02:17] [STT 01:03:22] [M01 slide 47]

## Key Takeaways

- **Identify the object before interpreting an expression.** A pointer’s address, its stored address, and its pointee are different.
- **Keep process context attached to addresses.** Equal virtual-address numbers do not establish shared state.
- **Keep storage quantities separate.** Object size, allocation capacity, member offset, padding, and array stride answer different questions.
- **Use the stated target assumptions.** The instructor specifically prioritizes common type sizes on x86-64 Linux; historical and cross-platform rows remain bounded comparisons. [STT 37:11] [STT 41:29]
- **C calls copy values, including pointer values.** A store through a copied pointer can change the caller’s object while leaving the pointer register unchanged.
- **Dirtree’s visible output is not its countable set.** Nonmatching ancestors can appear only to show the route to matching descendants.
- **Exact requirements matter independently of implementation.** Formatting, memory ownership, permitted APIs, build conditions, and submission rules remain part of the assignment.
- **Respect the session boundary.** Detailed paging, address-translation calculations, and a complete shared-memory implementation are later work. [STT 13:08] [STT 42:29]
