## Lecture Content and Explanation

### What System Programming studies
System Programming starts with an operating system already present and asks how an application uses its services. An API specifies how to request a service; a system call crosses into the operating system to obtain one. The emphasis is on the external interface and application–system interaction. An Operating Systems course instead studies how those mechanisms are implemented internally. C programming, data types and algorithms are assumed background. Computer Architecture is recommended for its CPU, pipelining and instruction-level perspective, but the lecturer did not make prior enrollment an absolute condition.

This foundation supports later work in compilers, databases, networks and embedded systems. The semester roadmap includes file systems, memory, processes and exceptions, shells, networking and concurrency. This first meeting covered motivation, computer trends and a C overview; dedicated pointer practice and file systems were announced as subsequent topics. Their presence among available slide files does not make them September 2 coverage.

### A service has clients, servers and a delivery path
A messaging application such as KakaoTalk has a client on the user's device and supporting servers in the cloud. The device is therefore only part of the running service. A video service adds a useful distribution problem: sending every video from one distant site is expensive and slow. A Content Distribution Network (CDN) places content at multiple locations so requests can be served from a suitable nearby copy. The lecture used YouTube and the CoBlitz project to motivate this distributed infrastructure.

The “browser finds the closest server” description is an introductory abstraction, not a specification of an actual browser routing protocol or a guarantee of geographic distance. The important relationship is client demand → placement and delivery decisions → machines and networks that execute software. Later networking topics explain more of the mechanism.

### Manuals turn unfamiliar interfaces into usable tools
The lecture demonstrated `man strstr` as a way to find a library function's declaration and behavior. Before using an unfamiliar function, identify its argument types, return value and required header; a similar name is not a sufficient specification. GNU debugging material and Intel architecture manuals were additional examples of documentation suited to different layers: a library call, a debugger and the instruction set do not answer the same questions. ### Debugging and independent implementation are learning activities
Readable code makes the program's intention visible when its behavior is wrong. A systematic debugging report includes the input, observed output, expected output and the reasoning that suggests a fault. Reproduce the symptom before changing code. Asking a TA to infer the entire problem from an unexplained source dump removes this useful evidence. Course advice was to read the material beforehand, internalize basic C grammar and allocate roughly 7–10 hours a week; that is study guidance, not a promised completion time.

The lecturer emphasized learning through one's own implementation and critical thinking. Course materials prohibit handing code to AI to have it written or fixed. The same policy says to turn off automatic code completion in editors and to write submitted documents and reports yourself. Concept explanations and tracing exercises in these notes support understanding; they do not supply a lab solution. When stuck, use eTL, office hours or TA sessions with a concrete question and what you have already tried.

### Why C and Linux matter for system software
Software supports large services and cloud infrastructure, creating demand for programs that use machines efficiently. Company examples motivate that demand; they are not a current market ranking. C combines relatively expressive statements and functions with direct access to memory and low-level I/O. The lecturer contrasted it with higher-level languages such as Python to explain control over resources. This does not establish that every C program is faster than every program in another language.

C also provides a practical portability compromise: operating-system services and most of a program can be expressed in a higher-level language, while some machine-specific assembly remains necessary. Portability requires compatible interfaces and assumptions, not just the same source extension. Linux supplies an open-source operating system and a rich set of development tools that can be inspected and used in teaching. Together, C and Linux expose the relationship between source code, machine behavior and operating-system services.

### A general-purpose computer includes communication
A general-purpose processor runs different programs instead of being fixed to one application. Multicore CPUs provide several execution resources; the hardware pictures motivate why software may need to coordinate work across them. An uncertain identification of one photographed accelerator is not used as a definitive GPU model name.

Network bandwidth is another resource. The lecturer contrasted approximately 1 Gbps PC links with 10–100 Gbps datacenter links as illustrative examples. These are lecture-context numbers, not current universal specifications. A program that can compute quickly may still wait for data moving between machines, so system performance depends on more than CPU arithmetic.

### Smaller computers appear in more places
The historical progression from ENIAC in 1946 through IBM-era systems of the 1960s to smartphones illustrates shrinking physical size and increasing capability. Very large performance multipliers mentioned orally are broad comparisons without a shared benchmark; they should not be used as precise measured ratios. The lesson is that more functionality can fit in smaller devices.

Ubiquitous computing extends this trend into cars, watches and everyday equipment. A computer need not look like a desktop. These examples explain why understanding the hardware–software interface remains relevant even when the user sees an appliance rather than a terminal.

### Datacenter scale, racks and memory communication
A datacenter rack houses multiple servers; racks and their network connections turn individual computers into service infrastructure. The lecture's rack figure should be read at these two scales: one machine executes instructions, while a collection of machines provides capacity and resilience for a service.

The lecturer cited roughly four million Microsoft servers in a 2021 example and 2.5 million Google servers in a 2016 example. Current private fleet sizes were not established. A roughly $600 billion 2026 infrastructure figure was presented as a forecast, not an observed completed expenditure. Any rough currency conversion belongs to that historical classroom discussion, not current financial information.

GPU training and inference motivate expensive high-bandwidth memory (HBM) and fast communication. If useful data is distributed across devices, obtaining remote data adds communication and latency costs that local arithmetic alone cannot remove. The petabyte-scale remark illustrates a capacity problem, not a theorem that a particular memory size is universally impossible. The course's software perspective is to understand how memory placement, networking and computation interact.

### C grew with Unix and acquired standards
The history connects BCPL, B and C with work around Multics and Unix. Ken Thompson and Dennis Ritchie are central names in that account; their 1983 Turing Award was mentioned. Rewriting much of Unix in C reduced dependence on machine-specific assembly and made moving the system to other machines more practical.

Kernighan and Ritchie's book popularized C before the standardized language. ANSI C89 and ISO C90 refer to closely corresponding standardization milestones. C99 is the course target. Later versions, including C23, were mentioned as context; their features should not silently enter assignments compiled with `-std=c99`.

[STT 54:41] [STT 55:41] [STT 56:32] [STT 57:11] [M04 slide 45] [STT 58:00] [STT 58:44]

The lecturer associated Ken Thompson with B and Unix and Dennis Ritchie with C. B already had ++ and --, but the significant comparison was its lack of C-like distinctions among data types: data was treated with a common word-oriented model. C introduced richer type distinctions. The classroom narrative described Multics as an ambitious, complex computing-service project, likened to a utility, that helped inspire a simpler Unix. This account motivates the desire for a higher-level systems language to replace CPU-specific assembly; it is not an independent complete history of either project. ### Abstraction organizes a larger program
Structured programming organizes work with functions and control structures. A function hides a sequence of steps behind a name and an interface, making a larger program easier to reason about. Assembly can also implement subroutines; the lecturer's broad contrast about assembly lacking “functions” concerns convenient language-level structure, not a literal impossibility of calls or reusable code.

Object-oriented programming groups state with operations exposed through an interface. This is another organization method, distinct from merely dividing code into free-standing functions. C is primarily the course's tool for procedural and system-level work; the comparison explains abstraction, not an additional C++ curriculum.

### From Hello World to an operating-system service
Consider the small program below, matching the lecture's basic structure:

```c
#include <stdio.h>

int main(void)
{
    printf("hello world\n");
    return 0;
}
```

The header provides the declaration needed to use `printf`; `main` is the program's entry function in this hosted example, and returning zero reports successful completion. The course command `gcc800 hello.c` builds an executable named `a.out` by default; `./a.out` runs the file in the current directory. Compilation and execution are separate steps.

`printf` performs formatted output in a user-space library. Output eventually relies on an operating-system facility such as `write`; `printf` itself is not synonymous with a system call. Similarly, mathematical routines, `strlen` and `strstr` can do library work without each operation inherently entering the kernel. Standard output normally appears in the terminal, but redirection later shows that the destination can differ. Detailed buffering and I/O error handling are later material.

### Program state lives in typed objects
A useful model is a collection of states changed by commands. A variable gives a name and type to an object whose stored value contributes to the state. The type determines what values and operations make sense and affects storage requirements.

Under the course's x86-64/Linux assumptions, `char`, `short`, `int` and `long` occupy 1, 2, 4 and 8 bytes respectively. These are environment assumptions: a 64-bit operating system alone does not force every C implementation to use an 8-byte `long`.

Floating-point values use a sign, exponent and significand (often called a mantissa in introductory explanations). The lecture connected this representation to IEEE 754 and listed 32-, 64- and 128-bit storage examples for `float`, `double` and `long double`. Storage size is not identical to precision: an object occupying 128 bits need not implement IEEE binary128 arithmetic. Exact widths and supported formats belong to the compiler and ABI. The purpose of the introductory diagram is to explain why floating-point storage has structure, not to derive all rounding rules.

[STT 01:13:18] [STT 01:13:59] [M04 slide 50] [STT 01:14:56] [STT 01:15:55] [M04 slide 51] [STT 01:16:42]

Finite binary representations cannot represent every real value exactly, so floating-point storage and computation can introduce representation or rounding error. The lecture introduced IEEE754 as the associated standard and sign, exponent and mantissa as the basic components. This introductory error point is separate from, and retained alongside, the storage-versus-precision qualification above; detailed numerical analysis was not covered. ### A pointer stores an address, not its target value
C's address-of operator `&` obtains an object's address; unary `*` accesses the pointed-to object when the pointer is valid. In `int x=102; int *p=&x;`, `p` holds the address of `x`, while `*p` is the int value 102. Changing `*p` changes `x`; changing a pointer variable changes where it points.

The slide's memory picture uses a schematic address label 2 for `x`. The slide shows x's stored value102 at schematic address label2, while the STT records ‘1 or2’ for x's value. That spoken-value conflict remains unresolved; the material determines the values used in this explanatory diagram. It is not an actual `%p` result, an alignment guarantee, or a to-scale byte layout. Byte addressing means adjacent addressable units are bytes rather than whole machine words.

In the course model, `sizeof p` is 8 while `sizeof *p` is 4. Equal-size pointer objects can nevertheless have different pointed-to types. A `void *` can hold an object address, but strict C does not permit dereferencing it as though `void` were an ordinary sized object type. The actual target type must be established before typed access.

### Constants and preprocessing serve different roles
`#define MAX 10` introduces preprocessor token replacement; it is not an ordinary variable declaration. `const int limit=10;` declares a typed object whose modification is restricted, while an enumeration can introduce named integer constants. These choices are related by the goal of giving values meaningful names, but their language rules differ.

Preprocessing occurs before normal compilation. `#include` makes header contents available, and `#pragma` carries implementation-related directives. A header is not a request to execute a library function: inclusion supplies declarations and other source content; a call is a separate expression in the program.

### Arrays collect similar objects; structures collect named fields
`char c[10]` reserves ten char elements. `double pi[5][2]` contains five arrays of two doubles, so with 8-byte doubles its total size is `5*2*8=80` bytes. This is the array object's size, not the 8-byte size of a pointer. An array expression often converts to a pointer to its first element, but this conversion does not make the declared array itself a pointer object.

A structure instead combines named members, possibly of different types: a student can have an integer ID and a pointer to a name. An array groups elements with the same element type and index-based access. The lecture introduced this distinction without teaching detailed padding calculations; adding member sizes is not generally a justified way to compute an arbitrary structure's size.

### A C string is a convention over characters
A C string is a character sequence terminated by a null character, `\0`. The terminator marks the end for string-processing functions; it is not an ordinary visible character. A pointer initialized with `char *s="hello world\n";` refers to the string literal's first character. An alternative declaration such as `char s[20]="SNU CSE00800";` creates its own array storage. These are alternative examples, not two declarations of the same name in one scope.

Attempting to modify a string literal through the first pointer has undefined behavior. The lecturer discussed a likely crash in the target environment; a crash is not the definition or a guaranteed result of undefined behavior. The initialized local array is writable within its valid bounds. The modification-target demand in2025-1 Q1(c)(1) is partially relevant: identify the object reached by a write before judging whether modification is allowed. That narrow demand supports the new literal/array practice here; the original task’s complete crash list and memory-section analysis require later environment details. A supplied observed crash list is not the definition of C undefined behavior. [EX:sp_2025_1_midterm_q01 p.3] Thus “a pointer is unwritable” is the wrong rule: identify the object being accessed and whether modification of that object is permitted.

### Expressions compute values and may change state
C supplies arithmetic, relational, logical, bitwise and assignment operators. `%` computes an integer remainder. Logical operators combine truth conditions, while bitwise operators act on individual bits. The slide's duplicated assignment entry is not evidence for a guessed missing operator, so it is not silently reconstructed.

An expression such as `2` or `2+3` has a value. A function call can also produce a value, and a call to a function returning `void` is still an expression, but it does not produce a usable result value. An assignment both changes an object and has a value: `i=j=0` groups as `i=(j=0)`, giving both variables zero. Right associativity describes this grouping; it is not a general statement about the evaluation order of every C expression.

An operator acts on operands: in a+b, + is the operator and a,b are operands. ### Statements control which state changes occur
An `if` chooses a path from a condition. A `switch` selects a case based on an expression; `break` commonly prevents execution from continuing into a later case, and `default` handles unmatched values. Not every statement is simply an expression followed by a semicolon: compound statements use braces to group several statements.

`for` brings initialization, continuation test and iteration update together. `while` tests before the body and may run zero times; `do ... while (condition);` tests afterward and runs its body at least once. The trailing semicolon belongs to the valid do-while form even where a slide's abbreviated example omits it.

`break` leaves the nearest enclosing loop or switch. `continue` moves to the loop's next iteration behavior, not out of the whole loop. `goto` transfers control to a label; escaping nested work or sharing cleanup were discussed as motivations, not reasons to replace every structured loop. C comments use `/* ... */` and, in the course's C99 mode, `//` to the end of the line. Braces establish a compound statement; comment markers instead make explanatory source text non-executable.

The source example `if (i < 0) statement1; else statement2;` selects statement1 when i is negative and statement2 when i is zero or positive. Its switch selects statement1 for i=1, statement2 for i=2, and statement3 for unmatched values, with break ending each selected case. [M04 slide 56]

For a concrete branch example, `if (x > 0) sign = 1; else sign = 0;` sets sign to 1 for x=3 and to 0 for x=0. In `switch (x) { case 1: y=10; break; default: y=20; }`, x=1 gives y=10; an unmatched x gives y=20. Removing break can cause fall-through into later code. These small examples explain the control structures rather than claim an exact reconstruction of the slide's code. [M04 slide 56]

### Functions and readable names make a calculation inspectable
`int add(int x, int y) { return x+y; }` declares two int parameters and an int result. `add(3,5)` therefore yields 8. A function returning `void` has a different contract: callers cannot use an absent result as an integer. Parameters and return values make a computation reusable without duplicating its body.

The final temperature example converts Fahrenheit values from 0 through 300 in steps of 20 using $C=(5.0/9.0)(F-32)$. At $F=0$, $C\approx-17.78$; at $F=100$, $C\approx37.78$; at $F=300$, $C\approx148.89$. Floating operands in `5.0/9.0` avoid the zero result of integer `5/9`. The following is a typed-out explanatory version of the slide example, not recovered verbatim speech:

```c
#include <stdio.h>
int main(void)
{
    int fahr;
    int lower = 0, upper = 300, step = 20;
    for (fahr = lower; fahr <= upper; fahr += step) {
        double celsius = (5.0 / 9.0) * (fahr - 32);
        printf("%3d %6.1f\n", fahr, celsius);
    }
    return 0;
}
```

Names such as `fahr`, `celsius`, `lower`, `upper` and `step` communicate roles more directly than `a`, `b`, `c`, `d` and `e`. The loop produces 16 rows, including both endpoints. The recording ends with this readability example and an announcement of subsequent pointer/file-system work, not a completed file-system lesson.

## Key Takeaways

- System Programming uses an existing operating system through its interfaces; the semester roadmap is broader than today’s completed coverage.
- Course environment assumptions must be explicit. Build success, warnings and correct runtime behavior are separate checks.
- Distinguish pointer storage from target values, array storage from conversion and string literals from writable arrays.
- Expressions, statements and functions have different roles; assignment grouping is not a universal evaluation-order rule.
- Readable independent implementation and systematic debugging are part of the course’s learning goals.
