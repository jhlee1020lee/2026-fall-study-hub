## 수업 직후 10분 복습

운영체제는 **hardware를 application이 사용하기 좋은 형태로 바꾸어 제공하는 software**다. 가장 아래에는 CPU·memory·disk 같은 hardware가 있고, 그 위에 OS kernel, software development environment와 middleware, application이 놓인다. 이 계층 구조 덕분에 application은 hardware 세부사항을 매번 직접 다루지 않고 OS가 제공하는 interface를 이용할 수 있다. [STT 05:01-06:02] [M01 p.3]

kernel은 단순히 “application이 아닌 모든 software”와 같지 않다. kernel은 privileged instruction과 system register에 접근할 권한을 가진 핵심 software다. compiler·loader·editor·utility·library는 system software일 수 있지만 반드시 kernel mode에서 실행되는 것은 아니다. middleware는 서로 다른 OS나 system의 interface 차이를 흡수해 application과 distributed system을 연결하는 계층으로 설명되었다. [STT 06:02-11:34] [M01 p.3]

OS 발전의 동력은 비싼 CPU를 놀리지 않고, 여러 user에게 더 빠른 반응을 주려는 요구였다. 2세대 resident system은 한 번에 job 하나만 실행했기 때문에 I/O 중 CPU가 쉬었다. 3세대 multiprogramming은 한 job이 I/O를 기다릴 때 다른 job에 CPU를 주어 utilization을 높였고, time-sharing은 terminal 앞에서 기다리는 user의 response time을 줄이는 방향으로 발전했다. [STT 15:56-37:29] [M01 p.5-8]

그 과정에서 job scheduling, memory management, CPU scheduling, protection, spooling이 필요해졌다. time-sharing에는 더 정교한 CPU scheduling, virtual memory와 swapping, file system, synchronization, IPC, interactive shell이 추가된다. 1960년대의 CTSS, OS/360, Multics, Unix는 이 변화의 핵심 사례이며, 특히 Unix는 현대 OS에 남은 단순하고 강력한 interface를 정착시켰다. [STT 28:59-42:11] [M01 p.7-10]

## 핵심 개념

### 1. OS를 계층으로 보기

```text
Applications
     ↓ service / interface
Middleware · libraries · development environment
     ↓
Operating System (Kernel)
     ↓ privileged control
Computer System Architecture (Hardware)
```

이 그림에서 가장 중요한 것은 **경계**다. application이 요청한 작업 중 hardware control과 protection이 필요한 부분은 kernel이 담당한다. kernel의 privilege는 막연한 권력이 아니라 privileged instruction을 실행하고 system register에 접근할 수 있다는 구체적인 차이다. [STT 05:01-08:45] [M01 p.3]

middleware는 여러 OS의 interface 차이를 가리는 library 성격의 계층이다. 예를 들어 같은 application이나 distributed system이 macOS, Linux, Windows처럼 서로 다른 환경과 통신해야 할 때 공통 interface를 제공할 수 있다. 따라서 middleware와 kernel은 application 아래에 있다는 점은 비슷하지만 역할과 실행 권한이 다르다. [STT 09:45-11:34]

### 2. 한 job씩 실행하면 왜 CPU가 노는가

2세대 resident system은 boot 시 memory에 상주해 system을 initialize하고 job을 받아 실행한 뒤, 종료되면 control을 되돌려받는다. 구조가 단순하지만 실행 중인 job이 card reader, disk, printer, keyboard 같은 느린 I/O를 기다리면 다음 job으로 넘어가지 못한다. 빠르고 비싼 CPU가 느린 I/O 때문에 idle 상태가 되는 것이 핵심 병목이다. [STT 14:56-22:58] [M01 p.5]

```text
single-job system:  Job A ─ CPU ─ I/O 대기(그동안 CPU idle) ─ CPU

multiprogramming:  Job A ─ CPU ─ I/O 대기 ──────────────── CPU
                   Job B ──────── CPU ─ I/O 대기 ─ CPU ───────
```

### 3. multiprogramming: CPU utilization 높이기

multiprogramming system은 여러 job을 memory에 두고, 실행 중인 job이 I/O를 기다리면 CPU를 다른 job에 넘긴다. CPU가 하나라면 어떤 한 순간에 실제로 실행되는 job은 하나뿐이다. 여러 job이 동시에 진전되는 것처럼 보이지만 이것을 여러 CPU에서의 물리적 parallel execution과 동일시하면 안 된다. [STT 28:59-29:18] [M01 p.7]

이때 두 종류의 선택이 필요하다.

| 구분 | 선택 대상 | 강의의 질문 |
|---|---|---|
| job scheduling | 대기 중인 job 가운데 memory에 올릴 job | “다음에 어떤 job을 system에 받아들일 것인가?” |
| CPU scheduling | 이미 memory에 올라온 runnable program 가운데 CPU를 받을 것 | “지금 CPU를 누구에게 줄 것인가?” |

memory 공간, job 크기, 도착 순서 같은 조건은 job scheduling에 영향을 준다. 실행 중인 program이 I/O를 기다리게 되었을 때 memory 안의 다른 program을 고르는 것은 CPU scheduling 문제다. protection과 concurrency 관리도 여러 program이 함께 존재하기 때문에 중요해진다. [STT 30:14-32:06] [M01 p.7]

spooling은 느린 peripheral을 기다리는 시간을 줄이는 대표 기법이다. print할 내용을 우선 disk에 저장하고 background 작업이 printer로 보내게 하면, foreground program은 실제 출력 완료까지 CPU를 붙들고 있을 필요가 없다. 이름은 `Simultaneous Peripheral Operation On-Line`에서 왔다. [STT 32:06-33:08] [M01 p.7]

### 4. time-sharing: response time 줄이기

multiprogramming의 일차 목표가 CPU utilization이라면 time-sharing의 일차 목표는 interactive user가 느끼는 response time이다. batch 환경에서는 job을 제출하고 나중에 결과를 받지만, time-sharing에서는 여러 terminal의 user가 직접 system을 사용한다. 이때 response time은 job 전체가 끝나는 시간이 아니라 **요청을 보낸 뒤 첫 반응이 오기까지의 시간**이다. [STT 33:36-36:22] [M01 p.8]

time-sharing을 위해서는 더 정교한 CPU scheduling뿐 아니라 virtual memory와 swapping, file system, synchronization, IPC, interactive shell, 더 강한 protection이 필요하다. virtual memory는 각 process에 실제 physical memory보다 큰 memory가 있는 것 같은 abstraction을 제공한다. [STT 36:22-37:29] [M01 p.8]

### 5. 세대별 발전을 문제와 해법으로 묶기

| 시기 | hardware·사용 방식 | OS 관점의 변화 | 해결하려던 문제 |
|---|---|---|---|
| 1G, 1945-55 | vacuum tube, plugboard | OS와 programming language가 없음 | 계산 자체를 자동화 |
| 2G, 1955-65 | transistor, mainframe, card/tape/printer | resident system, one job at a time | job loading과 control transfer 자동화 |
| 3G, 1965-80 | IC, disk, online terminal | multiprogramming과 time-sharing | CPU utilization과 response time 개선 |
| 4G, 1980- | microprocessor, PC, 큰 storage, network | GUI, multimedia, distributed/mobile, virtualization | 개인·연결 환경에서의 편의와 확장 |

computer architecture라는 stable interface도 3세대의 중요한 변화다. CPU 내부 구현과 성능이 달라져도 instruction, register, encoding 같은 software-visible interface를 유지하면 기존 compiler와 software를 재사용할 수 있다. 같은 논리로 OS가 기존 interface를 유지하면 application compatibility를 지킬 수 있다. [STT 24:02-28:02] [M01 p.6]

### 6. CTSS에서 Unix까지

| 연도 | system | 이 강의에서의 의미 |
|---|---|---|
| 1961 | MIT CTSS | 초기의 대표적 time-sharing system |
| 1964 | IBM OS/360 | fixed/variable number of tasks를 지원한 multiprogramming |
| 1965 | Multics | 현대 OS와 닮은 방대한 기능을 통합한 time-shared multiprocessor system |
| 1969 | Unix | 값싼 hardware에서 단순하고 이식성 높은 핵심 기능을 구현 |

Multics는 hierarchical file system, ACL, virtual memory, user-level shell, dynamic linking, shared memory, high-level language 구현, logical-to-physical volume mapping 등 많은 아이디어를 앞서 통합했다. 그러나 top-down 방식으로 목표가 크고 system과 hardware가 복잡·고가였다. 강의자료는 design/system programming에 150 man-years, 개선에 50 man-years가 들었다고 제시한다. [STT 44:13-47:38, 01:07:47-01:08:45] [M01 p.10-11, p.16]

Unix는 제한된 PDP-7 환경에서 bottom-up으로 출발했다. 초기에는 assembly로 작성되었고, Dennis Ritchie가 B를 발전시켜 만든 C로 다시 구현되면서 portability를 높였다. hierarchical file system과 i-node, device를 file처럼 다루는 special file, `fork()`·`exec()`·`wait()`·`exit()`, pipe, shell, redirection, signal 같은 작고 결합 가능한 interface가 핵심이다. [STT 48:54-57:49] [M01 p.12-13]

### 7. Unix 계보를 한 줄로 합치지 않기

- 전통적인 Unix license는 Bell Labs/AT&T에서 여러 회사로 이동한 역사가 있다. 강의에서는 Novell, SCO, Caldera/The SCO Group과 SCO 대 IBM 소송을 사례로 다뤘다. [STT 58:28-01:02:06] [M01 p.14]
- BSD는 Unix에서 갈라져 FreeBSD·NetBSD·OpenBSD로 발전했고, socket 등 중요한 기능을 남겼다. SunOS와 이후 Solaris도 이 흐름 및 System V의 영향을 받았다. [STT 01:03:09-01:05:23]
- Linux는 그림의 전통적인 Unix license 계보에 직접 놓이지 않으며, 강의에서는 Minix의 영향을 받은 별도 구현으로 설명했다. [STT 01:06:03]
- macOS kernel에는 BSD 계열의 구성 요소가 활용되며, AIX처럼 회사가 자체적으로 발전시킨 Unix 계열도 있다. [STT 01:06:03-01:07:18]

### 8. Windows의 두 층위

초기의 consumer Windows는 MS-DOS 위에 GUI를 더한 계열이었고, 한 번에 하나의 program을 다루던 DOS의 한계를 안고 있었다. 이후 Microsoft는 DEC에서 VMS를 개발하던 인력을 영입했고, 이들이 Windows NT 개발의 주축이 되었다. application이 보는 Windows API의 연속성은 유지하면서 OS 내부 기반은 NT 계열로 바뀌어 오늘날까지 이어진다는 것이 강의의 요점이다. [STT 01:08:45-01:13:01]

## 헷갈리기 쉬운 지점

1. **OS와 kernel은 완전히 같은 범위가 아니다.** 넓은 의미의 OS 주변에는 utility와 library도 있지만, kernel은 privilege를 가진 핵심 실행부다.
2. **multiprogramming은 single CPU에서의 parallel execution이 아니다.** I/O 대기 시간을 이용해 CPU가 다른 job으로 전환되며 concurrency가 생긴다.
3. **job scheduling과 CPU scheduling은 다르다.** 전자는 memory에 받아들일 job, 후자는 memory 안에서 CPU를 받을 실행 대상을 고른다.
4. **response time은 completion time이 아니다.** 요청 이후 첫 반응까지의 지연이다.
5. **GUI·Web·multimedia 전체가 kernel 기능인 것은 아니다.** 많은 부분은 user-level application과 service로 구현된다. [STT 38:05-40:17]
6. **Multics가 실패했고 Unix가 모든 아이디어를 새로 발명했다는 식으로 외우면 안 된다.** Multics가 남긴 많은 아이디어 중 핵심을 Unix가 더 단순한 환경에서 구현·확산시켰다는 비교가 정확하다.
7. **Linux를 전통적인 Unix license의 직계 계보로 넣으면 안 된다.** Unix와 유사한 interface와 철학을 갖지만 강의의 family tree에서는 별도 구현으로 설명된다.
8. **역사 일화는 slide로 고정되는 사실과 구분했다.** 44:13-55:45를 겹치는 2분 clip으로 재확인했고, 기존 STT·분할 ASR·slide가 함께 지지하는 내용만 노트에 사용했다.

## 능동회상 문제

1. OS를 한 문장으로 정의하고, kernel의 privilege를 instruction과 register 관점에서 설명해 보라.
<details><summary>정답</summary>OS는 hardware를 application이 사용하기 좋은 형태로 바꾸어 제공하는 software다. kernel은 privileged instruction을 실행하고 보호된 system register에 접근할 수 있다.</details>

2. single-job resident system에서 I/O가 CPU utilization을 떨어뜨리는 과정을 그려 보라.
<details><summary>정답</summary>실행 중인 유일한 job이 느린 I/O를 기다리는 동안 다음 job으로 전환할 수 없어 CPU도 함께 idle 상태가 된다.</details>

3. multiprogramming에서 job scheduling과 CPU scheduling은 각각 무엇을 고르는가?
<details><summary>정답</summary>job scheduling은 대기 job 중 memory에 받아들일 것을, CPU scheduling은 memory 안의 runnable program 중 지금 CPU를 받을 것을 고른다.</details>

4. spooling이 printer와 CPU 사이의 속도 차이를 어떻게 숨기는가?
<details><summary>정답</summary>출력 내용을 먼저 disk에 저장하고 background 작업이 느린 printer로 보내게 해 foreground program이 출력 완료를 기다리지 않게 한다.</details>

5. time-sharing에서 response time이 중요한 이유와 이를 위해 추가된 OS 기능 세 가지를 말해 보라.
<details><summary>정답</summary>terminal 앞의 user가 직접 기다리기 때문에 첫 반응까지의 시간이 중요하다. 정교한 CPU scheduling, virtual memory/swapping, synchronization·IPC·interactive shell·강한 protection 등을 들 수 있다.</details>

6. Multics와 Unix를 개발 접근법, 비용·복잡성, hardware, 영향 측면에서 비교하라.
<details><summary>정답</summary>Multics는 고가 hardware에서 방대한 기능을 top-down으로 통합해 많은 아이디어를 남겼고, Unix는 값싼 hardware에서 핵심 기능을 bottom-up으로 단순하게 구현해 대학과 연구소에 널리 퍼졌다.</details>

7. Unix의 file/process/shell interface 가운데 현대 system programming에서도 보이는 예를 네 가지 들어라.
<details><summary>정답</summary>i-node와 hierarchical file system, special file, `fork()`/`exec()` process control, pipe, standard I/O redirection, signal 중 네 가지를 들 수 있다.</details>

8. Linux, BSD, System V, macOS를 모두 “같은 Unix”라고 말하면 무엇이 부정확한가?
<details><summary>정답</summary>전통적인 Unix license 계열, BSD 파생 계열, 별도 구현인 Linux, BSD 구성 요소를 활용한 macOS는 역사와 code lineage가 서로 다르다.</details>
