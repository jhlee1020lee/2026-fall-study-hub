9월 17일 실습은 Object-Oriented Programming(객체지향 프로그래밍, OOP)을 복습한 뒤 Lab3의 상태와 동작을 읽는 수업이다.  
Object의 생성·공유·변경을 구분하고, 과제에서 확인된 요구사항과 미완성 설명의 경계를 함께 정리한다.

## 강의 내용과 설명

### Object-Oriented Programming(객체지향 프로그래밍, OOP): 대상과 상호작용으로 프로그램 바라보기

OOP는 소프트웨어를 서로 상호작용하는 **Object(객체)**들의 모음으로 바라보는 방식이다. Object는 프로그램에서 표현하려는 대상이며, 현실의 물건에만 한정되지 않는다. 자동차처럼 물리적인 대상뿐 아니라 계좌처럼 개념적인 대상도 Object로 표현할 수 있다. 이번 실습에서는 이러한 관점을 복습한 뒤 두 플레이어가 대결하는 게임에 적용한다고 안내한다. [STT 00:00] [M01 p.3] [M01 p.4]

**자료 그림 읽기 — 현실의 대상과 모델의 관계.** M01 p.3은 위쪽에 집·사람·자동차를, 아래쪽에 이들을 표현한 모델을 배치한다. 아래 그림에서 중요한 것은 상자뿐 아니라 상자를 잇는 관계이다. 사람이 집에 거주하고 자동차를 운전한다는 관계를 함께 표현해야 대상들이 하나의 시스템을 이룬다. OOP를 이해할 때는 “어떤 Object가 있는가?”와 “그 Object들이 어떻게 관계를 맺고 동작하는가?”를 함께 살펴야 한다. 이 그림은 강의 개념을 보충하는 자료이며, 이번 녹음에서 그림의 모든 요소를 설명했다는 뜻은 아니다. [M01 p.3]

M01 p.4는 자동차, 계좌, Linked List(연결 리스트)를 나란히 놓는다. 여기서 Linked List의 구현을 배우는 것은 아니다. 소프트웨어 내부에서 사용하는 구조도 Object가 나타내는 대상이 될 수 있다는 점을 읽으면 된다. 따라서 “Object는 화면에 보이는 물건을 그대로 코드로 옮긴 것”이라는 이해는 너무 좁다. [M01 p.4]

**Procedural Style(절차 중심 방식)**과 비교하면 차이가 더 분명해진다. 자료의 커피 만들기 예시에서 Procedural Style은 원두 준비, 분쇄, 물 준비, 끓이기, 섞기와 같은 작업 순서를 나열한다. Object-Oriented Style은 분쇄·끓이기·섞기 기능을 수행하는 Coffee Machine을 구성하고, 그 대상에 원두와 물을 넣어 작업하게 한다. [M01 p.5] [M01 p.6]

두 방식 모두 실제 작업 순서는 필요하다. 차이는 프로그램을 설명하고 구성할 때 작업을 어디에 묶느냐에 있다. Coffee Machine 예시에서는 관련 기능을 하나의 대상에 묶어 생각한다. OOP를 사용한다고 조건문이나 순차 실행이 사라지는 것은 아니다. 이 커피 예시는 이번 회차의 발화를 복원한 것이 아니라 자료에 근거한 설명이다. [M01 p.5] [M01 p.6]

### Class(클래스), Instance(인스턴스), Instantiate(인스턴스 생성하기)

Class는 Object를 만들기 위한 **blueprint(설계도)** 또는 **template(틀)**이다. 하나의 Class로 여러 Object를 만들 수 있으며, 그렇게 만들어진 각각의 Object를 Instance라고 부른다. Instantiate는 그 Instance를 만드는 행위를 가리킨다. 설계도, 만들어진 대상, 만드는 행위를 구별하는 것이 출발점이다. [STT 01:51] [STT 02:44] [STT 03:40] [M01 p.7] [M01 p.17]

**자료 그림 읽기 — 틀과 결과물.** M01 p.7의 붕어빵 틀은 Class, 틀에서 만들어진 개별 결과물은 Object의 비유이다. 옆의 자동차 그림도 하나의 `Car` Class와 여러 자동차 Object를 구분한다. 그림에서 읽어야 할 것은 “같은 틀을 사용했다”와 “동일한 하나의 대상이다”가 다른 주장이라는 점이다. 여러 Object가 공통 구조를 가진다고 해서 모두 같은 Object가 되는 것은 아니다. [M01 p.7]

자료의 기본 문법은 다음과 같다. [M01 p.9]

```java
class Car { }

Car myCar = new Car();
```

첫 줄은 `Car`라는 Class를 정의한다. 두 번째 줄의 `new Car()`는 그 Class의 Instance를 생성한다. `myCar`는 생성된 Object를 가리키는 변수이며, 뒤에서 설명할 reference(참조)를 통해 그 Object에 접근한다. `Car`라는 Class의 이름, `myCar`라는 변수의 이름, 생성된 Object 자체를 서로 구별해야 한다. [M01 p.9] [M01 p.36]

강의는 같은 Class에서 만들어진 Instance들이 공통 **Attributes(속성)**와 **Methods(메서드)**를 갖는다고 설명한다. 이 두 종류를 함께 **Members(멤버)**라고 부른다. 여기서 공통이라는 말은 어떤 상태와 동작을 갖는지에 대한 구조가 같다는 뜻이다. 각 Instance에 저장된 값까지 항상 같다는 뜻은 아니다. [STT 02:44] [M01 p.17]

**기출 적용 — 현재 접근 가능.** 파일명상 2025-1 중간고사로 분류된 복기본의 1번은 Class와 Object를 설명하도록 요구한다. 이 요구에는 Class를 설계도로, Object를 그 설계도로 만든 개별 대상으로 설명하고 둘의 관계를 연결하는 접근이 적절하다. 위 코드에서는 `Car` 정의와 `new Car()`에 의한 생성을 나누어 설명하면 된다. 용어를 각각 번역하는 데 그치거나 Class와 Object를 같은 것으로 설명하는 것이 함정이다. 해당 자료는 공식 원본으로 확인된 시험지가 아니라 복기본이며, 학기·담당교원 정보는 파일명에 의존한다. 현재 강의자료와 담당교원 표기도 다르므로 이번 수업의 출제 성향으로 일반화하지 않는다. [EX:cp_2025_1_midterm_q01 p.1]

### Attributes: Object의 상태를 저장하고 구별하기

Attributes는 Object의 외형, 상태, 그 밖의 성질을 나타내는 변수이다. 자동차의 폭이나 색처럼 “이 Object가 현재 어떤 상태인가?”에 답하는 정보를 담는다. 강의의 일부 설명 문구는 불명확하지만, Attributes가 상태나 성질을 나타낸다는 개념은 자료와 일치한다. [STT 02:44] [M01 p.8]

자료는 다음과 같이 `Car`에 두 Attributes를 선언한다. [M01 p.10]

```java
class Car {
    int width = 10;
    String color = "red";
}
```

`width`는 정수 값을, `color`는 문자열 값을 갖는다. 선언과 동시에 값을 지정했으므로 이 예시에서 새로 만든 `Car`의 초기 상태는 `width`가 `10`, `color`가 `"red"`이다. Object의 Attributes에 접근할 때는 **dot syntax(점 표기법)**를 사용한다. [M01 p.10] [M01 p.11]

```java
Car car = new Car();

System.out.println(car.width); // 10
car.width = 5;
System.out.println(car.width); // 5
```

`car.width`는 `car`가 가리키는 Object의 `width`를 뜻한다. 첫 출력은 초기값을 읽고, 대입문은 그 Object의 상태를 바꾸며, 두 번째 출력은 변경된 값을 읽는다. Class 정의 전체를 고치는 작업이 아니라 이미 만들어진 특정 Object의 값을 바꾸는 작업이다. [M01 p.11]

Attributes를 선언하면서 값을 지정하지 않으면 자료에서 설명하는 **default values(기본값)**가 적용된다. M01 pp.12–13의 `Foo` 예시는 다음 값을 보여 준다. [M01 p.12] [M01 p.13]

| Attribute의 자료형 | 자료에서 확인되는 기본값 |
| --- | --- |
| `boolean` | `false` |
| `int` | `0` |
| `float` | `0.0` |
| `String` 등 Object를 가리키는 Attribute | `null` |

`char`는 자료에서 값이 비어 보이는 표기와 출력으로 제시된다. 이를 유효한 빈 문자 리터럴 `''`로 옮겨 쓰면 안 된다. **해당 표기의 정확한 의미는 검증 필요**로 남긴다. 또한 이 부분은 Class의 Attributes에 관한 설명이므로, 모든 지역변수에도 같은 규칙을 그대로 적용한다고 확대해서 읽지 않는다. [M01 p.12] [M01 p.13]

서로 다른 Object는 각자의 Attribute 값을 갖는다. 자료에서 두 `Car`를 생성한 뒤 두 번째 Object의 `color`만 `"blue"`로 바꾸면 첫 번째 Object의 `color`는 `"red"`로 남는다. [M01 p.14]

| 실행 상태 | 첫 번째 Object의 `color` | 두 번째 Object의 `color` |
| --- | --- | --- |
| 각각 생성한 직후 | `"red"` | `"red"` |
| 두 번째 Object의 `color` 변경 후 | `"red"` | `"blue"` |

따라서 같은 Class의 Object들이 같은 이름의 Attributes를 갖는다는 것과 하나의 저장 상태를 공유한다는 것은 구분해야 한다. 여기서 다룬 것은 Object별 상태이며, Class 전체가 공유하는 `static` 상태는 별도로 설명한다. [M01 p.14] [M01 p.27]

### Methods: 호출한 Object의 상태로 동작하기

Methods는 Object가 Attributes를 바꾸거나 어떤 작업을 수행하는 방식을 정의한다. Attributes가 상태를 표현한다면, Methods는 그 상태를 사용하거나 바꾸는 동작을 표현한다. 강의는 이 두 요소를 함께 Class의 Members로 소개한다. [STT 02:44] [M01 p.8] [M01 p.17]

자료의 `printHello()`는 호출하면 메시지를 출력하는 Method이다. [M01 p.15]

```java
class Car {
    void printHello() {
        System.out.println("Hello World!");
    }
}

Car car = new Car();
car.printHello();
```

호출 부분은 Object를 가리키는 변수, 점, Method 이름, 괄호로 구성된다. `car.printHello()`는 `car`가 가리키는 Object에 해당 동작을 요청한다. Attribute 접근과 달리 괄호가 붙는다는 점도 구별해야 한다. [M01 p.15]

같은 Method를 사용하더라도 호출 대상의 상태가 다르면 결과가 달라질 수 있다. M01 p.16의 `getSpeed()`는 자신의 Object에 있는 `speed`를 반환한다. 자료에서 `myCar.speed`는 `100`, `yourCar.speed`는 `90`으로 설정되어 있으므로 각 호출 결과도 각각 `100`, `90`이다. [M01 p.16]

```java
class Car {
    int speed;

    int getSpeed() {
        return speed;
    }
}
```

이 예시를 이해하려면 Method의 코드뿐 아니라 **어느 Object를 통해 호출했는지**를 함께 보아야 한다. `myCar.getSpeed()`와 `yourCar.getSpeed()`는 같은 구조의 코드를 사용하지만 서로 다른 Object의 `speed`를 읽는다. [M01 p.16]

이 차이를 곧바로 Polymorphism의 구현 사례라고 부르지는 않는다. 여기서는 같은 Class의 같은 Method가 서로 다른 상태를 읽었기 때문에 결과가 달라진 것이다. 서로 다른 Class가 동작을 다르게 구현한다는 설명과 구분해야 한다. [M01 p.16] [M01 p.61]

### Encapsulation(캡슐화): 내부 상태를 보호하고 사용에 필요한 부분 드러내기

Encapsulation은 구성 요소의 **visibility(접근 가능 범위)**를 제한하여 Object 내부의 데이터를 보호하는 개념으로 소개된다. 외부에서 내부 구현을 모두 직접 다루지 않게 하면, 사용하는 쪽은 필요한 동작에 집중할 수 있다. 강의는 이 점을 **abstraction(추상화)**이 쉬워지는 이유와 연결한다. [STT 00:55] [M01 p.59]

**자료 그림 읽기 — Class를 나타내는 캡슐.** M01 p.59의 그림은 Variables와 Methods를 하나의 Class 안에 묶어 놓는다. 그림의 핵심은 관련 요소를 함께 담고, 내부 구현과 외부 접근 사이에 경계를 둔다는 것이다. 캡슐 그림 자체가 구체적인 접근 제어 문법이나 모든 Members의 접근 수준을 지정하는 것은 아니다. [M01 p.59]

**이해를 위한 예시:** 어떤 장치가 내부 상태를 관리하고 외부에는 필요한 동작만 제공한다고 생각해 보자. 장치를 사용하는 쪽은 내부 변수들을 직접 조정하는 대신 제공된 동작을 요청한다. 이렇게 하면 사용자가 내부 저장 방식을 모두 알아야 할 필요가 줄어든다. 이는 Encapsulation의 동기를 설명하기 위한 예시이며, 별도의 과제 명세가 아니다. [M01 p.59]

Encapsulation을 단순히 여러 변수를 Class 안에 모아 쓰는 것으로만 이해하면 데이터 보호와 접근 범위라는 목적을 놓친다. 반대로 이번 소개만으로 구체적인 접근 제어 문법을 모두 배웠다고 보아도 안 된다. 강의는 관련 특징들을 앞으로 더 배운다고 예고하며, 자료의 로드맵도 Encapsulation을 이후 학습 주제와 연결한다. [STT 00:55] [M01 p.58]

### Inheritance(상속): 공통 특성을 재사용하고 확장하기

Inheritance는 한 Class가 다른 Class의 특성을 이어받는 관계이다. 자료에서는 **parent class(부모 클래스)**의 코드를 **child class(자식 클래스)**가 재사용하고, 필요한 새 특성을 추가할 수 있다고 설명한다. 동기는 비슷한 내용을 매번 별도로 만드는 부담을 줄이는 데 있다. [STT 00:55] [M01 p.60]

**자료 그림 읽기 — 공통 분류와 세부 분류.** M01 p.60의 계층은 `Organisms` 아래에 `Animals`와 `Plants`, 그 아래에 `Duck`·`Cat`, `Tree`·`Grass`를 배치한다. 아래쪽 항목이 위쪽의 더 일반적인 분류와 어떤 관계를 갖는지 읽으면 된다. 이 그림은 공통 특성을 이어받는 구조를 설명하는 비유이지, 이번 시간에 해당 Class들의 구현 코드를 작성했다는 증거는 아니다. [M01 p.60]

Inheritance에서 재사용과 확장은 함께 생각해야 한다. Child class는 Parent class의 특성을 이용하면서 자신에게 필요한 특성을 더할 수 있다. “재사용한다”는 설명을 Parent class와 Child class가 항상 완전히 같은 동작과 상태를 가진다는 뜻으로 읽으면 확장의 의미를 놓치게 된다. [M01 p.60]

강의의 코드 재사용 관련 문장 일부는 전사가 불명확하다. 따라서 그 문장을 정확한 기술 설명으로 복원하지 않고, 특성 계승과 재사용이라는 확인 가능한 개념을 자료로 보충한다. 상세한 Inheritance 문법과 호출 규칙은 이번 소개의 범위로 확정하지 않는다. [STT 00:55] [M01 p.58] [M01 p.60]

### Polymorphism(다형성): 비슷한 동작을 서로 다르게 구현하기

Polymorphism은 서로 다른 Class들이 유사한 동작을 갖더라도 실제 수행 방식은 달라질 수 있다는 개념으로 소개된다. 자료는 같은 Parent class를 가진 Class들에서 같은 이름의 Methods를 서로 다르게 구현할 수 있다고 설명한다. [STT 01:51] [M01 p.61]

**자료 그림 읽기 — 같은 `animalSound()`, 서로 다른 소리.** M01 p.61은 개·고양이·오리를 같은 `animalSound()`와 연결한다. 공통된 동작의 이름은 같지만 각 동물이 내는 소리는 다르다. 이 그림에서 읽어야 할 것은 공통 동작을 이야기할 수 있다는 점과 실제 구현 결과가 달라질 수 있다는 점이다. [M01 p.61]

앞의 `getSpeed()` 예시와 비교하면 차이가 드러난다. 두 `Car`가 같은 Method로 각자의 `speed`를 읽는 것은 Object별 상태의 차이이다. `animalSound()` 그림은 서로 다른 Class가 유사한 동작을 다르게 구현한다는 설명이다. 결과가 다르다는 사실만으로 두 경우를 같은 개념으로 묶지 않아야 한다. [M01 p.16] [M01 p.61]

이번 녹음은 Polymorphism의 동기를 짧게 소개한다. 어떤 Method 구현이 선택되는지에 관한 상세한 Java 규칙이나 복잡한 Inheritance 코드를 이 회차에서 모두 배웠다고 확대하지 않는다. [STT 01:51] [M01 p.58]

### Constructor(생성자): Object가 만들어질 때 초기 상태 정하기

Constructor는 Object 생성 과정에서 초기화를 수행하는 특별한 구성이다. Class와 이름이 같고 **return type(반환형)**을 쓰지 않는다. 강의와 자료에는 Method에 빗댄 입문적 표현이 있지만, 노트에서는 일반 Method와 구분하여 이해한다. [STT 03:40] [M01 p.19]

초기화가 필요한 이유는 새 Object가 어떤 상태로 출발할지를 정해야 하기 때문이다. 자료의 가장 단순한 예시는 `Car()`가 생성 메시지를 출력하도록 한다. `new Car()`에 의해 Object가 만들어질 때 그 Constructor의 동작을 확인할 수 있다. [M01 p.20]

Constructor는 **Parameters(매개변수)**를 받아 Attributes를 초기화할 수 있다. 한 Class 안에 Parameters가 서로 다른 여러 Constructor를 정의하는 것도 가능하다. [STT 04:37] [M01 p.21]

M01 p.22는 `weight`와 `color`를 가진 `Car`로 이 차이를 설명한다.

```java
class Car {
    int weight;
    String color = "unknown";

    Car(int w) {
        weight = w;
    }

    Car(int w, String c) {
        weight = w;
        color = c;
    }

    void printInfo() {
        System.out.println(weight + " kg, " + color);
    }
}
```

`new Car(1500, "red")`는 두 Parameters를 받는 Constructor를 사용한다. 따라서 `weight`는 `1500`, `color`는 `"red"`가 된다. `new Car(2000)`는 한 Parameter를 받는 Constructor를 사용하므로 `weight`만 `2000`으로 설정하고, `color`는 선언에서 지정한 `"unknown"`을 유지한다. [M01 p.22]

| 생성 표현 | `weight` | `color` | `printInfo()`의 출력 |
| --- | --- | --- | --- |
| `new Car(1500, "red")` | `1500` | `"red"` | `1500 kg, red` |
| `new Car(2000)` | `2000` | `"unknown"` | `2000 kg, unknown` |

Constructor에 반환값이 없다는 설명을 보고 `void`를 붙이면 안 된다. 자료가 말하는 것은 return type 자체를 선언하지 않는다는 것이다. 또한 Object를 만든 뒤 일반 Method처럼 임의로 호출하는 구조와 구별해야 한다. [M01 p.19]

**노트의 보충 설명:** 녹음의 “생성될 때 호출된다”는 설명을 Constructor 본문이 어떤 경우에도 오직 하나만 한 번 실행된다는 보편 규칙으로 확대하지 않는다. 자료는 다른 Constructor 안에서 Constructor를 호출할 수 있다는 예외를 명시한다. 이 구분은 전사 내용을 바꾼 것이 아니라 자료에 근거하여 개념을 정확히 읽기 위한 보충이다. [STT 03:40] [M01 p.19]

개념 연결: [[concepts/constructor|Constructor]]

### `this`: 현재 Object와 같은 이름의 Parameter 구별하기

`this`는 현재 Object를 가리키는 키워드이다. 자료의 표현으로는 **self-object(자기 자신인 객체)**를 나타낸다. 현재 Object의 Attributes와 Methods를 명시적으로 가리킬 때 사용한다. 녹음에서 이 표현을 설명하는 명사 일부는 불명확하므로, 정확한 발화를 추정하지 않고 자료의 정의로 개념을 보충한다. [STT 04:37] [M01 p.23]

이름이 충돌하지 않는 경우 `this`를 생략할 수 있다. M01 p.24에서는 `this.color`와 `color`가 같은 Object의 Attribute를 가리킨다. 처음 `"red"`를 대입하고 이후 `"blue"`를 대입하면 같은 Attribute의 값이 순서대로 바뀐다. 두 개의 독립된 `color`가 만들어지는 것이 아니다. [M01 p.24]

Methods를 호출할 때도 같은 원리가 적용된다. M01 p.25의 `this.speedAndUnit()`는 현재 Object의 Method를 호출한다. 자료의 해당 문맥에서는 `this`를 생략해도 같은 Method를 호출한다. [M01 p.25]

`this`의 필요성이 가장 분명한 경우는 Parameter와 Attribute의 이름이 같을 때이다. 자료에는 다음 두 Methods가 나란히 제시된다. [M01 p.26]

```java
class Car {
    int speed = 30;

    void cantChangeSpeed(int speed) {
        speed = speed;
    }

    void changeSpeed(int speed) {
        this.speed = speed;
    }
}
```

첫 번째 Method의 `speed = speed`에서 양쪽 이름은 모두 Parameter를 가리킨다. 같은 Parameter에 자신의 값을 다시 넣으므로 Object의 `speed`는 바뀌지 않는다. 두 번째 Method의 왼쪽 `this.speed`는 현재 Object의 Attribute, 오른쪽 `speed`는 전달받은 Parameter이다. 따라서 두 번째 대입은 외부에서 받은 값을 Object의 상태에 반영한다. [M01 p.26]

**이해를 위한 예시:** 위 자료 코드의 두 Methods에 각각 `70`을 전달한다고 하자. 초기 `speed`가 `30`인 Object에서 `cantChangeSpeed(70)`을 호출하면 Object의 값은 여전히 `30`이다. 이어서 `changeSpeed(70)`을 호출하면 Object의 값이 `70`이 된다. 숫자 `70`은 설명을 위해 정한 값이며 이번 녹음의 실제 호출값을 복원한 것이 아니다. [M01 p.26]

자료는 `this()`를 다른 Constructor를 호출하는 용도로도 소개한다. 다만 세부 설명은 뒤의 학습으로 미룬다. `this.speed`, `this.speedAndUnit()`, `this()`를 모두 같은 형태의 Attribute 접근으로 혼동하지 않아야 한다. [M01 p.23]

강의자는 `this`를 이전 강의에서 다룬 내용 중 중요하다고 보아 복습에 포함했다고 설명한다. 확인되는 강조는 여기까지이며, 이를 시험 출제 가능성에 대한 예측으로 바꾸지 않는다. [STT 04:37]

**기출 적용 — 부분 연결.** 2025-1 중간고사 복기본의 5번은 `this`와 `super`를 설명하고 비교하는 요구이다. 현재 내용으로는 `this`가 현재 Object를 가리킨다는 부분을 설명할 수 있다. 그러나 문항 전체의 비교를 완성하려면 상위 Class를 다루는 `super`와 관련 Inheritance 규칙이 더 필요하다. 풀이를 준비할 때는 각 키워드가 무엇을 가리키는지를 먼저 구별해야 하며, `this`의 이름 충돌 예시만 이해했다고 문항 전체가 해결되었다고 판단하면 안 된다. [EX:cp_2025_1_midterm_q05 p.3]

### `static` Members: Object별 상태와 Class의 공유 상태

`static` Members는 개별 Object보다 Class에 연결되는 Members이다. 같은 Class의 여러 Object가 공통된 값을 보아야 할 때 `static` variable(정적 변수)로 설명할 수 있다. 반면 **instance variable(인스턴스 변수)**은 각 Object의 상태를 나타낸다. [STT 05:41] [M01 p.27] [M01 p.28]

**자료 그림 읽기 — 전체 개수와 개별 브랜드.** M01 p.27은 `Total number: 3`을 Class 쪽에, 서로 다른 자동차 브랜드를 각각의 Object 쪽에 놓는다. 전체 개수는 세 Object가 공유하는 정보이고, 각 자동차의 브랜드는 개별 Object의 정보이다. 그림의 화살표를 따라 “이 값은 Class 전체에 하나인가, Object마다 따로 있는가?”를 구별하면 된다. [M01 p.27]

이번 강의의 고유 예시는 `static String owner`이다. 녹음에서는 Constructor 입력으로 이 값을 바꾸고, `"Carol"`로 변경한 값을 다른 Instance에서도 관찰하는 상황을 설명한다. 이후 Class의 `owner`를 `"David"`로 바꾸면 여러 Instance를 통해 같은 새 값을 관찰한다고 설명한다. 핵심은 같은 이름을 여러 Object에 복사해 둔 것이 아니라 Class에 속한 공유 상태를 보고 있다는 점이다. [STT 05:41] [STT 06:33]

다만 해당 예시의 원 코드는 제공되지 않았다. 초기의 두 문자열 값이나 정확한 대입·출력 구문은 복원하지 않는다. Constructor와 `owner`를 연결하는 일부 발화도 **검증 필요**이다. 공유 상태라는 설명은 확인되지만, 전사에서 불분명한 동사를 완성된 코드로 바꾸지는 않는다. [STT 05:41] [STT 06:33]

자료는 Object를 먼저 생성하지 않고 `Car.num`, `Car.printNum()`처럼 Class를 통해 `static` Members에 접근하는 예시를 제시한다. Class에 연결된 값이나 동작임을 코드에서도 드러내는 방식이다. [M01 p.28] [M01 p.29]

M01 p.30은 Object별 상태와 공유 상태를 한 코드 안에서 비교한다. Constructor는 `num`을 증가시키고, `setMile()`은 해당 Object의 `mile`을 설정하면서 전달받은 값을 `totalMile`에 누적한다. [M01 p.30]

```java
class Car {
    static int num;
    static int totalMile;
    int mile;

    Car() {
        num++;
    }

    void setMile(int mile) {
        this.mile = mile;
        totalMile += mile;
    }
}
```

자료처럼 세 Object를 생성하고 각각 한 번씩 `20`, `30`, `40`으로 `setMile()`을 호출하면 다음 상태가 된다. [M01 p.30]

| 상태의 소속 | 변수 | 결과 |
| --- | --- | --- |
| Class 공유 | `num` | `3` |
| Class 공유 | `totalMile` | `90` |
| 첫 번째 Object | `mile` | `20` |
| 두 번째 Object | `mile` | `30` |
| 세 번째 Object | `mile` | `40` |

공유 누적값은 다음 계산으로 확인할 수 있다.

$$
20 + 30 + 40 = 90
$$

이 결과는 자료에 제시된 호출 순서에 대한 결과이다. `totalMile`이라는 이름만 보고 어떤 호출 순서에서도 모든 Object의 현재 `mile` 합계가 자동으로 유지된다고 판단하면 안 된다. 실제 코드는 `setMile()`을 부를 때마다 입력값을 더한다. 의미를 판단할 때는 변수 이름과 대입·누적 연산을 함께 읽어야 한다. [M01 p.30]

### `static` Method의 접근 제한: 어느 Object의 값인지 지정하기

`static` Method는 특정 Object를 통한 호출 없이도 사용할 수 있다. 따라서 Object마다 값이 다른 instance variable을 이름만으로 사용하면 어느 Object의 값을 뜻하는지 결정할 수 없다. 강의의 `totalFuel()` 예시는 이 문제를 보여 준다. [STT 07:35] [M01 p.31] [M01 p.32]

다음은 자료에 실린 오류 예시이다.

```java
class Car {
    float fuel;

    static float totalFuel() {
        return fuel; // 어느 Object의 fuel인지 지정되지 않음
    }
}
```

`fuel`은 Object별 Attribute인데, `static` Method 안의 `return fuel`에는 그 값을 읽을 대상 Object가 없다. 자료는 이를 오류로 표시한다. 정상 실행 뒤 어떤 값이 출력되는 문제가 아니라 Class의 코드가 유효한지부터 판단해야 하는 문제이다. 녹음의 결과 설명은 문장 중간에서 불완전하므로, 자료의 오류 판정을 완성된 강의 발화로 바꾸지는 않는다. [STT 07:35] [M01 p.32]

**노트의 보충 설명:** 자료의 제한은 대상 Object를 지정하지 않은 직접 접근을 뜻하는 것으로 읽어야 한다. `static` 코드에서 명시한 Object를 통해 상태를 읽는 것까지 전부 금지한다는 의미는 아니다. 핵심은 `static`이라는 단어 자체보다 “어느 Object를 통해 접근하는가?”이다. [M01 p.31]

**이해를 위한 예시:** 다음은 그 차이를 보여 주기 위해 별도로 만든 작은 코드이다.

```java
class Meter {
    int value = 4;

    static int read(Meter meter) {
        return meter.value;
    }
}
```

`read()`는 `static`이지만 `meter.value`에는 값을 읽을 Object가 지정되어 있다. 여기서는 `meter`가 실제 `Meter` Object를 가리킨다는 조건으로 읽는다. 앞의 `return fuel`과 달리 Object별 상태를 어디에서 가져오는지가 분명하다. 이 예시는 현재 Lab3의 구현 코드가 아니다. [M01 p.31] [M01 p.32]

반대 방향으로, instance Method 안에서 `static` Method를 호출하는 것은 자료에서 가능하다고 설명한다. 개별 Object의 동작이 Class에 연결된 기능을 사용하는 상황이다. [M01 p.31]

**기출 적용 — 부분 연결, 후속 선수 필요.** 2025-1 중간고사 복기본의 7번은 `static` 중첩 Class에서 바깥 Object의 상태에 접근하는 오류를 분석하고, 지정된 Method 본문을 유지하면서 코드를 수정하도록 요구한다. 현재 설명의 “어느 Object의 값인가?”라는 질문은 오류 분석의 출발점으로 연결된다. 다만 원문에는 중첩 Class의 의미와 수정 제약이 추가되므로, 단순히 모든 변수를 `static`으로 바꾸는 일반 규칙으로 읽거나 이번 예제와 같은 문제라고 간주하면 안 된다. 문항 전체의 수정은 중첩 Class를 배운 뒤 다룰 범위이다. [EX:cp_2025_1_midterm_q07 p.4]

### Object의 `==`: 내용이 같은가, 같은 Object를 가리키는가

Object에 대한 `==`는 두 reference가 같은 Object를 가리키는지 비교한다. Object의 내용이 같다는 사실과 같은 Object라는 사실은 구별해야 한다. 강의와 자료는 이를 주소에 빗대어 설명하지만, 실제 물리적 메모리 주소의 표현이나 배치를 보장한다는 뜻으로 확대하지 않는다. [STT 08:32] [M01 p.34]

자료는 내용이 같은 두 `String` Object를 각각 만든 뒤, 첫 번째 reference를 세 번째 변수에 대입한다. [M01 p.34] [M01 p.35]

```java
String str1 = new String("hey");
String str2 = new String("hey");
String str3 = str1;

System.out.println(str1 == str2); // false
System.out.println(str1 == str3); // true
```

첫 두 줄에는 각각 `new`가 있다. 따라서 같은 `"hey"`를 담고 있어도 서로 다른 Object가 만들어진다. 세 번째 줄은 새 Object를 만들지 않고 `str1`의 reference 값을 `str3`에 넣는다. 그러므로 `str1`과 `str3`는 같은 Object를 가리킨다. [M01 p.35]

**자료 그림 읽기 — 같은 문자열이 들어 있는 두 칸.** M01 pp.34–35의 메모리 그림에는 `"hey"`가 두 번 나타난다. 두 칸의 내용이 같다는 데서 멈추지 말고, `str1`과 `str2`가 서로 다른 Object에 대응한다는 사실을 읽어야 한다. 자료가 제시하는 두 비교 결과는 차례로 `false`, `true`이다. [M01 p.34] [M01 p.35]

**전사 주의:** 08:32의 부정 표현은 서로 다른 Object를 비교하는 상황 및 자료의 `false` 결과와 충돌한다. 그 발화의 정확한 의도는 **검증 필요**이다. 위 결과는 자료 코드와 reference 관계에 근거한 설명이며, 불명확한 발화를 이렇게 말했다고 고쳐 쓴 것이 아니다. [STT 08:32] [M01 p.35]

이 예시에서 피해야 할 오개념은 문자열 내용이 같으므로 `==`도 참일 것이라고 판단하는 것이다. 먼저 Object가 몇 개 만들어졌는지, 각 변수가 어느 Object를 가리키는지 확인해야 한다. [M01 p.35]

### Object reference의 `=`: 새 Object 생성과 reference 대입 구분하기

Object를 가리키는 변수에 `=`로 다른 reference를 대입하면, 같은 Object를 가리키는 변수가 늘어날 수 있다. 대입만으로 Object 자체가 복제되거나 이동하는 것은 아니다. [STT 08:32] [M01 p.36]

자료의 예시는 다음과 같다.

```java
Car myCar = new Car();
Car car1 = myCar;
Car car2 = myCar;
Car car3 = car1;
```

첫 줄에서 하나의 `Car` Object를 만든다. 이후 세 줄은 기존 reference 값을 대입한다. 따라서 변수는 네 개이지만 이 코드에서 생성된 `Car` Object는 하나이다. `car3`도 `car1`을 통해 같은 reference 값을 받으므로 다른 변수들과 같은 Object를 가리킨다. [M01 p.36]

**자료 그림 읽기 — 변수 개수와 Object 개수.** M01 p.36의 메모리 그림에는 `Car` Object가 하나만 표시된다. 그림을 읽을 때 변수 이름을 셈하는 것과 Object 생성을 셈하는 것을 분리해야 한다. 이 예시에서는 `new`가 한 번만 실행된다는 점이 Object 수를 판단하는 근거이다. 이를 어떤 코드에서도 `new`라는 글자의 개수만 세면 된다는 규칙으로 확대하지는 않는다. [M01 p.36]

이 설명은 앞의 Object별 Attributes와 모순되지 않는다. 서로 다른 두 Object는 각자의 상태를 가지지만, 두 변수가 같은 Object를 가리킨다면 그 둘은 같은 상태를 보는 것이다. “변수 이름이 다르다”는 이유만으로 서로 다른 Object라고 판단하지 않아야 한다. [M01 p.14] [M01 p.36]

08:32에서 Object의 주소가 바뀐다고 표현한 부분도 노트에서는 reference 변수의 대입으로 구분해 읽는다. Object 자체가 다른 위치로 이동했다는 실행 사실을 전사에서 확정할 수는 없다. [STT 08:32]

### Call-by-Value(값 전달): 바깥 변수와 안쪽 Parameter는 별개

Call-by-Value는 Method를 호출할 때 값을 복사하여 전달하는 방식이다. 강의는 정수 값을 전달한 뒤 Method 내부에서 받은 값을 바꾸어도, 호출한 쪽의 변수는 그대로 남는 상황을 설명한다. [STT 09:27] [STT 10:14] [M01 p.38]

여기서 중요한 구별은 변수의 이름보다 변수가 속한 위치이다. 호출한 쪽의 변수와 호출된 Method의 Parameter는 서로 다른 변수이다. 같은 이름을 사용하더라도 하나의 저장 공간을 공유하는 것이 아니다. [M01 p.37] [M01 p.39]

자료의 `swap()`은 이 차이를 드러낸다. 다음 Method는 전달받은 두 정수의 값을 내부에서 교환한다. [M01 p.37]

```java
static void swap(int a, int b) {
    int temp;
    temp = a;
    a = b;
    b = temp;
}
```

자료의 호출부에서 `a = 2`, `b = 3`을 준비하여 `swap(a, b)`를 호출하면, Method 진입 시 복사된 Parameters도 처음에는 `2`, `3`이다. 이후 `temp`가 `2`를 보관하고, 내부 `a`가 `3`, 내부 `b`가 `2`가 된다. 그러나 이 대입들은 호출한 쪽의 `a`, `b`를 대상으로 하지 않는다. [M01 p.37] [M01 p.39]

**자료 표 읽기 — 반환 직전의 두 영역.** M01 p.39의 메모리 표는 `main`과 `swap` 영역을 분리한다. 같은 `a`, `b`라는 이름이 두 영역에 등장하므로 영역을 생략하고 숫자만 추적하면 잘못된 결론에 도달한다. [M01 p.39]

| 반환 직전의 위치 | `a` | `b` | `temp` |
| --- | --- | --- | --- |
| 호출한 `main` | `2` | `3` | 해당 없음 |
| 호출된 `swap` | `3` | `2` | `2` |

따라서 자료의 `main`에서 출력되는 값은 `2 3`이다. `swap` 내부에서 값 교환이 일어났다는 사실과 호출자의 두 변수가 교환되었다는 주장은 다르다. [M01 p.37] [M01 p.39]

녹음에서는 `number`라는 정수 변수로 같은 원리를 설명하지만, 실제 수치와 코드 전체는 제공되지 않는다. 그 예시의 출력 동사를 정확히 복원하거나 위 `swap` 코드를 실제 녹음의 코드였다고 제시하지 않는다. 위 코드는 개념이 일치하는 자료 보충이다. [STT 10:14]

개념 연결: [[concepts/call-by-value|Call-by-Value]]

### Object 전달: reference 값의 복사와 Object 상태 변경

Object를 Method에 전달했을 때는 reference 값이 복사된다. 복사된 reference가 원래와 같은 Object를 가리키므로, Method 안에서 그 Object의 Attributes를 바꾸면 호출한 쪽에서도 변경을 관찰할 수 있다. 이것이 정수 Parameter 자체를 바꾸는 경우와 다른 관찰 결과를 만드는 이유이다. [STT 11:07] [STT 11:52] [M01 p.42]

**노트의 보충 설명:** 강의와 자료는 이 부분을 Call-by-Reference(참조 전달)라는 이름으로 소개한다. 그러나 Java의 전달 방식은 reference 값까지 포함하여 **값 전달**로 이해해야 한다. 자료 p.42도 전달되는 reference의 값을 생각하면 Call-by-Value로 볼 수 있다는 보충을 포함한다. 원래 변수 자체를 Method의 Parameter와 하나로 연결하는 방식으로 해석하지 않는다. [STT 10:14] [M01 p.42]

이번 강의의 예시는 `Car`의 `speed`를 `changeSpeed` 안에서 바꾸는 상황이다. 전달된 reference가 같은 `Car`를 가리키기 때문에, 그 Object 안의 `speed` 변경이 호출한 쪽에 보인다는 설명이다. 정확한 Method 선언이나 변경 전후 수치는 제공되지 않았으므로 복원하지 않는다. [STT 11:07] [STT 11:52]

자료의 `IntHolder`는 정수 하나를 Attributes로 가진 Class이다. [M01 p.40]

```java
class IntHolder {
    int value;

    IntHolder(int value) {
        this.value = value;
    }
}
```

앞서 배운 Constructor와 `this`가 함께 사용된다. Constructor의 Parameter `value`를 현재 Object의 `this.value`에 넣는다. 이후 자료의 `swap()`은 Parameters 자체가 아니라 각 Object의 `value`를 바꾼다. [M01 p.40] [M01 p.41]

```java
static void swap(IntHolder a, IntHolder b) {
    int temp = a.value;
    a.value = b.value;
    b.value = temp;
}
```

서로 다른 두 `IntHolder`의 초기 `value`가 각각 `2`, `3`이라면 다음 순서로 진행된다.

1. `temp`에 첫 번째 Object의 값 `2`를 보관한다.
2. 첫 번째 Object의 `value`에 두 번째 Object의 값 `3`을 대입한다.
3. 두 번째 Object의 `value`에 보관한 값 `2`를 대입한다.

결과적으로 호출한 쪽에서 두 Object의 Attributes를 읽으면 `3 2`를 관찰한다. Object를 가리키는 호출자 변수들을 서로 교환한 것이 아니라, 두 Object 내부의 정수 값을 바꾼 것이다. [M01 p.41] [M01 p.43]

**자료 표 읽기 — 바뀐 것은 Object 안의 `value`.** M01 p.43은 두 Object의 `value`가 각각 `3`, `2`가 된 상태와 `swap`의 지역변수 `temp = 2`를 보여 준다. 앞의 정수 `swap` 표와 비교할 때는 대입 대상이 Parameter 자체인지, reference를 따라간 Object의 Attribute인지 확인해야 한다. [M01 p.39] [M01 p.43]

| 대입의 대상 | 대입 예 | 호출한 쪽에서 관찰할 핵심 |
| --- | --- | --- |
| 정수 Parameter 자체 | `a = b` | 호출자의 정수 변수는 그대로이다. |
| 같은 Object의 Attribute | `a.value = b.value` | 해당 Object의 상태 변경이 보인다. |

여기서 “복사된다”는 말을 Object 전체가 복사된다는 뜻으로 읽으면 안 된다. 복사되는 것은 reference 값이다. 또한 Parameter에 다른 reference를 넣는 행위와, 그 reference로 접근한 Object의 Attributes를 바꾸는 행위도 구별해야 한다. [M01 p.36] [M01 p.42]

이 `IntHolder` 예시는 현재 개념을 보충하는 M01 pp.40–43의 자료이다. 뒤의 별도 `More on swaps` 절을 이번 실습에서 다뤘다는 근거로 확장하지 않는다.

### Memory Management(메모리 관리)와 Garbage Collector(가비지 컬렉터)

Java의 Memory Management는 자료에서 동적이고 자동적인 과정으로 소개된다. 새 Object를 만들 때 필요한 메모리가 할당되고, 더 이상 사용되지 않는 Object의 메모리는 Garbage Collector가 회수하는 역할을 맡는다. [STT 11:52] [STT 12:50] [M01 p.44]

이 설명에서 두 단계를 구별해야 한다. 하나는 Object가 만들어질 때 필요한 공간을 마련하는 일이고, 다른 하나는 더 이상 필요하지 않은 Object가 사용하던 공간을 회수하는 일이다. 자료는 이를 C에서 명시적으로 할당하고 해제하는 경우와 대비하여 설명한다. [M01 p.44]

자동으로 처리된다는 말은 프로그래머가 Object 생성 표현을 작성할 필요가 없다는 뜻이 아니다. 앞의 예시들은 여전히 `new Car()`와 `new IntHolder(...)`를 사용한다. 자동화되는 메모리 관리와 프로그램이 언제 어떤 Object를 만들지 정하는 일은 구별해야 한다. [M01 p.36] [M01 p.40] [M01 p.44]

**이해를 위한 예시:** 여러 변수가 같은 Object를 가리키는 앞의 `Car` 예시에서, 변수 하나를 더 이상 사용하지 않는다는 사실만 보고 Object 전체가 불필요해졌다고 결론 내릴 수는 없다. 다른 변수가 여전히 같은 Object를 가리킬 수 있기 때문이다. reference 변수 하나의 상태와 Object 전체의 사용 관계를 나누어 보아야 한다. [M01 p.36] [M01 p.44]

강의는 정확한 회수 시점이나 알고리즘을 제공하지 않는다. 따라서 어떤 대입문 직후 즉시 메모리가 회수된다고 주장하거나, 특정 시점의 회수를 코드의 정상 동작 조건으로 삼지 않는다. [STT 12:50] [M01 p.44]

**기출 적용 — 역할 설명은 연결되며, 엄밀한 조건은 추가 학습 필요.** 2025-1 중간고사 복기본의 3번은 Garbage Collector의 역할과 `new`로 생성한 Object가 수거 대상이 되는 조건을 함께 묻는다. 현재 범위에서는 자동 메모리 관리와 사용되지 않는 Object의 공간 회수라는 역할을 설명할 수 있다. 조건 부분을 엄밀히 답하려면 프로그램에서 해당 Object로 도달할 수 있는 reference 관계를 판단하는 기준이 더 필요하다. 접근할 때는 “수거 대상이 되는 조건”과 “실제로 회수되는 시점”을 구분해야 하며, 둘을 같은 것으로 쓰는 것이 함정이다. 이 노트는 원문 전체에 대한 공식 정답을 제공하는 것으로 보지 않는다. [EX:cp_2025_1_midterm_q03 p.2]

### `Player`: 관리할 상태와 제공할 동작 나누기

`Player`는 플레이어의 식별 정보와 health를 관리하는 Class로 설명된다. 앞의 개념에 대응시키면, 식별 정보와 health는 Attributes에 해당하고 공격·피해 반영·회복·생존 판단·행동 선택은 Methods에 해당한다. [STT 14:47] [STT 15:41]

전사에서 확인되는 Attributes의 역할은 다음과 같다.

| Attribute의 역할상 명칭 | 확인되는 내용 | 아직 확정할 수 없는 선언 정보 |
| --- | --- | --- |
| user ID | 플레이어를 식별하며 문자열로 설명된다. | 정확한 변수명과 대소문자 |
| health | 플레이어의 현재 상태를 관리한다. | 자료형 설명이 중간에서 끊겨 정확한 선언을 확정할 수 없다. |
| random 관련 Attribute | `Player`의 여러 Methods에서 사용한다. | 정확한 변수명·자료형·사용 API |

위 표는 전사에서 파악한 역할을 정리한 것이다. 완성된 Java 선언을 복원한 표가 아니다. 특히 문자열이라는 설명이 있다고 해서 식별자의 철자까지 `userId` 등으로 정할 수는 없고, health가 정수처럼 다뤄진다고 해서 잘린 자료형 설명을 `int`로 채우면 안 된다. [STT 14:47] [STT 15:41]

Methods는 14:47의 소개에 이어 15:41에서 다음 다섯 가지로 제시된다.

| Method 명칭 | 녹음에서 확인되는 책임 |
| --- | --- |
| `attack` | 상대 플레이어의 health 감소 |
| `getDamaged` | 지정된 양의 피해를 해당 플레이어에게 반영 |
| `heal` | 해당 플레이어의 health 증가 |
| `isAlive` | health에 따른 생존 여부 판단 |
| `getTactic` | 공격 또는 회복 선택 |

초기 소개에서 빠졌던 `getDamaged`는 뒤의 목록과 설명으로 보완된다. 따라서 첫 목록만 보고 네 Methods가 전부라고 정리하면 강의 내용을 놓치게 된다. 반대로 다섯 이름을 확인했다고 Parameters, return type, 접근 수준까지 확인된 것은 아니다. [STT 14:47] [STT 15:41] [STT 16:37]

강의는 필요한 정보를 얻기 위한 추가 Methods를 만들 수 있다고도 안내한다. 이는 추가 조회 기능의 허용이며, 모든 상태를 외부에서 직접 변경하도록 만들라는 지시로 확대하지 않는다. [STT 15:41]

### health: 초기값, 하한, 상한, 종료 의미

health는 `Player`의 상태를 나타내는 값이며, Methods가 실행된 뒤에도 과제에서 요구하는 범위를 유지해야 한다. 전사에서 직접 제시되는 초기값은 플레이어마다 `50`이다. 또한 health는 음수가 아니어야 하고, 0에 도달하면 해당 플레이어가 패배하며 게임이 종료된다고 설명한다. [STT 15:41]

초기 health를 $h_0$, 현재 health를 $h$라고 적으면, 이 설명은 다음과 같이 정리할 수 있다. 이 기호는 노트의 설명용 표기이며 과제의 변수명을 지정하는 것이 아니다.

$$
h_0 = 50,\qquad h \ge 0
$$

17:39에는 health가 초기값을 넘으면 안 된다는 상한 설명이 추가된다. 이를 앞의 초기값 `50`과 연결하면 다음 범위로 읽을 수 있다. [STT 17:39]

$$
0 \le h \le h_0
$$

즉, 문맥상 $0 \le h \le 50$으로 연결된다. 다만 17:39에서 상한 숫자 `50`을 다시 명확하게 발화한 것은 아니다. **초기값 50은 직접적인 STT 근거이고, 상한 50은 앞뒤 설명을 연결한 해석**이라는 차이를 남긴다. 이 수치는 사용자가 기술 명세를 확인해 준 내용으로 취급하지 않는다. [STT 15:41] [STT 17:39]

**이해를 위한 예시:** health가 `2`인 상태에서 감소량 `5`를 단순히 빼면 산술 결과는 `-3`이다. 그러나 이를 최종 health로 그대로 저장하면 음수가 아니어야 한다는 요구를 어긴다. 이 예시는 산술 연산 결과와 허용되는 Object 상태가 항상 같지는 않다는 점을 보여 준다. [STT 15:41] [STT 16:37]

여기서 특정 경계 처리 코드를 정답으로 제시하지는 않는다. 경계를 넘는 요청을 어떤 절차로 처리하는지, 관련 Methods가 무엇을 반환하는지는 원래 Lab3 명세로 확인해야 한다. 현재 확정할 수 있는 것은 초기값, 음수 금지, 초기값을 넘지 않는다는 상한 설명, 0일 때의 패배·종료 의미이다.

### `attack`과 `getDamaged`: 상대에게 가하는 동작과 피해 반영 구분하기

`attack`은 상대 플레이어의 health를 `1`부터 `5` 사이에서 선택한 정수만큼 감소시키는 Method로 설명된다. 여기서 대상은 공격한 플레이어 자신이 아니라 상대이다. 감소량의 범위와 변경 대상이라는 두 조건을 함께 읽어야 한다. [STT 16:37]

설명용으로 감소량을 $d$라고 두면 확인되는 범위는 다음과 같다.

$$
d \in \{1,2,3,4,5\}
$$

해당 문장은 정수를 선택한다고 설명하지만, 뒤의 `heal` 설명과 달리 무작위 선택이라는 표현을 명시적으로 포함하지 않는다. 따라서 정확한 선택 방식이나 각 값이 같은 확률로 나오는지는 **검증 필요**이다. `random` 관련 Attribute가 있다는 사실만으로 모든 선택의 분포를 확정해서는 안 된다. [STT 15:41] [STT 16:37]

`getDamaged`는 해당 플레이어의 health를 지정된 양만큼 감소시키는 역할이다. `attack`이 상대에게 가하는 동작을 설명한다면, `getDamaged`는 피해를 받는 쪽의 상태 변화를 설명한다. 다만 이것만으로 `attack`이 반드시 `getDamaged`를 어떤 Parameters로 호출해야 한다는 구체적인 내부 구조가 확정되는 것은 아니다. [STT 16:37]

**이해를 위한 예시:** 플레이어 A가 공격하고 플레이어 B가 피해를 받는 상황에서는, A가 동작을 시작했다는 사실과 B의 health가 바뀐다는 사실을 나누어 추적하면 된다. 이 구분은 Object의 Method와 상태 변경 대상이 어떻게 연결되는지 이해하기 위한 예시이며, `Fight`의 실행 코드를 제시한 것이 아니다. [STT 16:37]

강의는 힌트를 필요에 따라 사용해도 된다고 안내하고, `getDamaged`를 도움을 주기 위해 포함했다는 취지를 말한다. 그러나 힌트의 실제 내용과 Method를 수식하는 불명확한 표현은 복원하지 않는다. 특히 도움을 위한 설명을 필수 호출 구조나 완성된 해결법으로 바꾸지 않는다. [STT 16:37]

### `heal`: 증가량과 health 상한을 함께 읽기

`heal`은 해당 플레이어의 health를 무작위로 선택한 `1`부터 `3` 사이의 정수만큼 증가시키는 Method이다. `attack`과 달리 이 부분에는 무작위 선택이라는 설명이 확인된다. [STT 16:37]

설명용 증가량을 $r$이라고 쓰면 다음 범위이다.

$$
r \in \{1,2,3\}
$$

이 범위만 확인하고 상한 조건을 빠뜨리면 요구사항을 제대로 읽은 것이 아니다. `heal` 이후의 health도 초기값을 넘지 않아야 한다는 후속 설명과 함께 보아야 한다. [STT 17:39]

**이해를 위한 예시:** health가 `49`이고 선택된 증가량이 `3`이라면 단순 합은 `52`이다. 상한을 초기값 `50`과 연결해 읽는 문맥에서는 `52`를 그대로 최종 상태로 두는 것이 허용되지 않는다. 증가량 선택과 허용 상태 유지가 별개의 판단이라는 점이 핵심이다. [STT 15:41] [STT 16:37] [STT 17:39]

다만 경계에서 값을 제한하는 정확한 절차, 사용해야 할 random API, `1`·`2`·`3`의 동일 확률 여부는 제공된 소스만으로 확정할 수 없다. 증가량이 무작위라는 사실을 특정 API 호출이나 분포의 증거로 바꾸지 않는다.

### `isAlive`: health에 대한 참·거짓 판단

`isAlive`는 health가 `0`보다 크면 `true`, 그렇지 않으면 `false`를 반환하는 것으로 설명된다. 상태를 바꾸는 동작과 달리, 현재 상태가 생존 조건을 만족하는지 판단하는 역할이다. [STT 17:39]

설명용 기호 $h$를 사용하면 판정 관계는 다음과 같다.

$$
\operatorname{isAlive}(h)=
\begin{cases}
\mathrm{true}, & h>0\\
\mathrm{false}, & h\le 0
\end{cases}
$$

이 식은 전사의 조건을 표현한 것이며, 제출해야 할 Method의 정확한 선언을 제시한 것은 아니다. health의 정상 범위가 음수가 아니라는 요구를 함께 적용하면, 허용되는 상태 안에서 `false`가 되는 경계는 `0`이다. [STT 15:41] [STT 17:39]

**이해를 위한 예시:** health가 `1`이면 `true`, `0`이면 `false`이다. 생존을 판정할 때 `0`을 참에 포함시키면 전사의 조건과 달라진다. 반대로 `isAlive`가 `false`를 반환한다는 설명만으로 Method 내부에서 게임 전체를 종료시키는 코드까지 반드시 수행한다고 추정해서는 안 된다. 전사는 판정 조건과 게임 종료 규칙을 말하지만, 이를 어떤 Class와 호출 순서로 연결할지는 완전히 제공하지 않는다. [STT 15:41] [STT 17:39]

반환값을 설명하는 발화는 참·거짓 값이라는 의미로 읽을 수 있으나, Java 선언이 `boolean`인지 `Boolean`인지까지 확정하지 않는다. 정확한 return type은 skeleton에서 **검증 필요**이다.

### `getTactic`: 행동 선택과 미완성 반환 명세

`getTactic`은 플레이어가 공격할지 회복할지 결정하는 Method로 소개된다. 이것은 어떤 행동을 선택하는 역할이다. 선택한 공격이나 회복을 실제로 수행하는 Methods의 역할과 먼저 구별해야 한다. [STT 17:39]

확률 관련 전사에는 공격 쪽에 `70`, 회복 쪽에 `30%`가 제시된다. 공격 쪽은 퍼센트 단위가 빠져 있으므로, 두 선택의 문맥상 공격 `70%`, 회복 `30%`로 해석할 수는 있지만 확정된 원문 수치 표현과 동일하게 취급하지 않는다. **공격 70%는 문맥상 해석이며 검증 필요**이다. 이 비율이 사용자에게 기술적으로 확인된 사항이라는 근거도 없다. [STT 17:39]

이 설명에서 바로 정할 수 없는 것은 선택 결과의 표현 방식이다. 반환할 문자, return type, 실제 분기 코드가 완성되기 전에 마지막 문장이 끊긴다. Method 이름과 공격·회복이라는 두 선택지를 확인했다고 특정 문자를 반환하도록 임의로 설계하면 누락된 과제 명세를 만들어 내게 된다. [STT 17:39]

마지막 `17:39` 표시는 해당 전사 구간의 시작 시각이며, 과제 설명이 그 시각에 완결되었다는 뜻이 아니다. 녹음의 시작도 문장 흐름 중간이고 마지막 구간도 미완성이므로, 빠진 앞뒤 내용을 복원한 것으로 읽지 않아야 한다. 특히 `getTactic`의 완전한 반환 규칙과 이후 `Fight`·main class의 구현은 제공된 소스로 확인되지 않는다. 현재 단계에서는 행동 선택의 책임과 확인 가능한 확률 표현을 이해하고, 구체적인 반환 명세는 **검증 필요**로 남긴다. [STT 00:00] [STT 17:39]

### 개념 연결 지도

- [[concepts/object-oriented-programming|Object-Oriented Programming]] → [[concepts/class-and-object|Class와 Object]] → [[concepts/attributes-and-methods|Attributes와 Methods]]: 프로그램의 대상을 정하고 상태와 동작으로 표현한다.
- [[concepts/class-and-object|Class와 Object]] → [[concepts/constructor|Constructor]] → [[concepts/this-keyword|this]]: 새 Object의 초기 상태를 정하고, 현재 Object와 Parameter를 구별한다.
- [[concepts/attributes-and-methods|Attributes와 Methods]] ↔ [[concepts/static-members|static Members]]: Object별 상태와 Class 전체의 공유 상태를 나누어 읽는다.
- [[concepts/object-reference|Object reference]] → [[concepts/call-by-value|Call-by-Value]] → [[concepts/garbage-collection|Garbage Collector]]: 같은 Object를 가리키는 관계, 전달되는 값, 메모리 관리의 역할을 차례로 구분한다.
- [[concepts/encapsulation|Encapsulation]], [[concepts/inheritance|Inheritance]], [[concepts/polymorphism|Polymorphism]]: 내부 보호·재사용·동작 다양화라는 동기를 연결한다. 이번 소개를 상세 구현 규칙의 학습 완료로 확대하지 않는다. [M01 p.58]

### 그림과 표를 다시 읽는 기준

**`static` 그림에서는 값의 소속을 읽는다.** M01 p.27의 전체 자동차 수는 Class 쪽에, 개별 브랜드는 각 Object 쪽에 놓여 있다. 그림을 다시 볼 때는 숫자와 브랜드를 암기하기보다, 새로운 Attribute가 주어졌을 때 어느 쪽에 놓아야 하는지 판단한다. 이 구분이 Lab3에서도 각 플레이어의 health를 개별 상태로 이해하는 출발점이 된다. [M01 p.27] [STT 15:41]

**메모리 표에서는 대입 대상과 영역을 읽는다.** M01 p.39에서 호출자의 `a`, `b`는 `2`, `3`이고, `swap` 안의 같은 이름 Parameters는 `3`, `2`이다. M01 p.43에서는 두 Object 안의 `value`가 `3`, `2`로 바뀐다. 두 표의 차이는 교환이라는 동작 이름에 있지 않고, Parameter 자체와 Object의 Attribute 중 무엇에 대입했는지에 있다. [M01 p.39] [M01 p.43]

이 그림과 표는 본문 설명을 점검하는 자료이다. 녹음의 `owner`, `number`, `Car.speed` 예시와 개념적으로 연결되지만, 제공되지 않은 실습 화면의 코드를 대신 복원한 것은 아니다.

## 핵심 요약

- **Class(클래스)와 Object(객체):** Class는 공통 구조를 정하고, Instance는 그 구조로 만든 개별 Object이다. 공통 Attributes·Methods를 갖는다는 사실과 같은 상태를 공유한다는 사실은 다르다. [M01 p.7] [M01 p.14] [M01 p.17]
- **Attributes와 Methods:** 상태와 동작을 함께 읽는다. 같은 Method도 호출 대상의 상태에 따라 결과가 달라질 수 있으며, 이것만으로 Polymorphism의 구현 사례가 되지는 않는다. [M01 p.8] [M01 p.16] [M01 p.61]
- **Constructor와 `this`:** Constructor는 특별한 초기화 구성이며 반환형을 쓰지 않는다. `this`는 현재 Object를 가리켜 같은 이름의 Parameter와 Attribute를 구분한다. `this()`는 다른 Constructor 호출에 관한 별도 용법이다. [M01 p.19] [M01 p.23] [M01 p.26]
- **`static` Members:** 공유 상태는 Class에, 개별 상태는 Object에 연결된다. `static` Method의 문제를 판단할 때는 값을 읽을 대상 Object가 지정되었는지 확인한다. [M01 p.27] [M01 p.31] [M01 p.32]
- **Object reference와 값 전달:** `==`는 같은 Object를 가리키는지 비교하고, reference 대입 자체는 Object 복제가 아니다. Java는 reference 값도 복사해 전달하므로, Parameter 재대입과 Object 상태 변경을 구분해야 한다. [M01 p.35] [M01 p.36] [M01 p.42]
- **Memory Management와 Garbage Collector:** Object 생성에 필요한 메모리 할당과 사용되지 않는 Object의 메모리 회수는 서로 다른 역할이다. 자동 관리가 Object 생성 표현의 불필요함이나 즉시 회수를 뜻하지 않는다. [M01 p.44]
- **OOP의 세 동기:** Encapsulation은 내부 보호와 추상화, Inheritance는 재사용과 확장, Polymorphism은 유사한 동작의 다른 구현으로 연결된다. 상세 문법은 이번 소개만으로 확정하지 않는다. [M01 p.58] [M01 p.59] [M01 p.60] [M01 p.61]
- **Lab3의 확인 범위:** `Player`의 상태와 다섯 Methods의 책임은 정리할 수 있다. health 초기값 50은 직접 전사 근거이고, 상한 50은 초기값을 넘지 않는다는 후속 설명을 연결한 해석이다. `getTactic`의 공격 70% 해석, 정확한 선언·반환 문자·이후 게임 구현은 검증 필요이다. [STT 15:41] [STT 17:39]

#### R01. OOP는 프로그램을 어떤 관점으로 보는가?

자료의 Coffee Machine 예시를 이용하여 Procedural Style과의 차이를 설명하라.

<details><summary>정답</summary>

OOP는 프로그램을 상호작용하는 Object들의 모음으로 본다. Procedural Style의 커피 예시는 작업 순서를 나열하고, Object-Oriented Style은 관련 기능을 Coffee Machine에 묶는다. 어느 쪽이든 실행 순서는 필요하다. Object는 물리적 물건뿐 아니라 계좌 같은 개념적 대상이나 소프트웨어 내부 구조도 나타낼 수 있다. [M01 p.3] [M01 p.4] [M01 p.5] [M01 p.6]

</details>

#### R02. Encapsulation의 목적을 두 가지로 설명하라.

<details><summary>정답</summary>

구성 요소의 접근 가능 범위를 제한하여 Object 내부 데이터를 보호하고, 사용하는 쪽이 내부 구현을 모두 알지 않아도 되도록 추상화를 돕는다. Class 안에 변수를 모아 놓았다는 사실만으로 이 목적이 모두 충족되는 것은 아니다. 이번 소개에서는 상세 접근 제어 문법까지 확정하지 않는다. [STT 00:55] [M01 p.59]

</details>

#### R03. Inheritance는 재사용과 확장을 어떻게 연결하는가?

<details><summary>정답</summary>

Child class가 Parent class의 특성과 코드를 이어받아 재사용하면서 필요한 새 특성을 추가할 수 있다. 둘이 항상 완전히 같은 상태와 동작을 가져야 한다는 뜻은 아니다. 분류 계층 그림은 이 관계의 자료 비유이며, 실제 구현 문법 전체를 설명한 것으로 읽지 않는다. [M01 p.60]

</details>

#### R04. Polymorphism과 서로 다른 두 `Car`의 `getSpeed()` 결과 차이는 어떻게 구분되는가?

<details><summary>정답</summary>

자료의 `getSpeed()`는 같은 Class의 같은 Method가 각 Object의 다른 `speed` 값을 읽는 경우이다. Polymorphism 소개는 서로 다른 Class들이 유사한 동작을 다르게 구현할 수 있다는 설명이다. 결과가 다르다는 관찰 하나만으로 두 상황을 같은 개념으로 분류하지 않는다. [M01 p.16] [M01 p.61]

</details>

#### R05. Class, Instance, Instantiate, Members의 관계는 무엇인가?

<details><summary>정답</summary>

Class는 Object의 설계도이고, Instance는 그 Class로 만든 Object이며, Instantiate는 Instance를 만드는 행위이다. Members는 Attributes와 Methods를 함께 부르는 말이다. `Car`라는 Class, `myCar`라는 reference 변수, `new Car()`로 만들어진 Object를 구별한다. [M01 p.7] [M01 p.9] [M01 p.17]

</details>

#### R06. 공통 Attributes를 가진 두 Object는 값을 공유하는가? 초기값은 어떻게 읽어야 하는가?

<details><summary>정답</summary>

서로 다른 Object의 instance Attributes는 각자의 값을 가진다. 하나의 `color`를 바꾸었다고 다른 Object의 `color`까지 바뀌지 않는다.

자료는 명시적 초기화와 기본값을 구분하고, 초기화하지 않은 Attributes의 예로 `boolean`의 `false`, `int`의 `0`, `float`의 `0.0`, Object를 가리키는 Attribute의 `null`을 보여 준다. 이 설명을 모든 지역변수에 확대하지 않는다. `char`의 비어 보이는 표기는 유효한 빈 문자 리터럴로 확정하지 않고 검증 필요로 남긴다. [M01 p.10] [M01 p.11] [M01 p.12] [M01 p.13] [M01 p.14]

</details>

#### R07. Method 호출을 읽을 때 코드 본문 외에 무엇을 확인해야 하는가?

<details><summary>정답</summary>

어느 Object를 통해 호출했는지 확인해야 한다. `car.printHello()`는 점과 Method 이름, 괄호를 이용한 호출이다. `getSpeed()`처럼 자신의 Attribute를 읽는 Method는 호출 대상의 상태를 사용하므로, 자료의 두 호출 결과는 각각 `100`, `90`이다. [M01 p.15] [M01 p.16]

</details>

#### R08. Constructor의 이름·반환형·Parameters에 관한 규칙은 무엇인가?

<details><summary>정답</summary>

이름은 Class와 같고 반환형 자체를 쓰지 않는다. 따라서 `void`를 붙이는 것이 아니다. Parameters를 받아 초기화할 수 있고, 서로 다른 Parameters를 갖는 여러 Constructor를 둘 수 있다.

자료에서 한 Parameter를 받는 `Car` Constructor는 `weight`를 설정하고 `"unknown"`인 `color`를 유지한다. 두 Parameters를 받는 Constructor는 둘 다 설정한다. 다른 Constructor에서 Constructor를 호출할 수 있다는 보충도 있으므로, 초기화 과정에서 언제나 Constructor 본문 하나만 실행된다는 규칙으로 확대하지 않는다. [M01 p.19] [M01 p.20] [M01 p.21] [M01 p.22]

</details>

#### R09. `speed = speed`, `this.speed = speed`, `this()`는 어떻게 다른가?

<details><summary>정답</summary>

같은 이름의 Parameter가 있는 문맥에서 `speed = speed`는 Parameter 자기 대입이다. `this.speed = speed`는 현재 Object의 Attribute에 Parameter 값을 넣는다.

`this`는 현재 Object의 Method를 명시할 때도 쓰이며, 이름 충돌 등이 없는 자료의 문맥에서는 생략할 수 있다. `this()`는 Attribute 접근이 아니라 다른 Constructor 호출을 위한 용법이다. 세부 호출 규칙은 자료에서도 후속 설명으로 남겨 둔다. [M01 p.23] [M01 p.24] [M01 p.25] [M01 p.26]

</details>

#### R10. 녹음의 `owner` 값이 여러 Instance에서 함께 바뀌어 보이는 이유는 무엇인가?

<details><summary>정답</summary>

`owner`가 Class에 연결된 하나의 `static` 상태이기 때문이다. Object마다 독립적인 문자열을 바꾸는 상황으로 해석하면 안 된다. 원 코드는 없으므로 정확한 초기값과 대입·출력 구문은 복원하지 않는다.

자료의 별도 예시에서는 세 Object를 생성하면 `num`이 `3`이고, `setMile()`에 `20`, `30`, `40`을 한 번씩 전달하면 `totalMile`은 `90`이다. 이 누적 코드는 호출 때마다 입력을 더하므로 항상 현재 개별 값들의 합을 자동 유지한다고 일반화할 수 없다. [STT 05:41] [STT 06:33] [M01 p.29] [M01 p.30]

</details>

#### R11. `static totalFuel()`의 `return fuel`은 왜 문제인가?

<details><summary>정답</summary>

`fuel`은 Object별 Attribute인데, 해당 접근에는 어느 Object의 `fuel`인지 지정되어 있지 않다. 자료는 이를 오류로 표시한다. 정상 실행 후 출력값을 묻는 문제로 처리하면 안 된다.

이 제한을 `static` 코드에서 Object 상태에 접근하는 모든 경우의 금지로 확대하지 않는다. 실제 Object를 가리키는 변수를 통해 `meter.value`처럼 대상을 지정하는 경우와 구분해야 한다. instance Method에서 `static` Method를 호출하는 방향은 자료에서 허용된다고 설명한다. [M01 p.31] [M01 p.32]

</details>

#### R12. 내용이 같은 두 `new String("hey")`의 `==` 결과는 무엇인가?

<details><summary>정답</summary>

각각 생성한 두 Object를 비교하면 `false`이다. `str3 = str1`로 같은 reference 값을 대입한 뒤 `str1 == str3`를 비교하면 `true`이다. 내용 비교와 동일 Object 여부를 구별한다.

이 결과는 자료 코드의 결과이다. 08:32의 충돌하는 부정 표현을 확정된 발화로 고친 것이 아니며, 그 발화의 정확한 의도는 검증 필요이다. [M01 p.34] [M01 p.35] [STT 08:32]

</details>

#### R13. reference 변수가 네 개이면 Object도 네 개인가?

**이해를 위한 예시:** 다음 코드는 Lab3와 별도로 만든 상태 표시기이다.

```java
class Gauge {
    int level;
    String color = "gray";
    boolean ready;

    Gauge(int level) {
        this.level = level;
    }

    Gauge(int level, String color) {
        this.level = level;
        this.color = color;
    }

    void wrong(int level) {
        level = level;
    }

    void set(int level) {
        this.level = level;
    }

    int read() {
        return level;
    }
}
```

실행 조각은 적절한 Method 안에서 한 번 실행한다.

```java
Gauge a = new Gauge(6);
Gauge b = new Gauge(9, "blue");
a.wrong(14);
a.set(4);
```

1. 생성 직후 각 Object의 `level`, `color`, `ready`를 적어라.
2. `a.wrong(14)` 직후와 `a.set(4)` 직후의 `a.read()` 결과를 구하라.
3. 마지막 `b.read()` 결과와 그 이유를 설명하라.
4. 두 Constructor에 `void`를 붙여도 같은 의미인가?

<details><summary>풀이와 채점 포인트</summary>

생성 직후의 상태는 다음과 같다.

| Object | `level` | `color` | `ready` |
| --- | --- | --- | --- |
| `a`가 가리키는 Object | `6` | `"gray"` | `false` |
| `b`가 가리키는 Object | `9` | `"blue"` | `false` |

첫 Constructor는 `level`만 설정하므로 선언에서 정한 `color`가 남는다. 두 번째 Constructor는 두 Attributes를 모두 설정한다. `ready`는 명시적으로 초기화하지 않은 `boolean` Attribute이므로 `false`이다.

`wrong()`의 두 `level`은 모두 Parameter를 뜻하므로 Object 상태는 바뀌지 않는다. 따라서 그 직후 `a.read()`는 `6`이다. `set()`은 현재 Object의 Attribute에 대입하므로 그 뒤에는 `4`이다. `b`는 별개의 Object이므로 `b.read()`는 계속 `9`이다.

Constructor에는 반환형을 쓰지 않는다. `void`를 붙인 선언을 같은 Constructor로 취급할 수 없다.

**채점 포인트:** 초기 상태 표 2점, 두 대입 대상 구별 2점, `b`의 독립 상태 설명 1점, Constructor 반환형 구별 1점.

- **접근 상태:** 현재 접근 가능.
- **유형:** 일반 연습 — 관련 기출 근거 없음. 중첩 Class의 오류 수정 문제를 재현하지 않는다.

**이해를 위한 예시:** 아래 Class에 대해, 이전 Object 생성이나 호출이 없는 상태에서 실행 조각을 한 번 실행한다.

```java
class Ticket {
    static int count;
    static int total;
    int value;

    Ticket(int value) {
        this.value = value;
        count++;
    }

    void put(int value) {
        this.value = value;
        total += value;
    }

    static int read(Ticket ticket) {
        return ticket.value;
    }
}
```

```java
Ticket a = new Ticket(0);
Ticket b = new Ticket(0);
a.put(4);
b.put(6);
a.put(1);
```

1. 마지막 `Ticket.count`, `Ticket.total`, `a.value`, `b.value`를 구하라.
2. `Ticket.total`은 마지막 두 Object의 `value` 합과 같은가?
3. `Ticket.read(a)`가 읽는 값은 무엇인가?
4. 별도로 `static int bad() { return value; }`를 Class에 추가하면 왜 문제가 되는가?

<details><summary>풀이와 채점 포인트</summary>

Constructor가 두 번 실행되므로 `count`는 `2`이다. `put()`은 매번 전달값을 공유 `total`에 더한다.

$$
\text{total}=4+6+1=11
$$

반면 각 Object의 `value`는 최근 대입값을 저장하므로 `a.value`는 `1`, `b.value`는 `6`이다. 현재 두 값의 합은 `7`이며 누적값 `11`과 다르다.

`Ticket.read(a)`는 `a`가 가리키는 Object를 명시하여 `value`를 읽으므로 결과가 `1`이다. 가정한 `bad()`의 `return value`에는 어느 Object의 Attribute인지 지정되어 있지 않으므로 컴파일 오류가 발생한다. 이를 실행 후 임의의 값이 나오는 상황으로 처리하지 않는다.

**채점 포인트:** 공유값과 개별값 계산 2점, 누적합과 현재 합 구별 1점, 명시한 Object 접근 설명 1점, 오류의 원인과 단계 구별 1점.

</details>

**이해를 위한 예시:**

```java
class Box {
    int value;

    Box(int value) {
        this.value = value;
    }
}

class Tools {
    static void touch(int n, Box box) {
        n = 8;
        box.value = 8;
        box = new Box(20);
        box.value = 21;
    }
}
```

다음 실행 조각은 적절한 Method 안에서 한 번 실행한다.

```java
int n = 3;
Box a = new Box(3);
Box c = new Box(3);
Box alias = a;
Tools.touch(n, a);
```

1. 호출 뒤 `n`, `a.value`, `alias.value`, `c.value`는 각각 무엇인가?
2. `a == c`와 `a == alias`의 결과는 무엇인가?
3. `touch()` 안에서 `box`에 새 reference를 대입했는데도 `a`가 그 새 Object를 가리키지 않는 이유는 무엇인가?

<details><summary>풀이와 채점 포인트</summary>

호출 시 정수 값과 reference 값이 각각 복사된다.

| 확인 대상 | 호출 뒤 값 |
| --- | --- |
| 호출자의 `n` | `3` |
| `a.value` | `8` |
| `alias.value` | `8` |
| `c.value` | `3` |
| `a == c` | `false` |
| `a == alias` | `true` |

내부 `n = 8`은 복사된 Parameter만 바꾼다. 첫 `box.value = 8`은 아직 `a`와 같은 Object를 가리키는 reference를 통해 그 Object의 상태를 바꾼다. `alias` 역시 같은 Object를 가리키므로 `8`을 관찰한다.

이후 `box = new Box(20)`은 내부 Parameter에 새 reference 값을 넣는다. 호출자의 `a`에 대입하는 문장이 아니므로 `a`는 기존 Object를 계속 가리킨다. 마지막 `21`은 새 Object의 값이다. `c`가 가리키는 별개의 Object는 변경되지 않는다.

**채점 포인트:** 네 상태값 2점, 두 동일성 비교 1점, 값 복사·Object 변경·Parameter 재대입의 세 단계 설명 3점. 실제 물리적 주소값을 가정할 필요는 없다.

</details>
