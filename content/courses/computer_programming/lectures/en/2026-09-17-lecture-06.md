### Object-oriented programming models entities and their interactions

[[concepts/object-oriented-programming|Object-oriented programming (OOP)]] organizes a software system around objects that represent entities and interact with one another. An object is more than a collection of stored values: it combines state with operations that use or change that state. The recorded opening frames this lab as a review of objects and classes, constructors, and memory states, followed by an application of those ideas to a fighting game. The recording begins mid-flow, so the preceding explanation is unavailable; its exact content is **검증 필요 (verification needed)**. [STT 00:00]

The deck’s modeling diagram separates real-world entities from their software representations. A house, a person, and a car become objects in a model, while relationships describe the person living in the house and driving the car. The distinction matters: identifying the objects does not yet explain how the system works; the relationships and interactions supply that additional structure. This figure supports the recorded definition, but it does not establish that the instructor discussed every element of the diagram during this lab. [M01 p.3]

An object need not represent something physically tangible. The deck distinguishes a physical entity such as a car, a conceptual entity such as a bank account, and a software entity such as a Linked List. These examples broaden the meaning of “object”: the relevant question is whether an entity has useful state and behavior for the program being modeled. [M01 p.4]

The coffee example provides a concrete comparison with procedural organization. The procedural version lists operations in sequence: obtain ingredients, grind the beans, boil the water, and mix. The object-oriented version groups grinding, boiling, and mixing capabilities into a Coffee Machine and then supplies ingredients to that machine. Both descriptions still involve operations and an order of execution. The difference is how responsibilities are organized around an entity. [M01 p.5] [M01 p.6]

A useful reading of this example is:

- The coffee beans and water are inputs.
- The Coffee Machine is the entity responsible for the relevant operations.
- Producing coffee results from using those operations together.

The misconception to avoid is that OOP eliminates procedures or automatically makes every design better. Here, its purpose is to make the relationship between an entity, its state, and its responsibilities explicit. The coffee example is material-supported explanation, not a reconstruction of missing speech.

#### Encapsulation: controlling access to implementation and state

[[concepts/encapsulation|Encapsulation]] concerns the boundary around an object’s implementation. In this introduction, limiting the visibility of components helps protect an object’s data from outside access and makes the program easier to understand through abstraction. A user of an object can focus on its available behavior without needing to manipulate every internal detail. [STT 00:55] [M01 p.59]

For example, the Coffee Machine can be understood through its grinding and boiling capabilities without requiring its user to describe every internal mechanism. This is a conceptual application of the deck’s examples, not an additional lab requirement. [M01 p.6] [M01 p.59]

Encapsulation should not be reduced to “put everything in a class.” The recorded motivation includes protecting state and hiding implementation details. Detailed access-modifier rules are not established by this brief introduction.

### Attributes represent state, and instance fields belong to individual objects

An [[concepts/attributes-and-methods|attribute]] represents a property of an object, such as its appearance or current state. The recorded discussion uses this role to distinguish attributes from the actions performed by methods. A garbled phrase within the attribute description remains **검증 필요**; the deck supplies the clear distinction between properties and behavior. [STT 02:44] [M01 p.8]

The material’s `Car` example declares a `width` initialized to `10` and a `color` initialized to `"red"`. Dot notation selects an attribute through an object reference. Reading `car.width` obtains that object’s current width; assigning `car.width = 5` changes it. Consequently, the two reads around that assignment produce `10` and then `5`. [M01 p.10] [M01 p.11]

The multiple-object example then separates common structure from individual values. Both cars have a `color` field because both are instances of `Car`. Changing one object’s color to `"blue"` leaves the other object’s color `"red"`. The shared declaration does not turn their instance fields into one shared storage location. [M01 p.14]

| `float` | `0.0` |

These are examples of **field** initialization. They should not be generalized into a claim that every variable appearing anywhere in a method can be read before initialization. [M01 p.12] [M01 p.13]

### Methods act on the object selected by the call

A method defines an action an object can perform or a way it can use or change its attributes. In the recorded explanation, methods complement attributes: attributes describe state, and methods describe behavior. The exact subject of one spoken phrase is unclear, but that distinction is supported by the deck. [STT 02:44] [M01 p.8]

A call such as `car.printHello()` combines an object reference, a dot, a method name, and parentheses. The material’s method prints a greeting when invoked. This example establishes invocation syntax and the connection between an object and an available operation. [M01 p.15]

The `getSpeed()` example adds an important mechanism: the method reads the state of its **receiver**, meaning the object selected by the call. With `myCar.speed` set to `100` and `yourCar.speed` set to `90`, the calls `myCar.getSpeed()` and `yourCar.getSpeed()` return `100` and `90`, respectively. The method definition is the same, but the receiver’s state differs. [M01 p.16]

A small, independently authored illustration uses a different class:

```java
class Gauge {
    int reading;

    int read() {
        return reading;
    }
}
```

Inside a demonstration method:

```java
Gauge left = new Gauge();
Gauge right = new Gauge();

left.reading = 6;
right.reading = 9;

System.out.println(left.read());   // 6
System.out.println(right.read());  // 9
```

The result follows by identifying the receiver of each call and then reading its field. This is an explanation of object-specific state, not a recovered lecture example or an implementation of Lab3.

The misconception to avoid is treating the method name alone as sufficient to determine its result. For an instance method that uses fields, the receiver and its current state matter. Different results here also do not require different method implementations, so this example should not be relabeled as the polymorphism example introduced earlier.

### Constructors establish an object’s initial state

A [[concepts/constructors|constructor]] is a special initialization construct associated with creating an instance. The lecture introduces constructors after instantiation and then explains that they can accept multiple parameters and that a class can provide multiple constructors with different parameter lists. [STT 03:40] [STT 04:37]

A constructor has the same name as its class and no return type—not even `void`. Although the introductory speech and slide describe constructors using method-like terminology, the note-side distinction is important: a constructor is not an ordinary method that can subsequently be invoked through an expression such as `object.ConstructorName()`. [M01 p.19]

The simplest deck example has a `Car()` constructor that prints a creation message. Creating the object causes that initialization code to execute. The example demonstrates the relationship between construction and initialization; it does not mean every constructor must print anything. [M01 p.20]

The parameterized example is more informative. The class has a `weight` field and a `color` field initially set to `"unknown"`:

- `Car(int w)` assigns the supplied weight.
- `Car(int w, String c)` assigns both weight and color.

Thus, `new Car(1500, "red").printInfo()` reports `1500 kg, red`, while `new Car(2000).printInfo()` reports `2000 kg, unknown`. In the second case, the one-parameter constructor leaves the explicitly initialized color unchanged. The result comes from following which assignments each constructor actually performs. [M01 p.21] [M01 p.22]

The slide also qualifies its simplified constructor wording: one constructor can invoke another constructor. Therefore, the lecture’s introductory description must not be expanded into a universal claim that exactly one constructor body executes once for every object. The relevant lesson here is initialization during construction, with constructor chaining acknowledged but not developed into a new advanced topic. [M01 p.19]

A common mistake is to assume that all constructors must initialize every field in exactly the same way. The deck deliberately shows two construction paths that establish different initial information while leaving another field at its declared initial value.

### `this` identifies the current object and resolves name conflicts

The deck demonstrates this by assigning and printing the color using both forms. It also shows `this.speedAndUnit()` as an explicit call on the current object, with `this` optional in that example. [M01 p.24] [M01 p.25]

The more important case occurs when a parameter has the same name as a field. The slide starts with a `speed` field initialized to `30` and contrasts these two assignments:

```java

```

```java

```

Inside a method whose parameter is named `speed`, the first statement assigns the parameter to itself. It does not select the field, so the object’s speed remains unchanged. ### Object identity differs from equal contents

For object references, `==` tests whether the references identify the same object. It does not inspect all of the objects’ contents to decide whether those contents match. The lecture and deck describe this through “address” language; the precise note-side interpretation is reference identity, without promising that Java exposes literal physical memory addresses. [STT 08:32] [M01 p.34]

The material provides a deliberately revealing example:

```java
String str1 = new String("hey");
String str2 = new String("hey");
String str3 = str1;
```

The first two statements create separate `String` objects containing the same text. The third copies the reference held by `str1`. Therefore:

| Comparison | Result | Reason |
|---|---|---|
| `str1 == str2` | `false` | The references identify two separately created objects. |
| `str1 == str3` | `true` | Both references identify the same object. |

The deck explicitly supplies these results. [M01 p.35]

The memory figure reinforces the reasoning by showing two separate boxes containing `"hey"`. Equal text appears in both boxes, but two boxes still represent two objects. The third variable does not require a third object because it receives an existing reference. The visual distinction is between **what an object contains** and **which object a reference selects**. [M01 p.34] [M01 p.35]

The recorded negations around the first comparison contradict the surrounding explanation and the slide result. That speech remains **검증 필요**. The `false` result above is a material-supported Java explanation, not a claim that the uncertain sentence has been recovered or corrected verbatim. [STT 08:32]

The main misconception is that identical contents force `==` to be true. They do not. This lecture’s example establishes identity comparison; it does not develop a general framework for implementing content equality.

### Reference assignment creates another route to an existing object

Assigning an object reference with `=` copies the reference value. It does not, by itself, create another object or copy all of an object’s fields. This is the distinction behind the recorded explanation that a later identity comparison becomes true after assignment. [STT 08:32]

The deck illustrates the mechanism with one construction followed by several assignments:

```java
Car myCar = new Car();
Car car1 = myCar;
Car car2 = myCar;
Car car3 = car1;
```

There is one `new Car()` expression and one `Car` object. All four variables refer to that object. The diagram therefore shows one object rather than four separate cars. [M01 p.36]

These variables are [[concepts/object-references|aliases]] for the same object: they provide different routes to the same state. For example, in a class with a mutable field, changing that field through one alias changes the object that all aliases select. This differs from the earlier two-car example, where separate `new` expressions created separate objects with independent instance fields. [M01 p.14] [M01 p.36]

The recording’s wording about changing an object’s address should be read cautiously. The supported operation changes a variable’s reference; it does not relocate the object. Nor does it create a duplicate object. Those are different operations that the shown assignment does not perform. [STT 08:32]

A reliable tracing method is to distinguish variables from objects: track which reference each variable holds, then identify the object reached by that reference. Counting variable names alone overcounts the objects in this example.

### Primitive arguments are copied into method parameters

[[concepts/pass-by-value|Pass-by-value]] means that a method receives a copy of an argument’s value. With a primitive argument such as an `int`, changing the parameter changes that local copy, not the caller’s original variable. The recording explains this through an integer named `number` whose value outside the method remains unchanged. The exact code, numeric value, and one action verb in that example are unavailable and remain **검증 필요**. [STT 09:27] [STT 10:14]

The deck supplies a separate, fully specified example: a method that tries to swap two integer values.

```java
static void swap(int a, int b) {
    int temp = a;
    a = b;
    b = temp;
}
```

If the caller has `a = 2` and `b = 3`, invoking `swap(a, b)` copies those values into the parameters. The assignments then change the parameter values to `3` and `2`. They do not assign to the caller’s variables. The caller subsequently prints `2 3`. [M01 p.37] [M01 p.38]

The memory table on page 39 is especially important because it separates two execution contexts:

| Location immediately before `swap` returns | `a` | `b` | `temp` |
|---|---:|---:|---:|
| Caller’s variables | 2 | 3 | — |
| `swap` parameters and local variable | 3 | 2 | 2 |

The repeated names do not identify the same variables. The table’s separate regions explain how the method can successfully exchange its own parameter values while leaving the caller unchanged. [M01 p.39]

The step-by-step reasoning is:

1. Copy `2` and `3` into the parameters.
2. Save the parameter `a`’s value, `2`, in `temp`.
3. Assign `3` to parameter `a`.
4. Assign `2` to parameter `b`.
5. Return without any assignment to the caller’s variables.

A phrase in the recording ambiguously identifies which local variable remains unchanged. The supported distinction is the subsequent contrast between changes inside the method and the unchanged value outside it; the ambiguity is not resolved by inventing a corrected sentence. [STT 09:27]

The misconception is that sharing a name, or passing a variable as an argument, gives the method direct control over that caller variable. In this example, the parameter is a separate variable initialized with a copied primitive value.

### Reference values are also copied, but the referenced object can be changed

Java passes reference values by value as well. A method receiving an object reference gets a copy of that reference, and both copies can identify the same object. Consequently, an assignment to the object’s field can be visible to the caller even though the caller’s reference variable was not passed by reference. [M01 p.42]

The recording introduces this topic using the term “call by reference” and describes a `Car` whose `speed` changes inside `changeSpeed`. The supported behavioral point is that the method changes the state of the object reached through the supplied reference. The exact method signature and speed values are not supplied, and the class/object shorthand in the speech must not be expanded into invented code. [STT 10:14] [STT 11:07] [STT 11:52]

**Note-side qualification:** the recorded terminology is preserved as a source limitation. The explanation here uses Java’s more precise rule: all arguments are passed by value, including reference values. The deck itself provides a qualification that thinking in terms of copied reference values connects this behavior to call-by-value. This clarification is not recovered speech. [M01 p.42]

The material’s `IntHolder` example makes the difference visible. `IntHolder` contains an integer field named `value`, initialized by its constructor. Instead of assigning new values to primitive parameters, the method assigns to fields of the referenced objects:

```java
static void swap(IntHolder a, IntHolder b) {
    int temp = a.value;
    a.value = b.value;
    b.value = temp;
}
```

For two distinct holders initially containing `2` and `3`, the method saves `2`, writes `3` into the first holder, and writes `2` into the second. The caller then observes field values `3` and `2`. The method has changed the objects, not exchanged the caller’s reference variables. [M01 p.40] [M01 p.41]

The corresponding diagram shows those changed object fields and a temporary value of `2` inside the method. Compare this with the primitive diagram: the earlier assignments changed only local parameter values, whereas these assignments follow references and modify fields in shared target objects. [M01 p.43]

An independently authored example isolates that mechanism without a swap:

```java
class Box {
    int value;

    Box(int value) {
        this.value = value;
    }

    static void increase(Box target) {
        target.value = target.value + 1;
    }
}
```

Inside a demonstration method:

```java
Box item = new Box(4);
Box.increase(item);
System.out.println(item.value);  // 5
```

`target` receives a copy of the reference held by `item`. Both select the same box, so changing `target.value` changes the field later read through `item`.

The misconception is that a caller-visible change proves Java uses two different argument-passing mechanisms. The difference here is what gets changed: a local parameter value or a field of a referenced object.

The supporting examples are the primitive and `IntHolder` examples on pages 37–43. They do not establish coverage of the separate **More on swaps** section on pages 45–56.

### Automatic memory management handles allocation and reclamation

[[concepts/garbage-collection|Garbage collection]] is introduced as part of Java’s automatic memory management. The deck distinguishes two responsibilities: allocating memory when an object is created and reclaiming memory associated with unused objects. The recorded recap moves through these points immediately before the Lab3 transition. [STT 11:52] [STT 12:50] [M01 p.44]

Automatic allocation does not mean that a programmer never writes an object-creation expression. The earlier `new Car()` examples still request construction of an object. The point is that Java manages the memory needed for the object rather than requiring the programmer to specify and release that storage manually. [M01 p.9] [M01 p.44]

The deck contrasts this with explicit allocation and freeing in C. Within this lecture, the comparison motivates Java’s managed object memory; it is not a complete account of every storage-duration or allocation mechanism in C. [M01 p.44]

The earlier aliasing example also helps avoid an overly simple reclamation story.
