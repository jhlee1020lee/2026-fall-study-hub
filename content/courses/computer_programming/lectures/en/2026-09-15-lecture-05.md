Learn how classes organize state and behavior, how Java references determine the effects of assignments and method calls, and how encapsulation controls access to state.  
The practice follows the lecture through getter/setter validation and tracing. The introductory package definition and access distinctions are included; detailed package rules, inheritance implementation, and constructor chaining remain outside this session.

## Lecture Content and Explanation

### Object-oriented programming models entities and their interactions

[[concepts/object-oriented-programming|Object-oriented programming (OOP)]] organizes a software system around objects that represent entities and interact with one another. An entity need not be a physical object. The lecture distinguishes a car as a physical entity, a bank account as a conceptual entity, and a linked list as a software entity. The linked list is an example of what software can represent; its internal implementation was not taught here. [STT 00:57] [STT 01:48] [M01 p.3] [M01 p.4]

The figure on M01 p.3 separates a real-world scene from a simplified software model. Above the dividing line are a person, a house, and a car. Below it are corresponding objects connected by relationships: the person lives in the house and drives the car. The relationships matter as much as the individual entities. A model should represent the interactions relevant to the program without reproducing every detail of the world. [M01 p.3]

The instructor frames the course as learning how to design programs through OOP, beyond acquiring Java syntax alone. Conditions, loops, and assignments still perform the underlying work, but classes and objects provide a larger structure in which to understand that work. The lecture explicitly treats OOP as a way to improve organization and readability, rather than as a prerequisite for computations that procedural programs could never perform. [STT 00:00] [STT 22:24]

The coffee example makes this distinction concrete:

| Procedural description | Object-oriented description |
|---|---|
| Describe obtaining beans, grinding them, obtaining water, boiling it, combining the ingredients, and mixing them. | Define or obtain a Coffee Machine with grinding, boiling, and mixing capabilities. |
| The user-facing procedure includes the individual preparation operations. | The user-facing procedure becomes obtaining ingredients and supplying them to the machine. |
| Each relevant operation must still happen. | The machine takes responsibility for carrying out its internal operations. |

[M01 p.5] [M01 p.6]

The instructor specifically distinguishes the machine’s **capabilities** from the user’s **sequence of actions**. Grinding, boiling, and mixing describe what the machine can do; they are not three additional user instructions merely renamed as objects. This is the motivation for [[concepts/abstraction|abstraction]]: a useful component lets its user reason at the level of the task while its implementation manages the details. [STT 02:39] [STT 03:38] [STT 04:25]

A common misconception is that procedural code is inherently incorrect. The lecture says the procedural coffee description is perfectly reasonable. The difficulty arises as detailed procedures become long enough that understanding, changing, and maintaining them becomes harder.

### Classes define common structure; objects carry individual state

A [[concepts/classes-and-objects|class]] defines the structure and behavior of objects created from it. An **object**, also called an **instance** in this lecture, is a particular realization of that definition. To **instantiate** a class is to create an instance. [M01 p.7] [M01 p.17] [STT 16:40]

The mold-and-pastry illustration on M01 p.7 distinguishes a reusable specification from the individual things produced with it. The adjacent car illustration makes the same point: one `Car` class supplies a common definition for several car objects. Reusing a definition does not require every resulting object to have identical state. [M01 p.7]

The lecture divides the class definition into two complementary parts:

- **Attributes**, represented by fields in the Java examples, describe state or properties such as `fuel`, `speed`, and `color`.
- **Methods**, also called member functions, implement actions such as refueling or accelerating.

Together, attributes and methods are called **members** in the terminology introduced here. A property such as speed can be an attribute even though it is not a physical component that can be removed from a car. [STT 06:21] [STT 07:20] [M01 p.8] [M01 p.17]

The paired car diagrams on M01 p.8 place methods and attributes inside the same class boundary. This arrangement connects behavior to state: a refueling operation changes fuel, while an acceleration operation changes speed and may affect other properties. The diagram’s repeated structure represents a common definition, not a requirement that all cars share one set of field values. [M01 p.8]

The initial Java example separates three roles:

```java
class Car {
}

// A statement used in an appropriate method:
Car myCar = new Car();
```

Here, `class Car` declares a class, `Car` is the variable’s type, `myCar` is a reference variable, and `new Car()` creates an object and supplies the reference assigned to that variable. Calling the variable “an object” is convenient classroom shorthand, but distinguishing the variable from the object becomes essential when studying assignment and method arguments. [STT 08:16] [STT 09:15] [M01 p.9]

The instructor associates `new` with obtaining storage for a new object. This does not mean that the entire class definition or all method code is physically copied for every instance.

### Fields, initialization, and the independence of separate objects

A field stores an object’s state. In the introductory `Car` example, the declarations provide initial values:

```java
class Car {
    int width = 10;
    String color = "red";
}
```

These are starting values, not permanent properties of every car. The dot operator selects a member through an object reference:

```java
Car car = new Car();

System.out.println(car.width); // 10
car.width = 5;
System.out.println(car.width); // 5
```

The assignment changes the selected object’s `width`. It does not rewrite the class declaration. The lecture also introduces the naming convention of beginning class names with uppercase letters and ordinary variable names with lowercase letters; this convention is distinct from the language’s type rules. [STT 10:12] [STT 11:11] [M01 p.10] [M01 p.11]

The instructor recommends explicit initialization because visible starting values make behavior easier to anticipate and maintain. Java nevertheless supplies default values for fields that lack explicit initializers. The `Foo` code slide illustrates this distinction. [STT 12:04] [STT 13:00] [M01 p.12] [M01 p.13]

| Field type illustrated | Default value | Interpretation |
|---|---|---|
| `boolean` | `false` | A Boolean value |
| `int` | `0` | An integer value |
| `float` | `0.0f` | A floating-point value |
| `char` | `'\u0000'` | The null character, which may appear invisible when printed |
| `String` or another reference type | `null` | No object is referenced |

**Source clarification.** The blank-looking character notation on M01 p.12 must not be learned as an empty Java character literal: `''` is invalid. Also, the automatic-default rule applies to fields and array components. An ordinary local variable must be definitely assigned before it is read; it does not acquire a usable default merely because a field of the same type would. The mixed width/color wording at [STT 10:12] remains **검증 필요** as speech; the printed declarations establish `width = 10` and `color = "red"`.

Separate object creation produces separate instance state:

```java
Car car = new Car();
Car newCar = new Car();

newCar.color = "blue";

System.out.println(car.color);    // red
System.out.println(newCar.color); // blue
```

There are two `new` expressions and therefore two car objects. Changing the second car’s field does not change the first car’s corresponding field. This is the specific situation illustrated on M01 p.14. Later examples will show that two variables can instead refer to the *same* object, in which case changes through one variable are visible through the other. [STT 13:45] [M01 p.14]

The recurring distinction is between sharing a **definition** and sharing an **object**. Objects created from one class share the former; they do not automatically share the latter.

### Instance methods act through a particular receiver

An [[concepts/instance-methods|instance method]] is invoked on a particular object, its **receiver**. The receiver determines which instance fields the method reads or changes.

The first method example prints a message:

```java
class Car {
    void printHello() {
        System.out.println("Hello World!");
    }
}
```

Calling `car.printHello()` runs that method with `car` as its receiver. The parentheses denote a method call, and `void` means the method returns no value. Printing is an observable action; it is not the same as returning a result. [STT 14:42] [M01 p.15]

The next example makes the receiver’s importance visible:

```java
class Car {
    int speed;

    int getSpeed() {
        return speed;
    }
}
```

After constructing two cars and assigning `myCar.speed = 100` and `yourCar.speed = 90`, the calls `myCar.getSpeed()` and `yourCar.getSpeed()` return `100` and `90`, respectively. One method definition is reused, but each invocation reads the state of its own receiver. [STT 15:41] [M01 p.16]

The lecture’s statement that these methods belong to objects should be understood through this receiver relationship. It does not establish that a separate physical copy of each method’s code is stored inside every object. The design benefit is that callers can request a meaningful operation on a particular entity without duplicating the operation’s implementation. [STT 16:40]

The `Car` declarations throughout these explanations are independent teaching examples, as in the changing slide examples; they are not intended to be pasted together as repeated declarations in one compilation unit.

### Constructors make initialization part of object creation

A [[concepts/constructors|constructor]] participates in initializing a newly created object. It has the class’s name and declares no return type, including no `void`. The lecture’s first constructor performs a visible action during construction:

```java
class Car {
    Car() {
        System.out.println("A car is created.");
    }
}
```

Evaluating `new Car()` runs this constructor as part of creating the car. By contrast, declaring `void Car()` would declare an ordinary method with an unusual name, not the constructor shown here. [STT 17:35] [STT 18:33] [STT 19:33] [M01 p.19] [M01 p.20]

The slides describe constructors as special methods, but constructors do not follow all ordinary-method rules. The statement that constructors cannot be explicitly called is also qualified by the slide itself: constructor-to-constructor invocation exists, and its details were deferred. Likewise, the later mention of `this()` does not establish constructor chaining as completed material for this session. [M01 p.19] [M01 p.23] [STT 24:11]

Constructors can accept parameters, and a class can provide several constructors with different parameter lists. The `Car` example offers two initialization choices:

```java
class Car {
    int weight;
    String color = "unknown";

    Car(int w) {
        weight = w;
    }

    Car(int w, String c) {
        weight = w;
        color = c;
    }

    void printInfo() {
        System.out.println(weight + " kg, " + color);
    }
}
```

The two calls have different initialization paths:

| Construction | `weight` afterward | `color` afterward |
|---|---:|---|
| `new Car(1500, "red")` | `1500` | `"red"` |
| `new Car(2000)` | `2000` | `"unknown"` |

[M01 p.21] [M01 p.22]

Both constructors assign `weight`; only the two-argument constructor replaces the field initializer for `color`. The class as shown offers no zero-argument constructor. Calling `printInfo()` on these two objects prints `1500 kg, red` and `2000 kg, unknown`. Its return type remains `void`; different printed messages are not different return values. [STT 20:27] [STT 21:24]

The instructor’s design argument is that initialization should not have to be rewritten as a series of external assignments after every object creation. Constructors give callers named, consistent entry points into valid initial states and make repeated object creation easier to read. They do not make every possible invalid state impossible automatically; that depends on the initialization logic provided. [STT 22:24]

### `this` identifies the current object and resolves shadowing

The keyword [[concepts/this-keyword|`this`]] refers to the current object. It is particularly useful when a parameter or local variable has the same name as a field.

M01 p.26 provides the decisive comparison:

```java
class Car {
    int speed = 30;

    void cantChangeSpeed(int speed) {
        speed = speed;
    }

    void changeSpeed(int speed) {
        this.speed = speed;
    }
}
```

In `cantChangeSpeed`, both occurrences of `speed` resolve to the parameter. Assigning that parameter to itself leaves the field unchanged. In `changeSpeed`, `this.speed` explicitly selects the receiver’s field, while the right-hand `speed` selects the parameter. [STT 27:00] [STT 27:55] [M01 p.26]

For a newly created car:

| Operation | Field `speed` afterward | Reason |
|---|---:|---|
| Initial state | `30` | Field initializer |
| `cantChangeSpeed(90)` | `30` | Parameter assigns to itself |
| `changeSpeed(90)` | `90` | Parameter value is assigned to the field |

This is a case where the qualifier is needed to express the intended assignment. It is not evidence that every unqualified field name denotes a local variable.

**Source conflict: M01 p.24.** The earlier `changeColor()` example contains a `color` field but no local variable or parameter named `color`:

```java
void changeColor() {
    this.color = "red";
    System.out.println(this.color);

    color = "blue";
    System.out.println(color);
}
```

Both assignments therefore affect the same field. The method prints `red` and then `blue`, and the field is `blue` afterward. The explanation at [STT 24:11] that the second assignment changes only a local variable conflicts with the printed code. That explanation remains **검증 필요**; it must not be used to reinterpret a local declaration into the slide. [M01 p.24]

`this` can also qualify an instance-method call. M01 p.25 separates formatting from printing:

```java
class Car {
    int speed = 100;

    String speedAndUnit() {
        return speed + " km/h";
    }

    void printSpeedAndUnit() {
        System.out.println(this.speedAndUnit());
    }
}
```

`speedAndUnit()` returns `"100 km/h"` for this initial state. `printSpeedAndUnit()` prints that result. The `this` in this particular method call can be omitted, and the unqualified `speed` resolves to the field because no parameter or local variable shadows it. Keeping the formatting in a separate method lets other operations reuse the same representation without repeating the concatenation expression. [STT 25:10] [STT 26:08] [M01 p.25]

**Exam connection — partial.** The recalled 2025-1 midterm’s Question 5 compares `this` and `super`. The current lecture supports explaining the current-object role of `this`, including field selection and shadowing. A complete comparison requires the later superclass material; constructor chaining must not be inferred from today’s brief mention. [EX:cp_2025_1_midterm_q05 p.3]

### `static` associates a member with the class

A [[concepts/static-members|`static` member]] is associated with the class rather than with an individual instance. M01 p.27 contrasts one class-level count with three object-level brands. Each car has its own brand, while the illustrated total number describes the collection of cars. [STT 28:51] [STT 30:39] [M01 p.27]

The simplest example uses the class name directly:

```java
class Car {
    static int num = 3;

    static void printNum() {
        System.out.println("The number of cars is " + num);
    }
}
```

Both `Car.num` and `Car.printNum()` can be used without first creating a `Car`. All accesses to this same static field observe the same class-associated value. The static field is not an additional independent `num` field in each car object. [STT 29:50] [M01 p.28] [M01 p.29]

The next example combines shared state with instance state:

```java
class Car {
    static int num;
    static int totalMile;
    int mile;

    Car() {
        num++;
    }

    void setMile(int mile) {
        this.mile = mile;
        totalMile += mile;
    }
}
```

Starting with the default zero values of these static integer fields, three constructions increment `num` three times. Calling `setMile(20)`, `setMile(30)`, and `setMile(40)` once on the three different objects produces `Car.num == 3` and `Car.totalMile == 90`. The instructor uses this example to distinguish information about a particular car from information maintained at class level. [STT 31:39] [STT 32:37] [STT 33:33] [M01 p.30]

Two qualifications follow from the exact code:

1. `num` counts constructor executions. Nothing in this class decrements it when an object becomes unreachable, so it does not automatically track the number of currently live objects.
2. `totalMile` accumulates the arguments supplied to `setMile`. It is not maintained as the sum of the current `mile` fields.

For example, after the original `20`, `30`, and `40` calls, calling `car1.setMile(50)` changes the current fields to `50`, `30`, and `40`, whose sum is `120`. But `totalMile` becomes `140`, because the method adds another `50` to the previous `90`. This is a consequence of the displayed implementation, not an additional claim about what the instructor demonstrated. [M01 p.30]

The lecture’s suggestion to assume zero is unnecessary as a Java field-default rule, although its recommendation to make initial values explicit remains a readability recommendation. Similarly, class-associated storage should not be interpreted as a promise about a particular physical memory layout.

### A static context needs an explicit receiver for instance state

An instance method has a current object; a static method has no implicit current instance. Consequently, a static method cannot read an instance field merely by naming it when no receiver is available.

The printed example illustrates the problem:

```java
class Car {
    float fuel;

    static float totalFuel() {
        return fuel; // Compile-time error: no instance receiver
    }
}
```

Which car’s `fuel` should this expression read? The declaration supplies no answer. The defect is in the method definition and prevents compilation; constructing a car is not the event that creates the underlying error. The instructor’s explanation eventually makes this compilation distinction explicit. [STT 34:26] [STT 35:25] [STT 36:24] [M01 p.31] [M01 p.32]

The slides’ blanket wording about static methods being unable to use instance members needs qualification. The following independently adapted method supplies the missing receiver:

```java
static float fuelOf(Car car) {
    return car.fuel;
}
```

Placed inside the illustrated `Car` class and called with a non-null car, this method can read that car’s instance field. A static method can similarly call an instance method through an explicit object reference. Conversely, an instance method may call a static method. [M01 p.28] [M01 p.31]

The rule is therefore about the availability of an appropriate receiver, not a universal ban on mixing static and instance operations. The contradictory static/non-static sentence at [STT 34:26] remains **검증 필요** as speech; it is not silently reversed and attributed back to the instructor.

### Reference assignment preserves object identity rather than copying an object

A [[concepts/references-and-aliasing|reference]] is a value that identifies an object. A reference variable stores that value; it is not the object itself.

The `String` example separates equal contents from identical objects:

```java
String str1 = new String("hey");
String str2 = new String("hey");
String str3 = str1;

System.out.println(str1 == str2); // false
System.out.println(str1 == str3); // true
```

The first two construction expressions produce distinct `String` objects with the same contents. Assigning `str1` to `str3` copies a reference value, so those two variables refer to the same object. Reference comparison with `==` tests identity, not character-by-character equality. [STT 37:18] [STT 38:18] [M01 p.34] [M01 p.35]

The same reasoning applies to a user-defined class:

```java
Car myCar = new Car();
Car car1 = myCar;
Car car2 = myCar;
Car car3 = car1;
```

There is one car object and four references to it. These references are **aliases**. If a field of that object is changed through `car1`, reading that field through `myCar`, `car2`, or `car3` observes the same changed state. No object copy is performed by these assignments. [STT 39:13] [M01 p.36]

The memory pictures on M01 pp.47–48 clarify what the variable stores. For `int x = 2`, the selected variable holds the primitive value `2`. For `String s = "Hi"`, the selected variable holds a reference leading to a `String` object. The pedagogical address labels help distinguish the variable’s storage from the object it references. They should not be memorized as physical Java addresses or treated as a specification of runtime layout. [STT 51:03] [STT 52:02] [M01 p.47] [M01 p.48]

The “symbol table” in this explanation is a map connecting names to the locations shown in the diagram. The picture does not establish that Java keeps literal source-variable symbol-table objects in that arrangement, nor that string literals are outside Java’s object-memory model.

**Classification correction.** M01 p.46 distinguishes primitive types from reference types such as `String` and arrays, but incorrectly places the floating-point branch under an integral-value branch. `float` and `double` are floating-point types, not integral types. The diagram remains the source figure; this is a note-side correction, not a claim that the instructor corrected the figure during the lecture. [M01 p.46]

### Primitive arguments are copied into separate parameter variables

[[concepts/pass-by-value|Pass-by-value]] means that evaluating a method call supplies values that are copied into the method’s parameter variables. Java uses this rule for every argument, including reference values. The primitive swap example provides the first clear case. [M01 p.37] [M01 p.38]

Before tracing it, the instructor revisits:

```java
public static void main(String[] args)
```

`public` is an access modifier; `static` associates the method with the class; `void` declares no return value; `main` is the method name; and `String[] args` declares an array-of-strings parameter. In the example, this method calls a static `swap` without needing a receiver object. [STT 40:13] [M01 p.37]

The intended primitive swap body on M01 pp.37–39 is:

```java
static void swap(int a, int b) {
    int temp;
    temp = a;
    a = b;
    b = temp;
}
```

Suppose the caller holds `x = 2` and `y = 3` and evaluates `swap(x, y)`. The state changes are:

| Point in execution | Caller `x` | Caller `y` | Parameter `a` | Parameter `b` | Local `temp` |
|---|---:|---:|---:|---:|---:|
| Method entry | 2 | 3 | 2 | 3 | Not assigned |
| After `temp = a` | 2 | 3 | 2 | 3 | 2 |
| After `a = b` | 2 | 3 | 3 | 3 | 2 |
| After `b = temp` | 2 | 3 | 3 | 2 | 2 |

The callee’s parameters exchange values, but the caller’s variables remain `2` and `3`. Using the same parameter names as the caller’s variable names would not merge their identities. [STT 41:05] [STT 41:53] [STT 42:47] [M01 p.39]

The figure on M01 p.39 displays separate caller and callee regions. Its useful information is that the assignments target the callee’s variables while the caller’s variables remain unchanged. A function returning does not copy arbitrary parameter assignments back into the variables used as arguments.

**Printed-code discrepancy.** M01 pp.49–50 repeat the primitive example with `a = temp` as the final assignment, instead of `b = temp`. That printed sequence restores local `a` to `2` and leaves local `b` at `3`. The final diagram on p.50 nevertheless shows the locally swapped state `a = 3`, `b = 2`, so its code and picture disagree. Both versions leave the caller’s variables unchanged, but they do not produce the same local state. [M01 p.49] [M01 p.50]

### Copied references allow shared-object mutation

The lecture next places each integer inside an `IntHolder`:

```java
class IntHolder {
    int value;

    IntHolder(int value) {
        this.value = value;
    }
}
```

The holder is a small object containing an integer field. Its constructor also reuses the distinction between a parameter named `value` and the field `this.value`. [STT 43:42] [M01 p.40]

The corresponding swap changes fields:

```java
static void swap(IntHolder a, IntHolder b) {
    int temp = a.value;
    a.value = b.value;
    b.value = temp;
}
```

If the caller creates two holders containing `2` and `3`, the method receives copies of references to those same holders. Consequently:

1. `temp` receives the primitive value `2`.
2. `a.value = b.value` changes the first shared holder’s field to `3`.
3. `b.value = temp` changes the second shared holder’s field to `2`.

The caller then observes `3` and `2` in the holders. The assignments reach shared objects; they do not replace the caller’s reference variables. [STT 44:40] [STT 47:25] [M01 p.41] [M01 p.43]

M01 p.43 is useful when read beside p.39. In the primitive example, the changed values belong to separate callee parameters. In the holder example, the field changes occur in objects to which both caller and callee have access. The diagrams simplify storage, but the distinction between a parameter and an object field is decisive.

**Terminology correction.** The STT and slide headings call the holder case call-by-reference. M01 p.42 itself also notes the interpretation in which address values are passed by value. The precise Java account is that **reference values are copied into new parameter variables**. This explains both shared-field mutation and the failure of parameter reassignment to change caller variables. It does not require two different Java argument-passing mechanisms. [STT 45:28] [M01 p.42]

The instructor also motivates references by considering the cost of copying a potentially large object, including many fields or arrays. Passing a reference does not copy that entire object. However, avoiding an object copy is not equivalent to passing the caller’s variable itself by reference. [STT 45:28]

### Garbage collection concerns reachability, not immediate deletion

[[concepts/garbage-collection|Garbage collection]] is Java’s automatic mechanism for reclaiming storage occupied by objects that are no longer reachable for use. Object creation obtains the necessary storage; the programmer does not normally pair each `new` with an explicit deallocation operation. [STT 48:25] [M01 p.44]

The lecture’s additional example creates an `IntHolder` inside the swap method:

```java
IntHolder c = new IntHolder(4);
```

If this object remains accessible only through that local reference, and no reference to it escapes elsewhere, the object can become unreachable after the method finishes. It can then be eligible for garbage collection. Merely being created inside a method is insufficient: if the object were retained through another reachable reference, method return would not make it unreachable. [STT 48:25] [STT 49:18]

The important condition is the loss of reachability, not the name of the variable, its numerical value, or a guaranteed collection instant. Eligibility for collection does not mean that the collector must reclaim the object immediately when the method returns.

The lecture contrasts Java’s automatic management with explicit allocation and freeing in C. This comparison explains a programming responsibility; it is not a claim that every C variable has manually managed heap storage. The instructor’s accompanying claim that C++ is always faster than Java, by at least 10 or 20 times, has no benchmark evidence in these sources and remains **검증 필요**. It should not become a general performance law or a numerical expectation. [STT 48:25] [STT 50:04] [M01 p.44]

An answer should connect automatic reclamation to reachability, then distinguish eligibility from exact timing. “It is deleted when the function returns” misses the reference condition and overstates the timing guarantee. ### Swapping `String` parameters changes only local references

The plain `String` example tests whether the same argument-passing rule is being applied consistently. Consider this independently formatted version of the assignment sequence on M01 pp.52–53:

### Null validation depends on short-circuit evaluation

The `Person.setName` example combines reference checking, content checking, shadowing, and controlled assignment:

```java
class Person {
    private String name;

    public void setName(String name) {
        if (name == null || name.equals("")) {
            System.out.println("Name cannot be null or empty");
        } else {
            this.name = name;
        }
    }
}
```

[M02 p.21]

`null` means that a reference does not refer to an object. Comparing `name == null` checks this reference condition. In contrast, `name.equals("")` invokes a method on the referenced string to compare its contents with an empty string. Invoking an instance method through a null receiver causes a `NullPointerException`. [STT 01:26:50] [STT 01:27:49]

The order is safe because [[concepts/short-circuit-evaluation|short-circuit evaluation]] of `||` skips the right operand when the left operand is already `true`:

| Input | `name == null` | Evaluate `name.equals("")`? | Result |
|---|---|---|---|
| `null` | `true` | No | Reject; do not assign the field |
| `""` | `false` | Yes; result is `true` | Reject; do not assign the field |
| `"Aster"` | `false` | Yes; result is `false` | Assign the field |

The final input is an independently chosen example. The condition and branch behavior come from M02 p.21. [STT 01:28:49]

Reversing the operands would lose this protection: `name.equals("")` would be attempted before the null check. Replacing `||` with non-short-circuit Boolean `|` would also evaluate the unsafe method call for a null input. The first condition protects the second through evaluation order, not merely by appearing somewhere in the expression.

Several boundaries matter:

- A null receiver is different from passing null as a method argument; the immediate failure discussed here is invoking the method when there is no receiver object.
- The lecture’s address-zero analogy is a simplified model, not a guarantee that a Java null reference is a physical address zero.
- Reference fields receive default `null`; ordinary unassigned local variables are not automatically usable.
- Rejecting an input leaves the field unchanged. If no valid assignment has yet occurred, that unchanged field may still be `null`.
- The printed condition rejects null and the empty string. It does not reject whitespace-only strings or implement a complete naming policy.

[STT 01:26:50] [STT 01:27:49] [M02 p.21]

The setter’s `void` return type is this example’s design choice. Unlike the revised `sell`, it reports rejection by printing rather than by returning a success flag; “setter” does not impose a special Java return-type rule.

## Key Takeaways

- A class supplies a reusable definition; an object has particular state. Sharing a class definition does not mean sharing instance fields.
- Constructors establish initial state. `this` selects the current object, especially when a parameter shadows a field.
- A static member belongs to the class. An instance operation still needs a receiver, including when invoked from a static method.
- Java passes every argument by value. A copied reference can reach a shared object, but assigning a new value to a parameter does not assign to the caller’s variable.
- Trace assignment targets precisely: a primitive parameter, a reference parameter, and a field of a shared object produce different effects.
- Garbage-collection eligibility depends on reachability. Method return does not guarantee immediate reclamation.
- Encapsulation separates permitted observation and modification from implementation details. Private fields, getters, setters, and validation are tools for implementing that policy.
- Abstraction, code reuse, and behavior variation motivate encapsulation, inheritance, and polymorphism. Java/OOP precedes C++ because Java automates responsibilities handled more directly in C++. [M01 p.58] [STT 01:07:10]
- The printed examples contain consequential defects and simplifications. Preserve the distinction between source code, intended behavior, factual corrections, and explicitly authored adaptations.
