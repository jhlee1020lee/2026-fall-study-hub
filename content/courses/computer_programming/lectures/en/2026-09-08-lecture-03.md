This lecture connects calculations and stored values to arrays, conditional execution, repeated work, and reusable methods.  
The central reading task is to distinguish an expression’s value, changes to program state, the path execution follows, and the difference between returning and printing a result.

## Lecture Content and Explanation

### Operators and operands: identifying the work an expression performs

[[concepts/java-operators|Operators]] specify operations on variables and values. An **operand** is an input to an operation. In `x + 10`, `x` and `10` are the operands, while `+` specifies addition. During evaluation, Java uses the value stored in `x`; the variable’s name is not itself the quantity being added. The diagram on M01 p.51 labels these three parts separately. [STT 02:41] [M01 p.51]

The lecture distinguishes Arithmetic operators, Assignment operators, Comparison operators, Logical operators, and Bitwise operators. These categories describe the work performed. By contrast, **unary** describes the number of operands: a unary operator takes one operand. Consequently, `++` can be both a Unary operator and an Arithmetic operator. These classifications answer different questions and are not mutually exclusive. [STT 03:35] [M01 p.52] [M01 p.53]

The Arithmetic operators table also distinguishes operations that produce a calculated value from operations that update a variable. [M01 p.54]

| Operator | Source terminology | Operation | Source example |
|---|---|---|---|
| `+` | Addition | Add two values. | `x + y` |
| `-` | Subtraction | Subtract the right operand from the left. | `x - y` |
| `*` | Multiplication | Multiply two values. | `x * y` |
| `/` | Division | Divide the left operand by the right. | `x / y` |
| `%` | Modulus | Obtain the division remainder. | `x % y` |
| `++` | Increment | Increase a variable’s value by one. | `++x` |
| `--` | Decrement | Decrease a variable’s value by one. | `--x` |

For example, `1 + 2` produces `3`. It does not, by itself, store that result in a named variable. An assignment is needed to retain the result there. Conversely, increment changes the value already stored in its operand variable. Distinguishing **an expression’s result** from **a change to stored state** is essential when tracing the later examples. [STT 03:35] [M01 p.53] [M01 p.59]

### Shift and Bitwise operators: working with a number’s representation

A **shift** moves the positions of bits in a number’s representation. In `2 << 3`, the left operand is the value whose bits are shifted, and the right operand specifies three positions to the left. This is neither addition by three nor repeated addition of two. [STT 04:33] [M01 p.53]

Writing the small positive value in binary makes the operation visible:

```text
Binary representation of 2:       10
After shifting left three places: 10000
Decimal result:                   16
```

Thus, the source example evaluates to `16`. Moving a bit left increases the place value associated with that bit. The instructor mentioned integer and floating-point representations and byte ordering as background, but did not teach those representation systems in detail during this lecture. This small positive example should therefore not be extended into an unrestricted account of negative values, overflow, or arbitrary shift distances. [STT 04:33] [M01 p.53]

**Bitwise AND** applies AND separately to corresponding bits. In the slide’s `0b1 & 0b0`, the two bits are not both `1`, so the result is `0`. In contrast, `true && false` combines two `boolean` values and produces `false`. The instructor immediately corrected an initial verbal slip about this Boolean result. [STT 05:32] [M01 p.53]

The source tables also contain right shift, Bitwise inclusive OR, and Bitwise exclusive OR. The following are **newly authored explanatory illustrations** of those entries, rather than numerical examples recovered from the lecture. [M01 p.60] [M01 p.74]

| Expression | Bit-level interpretation for these inputs | Result |
|---|---|---|
| `13 >> 2` | Shift the positive binary value `1101` right twice, leaving `11`. | `3` |
| `6 \| 5` | Combine `0110` and `0101`, retaining a `1` wherever either input has one. | `0111`, or `7` |
| `6 ^ 5` | Retain a `1` only where the corresponding input bits differ. | `0011`, or `3` |

The distinction between `|` and `^` appears where both input bits are `1`: inclusive OR retains `1`, whereas exclusive OR produces `0`. These examples use small nonnegative integers. The tables support reading these operators, but do not establish that the lecture developed all their detailed rules. [M01 p.74]

### Division and Modulus: determine the operand types first

Division in Java must be interpreted using the operand types. In `5 / 2`, both operands are `int`, so the expression produces the integer result `2`. The mathematical quotient `2.5` does not determine the type or value of this Java expression. [STT 07:28] [STT 08:27] [M01 p.55]

The mixed-type example behaves differently:

```java
int x = 15;
double y = 3.0;
double result = x / y; // 5.0
```

For this operation, the integer value participates as a `double`, so the calculation uses `15.0` and `3.0` and produces `5.0`. The declaration of `x` remains `int`; the variable does not acquire a new declared type. [STT 08:27] [STT 09:18] [M01 p.55]

This connects to [[concepts/java-type-casting|Type casting]]. The instructor initially described operators as preserving their input types, then explained automatic conversion for mixed operands. The first statement must be read in that qualified context, rather than as a universal rule. The lecture also noted that languages differ in their support for automatic conversion. The complete widening and narrowing conversion chains were prior material, not a new topic developed here. [STT 09:18] [STT 34:00] [M01 p.35]

**Modulus** obtains the remainder rather than the quotient:

```java
int x = 5;
int y = 2;
int result = x % y; // 1
```

For these positive inputs,

$$
5 = 2 \times 2 + 1.
$$

Accordingly, `5 / 2` produces the quotient `2`, while `5 % 2` produces the remainder `1`. The operands are identical, but the requested information differs. [M01 p.55] [M01 p.56]

Integer division by zero, such as the slide’s `5 / 0`, cannot produce a normal division result. Later, the lecture places a denominator check before division so that an unsafe operation is not evaluated. This discussion concerns integer division; it should not be generalized to every numeric type’s behavior at zero. [STT 08:27] [M01 p.55] [M01 p.69]

### Increment and Decrement: expression values and final variable values

Increment and Decrement change a variable by one. Their **prefix** and **postfix** forms differ in the value supplied to the surrounding expression. [M01 p.54] [M01 p.57]

The lecture compares two independent examples with the same starting values:

```java
int x1 = 1, y1 = 1;
int prefixResult = x1 + ++y1;

int x2 = 1, y2 = 1;
int postfixResult = x2 + y2++;
```

In the prefix expression, `++y1` changes `y1` to `2` and supplies that updated value. The addition therefore produces `1 + 2`, or `3`.

In the postfix expression, `y2++` supplies the previous value `1`, while updating `y2` to `2`. The addition uses the supplied value and produces `1 + 1`, or `2`. [STT 09:18] [STT 10:13]

| Form | Value supplied to the addition | Addition result | Variable after the statement |
|---|---|---|---|
| Prefix `++y1` | Updated value `2` | `3` | `y1 == 2` |
| Postfix `y2++` | Previous value `1` | `2` | `y2 == 2` |

M01 p.58 confirms the different printed results: `Prefix result is: 3` and `Postfix result is: 2`. Looking only at the final values of `y1` and `y2` would miss the point of the example. Both finish at `2`, but they contributed different values to their expressions. [STT 11:10] [M01 p.58]

Postfix is best understood as **supplying the old value**, rather than as a blanket rule that the variable changes only after the entire surrounding statement has finished. Decrement follows the same distinction while subtracting one. [M01 p.54] [M01 p.57]

### Assignment: declaration, initialization, and subsequent updates

A **declaration** establishes a variable’s name and type. **Initialization** supplies its starting value. The statement `int x = 10;` performs both. An **assignment** subsequently stores a value in the variable. [STT 11:10] [STT 12:10] [M01 p.27] [M01 p.59]

```java
int x = 10;
x += 5; // x becomes 15
```

The second statement reads the current value of `x`, adds `5`, and stores the result back in `x`. The symbol `=` expresses assignment, not a test of equality. [M01 p.59]

The Assignment operators table combines an operation with assignment back to the left-hand variable. Each row below is an independent example, not another step in one continuous program. [M01 p.60]

| Operator | Source example | Expanded reading for the simple integer examples |
|---|---|---|
| `=` | `x = 5` | `x = 5` |
| `+=` | `x += 3` | `x = x + 3` |
| `-=` | `x -= 3` | `x = x - 3` |
| `*=` | `x *= 3` | `x = x * 3` |
| `/=` | `x /= 3` | `x = x / 3` |
| `%=` | `x %= 3` | `x = x % 3` |
| `&=` | `x &= 3` | `x = x & 3` |
| `\|=` | `x \|= 3` | `x = x \| 3` |
| `^=` | `x ^= 3` | `x = x ^ 3` |
| `>>=` | `x >>= 3` | `x = x >> 3` |
| `<<=` | `x <<= 3` | `x = x << 3` |

The left-hand variable’s previous value remains the first operand of the operation. Thus, `x <<= 3` follows the order of `x = x << 3`, not `x = 3 << x`. Operand order is especially consequential for subtraction, division, and shifts. [STT 14:06] [M01 p.60]

The instructor used the word unary while describing these abbreviated updates. That wording should be distinguished from the technical classification by operand count: `x += 3` involves both an update target and another operand. The explanation concerns combining an operation with reassignment. Likewise, the table is not an unrestricted textual substitution rule for every type or complicated left-hand expression. [STT 13:08] [M01 p.60]

**Correctness clarification from the fixed baseline.** The instructor recommended explicit initialization, but also suggested that an uninitialized value would be determined by the JVM or compiler. Java local variables must instead satisfy definite assignment before they are read. This applies to both primitive and reference local variables. An unreadied local variable does not simply produce an arbitrary value. [STT 12:10] [M01 p.30]

The following is a **newly authored explanatory illustration** of that distinction:

```java
int x;
// Reading x here would be a compile-time error.

x = 10;
System.out.println(x); // 10
```

This differs from the default initialization of fields and newly created array components. Explicit initialization remains useful for communicating intended state, but the instructor’s original wording must not be presented as the corrected Java rule.

### String and Reference: identifying the stored and compared objects

The lecture’s distinction between Primitive data types and Reference types explains why apparently similar comparisons can behave differently. In its storage model, `int x = 3` stores the primitive value `3`. A String variable instead stores a **reference** to a separately existing object. The instructor described that reference using a memory-address model and motivated it with the possibility of a very long String. [STT 15:04] [M01 p.43] [M01 p.49]

The classification diagram on M01 p.31 places numeric primitive types on one side and String and Array on the non-primitive side. For this lecture, the useful distinction is between storing a primitive value and referring to another object. The diagram is not a reason to introduce an exhaustive account of type sizes or object layout. [M01 p.31] [M01 p.49]

For [[concepts/java-strings|String]], two different comparisons are possible:

- Do the references identify the same object?
- Do the String objects contain the same characters?

The first comparison slide deliberately separates these questions. [M01 p.61]

```java
String appleObjOne = new String("Apple");
String appleObjTwo = new String("Apple");

System.out.println(appleObjOne == appleObjTwo);      // false
System.out.println(appleObjOne.equals(appleObjTwo)); // true
```

Two executions of `new String("Apple")` create distinct String objects with equal contents. Here, `==` compares reference identity and returns `false`. String’s `equals()` compares contents and returns `true`. [STT 15:58] [STT 16:54] [STT 17:48]

**Reading the heap diagram.** M01 p.61 contains two separate boxes labeled `"Apple"`. The arrows from the two variables end at different boxes. Those distinct destinations explain the false identity comparison. Comparing the characters inside the boxes explains the true content comparison. Equal text does not make two separately created objects identical. [M01 p.61]

The instructor introduced `equals()` as a function defined for String. At this point, its relevant behavior is to return a `boolean` result from a content comparison. The broader account of classes, members, and methods was deferred; detailed method declaration and return behavior appear later in this lecture. [STT 16:54] [M02 p.48]

### String literals and immutability: shared objects and replaceable references

A **String literal** is a directly written expression such as `"Apple"`. The next source example uses the same literal for two variables. [M01 p.47] [M01 p.62]

```java
String appleOne = "Apple";
String appleTwo = "Apple";

System.out.println(appleOne == appleTwo);      // true
System.out.println(appleOne.equals(appleTwo)); // true
```

In this example, the two variables refer to the same String object, so both comparisons return `true`. The immediate reason that `==` succeeds is shared identity, not merely equal contents. The earlier `new String` example shows why this observation does not justify using `==` as a general String-content test. [STT 18:44] [STT 19:41]

**Reading the String Pool diagrams.** M01 p.47 contrasts shared literal references with separately created objects. M01 p.62 places the **String Pool inside Heap Memory** and shows both literal references pointing into the same box. The instructor’s description of a different memory area should not be interpreted as placing the String Pool outside the heap. [M01 p.47] [M01 p.62]

A String is **immutable**: its existing character contents are not changed into another String’s contents. Nevertheless, a variable holding a String reference can be assigned a different reference. [M01 p.48]

```java
String appleOne = "Apple";
String appleTwo = "Apple";

appleTwo = "Pear";
```

The immutability diagram keeps `appleOne` pointing to `"Apple"` and redirects `appleTwo` to `"Pear"`. Consequently, reading the variables afterward gives `"Apple"` and `"Pear"` respectively. The original `"Apple"` object has not had its characters rewritten. [M01 p.48]

The misconception is to equate an immutable object with a variable that cannot be reassigned. **Immutable String contents and replaceable String references are compatible.** This distinction will also explain updates to elements of a String array. [M01 p.48] [M02 p.8]

### Comparison and Logical operators: constructing Boolean values

Comparison operators express equality, inequality, and ordering as `boolean` results. Both the spoken example `2 > 1` and the slide example `1 < 2` produce `true`. The instructor presented String comparison first because the meaning of equality depends on what is being compared: a primitive value or a reference. [STT 05:32] [STT 19:41] [M01 p.53] [M01 p.63]

| Source terminology | Operator | Question |
|---|---|---|
| Equal to | `==` | Are the compared values equal? |
| Not equal | `!=` | Are the compared values different? |
| Greater than | `>` | Is the left operand larger? |
| Less than | `<` | Is the left operand smaller? |
| Greater than or equal to | `>=` | Is the left operand larger or equal? |
| Less than or equal to | `<=` | Is the left operand smaller or equal? |

In `>=` and `<=`, the equals sign comes second. The slide explicitly rejects `=>`, `=<`, and `<>` as spellings of these comparisons. Assignment `=` must also be distinguished from equality comparison `==`. [M01 p.64]

Logical operators combine or reverse Boolean conditions. [M01 p.65]

| Source terminology | Operator | Result |
|---|---|---|
| Logical AND | `&&` | True when both conditions are true. |
| Logical OR | `\|\|` | True when at least one condition is true. |
| Logical NOT | `!` | Reverse true and false. |

The source example `x < 5 && x < 10` asks whether both comparisons hold. The OR example `x < 5 || x < 4` asks whether at least one holds. In `!(x < 5 && x < 10)`, the parentheses show that NOT applies to the combined result. [M01 p.65]

For String content inequality, use the Boolean result of `equals()`:

```java
!a.equals(b)
```

This reverses the content-equality result. By contrast, `a != b` asks about reference inequality. These are different questions. As in the lecture examples, assume here that the variables refer to actual String objects. [STT 20:44] [STT 21:36]

### Short Circuit Evaluation: distinguish skipped expressions from skipped bodies

[[concepts/java-short-circuit-evaluation|Short Circuit Evaluation]], also called minimal evaluation in the slides, omits the right-hand expression when the left-hand result already determines the combined result. The instructor framed this as avoiding unnecessary computation. [STT 24:17] [M01 p.66]

The two truth tables explain why that omission is possible. [M01 p.67] [M01 p.68]

| Left value | Right value | AND result | OR result |
|---|---|---|---|
| `true` | `true` | `true` | `true` |
| `true` | `false` | `false` | `true` |
| `false` | `true` | `false` | `true` |
| `false` | `false` | `false` | `false` |

In the AND table, both rows with a false left value have a false result. Therefore, `&&` does not evaluate its right operand when the left operand is false. In the OR table, both rows with a true left value have a true result, so `||` does not evaluate its right operand when the left operand is true. [STT 22:27] [STT 23:27] [STT 24:17]

The right-hand column in a truth table describes possible logical combinations. It does not imply that a program evaluates the right-hand expression on every execution.

The denominator example makes that distinction operational:

```java
int denominator = 0;
int num = 100;

if (denominator != 0 && num / denominator == 1) {
    // Executed only when both conditions are true.
}
```

The first comparison is false. Java therefore does not evaluate `num / denominator == 1`, and this execution does not attempt integer division by zero. The complete condition is also false, so the `if` body is skipped. [STT 25:11] [STT 26:11] [M01 p.69]

The check must appear before the division. Reversing the two expressions would attempt the unsafe operation before the denominator check could protect it. Condition order can therefore affect whether an operation is evaluated at all. [M01 p.69]

The `skipLongCode` slide illustrates a different outcome. With a true flag on the left of `||`, the complex condition on the right is omitted, but the overall condition is true and the body executes. The instructor explicitly corrected the earlier suggestion that this arrangement would skip the body. [STT 26:11] [STT 27:10] [M01 p.70]

| Left value and operator | Complex right-hand condition | Combined result | `if` body |
|---|---|---|---|
| `true` with `\|\|` | Not evaluated | `true` | Executes |
| `false` with `&&` | Not evaluated | `false` | Does not execute |

The second row is the alternative the instructor proposed for suppressing the body during debugging or testing. A variable name containing `skip` does not determine behavior; its value and the operator do. [STT 27:10]

**검증 필요 — unresolved wording.** At 21:36, the instructor made a low-importance qualification, but its referent is ambiguous between the preceding String-negation discussion and the introduction of Short Circuit Evaluation. It should not be converted into a definite ranking or examination exclusion. The mechanisms, truth tables, guard, and control-flag correction remain part of the taught content. [STT 21:36]

### Operator Associativity: following intermediate results

**Operator Associativity** describes grouping when operators at the same level are chained. For repeated String concatenation with `+`, follow the intermediate results from the left. [M01 p.71]

```java
System.out.println("The answer is: " + 2 + 3 + "!");
// The answer is: 23!

System.out.println(2 + 3 + " is the answer!");
// 5 is the answer!
```

The first expression develops as follows:

```text
"The answer is: " + 2
→ "The answer is: 2"

"The answer is: 2" + 3
→ "The answer is: 23"

"The answer is: 23" + "!"
→ "The answer is: 23!"
```

Because the first operation already involves a String, `2` and `3` are appended separately in their textual forms. The second expression first computes the numeric sum `2 + 3`, producing `5`, and only then concatenates with a String. The intermediate type determines which operation `+` performs. [STT 28:06] [M01 p.71]

The first output includes the colon present in the actual code. The slide’s output comment omits it; that comment should not override the expression being executed. [M01 p.71]

Earlier material provides the supporting example `1 + "2"`, which produces `"12"`, not `3`. Concatenation also adds no automatic spaces. The following is a **newly authored explanatory illustration**: [M01 p.45] [M01 p.46]

```java
System.out.println("Java" + "Basics");       // JavaBasics
System.out.println("Java" + " " + "Basics"); // Java Basics
```

Although the earlier slides also contain `concat()`, its detailed use was not newly taught in this session. Similarly, the instructor’s analogy between number-to-String conversion and Widening Casting should not be treated as a formal definition of primitive numeric conversion. [STT 28:06] [M01 p.35] [M01 p.46]

Assignment associates in the other direction:

```java
int x = 1;
int y = 2;
int z = 3;

x = y = z;
```

Read this as `x = (y = z)`. The inner assignment stores `3` in `y` and itself produces the assigned value `3`. That result becomes the value assigned to `x`. All three variables finish at `3`. [STT 29:09] [STT 30:09] [M01 p.72]

The example establishes both right-associative assignment and the fact that an assignment expression has a value. The instructor nevertheless discouraged compact constructions whose behavior is not readily apparent to the reader. Understanding a legal expression and recommending it as a writing style are separate judgments. [STT 30:09]

### Operator Precedence: grouping and evaluation order are different

**Operator Precedence** determines how different operations are grouped within an expression. The source example combines increment, multiplication, and addition. [M01 p.73]

```java
int x = 5;
int y = 10;
int z = ++x + y * 3;
```

Its grouping is:

```java
(++x) + (y * 3)
```

The fixed baseline’s correctness clarification distinguishes this grouping from Java’s left-to-right operand evaluation:

1. Evaluate the left operand `++x`: update `x` from `5` to `6` and obtain the value `6`.
2. Evaluate the right operand `y * 3`: obtain `30` while leaving `y` at `10`.
3. Add the two results and store `36` in `z`.

The final state is `x == 6`, `y == 10`, and `z == 36`. The instructor also corrected the suggestion that `y` itself changes. The slide prints `z is: 36`. [STT 31:04] [STT 32:03] [M01 p.73]

Precedence answers **how the expression is grouped**. Operand evaluation order answers **which operand is evaluated first**. Treating precedence as a rule that the highest-ranking symbol anywhere in an expression must execute first can lead to incorrect traces.

The following preserves the distinct Java-applicable levels shown in the source table. Higher rows bind more tightly. This is a qualified reading aid for that table, not a complete Java operator reference. [M01 p.74]

| Level | Relationship to retain from the source |
|---|---|
| 1 | Grouping `()`, array access `[]`, member access `.` |
| 2 | Unary `!`, `~`, `-`, `+`, type cast, prefix `++x`, `--x` |
| 3 | Multiplicative `*`, `/`, `%` |
| 4 | Additive `+`, `-` |
| 5 | Shift `<<`, `>>` |
| 6 | Relational `<`, `<=`, `>`, `>=` |
| 7 | Equality `==`, `!=` |
| 8 | Bitwise AND `&` |
| 9 | Bitwise exclusive OR `^` |
| 10 | Bitwise inclusive OR `\|` |
| 11 | Logical AND `&&` |
| 12 | Logical OR `\|\|` |
| 13 | Conditional expression `?:` |
| 14 | Assignment `=`, `+=`, `-=`, `*=`, `/=`, `%=`, `&=`, `\|=`, `^=`, `<<=`, `>>=` |

Relational and equality comparisons occupy different levels. Bitwise AND, exclusive OR, and inclusive OR are also separate, as are Logical AND and Logical OR. Combining each family into a single precedence level would lose information from the table. [M01 p.74]

**Source limitation.** The original table includes C/C++ entries. Its `sizeof`, pointer meanings of unary `*` and `&`, and comma operator must not be imported as Java syntax. Multiplication `*` and Bitwise AND `&` retain their separate meanings. Java also has distinct uses for `->` and `::`, but neither those uses nor the table’s C/C++ meanings were taught here. [M01 p.74]

The instructor qualified the increment discussion as a recollection requiring checking and then said increment could not be found in the table. The original unary row does contain `++x` and `--x`. That difference between uncertain speech and source content must remain visible. [STT 31:04] [STT 32:03] [STT 33:02]

### Arrays: grouping values of one element type

[[concepts/java-arrays|Arrays]] collect values or objects of the same element type so that multiple items can be handled through one variable. They provide a basic data structure for tasks that would otherwise require many separate variables. The instructor also identified String as a data structure and anticipated using or constructing others later. [STT 34:56] [M02 p.3]

The source presents array elements using a contiguous-storage model and connects that model to efficient access. An **index** identifies an element’s position. For an array of length `n`, valid indices run from `0` through `n - 1`. A length-four array therefore has positions `0`, `1`, `2`, and `3`; its length is not a valid final index. [STT 35:46] [M02 p.3]

```java
int[] arr = new int[4];
```

Here, `int[]` declares an array type, `new int[4]` creates an array with four integer components, and `arr` stores its reference. Specifying the size determines how many components the new array needs. Calling arrays fundamental does not classify them as Java primitive types. [STT 36:46] [STT 37:38] [M02 p.4]

For a String array, the components hold references. The storage model therefore does not imply that all the characters of all referenced Strings occupy one contiguous block. The instructor emphasized understanding such internal distinctions even when the surface syntax looks similar. [STT 35:46] [STT 41:21]

**Correctness clarification from the fixed baseline.** The instructor said the contents of an array created this way could not be guaranteed. Newly created Java array components instead receive default values:

| Component type | Default component value |
|---|---|
| `int` | `0` |
| `double` | `0.0` |
| `boolean` | `false` |
| `String` | `null` |

Thus, all four components of `new int[4]` initially contain `0`. Separately, declaring a local `int[] arr;` without assigning it does not provide a usable array reference. The local must be assigned before it is read or indexed. **Assignment of the local reference and initialization of the created array’s components are different issues.** This clarification preserves the instructor’s recommendation to make intended starting values explicit while correcting the language-rule claim. [STT 37:38] [M02 p.4]

### Array Initialization: letting the element list determine the length

### While and Do-While: when is the first condition evaluated?

[[concepts/java-loops|Loops]] repeat a block of work according to a condition. A While Loop tests its condition before entering the body. If the first test is false, the body executes zero times. Otherwise, execution alternates between the body and another condition test until the condition becomes false. [STT 65:53] [STT 66:50] [M02 p.30]

```java
while (condition) {
    // Repeated work.
}
```

A Do-While Loop enters the body before its first condition test:

```java
do {
    // Repeated work.
} while (condition);
```

It therefore executes the body at least once before deciding whether to repeat. The final semicolon is required. [STT 66:50] [M02 p.31]

| Form | Tests the condition before the first body execution? | Minimum body executions |
|---|---|---|
| While | Yes | `0` |
| Do-While | No | `1` |

The distinction concerns the order of testing and doing the work. Merely using the same Boolean expression in both forms does not guarantee the same behavior.

### For and For-Each: expose the information needed for repetition

### `break` and `continue`: different scopes of interruption

A loop’s `break` ends the targeted loop, whereas `continue` skips the remainder of the current iteration. In the source example, the `if` is inside a For Loop, so the break exits that loop; the `if` itself is not a loop. [STT 74:10] [STT 75:10] [M02 p.37]

| `continue;` | `0, 1, 2, 4` | Skip the current print, perform the update, and test again. |

### Nested Loop: trace output quantity and line placement separately

A **Nested Loop** places one loop inside another. In the star example, the outer loop determines the row, and the inner loop determines how many stars appear on that row. [M02 p.39]

```java

}
```

On the first outer iteration, `i == 5`. The inner loop visits `j == 0, 1, 2, 3, 4`, printing five stars. Because `print("*")` does not end the line, those stars remain together. The `println()` after the inner loop then ends that row. [STT 79:11]

***
**
*

| `4` | `0` through `3` | `4` |
| `3` | `0` through `2` | `3` |

### Finding Max Number: maintain the largest value seen so far

### Fencepost: distinguish characters, Strings, and the final delimiter

The **Fencepost** example prints commas between characters while avoiding a comma after the final character. Its type distinction is essential: Java’s `char[]` is different from String. ### Functions: define meaningful work once and call it again

[[concepts/java-methods|Functions]] are blocks of code that execute when called; Java calls them **methods**. Grouping a meaningful operation into a method allows other code to request that operation without reproducing its implementation. [STT 87:34] [STT 91:23] [M02 p.48]

**Reading the function illustration.** M02 p.43 shows apples entering a box labeled `function h` and cut apples leaving it. The illustration separates a specified input from a defined transformation. It does not mean that every method must both accept parameters and return a value; the later examples explicitly show all four combinations. [M02 p.43] [M02 p.50]

**Modularity** divides code into meaningful units that are easier to manage and test. **Reusability** allows a unit defined once to be called in multiple places. The instructor used maximum finding as an example: once that operation is a function, its loop, comparison, and update need not be rewritten each time a maximum is required. [STT 88:34] [M02 p.48]

Meaning matters as much as size. The instructor emphasized names such as `average`, `sum`, `divide`, and `concatenate` because they communicate the operation. Dividing arbitrary statements into arbitrarily named functions does not by itself achieve that purpose. [STT 92:23] [STT 95:20]

### `average`: extract repeated computation and separate return from output

The source supplies three arrays, each containing four `double` values: [M02 p.44]

```java
double[] arr1 = {1.2, 3.4, 2.5, 6.4};
double[] arr2 = {5.2, 6.7, 8.2, 3.6};
double[] arr3 = {0.2, 3.4, 4.5, 4.2};
```

The declarations are separated here for readability. The original combines variables of the same type in one declaration, which is legal, although the instructor expressed a preference against that compressed style. [STT 88:34] [M02 p.44]

Without a function, each average requires the same pattern: initialize a sum to zero, add every element, and divide by the array’s length. One such block is: [M02 p.45]

```java
double sum = 0;

for (double f : arr1) {
    sum += f;
}

System.out.println(sum / arr1.length);
```

Repeating this for `arr2` and `arr3` requires resetting the sum before each calculation. Otherwise, a previous array’s total contaminates the next result. The task is to compute an average, not merely a sum; division by the number of elements is part of the repeated operation. [STT 89:33] [M02 p.45]

The shared calculation becomes:

```java
static double average(double[] arr) {
    double sum = 0;

    for (double f : arr) {
        sum += f;
    }

    return sum / arr.length;
}
```

The method accepts a `double[]` and returns a `double`. Its local `sum` starts at zero on each call, so different calls do not carry one array’s accumulated sum into another. The `static` keyword is retained from the source, but the instructor explicitly deferred its detailed meaning. [STT 90:30] [M02 p.46]

For a nonempty array of length $n$, the intended mathematical calculation is:

$$
\text{average}=\frac{\text{sum of the elements}}{n}.
$$

For `arr1`, the listed values sum mathematically to `13.5`; dividing by four gives `3.375`. This explains the computation performed by the code without asserting that every floating-point calculation reproduces exact decimal arithmetic. [M02 p.44] [M02 p.46]

The method itself contains no printing statement. It returns the result to its caller, which can then print it:

```java
System.out.println(average(arr1));
System.out.println(average(arr2));
System.out.println(average(arr3));
```

The three output requests remain visible, but the averaging implementation exists in one place. This is the lecture’s concrete example of readable reuse. [STT 90:30] [STT 91:23] [M02 p.47]

As a **newly authored explanatory illustration**, `{2.0, 4.0, 6.0}` produces a sum of `12.0` and an average of `4.0`. A caller can save that returned value for another calculation or pass it to `println`. Returning and printing remain separate actions. This example, like the source’s intended use, assumes a nonempty array. [M02 p.46]

### Function declaration order: source placement does not determine execution order

Within the same class, a method can call another method declared later in the source. The final code slide illustrates that relationship. [M02 p.53]

static int offset(int code, int[] lengths) {

    int position = code % 100;
