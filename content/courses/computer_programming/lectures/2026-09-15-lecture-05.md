객체의 공통 설계와 개별 상태를 구분하고, 생성·대입·메서드 호출에서 무엇이 바뀌는지 추적한다.  
이 판단을 바탕으로 내부 상태를 보호하면서 조회·변경·검증·접근 기록을 제공하는 설계를 연결한다.

## 강의 내용과 설명

### Object-Oriented Programming(객체 지향 프로그래밍): 상호작용하는 Object로 프로그램 이해하기

Object-Oriented Programming, 즉 OOP는 프로그램을 서로 관계를 맺고 상호작용하는 Object(객체)들의 집합으로 바라보는 방식이다. 명령문이 실행되는 순서를 아는 것에 더해, 프로그램에 어떤 대상들이 있으며 각 대상이 어떤 상태와 행동을 담당하는지 생각한다. 강의의 사람·집·자동차 그림에서는 세 대상뿐 아니라 사람이 집에 살고 자동차를 운전한다는 관계도 중요하다. 프로그램을 구성하는 대상과 대상 사이의 관계를 함께 표현하는 것이다. [M01 p.3] [STT 00:57]

Object가 반드시 손으로 만질 수 있는 물체일 필요는 없다. 자료에서는 자동차를 Physical entity(물리적 대상), 은행 계좌를 Conceptual entity(개념적 대상), Linked list(연결 리스트)를 Software entity(소프트웨어적 대상)의 예로 제시한다. 계좌는 잔액과 거래처럼 관리해야 할 상태와 행동이 있으므로 하나의 Object로 생각할 수 있다. Linked list는 소프트웨어 안에서 정의되는 대상이라는 예시이며, 이번 시간에 그 내부 구현까지 배웠다는 뜻은 아니다. [M01 p.4] [STT 01:48] [STT 02:39]

OOP의 동기는 커피 제조 예시에서 드러난다. Procedural style(절차적 방식)로 쓰면 원두 준비, 분쇄, 물 준비, 가열, 원두 투입, 혼합을 차례로 나열한다. 이 절차 자체가 틀린 것은 아니다. 다만 전체 프로그램이 길어질수록 모든 세부 단계를 같은 수준에서 읽고 관리하기 어려워진다. [M01 p.5] [STT 02:39]

Object-oriented style에서는 분쇄·가열·혼합을 수행할 수 있는 Coffee Machine을 먼저 생각한다. 사용자는 원두와 물을 준비해 기계에 넣고 기계가 제공하는 동작을 이용한다. 여기서 기계가 할 수 있는 일의 목록과 사용자가 커피를 만드는 실행 순서는 구분해야 한다. 분쇄·가열·혼합은 기계가 제공하는 능력이고, 재료 준비와 기계 사용은 그 능력을 활용하는 절차다. [M01 p.6] [STT 03:38] [STT 04:25]

이처럼 필요한 기능을 사용하기 쉬운 단위로 묶고 세부 단계를 감추는 것이 Abstraction(추상화)의 동기다. 내부 계산이 없어지는 것이 아니라, 사용자가 매번 이해하고 조작해야 하는 범위가 줄어든다. 강의도 OOP를 통해서만 가능한 계산이 생긴다고 설명하지 않는다. 같은 일을 수행하더라도 프로그램을 읽고 재사용하고 관리하는 구조가 달라진다는 점을 강조한다. [STT 22:24] [STT 01:05:10]

### Class(클래스), Attribute(속성), Method(메서드): 공통 설계와 개별 상태

Class는 Object를 만들기 위한 Blueprint(설계도) 또는 Template(틀)이다. 무엇을 저장하고 어떤 행동을 제공할지를 한 번 정의한 뒤, 그 정의에 따라 여러 Object를 만든다. 자료의 붕어빵 틀과 붕어빵 그림은 설계와 결과물을 구분하게 한다. 같은 틀로 여러 결과물을 만들 수 있지만, 틀 자체와 만들어진 결과물은 같은 대상이 아니다. [M01 p.7] [STT 05:22]

같은 페이지의 자동차 그림도 같은 방식으로 읽는다. 왼쪽의 `Car`는 공통 설계이고, 오른쪽 자동차들은 그 설계에 따라 만들어진 개별 Object다. 이 그림에서 자동차 브랜드 표시는 서로 다른 개체를 구별하기 위한 예다. 브랜드마다 별도의 상속 관계가 정의되어 있다는 그림으로 확대해서 읽지 않는다. [M01 p.7]

Class를 설명하는 두 요소가 Attribute와 Method다.

| 요소 | 역할 | 자동차 예시 |
|---|---|---|
| Attribute | Object의 상태·성질을 저장한다. | `fuel`, `speed`, `color` |
| Method | 행동을 수행하고 필요하면 상태를 바꾼다. | `refuel`, `accel` |

`speed`는 자동차의 물리적 부품이 아니지만 상태를 나타내므로 Attribute가 될 수 있다. `refuel`은 `fuel`을 바꾸고, `accel`은 `speed`를 바꾸는 행동으로 생각할 수 있다. Method 하나가 반드시 Attribute 하나만 바꾸는 것은 아니다. 실제 행동에 따라 여러 상태가 함께 바뀔 수 있다. [M01 p.8] [STT 06:21] [STT 07:20]

Instance(인스턴스)는 이 문맥에서 Object를 가리키며, Instantiate(인스턴스 생성)는 Class의 Instance를 만드는 일을 뜻한다. 이번 자료에서는 Attribute와 Method를 합쳐 Member(멤버)라고 부른다. 따라서 “같은 Class의 Object들은 공통된 Members를 따른다”는 말은 같은 정의를 사용한다는 뜻이다. 모든 Object가 동일한 Attribute 값을 함께 보관한다는 뜻은 아니다. [M01 p.17] [STT 16:40]

**기출 연결 — 현재 접근 가능.** 2025-1 중간고사로 분류된 복기본의 1번은 Class와 Object를 설명하는 문항이다. 이 연결에서 필요한 능력은 두 용어를 각각 암기하는 데 그치지 않고, 공통 설계와 그 설계로 만든 개별 대상의 관계를 설명하는 것이다. 자동차 예시를 사용한다면 공통 Attribute·Method 정의와 Object마다 다른 상태를 함께 제시하면 된다. “Class는 자동차, Object는 자동차 브랜드”처럼 예시 이름만 대응시키는 것은 관계 설명으로 부족하다. 이 복기본의 교수·학기 정보는 파일명 기반이며 독립적으로 확인되지 않았고, 현재 강의와 동일한 담당·시험 범위를 전제하지 않는다. [EX:cp_2025_1_midterm_q01 p.1]

### `new`와 Reference(참조): Class 선언과 Object 생성을 구별하기

Class를 선언하는 것과 Object를 만드는 것은 서로 다른 단계다. 다음은 자료의 가장 단순한 예시다. `class` 선언은 설계를 정의하고, `new Car()`는 그 설계에 따라 새 Object를 생성한다. [M01 p.9]

```java
class Car {
}

// 다음 문장은 메서드 등의 실행 문맥에 둔다.
Car myCar = new Car();
```

마지막 문장은 세 부분으로 나누어 읽는다.

- `Car`: 변수의 자료형을 나타내는 Class 이름이다.
- `myCar`: 생성된 Object를 가리키는 Reference 값을 저장하는 변수다.
- `new Car()`: 새 `Car` Object를 만드는 표현식이다.

일상적인 설명에서는 `myCar`를 Object라고 부르기도 하지만, 코드의 동작을 분석할 때는 **변수와 변수가 가리키는 Object를 구분**해야 한다. 이 구분이 뒤에서 대입, 비교, Method 호출을 이해하는 기준이 된다. [M01 p.9] [STT 08:16] [STT 09:15]

강의는 `new`를 새로운 Object에 필요한 메모리 확보와 연결한다. 여기서 얻어야 할 결론은 새 Object가 만들어진다는 것이다. Class 정의 전체나 Method 코드가 Object마다 물리적으로 복제된다는 의미로 확대하지 않는다.

이후 자료에 반복해서 나오는 `Car` 정의들은 개념별로 사용하는 독립 예제다. 서로 다른 페이지의 모든 Attribute와 Method를 하나의 Class에 누적해서 해석하지 않는다.

개념 연결: [[concepts/object-instantiation|Object Instantiation]], [[concepts/reference|Reference]]

### Attribute 초기화와 Object별 독립 상태

Field(클래스에 선언한 변수)는 Object의 상태를 저장한다. 자료의 `Car` 예제는 `width`를 `10`, `color`를 `"red"`로 명시적으로 초기화한다. 이 값들은 생성 직후의 출발 상태이지, 모든 Object가 영원히 유지해야 하는 값은 아니다. [M01 p.10] [STT 10:12]

```java
class Car {
    int width = 10;
    String color = "red";
}
```

Dot syntax(점 표기법)는 특정 Object의 Member에 접근하는 표기다. 다음 사용 예시는 `car`가 가리키는 Object의 `width`를 읽고 바꾼다. [M01 p.11]

```java
Car car = new Car();

System.out.println(car.width); // 10
car.width = 5;
System.out.println(car.width); // 5
```

`car.width = 5`는 Class의 설계 자체를 수정하는 문장이 아니다. 이미 만들어진 특정 Object의 Field 값을 바꾼다. 강의에서 Class 이름은 대문자로, 변수 이름은 소문자로 시작하는 관례를 언급한 것도 둘의 역할을 읽기 쉽게 구분하기 위해서다. [STT 10:12] [STT 11:11]

명시적으로 초기화하지 않은 Field에는 기본값이 적용된다. 자료의 `Foo` 예제는 이를 출력으로 확인한다. [M01 p.12] [M01 p.13]

| Field의 자료형 | 예제에서 확인하는 기본값 |
|---|---|
| `boolean` | `false` |
| `int` | `0` |
| `float` | `0.0` |
| `String` 같은 Reference 자료형 | `null` |

자료의 `char` 출력은 눈에 보이지 않는 것처럼 나타난다. 이를 유효한 빈 문자 리터럴 `''`이 있다는 뜻으로 읽으면 안 된다. 또한 이 기본값 설명은 Field에 관한 것이다. Local variable(지역 변수)을 초기화하지 않고 읽어도 된다는 규칙이 아니다.

강사는 명시적 초기화를 권장하면서, 초기 상태가 코드에 드러나면 값을 예상하기 쉽고 유지보수에도 도움이 된다고 설명한다. 언어가 기본값을 제공한다는 사실과 초기 상태를 명료하게 표현하는 설계 관례는 구분할 수 있다. [STT 12:04] [STT 13:00]

별도로 생성한 Object들은 각자의 Instance Field를 가진다.

```java
Car car = new Car();
Car newCar = new Car();

newCar.color = "blue";

System.out.println(car.color);    // red
System.out.println(newCar.color); // blue
```

이 예제에는 `new`가 두 번 있으므로 두 Object가 만들어진다. `newCar`의 색상을 바꿔도 `car`의 색상이 유지되는 이유는 공통 설계와 개별 상태가 분리되어 있기 때문이다. 뒤에서 다룰 Reference 대입으로 같은 Object를 가리키는 상황과 혼동하지 않는다. [M01 p.14] [STT 13:45]

### Method와 호출 대상: 같은 정의가 다른 값을 반환하는 이유

Method는 Class 안에 정의한 Member function(멤버 함수)이다. Object가 수행할 행동을 정의하고, 호출할 때는 `car.printHello()`처럼 Object를 가리키는 변수, 점, Method 이름, 괄호를 사용한다. 자료의 `printHello()`는 문자열을 출력하며, Return type(반환형)이 `void`이므로 호출자에게 반환하는 값은 없다. **화면에 출력하는 것과 값을 반환하는 것은 다르다.** [M01 p.15] [STT 14:42]

Method는 호출 대상 Object의 상태를 이용할 수 있다.

```java
class Car {
    int speed;

    int getSpeed() {
        return speed;
    }
}
```

```java
Car myCar = new Car();
Car yourCar = new Car();

myCar.speed = 100;
yourCar.speed = 90;

System.out.println(myCar.getSpeed());   // 100
System.out.println(yourCar.getSpeed()); // 90
```

두 호출은 동일한 `getSpeed()` 정의를 사용하지만 호출 대상이 다르다. 첫 호출은 `myCar`가 가리키는 Object의 `speed`를 읽고, 두 번째 호출은 `yourCar`가 가리키는 Object의 `speed`를 읽는다. Method의 동작을 이해하려면 이름뿐 아니라 **어느 Object에 대해 호출했는가**를 확인해야 한다. [M01 p.16] [STT 15:41]

여기서 Method가 Object에 속한다는 설명은 호출 대상에 따라 사용하는 상태가 달라진다는 뜻이다. Object마다 같은 Method의 소스 코드가 별도로 복사되어야 한다는 주장은 아니다. 공통 행동을 한 번 정의하고 여러 Object에 적용할 수 있다는 점이 Class 재사용의 이점이다. [STT 16:40]

개념 연결: [[concepts/instance-method|Instance Method]]

### Constructor(생성자): 생성 과정에 초기화 규칙을 묶기

Constructor는 Object가 만들어질 때 초기화를 수행하는 구성 요소다. 이름이 Class 이름과 같고 Return type을 쓰지 않는다. 반환값이 없다는 이유로 `void`를 붙이는 것도 아니다. [M01 p.19]

```java
class Car {
    Car() {
        System.out.println("A car is created.");
    }
}
```

`new Car()`를 실행하면 생성 과정에서 Constructor 본문이 실행되어 메시지가 출력된다. 이를 일반 Method처럼 임의의 기존 Object에 대해 다시 호출하는 동작으로 이해하지 않는다. 자료가 Constructor를 특별한 Method라고 소개하더라도 일반 Method와 같은 호출 규칙을 가진다는 뜻으로 일반화할 수는 없다. [M01 p.20] [STT 17:35] [STT 18:33] [STT 19:33]

Constructor는 Parameter(매개변수)를 받아 초기값을 정할 수 있다. Parameter 목록이 다른 여러 Constructor를 제공하면 필요한 정보에 따라 초기화 방법을 선택하게 할 수 있다. [M01 p.21]

```java
class Car {
    int weight;
    String color = "unknown";

    Car(int w) {
        weight = w;
    }

    Car(int w, String c) {
        weight = w;
        color = c;
    }

    void printInfo() {
        System.out.println(weight + " kg, " + color);
    }
}
```

```java
new Car(1500, "red").printInfo(); // 1500 kg, red
new Car(2000).printInfo();       // 2000 kg, unknown
```

첫 번째 생성은 무게와 색상을 모두 전달한다. 두 번째 생성은 무게만 전달하므로 색상은 Field에 적힌 초기값 `"unknown"`을 유지한다. 두 Constructor 모두 `weight`를 설정한다는 점도 중요하다. 제시된 정의에는 인자를 받지 않는 `Car()`가 없다. [M01 p.22] [STT 20:27] [STT 21:24]

생성 후 Field에 하나씩 대입해서 비슷한 결과를 만들 수도 있다. 하지만 초기화 규칙을 Constructor에 모으면 Object를 만들 때마다 같은 대입문을 반복하지 않아도 되고, 어떤 정보가 필요한지도 생성 코드에서 드러난다. 이 예제의 `printInfo()`는 서로 다른 내용을 **출력**하는 `void` Method다. STT의 반환을 연상시키는 표현을 실제 반환값이 있다는 설명으로 채택하지 않는다. [STT 21:24] [STT 22:24]

Constructor 안에서 다른 Constructor를 호출하는 방식은 자료에 예고되어 있으나 상세 설명은 미뤄졌다. 따라서 이번 범위의 “생성 시 초기화”와 후속 Constructor 호출 규칙을 구분한다. [M01 p.19] [M01 p.23]

### `this`: 현재 Object의 Field와 Method를 명시하기

`this`는 현재 Object를 가리키는 키워드다. `this.speed`는 현재 Object의 `speed` Field를 뜻한다. 특히 Parameter나 Local variable이 Field와 같은 이름을 가질 때, 어느 변수를 읽고 쓰는지 구분하는 역할을 한다. [M01 p.23] [STT 23:22]

자료의 다음 두 Method를 비교하면 차이가 분명하다. [M01 p.26]

```java
class Car {
    int speed = 30;

    void cantChangeSpeed(int speed) {
        speed = speed;
    }

    void changeSpeed(int speed) {
        this.speed = speed;
    }
}
```

`cantChangeSpeed(90)`에서 이름만 쓴 `speed`는 Parameter를 가리킨다. 따라서 `speed = speed`는 Parameter에 자신의 값을 다시 대입할 뿐이며, Object의 Field는 `30`으로 남는다. 반면 `changeSpeed(90)`의 왼쪽 `this.speed`는 Field이고 오른쪽 `speed`는 Parameter다. 이 문장은 입력받은 `90`을 현재 Object의 Field에 저장한다. [STT 27:00] [STT 27:55]

**자료와 STT가 충돌하는 예제는 따로 구분해야 한다.** M01 p.24에는 Local variable `color` 선언이 없다.

```java
class Car {
    String color;

    void changeColor() {
        this.color = "red";
        System.out.println(this.color);

        color = "blue";
        System.out.println(color);
    }
}
```

따라서 이 코드에서 `this.color`와 `color`는 같은 Field를 가리킨다. 출력은 차례로 `red`, `blue`이고, Method 종료 후 Field도 `"blue"`다. `this`를 생략했다고 새로운 Local variable이 만들어지는 것은 아니다. STT의 두 번째 대입이 Local variable만 바꾼다는 설명은 이 인쇄 코드와 맞지 않으므로 **발화 의도는 검증 필요**로 남긴다. 실제로 같은 이름의 Parameter가 있는 p.26 예제와 구분해서 배워야 한다. [M01 p.24] [STT 24:11]

`this`로 현재 Object의 Method를 명시할 수도 있다.

```java
class Car {
    int speed = 100;

    String speedAndUnit() {
        return speed + " km/h";
    }

    void printSpeedAndUnit() {
        System.out.println(this.speedAndUnit());
    }
}
```

`speedAndUnit()`은 문자열을 반환하고, `printSpeedAndUnit()`은 그 문자열을 출력한다. 이 예제의 출력은 `100 km/h`다. 현재 코드에서는 `this.speedAndUnit()`의 `this`를 생략해도 같은 Method를 호출한다. 속도와 단위를 연결하는 표현을 별도 Method에 모았으므로, 필요한 곳마다 같은 문자열 연결식을 반복하지 않아도 된다. [M01 p.25] [STT 25:10] [STT 26:08]

**기출 연결 — 부분 연결.** 2025-1 중간고사 복기본 5번은 `this`와 `super`의 비교를 요구한다. 이번 강의로 설명할 수 있는 부분은 `this`가 현재 Object를 가리킨다는 점과 이름이 같은 Field·Parameter를 구분하는 역할이다. 전체 비교에는 `super`와 상속의 구체적인 규칙이 더 필요하다. `this`를 단순히 “현재 Class의 이름”이라고 설명하는 것이 이 단계의 함정이다. [EX:cp_2025_1_midterm_q05 p.3]

개념 연결: [[concepts/this-keyword|this]]

### `static` Member: 개별 Object가 아니라 Class에 속하는 상태

Instance Member가 개별 Object에 연결된다면, `static` Member는 Class에 연결된다. 자료의 자동차 그림은 개별 자동차의 브랜드와 자동차 전체 수를 대비한다. 브랜드는 각 Object의 상태이고, 전체 수는 Class 수준에서 함께 관리할 값으로 표현할 수 있다. [M01 p.27]

**그림 읽기:** p.27에서 `Total number: 3`은 왼쪽 Class 쪽에 놓여 있고, `Brand: Audi`, `Brand: Nissan`, `Brand: Volvo`는 오른쪽의 개별 Object 쪽에 놓여 있다. 두 종류의 정보를 같은 Field라고 생각하면 안 된다. 개별 브랜드를 변경한다고 다른 자동차 브랜드가 함께 바뀌는 것은 아니지만, 하나의 `static` 값을 변경하면 그 Member를 읽는 접근들은 변경된 값을 보게 된다.

```java
class Car {
    static int num = 3;

    static void printNum() {
        System.out.println("The number of cars is " + num);
    }
}
```

이 정의에서는 Object를 먼저 만들지 않고 `Car.num`, `Car.printNum()`처럼 Class 이름으로 접근할 수 있다. `static`의 핵심은 소속과 접근 방식이다. 강의의 메모리 공간 설명을 특정 물리적 저장 위치의 보장으로 받아들이지는 않는다. [M01 p.28] [M01 p.29] [STT 29:50]

다음 예제는 개별 상태와 공통 상태를 함께 갱신한다. [M01 p.30]

```java
class Car {
    static int num;
    static int totalMile;
    int mile;

    Car() {
        num++;
    }

    void setMile(int mile) {
        this.mile = mile;
        totalMile += mile;
    }
}
```

세 Object를 만들고 각각 `setMile(20)`, `setMile(30)`, `setMile(40)`을 한 번씩 호출하면 다음과 같다.

| 단계 | `num` | `totalMile` | 의미 |
|---|---:|---:|---|
| Object 세 개 생성 후 | 3 | 0 | Constructor가 세 번 실행됨 |
| 첫 호출에 `20` 전달 | 3 | 20 | 첫 Object의 `mile` 설정 및 누적 |
| 두 번째 호출에 `30` 전달 | 3 | 50 | 두 번째 Object의 `mile` 설정 및 누적 |
| 세 번째 호출에 `40` 전달 | 3 | 90 | 세 번째 Object의 `mile` 설정 및 누적 |

`static int` Field들의 출발값 `0`은 이 코드에 적용되는 기본값이다. STT에서 가정처럼 표현했더라도 임의로 정한 값은 아니다. 명시적 초기화가 읽기 쉽다는 강의의 조언은 별도로 유지할 수 있다. [STT 31:39] [STT 32:37] [STT 33:33]

중요한 오개념은 변수 이름만 보고 의미를 확정하는 것이다. 이 코드의 `num`은 생성 횟수를 센다. 더 이상 사용하지 않는 Object가 생겨도 자동으로 감소하지 않으므로 현재 살아 있는 Object 수를 추적하는 완성된 코드가 아니다. `totalMile`도 현재 모든 `mile` Field의 합을 항상 유지하지 않는다. `setMile()`에 전달한 값들을 계속 더한다.

**이해를 위한 예시:** 위 호출들 다음에 첫 Object에 `setMile(25)`를 다시 호출하면 `totalMile`은 $90+25=115$다. 하지만 현재 세 Field의 합은 $25+30+40=95$다. 재설정과 누적은 서로 다른 연산이므로, 실제 코드의 대입문을 기준으로 의미를 판단해야 한다.

개념 연결: [[concepts/static-members|static Members]]

### `static` Method의 제약과 `main` 선언 읽기

`static` Method에는 암묵적으로 정해진 현재 Object가 없다. 따라서 Instance Field에 접근하려면 어느 Object의 Field인지 알 수 있어야 한다. 자료의 다음 정의는 그 대상이 빠져 있다. [M01 p.31] [M01 p.32]

```java
class Car {
    float fuel;

    static float totalFuel() {
        return fuel; // 컴파일 오류: 어느 Car의 fuel인지 정해지지 않음
    }
}
```

오류 원인은 `new Car()`를 실행하면 문제가 발생한다는 데 있지 않다. `static` Method의 정의에서 Instance Field를 대상 없이 읽으려 하므로 컴파일 단계에서 문제가 된다. STT에서도 처음 표현 뒤에 정의와 컴파일의 문제로 다시 설명한다. [STT 36:24]

“`static` Method는 Instance Member를 사용할 수 없다”는 문장은 **Object를 지정하지 않은 직접 접근의 제약**으로 이해해야 한다. 명시적인 Object를 통한 접근까지 모두 금지된다는 뜻은 아니다.

다음은 이해를 위한 예시이며, 자료의 잘못된 정의를 그대로 옮긴 코드는 아니다.

```java
class Car {
    float fuel;

    static float fuelOf(Car car) {
        return car.fuel;
    }
}
```

여기서는 Parameter `car`가 어느 Object를 사용할지 알려 준다. 따라서 `car`가 유효한 Object를 가리킨다는 조건에서 그 Object의 `fuel`을 읽을 수 있다. 반대로 Instance Method에서 `static` Member를 사용하는 것은 가능하다. [M01 p.31]

STT 중 `static`·non-static의 방향이 주변 설명과 뒤바뀐 문장은 그대로 학습 규칙으로 삼지 않는다. 그 발화의 의도는 검증 필요이며, 노트에서는 “접근 대상 Object가 정해져 있는가”를 기준으로 설명한다. [STT 34:26]

이제 자료에 반복해서 등장하는 다음 선언도 구성 요소별로 읽을 수 있다.

```java
public static void main(String[] args)
```

`public`은 외부 접근을 허용하는 Access modifier(접근 제어자), `static`은 Class 수준의 Method라는 표시, `void`는 반환값이 없다는 표시다. `main`은 Method 이름이고, `String[] args`는 문자열 배열 Parameter다. 자료의 `main`에서 같은 Class의 `static swap()`을 별도의 Object 생성 없이 호출하는 이유도 이와 연결된다. [M01 p.37] [STT 40:13]

**기출 연결 — 부분 연결, 후속 선수 개념 필요.** 2025-1 중간고사 복기본 7번은 `static` 중첩 Class와 바깥 Instance Field 사이의 접근 오류를 진단하고, 지정된 Method 본문을 유지하며 수정하도록 요구한다. 현재 배운 내용에서 가져갈 접근법은 Field가 어느 Object에 속하는지 먼저 확인하는 것이다. 다만 문항 속 내부 Method 자체는 Instance Method이므로, 이를 단순히 “`static` Method라서 실패한다”라고 설명하면 안 된다. 전체 수정에는 중첩 Class와 바깥 Object의 관계를 더 배워야 한다. [EX:cp_2025_1_midterm_q07 p.4]

### Primitive Type과 Reference: 변수에 무엇이 저장되는가

Primitive Type(기본형)의 변수는 기본형 값 자체를 저장하고, Non-Primitive Type(참조형)의 변수는 Object를 가리키는 Reference 값을 저장한다. `int x = 2`에서 변수의 값은 정수 `2`다. `String s = "Hi"`에서 변수의 값은 String Object로 이어지는 Reference다. [M01 p.47] [M01 p.48]

자료의 메모리 그림은 다음 세 대상을 구별해서 읽어야 한다.

1. 코드에 쓰인 변수 이름
2. 그 변수에 저장된 값
3. Reference 값이 가리키는 Object

Primitive 변수의 저장값을 읽으면 바로 `2` 같은 값에 도달한다. Reference 변수의 저장값을 읽으면 Object로 이어지는 한 단계가 더 있다. 강의에서 Symbol table(심벌 테이블)은 이름과 저장 위치의 대응을 설명하기 위한 도식으로 사용된다. 그림의 주소 숫자나 상자 배치를 실제 실행 환경의 물리적 구조와 동일시하지 않는다. [STT 51:03] [STT 52:02]

**자료 오류 주의:** p.46의 자료형 분류 그림은 `Floating-Point`를 `Integral Value` 아래에 연결한다. 이 연결은 잘못되었다. `float`·`double`을 정수 유형이라고 외우면 안 된다. 여기서는 Primitive와 Non-Primitive의 구분을 배우되, 그림의 잘못된 하위 분류까지 정답으로 채택하지 않는다. 강사가 이 오류를 수업에서 수정했다고 주장하지도 않는다. [M01 p.46]

이 구분은 Object 비교와 대입에서 곧바로 필요하다.

```java
String str1 = new String("hey");
String str2 = new String("hey");
String str3 = str1;

System.out.println(str1 == str2); // false
System.out.println(str1 == str3); // true
```

Reference에 대한 `==`는 문자열 내용이 아니라 같은 Object를 가리키는지를 비교한다. `str1`과 `str2`는 `new`로 별도로 만든 Object를 가리킨다. `str3 = str1`은 Object 전체를 복제하지 않고 Reference 값을 복사한다. 따라서 첫 비교는 `false`, 두 번째 비교는 `true`다. [M01 p.34] [M01 p.35] [STT 37:18] [STT 38:18]

```java
Car myCar = new Car();
Car car1 = myCar;
Car car2 = myCar;
Car car3 = car1;
```

자료의 이 예제에는 `new`가 한 번뿐이다. 변수는 네 개지만 Object는 하나다. 한 변수로 그 Object의 Field를 바꾸면 다른 변수로 접근해도 바뀐 상태를 읽는다. 앞의 두 Object 예제와 결과가 다른 이유는 Class가 달라서가 아니라 **공유하는 Object가 같은지 다른지**에 있다. [M01 p.36] [STT 39:13]

개념 연결: [[concepts/primitive-and-reference-types|Primitive and Reference Types]], [[concepts/reference-equality|Reference Equality]]

### Call-by-Value(값에 의한 전달): Primitive `swap`이 호출자 변수를 바꾸지 못하는 이유

Call-by-Value는 전달할 값을 복사하여 호출된 Method의 Parameter에 넣는 방식이다. 호출자 변수와 Parameter의 이름이 같아도 두 변수는 구분된다. 다음은 자료의 의도된 Primitive `swap`이다. [M01 p.37] [M01 p.38]

```java
static void swap(int a, int b) {
    int temp = a;
    a = b;
    b = temp;
}
```

호출자의 `x = 2`, `y = 3`으로 `swap(x, y)`를 실행하면 Parameter `a`, `b`는 각각 복사된 `2`, `3`으로 시작한다.

| 실행 단계 | 호출자 `x` | 호출자 `y` | Parameter `a` | Parameter `b` | `temp` |
|---|---:|---:|---:|---:|---:|
| 호출 직후 | 2 | 3 | 2 | 3 | 아직 선언되지 않음 |
| `int temp = a` | 2 | 3 | 2 | 3 | 2 |
| `a = b` | 2 | 3 | 3 | 3 | 2 |
| `b = temp` | 2 | 3 | 3 | 2 | 2 |

Method 안에서는 `a`, `b`가 교환되었지만 호출자의 `x`, `y`는 계속 `2`, `3`이다. 대입의 왼쪽이 Parameter이므로 그 Parameter의 값이 바뀔 뿐이다. [STT 41:05] [STT 41:53] [STT 42:47]

**그림 읽기:** p.39는 `main function`과 `swap function`의 변수들을 분리해서 표시한다. 같은 `a`, `b`라는 이름이 반복되어도 소속이 다르다. 그림에서 확인할 것은 호출자 쪽의 `2`, `3`은 그대로이고 호출된 쪽의 값만 `3`, `2`가 되었다는 사실이다. 상자의 위치를 실제 메모리 배치에 대한 정밀한 명세로 읽을 필요는 없다. [M01 p.39]

뒤에 반복되는 자료에는 별도의 코드 오류가 있다. p.49와 p.50의 마지막 대입은 `b = temp`가 아니라 `a = temp`다.

```java
int temp = a;
a = b;
a = temp; // p.49–50에 인쇄된 대입
```

초깃값이 `a = 2`, `b = 3`이면 이 순서는 마지막에 `a`를 다시 `2`로 돌려놓으므로 Local 값도 `2`, `3`이다. 그런데 p.50 그림은 `3`, `2`를 보여 주어 코드와 충돌한다. **호출자 값이 바뀌지 않는다는 결론은 두 버전에서 같지만, Method 내부의 최종값은 다르다.** 그림의 결과를 외우기보다 실제 대입문을 따라가야 한다. [M01 p.49] [M01 p.50] [STT 53:03]

개념 연결: [[concepts/pass-by-value|Call-by-Value]]

### `IntHolder`: Reference 값을 복사해도 공유 Object는 바꿀 수 있다

`IntHolder`는 정수 하나를 Field에 담는 작은 Class다. 자료에서는 Primitive 값을 직접 전달하는 경우와 Object의 Field를 바꾸는 경우를 비교하기 위해 도입한다. [M01 p.40]

```java
class IntHolder {
    int value;

    IntHolder(int value) {
        this.value = value;
    }
}
```

```java
static void swap(IntHolder a, IntHolder b) {
    int temp = a.value;
    a.value = b.value;
    b.value = temp;
}
```

호출자가 값 `2`, `3`을 가진 두 `IntHolder` Object를 만들고 전달하면, Method의 Parameter `a`, `b`는 호출자와 같은 두 Object를 가리킨다. `a.value = b.value`의 대입 대상은 Parameter 변수 `a`가 아니라 **`a`가 가리키는 Object의 Field**다. 따라서 호출자는 Method 종료 뒤 `3`, `2`로 바뀐 Field를 읽는다. [M01 p.41] [STT 43:42] [STT 44:40]

자료와 STT는 이 현상을 Call-by-Reference(참조에 의한 전달)라고 부른다. 하지만 Java의 인수 전달을 정확히 설명하면 **Reference 값도 Call-by-Value로 복사된다.** Object 자체를 통째로 복사하는 것은 아니며, 호출자 변수 자체를 Parameter로 직접 연결하는 것도 아니다. p.42에도 주소 값을 기준으로 보면 Call-by-Value로 이해할 수 있다는 단서가 있다. [M01 p.42] [STT 45:28]

강사는 수백 개의 Attribute와 수백 개의 배열을 담을 수 있는 큰 Object를 함수 호출 때마다 통째로 복사한다고 가정하면, 사용 가능한 메모리가 크게 줄어 비효율적이라고 설명했다. 이는 Object 전체를 복사하는 가상의 방식과 Reference 값만 복사해 전달하는 방식을 대비한 동기 설명이다. [STT 45:28]

구별할 것은 다음 두 대입이다.

```java
a = anotherHolder; // Parameter a가 가리키는 대상을 바꿈
a.value = 7;       // a가 현재 가리키는 Object의 Field를 바꿈
```

첫 문장은 호출자의 Reference 변수를 다시 대입하지 않는다. 두 번째 문장은 호출자와 공유하는 Object를 대상으로 했다면 호출자에게도 보이는 상태를 바꾼다. 이 두 연산을 구분하면 Object를 인수로 전달했을 때의 동작을 일관되게 설명할 수 있다.

**그림 읽기:** p.43에서는 교환된 `value`가 Object 쪽에 표시되고, `temp`는 호출된 Method의 Local 값으로 표시된다. 핵심은 호출자가 보는 Object의 Field가 바뀌었다는 점이다. STT의 Class·Object·메모리 위치를 혼용한 표현으로부터 세부 저장 구조를 추정하지 않는다. [M01 p.43] [STT 46:25] [STT 47:25]

개념 연결: [[concepts/object-mutation|Object Mutation]], [[concepts/pass-by-value|Call-by-Value]]

### Garbage collector(가비지 컬렉터): Object의 생성과 사용 종료 구분하기

Java는 새 Object를 만들 때 필요한 메모리를 할당하고, 사용하지 않게 된 Object의 메모리 회수를 Garbage collector에 맡긴다. 자료는 이를 C에서 명시적으로 메모리를 할당하고 해제하는 작업과 대비하여 설명한다. 핵심 동기는 프로그래머의 관리 부담을 줄이는 것이다. 이 대비를 C의 모든 변수가 반드시 수동 할당·해제를 필요로 한다는 규칙으로 확대하지 않는다. [M01 p.44] [STT 48:25]

강의에서는 `swap` 내부에서 추가로 `new IntHolder(4)`를 만드는 상황을 든다. Method가 끝난 뒤 다른 곳에서도 그 Object를 참조하지 않는다면, 더 이상 프로그램이 그 Object에 도달할 수 없게 되어 회수 대상이 될 수 있다. [STT 48:25] [STT 49:18]

다음은 그 조건을 설명하기 위한 예시다.

```java
static void makeTemporaryHolder() {
    IntHolder temporary = new IntHolder(4);
}
```

이 예시에서 만든 Object를 다른 곳에 전달하거나 저장하지 않았다면, 호출 종료 뒤 사용할 경로가 남지 않는다. 반면 Object의 Reference를 다른 곳에 보관했다면 Method가 끝났다는 사실만으로 사용이 종료되었다고 할 수 없다.

또한 **회수 대상이 되는 조건과 실제 회수 시점은 다르다.** Method가 반환하는 순간 반드시 즉시 회수된다고 보장하지 않는다. 변수의 사용 범위가 끝났다는 설명과 Object의 사용 가능성을 구분해야 한다.

**기출 연결 — 현재 접근 가능.** 2025-1 중간고사 복기본 3번은 Garbage Collector의 역할과 `new`로 만든 Object에 적용되는 조건을 함께 설명하도록 요구한다. 풀이 접근은 “어떤 일을 자동으로 하는가”와 “어떤 Object가 대상이 되는가”를 나누는 것이다. 단순히 Method 종료를 조건으로 적거나 정확한 회수 시점을 보장하는 것이 함정이다. 공식 답안이 제공된 문항은 아니므로, 여기의 설명은 강의 개념과 Reference 관계를 바탕으로 한 해설이다. [EX:cp_2025_1_midterm_q03 p.2]

STT에는 강사가 속도를 비교하며 C++이 Java보다 항상 낫고 적어도 10배 또는 20배 더 빠르다는 취지로 일반화한 발언이 있다. 제시된 자료에는 이를 뒷받침하는 측정 조건이나 결과가 없으므로 성능 수치와 보편적 우열은 **검증 필요**다. 이번 학습에서는 자동 관리의 편의와 프로그래머가 직접 관리해야 하는 부담의 대비를 이해한다. [STT 50:04]

개념 연결: [[concepts/garbage-collection|Garbage Collection]]

### `String` Parameter 교환: Reference 재대입은 호출자 재대입이 아니다

`String`은 Reference를 사용하는 자료형이다. 그렇다고 `String` Parameter 두 개를 교환하면 호출자 변수도 바뀌는 것은 아니다. 자료의 p.52–53은 다음 대입을 보여 준다. [M01 p.52] [M01 p.53]

```java
static void swap(String a, String b) {
    String temp = a;
    a = b;
    b = temp;
}
```

```java
String s1 = "Hi";
String s2 = "all";

swap(s1, s2);

System.out.println(s1 + " " + s2); // Hi all
```

호출 직후 `s1`과 `a`는 같은 String Object를 가리키고, `s2`와 `b`도 같은 String Object를 가리킨다. 그러나 `s1`과 `a`는 서로 다른 변수다. `a = b`는 `a`에 저장된 Reference 값만 바꾼다. 호출자의 `s1`에 대한 대입은 실행되지 않는다.

| 시점 | 호출자 `s1` | 호출자 `s2` | Parameter `a` | Parameter `b` |
|---|---|---|---|---|
| 호출 직후 | `"Hi"`를 가리킴 | `"all"`을 가리킴 | `"Hi"`를 가리킴 | `"all"`을 가리킴 |
| 세 대입 완료 후 | `"Hi"`를 가리킴 | `"all"`을 가리킴 | `"all"`을 가리킴 | `"Hi"`를 가리킴 |

**그림 읽기:** p.53에서 바뀐 것은 `a`, `b`에 저장된 Reference이고, `s1`, `s2`에 저장된 Reference는 그대로다. 문자열 내용이 있는 두 Object도 그대로다. 따라서 이 예제는 문자열 내용을 바꾸지도, 호출자 Reference 변수들을 교환하지도 않는다.

STT의 교환 성공을 말하는 표현을 호출자 변수까지 바뀐다는 결론으로 채택해서는 안 된다. 해당 표현의 의도는 검증 필요이며, 여기서는 코드와 그림이 보여 주는 변수별 대입 결과를 따른다. [STT 54:00] [STT 54:55] [STT 55:51]

p.51에는 또 다른 인쇄 차이가 있다. 마지막 줄이 `b = temp`가 아니라 `a = temp`여서 Parameter들 사이의 교환조차 완성하지 않는다. p.51의 오타와, p.52–53의 의도된 교환 코드도 호출자 변수를 바꾸지 못한다는 사실은 별개의 문제다. [M01 p.51]

개념 연결: [[concepts/reference-reassignment|Reference Reassignment]], [[concepts/pass-by-value|Call-by-Value]]

### Wrapper Class(감싸는 클래스): 두 단계의 Reference 추적하기

자료의 `Wrapper`는 `String s`라는 Field를 가진 Class다. 이 예제에서 추적해야 할 연결은 두 단계다.

```text
호출자 변수 또는 Parameter
          ↓
      Wrapper Object
          ↓ s
      String Object
```

호출자와 Parameter는 같은 Wrapper Object를 가리킬 수 있고, 그 Wrapper의 `s` Field는 다시 String Object를 가리킨다. 이 경우 `a = b`와 `a.s = b.s`는 전혀 다른 위치를 바꾸는 문장이다. [M01 p.54] [STT 56:50]

다음은 p.55–56이 보여 주는 의도된 `swap` 본문의 대입이다.

```java
String temp = a.s;
a.s = b.s;
b.s = temp;
```

처음에 첫 Wrapper의 `s`가 `"Hi"`, 두 번째 Wrapper의 `s`가 `"all"`을 가리킨다고 하자.

1. `temp = a.s`는 `"Hi"`를 가리키는 Reference 값을 보관한다.
2. `a.s = b.s`는 첫 Wrapper의 `s` Field가 `"all"`을 가리키도록 바꾼다.
3. `b.s = temp`는 두 번째 Wrapper의 `s` Field가 `"Hi"`를 가리키도록 바꾼다.

호출자도 같은 Wrapper Object들을 사용하므로, 호출 뒤 첫 Wrapper의 `s`에서 `"all"`, 두 번째 Wrapper의 `s`에서 `"Hi"`를 읽는다. 호출자 변수들이 가리키는 Wrapper 자체는 그대로다. String의 내용 자체도 바뀌지 않는다. **변한 것은 공유 Wrapper 안의 Reference Field다.** [M01 p.55] [M01 p.56] [STT 57:33] [STT 58:31]

**그림 읽기:** p.56에서는 호출자 변수와 Parameter에서 Wrapper로 이어지는 연결이 유지된다. 변경 표시가 붙은 곳은 그 다음 단계인 Wrapper의 `s`에서 String으로 이어지는 연결이다. 앞의 String Parameter 교환 그림과 비교할 때는 화살표가 교차하는지만 보지 말고, 어느 상자에 저장된 Reference가 변경되었는지 확인해야 한다.

강사는 시작과 끝의 두 그림만 보면 중간 과정이 잘 드러나지 않으므로 대입을 한 줄씩 따라가도록 설명한다. 각 줄의 왼쪽이 Parameter인지, 공유 Object의 Field인지 적어 보면 변화가 명확해진다. [STT 59:27]

여기에도 원본 코드 차이가 있다. p.54의 마지막 대입은 `a.s = temp`여서 첫 Field를 원래 값으로 되돌린다. 두 Wrapper가 서로 다른 Object라는 제시 상황에서 최종 Field들은 교환되지 않는다. 또한 p.54의 `Wrapper`는 바깥 Class 안에 선언된 non-static Member Class다. 실행 편의를 위해 별도 Class나 `static` 중첩 Class로 바꾼 예시를 원본과 동일한 코드라고 부르면 안 된다. [M01 p.54]

개념 연결: [[concepts/wrapper-class|Wrapper Class]], [[concepts/object-mutation|Object Mutation]]

### Encapsulation(캡슐화): 내부 구현과 사용하는 방법 분리하기

Encapsulation은 Object의 상태와 행동을 묶고, 외부에는 필요한 상호작용을 제공하면서 내부 구현에 대한 접근을 제한하는 개념이다. M01의 캡슐 그림은 Variables와 Methods를 Class 안에 함께 묶는 모습을 보여 준다. 그림의 목적은 단순히 이름을 하나 붙이는 것이 아니라, 내부 구성과 외부 사용 사이에 경계를 둔다는 점을 설명하는 데 있다. [M01 p.59]

강의의 자동차 비유에서는 운전자가 조향 장치와 가속 장치를 사용할 수 있으면 된다. 모든 엔진 부품의 작동을 알아야만 자동차를 사용할 수 있는 것은 아니다. 필요한 사용 방법을 제공하는 Interface(상호작용 경계)와 내부 구현을 분리하는 것이다. 여기서 Interface는 일반적인 설계 의미이며, Java의 `interface` 선언 문법을 이미 배웠다는 뜻은 아니다. [STT 01:00:23] [STT 01:01:19]

**그림 읽기:** M02 p.3은 복잡한 기계 내부 사진과 간단한 조작 패널 사진을 대비한다. 왼쪽에서는 수많은 연결과 부품이 드러나지만, 오른쪽에서는 사용자가 선택할 기능과 조작부가 드러난다. 사진 속 장치의 정확한 내부 구조를 외울 필요는 없다. 수리하는 사람에게 필요한 정보와 정상 기능을 사용하는 사람에게 필요한 정보가 다르다는 점을 읽어야 한다. [M02 p.3] [STT 01:08:07]

로봇의 팔·머리·몸통을 나누어 구현한다는 비유는 STT에서 추가된 협업 예시다. 각 담당자는 다른 부품의 모든 내부 코드를 알아야 하는 대신, 어떤 동작을 요청할 수 있고 어떤 결과를 기대할 수 있는지 합의한다. 이처럼 Encapsulation은 외부 사용자가 알아야 할 범위를 줄여 여러 사람이 작업을 나눌 수 있게 한다. 비유 중 불명확하게 인식된 사람 수나 비율은 확정하지 않는다. [STT 01:08:56] [STT 01:09:54]

개념 연결: [[concepts/encapsulation|Encapsulation]], [[concepts/abstraction|Abstraction]]

### Inheritance(상속)와 Polymorphism(다형성): 재사용과 행동의 다양화

Inheritance는 Class 사이의 관계다. Parent class(상위 클래스)의 특성과 코드를 Child class(하위 클래스)가 재사용하고, 필요한 새 특성을 더할 수 있다. Object를 새로 만드는 것과 Class 사이에 이런 관계를 정의하는 것은 서로 다른 단계다. [M01 p.60]

자료의 계층 그림은 `Organisms` 아래에 `Animals`와 `Plants`를, 다시 그 아래에 `Duck`·`Cat`과 `Tree`·`Grass`를 둔다. 아래쪽 Class가 더 일반적인 위쪽 Class의 특성을 이어받는 관계로 읽는다. STT의 동물 예시는 그림의 항목과 완전히 같지 않으므로, 두 표현을 하나의 동일한 원문처럼 합치지 않는다. [M01 p.60] [STT 01:01:19] [STT 01:02:17]

강의에서는 동물의 특성을 재사용하는 `Cat` Class에 꼬리(tail)라는 새 특성을 더하고, 그 `Cat` Class에서 ‘내 고양이(my cat)’와 ‘네 고양이(your cat)’ 같은 개별 Object를 여러 개 만드는 예를 들었다. [STT 01:03:16] 여기서 구분할 것은 다음 두 가지다.

- Class 사이에서는 공통 특성을 재사용하고 더 구체적인 특성을 정의한다.
- 하나의 Class에서는 그 정의를 따르는 여러 Object를 만든다.

생물학적 공통점이나 특정 Method 이름처럼 STT에서 불분명한 부분은 검증 필요이며, 임의로 복원하지 않는다. 이번 범위의 학습 대상은 Class 관계를 통한 재사용의 동기다. [STT 01:02:17] [STT 01:03:16]

Polymorphism은 공통된 이름과 사용 약속을 유지하면서 구체적인 Class마다 다른 행동을 제공하는 개념으로 소개된다. 자료의 `animalSound()` 그림에서 개·고양이·오리는 같은 이름의 동작에 대해 서로 다른 소리를 낸다. 호출하는 쪽은 각 동물의 소리를 미리 전부 알지 못해도, 소리를 내는 동작을 요청할 수 있다는 공통 약속을 이용한다. [M01 p.61] [STT 01:04:10]

Inheritance의 초점이 공통 특성과 코드의 재사용이라면, 이 예시에서 Polymorphism의 초점은 구체적인 Class에 따른 행동의 차이다. 이번 시간에는 이를 동기와 개념 수준에서 소개했으며, 실제 호출 대상 선택 규칙이나 후속 Java 구현 문법까지 다룬 것으로 확장하지 않는다.

자료는 Abstraction을 Encapsulation에, 코드 재사용을 Inheritance에, 행동의 다양화를 Polymorphism에 연결한다. 강의의 Java에서 C++로 이어지는 설명도 이러한 OOP 관점을 먼저 익힌 뒤 더 직접적인 관리가 필요한 언어로 나아가겠다는 수업 설계의 소개다. 이 시간에 C++ 구현 내용을 이미 배웠다는 의미는 아니다. [M01 p.58] [STT 01:05:10] [STT 01:07:10]

개념 연결: [[concepts/inheritance|Inheritance]], [[concepts/polymorphism|Polymorphism]]

### `FruitStore`: 함께 바뀌어야 하는 상태를 행동으로 묶기

Encapsulation이 필요한 이유를 `FruitStore`의 판매 동작으로 구체화할 수 있다. 초기 상태는 `balance = 10000`, `stock = 30`이고, 과일 한 개의 가격은 `2000`이다. 세 개를 판매하면 재고와 잔액이 함께 바뀌어야 한다. [M02 p.4]

$$
\text{stock}' = 30 - 3 = 27
$$

$$
\text{balance}' = 10000 + 2000 \times 3 = 16000
$$

외부 코드가 직접 `stock`과 `balance`를 수정하려면 판매가 어떤 Field들을 어떤 방식으로 바꾸는지 알아야 한다. 한쪽 변경을 빠뜨리면 재고만 줄고 대금은 늘지 않는 상태가 생긴다. 강의의 재고만 가져가는 사람 비유는 이런 잘못된 상태 변경의 가능성을 보여 준다. [M02 p.6] [STT 01:10:38] [STT 01:11:36]

자료는 두 변경을 `sell()`에 모은다.

```java
void sell(int num) {
    balance += 2000 * num;
    stock -= num;
}
```

이제 외부 사용자는 세부 대입문을 구성하는 대신 `sell(3)`이라는 행동을 요청한다. 이는 사용 방법을 단순하게 하는 Abstraction이다. 그러나 Method를 추가했다는 사실만으로 외부의 직접 Field 접근까지 막히지는 않는다. 예상하지 않은 변경을 제한하는 Defensive programming(방어적 프로그래밍)을 구현하려면 접근 제어도 필요하다. [M02 p.5] [M02 p.7] [STT 01:12:31]

따라서 이 예제의 설계 문제는 두 부분이다. 판매라는 의미 있는 행동을 Method로 제공하고, 그 행동을 우회해 내부 상태를 임의로 바꾸는 경로를 제한해야 한다. Java에서는 Class, Access modifier, Getter와 Setter를 활용한다고 이어서 소개한다. [M02 p.8]

개념 연결: [[concepts/encapsulation|Encapsulation]], [[concepts/defensive-programming|Defensive Programming]]

### Access modifier: 접근할 수 있는 범위를 정하기

Access modifier는 Member 등에 접근할 수 있는 범위를 정한다. 이번 강의는 네 수준을 개괄한다. Package(패키지)는 여기서 Class들의 묶음 정도로 소개되며, 선언·사용법의 상세 설명은 후속 범위다. [M02 p.9] [STT 01:13:13] [STT 01:14:06]

| 표기 | 이번 강의에서 소개한 의미 | 주의할 점 |
|---|---|---|
| `private` | 선언한 Class 내부의 접근에 사용한다. | 존재 자체를 타인이 알 수 없다는 의미가 아니다. |
| modifier 생략, default access | 같은 Package에서 접근할 수 있다. | 이 자리에 `default`라는 단어를 적는 것이 아니다. |
| `protected` | 같은 Package와 상속 관계의 Child class에 관련된 접근을 허용한다. | 다른 Package의 접근에는 추가 조건이 있다. |
| `public` | 다른 Class에 대한 접근을 허용한다. | Member가 속한 Class의 접근 가능성도 함께 고려해야 한다. |

이 표는 입문 수준의 개괄이다. 모든 Class 선언에 네 종류가 똑같이 허용된다거나, 다른 Package의 Child class가 임의의 Object를 통해 모든 `protected` Member에 접근할 수 있다는 보편 규칙으로 확장하지 않는다.

자료의 `Person` 예시는 `private`의 기본 효과를 보여 준다.

```java
class Person {
    private int weight = 80;
}
```

이 Class와 별개의 외부 Class에서 `person.weight`처럼 직접 읽으려 하면 접근 제한으로 컴파일 오류가 발생한다. 값이 존재하지 않거나 Object 생성에 실패한 것이 아니라, 그 위치에서 직접 읽도록 허용되지 않은 것이다. [M02 p.10] [STT 01:15:33]

**기출 연결 — 부분 연결.** 2025-1 중간고사 복기본 4번은 두 Package와 상속 관계가 있는 그림을 보고 접근 범위를 판단하도록 요구한다. 접근법은 “같은 Package인가”와 “상속 관계인가”를 따로 확인하는 것이다. 현재 배운 `private`와 modifier 생략의 의미는 연결할 수 있지만, 다른 Package에서의 `protected` 접근을 완전히 판단하려면 후속 규칙이 필요하다. 넓은 범위의 표 하나를 외워 모든 접근 표현에 기계적으로 적용하는 것이 함정이다. [EX:cp_2025_1_midterm_q04 p.2]

### `AppleStore`: 읽기 허용과 변경 허용을 분리하기

자료의 `AppleStore`는 `balance`와 `stock`을 `private`로 바꾸고, 읽기용 Method와 판매용 Method를 제공한다. 다음은 p.11의 Class와 Method 조각들을 한 정의로 정리한 것이다. modifier가 없는 Method들은 원본처럼 생략 상태를 유지했다. [M02 p.11]

```java
class AppleStore {
    private int balance = 10000;
    private int stock = 30;

    void sell(int num) {
        balance += 2000 * num;
        stock -= num;
    }

    int getBalance() {
        return this.balance;
    }

    int getStock() {
        return this.stock;
    }
}
```

같은 Package의 외부 코드에서는 `getBalance()`와 `getStock()`으로 값을 읽고, `sell()`로 판매를 요청할 수 있다. 초기 상태에서 `sell(3)`을 실행하면 잔액과 재고는 `16000`, `27`이 된다. [M02 p.12]

값을 Getter로 알려 준다고 해서 `private`가 무의미해지는 것은 아니다. **읽을 수 있다는 사실과 임의로 대입할 수 있다는 사실은 다르다.** 사용자는 현재 잔액을 확인할 수 있어도 `balance`를 원하는 값으로 직접 바꾸는 대신 허용된 행동을 이용해야 한다. 이 예제에서 Encapsulation의 목적은 값의 존재를 비밀로 만드는 것보다 지정된 상호작용으로 유도하는 데 있다. [STT 01:16:32] [STT 01:17:28]

자료의 Method에는 `public`이 없으므로 실제 접근 수준은 modifier 생략에 따른 같은 Package 접근이다. 강사는 모든 예제가 같은 Package에 있다고 가정하면서 편의상 공개된 Method처럼 부른다고 설명한다. 이 편의적 표현을 실제 `public` 선언으로 바꾸어 기억하지 않는다. [STT 01:18:17]

개념 연결: [[concepts/encapsulation|Encapsulation]], [[concepts/getter-and-setter|Getter and Setter]]

### `private` Method와 `boolean` 결과: 실패 가능한 판매 설계하기

앞의 `sell()`은 재고보다 많은 수량도 처리한다. 예를 들어 재고가 `30`인데 `100`개를 팔면 재고가 `-70`이 된다. 접근 경로를 Method 하나로 모았어도 그 Method가 조건을 검사하지 않으면 잘못된 상태를 만들 수 있다. Encapsulation은 검사를 넣을 위치를 제공하지만, 검사 내용까지 자동으로 완성해 주지는 않는다. [STT 01:19:16]

자료는 내부 검사 Method `inStock()`을 추가한다. 이 Method는 외부 사용자가 직접 이용할 기능이 아니라 `sell()`의 내부 구현을 돕는 기능이므로 `private`로 둔다. [M02 p.13]

```java
private boolean inStock(int num) {
    int shortage = num - stock;

    if (shortage > 0) {
        return false;
    } else {
        return true;
    }
}
```

`shortage`가 양수이면 주문 수량이 재고보다 많다는 뜻이다. 새 `sell()`은 검사에 성공했을 때만 두 Field를 바꾼다. [M02 p.14]

```java
boolean sell(int num) {
    if (inStock(num)) {
        balance += 2000 * num;
        stock -= num;
        return true;
    } else {
        return false;
    }
}
```

초기 상태에서 `sell(50)`을 호출하면 `50 - 30 = 20`이므로 검사는 실패한다. 잔액과 재고는 `10000`, `30`으로 유지되고, `sell()`은 `false`를 반환한다. 호출자는 반환값을 `success` 같은 변수에 저장한 뒤 성공과 실패에 맞게 분기할 수 있다. [M02 p.15] [M02 p.16]

Return type이 `void`에서 `boolean`으로 바뀐 이유는 판매 요청과 판매 성공이 더 이상 같은 사건이 아니기 때문이다. 호출자는 요청이 실제로 처리되었는지 알아야 한다. 반환값은 이 결과를 전달하는 Interface의 일부다. [STT 01:20:14] [STT 01:21:14] [STT 01:22:07]

다만 원본 검사는 완전한 입력 검증이 아니다. **이해를 위한 경계 사례:** 초기 상태에서 `sell(-1)`을 호출하면 다음 계산이 이루어진다.

$$
\text{shortage} = -1 - 30 = -31
$$

원본 조건은 이를 허용하므로 잔액은 $10000-2000=8000$, 재고는 $30-(-1)=31$이 된다. 이는 코드에서 도출한 결과이며, 강사가 이 음수 사례를 직접 설명했다는 뜻은 아니다. 음수 수량을 거부하려면 별도의 조건을 추가해야 한다. 그러한 개선을 원래 슬라이드에 이미 있던 기능처럼 제시하지 않는다.

### Getter(조회 메서드)와 Setter(설정 메서드): 통제된 접근 경로 만들기

Getter와 Setter는 private Attribute를 읽거나 바꾸는 일반 Method의 관례다. Java가 `getAge`, `setAge`라는 이름에 특별한 문법적 동작을 부여하는 것은 아니다. 이름과 구현 방식으로 역할을 드러내는 것이다. [M02 p.18] [STT 01:23:05]

```java
private int age;

public int getAge() {
    return age;
}

public void setAge(int age) {
    this.age = age;
}
```

Getter는 현재 Field 값을 반환한다. Setter의 왼쪽 `this.age`는 Field이고 오른쪽 `age`는 Parameter다. 앞에서 배운 `this`가 실제 접근 Method의 구현에 다시 사용된다.

**그림 읽기:** p.19의 왼쪽 그림은 외부에서 Public Field로 직접 이어지는 접근을 표시한다. 오른쪽 그림은 Private Field 앞에 Getter/Setter를 놓아 외부 접근이 그 경로를 통과하게 한다. 그림의 벌레와 차단 표시는 예상하지 못한 접근을 비유한다. Getter/Setter라는 이름만 붙이면 모든 오류가 자동으로 제거된다는 뜻은 아니다. [M02 p.19] [STT 01:23:59]

슬라이드의 Getter/Setter를 통해서만 접근한다는 설명은 선택한 외부 Interface에 관한 것이다. Class 내부의 다른 Method까지 해당 Field에 접근할 수 없다는 언어 규칙은 아니다. 예를 들어 앞의 `sell()`은 Getter나 Setter를 거치지 않고 자기 Class의 private Field를 변경한다.

Getter/Setter를 두는 목적은 단순 전달을 넘어선다. 자료는 세 용도를 구분한다. [M02 p.20]

| 용도 | 설계 방법 | 의미 |
|---|---|---|
| Read-only(읽기 전용) 또는 Write-only(쓰기 전용) 접근 | 외부에 Getter만 또는 Setter만 제공한다. | 읽기와 쓰기의 허용 여부를 따로 정한다. |
| Validation(유효성 검사) | 대입 전에 입력 조건을 확인한다. | 허용하지 않는 값으로 상태가 바뀌는 것을 막는다. |
| Tracing(접근 추적) | 읽기·설정 시 횟수나 기록을 남긴다. | Debugging(오류 분석)과 동작 관찰에 활용한다. |

모든 private Field에 Getter와 Setter를 반드시 둘 다 제공해야 하는 것은 아니다. 외부에 어떤 행동을 허용할지에 따라 선택한다. 또한 여기서 Read-only는 외부에 제공하는 접근 경로에 관한 말이지, Class 내부에서도 값이 영원히 바뀌지 않는다는 뜻은 아니다. [STT 01:24:58]

강사는 `age = -20`으로 바꾸려는 입력을 Setter에서 거부하는 예를 들었다. 이어 큰 나이 입력도 거부할 수 있다고 설명하다가 `100`을 예로 든 뒤 `1000`으로 스스로 정정했다. 이는 음수나 부적절한 입력을 거부할 수 있다는 동기 설명이며, 완성된 나이 허용 범위 규칙이 아니다. 필요한 조건은 해당 Class의 목적에 맞게 정의해야 한다. [STT 01:24:58] [STT 01:25:52]

개념 연결: [[concepts/getter-and-setter|Getter and Setter]], [[concepts/input-validation|Input Validation]]

### `null` 검사와 Short-circuit evaluation(단락 평가)

`null`은 Reference가 Object를 가리키지 않는 상태를 나타낸다. 빈 String `""`과는 다르다. 빈 String은 길이가 없는 String Object를 사용하는 경우이고, `null`에서는 Method를 호출할 대상 Object가 없다. 자료의 `setName()`은 두 입력을 모두 거부한다. [M02 p.21]

```java
class Person {
    private String name;

    public void setName(String name) {
        if (name == null || name.equals("")) {
            System.out.println("Name cannot be null or empty");
        } else {
            this.name = name;
        }
    }
}
```

조건의 두 부분은 서로 다른 판단을 한다.

- `name == null`: Reference가 Object를 가리키지 않는지 검사한다.
- `name.equals("")`: 유효한 String Object의 내용을 빈 문자열과 비교한다.

앞에서 String의 `==`는 내용 비교가 아니라고 배웠지만, `null`과의 비교에서는 바로 Reference 상태를 확인하려는 것이므로 `==`를 사용한다. STT의 주소가 0인지 확인한다는 설명은 개념적 단순화다. `null`을 Java에서 보장하는 물리적 주소 0이라고 외우지 않는다. [STT 01:26:50]

`||`는 왼쪽 조건이 `true`이면 오른쪽 조건을 평가하지 않는다. 따라서 `name`이 `null`인 경우 첫 검사가 참이 되고 `name.equals("")` 호출은 건너뛴다. 이 순서 덕분에 대상 Object가 없는 상태에서 Method를 호출하는 오류를 피한다. [STT 01:27:49] [STT 01:28:49]

| 입력 | `name == null` | `name.equals("")` 평가 | 처리 |
|---|---|---|---|
| `null` | `true` | 건너뜀 | 거부 메시지, Field 대입 없음 |
| `""` | `false` | `true` | 거부 메시지, Field 대입 없음 |
| 비어 있지 않은 String | `false` | `false` | Field에 저장 |

이해를 위한 잘못된 순서의 예시는 다음과 같다.

```java
if (name.equals("") || name == null) {
    // ...
}
```

`name`이 `null`이면 왼쪽에서 이미 Method 호출 오류가 발생하므로, 뒤에 적힌 `null` 검사가 보호해 주지 못한다. 조건에 필요한 검사들이 모두 들어 있다는 것만으로 충분하지 않고 평가 순서도 맞아야 한다.

거부된 입력에 대해 원본 Setter는 기존 Field를 지우지 않는다. 단지 대입을 실행하지 않는다. 따라서 기존에 유효한 이름이 저장되어 있었다면 그 값이 유지된다. 또한 `private String name;`의 기본값이 `null`이라는 설명을 모든 Local variable이 자동 초기화되거나 새 Object 자체가 `null`이라는 의미로 확대하지 않는다.

개념 연결: [[concepts/null|null]], [[concepts/short-circuit-evaluation|Short-circuit Evaluation]]

### `ChangableVar`: Getter/Setter에 접근 기록을 넣기

자료의 Class 이름은 `ChangableVar`다. 이 예제는 Getter와 Setter가 단순한 읽기·대입뿐 아니라 부가 동작도 수행할 수 있음을 보여 준다. 원본의 핵심 구조는 다음과 같다. [M02 p.22]

```java
class ChangableVar {
    private int valueToBeWatched;
    private int countOfChange = 0;
    private int readHistory = 0;

    public void setValue(int newval) {
        valueToBeWatched = newval;
        countOfChange++;
        System.out.println("This is change #" + countOfChange);
    }

    public int getValue() {
        readHistory++;
        return valueToBeWatched;
    }
}
```

`setValue()`는 새 값을 대입하고 `countOfChange`를 증가시킨다. `getValue()`는 `readHistory`를 증가시킨 뒤 값을 반환한다. 외부 코드는 평소처럼 값을 설정하거나 읽지만, 그 접근 경로 안에서 기록이 함께 남는다. 강의는 이러한 추적을 Debugging이나 기록 관리에 활용할 수 있다고 설명했다. [STT 01:29:46]

두 Counter의 의미는 변수 이름만으로 확정하면 안 된다. `readHistory`는 제시된 `getValue()` 호출 횟수를 센다. `countOfChange`는 이전 값과 새 값이 다른지 검사하지 않으므로, 같은 값을 다시 설정해도 증가한다. 즉 이 구현에서는 값이 실제로 달라진 횟수보다 Setter 실행 횟수에 가깝다.

p.23의 사용 예시는 첫 조회 후 `52`, `53`을 차례로 설정하고 다시 조회하는 흐름이다. 의도된 상태 변화는 다음과 같이 읽을 수 있다. [M02 p.23]

| 실행 | 저장된 값 | 설정 Counter | 조회 Counter |
|---|---:|---:|---:|
| 생성 직후 | 0 | 0 | 0 |
| 첫 `getValue()` | 0 | 0 | 1 |
| `setValue(52)` | 52 | 1 | 1 |
| `setValue(53)` | 53 | 2 | 1 |
| 두 번째 `getValue()` | 53 | 2 | 2 |

첫 값이 `0`인 것은 `valueToBeWatched`가 초기화되지 않은 `int` Field이기 때문이다. 첫 조회 결과와 조회 횟수는 각각 `0`, `1`이고, 두 번 설정한 뒤의 조회 결과와 조회 횟수는 `53`, `2`다. 강사는 이 긴 사용 예제의 상세 순회는 생략한다고 했으므로, 표의 단계별 해설은 인쇄 코드를 분석한 설명이지 모든 단계를 강사가 직접 낭독했다는 기록은 아니다. [STT 01:29:46] [STT 01:30:43]

**원본 코드 누락:** p.23에서는 `getReadHistory()`를 호출하지만 p.22의 Class 정의에는 해당 Method가 없다. 따라서 두 페이지를 그대로 합친 코드를 완전한 실행 가능 프로그램이라고 할 수 없다. 다음 Method를 추가하면 의도된 조회를 구현할 수 있지만, 이는 노트에서 명시적으로 보완하는 코드다.

```java
// 이해를 위한 보완: 원본 p.22에는 없는 Method
public int getReadHistory() {
    return readHistory;
}
```

이 보완 Method는 Counter를 반환할 뿐 증가시키지 않는다. 따라서 조회 이력 숫자를 확인하는 행위가 다시 `getValue()` 호출로 집계되지는 않는다. 원본의 누락과 보완 후 동작을 구분해야 한다.

개념 연결: [[concepts/access-tracing|Access Tracing]], [[concepts/getter-and-setter|Getter and Setter]]

### Class와 Object에서 Encapsulation으로 이어지는 흐름

전반부의 질문은 “어떤 대상이 어떤 상태를 가지며, 코드 한 줄이 그중 무엇을 바꾸는가?”이다. Class와 Object를 구분한 뒤 Constructor로 초기 상태를 만들고, `this`와 `static`으로 Member의 소속을 구별한다. 이어 Reference 대입과 여러 `swap`을 비교하면서 변수 자체의 변경과 공유 Object의 Field 변경을 분리한다. [M01 p.7] [M01 p.19] [M01 p.27] [M01 p.36] [M01 p.43]

후반부에서는 질문이 “그 상태를 외부에서 어떤 방법으로 바꾸도록 허용할 것인가?”로 이어진다. `FruitStore`의 관련 상태 변경을 `sell()`로 묶고, `AppleStore`의 접근 제한·성공 여부 반환·Getter와 Setter로 사용 방법을 구체화한다. 따라서 Encapsulation은 앞에서 배운 Class와 Method에 접근 규칙을 더하는 설계 과정으로 읽을 수 있다. [M02 p.5] [M02 p.11] [M02 p.14] [M02 p.18]

01:06:10의 정리는 수업 전체의 종료가 아니다. OOP 전반부를 정리한 뒤 Encapsulation으로 전환했으며, M02의 Packages 상세 설명은 마지막에 다음 수업으로 미뤘다. [STT 01:06:10] [STT 01:08:07] [STT 01:30:43]

## 핵심 요약

| 개념 | 독립적으로 기억할 핵심 |
|---|---|
| Object-Oriented Programming(객체 지향 프로그래밍) | 상태와 행동을 가진 Object들의 관계로 프로그램을 구성한다. Coffee Machine의 능력과 사용자의 실행 순서는 구분한다. |
| Class(클래스)와 Object(객체) | Class는 공통 설계다. 같은 설계로 만든 Object들도 각자의 Instance Field 값을 가질 수 있다. |
| Constructor(생성자)와 `this` | Constructor는 생성 과정의 초기화를 담당하고 Return type을 쓰지 않는다. `this`는 현재 Object를 명시한다. |
| `static` Member | Class에 속한다. 생성 Counter와 누적값의 의미는 변수 이름이 아니라 실제 갱신 코드로 판단한다. |
| 기본형 값과 기본값 | 기본형 값은 `2`처럼 변수에 저장되는 값이다. 기본값은 명시적으로 초기화하지 않은 Field에 적용되는 초기값이며, 미초기화 Local variable을 읽어도 된다는 뜻이 아니다. |
| Reference(참조) | `=`는 Reference 값을 복사하고, Reference에 대한 `==`는 같은 Object를 가리키는지 비교한다. |
| Call-by-Value(값에 의한 전달) | Java는 Primitive 값과 Reference 값 모두를 복사하여 전달한다. Parameter 재대입과 공유 Object의 Field 변경은 결과가 다르다. |
| String·Wrapper `swap` | String Parameter 교환은 호출자 변수를 바꾸지 않는다. Wrapper의 공유 Field를 교환하면 호출자도 바뀐 Field를 읽는다. |
| Garbage collector(가비지 컬렉터) | 도달할 수 없게 된 Object의 메모리가 회수 대상이 될 수 있다. Method 종료와 즉시 회수를 같은 사건으로 보지 않는다. |
| Encapsulation(캡슐화) | 내부 구현과 사용 방법을 나누고, 관련 상태가 지정된 행동을 통해 바뀌도록 접근을 통제한다. |
| Inheritance(상속)·Polymorphism(다형성) | 각각 공통 특성의 재사용과 구체적인 행동의 다양화로 소개되었다. 이번 범위는 동기와 개념 수준이다. |
| Getter·Setter | 일반 Method의 관례다. 읽기·쓰기 선택, Validation, Tracing을 구현할 수 있으며 두 Method를 항상 모두 제공할 필요는 없다. |
| `null`과 `||` | `name == null`을 먼저 검사하면 참일 때 `name.equals("")`를 건너뛴다. 검사 항목뿐 아니라 평가 순서도 중요하다. |

자료를 읽을 때는 특히 **대입 대상, 호출 대상, 접근 주체, 검사 순서**를 표시한다. 이 네 가지를 구분하면 `this`, `static`, 여러 `swap`, `sell()`, `setName()`을 서로 일관되게 설명할 수 있다.

## 회상·연습문제

### 1단계: 개념을 자신의 말로 회상하기

#### R01. Object의 종류와 Coffee Machine의 역할

자동차·은행 계좌·Linked list를 각각 어떤 종류의 entity로 볼 수 있는가? Coffee Machine의 분쇄·가열·혼합 능력과 사용자의 커피 제조 절차는 어떻게 다른가? [M01 p.4] [M01 p.5] [M01 p.6]

<details><summary>정답</summary>

자동차는 Physical entity, 은행 계좌는 Conceptual entity, Linked list는 Software entity의 예다. Object는 물리적인 물체에 한정되지 않는다.

분쇄·가열·혼합은 기계가 제공하는 능력이고, 재료를 준비하고 기계를 사용하는 것은 사용자의 실행 절차다. Abstraction은 내부 작업을 없애는 것이 아니라 사용자가 매번 알아야 할 세부 작업을 줄인다. Linked list의 내부 구현은 이번 설명 범위에 포함되지 않는다.

</details>

#### R02. Class·Object·Member와 `new`

Class와 Object의 관계를 설명하고, Attribute·Method·Member·Instance·Instantiate를 연결하라. `Car myCar = new Car();`에서 각 부분은 무엇인가? [M01 p.7] [M01 p.8] [M01 p.9] [M01 p.17]

<details><summary>정답</summary>

Class는 Object의 공통 설계다. Attribute는 상태를 저장하고 Method는 행동을 정의하며, 이번 자료에서는 둘을 Member라고 부른다. Instance는 Object를 가리키고 Instantiate는 Class의 Instance를 만드는 일이다.

`Car`는 자료형으로 사용한 Class 이름, `myCar`는 Reference 값을 저장하는 변수, `new Car()`는 새 Object를 생성하는 표현식이다. 변수 선언과 Object 생성은 구분해야 한다.

</details>

#### R03. Field 초기화와 Object별 상태

초기 `width`가 `10`인 Object에서 `car.width = 5`를 실행하면 무엇이 바뀌는가? Field 기본값을 Local variable에 그대로 적용할 수 있는가? 두 번의 `new Car()`로 만든 Object들의 색상이 서로 독립적인 이유는 무엇인가? [M01 p.10] [M01 p.11] [M01 p.12] [M01 p.14]

<details><summary>정답</summary>

해당 Object의 `width`가 `5`로 바뀐다. Class의 설계 전체를 변경하는 것은 아니다.

명시적으로 초기화하지 않은 Field에는 자료형에 맞는 기본값이 적용된다. 예제의 `boolean`은 `false`, `int`는 `0`, `float`는 `0.0`, Reference는 `null`이다. 초기화하지 않은 Local variable을 바로 읽어도 된다는 뜻은 아니다. 자료의 `char` 표기를 유효한 빈 문자 리터럴 `''`로 읽어서도 안 된다.

별도의 `new` 호출은 별개의 Object를 만들므로 각 Object가 자신의 Instance Field를 가진다. 명시적 초기화는 이러한 출발 상태를 코드에 드러내어 이해와 유지보수를 돕는다.

</details>

#### R04. Method의 호출 대상과 재사용

같은 `getSpeed()`를 호출해도 두 자동차에서 다른 결과가 나오는 이유는 무엇인가? `speedAndUnit()`과 `printSpeedAndUnit()`을 나누면 무엇을 재사용하며, 출력과 반환은 어떻게 다른가? [M01 p.15] [M01 p.16] [M01 p.25]

<details><summary>정답</summary>

각 호출이 서로 다른 Object의 `speed`를 읽기 때문이다. Method 이름뿐 아니라 호출 대상 Object를 확인해야 한다.

`speedAndUnit()`은 속도와 단위를 결합한 String을 반환하여 문자열 구성 작업을 재사용하게 한다. `printSpeedAndUnit()`은 그 반환값을 화면에 출력한다. `void` Method의 출력은 호출자에게 값을 반환하는 것과 다르다. 제시된 `this.speedAndUnit()`에서는 `this`를 생략해도 같은 Instance Method를 호출한다.

</details>

#### R05. Constructor의 표기와 초기화 선택

Constructor 앞에 `void`를 붙이지 않는 이유는 무엇인가? 자료의 `Car(int w)`와 `Car(int w, String c)`는 어떤 초기화 선택을 제공하는가? [M01 p.19] [M01 p.21] [M01 p.22]

<details><summary>정답</summary>

Constructor는 Return type을 선언하지 않는 구성 요소다. 반환값이 없다는 이유로 `void`를 붙이는 일반 Method와 다르며, 이름은 Class 이름과 같다.

두 Constructor는 모두 `weight`를 설정한다. 두 인자 Constructor는 `color`도 입력값으로 설정하고, 한 인자 Constructor는 `color`의 초기값 `"unknown"`을 유지한다. 제시된 Class에는 인자를 받지 않는 Constructor가 없다. Constructor 사이의 호출 규칙은 후속 설명으로 미뤄졌다.

</details>

#### R06. `this`가 필요한 경우와 필요하지 않은 경우

`speed`라는 Parameter가 있을 때 `speed = speed`와 `this.speed = speed`는 어떻게 다른가? 반대로 M01 p.24에서 `color = "blue"`가 Field를 바꾸는 이유는 무엇인가? [M01 p.24] [M01 p.26]

<details><summary>정답</summary>

같은 이름의 Parameter가 있으면 이름만 쓴 `speed`는 그 Parameter를 가리킨다. `speed = speed`는 Parameter의 자기 대입이고, `this.speed = speed`는 현재 Object의 Field에 Parameter 값을 저장한다.

p.24에는 같은 이름의 Local variable이나 Parameter 선언이 없다. 따라서 `this.color`와 `color`는 같은 Field를 가리키며 마지막 Field 값은 `"blue"`다. `this`를 생략했다고 Local variable이 새로 만들어지지 않는다. 이 코드와 충돌하는 발화의 의도는 검증 필요다.

</details>

#### R07. `static` 값은 무엇을 세는가?

자동차별 브랜드와 전체 생성 횟수를 각각 어디에 두는 것이 자연스러운가? M01 p.30의 `num`과 `totalMile`은 정확히 무엇을 누적하는가? [M01 p.27] [M01 p.30]

<details><summary>정답</summary>

브랜드는 개별 Object의 상태이고 전체 생성 횟수는 Class 수준의 공통 상태로 표현할 수 있다.

`num`은 Constructor 실행 횟수를 센다. Object가 사용되지 않게 되었다고 자동 감소하지 않는다. `totalMile`은 `setMile()`에 전달된 값을 매번 더한다. 같은 Object에 다시 설정하면 현재 모든 `mile` Field의 합과 달라질 수 있다. 두 `static int` Field의 기본값은 `0`이다.

</details>

#### R08. `static` 접근 오류와 `main`

`static` Method의 `return fuel;`에서 `fuel`이 Instance Field라면 왜 문제가 되는가? 명시적인 Object를 통한 접근도 금지되는가? `main` 선언의 구성 요소를 설명하라. [M01 p.31] [M01 p.32] [M01 p.37]

<details><summary>정답</summary>

직접 참조한 `fuel`이 어느 Object의 Field인지 정해지지 않았기 때문이다. 이는 컴파일 단계의 문제다. 유효한 Object를 가리키는 `car`가 있다면 `car.fuel`처럼 대상을 지정하는 접근은 가능하다. Instance Method에서 `static` Member를 사용하는 것도 가능하다.

`public static void main(String[] args)`에서 `public`은 접근 수준, `static`은 Class 수준의 Method, `void`는 반환값 없음, `main`은 Method 이름, `String[] args`는 문자열 배열 Parameter를 나타낸다.

</details>

#### R09. Reference 대입·비교와 메모리 도식

같은 내용을 넣어 `new String(...)`을 두 번 실행한 결과를 `==`로 비교하면 왜 `false`인가? `str3 = str1`은 무엇을 복사하는가? `int x = 2`의 기본형 값과 명시적으로 초기화하지 않은 `int` Field의 기본값은 어떻게 다른가? Primitive/Reference 그림과 자료형 분류 그림에서 주의할 점은 무엇인가? [M01 p.12] [M01 p.34] [M01 p.35] [M01 p.36] [M01 p.46] [M01 p.47] [M01 p.48]

<details><summary>정답</summary>

두 `new`가 서로 다른 String Object를 만들기 때문이다. Reference에 대한 `==`는 내용이 아니라 같은 Object를 가리키는지 비교한다. `str3 = str1`은 Reference 값을 복사하므로 새 Object를 만들지 않는다.

Primitive 변수는 기본형 값 자체를, Reference 변수는 Object로 이어지는 Reference 값을 저장한다. `int x = 2`에서 저장값 `2`는 명시적으로 지정한 기본형 값이지 자동 기본값이 아니다. 명시적으로 초기화하지 않은 `int` Field에는 기본값 `0`이 적용된다. 기본형 값은 저장값의 종류를, 기본값은 초기화 규칙을 설명하므로 두 말을 혼용하지 않는다. 미초기화 Local variable을 그대로 읽을 수 있다는 뜻도 아니다.

변수 이름·변수의 저장값·참조 대상 Object를 구분해야 하며 그림을 물리적 메모리 배치의 보장으로 읽지 않는다. p.46에서 `Floating-Point`를 `Integral Value` 아래에 둔 연결은 오류다. `float`·`double`을 정수 유형으로 분류하지 않는다.

</details>

#### R10. Primitive `swap`과 인쇄 오류

의도된 `temp = a; a = b; b = temp;`는 호출자 변수를 바꾸는가? 마지막 줄이 `a = temp`라면 Method 내부의 결과는 어떻게 달라지는가? 초깃값은 `a = 2`, `b = 3`이다. [M01 p.37] [M01 p.39] [M01 p.49] [M01 p.50]

<details><summary>정답</summary>

의도된 코드의 Parameter는 마지막에 `3`, `2`가 되지만 호출자 변수는 `2`, `3`으로 남는다. Parameter가 호출자 값의 복사본이기 때문이다.

마지막 줄이 `a = temp`라면 Parameter도 최종적으로 `2`, `3`이 된다. 따라서 p.50의 인쇄 코드와 `3`, `2`를 보여 주는 그림은 서로 맞지 않는다. 호출자 값이 유지된다는 결론과 Parameter의 최종값은 따로 판단해야 한다.

</details>

#### R11. `IntHolder`, String, Wrapper의 차이

세 예제에서 호출자가 바뀐 상태를 보거나 보지 못하는 이유를 대입 대상으로 설명하라. Java가 Reference를 전달한다는 이유로 호출자 변수 자체가 Parameter와 같아지는가? 강사는 많은 Attribute와 배열을 담은 Object 전체를 호출 때마다 복사한다고 가정하여 어떤 비용을 설명했는가? [M01 p.41] [M01 p.42] [M01 p.53] [M01 p.56] [STT 45:28]

<details><summary>정답</summary>

Java는 Reference 값도 복사한다. 호출자 변수와 Parameter는 별개의 변수이며 같은 Object를 가리킬 수 있다.

- `IntHolder`의 `a.value = ...`는 공유 Object의 정수 Field를 바꾼다.
- String의 `a = ...`는 Parameter 변수의 Reference 값을 바꾼다.
- Wrapper의 `a.s = ...`는 공유 Wrapper 안의 Reference Field를 바꾼다.

따라서 첫 번째와 세 번째는 호출자도 변경된 Field를 읽지만, String Parameter 교환은 호출자 변수의 Reference를 교환하지 않는다. Wrapper에서도 String 내용 자체가 바뀌는 것은 아니다.

강사는 수백 개의 Attribute와 수백 개의 배열을 담을 수 있는 큰 Object를 매 호출마다 통째로 복사한다면 사용 가능한 메모리가 크게 줄어 비효율적이라고 설명했다. 이는 가상의 전체 복사와 Reference 값의 복사를 대비한 동기 설명이다. 실제 Java 호출에서 Object 전체가 복사되거나 호출자 변수 자체가 Parameter와 공유된다는 뜻은 아니다. [STT 45:28]

</details>

#### R16. Access modifier의 적용 한계

<details><summary>정답</summary>

Modifier를 생략하면 같은 Package에서 접근하는 default access이며 실제 `public` 선언과 다르다. 이 위치에 `default`라는 단어를 적는 것도 아니다.

### 기출 스타일 기반 예상·변형 문제

#### 연습 P01

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** Class와 Object의 관계 설명.

**스타일 근거:** Class와 Object를 설명하게 하는 요구를 가져왔다. 아래의 오개념 진단 조건은 새로 추가했다. [EX:cp_2025_1_midterm_q01 p.1]

이해를 위한 예시로 `Car` 설계에 `color`, `fuel`, `refuel()`이 정의되어 있고, 그 설계로 만든 두 Object의 색상이 각각 빨강과 파랑이라고 하자.

1. Class·Object·Attribute·Method를 각각 식별하라.
2. “두 자동차의 색상이 다르므로 서로 다른 Class여야 한다”는 설명을 고쳐라.
3. 같은 Class를 재사용할 때 무엇을 다시 작성하지 않아도 되는지 설명하라.

<details><summary>풀이와 채점 포인트</summary>

`Car`는 Class이고 두 자동차는 각각 Object 또는 Instance다. `color`와 `fuel`은 Attribute이며 `refuel()`은 Method다. 이 Attribute와 Method 정의를 합쳐 이번 자료의 Member라고 부른다.

두 Object가 같은 정의를 따르더라도 각자의 Instance Field 값은 다를 수 있다. 따라서 색상이 다르다는 사실만으로 Class가 달라야 하는 것은 아니다.

재사용하는 것은 상태와 행동의 공통 정의다. Object를 만들 때마다 `color`라는 Attribute의 존재나 `refuel()`의 행동 정의를 다시 작성할 필요가 없다. 모든 Object가 하나의 색상 값을 공유한다는 뜻은 아니다.

**채점 포인트 — 4점:** Class/Object 구분 1점, Attribute/Method 식별 1점, 공통 정의와 개별 값 구분 1점, 재사용의 대상을 정확히 설명 1점.

3. “기계를 도입했으므로 분쇄·가열·혼합 계산이 프로그램에서 사라진다”는 주장을 평가하라.
4. Procedural style의 절차가 틀린 것은 아닌데도 이러한 구조를 도입하는 이유를 설명하라.

<details><summary>풀이와 채점 포인트</summary>

자동차는 Physical entity, 은행 계좌는 Conceptual entity, Linked list는 Software entity로 분류할 수 있다.

**채점 포인트 — 5점:** entity 분류 1점, 능력과 절차 구분 1점, 내부 계산이 남는다는 설명 1점, 관리 복잡성과의 연결 1점, Procedural style 자체를 잘못된 방식으로 단정하지 않음 1점.

```java
class Foo {
```

<details><summary>풀이와 채점 포인트</summary>

`Car` Object는 두 개이며 해당 Reference 변수는 `a`, `b`, `c` 세 개다. `c = a`는 새 Object를 만들지 않는다.

```text
12
0
12
false
true
```

**일반 연습 — 관련 기출 근거 없음**

**학습목표·범위:** Parameter 목록에 따른 Constructor 선택, Field와 Parameter 구분, 문자열 구성 Method의 재사용을 설명한다. [M01 p.19] [M01 p.21] [M01 p.22] [M01 p.24] [M01 p.25] [M01 p.26]

**선수 개념:** Field, Parameter, Constructor, `this`, 반환과 출력. **접근 상태: 현재 접근 가능.**

다음은 이해를 위한 예시다. 첫 Constructor에는 의도적으로 잘못된 대입을 넣었다.

```java
class Car {
    int speed = 30;
    String color = "unknown";

    Car(int speed) {
        speed = speed;
    }

    Car(int speed, String color) {
        this.speed = speed;
        this.color = color;
    }

    String speedAndUnit() {
        return speed + " km/h";
    }

    void printSpeedAndUnit() {
        System.out.println(this.speedAndUnit());
    }

    void changeColor() {
        this.color = "red";
        color = "blue";
    }
}
```

Method 내부에서 다음을 실행한다.

```java
Car a = new Car(60);
Car b = new Car(90, "green");

a.printSpeedAndUnit();
b.printSpeedAndUnit();
a.changeColor();
```

1. 두 출력과 마지막의 두 Object 색상을 구하라.
2. 첫 Constructor가 받은 속도를 저장하도록 한 줄을 고쳐라.
3. 현재 정의로 `new Car()`를 사용할 수 있는가? Constructor 앞에 `void`를 붙이는 것은 올바른 수정인가?
4. `speedAndUnit()`을 별도로 둔 이점과 `printSpeedAndUnit()`의 반환형을 설명하라.

<details><summary>풀이와 채점 포인트</summary>

첫 Constructor의 두 `speed`는 모두 Parameter다. 따라서 첫 Object의 Field는 `30`으로 남는다. 두 번째 Constructor는 Field에 입력값을 저장한다.

```text
30 km/h
90 km/h
```

`changeColor()`에는 같은 이름의 Local variable이나 Parameter가 없으므로 두 대입이 같은 Field를 바꾼다. 마지막 색상은 `a`가 `"blue"`, `b`가 `"green"`이다.

수정할 대입은 다음과 같다.

```java
this.speed = speed;
```

제시된 정의에는 인자를 받지 않는 Constructor가 없으므로 `new Car()`를 사용할 수 없다. Constructor에는 Return type을 적지 않으며 `void`를 붙이는 수정도 올바르지 않다.

`speedAndUnit()`은 속도와 단위의 문자열 구성을 재사용한다. `printSpeedAndUnit()`은 그 결과를 출력하는 `void` Method다. 해당 호출의 `this`는 현재 Object의 Method를 명시하며 이 예제에서는 생략해도 된다.

**채점 포인트 — 6점:** 출력 1점, 색상과 이름 해석 1점, 대입 수정 1점, Constructor 표기·호출 가능성 1점, 반환·출력 구분 1점, Method 재사용 설명 1점.

이해를 위한 예시로 본문의 M01 p.30 `Car` 정의를 사용한다. 시작할 때 생성된 Object가 없고 `num`, `totalMile`은 `0`이다. 다음 `main`은 이를 사용하는 별도 Class 안에 둔다.

```java
public static void main(String[] args) {
    Car a = new Car();
    Car b = new Car();

    a.setMile(4);
    b.setMile(7);
    a.setMile(6);

    System.out.println(Car.num);
    System.out.println(Car.totalMile);
    System.out.println(a.mile + b.mile);
}
```

1. 세 출력을 구하라.
2. `totalMile`을 “현재 모든 자동차의 `mile` 합”이라고 부를 수 있는지 설명하라.
3. `main` 선언의 다섯 구성 요소를 설명하라.
4. 같은 `Car` 안에 `static int readMile() { return mile; }`을 추가하면 왜 실패하는가? 유효한 Object를 Parameter로 받아 읽는 형태를 제시하라.

<details><summary>풀이와 채점 포인트</summary>

Constructor가 두 번 실행되므로 `num`은 `2`다. `totalMile`은 전달값을 계속 더하므로 $4+7+6=17$이다. 현재 Field 값은 `a.mile = 6`, `b.mile = 7`이므로 합은 `13`이다.

```text
2
17
13
```

따라서 `totalMile`은 이 코드에서 Setter에 전달된 값의 누적합이다. `num`도 생성 횟수이며 현재 살아 있는 Object 수를 자동 추적하지 않는다.

`public`은 접근 수준, `static`은 Class 수준의 Method, `void`는 반환값 없음, `main`은 이름, `String[] args`는 문자열 배열 Parameter다.

```java
static int readMile(Car target) {
    return target.mile;
}
```

이 코드는 `target`이 유효한 `Car` Object를 가리킨다는 조건에서 사용한다. “`static` Method는 어떠한 Instance Field도 사용할 수 없다”는 설명은 지나치게 넓다.

#### 연습 P06

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** Primitive Parameter와 공유 `IntHolder` Field.

**일반 연습 — 관련 기출 근거 없음**

**학습목표·범위:** Call-by-Value와 공유 Object의 Field 변경을 구분하고 마지막 대입의 차이를 추적한다. [M01 p.37] [M01 p.39] [M01 p.40] [M01 p.41] [M01 p.42] [M01 p.49]  
**요구 능력:** 호출자·Parameter·Field의 상태를 분리한 순차 추적.  
**선수 개념:** Primitive/Reference 구분, Constructor, 대입. **접근 상태: 현재 접근 가능.**

다음은 이해를 위한 예시다. 각 Method는 적절한 Class 안에 정의한다.

```java
static void swapNumbers(int a, int b) {
    int temp = a;
    a = b;
    b = temp;
}

static void swapFields(IntHolder a, IntHolder b) {
    int temp = a.value;
    a.value = b.value;
    b.value = temp;
}
```

`IntHolder`는 본문처럼 생성 인자를 `value`에 저장한다.

1. 호출자의 `x = 4`, `y = 9`로 `swapNumbers(x, y)`를 실행한다. 반환 직전 Parameter와 반환 뒤 호출자 값을 각각 구하라.
2. 서로 다른 두 `IntHolder`의 초기 Field가 `4`, `9`일 때 `swapFields()` 뒤의 Field를 구하라.
3. 첫 Method의 마지막 줄만 `a = temp`로 바꾸면 결과가 어떻게 달라지는가?
4. 두 Method의 전달 방식이 서로 다른지 설명하라.

<details><summary>풀이와 채점 포인트</summary>

첫 Method의 Parameter는 다음과 같이 바뀐다.

| 단계 | `a` | `b` | `temp` |
|---|---:|---:|---:|
| 호출 직후 | 4 | 9 | 아직 없음 |
| `temp = a` | 4 | 9 | 4 |
| `a = b` | 9 | 9 | 4 |
| `b = temp` | 9 | 4 | 4 |

호출자의 `x`, `y`는 계속 `4`, `9`다.

두 번째 Method는 공유 Object의 Field를 바꾸므로 호출자도 `9`, `4`를 읽는다. Parameter의 Reference 값이 호출자와 같은 두 Object로 이어지기 때문이다.

마지막 줄을 `a = temp`로 바꾸면 Parameter가 `4`, `9`로 끝난다. 호출자 값은 여전히 `4`, `9`다. 이는 자료의 인쇄 오류를 읽을 때도 필요한 구분이다.

두 경우 모두 Java는 값을 복사한다. 첫 번째에서는 정수 값을, 두 번째에서는 Reference 값을 복사한다. Object 전체를 복사하거나 호출자 변수 자체를 Parameter로 공유하는 것이 아니다.

**채점 포인트 — 5점:** Parameter 추적 1점, 호출자 값 유지 1점, 공유 Field 결과 1점, 마지막 줄 변형 1점, 일관된 Call-by-Value 설명 1점.

</details>

#### 연습 P07

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** String Reference 재대입과 Wrapper의 Reference Field 변경.

**일반 연습 — 관련 기출 근거 없음**

**학습목표·범위:** 호출자 변수·Parameter·Wrapper·String의 연결을 나누고 바뀌는 대상을 식별한다. [M01 p.34] [M01 p.51] [M01 p.52] [M01 p.53] [M01 p.54] [M01 p.55] [M01 p.56]  
**요구 능력:** 두 단계 Reference 추적과 대입 대상 비교.  
**선수 개념:** Call-by-Value, Field, Reference 비교. **접근 상태: 현재 접근 가능.**

다음은 이해를 위한 예시다. 이 연습의 `Wrapper`는 별도 Class로 정의한 창작 예시이며, 원본 p.54의 중첩 선언을 그대로 재현한 것이 아니다.

```java
class Wrapper {
    String s;

    Wrapper(String s) {
        this.s = s;
    }
}
```

두 Method는 별도의 실행용 Class 안에 둔다.

```java
static void swapStrings(String a, String b) {
    String temp = a;
    a = b;
    b = temp;
}

static void swapWrapperFields(Wrapper a, Wrapper b) {
    String temp = a.s;
    a.s = b.s;
    b.s = temp;
}
```

호출자는 다음 상태로 시작한다.

```java
String s1 = new String("left");
String s2 = new String("right");
String saved = s1;

Wrapper w1 = new Wrapper(s1);
Wrapper w2 = new Wrapper(s2);

swapStrings(s1, s2);
swapWrapperFields(w1, w2);
```

1. 마지막의 `s1`, `s2`, `w1.s`, `w2.s`가 가리키는 내용을 순서대로 쓰라.
2. `s1 == saved`의 결과를 구하라. String 내용 자체가 바뀌었는가?
3. 새로운 `"same"` String을 `new`로 두 번 만들어 `==`로 비교하면 무엇이 나오는가?
4. 새로 초기화한 두 Wrapper에서 마지막 대입을 `a.s = temp`로 바꾸면 Field가 교환되는가?

<details><summary>풀이와 채점 포인트</summary>

결과는 다음과 같다.

| 접근 | 가리키는 String의 내용 |
|---|---|
| `s1` | `"left"` |
| `s2` | `"right"` |
| `w1.s` | `"right"` |
| `w2.s` | `"left"` |

`swapStrings()`는 Parameter 변수만 재대입한다. `swapWrapperFields()`는 호출자와 공유하는 두 Wrapper의 `s` Field를 바꾼다.

`s1 == saved`는 `true`다. 두 변수의 Reference는 그대로이며 String 내용 자체도 변경되지 않았다. Wrapper로 이어지는 호출자 Reference도 그대로이고 그다음 단계인 `s` Field만 바뀌었다.

`new String("same")`을 두 번 실행하면 내용이 같더라도 서로 다른 Object이므로 `==`는 `false`다.

마지막 대입을 `a.s = temp`로 바꾸면 첫 Field를 원래 Reference로 되돌리고 두 번째 Field는 처음부터 변경하지 않는다. 따라서 새로 초기화한 두 Wrapper의 Field는 원래 `"left"`, `"right"`로 남는다.

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**학습목표·범위:** Object를 생성한 Method의 종료와 Object에 도달할 수 없게 되는 조건을 구분한다. [M01 p.44] [STT 48:25] [STT 49:18]

**선수 개념:** `new`, Reference, `static` Field. **접근 상태: 현재 접근 가능.**  
**스타일 근거:** 역할과 적용 조건을 함께 설명하는 요구를 가져와, 외부에 Reference를 남기는 경우와 남기지 않는 경우를 추가했다. [EX:cp_2025_1_midterm_q03 p.2]

다음은 이해를 위한 예시다. 같은 Class 안에 다음 Field와 Method가 있고, `IntHolder`는 앞서 설명한 형태라고 하자.

```java
static IntHolder saved;

static void build(boolean keep) {
    IntHolder local = new IntHolder(4);

    if (keep) {
        saved = local;
    }
}
```

다른 Reference 저장이나 동시 실행은 없으며, 다음 문장을 순서대로 실행한다.

```java
saved = null;
build(false);
build(true);
saved = null;
```

각 `build()`가 만든 Object를 생성 순서대로 A, B라고 부른다.

1. 첫 `build(false)`가 반환한 뒤 A의 상태를 설명하라.
2. `build(true)`가 반환한 직후 B에 접근할 수 있는 경로를 쓰라.
3. 마지막 대입 뒤 B의 상태와 즉시 회수 여부를 설명하라.

<details><summary>풀이와 채점 포인트</summary>

A는 `local` 외의 곳에 Reference를 남기지 않았으므로 첫 호출이 반환한 뒤 접근 경로가 남지 않는다. 따라서 회수 대상이 될 수 있다.

B는 `saved`에 Reference를 저장했으므로 두 번째 호출이 반환해도 `saved`를 통해 접근할 수 있다. Method가 끝났다는 사실만으로 B를 더 이상 사용하지 않는다고 판단할 수 없다.

마지막 `saved = null`은 주어진 조건에서 B로 이어지는 남은 경로를 제거한다. B도 회수 대상이 될 수 있지만 그 줄 실행 즉시 반드시 회수된다고 보장하지 않는다. Garbage collector의 역할은 사용하지 않게 된 Object의 메모리 회수이며, 이 설명으로 실제 회수 시각을 결정할 수는 없다.

**채점 포인트 — 4점:** A의 경로 부재 1점, B의 유지 경로 1점, 마지막 대입의 의미 1점, 회수 가능성과 시점 구분 1점.

</details>

```java
public int d;
```

유효한 `Store` Object가 있고, 아래 Class들은 서로 상속 관계도 중첩 관계도 없다.

- 위치 A: `Store` 내부의 Instance Method
- 위치 B: 같은 Package의 별도 Class
- 위치 C: 다른 Package의 별도 Class

2. `b`의 선언에 `default`를 추가해야 하는지 설명하라.

<details><summary>풀이와 채점 포인트</summary>

| 접근 위치 | `a`: `private` | `b`: modifier 생략 | `c`: `protected` | `d`: `public` |
|---|---|---|---|---|
| A: 선언 Class 내부 | 가능 | 가능 | 가능 | 가능 |
| B: 같은 Package의 별도 Class | 불가 | 가능 | 가능 | 가능 |

**새로 만든 연습 — 실제 기출·공식 정답이 아님**

**주제:** `ChangableVar`의 호출 횟수와 실제 값 변경 횟수.

**일반 연습 — 관련 기출 근거 없음**

**학습목표·범위:** Getter/Setter의 Counter를 순서대로 추적하고 원본의 누락을 구분한다. [M02 p.22] [M02 p.23] [STT 01:29:46]  
**요구 능력:** 상태 표 작성, Counter 의미 해석, 누락 Method 식별.  
**선수 개념:** Field 기본값, Getter, Setter, 증가 연산. **접근 상태: 현재 접근 가능.**

이해를 위한 예시로 본문의 `ChangableVar`를 사용한다. 새 Object의 값과 두 Counter는 `0`이다.

- `setValue(n)`은 대입 후 `countOfChange`를 1 증가시킨다.
- `getValue()`는 `readHistory`를 1 증가시킨 뒤 값을 반환한다.
- 이번 연습에서는 원본에 없는 다음 Method를 **명시적으로 보완**한다.

```java
public int getReadHistory() {
    return readHistory;
}
```

다음을 순서대로 실행한다.

```java
var.setValue(7);
var.getValue();
var.setValue(7);
var.getValue();
var.getReadHistory();
var.getReadHistory();
```

1. 각 단계의 저장값과 두 Counter를 구하라.
2. Getter들의 반환값을 순서대로 쓰라.
3. `countOfChange`를 실제 값이 달라진 횟수라고 설명해도 되는가?
4. 보완 Method 없이 원본 p.22–23을 합친 코드의 문제를 설명하라.

<details><summary>풀이와 채점 포인트</summary>

| 실행 | 저장값 | `countOfChange` | `readHistory` | 반환값 |
|---|---:|---:|---:|---|
| `setValue(7)` | 7 | 1 | 0 | 없음 |
| `getValue()` | 7 | 1 | 1 | 7 |
| `setValue(7)` | 7 | 2 | 1 | 없음 |
| `getValue()` | 7 | 2 | 2 | 7 |
| `getReadHistory()` | 7 | 2 | 2 | 2 |
| `getReadHistory()` | 7 | 2 | 2 | 2 |

두 번째 Setter에서도 Counter가 증가한다. 실제 값은 처음 `0`에서 `7`로 한 번 바뀌었지만 Setter는 두 번 호출되었으므로 `countOfChange`는 `2`다. 변수 이름만 보고 의미를 확정할 수 없다.

보완한 `getReadHistory()`는 Counter를 반환할 뿐 증가시키지 않는다. 따라서 이 Method를 읽는 행위가 `getValue()` 호출 횟수에 포함되지 않는다.

원본 p.23에는 `getReadHistory()` 호출이 있지만 p.22에는 그 정의가 없다. 그대로는 해당 Method를 찾지 못하는 컴파일 문제가 있다. 위 Method를 추가한 결과와 원본 코드를 구분해야 한다.

**채점 포인트 — 5점:** 상태 표 2점, 반환값 1점, 호출 횟수와 값 변경 횟수 구분 1점, 원본 누락과 보완 구분 1점.
